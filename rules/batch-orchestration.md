# 批量编排规则（batch-* 技能的公共契约）

`batch-*` 技能把一个既有的单会话技能扩展为**一次会话覆盖多份文档 / 多个问题**：主会话（orchestrator）把范围切成分片，分派给若干 subagent（worker）并行或按波次执行，收尾统一合并。目的有两个：

1. **覆盖面**——一次跑完一批输入，交叉核对能发现单次运行看不见的跨区问题（两份草稿互相矛盾、两个 FR 切出同一行为、两份蓝图对同一共享部件给出不同形状）。
2. **省重复 token**——多步链路里反复传递同一批背景文档的成本，收敛为每个 worker 只读它那一片所需的上下文。

**批量绝不等于自动化拍板。** 单会话技能里所有「必须 interview / 必须停下询问」的门，在批量模式下**一个都不放松**——只是把「问」从逐次分散，改为**一场合并的大 interview**。这是本文件的第一铁律。

## 角色

- **orchestrator（主会话，即运行 `/batch-*` 的会话）**：确定范围与分区、分派 worker、合并问题并主持 interview、统一写共享台账、出总报告。它自己不做分片内的实质工作。
- **worker（subagent）**：执行**对应的单会话技能**（在派单 prompt 里点名技能与本文件），范围锁定在分派给它的分片。worker 之上叠加下方「worker 契约」的三条覆盖。

## 三条铁律

**① 不替用户拍板。** worker 校验出的每一个 🔴 / 🟠 / `[取向选择]`，都必须进入合并 interview 由用户裁决；不许用「按最合理解读先写下去」「记进 Open questions 备注」绕过。用户明确授权「按推荐来」时，按单会话技能的既有规则处理（标 `[采纳推荐 — 待复核]` 并留在待决清单），**不当作用户拍板**。

**② 共享台账单写者。** 多个 worker 都会触碰的文件——各库 `*_index.md`（inbox / handoffs / requirements / answer-logs / blueprints / 类型档案台账）、`open-questions.md` 与 `open-questions/` 分片、`update-log.md`——**一律由 orchestrator 在收尾阶段统一写入**。worker 只产出「台账行 / 增删条目」的文本，随报告交回。worker 只写分派给它的**独占文件**（它自己的草稿 / handoff / FR / 蓝图 / 条目 / answer-log 文件）。
> 理由：并行写同一份台账必然互相覆盖；而这些台账本就有「单写者」纪律（`answer-logs/`、「derive 就绪度」小节皆是先例）。

**③ 写入面先分区，分不开就串行。** 分派前，orchestrator 先推算每个分片的**写入目标文件集合**（含主题文档）。两个分片会写同一文件 → 合并给同一个 worker，或拆成先后波次串行。推算不出、拿不准 → 串行。**绝不让两个并行 worker 写同一份文件。**

## 两阶段执行（凡底层技能带 interview / 澄清门的，强制）

```
Phase A（并行 · 只读）   worker 执行技能的读取与校验步骤，不写任何文件；
                        产出：发现分级（🔴/🟠/🔵）+ 问题清单 + 拟改动文件清单 → run 目录
     ↓
合并 interview（orchestrator）
                        去重合并全部问题 → AskUserQuestion 分轮问齐 → answers 落盘
     ↓
Phase B（按分区并行 / 按波次串行）
                        worker 拿着 answers 执行技能的写入步骤；
                        answers 视同用户裁决，优先级高于原始输入
```

- **Phase A 的产物是结构化问题清单**，每条含：来源分片、级别（🔴/🟠/取向）、问题陈述、可选项与各自后果、推荐项与理由（依据既有设计）。
- **orchestrator 在合并时追加一类跨分片检查**：比对各 worker 的发现与拟写入要点，两个分片互相矛盾（对同一对象给出不同结论 / 形状）→ 作为一条新的 🔴 进 interview。这是批量相对逐次运行的独有价值，不要省。
- **合并 interview 没问完，不得进入 Phase B。** 分轮问（每轮 ≤4 问，按阻断程度排序——先问会改变路由 / 机制 / 契约形状的），全部问完再落笔。
- **答复引入新冲突 → 回到出题**，补一轮 interview，不由 orchestrator 或 worker 自行消化。
- 底层技能**没有** interview 门的（如 derive / breakdown），跳过合并 interview，但 Phase A 的「拟写入推算 + 跨分片核对」照做，就绪门拦下的项如实进总报告。

## 问题合并判据

- **同一问题**（同一对象 + 同一待决点）被多个 worker 提出 → 合并为一条，列出全部来源分片；答案回填给每个来源。
- **相似但对象不同**（两份草稿各自问自己的 TTL / 数值）→ **不合并**成一题——答案未必相同；编组相邻呈现即可。
- **一题的答案会改变另一题的前提** → 排前面先问；必要时分轮。
- 每题呈现时带上 worker 已给出的选项、后果与推荐（有草稿 / 方案的连方案要点一起给），让用户在一处看全。

## run 目录（过程档案）

每次批量运行建 `.claude/batch-runs/<YYYY-MM-DD>-<slug>/`，内放：`plan.md`（范围、分区、波次）、`questions-<分片>.md`（Phase A 产物）、`questions-merged.md`、`answers.md`、`report-<分片>.md`。

- 它是**过程档案，不是任何事实来源**——设计库与台账不得回链它；运行结束后可随时整目录删除。
- 派单 prompt 里把 run 目录路径与分片名交给 worker；worker 的问题与报告都落在这里，不落设计库。

## 失败与范围纪律

- 某个 worker 失败 / 产出越界（写了不该写的文件）→ 记录、不阻塞其余分片；总报告里如实点名，越界写入由 orchestrator 回滚或提请用户处理。**绝不因部分失败静默缩小已确认的范围。**
- 批次范围本身要**用户确认**：参数未显式给全清单时，orchestrator 先枚举候选（含库归属），列给用户圈选后再分派——这与「绝不静默默认」同一条纪律。
- 报告与单会话技能的输出形态对齐，**按库、按分片分区**列出改动文件；interview 摘要（问了什么、用户如何裁决）单列一节。

## worker 契约（对单会话技能的三点覆盖）

worker 执行单会话技能时，以下三点覆盖原技能文本，其余步骤原样遵守：

1. **不调用 `AskUserQuestion`**（subagent 无法触达用户）。原技能要求 interview / 澄清检查点处：Phase A worker 把问题按上述结构写进 run 目录并**就此停止**；Phase B worker 把 `answers.md` 中对应条目视同用户当面答复。
2. **不写共享台账**（铁律 ②）。原技能的台账步骤改为：把要写的行 / 条目原样写进自己的 `report-<分片>.md`，由 orchestrator 代笔。
3. **范围锁死在派单分片**。发现相邻分片的问题 → 写进报告的「越界发现」，不顺手处理。

单会话技能被人直接运行时（非批量），本文件不适用，一切照原技能执行。
