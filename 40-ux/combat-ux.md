# combat-ux

> 战斗手感:出牌/拖拽/指定目标、节奏。**主视觉 = 双方道念对比**;**敌人意图按等级差三档呈现**(见下)。

## 意图

- **道念是战斗屏幕的主视觉(已定案)。** 胜负判据是**道念(momentum)高者胜**(见 `20-systems/scoring.md`),因此战斗屏幕的视觉重心是**双方道念的对比**——玩家任何时刻都应一眼看出「我现在领先还是落后、差多少」。**lifeTotal 退居次要**:它在战斗过程中不变化,只在结算时按道念差被扣减,故不需要战斗内的常驻血条式强调。具体形态(对比条 / 双数值 / 天平隐喻)待战斗 UX 专场。Source: `10-handoffs/2026-08-01-momentum-scoring-lifespan-tuning-and-failure-payoff.md`。
- **战斗是定长的 10 个回合,故进度可视(已定案的连带)。** 双方各 5 个回合、打满即比大小——**「还剩几回合」是一个必须呈现的信息**:它把「我落后 8 点、还剩 2 个回合」变成玩家可算的账,是限时积分对抗的紧张感来源。**起始道念按等级给**,故战斗一开场就可能呈现出一段明显的落差。呈现形态(回合计数器 / 进度条 / 双方轮次指示)待战斗 UX 专场。Source: `10-handoffs/2026-08-01b-abstraction-levels-combat-numbers-codex-family-and-monetization.md`。
- **敌人等级精确可见(已定案 · 答结「等级差是否可见」)。** 玩家**能**看到敌人的等级——**在 eventOptions 上就已精确标注**(见 `20-systems/services/future-event-service.md`),而非模糊的危险度档位(「同阶 / 略高 / 越阶 / 无从揣度」一类标签**否决**)。玩家自行与自身等级比对,由此**理解意图为何被遮蔽**;「越级挑战」也因此成为可主动选择的风险 / 回报维度。Source: 同上。
- **敌人意图三档呈现(已定案)。** 呈现档位由**全局等级序**上的「敌人 − 角色」等级差决定,**默认给完整意图,越级才降级**:

  | 情形（`diff` = 敌人全局等级 − 角色全局等级） | 呈现 |
  |---|---|
  | **越阶**（敌人境界更高） | **完全不呈现**,且**没有任何替代线索** —— 不论 `diff` 多小 |
  | 同阶 · 第一篇章、`diff ≤ -3` | **完整意图**:动作类型图标 + 综合数值 |
  | 同阶 · 第一篇章、`-2 ≤ diff ≤ 2` | **仅类别**:攻击 / 防御 / 增益 / 特殊——符号或剪影,**不带数值** |
  | 同阶 · 第一篇章、`diff ≥ 3` | **完全不呈现** |
  | 同阶 · 第二 / 第三篇章、`diff ≤ -2` | **完整意图** |
  | 同阶 · 第二 / 第三篇章、`-1 ≤ diff ≤ 1` | **仅类别** |
  | 同阶 · 第二 / 第三篇章、`diff ≥ 2` | **完全不呈现** |

  **「越阶 = 黑箱」是一道硬门**——它让境界鸿沟在呈现上也成为一条明确的界线,而不只是数值差的连续衰减;玩家在 eventOptions 上已看到敌人的精确等级,故这一遮蔽**有可解释的因**。服务侧与全局等级序见 `20-systems/services/combat-service.md`、`20-systems/game-progression.md`。Source: `10-handoffs/2026-08-02c-intent-threshold-inversion-and-aggregate-intent.md`。
- **第二档「仅类别」是常态呈现,不是边缘情形(已定案 · 08-02c · 承重)。** 阈值下移后**同级对局(`diff = 0`)也只给类别——这是有意为之,不做可读性补偿**;完整意图只在明显压制时出现(ch1 低 3 级、ch2 · ch3 低 2 级及以上)。**推论 ①:「仅类别」的视觉语言从可粗做升为战斗屏的核心可读性来源**——它是玩家看得最多的一档,其符号 / 剪影体系直接决定玩家能否读懂战斗(**这条把下方「第二档视觉语言」的待决问题提到承重级**)。**推论 ②:完整意图成为碾压时的即时反馈**,呈现上可以做得更"给"(它是奖励而非基础信息)。**推论 ③:探查(probe)的入口值得在战斗屏留位置**——常态只有类别,主动买信息有了稳定需求。**推论 ④:同级对局缺少可算的账是设计意图,不是缺口**——玩家在标准 Combat 中读不到数值,**不为此另做补偿**(图鉴查数值区间 / 打出后回显实际值一类的方案不采用)。Source: 同上。
- **意图是回合级的综合描述,不是逐张预告(已定案 · 08-02c)。** 一个回合对手可以打出多张牌,故呈现的是**本回合的汇总**:**数值 = 计算后合并的最终结果**(一个结果值,例:削减 12),**类别 = 主类别并行陈列**(跨类别的一回合并列显示各主类别,不压缩成单一类别、不归入「特殊」),**不列张数、不做逐张分解**。**推论 ①:意图不是一串图标而是一条摘要**——不采用 Slay the Spire 式「一个敌人一个意图图标」的逐动作映射,也不排出牌序列;但**并行陈列意味着一条摘要里可能有 2~4 个类别符号**,布局须容得下(竖屏窄边尤其吃紧)。**推论 ②:呈现的数值是声明量,可能与实际结算不符**(下限 0 的饱和减法 + 触发入栈),UI 须容得下"意图说 12、实际掉 8"而不显得像 bug。Source: 同上。
- **意图只在玩家回合呈现,内容是敌人的下一个回合(已定案 · 08-02c)。** 敌人回合内**不呈现意图**——那时它正在出牌,呈现的是出牌本身。**推论 ①:意图是玩家回合内的常驻信息**,随回合归属切换而出现 / 消失,不是逐次出牌的飘字。**推论 ②:它是玩家出牌决策的依据**(「我该防多少 / 追多少」),故与道念对比、剩余回合数同属决策面板一组,应就近呈现。**推论 ③:敌人回合内意图区收起(已定案)** —— 不留占位、不换成其他指示,该区域在敌方回合直接收起。**连带:布局必须扛得住这块区域的出现 / 消失**,竖屏下不能因此让道念对比、手牌区整体跳位——意图区应有稳定的落位策略(固定预留高度或明确的收起动画),否则每回合切换都会引起画面重排。Source: 同上。
- **意图即承诺:公布后不因玩家行动重算(已定案 · 08-02c)。** 玩家在主阶段做什么都不改写已公布的意图,**屏上的意图数字在整个玩家回合内不跳动**。**推论 ①:玩家可以据它布局**(「它要打 12,我这回合防住 12」),意图从"提示"升级为"可依赖的账"——这与道念差 1:1 换算合流,战斗屏上的算术因此完全可算。**推论 ②:UI 无需表达"意图已变更"这一状态**(没有重算就没有刷新动画 / 变更高亮)。Source: 同上。
- **不做「敌人状态可读」的补偿(已否决)。** 「以蓄力 / 凝聚 / 破绽等显式状态标记替代意图」的方案**明确否决**:大幅越级就是彻底的信息黑箱,不给替代线索。Source: 同上。
- **探查(probe)是玩家主动买信息的通道。** 与被动的意图档位相对:玩家**付出代价换取当回合敌人意图**。方向与定名已成,**呈现形态(按钮 / 手势 / 常驻入口)与花费形式归卡牌与技能内容的横向扩展阶段,本阶段搁置**。「能力 / 道具授予窥视意图」即探查能力的授予形式。Source: 同上。
- **敌人图鉴给静态知识,不给动态情报。** 账号级敌人图鉴(`20-systems/player-profile/codex/`)记录「这个敌人**会做哪些事**」;它**不揭示本回合的具体意图**,因此不架空越级时的信息黑箱。战斗内是否可直接查阅图鉴未定。Source: 同上。
- **战后奖励面板是战斗流程的一屏(已定案 · 新增)。** 「获取奖励」属于战斗流程本身,故战斗结束后**在战斗流程内**呈现奖励:**强制部分自动计入**(无需玩家操作,例:`experiencePoint`),**可选部分由玩家从若干候选中择一**——形态**参照 Slay the Spire** 的战后奖励面板。**推论:这是战斗 UX 至今未有的一屏**,且它在返回结果之前,不是事件收口后的另一步。**奖励预先算定,选择不是决策点**——退出重进得到同一组选项,故 UI 不必表达"已存档"。具体形态(候选项呈现、强制项的提示方式、竖屏布局)待战斗 UX 专场。Source: `10-handoffs/2026-08-02-momentum-conversion-reward-structure-and-mtg-stack.md`。
- **回合不是交互式的:stack 保留、交互与优先权移除(已定案 · 承重 · 08-02b 收窄)。** 卡牌入栈后按 LIFO 结算,但**没有响应窗口、没有优先权传递**——**"我打完换你打"的简单交替成立**,理由是交互 / 优先权**拉长时长、决策点过多、复杂度高而深度收益小**。**推论 ①:不需要"轮到你响应"这套交互**(何时提示 / 如何 pass / 自动 pass / 超时),竖屏触控上最吃紧的那一环由此消失。**推论 ②:栈仍必须进入呈现层**——虽然玩家不再为"是否响应"读栈,但**触发式能力也入栈**,故栈深可以大于 1(见 `20-systems/character-profile/deck/`);玩家要看懂"现在有哪些东西在等待结算、以什么顺序",否则触发连锁不可读。**推论 ③:敌人的出牌仍要呈现**(敌人也持有卡组),但只在敌方回合内呈现,不再穿插进玩家回合。Source: `10-handoffs/2026-08-02b-stack-without-interaction-and-three-step-turn.md`。
- **回合的三步结构给了 UX 一条明确的时间轴(已定案 · 08-02b)。** **起始步**(归属方 mana 恢复至 `manaLimit` → 触发「回合开始时」→ 抽牌)→ **主阶段**(唯一出牌阶段)→ **结束步**(触发「回合结束时」→ 清理回合内状态)。**三步是回合归属方的流程,双方不同时走。** **推论 ①:每回合有三个可被呈现的节拍**——mana 刷满、抽牌、以及结束步的触发 / 状态消散,动画节奏可依此编排,不必自创分段。**推论 ②:手牌上限需要在 UI 上可读**——上限是**任何时刻都不得超过**的硬约束(**没有弃牌机制**),故玩家必须能随时看出"我还能拿几张";满手时抽牌的表现要能被看见(见待决问题)。**推论 ③:"轮到谁"是一个必须常驻的指示**,它现在是回合归属权的唯一表达。具体形态待战斗 UX 专场。Source: 同上。
- **战斗屏多了一个区:战场(battlefield)(已定案 · 08-03 · 承重)。** 场上**正在生效**的卡牌 / 持续状态 / 等待中的触发器落在 battlefield 上,与**栈**(等待结算的队列)是**两个不同的区**。**推论 ①:竖屏要容下三块**——战场 / 栈 / 手牌,再加上道念对比、回合计数与意图区,窄高屏的分区压力显著上升(具体排布待战斗 UX 专场)。**推论 ②:玩家须能区分"已经在生效"与"正在等待结算"**——二者混成一片就读不懂触发连锁。**推论 ③:回合内状态的消散有了可视对象**——结束步清理的是战场上标记为回合内的条目,动画有了明确的落点。Source: `10-handoffs/2026-08-03-battlefield-stack-hand-limit-and-power-item-naming.md`。
- **满手时抽牌的表现:牌抽不进(规则已定 · 08-03)。** 满手时抽牌**抽不进**(牌留在抽牌堆、本次抽牌无事发生),「加入手牌」类效果同理落空——**规则已定,剩下的只是表现形式**。**推论 ①:需要一个"没抽进"的可见反馈**,否则玩家会以为抽牌漏了或界面卡了;**推论 ②:手牌上限本身要常驻可读**(「我还能拿几张」),否则满手是个突然出现的意外;**推论 ③:不会有牌被弃掉或销毁的画面**——上限是纯上界,不产生弃牌堆流量,视觉上不该出现"牌被丢掉"的动作。Source: 同上。
- **道念差是玩家可直接换算的账(已定案的连带)。** 失败时 `lifeTotal` 的扣减量**就是道念差**(1:1),故战斗屏上的「我落后 8 点」同时就是「输了要掉 8 点 lifeTotal」——**这条 1:1 关系让主视觉的价值大增**:玩家不需要额外的教学就能读懂风险,也让「道念差是否显式呈现」这个问题的答案更倾向于「显式呈现」。Source: 同上。
- **回合数不是固定的 10(已定案的连带)。** 10 回合是 **Combat 档的标准值**;Practice / Finale 可改写回合数与胜负条件。**推论:「还剩几回合」的呈现必须由本场遭遇的配置驱动**,不能把 10 写死进 UI。Source: 同上。
- **寿元红字倒数不进战斗内。** 寿元告警的呈现位置已定为 **EventOption 选择界面**的静态标注,**不常驻战斗屏幕**、不做全局 HUD。见 `40-ux/screen-flow.md`。Source: `10-handoffs/2026-07-30-claude-engineering-scope-enemy-manager-and-requirement-breakdown.md`。

## 待解问题
> _尚未解决,需要一次 handoff/决策。_

- **回合进度与道念差的组合呈现。** 「还剩几回合」与「差多少道念」共同决定紧张感;二者是同屏两个独立元素,还是合成一个「还追得回来吗」的复合指示?未定。Source: 同上。
- **第二档「仅类别」的视觉语言(08-02c 提为承重)。** 四个类别(攻击 / 防御 / 增益 / 特殊)用什么符号 / 剪影表达、如何与完整意图的图标体系区分(是同一图标去掉数值,还是另一套模糊化视觉)未定——**阈值下移后它是常态呈现**,直接决定战斗可读性;**并须容纳「主类别并行陈列」**(一条摘要里可能并列 2~4 个类别符号,竖屏窄边的排布未定)。Source: `10-handoffs/2026-08-02c-intent-threshold-inversion-and-aggregate-intent.md`。
- **意图区收起后的布局稳定性(08-02c 追加)。** 「敌人回合内收起」已定案;**怎么收**未定——固定预留高度(空着)还是让其余元素上移?收起 / 展开是否有动画?竖屏窄高下这块区域的位置与尺寸尚未确定。→ 待战斗 UX 专场。Source: 同上。
- **承诺与执行不一致时的呈现(08-02c 追加)。** 意图不重算已定案,但计划中的牌可能在敌人回合无法照原样执行(资源 / 目标变化);**处理方式本身未定**(见 `20-systems/services/combat-service.md`),其呈现——玩家看到的是"它没打出那张"还是"打了但效果不同"——亦未定。Source: 同上。
- **敌人等级的展示措辞。** 「精确标注等级」已定案;但**用什么措辞**(境界名 + 层级如「筑基中期」?全局等级序数字?二者并列?)以及**是否同屏并列玩家自己的等级**便于比对,未定。Source: `10-handoffs/2026-08-01-momentum-scoring-lifespan-tuning-and-failure-payoff.md`。
- **道念对比的视觉形态。** 主视觉地位已定;**用什么形态**(左右对比条 / 双数值 / 天平隐喻)、道念变化时的反馈(数字跳动 / 特效)、以及「道念差」是否显式呈现(它决定失败时扣多少 lifeTotal,而 lifeTotal 归 0 即角色终结)均未定。→ 亦见 `20-systems/scoring.md`。Source: 同上。
- **lifeTotal 在战斗屏幕上的位置。** 已定「退居次要」;但**是否仍常驻显示**(作为「失败会掉多少」的参照)还是完全移出战斗屏,未陈述。Source: 同上。
- **战后奖励面板的形态(08-02 新增)。** 强制项与可选项如何同屏区分(自动计入的部分是否也要展示"你获得了什么")、可选候选的数量与竖屏排布、选择是否可反悔、以及它与"事件收口"之间的视觉衔接均未定。Source: `10-handoffs/2026-08-02-momentum-conversion-reward-structure-and-mtg-stack.md`。
- **栈与战场的同屏呈现(08-02b 新增 · 08-03 加压 · 承重)。** 触发式能力入栈使**栈深可以大于 1**,故栈**必须**可见;**08-03 起还多一个战场区**(正在生效的卡牌 / 持续状态 / 触发器)。仍待定:竖屏小尺寸上如何**同时**表达"哪些东西在等待结算、以什么顺序"与"哪些东西已经在生效"、两区如何在视觉上区分、连锁触发的结算动画如何不拖慢节奏、玩家能否在结算过程中查看条目详情。→ `20-systems/character-profile/deck/`、`20-systems/services/combat-service.md`。Source: `10-handoffs/2026-08-02b-stack-without-interaction-and-three-step-turn.md` + `10-handoffs/2026-08-03-battlefield-stack-hand-limit-and-power-item-naming.md`。
- **三步结构的呈现细节(08-02b 新增 · 08-03 收窄)。** 起始步的 mana 刷满与抽牌是否各有独立节拍与动画、**"没抽进"的反馈形态**(规则已定为抽不进,表现未定)、**手牌上限的常驻可读形态**、**回合内状态消散**如何被看见、以及"轮到谁"的常驻指示形态,均未定。→ `20-systems/services/combat-service.md`。Source: 同上。
- **战斗屏幕的其余形态整体未设计**——出牌手势(拖拽 vs 点按)、目标指定、手牌布局、回合节奏与动画时长、竖屏下的敌我分区,以及**敌人也持有卡组**后敌方出牌的呈现方式,均待一次专门的战斗 session(见 `20-systems/adventure-event/_index.md` 的逐类型 session 约定)。
