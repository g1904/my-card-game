# compliance-ops —— 合规域的运维形态：可信时钟 · 三类状态与产物 · 降级

> 语义权威在 `contracts/compliance.md`，**本文件不复述报文**，只写后端如何兑现它：时刻从哪来、状态存在哪、产物怎么发、失败时往哪一侧倒。
> 三张表的承重列、事务边界与逐条服务端保证在 `systems/account.md`；单库 PostgreSQL · 并发单元 = `account` 行 · 契约条款落为数据库不变式等公共前提见 `systems/_index.md`，此处不重复。
> 旋钮的**取值**权威在 `contracts/compliance.md` §9 与 `operations/environments.md` 的旋钮清单；本文件只给每个旋钮的**校准信号**（线上哪个指标动了就该改这个值）。

## 可信时钟：判定基准与同步纪律

**全部合规判定与长时状态机的时刻，一律取该次判定所在事务的数据库时钟**（`now()`，即事务开始时刻），不取应用容器的进程时钟。

- 单主 PostgreSQL 已经是全库唯一的串行点与并发单元；容器可弹性伸缩、副本各有各的进程时钟，而**主库只有一台**。取库时钟即天然得到全站唯一的时间基准，不需要为「跨副本时钟一致性」再引入任何机制。
- 合规判定本就发生在一次已经握着 `account` 行锁的事务里（`signin` 的 `SELECT … FOR UPDATE`，见 `systems/account.md`），因此 `now()` 零额外开销。
- **判定与写入看到同一个时刻**，不在两者之间开竞态缝——与 `systems/profile-store.md` 那条「回声校验读的是本事务内已加锁的当前值，不是事务外的一次预读」是同一条纪律的第二个实例。

**两处例外，明写以免被误推广：**

| 例外 | 用什么时钟 | 为什么不受本条约束 |
|---|---|---|
| access token 的 `iat` / `exp` | 从**会话状态**派生（`systems/account.md`） | 它必须对同一次幂等回放字节相同，取任何「当前时刻」都会破坏这一点 |
| JWT 验签时的 `exp` 比对 | 验签侧进程时钟 | 它的时钟容错已由「旧 `kid` 保留 ≥ access token TTL + 时钟偏移余量」承接（`operations/environments.md`） |

**跨区域一致性在当前拓扑下不存在。** 单区域部署、不做跨区域多活、只读副本不承接任何玩家读路径（`operations/environments.md`），加上基准收敛到主库一台机器 ⇒ **参与合规判定的时钟只有一个**。海外扩展是另一套独立部署 + 独立 `accountId` 空间，它有自己的一套时钟与自己的一套监管口径，不是本套的跨区域拉伸。这一段记的是「这个问题已经消解」，不是给出机制——不写它，下一个读到时钟需求的人会重新去设计一套跨区域时钟同步。

**同步纪律：**

- 容器宿主与数据库实例一律由**云厂商内网 NTP 授时**，`chrony` 一类守护进程**常驻**，不用一次性对时命令。托管数据库的授时由厂商负责，本条对它的要求是「可观测」而非「可配置」（探针见 `operations/observability.md`）。
- **绝不允许时钟向后跳变。** 偏差修正一律走渐进式（slew）；超出 slew 能力的偏差**告警并人工介入，不静默 step**。向后跳的时钟会让「一次性消费」「到期即生效」「单调序号」这类判定看到时间倒流，而它们的错误后果都不可回收——一枚已消费的 ticket 重新变得可用、一次已生效的注销回到冷静期。
- **不可逆动作在时钟异常期间暂停。** 检测到 step 级跳变或 NTP 失同步时，**注销执行**这条本库唯一不可逆的动作暂停一轮（下一轮扫描自然重试）；时段判定与 ticket 判定照常——它们的边界是小时 / 分钟级，秒级偏差不改变结论。这条把时钟异常的爆炸半径限制在「晚几分钟执行」，而不是「错误地永久删号」。

Source: `handoffs/2026-09-06-trusted-server-clock.md`。

## 时区与时段规则集

- **判定一律在 `Asia/Shanghai` 本地时间下进行；存储与报文一律 UTC**（`contracts/envelope.md` §2 已定 RFC 3339 UTC 带 `Z`、字段名以 `AtUtc` 结尾）。`resumeAtUtc` 与 `playtimeRemainingSeconds` 由服务端在该时区算好后转 UTC 下发。
- **时区是时段规则的一员，与时段表同处规则集，不是代码常量、也不落 `config_knob`。** 判据与契约那句「时段口径落配置」相同：口径由监管决定，而监管口径的任何一部分都不该要求发版才能改。把时区单独放进旋钮表会造出「时区改了但时段没改」的半版本态。
- **用 IANA 时区名（`Asia/Shanghai`），不用固定偏移。** 中国大陆当前无夏令时，两者今天等价；但写成固定偏移时，扩展到任何带夏令时的地区都要改代码形状，而用 tz 名的成本为零。
- **镜像必须内置 tzdata，并作为一条启动断言**：启动自检解析一次规则集中的时区名，失败即拒绝启动。精简基镜像默认不含 tzdata，缺失时的表现是运行期合规判定当场抛异常——一次典型的「本地跑得通、云上跑不通」。断言落点见 `operations/deployment.md`。

**规则集不是单值旋钮，是一份结构化的规则集**（星期集合 + 时段区间 + 日历），因此它**不塞进 `config_knob` 的 key/value 表，而是逐条复用昵称词表的不可变版本化发布**（`operations/moderation.md`：无原地编辑路径 · 版本号单一分配点且单调 · 回滚 = 以历史内容发起更大版本 · 留痕四项 · 历史永久保留）。

理由与词表那条同构且更强：

- 存量审计必须能回答「**这一次拦截是按哪一版规则做的**」。防沉迷是监管面，一次「谁在什么时候把时段改宽了」的追问是可以预期的；而「随手改一下数据源」正是不可变发布要堵的静默失效模式。
- 规则集体量与词表同量级（一年一张日历 + 几行周规则），永久保留成本近似为零。
- **零新增机制**：发布通道、留痕字段、回滚语义全部已经存在，本条只是给它加第二类载荷。

规则集的承重列：

```
playtime_ruleset (version 单调主键, published_at_utc, published_by,
                  derived_from, change_summary,
                  timezone,              -- IANA 名，例 "Asia/Shanghai"
                  weekly_days,           -- 允许的星期，初值 周五 / 六 / 日
                  window_start, window_end,      -- 初值 20:00 / 21:00
                  daily_limit_seconds,   -- 初值 3600，供 MinorDailyLimit
                  calendar)              -- 见下一节
```

- `daily_limit_seconds` 与时段并列，**因为契约把 `MinorCurfew` 与 `MinorDailyLimit` 分列了**——即使现行口径下两者几乎重合，规则表也要能分别表达，否则监管口径一旦拆开就要改表结构。
- **生效时刻只有一个：判定时读当前最高版本。** 不做「预约生效」——它会引入一个自己也要判时刻的调度器，而运营在发布动作上择时的成本为零。

Source: `handoffs/2026-09-06-trusted-server-clock.md`。

## 法定节假日日历

**数据源：人工录入，随规则集一次发布。** 国务院办公厅每年（通常 11–12 月）发布次年放假安排，没有官方机读接口。因此：

- **不接任何第三方节假日接口作判定输入。** 它是无 SLA 的外部依赖，一旦不可达就直接决定未成年玩家能否进入；而这份数据一年只变一次、总量二十余行。第三方数据可作**发布前的交叉核对**辅助，不作判定输入。这与「C 层原子能力一律外接以适配器隔离」是相反方向的两类：外接的是**每次请求都要调**的能力，日历是**一年录一次**的数据。
- 录入走与人工判定结果回灌同一条来源通道（`operations/moderation.md`）：**收敛到同一次发布动作，不存在旁路写入。**

**日历必须有两类条目，只列节假日是错的：**

| 条目类别 | 语义 | 对判定的影响 |
|---|---|---|
| `StatutoryHoliday` | 法定节假日（含调休放假日） | 该日**可玩**，无论星期几 |
| `WorkingWeekend` | 调休上班的周六 / 周日 | 该日**不可玩**，尽管它是周末 |

**`WorkingWeekend` 是最容易漏的一项**：中国的调休会把周末调成工作日，若日历只有节假日正列表，一个被调成工作日的周六仍会被基础周规则判为可玩——方向是「多给」，即不合规的那一侧。

判定算法（顺序即语义，写死）：

```
本地日期 d = 该次事务的库时钟在 ruleset.timezone 下的日期
① d ∈ calendar[WorkingWeekend]        → 不可玩
② d ∈ calendar[StatutoryHoliday]      → 可玩（受 window 与 daily_limit 约束）
③ weekday(d) ∈ ruleset.weekly_days    → 可玩（同上）
④ 否则                                 → 不可玩
```

`WorkingWeekend` 排在最前，因为它是**减法**：一个既被调休上班、又碰巧挨着假期尾巴的日子，减法必须赢——判定顺序永远让保守的那一侧优先。

**到期告警是日历失效唯一的机制发现面**：日历覆盖的最后一个日期距今 < 60 天即工程告警（`operations/observability.md`）。没有它，日历过期的表现是**静默地走降级路径**，而没有任何人会知道。60 天的推导：次年安排通常在 11–12 月发布，60 天使告警落在「已经可以拿到数据」之后、且在跨年之前留出录入与发布的余量。**待实测校准。**

年度录入本身是一条**周期性运维日程项**（每年 12 月），登记在 `operations/deployment.md`，不并入「首个真实账号建号之前」那份一次性清单——那份清单的成立前提是四项共用同一个不可逆时刻，而本条每年重来一次。

Source: `handoffs/2026-09-06-trusted-server-clock.md`。

## 降级语义：三个失败面

三个失败面处置不同，逐条给：

| # | 失败面 | 处置 |
|---|---|---|
| F1 | **NTP 失同步 / 进程与库时钟偏差超阈** | 判定**照常进行**（库时钟仍是唯一基准，秒级偏差不改变小时级的时段边界）+ 探针告警；**但暂停注销执行**这条不可逆动作 |
| F2 | **时段规则集读取失败**（配置存储抖动、进程缓存已失效且回源失败） | 对**未成年账号 fail-closed**：判为不在允许时段，回 `compliance.playtime_blocked` + `MinorCurfew`；成年账号不做时段判定，**不受影响** |
| F3 | **日历过期**（当天超出日历覆盖范围） | **与 F2 同处置**：未成年账号一律拦截。错误拦截可回收、错误放行不可回收；日历过期已有提前 60 天的告警，是一次可预防的运维失职，不为它设计一条会产生合规风险的降级路径。**降级路径因此只有一条**——两条降级路径必然有一条长期没被走过，因而是坏的 |

**F2 / F3 为什么 fail-closed，而限流默认 fail-open：** 判据在 `operations/environments.md`「限流的实现分层」——**例外的判据是「错误放行的代价不可回收」**。合规判定命中该判据且代价方向更硬：错误放行一个未成年账号是合规事故（渠道下架 / 监管处罚），不可回收；错误拦截的代价是一小部分未成年账号在几十秒内进不去，配置回源恢复即自动解除。

**爆炸半径三重夹住，因此这条 fail-closed 不与「绝不打断进行中的轮回」相抵：**

1. 只影响**已判定为未成年**的账号——成年账号根本不走时段判定；
2. 只在**配置回源失败**时触发——`config_knob` 有约 30 秒进程内缓存，寻常抖动到不了这条路径；
3. 拦截发生在 `signin`，不打断进行中的轮回。

**降级路径下 `resumeAtUtc` 怎么给（承重，否则报文形状不成立）：** 错误码台账把 `compliance.playtime_blocked` 的 `detail` 写死为 `{ reasonKey, resumeAtUtc }`，而降级时「什么时候能玩」恰恰是算不准的那一项。解法：**给基础周规则下的下一个允许时段起点**——它只依赖星期与时钟，不依赖日历与规则集（用编译期兜底常量：周五 / 六 / 日 20:00，`Asia/Shanghai`）。它可能**晚于**实际可玩时刻（漏掉了节假日），方向保守、形状完整、零契约改动。

Source: `handoffs/2026-09-06-trusted-server-clock.md`。

## `complianceTicket`：存储与一次性消费

### 载体 = Postgres 表，不是 Redis

- Redis 只承担限流计数器、**不持有任何权威状态**（`systems/_index.md`）。ticket 的消费态是权威状态：它决定一次按次计费的实名核验会不会被重复调用、一次注销撤销会不会被重放。
- 更硬的理由：**消费标记必须与它守护的状态写入落在同一次事务**。跨存储会造出「ticket 已消费但结果未落」或反之——正是拒绝独立文档数据库时逐字点名的那类失败态。
- 同一条判据的先例已在库内：`signin_replay` 需要与会话写入同一事务，因此放关系库而不是缓存（`systems/account.md`）。**ticket 是这条判据的第二个实例。**

表承重列见 `systems/account.md`。三条形态纪律：

- **存哈希不存明文**（`ticket_hash = SHA-256(ticket)`）。ticket 是一枚活凭据；库内已有两条同向纪律（`identifier_mac` 存 HMAC、refresh 宽限回放不缓存明文而靠重算）。ticket 本身是高熵随机串，无需加盐或加密钥抗字典。
- **明文形态：32 位小写十六进制**（128 bit 随机）。与 `taskId` 和 `accountSeed` 同向——定长 · 无前缀 · 无分隔符 ⇒ 两侧不需要对大小写或分隔符做归一，库内不再多立一套编码约定。
- **`response_snapshot` 只装应答体，绝不装请求体。** 实名端点存 `{ realnameStatus, isMinor }`；撤销端点回 `204` 无体 ⇒ 存空对象。**姓名 / 证件号不进这张表的任何一列**——脱敏纪律约束的是「永不进任何应答、永不进日志」，而一份会被原样回放成应答的快照正是应答本身。

### 一次性 + 60 秒回放：条件更新 + 受影响行数分支

契约把这一对写成看似冲突的两条（一次性，消费后即失效 + 首次成功后 60 秒内原样回放上次应答、不再消费、不产生任何副作用）。**它们不冲突**：一次性约束的是**副作用**，回放只是重发一份已产生的应答。

落地形态是一次条件更新，照 CAS 的既有手法**用受影响行数分支，不先 `SELECT` 再 `UPDATE`**（`systems/profile-store.md`）：

```
UPDATE compliance_ticket
   SET consumed_at_utc = now(),
       expires_at_utc  = GREATEST(expires_at_utc, now() + 60 秒)
 WHERE ticket_hash = :h AND consumed_at_utc IS NULL
```

- **1 行** ⇒ 本次是首次消费，执行业务副作用并把要回给客户端的应答体写进 `response_snapshot`。
- **0 行** ⇒ 再读该行判两种情形：行存在且距 `consumed_at_utc` ≤ 60 秒 ⇒ **原样回放 `response_snapshot`，零副作用**；否则 ⇒ `compliance.ticket_invalid`。

**求值顺序写死，逐级短路，使应答唯一**（顺序体例与 refresh「先判到期、再判宽限回放」相同）：

```
① 按 ticket_hash 查行           查不到 → ticket_invalid { Unknown }
② purpose / account 匹配        不匹配 → ticket_invalid { Unknown }
③ 已过期                        → ticket_invalid { Expired }
④ 已消费                        → 窗口内回放；窗口外 → ticket_invalid { Consumed }
⑤ 否则                          首次消费
```

**关键一笔：消费时把 `expires_at_utc` 拉到 `max(原值, consumed_at_utc + 60 秒)`。** 这使回放窗口成为**寿命的延长**，而不是与寿命竞争的第二把尺。否则会出现一个边角：在第 9 分 30 秒消费、第 10 分 30 秒回放，此时「已过期」与「在回放窗口内」同时为真，③ 与 ④ 的先后决定应答，而契约没有给这个边角定过口径。做成延长后**边角消失**，`Expired` 与 `Consumed` 在任何时刻都互斥且确定，验收断言无歧义。代价是一条取最大值的表达式。

### 外部核验调用：两段事务，以及它的终局出路

实名兑付要调一次外部核验服务。**外部 HTTP 调用不放进持锁事务**——那会把外部延迟变成锁持有时长。因此上面那条「消费与业务写入同事务」在此收窄为它的准确形态：**消费标记与它守护的状态写入同事务，外部调用是唯一例外**，取两段：

1. 条件更新占位（标记消费）并提交；
2. 调核验服务；
3. 第二次事务写核验结果与 `response_snapshot`。

第二段未完成前重试会读到「已消费但 `response_snapshot` 为空」。**处置：回 `server.unavailable`（`Retryable`）**，与契约「核验服务不可达 → `server.unavailable`」逐字一致，客户端照既有路径重试，不新增任何 `code`。

**终局出路必须写下，否则这条路径没有尽头**：若进程在两段之间彻底崩溃，该 ticket 会一直停在「已消费、无快照」。玩家的出路是重走 `signin`——实名状态仍为未提交 ⇒ 拦截恒成立 ⇒ 按下面的签发纪律拿到一枚**新** ticket。因此这一态的代价上界是「一次重新登录」，不需要任何补偿任务或人工介入。

### 签发与清理

- 签发落点是 `signin` 判定被拦的那一刻，**与拦截应答同一次请求、同一次事务**（`signin` 本就握着 `account` 行锁）。
- **每次拦截签发新 ticket，不复用未消费的旧枚。** 理由是寿命重置：玩家在第 9 分钟重试登录时若拿到一枚只剩 1 分钟的复用 ticket，实名表单根本填不完，而 10 分钟这个初值的推导正是「覆盖一次实名表单填写 + 一次重试」。旧枚不主动失效、自然到期；多枚并存不构成滥用面（单端点 · 单账号 · 10 分钟 · 一次性）。
- **清理**：过期后再留 24 小时供排障溯源上一次判定，之后按批删除，挂在下方的周期任务通道上。**不分区、不设 TTL 扩展机制**——稳态存量极小：实名是每账号一生一次的动作，注销撤销更罕见。

Source: `handoffs/2026-09-06-compliance-domain-storage.md`。

## 注销冷静期：跨天长时状态机

### 状态承载 = 独立表，`pendingDeletion` 由它派生

- **为什么不是 `account` 上的两列**：注销是一个有多个时刻与多个终态的对象，还要能被审计追问（谁在什么时候申请、什么时候撤销的）。`account.status` 是「当前可玩性」的单点，不该兼职承载时刻与历史。
- **`account.status = pendingDeletion` 由「存在处于冷静期的 `account_deletion` 行」派生**，与 `nicknameChangeRequired` 由云端状态算出是同一手法。契约的 status 四值**一字不改**。
- **`previous_status` 是承重列，不是审计装饰。** 契约明写受限 / 封禁的账号同样可以申请注销（删除权不因风控状态而消失）；撤销时若无脑把 `status` 置回 `active`，就成了**用「申请注销 + 撤销」洗白风控处置**的一条路径。撤销必须恢复到 `previous_status`。这一处漏掉后**线上不可发现**——表现只是「某些被封号的玩家又能进了」，没有任何报错。
- **状态取值三个**：冷静期中 · 执行中 · 已执行。**撤销即删除该行**，因此没有「已撤销」这个取值：`account_deletion` 不承担历史归档职责，「谁在什么时候申请 / 撤销过」交给风控事件流（只追加、有自己的保留期，`operations/moderation.md`），它已经是本库登记这类行为记录的地方。这样 `account_deletion` 恒为「至多一行在办」的小表，且不额外造一份需要自己定保留期的历史。撤销后玩家可以再次申请注销，主键因此不会冲突。

### 调度形态：周期扫描 + `SKIP LOCKED`，零新增组件

跨天长时状态机对可靠调度的追加要求，**由单库即可满足，不需要任何调度中间件或消息队列**（后者已被明确不引入）：

```
每 5 分钟一轮（初值）：
  SELECT account_id FROM account_deletion
   WHERE 处于冷静期 AND effective_at_utc <= now()
   ORDER BY effective_at_utc
   FOR UPDATE SKIP LOCKED
   LIMIT :batch
  → 逐个账号在各自的事务里执行删除，成功即置「已执行」
```

四条性质逐一对上可靠调度的要求：

| 要求 | 兑现方式 |
|---|---|
| **多副本安全** | `SKIP LOCKED` 使两个容器同时跑同一个任务互不重叠 ⇒ 不需要 leader 选举、不需要分布式锁 |
| **幂等重入** | 执行是条件转移 + 受影响行数分支；进程中途崩溃 ⇒ 事务回滚，下一轮重新领取 |
| **到期精度** | 冷静期 15 天，晚几分钟生效无任何语义影响——**这正是可以不引入调度中间件的判据**，写下来使它不必被重新论证 |
| **不与撤销竞态** | 撤销与执行争用同一行的行锁，先到者赢；撤销在行已非冷静期态时回 `compliance.deletion_irrevocable` |

**时钟异常时暂停本任务一轮**：注销执行是本库唯一不可逆的动作，不在时钟可疑时执行。

### 三个端点的落地分支

| 端点 | 事务内写入 | 分支 |
|---|---|---|
| 申请注销 | 插入 `account_deletion`，键冲突则不写；`effective_at_utc = now() + 冷静期`，`previous_status = account.status` | 插入 0 行且既有行处于冷静期 ⇒ 回既有 `deletionEffectiveAtUtc` + `deduplicated`，**绝不顺延**；既有行为终态 ⇒ 新起一行 |
| 撤销注销 | 删除处于冷静期的那一行 · 同事务把 `account.status` 恢复为 `previous_status` · 落一条撤销事件 | 1 行 ⇒ `204`；0 行且无行 ⇒ `204`（幂等）；0 行且行处于执行中 / 已执行 ⇒ `compliance.deletion_irrevocable` |
| 查合规态 | — | `deletionEffectiveAtUtc` 仅在行处于冷静期时下发（契约：存在即处于冷静期） |

**申请不吊销任何会话**（契约已定），因此申请端点不触碰会话表。

### 执行时删什么：一次事务、全有或全无

`identity` 与 `profile` 分表分权限的前提已经铺好，**使注销与数据导出能按数据类别定位**（`operations/environments.md`）。执行即按数据类别逐条落：

| 对象 | 处置 | 依据 |
|---|---|---|
| `identity` 行 | **硬删除** | 渠道身份是个人信息；删后同一渠道身份再登录即建**新** `accountId`，进度不恢复 |
| 实名材料（姓名 / 证件号 / 出生日期） | **硬删除** | 最敏感的一项 |
| `profile` 行 | **硬删除** | 玩家进度 |
| `signin_replay` · `compliance_ticket` · `session` | **硬删除** | 含 `identifier_mac` 与活凭据 |
| `export_task` 与其对象存储产物 | **硬删除** | 产物含个人信息 |
| 风控事件（`risk_event` 中该账号的全部条目） | **硬删除** | 已定性为可关联到个人的行为数据 |
| `nickname_review`（该账号的全部条目） | **硬删除** | 含玩家提交的昵称串与判定记录，属可关联到个人的行为数据 |
| `nickname_scan`（该账号的一行） | **硬删除** | 含 `last_accepted_nickname` |
| `push_idem` | **硬删除** | 无独立价值，随 profile 走 |
| `account` 行 | **保留墓碑**：`account_id` + `created_at_utc` + `deleted_at_utc`，其余列置空 | 见下 |
| `receipt_idem` | **保留全行** | 见下 |
| `deletion_audit`（该账号的注销申请 / 撤销条目） | **保留全行** | 见下 |

**三条保留各有硬理由，不是偷懒：**

- **`receipt_idem` 必须保留。** 它的 `receipt_id` 全局唯一是**防重复发放的唯一防线**（永久保留、不设 TTL，且配置层有一条启动期断言，见 `operations/purchase-ops.md`）。删掉它 = 同一张收据可被新账号再核销一次，且**线上不可发现**——第二次提交查不到记录即当作新票，没有任何报错，攻击形态明确：买一次 → 注销 → 重建号 → 再核销同一张票。它含 `account_id` 但不含个人信息；交易记录另有法定保存期。
- **`account` 墓碑必须保留**，否则 `receipt_idem.account_id` 悬空、退款对账通道断裂。墓碑不含任何个人信息、**不可关联到自然人**，只是一个已删除标记加时间戳。**它不进 `account.status` 枚举**（契约四值不动）——「已删除」由 `deleted_at_utc` 非空表达，而已删除账号在任何端点上都不可达（identity 已删，无从登录）。

- **`deletion_audit` 必须保留**（保留期 3 年，与本次执行无关）。撤销即删 `account_deletion` 行 ⇒ 这张表是「谁在什么时候申请过 / 撤销过」在库内的唯一留痕，而这条路径直接决定账号是否被删除；在执行时把它一并删掉，等于在**最需要它举证的那一刻**销毁唯一的证据（一次「我明明撤销过」的客诉往往在半年、一年后才到）。它的条目**不含任何个人信息**，与 `account` 墓碑同一性质，故长留不构成个人信息超期留存。形态见 `operations/moderation.md`。

删除权针对的是个人信息；保留不可关联到自然人的内部键与审计留痕，换来一条不可发现的重复发放漏洞被永久堵死、一条删号客诉可举证。

**执行必须在一次事务内完成、全有或全无**：删到一半崩溃 ⇒ 回滚 ⇒ 下一轮重新领取。逐表删除的顺序按外键依赖排即可，不需要额外机制。

Source: `handoffs/2026-09-06-compliance-domain-storage.md` · `handoffs/2026-09-08-risk-ledger-storage-shapes.md`（删除清单的三张风控台账与 `deletion_audit` 的保留）。

## 数据导出：任务 · 产物 · 链接签发

### 任务表与一条数据库不变式

`export_task` 的承重列见 `systems/account.md`。其中**部分唯一索引是承重项**：契约的幂等语义是「命中既有未过期的在办任务时回同一 `taskId` + `deduplicated`」，而两次并发申请若靠应用层「先查再插」会各建一个任务。把它落成**数据库不变式**，与「单账号活跃会话上限 1」是同一手法——**并发下只有约束是可靠的**。

- 命中冲突 ⇒ 读出既有行回幂等应答（同 `push_idem` 的「主键冲突 ⇒ 读出回幂等应答」处置）。
- 上一个任务为失败 / 已过期时索引不再拦截 ⇒ 自动建新任务、给新 `taskId`。

### 产物存储：私有对象存储桶，绝不走 CDN

- 载体 = 对象存储的**私有 bucket**，与内容分发用的公开 bucket **分开**：不同权限边界、不同保留策略、不同审计线。
- **导出产物绝不进 CDN。** 内容分发侧的 CDN 形态是内容寻址对象 + 一年期 immutable 长缓存（`operations/content-delivery-ops.md`）——把含个人信息的产物放进那条通道，等于把它复制到全部边缘节点，且**缓存生命周期不受保留期控制**，删了源对象边缘仍可能命中。这条是护栏，不是优化建议。
- **`object_key` 与 `taskId` 解耦**：对象键取「年 / 月 / 32 位随机 hex」。`taskId` 会出现在客户端、URL path 与日志里；若用它作对象键，「拿到 `taskId` 即能构造对象路径」，不可枚举就只剩签名一道。两者解耦是**纵深防御**，与契约对 `taskId` 拒绝时间前缀时那句「不可枚举性是纵深防御，不是访问控制」同一取向。

### 链接签发：每次查询现签一枚短寿命预签名 URL（承重）

**`downloadExpiresAtUtc` 是产物保留期的终点，不是链接的寿命。** 照字面把它当链接有效期实现，会签出一枚**7 天有效、无鉴权、可直下含个人信息文件**的凭据，它会落进浏览器历史、下载管理器、剪贴板与任何一次截屏。

正确形态：

- 查导出任务的端点**每次应答都现签一枚新的预签名 URL**，单次有效期 **15 分钟**。`downloadUrl` 因此是每次应答各不相同的临时值——契约没有要求它稳定，客户端的用法是「拿到即用系统浏览器打开」。
- **`downloadExpiresAtUtc` 仍下发产物保留期终点**，它回答的是「这份产物还能取到多久」。玩家在保留期内任意时刻重新查一次即可拿到新链接。
- 签名时一并指定附件式的内容处置头与 JSON 内容类型，避免浏览器内联渲染个人信息。
- 15 分钟的推导：覆盖玩家从看到按钮、到系统浏览器起下载、到一次失败重试；产物是单份 JSON（KB–MB 级），不存在长时续传需求。**待实测校准。**

### 生成执行与有限重试

- 领取形态与冷静期扫描逐字相同（`FOR UPDATE SKIP LOCKED` 扫待生成任务），**不引入消息队列**——本域也没有削峰需求，导出限流是每账号 24 小时一次。
- **有限重试**：尝试次数达上限 **3 次**后置为失败终态。没有重试，一次数据库抖动就让玩家白等满一个限流窗口才能重新申请；没有上限，一个永久失败的任务会被无限重领。
- 失败**不带原因取值**（契约已定），内部原因只进日志与指标。

### 产物内容：白名单序列化器 + 一条断言

契约已把产物定成**正列白名单**（profile 整份 + 账号的三项，身份条目每条仅渠道与绑定时刻）。落地时加一条自动断言，与内容发布侧的校验闸同一取向：

```
产物顶层键集合            == { profile, account }
account 的键集合          == { accountId, createdAtUtc, identities }
identities 每项的键集合   == { channel, boundAtUtc }
```

理由：白名单靠人自觉必然漂移，而这是**一份直接交到玩家手里的文件**——漏一个内部字段出去不可撤回。断言校验的是一份 JSON，可作为普通检查步骤挂在既有流水线上。

### 保留期落地：两道，缺一不可

| 层 | 做什么 | 缺了它会怎样 |
|---|---|---|
| **应用层过期扫描**（主路径） | 到产物保留期 ⇒ 删对象 + 置为已过期；到记录保留期 ⇒ 整行删除 | 只靠桶规则 ⇒ 对象没了但状态仍是就绪，客户端拿到一枚指向不存在对象的链接 |
| **对象存储生命周期规则**（兜底） | 桶级自动删除，**留余量**（建议 8 天而非 7 天） | 只靠应用扫描 ⇒ 扫描任务失效时**个人信息无限期留存**，是一次静默的合规事故 |

- 「已过期」这个状态被契约刻意保留（玩家几天后回来点旧入口时，「已过期，重新申请一次」与「找不到」是两句完全不同的话），**因此记录保留期长于产物保留期**，两个时刻分开而不是共用一个。
- **兜底规则的余量要留**，使应用层始终是先动手的那一个，否则兜底会抢在扫描之前删掉对象、制造上表第一行那种不一致。

### 日志与观测

- **`downloadUrl` 绝不落日志**——它是一枚含签名的临时凭据。日志脱敏是一处白名单式序列化而不是各处自觉，本条是该白名单的一员（`operations/observability.md`）。
- 三条运维探针（口径见 `operations/observability.md`）：生成时长分布 · 失败率 · **到期扫描的滞后量**（阈值应恒接近 0——它是「个人信息超期留存」唯一的机制发现面）。

Source: `handoffs/2026-09-06-compliance-domain-storage.md`。

## 周期任务与旋钮的校准信号

本域共用一条周期任务通道（形态与出口登记见 `operations/environments.md`「定时任务出口」），四条任务全部走 `FOR UPDATE SKIP LOCKED` 的条件转移，零新增组件：

| 任务 | 触发 | 备注 |
|---|---|---|
| 注销冷静期到期执行 | 到 `effective_at_utc` | 唯一不可逆动作，时钟异常时暂停一轮 |
| 导出任务生成 | 有待生成任务 | 有限重试 3 次 |
| 导出产物与记录的到期清理 | 到各自保留期 | 桶级生命周期规则兜底 |
| `complianceTicket` 过期清理 | 过期后 24 小时 | 按批删除 |

**旋钮的取值权威不在本文件**（契约 §9 + `operations/environments.md` 旋钮清单）；本表只给校准信号——线上哪个指标动了就该改这个值。

| 旋钮 | 校准信号 |
|---|---|
| 实名提交次数上限 | 命中 `rate.limited` 的账号占比 > 1% ⇒ 上限偏低；核验拒绝后同日仍重试的次数分布是直接依据 |
| 导出申请限流 | 命中数应**恒接近 0**（正常玩家一生几次）；非零即客户端重试风暴或滥用，先查客户端再动值 |
| `pollAfterSeconds` | 生成时长 p95：若 p95 > 15 秒则提到 p95/3 量级，避免无效轮询把端点打成高频面 |
| 导出下载链接的单次签发有效期 | 下载失败率与「同一任务连续重新查询」的频次；两者同时抬头即偏短 |
| 导出生成重试上限 | 重试后成功的占比：恒为 0 说明失败是确定性的、加大上限无用；接近 1 说明上限偏低 |
| 合规周期任务的扫描间隔 | 到期扫描滞后量；它长期非零即间隔偏长或批量偏小 |
| 时钟偏差警告 / 告警阈值 | 稳态下应恒为 0 命中；持续非零即授时配置有问题，先修配置再动阈值 |
| 时段日历到期告警提前量 | 若连续两年在告警后仍来不及录入，提高到 90 天 |

**两条计数落点：**

- **实名限流的计数落 Postgres，且 fail-closed。** 核验服务按次计费，命中「错误放行的代价不可回收」这条例外判据（`operations/environments.md`「限流的实现分层」）；计数不可用时对该端点返回 `rate.limited`。
- **导出限流零新增存储**：`export_task` 表本身就是计数器——「24 小时内该账号是否已有任务行」是一次索引查询，不必再立一份计数。

## 上线分级

本文件的能力**形态与上线时点是两件事**：形态在此定死，时点在 `operations/deployment.md` 的两份发布前置清单上过闸。分档结论如下，**不改动本文件的任何形态**：

| 能力 | 落位 | 过闸清单 |
|---|---|---|
| 实名核验（含 ticket 兑付与外部核验调用） | 首版必备 | 「首个真实账号建号之前」第 5 项 |
| 防沉迷时段判定（时钟 · 规则集 · 日历 · 三个失败面） | 首版必备 | 同上，第 6 项 |
| 账号注销（冷静期状态机与执行） | 首版必备 | 「首次面向公众发行之前」第 1 项 |
| 数据导出（任务 · 产物 · 链接签发） | 首版必备 | 同上，第 2 项 |

分档判据是「**后置之后再补，是否需要对存量账号做一次追溯动作**」——这正是本文件把年度日历录入排除在第一份清单之外时用的同一条（那一条每年重来一次，不共用那个不可逆时刻）。可后置的是各项的增强项，不是能力本身：实名的证件类型扩展与第二家供应商 · 日历的第三方交叉核对 · `MinorCurfew` 与 `MinorDailyLimit` 在监管口径拆开后的差异化 · 导出产物的内容扩类。四项均无「先上线后补」的形态——拦截只在 `signin`、四码求值顺序写死、无灰度旋钮。
