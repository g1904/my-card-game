# deployment —— 构建 · 发布 · 迁移 · 回滚 · 上线核对

从一次提交到线上生效的完整路径。环境实体与配置分层见 `environments.md`；内容 overlay 与 flags 的发布流程是另一条独立通道，见 `content-delivery-ops.md`。

## 构建与制品

- **镜像 tag = commit sha，不可变。** 同一个 tag 永远对应同一份字节。
- **三处环境跑同一个 artifact，只有配置不同**——「在 testing 验过的东西」与「上生产的东西」必须是同一个制品，否则 testing 的同构性没有意义。
- **代码可回滚**：回滚 = 把服务指回一个更早的镜像 tag。

## 数据库迁移

**强制在线 · 云端权威 ⇒ 没有停机窗口。** 因此：

- **迁移与代码发布分离，走 expand → deploy → contract 三步**：先加（新列 / 新表 / 新索引，与旧代码兼容）→ 再发新代码 → 确认稳定后才删（旧列 / 旧路径）。
- **迁移只前滚、不回滚。** 代码可回滚镜像 tag，**schema 不回滚**——这与内容侧「回滚 = 一次以历史内容发起的更大版本发布」是同一条纪律：向后走的路只有一条，就是继续向前发一版。
- expand 与 contract 之间必须至少隔一次完整的稳定观察，否则 contract 会把回滚路径一起删掉。

## 网关配置的两条纪律（承重）

托管网关的默认全局限流是这两条最现实的破坏源，因此它们是**上线核对项，每次发布逐次过闸**，不是一次性配置。

| # | 纪律 | 破坏后果 |
|---|---|---|
| G-1 | **`/v1/auth/refresh` 上不得存在任何返回限流码的限流。** 该端点的错误清单刻意只有两条，客户端的两条处置路径靠「报文层面只有两种可能」才无歧义。滥用面靠**记账 + 告警**承接，不返回限流码 | 网关静默加一条限流 ⇒ 客户端收到清单外的 `code`，两条处置路径的互斥前提当场失效 |
| G-2 | **push 滥用阈值走应用层的账号维度，不走网关默认的 IP 维度全局限流** | 移动网络 NAT 下按 IP 限流会误伤整个小区的玩家 |

> 若日后认定 refresh 必须限流，须回改契约**并同时给客户端第三条处置路径**——**不能只在网关侧悄悄加**。

## 发布前置清单：首个真实账号建号之前

下列四项**共用同一个不可逆时刻**：首批真实账号落地的那一刻，「线上无真实账号数据」这个前提永久失效，而这四项全都依赖它。因此它们作为**一份清单一起过闸**，不各自记在各自的文档里。

| # | 项 | 为什么在这一刻之前 |
|---|---|---|
| 1 | **全部透明路径的命名定稿** | 此后重命名不再能一次性切换，需要一次全量存量迁移（`decisions/ADR-0014-*`） |
| 2 | **`Source` / `AccountStream` 的成员名与整数值冻结** | 存档侧靠整数、契约侧靠名，两者都是稳定键，重命名在两侧都是破坏性变更 |
| 3 | **`accountId` 形态定稿** | 它进入每一条存量记录（`decisions/ADR-0010-*`） |
| 4 | **微信开放平台资质 + 以 `unionid` 建 identity** | 以 per-app 标识建立的 identity 在新增第二个应用时会分裂，届时统一需要全量身份迁移（`contracts/auth.md` §3a）。支付侧渠道排期不影响本条——它是登录侧的不可逆决定 |

**域名备案与国内发行资质**与本清单同批推进（`environments.md`）。

## 内容发布侧的能力要求

内容 overlay 的发布流程、签名与校验闸的权威在 `content-delivery-ops.md`；本节只记它对**部署与制品管理**提出的一条要求：

- **发布侧须能取到每个在架客户端版本的基线内容快照。** 校验闸要对每个在架基线各跑一遍以检出基线漂移，而基线快照若只存在于某次构建的产物里，发布侧就取不到它。**因此基线快照要随客户端发版一起归档到发布侧可达的存储**（对象存储的固定路径 + 与客户端版本号一一对应的键），而不是依赖构建产物的保留期。
- 在架版本集合的权威是版本兼容矩阵（`version-matrix.md`）——「哪些基线要跑」由它给出，不另立一份清单。

## 契约变更的完成判据与机检断言

契约变更的完成判据六条与三条机检断言的权威在 `contracts/_index.md`。本形态**具备承接能力**：断言校验的是 markdown 与 YAML / JSON，可作为普通检查步骤挂在同一条流水线上，与镜像构建互不依赖。

**承载位置本身（有无自动化流水线、跑在哪里）仍是一条待答项**（`open-questions/01-contracts.md`），在此之前以人工清单执行。

## 同语言不解锁共享 DTO（护栏）

后端选 C# 之后，「都用 C# 了，不如让两侧共享一套 DTO 程序集」会被反复重新提出。**这条已被明确否决——即使后端最终也选 C#**（`decisions/ADR-0003-*`）。

它否决的是**跨边界的编译期依赖**，不是同语言本身：共享 DTO 会把两条独立的分支线焊在一起，使客户端发版节奏与后端发版节奏互为约束，而契约的单一事实来源是 spec，不是任何一侧的代码。**要复议，须先驳倒这一条。**
