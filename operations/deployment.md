# deployment —— 构建 · 发布 · 迁移 · 回滚 · 上线核对

从一次提交到线上生效的完整路径。环境实体与配置分层见 `environments.md`；内容 overlay 与 flags 的发布流程是另一条独立通道，见 `content-delivery-ops.md`。

## 构建与制品

- **镜像 tag = commit sha，不可变。** 同一个 tag 永远对应同一份字节。
- **三处环境跑同一个 artifact，只有配置不同**——「在 testing 验过的东西」与「上生产的东西」必须是同一个制品，否则 testing 的同构性没有意义。
- **代码可回滚**：回滚 = 把服务指回一个更早的镜像 tag。

## 数据库迁移

**强制在线 · 云端权威 ⇒ 没有停机窗口。** 因此：

- **迁移与代码发布分离，走 expand → deploy → contract 三步**：先加（新列 / 新表 / 新索引，与旧代码兼容）→ 再发新代码 → 确认稳定后才删（旧列 / 旧路径）。
- **迁移只前滚、不回滚。** 代码可回滚镜像 tag，**schema 不回滚**——这与内容侧「回滚 = 一次以历史内容发起的更大版本发布」是同一条纪律：向后走的路只有一条，就是继续向前发一版。
- expand 与 contract 之间必须至少隔一次完整的稳定观察，否则 contract 会把回滚路径一起删掉。

## 网关配置的两条纪律（承重）

托管网关的默认全局限流是这两条最现实的破坏源，因此它们是**上线核对项，每次发布逐次过闸**，不是一次性配置。

| # | 纪律 | 破坏后果 |
|---|---|---|
| G-1 | **`/v1/auth/refresh` 上不得存在任何返回限流码的限流。** 该端点的错误清单刻意只有两条，客户端的两条处置路径靠「报文层面只有两种可能」才无歧义。滥用面靠**记账 + 告警**承接，不返回限流码 | 网关静默加一条限流 ⇒ 客户端收到清单外的 `code`，两条处置路径的互斥前提当场失效 |
| G-2 | **push 滥用阈值走应用层的账号维度，不走网关默认的 IP 维度全局限流** | 移动网络 NAT 下按 IP 限流会误伤整个小区的玩家 |

> 若日后认定 refresh 必须限流，须回改契约**并同时给客户端第三条处置路径**——**不能只在网关侧悄悄加**。

## 发布前置清单：首个真实账号建号之前

下列六项**共用同一个不可逆时刻**：首批真实账号落地的那一刻，「线上无真实账号数据」这个前提永久失效，而这六项全都依赖它。因此它们作为**一份清单一起过闸**，不各自记在各自的文档里。

判据即「**后置之后再补，是否需要对存量账号做一次追溯动作**」——需要则不得后置。年度法定节假日日历的录入不在本清单内，正是因为它每年重来一次、不共用那个不可逆时刻（见下方「启动自检与周期性运维日程」）。

| # | 项 | 为什么在这一刻之前 |
|---|---|---|
| 1 | **全部透明路径的命名定稿** | 此后重命名不再能一次性切换，需要一次全量存量迁移（`decisions/ADR-0014-*`） |
| 2 | **`Source` / `AccountStream` 的成员名与整数值冻结** | 存档侧靠整数、契约侧靠名，两者都是稳定键，重命名在两侧都是破坏性变更 |
| 3 | **`accountId` 形态定稿** | 它进入每一条存量记录（`decisions/ADR-0010-*`） |
| 4 | **微信开放平台资质 + 以 `unionid` 建 identity** | 以 per-app 标识建立的 identity 在新增第二个应用时会分裂，届时统一需要全量身份迁移（`contracts/auth.md` §3a）。支付侧渠道排期不影响本条——它是登录侧的不可逆决定。**过闸断言 = 在 `backend-testing` 环境完成一次真实的微信登录，服务端取到非空 `unionid`，且该条 identity 的 `idKind` 落为 `unionid`**：一份「审核通过」的凭证证明不了我方代码实际走的是 `unionid` 分支，而那正是不可逆的那一条。前置链与延误处置见 `operations/external-providers.md` |
| 5 | **实名核验能力在线** | 它是防沉迷判定的唯一数据源（`contracts/compliance.md` §7），且后置需要一次存量追溯：积累一批未实名账号后启用，`compliance.realname_required` 对全体存量同时成立，是一次全量拦截潮，而拦截只在 `signin`、四码求值顺序写死、**无灰度旋钮**。**过闸断言 = 在 `backend-testing` 环境完成一次真实核验，`realnameStatus` 落 `Verified`、`isMinor` 由核验回传的出生日期算得；且 `realName` / `idNumber` 在应答、日志与 `response_snapshot` 中零出现**（对位 `systems/account.md` C6） |
| 6 | **防沉迷时段判定在线** | 实名一旦在线，服务端就已经知道某账号是未成年——知情而不限制的合规敞口大于两项都不上。它也是合规四项里唯一会在会话中途生效的能力（`contracts/compliance.md` §7 五步映射）。**过闸断言 = 时段规则集与当年日历已发布至 `version ≥ 1` 且含 `WorkingWeekend` 条目；启动自检解析时区名通过；对一个已判未成年的测试账号，在非允许时段 `signin` 得 `compliance.playtime_blocked` + `detail.resumeAtUtc`** |

**域名备案与国内发行资质**与下方第二份清单同批推进（`environments.md`）。

**第 4 项是清单上唯一一项完成时刻不由我方决定的**——其余五项想定就能定（第 5、6 项只依赖我方接入与配置），它的每一环都是外部审批。因此它的资质链与域名备案**同批发起**，不排在上线路径的末端；若审批未在计划上线日前到位，**推迟上线，不以 `openid` 先行建号**。以 `openid` 建号的代价随存量账号数增长，而任何形式的事后回填都会撞上「绝不做隐式账号合并」（`contracts/auth.md` §1a）——那条禁令保护的是玩家的存档。

## 发布前置清单：首次面向公众发行之前

合规域的另两项能力**不绑上一份清单那个不可逆时刻**——它们后加不产生存量追溯动作；绑的是渠道闸：**首次面向公众发行**。因此单列一份，与域名备案 / 国内发行资质、以及内部处置台同批推进（`environments.md` 已定二者是上线时序的前置）。

| # | 项 | 过闸断言 |
|---|---|---|
| 1 | **注销两端点可用** | `POST /v1/compliance/deletion` 与 `POST /v1/compliance/deletion/cancel` 在 `backend-testing` 走通一次完整的申请 → 撤销，且客户端**有 App 内可达入口**（客户端侧对位，权威在 `game-design-documents/systems/services/account-service.md`，本库不复述）。PIPL 要求删除权，国内应用商店审核实测「App 内可注销」，而走站外已被 `contracts/compliance.md` §1 否决 |
| 2 | **导出两端点可用** | `POST /v1/compliance/export` 与 `GET /v1/compliance/export/{taskId}` 走通一次异步任务，且产物白名单三条断言（`operations/compliance-ops.md`）在流水线上绿灯 |
| 3 | **域名备案与国内发行资质到位** | 权威在 `environments.md`，此处只作过闸登记 |
| 4 | **内部处置台可用** | 在 `backend-testing` 走通一次完整的昵称复核（领取 → 判定 `Violation` → `nickname_scan.review_state` 落「须改名」档、云端 `/accountInfo/nickname` 一字未变）与一次完整的工单处置（领取 → `Ban` → 该账号全部会话被吊销 → 一条 `operator_audit` 已落）；且 `realName` / `idNumber` 在两条链路的应答与日志中零出现；入站运维通道（堡垒机或 VPN）已就位、内部监听不对公网暴露。形态见 `operations/internal-tools.md`。公开发行后复核级命中与风控阈值触发会持续产生待办，无人能处置即合规敞口，且「人必须在回路里」在没有面的情况下无法兑现 |

**两份清单的未就绪处置相同：推迟上线，不降级放行。** 合规项没有「先上线后补」的形态——拦截只在 `signin`、四条码的求值顺序写死、无灰度旋钮，能力关掉会让求值顺序出现一个未定义的空档。这与第一份清单第 4 项对微信资质的处置是同一条纪律（`decisions/ADR-0042-*`），不新造。

## 内容发布侧的能力要求

内容 overlay 的发布流程、签名与校验闸的权威在 `content-delivery-ops.md`；本节只记它对**部署与制品管理**提出的一条要求：

- **发布侧须能取到每个在架客户端版本的基线内容快照。** 校验闸要对每个在架基线各跑一遍以检出基线漂移，而基线快照若只存在于某次构建的产物里，发布侧就取不到它。**因此基线快照要随客户端发版一起归档到发布侧可达的存储**（对象存储的固定路径 + 与客户端版本号一一对应的键），而不是依赖构建产物的保留期。
- 在架版本集合的权威是版本兼容矩阵（`version-matrix.md`）——「哪些基线要跑」由它给出，不另立一份清单。

## 启动自检与周期性运维日程

- **启动自检解析时段规则集的时区名**（IANA 名，例 `Asia/Shanghai`），解析失败即**拒绝启动**。精简基镜像默认不含 tzdata，缺失时的表现是运行期合规判定当场抛异常——这是一次典型的「本地跑得通、云上跑不通」，而启动断言是它唯一可靠的发现面。取向同 `purchase-ops.md` 对收据表 TTL 策略的启动期断言。
- **年度法定节假日日历的录入是一条周期性运维日程项**（每年 12 月，次年放假安排通常 11–12 月发布）。它**不并入**上方「首个真实账号建号之前」那份清单——那份清单的成立前提是四项共用同一个不可逆时刻，而本条每年重来一次。到期未录入的机制发现面是 `observability.md` 的日历到期告警。形态见 `operations/compliance-ops.md`。
- **合规域三张新表**（`compliance_ticket` · `account_deletion` · `export_task`）**与 `account` 的 `deleted_at_utc` 列**走上方 expand → deploy → contract 三步；线上尚无真实账号，**无既有数据迁移**。

## 契约变更的完成判据与机检断言

契约变更的完成判据六条与三条机检断言的权威在 `contracts/_index.md`。**它们不挂在本节描述的构建流水线上**：断言校验的是 markdown 与 YAML / JSON、零云资源依赖，承载为**设计库分支（`backend-design`）上的一条独立 workflow**（`contract-spec-check`，push + 手动触发，路径过滤 `contracts/**` 与校验脚本自身），与镜像构建**无依赖**。**该 workflow 与校验脚本尚未落地；在此之前三条断言以人工清单的前三项形式执行。**

分处两条流水线是形态使然而非取舍：`contracts/` 只存在于 `backend-design`，而镜像构建跑在 `backend-feature` 且需云侧镜像仓库凭据。让镜像构建跨分支检出设计库去跑一条纯文本检查，会把两条本应独立的分支线在 CI 层重新耦合起来。

- **绿灯 = 完成判据第 4 条的兑现物**：该次提交上的 workflow 结论即「三条机检断言通过」这个可勾选项。
- **红灯 = 该次契约变更未完成**（六条判据是合取），修复形式是**前滚一次提交**，与迁移的「只前滚」同向；红灯期间不得据该契约推进实现或跨库 handoff。
- **无条件触发、不设跳过开关**，与 `content-delivery-ops.md` C3 同构。但 C5 的「阻断 = 什么都还没发生」在此**不成立**——提交已进入历史，阻断的对象是「变更被视为完成」，不是产物生成。
- **失败走代码托管方的默认通知，不接入 `observability.md` 的告警面**——那是线上服务的告警口径，混进工程流水线的红灯会稀释它的信噪比。
- **同一套检查须能在本地以一条命令跑完**，CI 只是它的无人值守执行；只能在 CI 上跑的检查会把「变更内原子」拖成「推上去再说」。

## 同语言不解锁共享 DTO（护栏）

后端选 C# 之后，「都用 C# 了，不如让两侧共享一套 DTO 程序集」会被反复重新提出。**这条已被明确否决——即使后端最终也选 C#**（`decisions/ADR-0003-*`）。

它否决的是**跨边界的编译期依赖**，不是同语言本身：共享 DTO 会把两条独立的分支线焊在一起，使客户端发版节奏与后端发版节奏互为约束，而契约的单一事实来源是 spec，不是任何一侧的代码。**要复议，须先驳倒这一条。**
