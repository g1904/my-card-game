# 内容分发的运维形态

> 语义权威在 `contracts/content-manifest.md`；本文件只记它对运维形态的**要求**，以及由此反向落在托管选型上的约束。
> Source: `handoffs/2026-08-11-content-delivery-manifest-signing-and-flags.md` · `handoffs/2026-08-23b-flags-version-monotonic.md`（flags 发布 / 回滚流程与留痕四项）· `handoffs/2026-09-03-content-delivery-ops.md`（flags 规则集存储与变更通道 · 签名私钥保管与 `keyId` 轮换 · 发布侧校验闸）。


- **CDN 缓存：两类对象两种 TTL。** `/blobs/<hash>` 内容寻址 → `public, max-age=31536000, immutable`（可永久缓存）；manifest / flags 端点 → `no-cache` 或秒级 TTL——**秒关与回滚的实际生效速度由后者决定**。

## 内容发布流水线（顺序即正确性）

```
⓪ 产物认证核对   证明存在 ∧ 逐文件 hash 与待推集一一对应   失败→非零退出，无补偿
① 推 blob        SHA-256 内容寻址，幂等跳过已存在的 hash
② 生成 manifest  contentVersion = 内容版本高水位 + 1
③ 签名           密钥服务对 manifest 原始字节做 ES256
③b 编码归一      DER → IEEE P1363（密钥服务返回 DER 时必做）
④ 自验           用客户端内置的那份公钥验签，失败即中止
⑤ 确认 blob 可读  对 files[] 逐一或抽样探针 GET
⑥ 原子发布       .sig 先于或与 manifest 同一次切换
⑦ 留痕           内容发布留痕八字段（见下）
```

- **④ 自验是承重步，且必须用客户端内置的那份公钥**（不是从密钥服务现取的那份）。验签失败在客户端的表现是「拒绝 overlay + 回退基线 + 上报一次事件」——不崩，只是**静默地让全体玩家收不到这次更新**，症状与网络不好难以区分。用内置公钥验，验的才是「玩家手里那把钥匙能不能验通」。
- **③b 存在的理由**：ECDSA 签名有 IEEE P1363（`r‖s` 定长）与 ASN.1 DER（变长）两种编码，`ES256` 定义为前者、客户端 .NET 的 `ECDsa.VerifyData` 默认期望前者，而多数密钥服务的签名 API 返回后者。这是典型的「两侧各自都没错、合起来不通」：签名生成毫无报错，客户端 100% 验签失败，且只在真机集成时暴露。编码形态见 `contracts/content-manifest.md`「防篡改」。
- **`contentVersion` 的分配形态与 `flagsVersion` 同构、但是两条独立序列**：单调高水位、只在发布动作时分配、备份恢复后取 `max(恢复值, 高水位)` 并强制跳号（O2 / O3 的失效模式对它逐字成立，而客户端对它有「更大即增量更新」的判据）。两条序列**不合并**——发布节奏完全不同，合并会让一次秒关白白推高 `contentVersion`。
- **`contentVersion` 的分配由后端受权限保护的发布动作承担，流水线不持有直连库凭据**（理由同下方 A3 的直连写入禁令）。
- **回滚 = 重跑 ⓪–⑥，manifest 指回旧 blob，`contentVersion` 继续前进**（不允许版本号回退）。
- **秒关 / 灰度不触碰 blob 与 manifest，不走这条流水线**，它有自己的一条发布流程（见下），同样产出一个更大的 `flagsVersion` 并留痕。
- **签名是流水线上最后一个产生可分发产物的动作**（⑤ ⑥ 只做探针与切换，不产生新产物）。

## 发布侧内容校验闸

**分工的准确切法。** 客户端保证「凡是打包工具产出的包，都过了闸」；它**没有也无力**保证「凡是被发布出去的文件集，都是打包工具产出的」。后者是本库的义务，也是这条链上唯一还敞着的口子——一个手工塞进目录的文件、一次「就改一个字、不重新产包了」的操作，会绕过整道闸而客户端毫无察觉。故本库那一半**不是**「在流水线里再跑一遍校验」（那会造出第二份实现，与对侧规则随时漂移），而是：**发布流水线拒绝任何没有打包工具背书的文件集**。校验规则本身的权威在对侧，本库不复述：`game-design-documents/systems/services/content-service.md`、`.../systems/architecture.md`「纪律的可执行化」、`.../decisions/ADR-0013-discipline-enforceability-ladder.md`、`.../decisions/ADR-0125-no-binary-over-overlay.md`。

| # | 要求 |
|---|---|
| C1 | **产物认证核对（步 ⓪）**：打包工具与文件集同批产出一份**机读的产包证明**，至少含工具版本 · 所用基线的 `appVersion` · 校验通过的断言项计数 · 逐文件 `path` + `sha256`（字段形态归客户端）。步 ⓪ 核对两件事：证明存在且自洽 · 证明的文件清单与待推文件集**逐文件 hash 一一对应，不多不少**。不一致 / 缺失 → 中止、非零退出。**用一次 hash 比对把对侧的闸延伸到发布面，不在本库复制任何一条校验规则** |
| C2 | **位置 = 最前（推 blob 之前）**。三条独立理由：完整文件集在产包结束即具备 · blob 是内容寻址 + `immutable` 长缓存的永久对象，不合格产出一个字节都不该落到分发面 · 失败无需任何补偿动作 |
| C3 | **触发方 = 流水线自身、无条件，不设跳过开关**。人可以跳过的闸不是闸；紧急发布走同一条路径——紧急场景恰是最易出引用图错误的场景。若日后确需 break-glass，须与 O5 同构留痕并触发告警，而不是一个静默的命令行参数 |
| C4 | **校验在签名之前**，中间隔着推 blob 与生成 manifest。**签名即背书**：先签后验会产生「已签名但不合格」的产物，它一旦离开流水线（哪怕只落到中间存储），在密码学上与合法产物无法区分 |
| C5 | **阻断形态 = 该步非零退出，①–⑦ 全不执行**。闸在最前 ⇒ 阻断天然等于「什么都还没发生」：无孤儿 blob、无 manifest、无签名、无留痕需要撤销。阻断路径因此不需要补偿逻辑，而补偿逻辑正是这类流水线里最易写错、最少被测试的部分 |
| C6 | **基线漂移**：闸的规则里有「必须存在于基线」这一类判据，故闸的输入不只是待发 overlay，还有一份基线内容集。一次 overlay 会被多个在架客户端版本消费，各自的 `res://` 基线不同 ⇒ 闸须对**兼容矩阵内每一个 ≥ 本次 `minAppVersion` 的在架基线各跑一遍**，全部通过才算通过（并存版本数是个位数，成本可忽略）。不采用「只跑最新基线」的简化——它需要「更高版本基线是更低版本基线的超集」这个本库不裁决且不必然成立的前提。**发布侧须能取到每个在架版本的基线内容快照**，该能力要求的落点见 `deployment.md`。`minAppVersion` 在此是一个真正的旋钮：某个老基线过不了闸时，提高它是合法且已被契约支持的处置 |

**内容发布留痕（步 ⑦）八字段**，与 flags 留痕**同构但不合并**（另一条版本轴、另一种爆炸半径、另一套回滚语义；合并后要靠字段是否为空去猜这一条是内容发布还是秒关）：`contentVersion` · `publishedBy`（具名人类身份）· `publishedAtUtc`（RFC 3339 UTC）· `derivedFrom`（正常发布 = 上一版，前滚 = 被回指的版本）· `summary`（文件增 / 改 / 删计数 + 本次 `minAppVersion`）· `manifestSha256`（manifest 原始字节的摘要，是「这一版到底签的是什么」的唯一凭据）· `keyId`（轮换期排查的第一现场）· `gateAttestation`（打包工具版本 · 所用基线 `appVersion` · 断言项计数）。

> `gateAttestation` 单列的理由：闸的规则由客户端实现且**会随客户端版本演进**。事后追一次事故时，「这一版内容是被**哪一版规则**校验过的」是唯一能把内容与当时纪律对上的凭据；不记它，日后只能靠发布日期去猜工具版本。

留痕与 flags 留痕同处后端主存储（另一张表），不落 CI 产物——它须能长期查询，且与版本序列同事务边界，而 CI 产物有保留期。

## flags 规则集的存储形态与变更通道

| # | 要求 |
|---|---|
| A1 | **规则集是后端主事务性存储中的一条不可变版本化记录。** 字段：`flagsVersion`（主键）· `rules`（规则本体：`disabledIds` 的规则来源、分桶比例、白名单、篇章档位）· `bucketSalt` · `derivedFrom` · `publishedBy` · `publishedAtUtc` · `summary` / `scope` · `contentFingerprint`。另一条单行记录承载 `flagsVersionHighWater`，**插入规则集与推进高水位在同一次事务内**（O2 / O3）。**这些字段全部是后端内部形态，一个都不下发**（载荷边界见 `decisions/ADR-0002-flags-channel-content-enabled-scope.md`） |
| A2 | **分桶盐值 `bucketSalt` 必须是规则集的字段、随版本冻结**，不得是环境变量 / 部署配置。盐放在部署配置里意味着改一次配置就改变全体账号的解析结果**而版本号一动不动**——与「手工改规则」同一个静默失效模式，只是换了个更隐蔽的入口。推论：规则集不可变 ⇒ 盐随版本冻结 ⇒ **分桶函数天然是 `(accountId, 规则集版本)` 的纯函数**，B 组第 7 条的后半句因此是存储形态的直接后果，而非一条要靠实现者记住的纪律 |
| A3 | **唯一写入面是一个发布动作** `publish(draft, summary, scope)`：分配 `flagsVersion` = 高水位 + 1、插入记录、推进高水位，同一事务。`rollback(to: v_k)` ≡ `publish(rules = v_k.rules, derivedFrom = v_k)`，**不是第二条路径而是同一函数的一次调用**（这使「回滚会不会漏掉留痕 / 漏掉版本推进」这类问题不存在）。草稿态存另一个键空间，**不占号**。**数据库直连写规则集必须在权限上被禁止**：应用身份对规则集表只有 `INSERT` + `SELECT`（无 `UPDATE` / `DELETE`），人类身份只有 `SELECT`。O1 的「不存在原地编辑路径」若只体现在应用层 API、而运维仍持可写库凭据，这条纪律就停在评审级 |
| A3' | **人机接口 = CLI / 脚本，规则草稿以文本形式进版本控制**（顺便得到评审与历史）。控制台若日后引入，只作 `publish` 的调用方——不动存储、不动纪律、不需迁移 |
| A4 | **`publishedBy` 必须解析到具名人类身份**，不得是流水线 / 共享服务账号。flags 是唯一一条能绕过发版直接改变玩家可见内容的通道；留痕四项里最贵的就是操作者，记成 `ci-bot` 即当场归零。**不设强制第二人审批**——当前单人维护，四眼原则是纯摩擦 |
| A4' | **爆炸半径闸**：单次发布使 `disabledIds` 的解析结果规模较上一版增长 **> 20 条**时，`publish` 须带一个显式确认参数。**后端只数 `Id` 的个数、不感知内容类别**——契约逐字要求服务端不区分内容类别、`disabledIds` 只是一串 `Id`，语义与准入由客户端裁决。理由：这条通道的误操作（一个写错的规则关掉半个卡池）与它要止血的事故同量级，而分钟级生效意味着没有观察窗口。**内容规模长大后的优化路径**：让阈值按类型池规模缩放（例如同时判「> 该类型可抽取池的 5%」）。它要求池规模由**发布侧产包证明供数**（客户端打包工具产出按类型的条目计数，后端只读数字、不解析 `.tres`），因而会扩大客户端承接面，须与对侧同批落地——不为一个初值旋钮提前付这笔账 |
| A5 | **O7 的内容指纹自检直接开启**（不停留在「可选加固」）：规则集不可变 ⇒ 指纹在插入时算一次即永不重算，成本是一次 SHA-256；收益是把「同版本不同指纹」这个**唯一无法被单调性堵住的失效模式**变成一条可告警的机检断言。指纹只作服务端自检，**不下发** |
| A6 | **不引入按账号的解析结果缓存；缓存的对象是规则集本身。** 键 = `flagsVersion`，值不可变 ⇒ **这个缓存永不需要失效逻辑**（版本提升后旧条目自然不可达，LRU 回收即可），且它使「缓存键必须含 `flagsVersion`」这条硬约束成为**结构上不可能违反**的事。冷启动 / 新版本首波用**请求合并（single-flight）**收敛回源。**引入按账号结果缓存的触发判据**：`GET /v1/content/flags` 服务端处理时延 p99 > 50 ms，或该端点占后端 CPU > 5%，且已确认瓶颈在分桶计算而非存储读取；一旦引入，键**必须**是 `(flagsVersion, accountId)` |

**该端点的真实负载**：flags 的刷新时机是「搭车信封、零轮询」，客户端只在 `X-Flags-Version` 增大时才拉一次全量 ⇒ 请求量 ≈ 活跃账号数 × （每日发布批次数 + 每会话首次），而**不是** × 事件推进次数，比 `/v1/profile/push` 低一到两个数量级。单次请求的成本是：取规则集 → 跑纯函数分桶 → 得出 `disabledIds` → **对该账号的应答做一次签名**（应答走同一密钥体系，见下）。前三项中唯一可能有成本的是存储读取，由规则集缓存覆盖；签名一项按 `(flagsVersion, accountId)` 缓存签名结果覆盖——**缓存的是 `sig` 而非 `disabledIds`**，故「同一 `(flagsVersion, 账号)` 解析结果恒定」不受影响（契约要求 `disabledIds` 恒定，不要求 `sig` 逐字节恒定），而键含版本使 B 组的硬约束同样结构性满足。

- **flags 的发布 / 回滚流程（与内容发布流水线并列，不是它的例外）。** 语义权威在 `contracts/content-manifest.md`「服务端保证」B 组；此处只记运维形态须满足的性质：

  | # | 要求 |
  |---|---|
  | O1 | **规则集不可变、版本化**：每次发布产出一个新版本，既有版本只读，**不存在原地编辑路径**。「随手改一下数据源」正是「同版本内容漂移」这个静默失效模式的来源 |
  | O2 | 版本号由**单一全局分配点**分配，**只在发布动作时分配**（草稿态编辑不占号），并持久化一条单调高水位 |
  | O3 | 备份恢复后取 `max(恢复值, 高水位)` 并**强制跳号**（留一段安全余量）；「版本号未倒退」列为恢复演练的必检项 |
  | O4 | **回滚 = 一次以历史版本内容发起的发布**：`rollback(to: v_k)` ≡ 创建 `v_new = 当前最大版本 + 1`，其规则内容逐字等于 `v_k`。若实现上存在「当前生效版本」指针，它**只能单向前移** |
  | O5 | 每版留痕四项，缺一不可：**操作者** · **时间**（RFC 3339 UTC）· **来源版本 `derivedFrom`**（回滚时即被回指的版本，正常发布时为上一版）· **变更摘要与生效范围**（全量 / 分桶） |
  | O6 | **历史规则集永久保留**，期内任一版本可直接作为回滚的输入。规则集体积极小（一批 `Id` 集合 + 分桶规则），永久保留成本近似为零，与收据幂等窗口的同形取舍一致（`contracts/purchase.md` §7） |
  | O7 | 可选加固：规则集内容指纹与版本号绑定，服务端自检到「同版本不同指纹」即告警。**指纹不下发给客户端** |

  **为什么留痕是最低要求而非「有更好」：** flags 是**唯一一条能绕过发版直接改变玩家可见内容**的通道；而 `derivedFrom` 是「回滚 = 以历史规则内容发布更大版本」这条能被**机读核对**的唯一凭据，脱离它，「这一版是不是一次回滚、回指的是哪一版」就只能靠备注措辞去猜。
  **只留变更日志、不留历史规则集快照是明确否决的**——回滚时须由人工按日志重建规则，而手工编辑正是 O1 要堵的那条路径。
## 内容签名私钥的保管

私钥存放与流水线中的签名步骤**反向约束托管选型**——选型时不带着下面五条，选完才会发现不满足。

| # | 能力判据 | 不满足的后果 |
|---|---|---|
| B1 | **私钥不可导出**：签名以「把字节交给密钥服务、拿回签名」的形式发生，私钥永不出现在仓库 / CI 变量 / 构建机磁盘 / 日志 | CI 环境变量存 PEM 把私钥暴露给每个能改流水线的人；泄漏后只能靠轮换，而轮换要跨一个发版周期 |
| B2 | **签名操作可审计**：谁 · 何时 · 哪个 `keyId` · 签了哪个摘要 | 与 flags 留痕四项同构；签名是客户端唯一的信任根，不可审计等于事故后没有第一现场 |
| B3 | **原生支持 ECDSA P-256 + SHA-256，且能并存多把密钥**（active + standby） | 被 `contracts/content-manifest.md` 的签名形态钉死，不是选择项 |
| B4 | **签名权限授予发布流水线的身份，而非个人**：人触发流水线，但拿不到签名能力之外的任何东西 | 「人能直接签一份 manifest」这条旁路会让整条流水线纪律退化为评审级——它也是「私钥离线保管、发布时人工签名」这个形态被排除的理由 |
| B5 | **可用性与 flags 端点同档**（仍低于会话 token 签名密钥） | 见下 |

**B5 值得单独论证。** 内容签名私钥**在 flags 的读路径上，但不在写路径的关键区**：`GET /v1/content/flags` 的应答按账号计算，而它走同一密钥体系（同 `keyId` 空间、同 detached 形态），故每个 `(flagsVersion, 账号)` 组合都要发生一次签名（已由签名结果缓存收敛到与该端点请求量同量级）。密钥服务停机的后果因此是两条：这段时间不能发布新内容 · flags 端点无法产出合法应答，客户端降级到本地缓存的上一批。这比「玩家完全无感」重，但仍低于会话 token 签名密钥——后者停机即**全体无法登录**。两把钥匙的档位、轮换窗口、爆炸半径、连签名算法都不同（token 侧的形态见 `open-questions/06-platform-stack.md` 与其落点，本节不复述），**不得混写成一条运维流程，也不得共用同一把密钥**。

**standby 私钥 = 同一密钥服务内的独立密钥**：独立密钥 ID、独立权限策略、独立审计线，**standby 的签名权限平时不授予任何身份**。它防住的是「私钥泄漏给能改流水线的人」「单个密钥材料失陷」「持签名权限的人员变更」；防不住的是整个云账号 / 密钥服务被攻破或误删——而威胁模型逐字只到「防误 / 防随手改」，那一档不在模型内。把 standby 挪到离线 / 另一保管方几乎必然引入「人可直接签」的旁路，与 B4 相抵。

**首版即内置 active + standby 两把公钥。** 契约写的是客户端内置**一组** `keyId → publicKey` 映射——复数从第一天就在，这里只是把它用满，**报文零改动**。理由是把轮换机制里最贵的那一段拿掉：既定机制「先发内置新旧两把公钥的版本 → 覆盖率足够后切私钥」隐含「新公钥的分发要等一个客户端发版周期」，计划轮换里这没问题，但在**紧急轮换**里意味着从发现泄漏到能切钥有数周窗口，期间唯一的止血手段是为一次密钥事故强更全体玩家。预置 standby 后，紧急轮换退化为服务端切一个字符串，分钟级完成、零客户端动作。成本是多生成一把密钥对与客户端内置的几十字节。**客户端侧的内置动作是一项跨库承接项**，见 `game-design-documents/` 对侧承接记录。

## `keyId` 轮换的触发条件、节奏与覆盖率口径

| 类别 | 触发 | 处置 |
|---|---|---|
| **计划轮换** | 周期到期（初值 12 个月） | 走完整四阶段，不急 |
| **紧急轮换** | 疑似泄漏 · 持签名权限的人员离职或权限变更 · 密钥材料迁移 | **立即切到 standby**，跳过等覆盖率——standby 的公钥早已内置 |
| **不构成触发** | 客户端发版加入了新 `keyId` 的公钥 | 只是为下一次轮换预置条件，服务端不动 |

12 个月的推导：威胁模型只到「防误 / 防随手改」，不引入 PKI、不承诺防作弊；私钥不可导出、签名权限只授予服务身份 ⇒ 暴露面受控。另一侧，每次计划轮换要跨一个客户端发版周期 + 等覆盖率，运营成本不低。**待运营实际节奏校准。**

**紧急轮换的止血范围覆盖两条通道。** 内容签名密钥同时签 manifest 与 flags 应答，故切 active `keyId` 之后，**未内置该公钥的客户端不仅收不到内容更新，flags 也会验签失败并保留上一批**——秒关通道对这部分玩家暂时失效。这正是「首版即内置 standby 公钥」从省事抬为止血前提的原因：没有预置，紧急轮换的代价里要额外算上一段秒关能力的空窗。

**四阶段：** T0 预置（新公钥进**下一个**客户端版本的内置映射，服务端仍用旧 `keyId` 签名）→ T1 等覆盖率达阈值 → T2 切 active `keyId`（**历史 manifest 不重签**）→ T3 旧 `keyId` 保留在客户端映射里、**不主动移除**（保留成本近零，且它是回切的输入面；唯一必须移除的情形是旧私钥确认泄漏，那时移除随常规发版慢慢做即可——这恰是 standby 存在的理由）。

**覆盖率口径（零新增契约面）：** 后端在每个 API 请求上已经收到 `X-App-Version`（`contracts/envelope.md` §4a）。覆盖率 = **过去 N 天有过请求的账号中 `appVersion ≥ 引入新公钥的那个版本` 的比例**。N 初值 7 天（移动游戏常见的活跃回访窗口）。数据已在手，不需要任何新报文或新埋点。

**阈值初值 95% 的推导（承重）：** 未覆盖的那部分玩家在 T2 之后验签失败 ⇒ 拒绝 overlay + 回退 `res://` 基线 + **照常开局**。轮换的爆炸半径是「一部分玩家暂时收不到内容热更」，**不是「玩不了」**——比强更闸门低一整档，故阈值不必按强更的标准取。取 99%+ 会让长期不更新的尾部把轮换无限期推迟；低于 90% 则受影响人群规模开始与一次内容事故本身相当。

**两条配套：** T2 前先在非生产环境用新 `keyId` 走完整条流水线并用真实客户端验通一次（编码形态一类的错误若在切换当天才暴露，代价是一次全量内容更新中断）· T2 后设 **48 小时观察窗口**，监控客户端验签失败上报量，异常即**回切 active `keyId`**。**签名密钥的回切是安全的**——旧公钥仍内置于全部客户端，`keyId` 只是一个查表键。**不要把 `contentVersion` / `flagsVersion` 的「回滚即前滚」纪律误扩到它身上**：那两者被禁止回退是因为客户端对它们有单调判据。

## flags 读路径的拓扑自由度

flags 的读路径**不受读己所写约束**——这是一条被保留但当前未被使用的自由度；当前拓扑取「玩家读路径全走写入区」，flags 随之。规模到需要时可无额外一致性代价地把 flags 读移出写入区。

判据：flags 的写入者是运营发布动作、读取者是玩家请求，二者之间没有「同一主体写后立刻读」的语义；副本滞后在这里表现为**传播时延**，已被 B 组第 5 条（单一全局序列）与运维 SLO 窗口 T 覆盖，且客户端观测到更小版本已被定义为**已知良性态**。只有 A1 的版本分配点与高水位写入必须是单点。

## 存储 · 权限 · 密钥服务的能力要求（栈中立）

同时是对 `open-questions/06-platform-stack.md` 的**反向约束**：选型不满足即出局。

| 要求 | 为什么 |
|---|---|
| 主存储支持**规则集插入 + 高水位推进的原子多记录写**（关系库的事务；文档库则须单文档承载或条件写 + 单调 CAS） | O2 / O3 |
| 存储能表达**「应用身份只有 `INSERT` + `SELECT`、人类身份只有 `SELECT`」的权限分层**，且落在建库脚本里而非停在约定 | A3 |
| 密钥服务满足 B1–B5 五条；**签名 API 的返回编码须明确**，返回 DER 时流水线必做 ③b 转换 | B 组 |
| **签名权限绑定流水线身份，不得给个人授予签名权限**；standby 密钥的签名权限平时不授予任何身份 | B4 |
| 发布侧可取到**每个在架客户端版本的基线内容快照** | C6（落点见 `deployment.md`） |

- **对 CDN 的能力要求**（不算苛刻，主流 CDN 均满足）：按路径设置差异化 `Cache-Control`、支持 immutable 长缓存、支持 `contentRoot` 域名切换（`contentRoot` 不在被签名的 manifest 内，故切换无需重签历史 manifest）。
