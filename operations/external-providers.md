# 外接原子能力 —— 适配接口 · 归一映射 · 灾备与切换 · 选型与凭据

> 短信 / 邮件 / 实名核验 / 第三方昵称审核 / 第三方渠道换 openid 都是**外接的原子能力**：后端内部各有一个稳定接口使服务商可换。语义权威在 `contracts/auth.md` §3 §3a §8 与 `contracts/compliance.md` §10 §11；判定链与存量扫描的服务内部形态在 `systems/account.md`，昵称词表与处置阶梯在 `operations/moderation.md`。**本文件只记外接这一侧的形态**：接口长什么样、错误怎么归一、接几家、什么时候切、凭据放哪、怎么看它是否健康。
> **本文件不点名任何一家服务商**——那是商业决定（价格、合同、资质、既有关系），不是可推演项。可推演的是它周围的全部形态。
> Source: `handoffs/2026-09-06-external-provider-selection-dr.md` · `handoffs/2026-09-07-compliance-launch-tiering.md`（昵称审核能力的启用触发条件）。

## 四类能力的适配接口

四个接口**共用同一套出参判别式**。`Outcome` 三档（受理 / 明确拒绝 / 不可达）是「明确拒绝与服务不可达必须在归一时就分开」这条纪律在类型层面的兑现，合并即当场违规。

**共有形状（四个接口逐条满足）：**

| # | 要求 | 理由 |
|---|---|---|
| A1 | 出参含 `Outcome` 判别式，且**「明确拒绝」与「不可达」是两个不同取值**，永不合并 | 合并 = `Fatal` 与 `Retryable` 在源头就分不开（`contracts/auth.md` §3a） |
| A2 | 出参含可选 `providerCode`（服务商原始码）+ `providerTraceId`，**只随日志上报，永不进报文、永不参与分支** | 与 `auth.md` §3a 对 `channelCode` 的处理逐字同构：服务商原始码是服务商版本的产物，任何依赖它的分支都会在服务商更新时静默失效 |
| A3 | 入参含 `requestId`（透传 `X-Request-Id`） | 服务商侧排障要能由玩家上报的 `requestId` 反查（`observability.md`「三者贯通」） |
| A4 | **每次外部调用有硬超时**，超时归不可达；适配层内**不做应用层重试**（唯一例外是跨供应商 fail-over 的那一次，见下方灾备一节） | 应用层重试在下游劣化时放大流量，把一次抖动变成一次雪崩 |
| A5 | 个人信息**只作入参穿过适配层**，不落适配层自己的日志与缓存 | 手机号 / 邮箱明文绝不落库落日志；实名姓名 / 证件号永不回显、永不进任何应答、永不进日志（`environments.md` · `contracts/compliance.md` §10） |
| A6 | **适配层不认识 `code`**：它只产出 `Outcome`，归一到 `code` 发生在调用方（端点） | 单一归一点。否则每换一家服务商都要重读一遍错误码台账 |

**四个接口的入出参：**

```
// ① 短信 / 邮件下发（同一接口，channel 分形；Email 首版无调用面）
SendChallenge(channel, identifier, code, purpose, ttl, requestId)
  → { outcome: Accepted | Rejected | Unavailable,
      providerMessageId?, providerCode?, retryAfter? }

// ② 实名核验
VerifyRealName(accountId, realName, idNumber, docKind, requestId)
  → { outcome: Verified | Mismatch | Malformed | Pending | Unavailable,
      birthDateUtc?（仅 Verified）, providerCode?, providerTraceId? }

// ③ 第三方昵称审核（首版留位，实现为透传恒放行）
ModerateNickname(normalizedText, originalText, requestId)
  → { outcome: Reject | Review | Pass | Unavailable,
      score?, labelKeys[], providerCode? }

// ④ 第三方渠道换 openid —— 义务与错误映射的权威在 contracts/auth.md §3a，
//    此处只登记它与上述三者同属适配层、同守 A1–A6。
```

- **`birthDateUtc` 只在核验通过时返回、且只用于算 `isMinor`**——不单独存年龄，出生日期本身永不下发（`contracts/compliance.md` §7 §10）。
- **`ModerateNickname` 传归一化串与原串两个入参**：词表匹配用归一化串是既定纪律（`auth.md` §8），但多数外部审核服务自带归一化，把原串一并给它使其能用自己的模型；本方不因此放松自己的归一化。
- **`Malformed` 两个来源，同一个落点。** 证件号格式非法由本方先判、命中即不调外部（省一次按次计费）；服务商也可能返回同类判定。两者归同一个 `reasonKey: "Malformed"`，本地命中时不产生任何外部调用。

## 归一映射

归一到本库已有的 `code`，**按调用点所在域取**——auth 域的调用点归 auth 域的 `code`，合规域的归 `compliance.*`。目标集合逐条取自 `contracts/envelope.md` §6 台账，**不新增任何 `code`**。

**`auth.challenge_expired` 永不来自服务商。** 验证码由本方生成、本方存储、本方判超时；服务商只负责把一串字符送出去。把它列进归一目标集合，会让实现者去找一个服务商侧根本不存在的对应物。

**`Outcome` 为不可达时归哪一个 `code`，判据是出参有没有 `retryAfter`**：有 ⇒ `rate.limited`（该值同时填进 `Retry-After` 头与 `detail.retryAfterSeconds`，形状见台账）；无 ⇒ `server.unavailable`。**不得靠 `providerCode` 分支**（违反 A2）。

**① 短信下发（`POST /v1/auth/challenge` 调用点）**

| 服务商侧情形 | `Outcome` | 归一 `code` | `class` |
|---|---|---|---|
| 号码非法 / 空号 / 明确黑名单 / 模板不匹配被拒 | 明确拒绝 | `auth.credential_invalid` | `Fatal` |
| 服务商限流 / 单号码频控 / 账户余额或额度耗尽 | 不可达（带 `retryAfter`） | `rate.limited` | `Retryable` |
| 超时 / 5xx / 连接失败 / 服务商侧故障 | 不可达（无 `retryAfter`） | `server.unavailable` | `Retryable` |

- **余额 / 额度耗尽归 `rate.limited` 而非 `server.unavailable`**：客户端处置需要 `Retry-After`，而 `server.unavailable` 没有这个字段。语义上它确实是「此刻不给你发」，不是「我方组件坏了」。它同时是一条**可预警**的运维告警，见下方可观测性一节。

**② 实名核验（`POST /v1/compliance/realname` 调用点）**

| 服务商侧情形 | `Outcome` | 归一 `code` |
|---|---|---|
| 姓名 / 证件号不匹配 | 明确拒绝 | `compliance.verification_failed` + `reasonKey: "Mismatch"` |
| 证件号格式非法（本方先判，命中即不调外部） | 明确拒绝 | `compliance.verification_failed` + `reasonKey: "Malformed"` |
| 核验异步未回 | 未决 | `200` + `realnameStatus: "Pending"`（**不是错误**） |
| 不可达 / 超时 / 限流 / 额度耗尽 | 不可达 | 按上方判据取 `rate.limited` 或 `server.unavailable` |

核验的明确拒绝归 `compliance.verification_failed`——`contracts/compliance.md` §11 明写它「必须与核验服务不可达在报文层面可区分」。把核验拒绝归进 `auth.credential_invalid` 会破坏该条纪律，且跨了域。

**③ 第三方昵称审核（`POST /v1/auth/nickname` 判定链第④级）**

**本能力的归一目标不是 `code`，而是判定链的档位**——这是它与前两者的结构性差异：

| `Outcome` | 落点 |
|---|---|
| 拒绝（评分 ≥ `rejectThreshold`） | `auth.nickname_rejected` + `reasonKey: "SensitiveWord"` |
| 待复核（评分落在两阈值之间） | 第⑤级接受（`204`）+ 入复核队列 |
| 放行 | 第⑤级接受（`204`） |
| 不可达 | 第⑤级接受（`204`）+ 入复核队列，**不返回任何错误** |

不可达按「待复核」接受、绝不返回 `SensitiveWord`：把外部抖动伪装成明确拒绝会让玩家以为自己的昵称违规（`systems/account.md` N9）。**本能力的硬超时是玩家等待预算**——它在同步路径上，超时即落第⑤级接受，玩家侧无可见失败。

阈值的形态（两个阈值 · 服务商 × 环境维度 · 标定方式 · 首版不定值）见 `operations/moderation.md`。

## 多供应商灾备与切换

判据是「**这个能力停摆，玩家会怎样**」，而不是一刀切上双供。

| 能力 | 首版供应商数 | 停摆的玩家后果 | 结论 |
|---|---|---|---|
| **短信** | **2（主 + 备，首版即接）** | `Phone` 渠道玩家全体无法登录，且他们**无法改走 `WeChat`**——那会建出第二个账号（`auth.md` §1a 明禁隐式合并） | 唯一「外部停摆 = 一半玩家完全进不来」的能力，必须双供 |
| **邮件** | **0（不选型，只留接口位）** | 零调用面：`Email` 渠道首版返回 `auth.channel_rejected`（`auth.md` §3） | 为一条不存在的路径选型、报备模板、养一份凭据，是纯负债 |
| **实名核验** | **1（另有一家完成合规评估但不接入）** | 新账号卡在实名前；契约已有 `Pending` 态与 `server.unavailable`（`Retryable`），玩家稍后重试即可 | 按次计费、一生一次、有既定的可重试语义 ⇒ 双供的收益不抵接入与合规成本 |
| **第三方昵称审核** | **0（首版不启用）** | 判定链第④级透传恒放行，玩家零感知 | 抽查面已由本地词表与存量扫描完整承接，第④级是增强不是承重；**启用触发条件唯一**——渠道过审点名要求接入第三方内容审核（`operations/moderation.md`） |

**切换触发判据（只对短信）：**

```
滑动 5 分钟窗口内：不可达占比 > 20% 且样本 ≥ 20 次
                 或 连续 10 次不可达
  → 自动降级到备用供应商，同时发一条 P1 告警
回切：备用运行 ≥ 30 分钟 且 主供在旁路探测上连续 10 分钟成功率 ≥ 95%
  → 自动回切（带滞后），回切也发告警
```

- **明确拒绝不计入触发判据。** 它是号码本身的问题，与供应商健康无关；把它计进去，一批脏号码就能触发一次假降级。
- **降级自动、回切带滞后。** 无滞后的自动回切会在主供半死不活时来回抖动，而每次抖动都在真实地少发一批验证码。
- **备用供应商必须持续保持「可用」而非「可接入」**：至少一条低频合成探测（旁路，不占玩家路径），否则降级当天才发现备用家的模板报备过期了。

**重复计费与重复送达的处置（承重）：**

- **禁止并发双发**（同一个码同时发两家）。双倍计费，且玩家收到两条一模一样的短信；可用性收益仅覆盖「主供受理后静默不送达」这一小类失败，不值。
- **允许「同码转备用」一次，且只在首家未返回受理 id 时。** 关键性质是**验证码由本方生成**，因此重发同一个码是幂等的——两条短信里是同一个码，玩家用哪条都对，唯一代价是可能多一条计费。若首家已返回 `providerMessageId`（已受理），**不转备用**：那时更可能是送达慢而非失败。
- **一次 `challenge` 请求至多产生两次外部调用**（首家 + 转备用一次），此外一律归不可达，交由客户端退避重试。这与 A4 不冲突——转备用是**换目标**，不是重试同一目标。
- **`resendAfterSeconds` 与验证码有效期由本方决定，与供应商无关**（`auth.md` §8 的旋钮），切换不改变契约面的任何一个字段。
- **禁止双验（实名核验）**：两家同时验一次，双倍计费，且两家结论不一致时**没有任何仲裁规则**——而这是一个直接决定「这个人是不是未成年」的判定。一个没有仲裁规则的双源比单源更坏。

## 选型判据与凭据托管

接入前逐项签核；**不满足 H 类即出局**。

| # | 类 | 判据 | 不满足的后果 |
|---|---|---|---|
| H1 | 硬 | **数据处理节点全部在中国大陆境内**，含任何边缘 / 加速 / 灾备节点 | 直接违反「个人信息不出境」（`environments.md`「区域与合规」） |
| H2 | 硬 | **资质齐备**：短信需增值电信业务经营许可与签名 / 模板报备通道；实名核验需持牌数据源（权威库或运营商要素核验） | 无资质的通道会在过审或抽查时整条中断 |
| H3 | 硬 | **提供沙箱 / 测试通道**，使 `backend-testing` 环境不真实发短信、不真实计费、不真实核验 | 与「测试环境用沙箱凭据」同构（`purchase-ops.md` §1）；缺它则每次集成验证都在真花钱、真发短信 |
| H4 | 硬 | 凭据可**无停机轮换**，且支持新旧并存窗口 | 轮换当天该能力整体中断 |
| S1 | 软 | 与主区**同区或内网可达**，公网出口有确定的 IP / 域名（便于出网白名单） | 时延与网络故障面 |
| S2 | 软 | 有可查的 **SLA 与状态页**，且回执 / 送达率可按条查询 | 缺回执则「服务商受理了但没送达」永远归因不了 |
| S3 | 软 | **计费模型清晰**：按条 / 按次；预付余额有**可编程的余额查询接口** | 无余额查询 ⇒ 低水位告警做不了，只能等发不出去才知道 |
| S4 | 软 | 支持按业务维度拆分子账户 / 子签名，使 `testing` 与 `production` 用量可分账 | 分账不清则成本模型拿不到干净输入 |

**凭据托管：形态复用 `purchase-ops.md` §1，条目粒度 = 能力 × 供应商 × 环境。**

- 载体同为云 Secrets 条目（底层 KMS 加密），沿用「只在内存、不落盘、不进环境变量、不进镜像」与「运行角色只读、写入只经部署角色」。
- **自成一类托管条目与独立审计线，与既有各类钥匙不共用托管配置与轮换流程**（内容签名私钥 · 会话 token 签名密钥 · 渠道验票凭据）。理由与那几类之间的分立同源：轮换节奏由各自的外部方驱动，共用一份托管配置会让最慢的那条绑架其余。
- 新旧并存沿用 `credentials[]` 数组 + 供应商侧标识的形态，轮换 = 追加新项 → 确认 → 删旧项。
- 凭据拉取失败或服务商 API 回 401 / 403 → 既有 P1 告警面，零新增机制。

## 可观测性增量

`observability.md` 已有「RED 三件套 + 按 `code` 的错误分布」与既有告警面；本节只写外接能力特有的维度，不复述基座。三个标签均为低基数。

| 指标 | 标签 | 告警口径 |
|---|---|---|
| 外部调用结果分布 | `capability` · `provider` · `outcome` | 不可达占比触及上方降级判据即 P1 |
| 外部调用时延 p50 / p95 / p99 | `capability` · `provider` | 相对基线劣化 |
| **供应商余额 / 剩余额度** | `capability` · `provider` | **低水位两档**：可用量 < 7 天用量 ⇒ 提醒；< 1 天用量 ⇒ P1 |
| 降级 / 回切事件 | `capability` · `provider` | 任一次即告警（两个方向都告） |
| 备用供应商合成探测 | `capability` · `provider` | 连续失败即告警 |

- **余额耗尽是可预警的事故。** 等它变成一串 `rate.limited` 才发现，是纯粹的运维失职——这正是要求服务商提供可编程余额查询（S3）的原因。
- **`providerCode` 的分布也上看板**：它是唯一能发现「服务商悄悄改了错误码语义、我方归一映射从此错位」的面，与「新增未登记的 `code` 会在按 `code` 的分布里显形」同一手法。它只上看板，**不参与任何分支**（A2）。

## 微信开放平台资质：时序与过闸

首版即以 `unionid` 建 identity，这是**不可逆**决定，且必须在首个玩家建号之前完成（`contracts/auth.md` §3a · `operations/deployment.md` 发布前置清单第 4 项）。

**为什么它比清单上另外三项更险。** 另外三项（透明路径命名、`Source` 枚举冻结、`accountId` 形态）全部在我方掌控内——想定就能定。本项的完成时刻由外部审批决定，我方只能等。它因此是清单上**唯一一项可能因外部原因而未能在闸门前完成**的，而闸门本身不可协商：过了那一刻，identity 已按 per-app 标识落地。

**前置链（逐环都是外部审批，串行、以周计）：**

```
企业主体资质 → 软件著作权 → ICP 备案 / 域名备案（与域名备案同批推进）
  → 微信开放平台账号 + 企业开发者认证（年审制）
    → 创建「移动应用」并提交审核（需包名 / 签名指纹 / 应用材料）
      → 应用审核通过并绑定到该开放平台账号
        → 此后渠道登录才会同时返回 unionid
```

- **`unionid` 的产生条件是「该应用已绑定到一个开放平台账号」，与应用数量无关。** 首版只有一个 App 时同样能取到它——这正是「首版即以 `unionid` 建 identity」得以成立的前提，也是提前申请的全部价值：**不是为了今天有两个应用，是为了明天有第二个应用时不必迁移。**
- **过闸断言必须是可验证的运行时事实，不是「已提交申请」。** 断言形态见 `deployment.md` 前置清单第 4 项：在 `backend-testing` 环境完成一次真实的微信登录、服务端取到非空 `unionid`、该条 identity 的 `idKind` 落为 `unionid`。一份「审核通过」的凭证证明不了我方代码走的是 `unionid` 那条分支，而那恰恰是不可逆的那一个。
- **审批未在计划上线日前到位 ⇒ 推迟上线，不以 `openid` 先行建号。** 以 `openid` 建号的代价随存量账号数增长；任何形式的事后回填都必然撞上「同一人两条 identity」的合并，而绝不做隐式账号合并是 `auth.md` §1a 的承重禁令，它保护的是玩家的存档，不是一条工程偏好。时程压力可以协商，`unionid` 的不可逆性不能。
- **与支付侧解耦**：微信支付商户资质是另一条链、另一个闸（`purchase-ops.md`），两者不互为前置。
- 具体审批时长与所需材料清单属外部事实，**接入时一律以官方文档核实**（与 `purchase-ops.md` 同一纪律）；本文件只给链路结构与过闸断言，不给天数。

## 数值初值（待实测校准，落 `config_knob` 表）

## 备选方案（已考虑并否决）

- **首版只接一家短信供应商，靠人工快速切换** — 「人工切换」在无人值守时段等于停摆数小时，而后果是 `Phone` 渠道玩家全体无法登录且无替代登录路径（改走 WeChat 会建出第二个账号）。这是全部外接能力里唯一具备这种后果的一条。
- **并发双发同一验证码到两家** — 双倍计费、玩家收两条同内容短信；可用性增益只覆盖「已受理但静默不送达」这一小类，而顺序转备用已覆盖其余全部。
- **两家实名核验并行核验、取一致结论** — 双倍计费（按次），且不一致时无仲裁规则，而这是决定「是否未成年」的判定。
- **为「服务商不可达」新增一条 `code`** — 服务商错误码不上契约面；`server.unavailable` 逐字覆盖，且客户端已有 `Retryable` 处置。
- **把服务商原始码放进 `detail` 供客户端分支** — `auth.md` §3a 已为 `channelCode` 定死「客户端不解析、只随日志上报」，理由（服务商版本更新时分支静默失效）在此完全同源。
- **首版即为 `Email` 选型并接入** — 该渠道首版返回 `auth.channel_rejected`，零调用面；接入即产生一份要轮换的凭据、一次模板报备与一条要监控的曲线，全是负债。
- **昵称审核用单一评分阈值** — 表达不了判定链要求的三档落点（拒绝 / 待复核 / 放行）。
- **昵称审核阈值取全局单值** — 不同服务商评分刻度互不可比（有的 0–1、有的 0–100、有的分类标签 + 置信度），换一家当天判定口径就静默漂移。
- **外接能力凭据并入其余任一类钥匙的托管配置** — 各类钥匙不共用托管配置的理由（最慢的轮换节奏绑架其余）在此同源。
- **适配层内对外部调用做多次重试** — 下游劣化时放大流量；跨供应商 fail-over 是换目标而非重试，不在此列。
- **以 `openid` 先行建号、日后全量迁移或增量回填** — 代价随存量账号数增长，且回填必然撞上隐式账号合并这条承重禁令。
