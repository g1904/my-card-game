# 购买与验票的运维面 —— 渠道凭据 · 对账 · 幂等记录的存储要求

> 语义权威在 `contracts/purchase.md`（报文、权威分配、七条服务端保证、`receiptId` 幂等窗口）与 `decisions/ADR-0007-purchase-write-authority.md`；**此处只记它对运维形态的要求**，不复述契约语义。
> 客户端侧的购买流程与待兑现态形态在 `game-design-documents/systems/monetization.md`，同样只回链、不复述。
> **存储产品选型与事务实现**：本文件给的是**判据与断言**（选型的输入），结论落 `systems/profile-store.md`。渠道凭据的**托管形态**见 §1「托管形态」。

## 1. 渠道验票凭据与轮换

| 渠道 | 服务端凭据 | 轮换特征 |
|---|---|---|
| Google Play | Play Developer API 的服务账号凭据（或等价的工作负载身份） | 可无停机轮换；权限范围只给「查询 + 消费购买」 |
| App Store | In-App Purchase key（`.p8` + keyId + issuerId）用于 Server API；Apple 根证书用于离线 JWS 校验 | key 可并存新旧；**根证书随 Apple 更新，须有更新通道** |
| 微信支付 | 商户 API 私钥 + 证书序列号、APIv3 密钥（回调解密）、平台证书 / 公钥（回调验签） | **平台证书会轮换**，须支持新旧并存期，否则轮换当天全渠道验票中断 |

- **三套凭据一律只在服务端，绝不进客户端二进制**——与 `contracts/auth.md` §3a 的渠道 secret 义务逐字同构。
- **各类钥匙不共用托管配置**：内容签名 ES256 私钥（`_index.md`「内容分发」）· 会话 token 签名密钥 · **渠道验票凭据（本条）**。轮换节奏逐类不同——内容签名的轮换跨越一个客户端发版周期，token 密钥的轮换只在服务端，渠道凭据的轮换由渠道方的日程驱动。共用一份托管配置会让最慢的那条节奏绑架其余各条。**判据是轮换的驱动方**：同一驱动方的材料可共用一份托管配置，驱动方不同即各自独立——凭据类别增员时按此判据落位，不必回头改一个写死的个数。
- **环境隔离是凭据层的事**：测试环境用沙箱凭据、生产用生产凭据。且收据的环境校验（Apple `environment` / Google `purchaseType = Test`）以**部署环境配置**为准，**不以收据自述为准**——沙箱交易在生产被接受等于任何人可无限白嫖礼包。

### 托管形态：云 Secrets 条目（SSM，底层 KMS 加密）

- **载体 = 云凭据管理系统（SSM）**，条目粒度 = **渠道 × 环境**，值为 JSON 载荷。SSM 底层本就以 KMS 加密，天然满足「同一 KMS、不同密钥 / 权限 / 审计线」的既有分层（与内容签名密钥的分层同构，见 `operations/environments.md`「密钥保管」）。
- **不复用签名密钥的「KMS 包裹私钥 + 进程启动解包一次」形态。** 那套形态的取舍点是「KMS 不在签发热路径上」；渠道凭据则是**向外调用的客户端凭据**——形态杂（`.p8` 文本 / 服务账号 JSON / APIv3 对称密钥 / 商户 RSA 私钥），且轮换由**渠道方**驱动、需要新旧并存窗口。Secrets 的条目版本化天然承载这两点，KMS 信封包裹则要自管存储与版本并存逻辑。这正是「各类钥匙不共用托管配置」在形态上的兑现。
- **新旧并存的表达：** secret JSON 载荷内含 `credentials[]` 数组，每项带渠道侧标识（Google 的 key id / Apple 的 `keyId` / 微信的证书序列号）与可选生效边界；验票代码按渠道侧标识选用。轮换 = 先追加新项、渠道侧切换确认后删旧项。**不设「秒级双活切换」机制**——渠道方的轮换窗口以天计，追加-确认-删除三步足够。
- **读取形态：** 进程启动拉取进内存 + **周期刷新**（间隔初值 **5 分钟**，运行期可调旋钮、待实测校准，登记于 `operations/environments.md`「旋钮清单」），换凭据**不重启、不发版**；凭据只在内存，沿用「不落盘、不进环境变量、不进镜像」纪律。
- **权限与审计：** 验票服务的运行角色对这些条目**只读**，写入只经部署 / 运维角色；审计线**自成一条，与各把签名密钥的审计线彼此独立**。
- **失效告警衔接：** 凭据拉取失败或渠道 API 回 401 / 403 → 既有 P1 告警面（§4），零新增机制。

**逐渠道进不进 Secrets 的分界（判据：是不是秘密）。** 版本 / 产品行为假设，接入时一律以官方文档核实：

| 渠道 | 进 Secrets | 不进 Secrets（公开材料，走配置 / 代码 / 自动拉取） |
|---|---|---|
| Google Play | Play Developer API 服务账号 JSON key（权限只给查询 + 消费，见上表） | `packageName`——取自身配置（`contracts/purchase.md` §3a） |
| App Store | IAP `.p8` 私钥 + `keyId` + `issuerId` | **Apple 根证书**——公开证书不是秘密，随镜像 / 配置分发并保留更新通道（上表既有要求），不占 Secrets |
| 微信支付 | 商户 API 私钥 + 证书序列号 + APIv3 密钥 | **微信平台证书 / 公钥**——由官方接口定期拉取 + 本地缓存（以 APIv3 密钥解密下载），新旧并存由拉取逻辑天然承载；它是渠道下发的材料，不由我方托管 |

- **Google 侧首版用服务账号 key + 例行 90 天轮换。** 「工作负载身份联合」（免长期 key）是更优方向，但跨云 OIDC 联合的配置与排障成本高、可行性待接入实测核实——**留作后续优化，不作首版前提**（备选记录：首版即上联合被否决——配置与排障成本高，而渠道接入本身已在首版关键路径上）。
- **微信条目随资质开通时再建。** Secrets 结构按三渠道设计、条目后补——契约面与托管结构零变更，与 `purchase.channel_disabled` 的「开通时只删实现分支」（`contracts/purchase.md` §3b）同一形态。

## 2. 退款 / 撤单的对账通道

| 渠道 | 对账通道 | 补漏手段 |
|---|---|---|
| Google Play | Real-time Developer Notifications（推送）+ voided purchases 列表 | 定期拉 voided 列表兜底，不依赖推送必达 |
| App Store | App Store Server Notifications V2（`REFUND` / `REVOKE` 等） | 通知历史接口回补漏收的通知 |
| 微信支付 | 退款结果通知 + 退款查询 | 定期按时间窗查单兜底 |

- **三条通道的共同形态：推送只作「更快知道」，周期性拉取才是正确性来源。** 回调不可达是常态，而对账的正确性不能押在推送必达上。
- **对账任务日频**，足以落在平台退款 / 客诉窗口（以月计）之内。
- **对账不驱动任何自动写入**（`contracts/purchase.md` §7 · `ADR-0007`）：退款只在幂等记录的运维侧字段上打标并进工单，权益不回收、序号不回退。**「已付款但从未 verify」**的兜底发现也在这条任务上，同样只产出工单。
- 微信渠道的**未支付订单关单**由同一条任务承担：预落的 `status = Unknown` 记录在订单有效期后仍未转 `Verified` 即标记关单，**记录本身不删**。

## 3. 幂等记录的存储要求

### 3a. 三条选型判据（不满足即出局）

| # | 判据 | 不满足的后果 |
|---|---|---|
| S1 | 幂等记录的写入与 `bundleGrantOrdinal += 1`、`cloudRevision += 1` **能落在同一次事务内** | 出现「revision 已 `+1` 但幂等记录未落」的中间态——正是重放会重复发放的那一刻 |
| S2 | `receiptId` 的唯一性由**存储层的唯一约束**保证，不由应用层「先读后写」保证 | 并发双提交在读-写窗口内双双通过，同一张票 `+1` 两次；这类窗口在压测下不出现、在线上偶发 |
| S3 | 收据记录的读路径与 profile 读路径受**同一条读己所写约束**（`contracts/purchase.md` §6 保证 3） | `GET /receipt/{receiptId}` 读到滞后副本 ⇒ 客户端在阻塞重试态下反复读到 `Unknown`，与「verify 从未成功」不可区分 |

**S1 与「全局唯一键」的张力，以及退化形态。** 全局唯一要求一条跨账号的唯一索引，而账号级事务通常按账号分区。若选型无法让两者同处一次事务，**退化形态**（仅在 S1 不可满足时启用）是拆成两条记录：`receiptClaim`（全局唯一索引 `receiptId → { accountId, claimedAtUtc, state }`，在事务**之前**以 `state = claiming` 写入）与 `receiptRecord`（与账号聚合同处，随 `+1` 事务一并写入）。判定规则：claim 命中且 `accountId` 相同 ⇒ 同一账号的重试，接管并继续；`accountId` 不同 ⇒ `purchase.receipt_claimed`。悬挂的 `claiming`（超过阈值仍无对应 `receiptRecord`）由清理任务回收，**阈值初值 10 分钟**（一次验票的端到端上界是渠道查询超时 + 事务耗时，秒级；10 分钟给异常态两个数量级余量，且远短于玩家重试的耐心周期；**初值待实测校准**，运行期可调旋钮 `claimingSweepMinutes`，登记于 `operations/environments.md`「旋钮清单」——**仅在本退化形态启用时生效**）。**这是退化形态而非首选**——它把一个事务变成两步，正确性靠一条清理任务维持。

### 3b. 分区与索引

- **按 `receiptId` 做哈希分区。** 本表的在线负载**只有点查**（验票查重、补查端点），没有任何按 `receiptId` 的范围扫描，哈希分区给出最均匀的分布。
- **按时间做在线分区是错的**：查询时不知道这张票是哪年的，点查会退化为跨全部分区的广播。时间维度只用于归档（3d），不用于在线分区。
- **一条二级索引 `(accountId, verifiedAtUtc)`，且是 `WHERE tier = 'hot'` 的部分索引**（`tier` 列见 3d）。对账、客服排障、退款处置的唯一查询路径都是「这个账号买过什么」；缺它则这三件事只能全表扫。取部分索引使已归档的行自动移出该索引，历史区间的同类查询走归档表上的同名索引——**索引高度与缓存命中率才是点查 p99 的因变量**，压住它比搬运记录体更直接。

### 3c. 与 `(accountId, pushId)` 幂等记录：可同系统，不可合表

| 维度 | `receiptId` | `(accountId, pushId)` |
|---|---|---|
| 键作用域 | 全局 | 账号内 |
| 保留期 | **永久，不设 TTL** | 30 天 TTL |
| 写入频次 | 每账号个位数 / 年 | 稳态约每分钟 1 次 / 账号 |

- **同一存储系统可以，同一张表不行。** 差三个数量级的写入频次与两套相反的保留策略共表，唯一的好处是少建一张表。
- **收据表须显式关闭任何 TTL / 过期清理机制，并在配置层留一条断言。** 这是本节最承重的一条：合表或共享 TTL 配置时，一次误配置就等于收据记录被清掉 = 重复发放漏洞，而这个漏洞**线上不可发现**（第二次提交查不到记录即当作新票，玩家白得一份，没有任何报错）。断言的形态是配置层的显式校验（部署时读取该表的过期策略，非「永不过期」即拒绝启动），不是一条人工检查清单项。
- 历史规则集永久保留（`_index.md` O6）与本条是同形取舍：保留成本近似为零，过期成本不对称地高。

### 3d. 冷存归档：形态已定，任务默认关闭

体量数量级（估算，非承诺）：单条记录以 `receiptId` 为主、含索引约 0.5 KB；购买次数与付费用户数同阶、每账号个位数 / 年 ⇒ 即便按每年 100 万次购买估，也只有约 0.5 GB / 年。**首版不开启归档任务**（`receiptArchiveEnabled` 初值 `false`）：为一个尚不存在的问题增加一条正确性关键路径是不划算的。形态在此写全，是为了触发条件真的命中那天不必临场设计——归档动的是幂等查重这条**正确性关键路径**，一次查不到就等于「当作新票」重复发放，且线上不可发现。

**承重约束（形态必须同时满足）：`receiptId` 的全量唯一性索引永不归档，可归档的只有记录体；冷数据仍需点查。** 因此**明确否决归档到只能顺序扫描的介质**（日志式冷存）。可接受的形态是归档后仍可点查、只是延迟更高——补查端点的延迟预算宽松，玩家侧本就处在阻塞重试态。

#### 三层分工

| 层 | 载体 | 在读路径上 |
|---|---|---|
| 热 | 现有 `receipt_idem` 表本身（按 `receiptId` 哈希分区，形态不变） | 是，一跳 |
| 温 | **同库同实例的独立表 `receipt_idem_archive`**，只装被搬走的记录体列，按 `record_at_utc` 做**年度 RANGE 分区**，每个分区上有 `receipt_id` 唯一索引 ⇒ 仍是点查 | 是，二跳 |
| 冷 | 对象存储的年度导出，只作长期备份与离线分析 | **否** |

三层同处一个库 / 一个实例：温层若移到另一实例或只读副本，S3（读己所写）与 S1（同事务）当场破防，且与「不引入独立存储系统」（`systems/_index.md`）相抵。

**归档表是另一张表，这正是两个分区维度能并存的原因**：单表只有一个分区键，在线哈希分区（3b）与按年 RANGE 分区各在各的表上，互不冲突。在线分区键不因归档而改动。

#### 哨兵行：唯一性与他账号判定永不离线

每一张收据**永远**在热层保留一行（**哨兵行**）。归档不删行，只把记录体列置 `NULL`。哨兵列永不归档、永不置空：

| 列 | 为什么必须常驻 |
|---|---|
| `receipt_id`（主键） | 唯一性约束本体。少一行 = 一次重复发放 |
| `account_id` | 「已被其他账号核销」是一次索引冲突后的当场判定（`systems/_index.md` 的数据库不变式），二跳判定会把它变回应用层查重 |
| `status` | 补查端点的应答主体；`Unknown` / `Rejected` 两态不需要记录体即可作答 |
| `tier`（`hot` \| `archived`） | 读路径判断要不要走第二跳 |
| `record_at_utc` = `COALESCE(verified_at_utc, ordered_at_utc)` | **二跳的分区剪枝键**。缺它，按 `receipt_id` 查温层会广播到全部年度分区——正是 3b 拒绝在线时间分区的那条退化 |

其余列（`channel` · `bundle_grant_ordinal` · `revision` · `ordered_at_utc` · `verified_at_utc` · 退款 / 关单等运维侧字段）是**记录体**，归档时写入温层并在热层置 `NULL`。`archived_at_utc` 为可空的运维列。

**归档因此不触碰任何事务路径**：verify 与下单仍只写 `receipt_idem` 一张表、仍是一次本地事务，3a 的 S1 / S2 逐字不变。

**`receipt_idem` 没有任何删除行的路径**，归档任务是**唯一**被允许把记录体列置 `NULL` 的路径。账号注销执行时该行同样保留，保留深度与账号侧墓碑的形态权威在 `operations/compliance-ops.md`。

#### 读路径

```
查重 / 补查 → 热层按 receipt_id 主键点查
  未命中                     ⇒ 按新票处理（verify 走正常流程；补查端点的应答语义见 contracts/purchase.md §4）
  命中且 account_id 不同      ⇒ purchase.receipt_claimed          （零二跳）
  命中且 status ≠ Verified    ⇒ 直接作答 Unknown / Rejected        （零二跳）
  命中且 tier = hot           ⇒ 直接作答（含序号与 revision）       （零二跳）
  命中且 tier = archived      ⇒ 按 (record_at_utc → 年度分区, receipt_id) 点查温层，取记录体作答
```

**verify 热路径永不二跳**：新票在第一跳未命中即结束。走第二跳的只有「几个月后重装回来的老票重复提交」与「客服补查老订单」，这两条路径的延迟预算本就宽松（玩家侧处在阻塞重试态，轮询间隔以秒计）。

| 路径 | 预算（初值，待实测校准） |
|---|---|
| 热层点查 p99 | ≤ 20 ms（与下方触发信号 ③ 同一个数，只有一个落点） |
| 温层二跳点查 p99 | ≤ 100 ms |
| 补查端点端到端 p99（含二跳） | ≤ 300 ms |
| 冷层导出 | 不在在线读路径上，无预算 |

#### 归档任务：单向、幂等、可重入

按批（`receiptArchiveBatchRows` 行）循环，每批一个事务，顺序固定：

1. `SELECT … FROM receipt_idem WHERE tier = 'hot' AND record_at_utc < now() - :ageMonths AND status <> 'Unknown' … FOR UPDATE SKIP LOCKED`；
2. `INSERT INTO receipt_idem_archive … ON CONFLICT (record_at_utc, receipt_id) DO NOTHING`（重入安全；冲突目标须含分区键，才能命中分区表上的主键）；
3. **确认温层该行已存在**后，同一事务内 `UPDATE receipt_idem SET tier = 'archived', archived_at_utc = now(), <记录体列> = NULL`。

- **顺序不可颠倒**：先写温层、后改哨兵。任何中断的最坏结果是「温层多一行、热层仍是 `hot`」——一次可重跑的空转；反序的最坏结果是「热层已置空、温层未写」这一**不可恢复的记录体丢失**。
- **`status = 'Unknown'` 的记录不归档**：微信渠道的未决 / 关单记录是对账任务的日常工作面（§2），搬走只会让日频对账天天二跳。
- 任务频次周级、跑在低峰，与既有的轻量周期任务同处一个出口（`operations/environments.md`「定时任务出口」），**不新增调度设施**。

#### TTL 禁用断言与备份口径

- **断言逐张表、逐个分区覆盖 `receipt_idem` 与 `receipt_idem_archive`。** 3c 的断言形态（部署时读取过期策略，非「永不过期」即拒绝启动）在引入温层后必须同时覆盖两张表的全部分区。少写一张表 = 归档表被一次误配置清掉 = 老票二跳查不到 = 重复发放，且线上不可发现，与合表漏洞逐字同形。
- **两张表须在同一 PITR 一致点上恢复**，并作为恢复演练的必检项（`decisions/ADR-0009-*` O3 的可演练恢复）。分开备份会恢复出「哨兵 `tier = archived`、温层无此行」的悬空指针，表现与记录被清掉相同。
- **冷层导出是备份的补充，不是温层的替代**：导出完成**不得**触发温层分区删除。

#### 触发信号

三个阈值均为初值，**待实测校准**：

| 信号 | 阈值初值 | 判为 |
|---|---|---|
| 在线表行数 > 5,000 万 | 5,000 万 | **容量 / 扩容信号**，不是归档信号 |
| 表 + 索引 > 50 GB | 50 GB | 归档信号 |
| 点查 p99 > 20 ms 持续 7 天 | 20 ms / 7 天 | 归档信号，**须先完成下列排除** |

- **行数阈值归档解决不了**：哨兵行必须常驻，键的条数只增不减，归档能降的只有行宽、堆体积与二级索引条目数。它的处置是纵向扩容 + 哈希分区数扩容（`systems/_index.md` 已给的扩展方向）。
- **点查 p99 劣化时，归档是最后手段而不是第一反应。** 按序排除：表 / 索引膨胀与 autovacuum 是否跟得上 · 二级索引是否已膨胀 · 连接池饱和与最长事务时长（`observability.md`「数据面」已有这两条指标）· 实例规格与共享缓冲区。在 0.5 GB / 年的体量下，p99 劣化几乎必然出自这四项之一而非行数——先归档等于为一个错误诊断增加一条正确性关键路径。
- **收益如实记下**：`receiptId` 本身（Google 的 `purchaseToken` 常见即数百字符）往往就是行的主体，记录体列合计约 60–90 字节 / 行、二级索引项约 40 字节 / 行 ⇒ 归档对体积阈值的收益上界大致在 **30–50%**，不是一个数量级。归档不是扩容手段。

#### 表形态与迁移

```
receipt_idem                                   -- 热层，PARTITION BY HASH (receipt_id)
  receipt_id            text        PK         -- 哨兵

  archived_at_utc       timestamptz            -- 可空，运维列
  channel               text                   -- ↓ 记录体，归档后置 NULL
  bundle_grant_ordinal  bigint
```

## 4. 对账信号与指标

| 信号 | 阈值初值 | 推导 |
|---|---|---|
| `bundleGrantOrdinal > bundleRedeemedOrdinal` **持续 N 天**（旋钮 `grantRedeemedLagAlertDays`） | N = 3 天 | 客户端的兑现触发点是「主菜单、一次 pull 完成之后」⇒ 正常玩家在下一次登录即追平。3 天覆盖一个周末的正常缺席，同时远短于平台退款 / 客诉窗口（以月计），使工单仍落在可处置期内 |
| 该差值 **≥ 2** | 立即（不设持续时长） | 正常路径下差值只会短暂为 1；≥2 意味着连续两次购买都未兑现，或兑现路径本身坏了——这是故障信号，不是玩家缺席信号 |
| 「已付款但从未 verify」（渠道对账发现） | 按对账周期，日频 | 日频足以落在退款窗口内 |

- **指标形态：一条 gauge「当前处于 `grant > redeemed` 的账号数」+ 一条按持续时长分桶的分布。不做逐账号告警**——逐账号会在任何一次客户端发版事故中变成告警风暴。

#### N 的旋钮位置与校准口径

- **N 落 `config_knob` 表**（`grantRedeemedLagAlertDays`，名目登记于 `operations/environments.md`「旋钮清单」）。写死在正文意味着改一次阈值发一次版，与「标注初值 / 待实测校准的数值一律落旋钮表」这条判据不符。
- **上线后先静默观测**：布尔旋钮 `grantRedeemedLagTicketEnabled` 初值 `false` —— 信号只上看板、不产出工单，**连续 4 周**（覆盖至少两个完整周末与一个月度活跃周期）之后再置 `true`。N 的正确性完全取决于「正常玩家的追平时长分布」，而这条分布在有真实玩家之前不存在；先出工单只会让首批工单全是正常在途。
- **校准公式**（数据源即上表的「按持续时长分桶的分布」）：

  ```
  N := clamp( ceil( P99(追平时长_天) ) + 1, 3, 14 )
  ```

  - 分桶取 **1 / 2 / 3 / 5 / 7 / 14 / 30+ 天**（低基数、覆盖 P99 可读区）。
  - `+1` 是余量位：分桶是离散的，P99 落在桶内何处不可知。
  - **下界 3 天**——一个周末的正常缺席，不下调。
  - **上界 14 天**——平台退款 / 客诉窗口以月计，工单须留出至少两周处置期 ⇒ N 不得超过窗口的一半。
- **复核节奏**：定值后每季度复核一次；**客户端兑现触发点的形态一变更即刻复核**——N 的整条推导挂在「兑现发生在主菜单、一次 pull 之后」这个前提上。
- **「差值 ≥ 2」不参与校准、不受 N 影响。** 它是故障信号（连续两次购买都未兑现，或兑现路径本身坏了），与「玩家缺席」不同轴；并进 N 的分布里会让一条故障曲线被玩家作息淹没。
- **N 命中只产出看板计数与工单。** 不存在也不得引入任何自动补发 / 自动核销 / 自动改写 `bundleRedeemedOrdinal` 的路径——那等于后端具备发放权，与「兑现段客户端演算、后端只复算」正面相悖（`contracts/purchase.md` §7 · `decisions/ADR-0007-purchase-write-authority.md`）。
- 三条信号**只作人工 / 工单入口**，与 `observability.md` 的三条同步探针并列。
- **P1 告警面：渠道 API 的 401 / 403**（服务账号凭据失效、IAP key 过期、微信平台证书轮换未跟上）。它表现为玩家侧的 `server.unavailable`，但根因是我方配置事故，不是玩家问题——混在普通不可达曲线里会被当作渠道抖动忽略过去。
- **下单端点的滥用阈值**：`POST /v1/purchase/order` 是一条需鉴权的写路径，须有按账号的频次上限，形态与 push 滥用阈值同构（`contracts/profile-sync.md` 侧的先例）；具体数值与实现随栈落定。

## 5. 风控事件

验票路径产出的风控事件（账号 · 平台 · 失败项 · `requestId`）落同一条风控通道，**高优项**为：收据环境与部署环境不符 · 微信必查四项不符 · 已消费但本库无记录 · 同一 `receiptId` 被他账号提交。`message` 的落日志纪律（不得含完整凭据，标识按前缀截断）沿用 `_index.md`「版本兼容矩阵与错误码台账」一节，本文件不另立一套。
