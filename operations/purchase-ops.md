# 购买与验票的运维面 —— 渠道凭据 · 对账 · 幂等记录的存储要求

> 语义权威在 `contracts/purchase.md`（报文、权威分配、七条服务端保证、`receiptId` 幂等窗口）与 `decisions/ADR-0007-purchase-write-authority.md`；**此处只记它对运维形态的要求**，不复述契约语义。
> 客户端侧的购买流程与待兑现态形态在 `game-design-documents/systems/monetization.md`，同样只回链、不复述。
> **存储产品选型、事务实现、密钥托管形态随后端栈落定**：本文件给的是**判据与断言**（选型的输入），不是选型结论。选型见 `operations/environments.md` 与 `open-questions/06-platform-stack.md` 的余项。

## 1. 渠道验票凭据与轮换

| 渠道 | 服务端凭据 | 轮换特征 |
|---|---|---|
| Google Play | Play Developer API 的服务账号凭据（或等价的工作负载身份） | 可无停机轮换；权限范围只给「查询 + 消费购买」 |
| App Store | In-App Purchase key（`.p8` + keyId + issuerId）用于 Server API；Apple 根证书用于离线 JWS 校验 | key 可并存新旧；**根证书随 Apple 更新，须有更新通道** |
| 微信支付 | 商户 API 私钥 + 证书序列号、APIv3 密钥（回调解密）、平台证书 / 公钥（回调验签） | **平台证书会轮换**，须支持新旧并存期，否则轮换当天全渠道验票中断 |

- **三套凭据一律只在服务端，绝不进客户端二进制**——与 `contracts/auth.md` §3a 的渠道 secret 义务逐字同构。
- **三把钥匙、三套轮换窗口，不共用托管配置**：内容签名 ES256 私钥（`_index.md`「内容分发」）· 会话 token 签名密钥 · **渠道验票凭据（本条）**。三者的轮换节奏互不相同——内容签名的轮换跨越一个客户端发版周期，token 密钥的轮换只在服务端，渠道凭据的轮换由渠道方的日程驱动。共用一份托管配置会让最慢的那条节奏绑架其余两条。
- **环境隔离是凭据层的事**：测试环境用沙箱凭据、生产用生产凭据。且收据的环境校验（Apple `environment` / Google `purchaseType = Test`）以**部署环境配置**为准，**不以收据自述为准**——沙箱交易在生产被接受等于任何人可无限白嫖礼包。

## 2. 退款 / 撤单的对账通道

| 渠道 | 对账通道 | 补漏手段 |
|---|---|---|
| Google Play | Real-time Developer Notifications（推送）+ voided purchases 列表 | 定期拉 voided 列表兜底，不依赖推送必达 |
| App Store | App Store Server Notifications V2（`REFUND` / `REVOKE` 等） | 通知历史接口回补漏收的通知 |
| 微信支付 | 退款结果通知 + 退款查询 | 定期按时间窗查单兜底 |

- **三条通道的共同形态：推送只作「更快知道」，周期性拉取才是正确性来源。** 回调不可达是常态，而对账的正确性不能押在推送必达上。
- **对账任务日频**，足以落在平台退款 / 客诉窗口（以月计）之内。
- **对账不驱动任何自动写入**（`contracts/purchase.md` §7 · `ADR-0007`）：退款只在幂等记录的运维侧字段上打标并进工单，权益不回收、序号不回退。**「已付款但从未 verify」**的兜底发现也在这条任务上，同样只产出工单。
- 微信渠道的**未支付订单关单**由同一条任务承担：预落的 `status = unknown` 记录在订单有效期后仍未转 `verified` 即标记关单，**记录本身不删**。

## 3. 幂等记录的存储要求

### 3a. 三条选型判据（不满足即出局）

| # | 判据 | 不满足的后果 |
|---|---|---|
| S1 | 幂等记录的写入与 `bundleGrantOrdinal += 1`、`cloudRevision += 1` **能落在同一次事务内** | 出现「revision 已 `+1` 但幂等记录未落」的中间态——正是重放会重复发放的那一刻 |
| S2 | `receiptId` 的唯一性由**存储层的唯一约束**保证，不由应用层「先读后写」保证 | 并发双提交在读-写窗口内双双通过，同一张票 `+1` 两次；这类窗口在压测下不出现、在线上偶发 |
| S3 | 收据记录的读路径与 profile 读路径受**同一条读己所写约束**（`contracts/purchase.md` §6 保证 3） | `GET /receipt/{receiptId}` 读到滞后副本 ⇒ 客户端在阻塞重试态下反复读到 `unknown`，与「verify 从未成功」不可区分 |

**S1 与「全局唯一键」的张力，以及退化形态。** 全局唯一要求一条跨账号的唯一索引，而账号级事务通常按账号分区。若选型无法让两者同处一次事务，**退化形态**（仅在 S1 不可满足时启用）是拆成两条记录：`receiptClaim`（全局唯一索引 `receiptId → { accountId, claimedAtUtc, state }`，在事务**之前**以 `state = claiming` 写入）与 `receiptRecord`（与账号聚合同处，随 `+1` 事务一并写入）。判定规则：claim 命中且 `accountId` 相同 ⇒ 同一账号的重试，接管并继续；`accountId` 不同 ⇒ `purchase.receipt_claimed`。悬挂的 `claiming`（超过阈值仍无对应 `receiptRecord`）由清理任务回收，**阈值初值 10 分钟**（一次验票的端到端上界是渠道查询超时 + 事务耗时，秒级；10 分钟给异常态两个数量级余量，且远短于玩家重试的耐心周期；**初值待实测校准**）。**这是退化形态而非首选**——它把一个事务变成两步，正确性靠一条清理任务维持。

### 3b. 分区与索引

- **按 `receiptId` 做哈希分区。** 本表的在线负载**只有点查**（验票查重、补查端点），没有任何按 `receiptId` 的范围扫描，哈希分区给出最均匀的分布。
- **按时间做在线分区是错的**：查询时不知道这张票是哪年的，点查会退化为跨全部分区的广播。时间维度只用于归档（3d），不用于在线分区。
- **一条二级索引 `(accountId, verifiedAtUtc)`。** 对账、客服排障、退款处置的唯一查询路径都是「这个账号买过什么」；缺它则这三件事只能全表扫。

### 3c. 与 `(accountId, pushId)` 幂等记录：可同系统，不可合表

| 维度 | `receiptId` | `(accountId, pushId)` |
|---|---|---|
| 键作用域 | 全局 | 账号内 |
| 保留期 | **永久，不设 TTL** | 30 天 TTL |
| 写入频次 | 每账号个位数 / 年 | 稳态约每分钟 1 次 / 账号 |

- **同一存储系统可以，同一张表不行。** 差三个数量级的写入频次与两套相反的保留策略共表，唯一的好处是少建一张表。
- **收据表须显式关闭任何 TTL / 过期清理机制，并在配置层留一条断言。** 这是本节最承重的一条：合表或共享 TTL 配置时，一次误配置就等于收据记录被清掉 = 重复发放漏洞，而这个漏洞**线上不可发现**（第二次提交查不到记录即当作新票，玩家白得一份，没有任何报错）。断言的形态是配置层的显式校验（部署时读取该表的过期策略，非「永不过期」即拒绝启动），不是一条人工检查清单项。
- 历史规则集永久保留（`_index.md` O6）与本条是同形取舍：保留成本近似为零，过期成本不对称地高。

### 3d. 冷存归档：首版不做，只留触发条件

体量数量级（估算，非承诺）：单条记录以 `receiptId` 为主、含索引约 0.5 KB；购买次数与付费用户数同阶、每账号个位数 / 年 ⇒ 即便按每年 100 万次购买估，也只有约 0.5 GB / 年。

- **触发任一即启动归档**（三个阈值均为初值，**待实测校准**）：① 在线表行数 > 5,000 万；② 表 + 索引 > 50 GB；③ 点查 p99 > 20 ms 持续 7 天。按上述体量，①② 相当于数十年量级，实际上必然先经历一次栈演进；③ 是唯一可能提前到来的信号，且它直接对应玩家侧的阻塞等待时长。
- **首版即上冷存归档是明确否决的**：为一个尚不存在的问题增加一条正确性关键路径。
- **归档形态的承重约束：`receiptId` 的全量唯一性索引永不归档，可归档的只有记录体。** 幂等查询必须命中冷数据——一次查不到就等于「当作新票」重复发放。因此**明确否决归档到只能顺序扫描的介质**（日志式冷存）：本表的冷数据仍需**点查**。可接受的形态是冷分区仍可点查、只是延迟更高——补查端点的延迟预算宽松，玩家侧本就处在阻塞重试态。
- 归档切分维度用 `verifiedAtUtc`（年度分区），与 3b 的在线哈希分区不冲突：归档是把整个「年」的记录体搬走，不改变在线点查路径。

## 4. 对账信号与指标

| 信号 | 阈值初值 | 推导 |
|---|---|---|
| `bundleGrantOrdinal > bundleRedeemedOrdinal` **持续 N 天** | N = 3 天 | 客户端的兑现触发点是「主菜单、一次 pull 完成之后」⇒ 正常玩家在下一次登录即追平。3 天覆盖一个周末的正常缺席，同时远短于平台退款 / 客诉窗口（以月计），使工单仍落在可处置期内 |
| 该差值 **≥ 2** | 立即（不设持续时长） | 正常路径下差值只会短暂为 1；≥2 意味着连续两次购买都未兑现，或兑现路径本身坏了——这是故障信号，不是玩家缺席信号 |
| 「已付款但从未 verify」（渠道对账发现） | 按对账周期，日频 | 日频足以落在退款窗口内 |

- **指标形态：一条 gauge「当前处于 `grant > redeemed` 的账号数」+ 一条按持续时长分桶的分布。不做逐账号告警**——逐账号会在任何一次客户端发版事故中变成告警风暴。
- 三条信号**只作人工 / 工单入口**，与 `observability.md` 的三条同步探针并列。
- **P1 告警面：渠道 API 的 401 / 403**（服务账号凭据失效、IAP key 过期、微信平台证书轮换未跟上）。它表现为玩家侧的 `server.unavailable`，但根因是我方配置事故，不是玩家问题——混在普通不可达曲线里会被当作渠道抖动忽略过去。
- **下单端点的滥用阈值**：`POST /v1/purchase/order` 是一条需鉴权的写路径，须有按账号的频次上限，形态与 push 滥用阈值同构（`contracts/profile-sync.md` 侧的先例）；具体数值与实现随栈落定。

## 5. 风控事件

验票路径产出的风控事件（账号 · 平台 · 失败项 · `requestId`）落同一条风控通道，**高优项**为：收据环境与部署环境不符 · 微信必查四项不符 · 已消费但本库无记录 · 同一 `receiptId` 被他账号提交。`message` 的落日志纪律（不得含完整凭据，标识按前缀截断）沿用 `_index.md`「版本兼容矩阵与错误码台账」一节，本文件不另立一套。
