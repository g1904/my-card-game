# 昵称审核 · 存量扫描 · 风控的运维形态

> 语义权威在 `contracts/auth.md` §8 §10 与 `contracts/profile-sync.md` §5c §7a；本文件只记运维形态须满足的性质，不指定实现。判定链的服务内部形态见 `systems/account.md`。
> Source: `handoffs/2026-09-03-nickname-moderation-and-risk-control.md`。

## 昵称词表的不可变版本化发布

词表是后端配置数据，**不下发客户端、不进任何报文**——客户端自带一份即第二权威，且补一句禁词就要发版。

- **发布形态逐条复用 flags 规则集的 O1–O7 与留痕四项**（无原地编辑路径 · 版本号单一分配点且单调 · 回滚 = 以历史内容发起更大版本 · 操作者 / 时间 / `derivedFrom` / 变更摘要 · 历史永久保留）。**不是顺手抄一套**：存量扫描必须能回答「这个昵称当初是按哪一版词表放行的」，而「随手改一下数据源」正是 O1 要堵的静默失效模式。词表体积与 flags 规则集同量级，永久保留成本近似为零。
- **两档分级**，与判定链一一对应：

  | 档 | 判定 | 端点应答 | 后续 |
  |---|---|---|---|
  | **禁止级** | 政治 / 涉恐 / 色情 / 极端辱骂等无争议违禁 | `auth.nickname_rejected` + `SensitiveWord` | 无 |
  | **复核级** | 擦边、谐音变体、疑似冒充官方 / 客服 | `204` | 入复核队列 |

  两档而非三档：**「放行」不是一档，是补集**——同「白名单的补集即不透明段」的措辞纪律，避免第三份清单漂移。
- **来源三条通道**：① 监管 / 行业公开基础表导入为初始基线；② 人工复核队列的判定结果回灌；③ 渠道过审反馈与工单。三条**都收敛到同一次发布动作，不存在旁路写入**。
- **第三方审核适配器首版不启用、只留位**（实现为透传恒放行）；C 层原子能力一律外接以适配器隔离，服务商与评分阈值归 `06`。是否启用取决于「合规能力的上线分级」。

## 未过审昵称的存量扫描

扫描范围恒为单字段 `/accountInfo/nickname`（它在透明白名单内、后端有权读；后端不解不透明段）。

| # | 触发 | 覆盖面 | 频率 |
|---|---|---|---|
| **T1** | **push 事件驱动**：`playerDiff` 含 `accountInfo` 顶层键 | 全部活跃改名 | 每次（零额外成本） |
| **T2** | **词表版本更新驱动** | `reviewedWordlistVersion` 落后的账号 | 每次发布一轮 |
| **T3** | **定期兜底全量** | 全部账号 | 30 天 / 轮（初值） |

- **T1 是确定性检出，不是抽查。** 后端本就要解 `playerDiff` 的顶层键，比对本次 `nickname` 与该账号最近一次经改名端点接受的值——**不等 ⇒ 该账号绕过了改名端点**，成本是一次字符串比较。`/accountInfo/nickname` **不受回声校验约束**（它不在后端写入表，客户端有权写它）⇒ **T1 只记账与判定，绝不拒绝上行、绝不改写**：在 push 上拒绝会同时撞「客户端有权写的路径只记账不拒绝」「同步通道不承载合规拦截」与 pillar #4。
- **T2 的增量面明确，正因为词表不可变版本化**：每个账号记着「上次按哪一版词表通过」，新版本发布后只重扫落后的那批。没有版本化，T2 只能退化为每次全量。
- **T3 只兜 T1 / T2 的实现缺陷与边角**（长期不上行、不改名的沉睡账号）：30 天与 `pushId` 保留期 / refresh 滑动 TTL 同量级，使三处窗口不互相穿帮；合规抽查本身是月度节奏。纯离线批处理、可错峰。待实测校准。
- **扫描台账落后端内部存储，不进 profile**（后端内部状态，且写入表封闭）。字段：`accountId` · `lastAcceptedNickname` · `acceptedAtUtc` · `reviewedWordlistVersion` · `reviewState` · `lastScannedAtUtc`。
- **复核队列与存量扫描是同一条处置通道的两个入口**，不是两套机制。

**处置阶梯**（后端**绝不改写或置空**云端昵称，处置只落 `status` 侧）：

| 档 | 判据 | `status` | 玩家可见 |
|---|---|---|---|
| **观察** | 复核级命中；T1 首次检出绕过写入 | 不变（`active`） | 无 |
| **须改名** | 禁止级命中；复核判违规 | 不变 | `GET /v1/compliance/status` 的 `nicknameChangeRequired` 为真，登录后走一次改名流程即自解除 |
| **限制 / 封禁** | 拒不改名；恶意反复；申诉驳回 | `restricted` / `banned` | `compliance.account_restricted` + `UnderReview` / `Banned`，申诉走站外 |

`nicknameChangeRequired` **由云端状态算出**：处置台账处于「须改名」档、且云端 `/accountInfo/nickname` 仍是被判违规的那个值时为真；玩家改名并 push 后由 T1 的比对自动清零。**不在端点判定通过的那一刻清零**——那会让「调用端点但不 push」成为绕过路径；T3 仍兜底。`status` 变更连带吊销全部会话、下行 `OperatorRevoked`，因此 `restricted` / `banned` 的解除**只改回 `status`，永不带外改写昵称**：玩家重登后标记仍为真，自己改名即可。

## 风控事件流与阈值

**风控不是第四个后端服务**：事件产出在 `account` / `profile-store` 内部旁路（**绝不在同步热路径上裁决**，push 的应答不等待它落盘），聚合、阈值与处置流程落本文件。

**事件字段表**（一张表同时装下回声校验与越界记账两组已具名字段，不另立两套）：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `eventId` | string | ✅ | 去重与工单关联的键 |
| `occurredAtUtc` | string (RFC 3339 UTC) | ✅ | — |
| `accountId` | string | ✅ | — |
| `kind` | string enum (PascalCase) | ✅ | 取值见下 |
| `severity` | string enum (PascalCase) | ✅ | `Info` / `Warn` / `Critical` |
| `subject` | string | 可选 | 被判定对象的定位串：JSON path 或字段名 |
| `expected` | string | 可选 | 期望值。**一律字符串序列化**——取值域跨类型，且 `ulong` 类超 2⁵³ 会在 JSON number 上静默丢低位 |
| `actual` | string | 可选 | 实收值，同上 |
| `requestId` | string | 可选 | 回显 `X-Request-Id`，把两侧日志接起来 |
| `deviceId` | string | 可选 | **只作观测维度，永不参与判定**（客户端自报可伪造值） |
| `appVersion` · `contentVersion` | string | 可选 | 取自请求头；**熔断判据的分组维度** |
| `context` | object | 可选 | 按 `kind` 取固定形状（同 `detail` 按 `code` 定形的纪律） |

**`kind` 八值**（清单可增量，未知取值不驱动判定）：`RollMismatch` · `ChanceInconsistent` · `InvariantViolated` · `EchoRejected` · `NicknameBypassed` · `NicknameViolation` · `RevisionAhead` · `RateLimitTripped`。

**四条落地纪律：** 只追加（条目永不改写、永不单条删除，到期整体过期）· 旁路不在热路径裁决 · **不进 profile** · 保留期初值 **180 天**（覆盖两倍于最长累计窗口 90 天；含可关联到个人的行为数据，不宜永久）。

**累计阈值（按 `kind` 分档，一律落后端配置）：**

| `kind` | 观察阈值 | 升级阈值 | 推导 |
|---|---|---|---|
| `RollMismatch` · `ChanceInconsistent` · `InvariantViolated` | ≥1 次 / 90 天 | ≥3 次 / 90 天 且 ≥2 个不同 `finaleWinOrdinal` | 正常账号的期望值是 0（复算是确定性纯函数），但迁移期 / 实现差一位会产生噪声，故不能一次即封。三篇章 ⇒ 一个轮回周期最多 3 次机会；90 天 ≈ 一个内容大版本周期 |
| `EchoRejected` | ≥3 次 / 7 天 | ≥10 次 / 7 天 | 正常客户端零误报（判据是所有权）⇒ 阈值可更紧、窗口可更短 |
| `NicknameBypassed` | ≥1 次即进复核 | 无累计档 | 它是确定性检出而非概率信号，累计计数对它无意义 |
| `NicknameViolation` | ≥1 次 → 须改名档 | ≥3 次 / 180 天 → 封禁档 | 反复取违规昵称是意图信号，而非失误 |

> **全局熔断（承重）：** 同一 `appVersion` / `contentVersion` 分组内，`RollMismatch` 触发率 > **1%** 账号，或 `EchoRejected` > **0.5%** 账号 ⇒ **一律判为我方实现缺陷，立即暂停该分组的一切自动处置并告警。** 单人游戏、无玩家间交互、作弊收益是「每篇章至多一次的低价值掉落」——真实作弊渗透率不可能达到 1%，故 1% 是「这是 bug」的强信号，不是「这是作弊潮」。`EchoRejected` 取更低的 0.5%，因为它的误报会**当场丢玩家进度**。它防的正是最坏那一类事故：后端复算差一位或客户端一次发版 bug ⇒ 大批正常玩家被限制。

**自动化止步于「观察」与「生成工单」；`restricted` / `banned` 一律需人工确认。** 两条依据：`status` 变更连带吊销全部会话（一次误判 = 一次强制下线，撞 pillar #4）；且全局熔断的存在本身就意味着必须有人在回路里判断「这是作弊还是我方 bug」。

**线上探针的采集口径：** **复算不一致率与「本地领先」两条探针由本事件流聚合得出，不另建第二条采集路径**（分别对应 `RollMismatch` 与 `RevisionAhead`）——两条采集路径必然漂移，而漂移时没有任何机制会报错。**`pushId` 去重命中率不是风控事件**：它是同步通道的常规计数（弱网下的去重命中是常态，不是异常信号），做成风控事件会淹没事件流；透明路径缺失告警同理，仍走告警台账。
