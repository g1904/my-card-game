> Source: `handoffs/2026-09-03-nickname-moderation-and-risk-control.md` · `handoffs/2026-09-07-compliance-launch-tiering.md`（第三方审核适配器的启用触发条件）。

## 昵称词表的不可变版本化发布

词表是后端配置数据，**不下发客户端、不进任何报文**——客户端自带一份即第二权威，且补一句禁词就要发版。

- **发布形态逐条复用 flags 规则集的 O1–O7 与留痕四项**（无原地编辑路径 · 版本号单一分配点且单调 · 回滚 = 以历史内容发起更大版本 · 操作者 / 时间 / `derivedFrom` / 变更摘要 · 历史永久保留）。**不是顺手抄一套**：存量扫描必须能回答「这个昵称当初是按哪一版词表放行的」，而「随手改一下数据源」正是 O1 要堵的静默失效模式。词表体积与 flags 规则集同量级，永久保留成本近似为零。
- **两档分级**，与判定链一一对应：

  | 档 | 判定 | 端点应答 | 后续 |
  |---|---|---|---|
  | **禁止级** | 政治 / 涉恐 / 色情 / 极端辱骂等无争议违禁 | `auth.nickname_rejected` + `SensitiveWord` | 无 |
  | **复核级** | 擦边、谐音变体、疑似冒充官方 / 客服 | `204` | 入复核队列 |

  两档而非三档：**「放行」不是一档，是补集**——同「白名单的补集即不透明段」的措辞纪律，避免第三份清单漂移。
- **来源三条通道**：① 监管 / 行业公开基础表导入为初始基线；② 人工复核队列的判定结果回灌；③ 渠道过审反馈与工单。三条**都收敛到同一次发布动作，不存在旁路写入**。
- **第三方审核适配器首版不启用、只留位**（实现为透传恒放行）；C 层原子能力一律外接以适配器隔离，适配接口、归一档位与灾备形态见 `operations/external-providers.md`。
  **触发启用的唯一条件：渠道过审点名要求接入第三方内容审核能力。** 触发时以真实人工判定样本标定下方两阈值，并登记进本文件的数值初值表。
  留位而不启用的理由：昵称在本作没有任何玩家间可见性（`contracts/auth.md` §8）⇒ 残留风险面只剩合规抽查，而抽查面已由本地词表两档分级 + 存量扫描 + 三档处置阶梯完整承接——**第④级是增强，不是承重**；启用的边际成本则是明确且非零的一份负债（一家服务商过选型判据 · 一份独立审计线的凭据轮换 · 同步路径上的玩家等待预算 · 一条要监控的曲线）。给它写死触发条件而非留一个开放留位，是因为没有触发条件的留位会变成没有人会再想起来的空位。

  **适配器阈值是两个，不是一个**：`rejectThreshold`（判拒绝，落禁止级同一出口）与 `reviewThreshold`（入复核）。单阈值表达不了判定链要求的三档落点（拒绝 / 待复核 / 放行）。
  - **阈值的维度是「服务商 × 环境」，不是一个全局数。** 不同审核服务的评分刻度互不可比（有的 0–1、有的 0–100、有的分类标签 + 置信度），写成一个全局单值，换一家服务商当天判定口径就会静默漂移。
  - **标定方式**：拿一批人工已判定的昵称跑一遍，取使漏放（判放行实为违规）最小、且误拒可接受的一对阈值。
  - **能力未启用 ⇒ 不定值。** 启用之日（触发条件见上）以真实样本标定，届时登记进下方数值初值表。首版无人工判定样本可用，上一对未标定的阈值等于让误拒以 `SensitiveWord` 告诉玩家「你的昵称违规」——那正是判定链明令避免的体验（`systems/account.md` N9）。

## 未过审昵称的存量扫描

扫描范围恒为单字段 `/accountInfo/nickname`（它在透明白名单内、后端有权读；后端不解不透明段）。

| # | 触发 | 覆盖面 | 频率 |
|---|---|---|---|
| **T1** | **push 事件驱动**：`playerDiff` 含 `accountInfo` 顶层键 | 全部活跃改名 | 每次（零额外成本） |
| **T2** | **词表版本更新驱动** | `reviewedWordlistVersion` 落后的账号 | 每次发布一轮 |
| **T3** | **定期兜底全量** | 全部账号 | 30 天 / 轮（初值） |

- **T1 是确定性检出，不是抽查。** 后端本就要解 `playerDiff` 的顶层键，比对本次 `nickname` 与该账号最近一次经改名端点接受的值——**不等 ⇒ 该账号绕过了改名端点**，成本是一次字符串比较。`/accountInfo/nickname` **不受回声校验约束**（它不在后端写入表，客户端有权写它）⇒ **T1 只记账与判定，绝不拒绝上行、绝不改写**：在 push 上拒绝会同时撞「客户端有权写的路径只记账不拒绝」「同步通道不承载合规拦截」与 pillar #4。
- **T2 的增量面明确，正因为词表不可变版本化**：每个账号记着「上次按哪一版词表通过」，新版本发布后只重扫落后的那批。没有版本化，T2 只能退化为每次全量。
- **T3 只兜 T1 / T2 的实现缺陷与边角**（长期不上行、不改名的沉睡账号）：30 天与 `pushId` 保留期 / refresh 滑动 TTL 同量级，使三处窗口不互相穿帮；合规抽查本身是月度节奏。纯离线批处理、可错峰。待实测校准。
- **扫描台账落后端内部存储，不进 profile**（后端内部状态，且写入表封闭）。字段：`accountId` · `lastAcceptedNickname` · `acceptedAtUtc` · `reviewedWordlistVersion` · `reviewState` · `lastScannedAtUtc`。
- **复核队列与存量扫描是同一条处置通道的两个入口**，不是两套机制。

**处置阶梯**（后端**绝不改写或置空**云端昵称，处置只落 `status` 侧）：

| 档 | 判据 | `status` | 玩家可见 |
|---|---|---|---|
| **观察** | 复核级命中；T1 首次检出绕过写入 | 不变（`active`） | 无 |
| **须改名** | 禁止级命中；复核判违规 | 不变 | `GET /v1/compliance/status` 的 `nicknameChangeRequired` 为真，登录后走一次改名流程即自解除 |
| **限制 / 封禁** | 拒不改名；恶意反复；申诉驳回 | `restricted` / `banned` | `compliance.account_restricted` + `UnderReview` / `Banned`，申诉走站外 |

**「须改名」档豁免改名频次闸的拦截，不豁免计数。** 该档的解除路径就是走一次改名流程；若该玩家此前刚好用尽改名配额，他会撞上 `TooFrequent` 而无法解除自己的处置状态——处置阶梯与频次闸互相锁死，且没有任何自解通道。频次闸防的是刷子，而处于本档的玩家是**被我方要求**改名的。该次改名照常计数，使解除后立刻再刷仍会被挡住。判定链上的落点见 `contracts/auth.md` §8 与 `systems/account.md`。

`nicknameChangeRequired` **由云端状态算出**：处置台账处于「须改名」档、且云端 `/accountInfo/nickname` 仍是被判违规的那个值时为真；玩家改名并 push 后由 T1 的比对自动清零。**不在端点判定通过的那一刻清零**——那会让「调用端点但不 push」成为绕过路径；T3 仍兜底。`status` 变更连带吊销全部会话、下行 `OperatorRevoked`，因此 `restricted` / `banned` 的解除**只改回 `status`，永不带外改写昵称**：玩家重登后标记仍为真，自己改名即可。

## 风控事件流与阈值

**风控不是第四个后端服务**：事件产出在 `account` / `profile-store` 内部旁路（**绝不在同步热路径上裁决**，push 的应答不等待它落盘），聚合、阈值与处置流程落本文件。

**事件字段表**（一张表同时装下回声校验与越界记账两组已具名字段，不另立两套）：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `eventId` | string | ✅ | 去重与工单关联的键 |
| `occurredAtUtc` | string (RFC 3339 UTC) | ✅ | — |
| `accountId` | string | ✅ | — |
| `kind` | string enum (PascalCase) | ✅ | 取值见下 |
| `severity` | string enum (PascalCase) | ✅ | `Info` / `Warn` / `Critical` |
| `subject` | string | 可选 | 被判定对象的定位串：JSON path 或字段名 |
| `expected` | string | 可选 | 期望值。**一律字符串序列化**——取值域跨类型，且 `ulong` 类超 2⁵³ 会在 JSON number 上静默丢低位 |
| `actual` | string | 可选 | 实收值，同上 |
| `requestId` | string | 可选 | 回显 `X-Request-Id`，把两侧日志接起来 |
| `deviceId` | string | 可选 | **只作观测维度，永不参与判定**（客户端自报可伪造值） |
| `appVersion` · `contentVersion` | string | 可选 | 取自请求头；**熔断判据的分组维度** |
| `context` | object | 可选 | 按 `kind` 取固定形状（同 `detail` 按 `code` 定形的纪律） |

**`kind` 取值**（清单可增量，未知取值不驱动判定）：`RollMismatch` · `ChanceInconsistent` · `InvariantViolated` · `EchoRejected` · `NicknameBypassed` · `NicknameViolation` · `RevisionAhead` · `RateLimitTripped` · `DeletionRequested` · `DeletionCancelled`。

**后两值只作审计，不进阈值表、不驱动任何自动处置**。它们**不写 `risk_event`，落单独的 `deletion_audit` 表**（保留 3 年、注销执行时不删，判据见下方「四张台账的存储形态」）：

| `kind` | 写入时点 | `severity` | `context` |
|---|---|---|---|
| `DeletionRequested` | 注销申请端点**同一次事务内**，与 `account_deletion` 行的插入同批写入 | `Info` | `{ effectiveAtUtc, previousStatus }`，**不含任何个人信息** |
| `DeletionCancelled` | 撤销端点**同一次事务内**，与「删 `account_deletion` 行 + 恢复 `status`」同批写入 | `Info` | `{ restoredStatus }` |

**它们与其余八值分表，因为不在同一条时间轴上。** 其余八值服务于风控判定，尺度是累计窗口；这两值服务于**举证**：撤销即删行 ⇒ 它是「谁在什么时候申请过 / 撤销过」在库内的唯一留痕，而一次「我明明撤销过、账号却被删了」的客诉往往在半年、一年后才到（玩家在想回来玩时才发现）。同处一张按 180 天裁剪的表会让那时的服务端零证据可查。

**为什么必须有这两值（承重）：** 注销冷静期的撤销形态是**撤销即删行**——行一删，「谁在什么时候申请过 / 撤销过」在库内就**只剩事件流这一个落点**。没有它，一次「我明明撤销过」的客诉在服务端零证据可查，而这条路径直接决定账号是否被删除。与事件流同一次事务写入是必需的：拆成两次写会让「行已删、事件未落」成为一个可达状态，而那正是要留证的那一刻。

**四条落地纪律：** 只追加（条目永不改写、永不因业务原因单条删除，到期整体过期）· 旁路不在热路径裁决 · **不进 profile** · 保留期初值 **180 天**（覆盖两倍于最长累计窗口 90 天；含可关联到个人的行为数据，不宜永久）。这四条约束的是 `risk_event` 承载的八个 `kind`；`deletion_audit` 的两值另有保留期与删除语义，见下方存储形态一节。

**累计阈值（按 `kind` 分档，一律落后端配置）：**

| `kind` | 观察阈值 | 升级阈值 | 推导 |
|---|---|---|---|
| `RollMismatch` · `ChanceInconsistent` · `InvariantViolated` | ≥1 次 / 90 天 | ≥3 次 / 90 天 且 ≥2 个不同 `finaleWinOrdinal` | 正常账号的期望值是 0（复算是确定性纯函数），但迁移期 / 实现差一位会产生噪声，故不能一次即封。三篇章 ⇒ 一个轮回周期最多 3 次机会；90 天 ≈ 一个内容大版本周期 |
| `EchoRejected` | ≥3 次 / 7 天 | ≥10 次 / 7 天 | 正常客户端零误报（判据是所有权）⇒ 阈值可更紧、窗口可更短 |
| `NicknameBypassed` | ≥1 次即进复核 | 无累计档 | 它是确定性检出而非概率信号，累计计数对它无意义 |
| `NicknameViolation` | ≥1 次 → 须改名档 | ≥3 次 / 180 天 → 封禁档 | 反复取违规昵称是意图信号，而非失误 |

> **全局熔断（承重）：** 同一 `appVersion` / `contentVersion` 分组内，`RollMismatch` 触发率 > **1%** 账号，或 `EchoRejected` > **0.5%** 账号 ⇒ **一律判为我方实现缺陷，立即暂停该分组的一切自动处置并告警。** 单人游戏、无玩家间交互、作弊收益是「每篇章至多一次的低价值掉落」——真实作弊渗透率不可能达到 1%，故 1% 是「这是 bug」的强信号，不是「这是作弊潮」。`EchoRejected` 取更低的 0.5%，因为它的误报会**当场丢玩家进度**。它防的正是最坏那一类事故：后端复算差一位或客户端一次发版 bug ⇒ 大批正常玩家被限制。

**自动化止步于「观察」与「生成工单」；`restricted` / `banned` 一律需人工确认。** 两条依据：`status` 变更连带吊销全部会话（一次误判 = 一次强制下线，撞 pillar #4）；且全局熔断的存在本身就意味着必须有人在回路里判断「这是作弊还是我方 bug」。

**工单与人工确认的落点：本库自己的 `ops_ticket` 表 + 内部端点。** 不进外部工单系统——处置必须与 `account.status` 写入同一次事务（含会话吊销），跨系统即让「工单已关、`status` 未改」成为可达状态。工单形态、领取语义、处置端点、`baseAccountStatus` 前置条件与内部人员身份见 `operations/internal-tools.md`；表的承重列与事务边界见 `systems/account.md`。复核台判违规落「须改名」档、以及 `restricted` / `banned` 的人工确认，都经这一个面写回。

**线上探针的采集口径：** **复算不一致率与「本地领先」两条探针由本事件流聚合得出，不另建第二条采集路径**（分别对应 `RollMismatch` 与 `RevisionAhead`）——两条采集路径必然漂移，而漂移时没有任何机制会报错。**`pushId` 去重命中率不是风控事件**：它是同步通道的常规计数（弱网下的去重命中是常态，不是异常信号），做成风控事件会淹没事件流；透明路径缺失告警同理，仍走告警台账。

## 与合规域运维面的交叉点

合规域的运维形态已展开为 `operations/compliance-ops.md`（可信时钟与同步纪律 · 时区与时段规则集 · 法定节假日日历 · 三个失败面的降级语义 · `complianceTicket` 的存储与一次性消费 · 注销冷静期的跨天长时状态机 · 数据导出的任务 / 产物 / 链接签发 · 周期任务与旋钮的校准信号 · 上线分级）；语义权威在 `contracts/compliance.md`。**本节不复述它**，只记两者的交叉面。

- **交叉面只有一条：注销申请与撤销各在自己的事务内写一条审计事件**（`DeletionRequested` / `DeletionCancelled`，落 `deletion_audit` 表，形态见上方 `kind` 取值一节与下方存储形态一节）。撤销即删行 ⇒ 这张表是两个动作在库内的唯一留痕，因此写入必须与状态变更同事务。**它也是注销执行删除清单的唯一例外**（`operations/compliance-ops.md`「执行时删什么」）：条目不含任何个人信息，与 `account` 墓碑同一性质。
- **实名核验的服务商、灾备与归一映射**见 `operations/external-providers.md`，不在本文件也不在合规运维面。

## 四张台账的存储形态

风控事件流 · 复核队列 · 昵称扫描台账落**四张表**——注销审计的两个 `kind` 因不在同一条时间轴上而单独成表（理由见上方 `kind` 取值一节）。四张表同处单库、同一 schema，但**形态各不相同：判据是「体量随什么增长」与「访问模式是不是点查」，不是「它们都叫台账」。**

承重列见 `systems/account.md`「存储形态：承重列」；本节只写分区 / 索引 / 裁剪 / 领取语义 / 探针——与 `receipt_idem`（承重列在 `systems/profile-store.md`、运维形态在 `operations/purchase-ops.md`）同一分工。

| 表 | 体量随什么长 | 主访问模式 | 分区 | 过期 |
|---|---|---|---|---|
| `risk_event` | **时间**（只追加） | 按账号 + `kind` 的窗口计数；按版本分组的聚合 | 按 `occurred_at_utc` **月 RANGE 分区** | **整分区 `DROP`**（180 天水位） |
| `deletion_audit` | 账号数（一生零到少数几行） | 按 `account_id` 点查（客诉举证） | 不分区 | 按批 `DELETE`（3 年水位）；**注销执行不删** |
| `nickname_review` | 待办积压（人工处置速度） | 按状态取待办；按 `account_id` 点查 | 不分区 | 终态行按批 `DELETE`（180 天） |
| `nickname_scan` | **账号数**（一行一账号） | 按 `account_id` 点查；按落后的词表版本取批 | 不分区 | **无到期过期**；随注销硬删 |

**四张表都在承载 `account` 域权威状态的那个库里，不新增存储系统**（`systems/_index.md`「明确不引入」）：注销审计要与 `account_deletion` 行同事务、四张表中的三张要与其余七表同处一次全有或全无的删除事务——跨存储写入会让「行已删、事件未落」成为可达状态，而那正是要留证的那一刻。Redis 不是候选：它只承担限流计数器、不持有权威状态，而复核判定结果会回灌词表、扫描台账决定 `nicknameChangeRequired` 是否为真，两者都是权威状态。

### `risk_event`：月分区，整分区 `DROP`

「到期整体过期」这句话本身就是分区裁剪的规格说明，`push_idem` 是同库同形的现成实现。**粒度取月不取日**：180 天 ⇒ 稳态 7 个活分区（6 个整月 + 当月）；日分区的 180+ 个分区只换来过期精度，代价是规划器与 DDL 维护负担。

**实际保留期因此是 [180, 210] 天，不是精确 180 天**——只有整月边界越过水位线才 `DROP`。这不违反任何约束：180 天的推导是「覆盖两倍于最长累计窗口 90 天」，是下界性质；合规侧「不宜永久」是上界性质。

**主键 `(occurred_at_utc, event_id)`** —— 分区表的唯一索引必须含分区键，同 `receipt_idem_archive` 的形态。`eventId` 作为「去重与工单关联的键」不受影响：`eventId` 由服务端生成（不接受客户端提供），去重发生在写入侧，工单关联恒带时间戳。**不追求跨分区的全局 `event_id` 唯一**：那要另立一张键表，而当前没有任何以裸 `eventId` 为唯一入参的读路径。

分区的预建与裁剪挂既有的定时任务通道（`operations/environments.md`「定时任务出口」），**不引入分区管理插件**：每轮预建**未来 2 个月**空分区、`DROP` 早于保留期上界的整分区。余量取 2 个月而不是 1 个——任务连续失败一整月时写入不应当场失败（缺分区的 `INSERT` 在 PostgreSQL 上直接报错）。

### `risk_event` 的索引：两条，各对一条既有判定路径

索引不按「可能会查什么」铺，按上方已写死的两条判定路径铺——它们是这张表**全部**的读路径。

| 索引（逐分区） | 服务的路径 |
|---|---|
| `(account_id, kind, occurred_at_utc)` | **累计阈值表**：按 `kind` 在窗口内计某账号的次数。列序是「等值 · 等值 · 范围」的标准前缀形态；它同时是注销按账号硬删的走索引前缀 |
| `(kind, occurred_at_utc)` | **全局熔断**：取窗口内某 `kind` 的切片，再按 `app_version` / `content_version` 分组去重计数 |

- **`(app_version, content_version)` 不进索引键**：熔断是周期性聚合而非点查，窗口内某 `kind` 的行数本身就少（正常账号的期望值是 0），而这两列的基数在任一时刻只有个位数——塞进索引键只让写放大跟着涨。
- **不建 rollup / 物化聚合表**：写入是**异常驱动**的，稳态量级远低于 `receipt_idem`。为一个尚不存在的聚合压力先建一条派生数据路径不划算；真成为负担时先按 `operations/purchase-ops.md` §3d 的四项排除法诊断，rollup 是最后手段。
- **`device_id` 不建索引**（只作观测维度，永不参与判定）；**`request_id` 不建索引**（两侧日志的接起来发生在日志系统侧，不是这张表的读路径）。

### 「只追加」到底禁的是什么

「永不单条删除」与「注销时按账号硬删」必须一起读，否则实现者会二选一：

> **业务路径上只追加**：条目永不改写、永不因业务原因单条删除。**恰有两条删除路径，都不是业务路径**：① 到期的**整分区 `DROP`**；② **注销执行时按 `account_id` 的硬删**（合规删除权，与其余各表同处一次全有或全无的事务）。除此之外没有任何删除 SQL。

② 是跨全部活分区的 `DELETE … WHERE account_id = ?`：7 个分区 × 单账号的稀疏行数，代价可忽略，每个分区都走 `(account_id, …)` 索引前缀。**这是 `account_id` 必须是首列的第二个理由**。

注销事务因此会与裁剪任务在同一批分区上并发（`DROP` 需 `ACCESS EXCLUSIVE`，会与同分区的 `DELETE` 互相等锁）。处置沿用既有形态：裁剪任务**跑在低峰**、失败即下一轮重试；**注销执行永不为裁剪让路**——它是本库唯一不可逆的周期动作，语义优先级最高。

### 写入路径：默认旁路批量，两类例外同事务

`push` 的应答不等待事件落盘，而消息队列是明确不引入项 ⇒ **进程内有界缓冲 + 后台批量 `INSERT`** 是唯一剩下的形态。三条纪律：

- **缓冲有界，溢出即丢弃并计数，绝不反压请求路径**——反压等于把旁路做回热路径。丢弃计数出一条指标（应恒为 0）。
- **概率信号容得下极少量丢失**：`RollMismatch` / `ChanceInconsistent` / `InvariantViolated` / `EchoRejected` / `RevisionAhead` / `RateLimitTripped` 都带累计阈值与窗口，丢一条只让一次判定晚到。
- **两类例外必须与状态变更同一次事务、不走缓冲**：
  - `DeletionRequested` / `DeletionCancelled` 写 `deletion_audit`，与 `account_deletion` 行的插入 / 删除同事务——丢一条 = 一次客诉在服务端零证据；
  - `NicknameBypassed` —— 它是确定性检出而非概率信号，**没有累计冗余的信号不能走可丢弃的通道**；且它与复核入队是同一次检出的两个落点，拆开会让「事件已落、未入队」成为可达状态，那正是一次绕过检出被静默吞掉的形态。

  同事务写一行 `INSERT` **不违反**「绝不在同步热路径上裁决」：被禁的是**裁决**（阈值判定、处置升级）在热路径上，不是记一行账。这层区分必须写明，否则实现者会把它读成「一律异步」而把同事务留证也异步掉。

### `deletion_audit`：不分区，保留 3 年，注销执行不删

极小的一张表（每账号一生零到少数几行），不分区、不上任何分区机制——同 `compliance_ticket` 与 `signin_replay` 的判据。只追加，**唯一的删除路径是到期按批 `DELETE`**（3 年水位，挂既有周期通道）。

**注销执行时不删，它是删除清单的唯一例外**：条目的 `context` 已明写「不含任何个人信息」，与 `account` 墓碑同一性质 ⇒ 长留不构成个人信息超期留存，也就不需要为它设计合规删除路径。反过来说，注销执行时删掉它等于在**最需要它举证的那一刻**销毁唯一的证据。

保留 3 年而非永久：与交易记录法定保存期同量级，覆盖客诉的实际到达窗口。**不把其余八个 `kind` 一并提到 3 年**——它们是可关联到个人的行为数据，「不宜永久」对它们仍然成立。

### `nickname_review`：不分区，状态机 + 租约

- **不分区。** 体量随**待办积压**增长而非随时间增长，稳态存量取决于人工处置速度（复核级命中 + T1 绕过检出，稀疏）。给一张几千行的表上分区只增加维护面。
- **领取语义不照抄合规域的周期任务。** 那几条 `FOR UPDATE SKIP LOCKED` **持锁到事务结束**，成立前提是「处置在毫秒到秒级内完成」。复核是**人工**动作、持有时长以分钟计：把数据库事务开着等人点按钮会长期占住连接、把最长事务时长指标（`observability.md`「数据面」）打成常态告警，并阻塞 autovacuum。
- **形态是条件 `UPDATE` 取租约**：`SKIP LOCKED` 仍用，但只用在**选行的那一条语句**里，事务在语句返回即提交。

  ```
  领取（一次短事务）：
    WITH picked AS (
      SELECT review_id FROM nickname_review
       WHERE state = 'Pending'
       ORDER BY enqueued_at_utc
       FOR UPDATE SKIP LOCKED
       LIMIT :batch)
    UPDATE nickname_review r
       SET state = 'Claimed', claimed_by = :reviewer,
           claim_expires_at_utc = now() + :leaseMinutes
      FROM picked WHERE r.review_id = picked.review_id
    RETURNING …
  判定：state = 'Claimed' AND claimed_by = :reviewer 的条件 UPDATE，按受影响行数分支
  租约回收：state = 'Claimed' AND claim_expires_at_utc <= now() ⇒ 置回 'Pending'，claim_attempts += 1，
           并一并置空 claimed_by 与 claim_expires_at_utc
  ```

  - 多副本 / 多复核员安全由 `SKIP LOCKED` + 受影响行数分支共同兑现，**仍是零分布式锁、零调度中间件**。
  - 判定写的是条件 `UPDATE`，因此租约过期后原复核员的迟到提交会命中 0 行而被拒——不会覆盖已被他人处置的条目。
  - **租约超时初值 30 分钟**：一次昵称复核是秒级判断，30 分钟覆盖一次中途被打断的班次；上界的代价只是条目滞留，下界的代价是复核员正在看的条目被他人抢走。
  - `claim_attempts` 反复升高 = 某条目每次被领走都无人判定（多为疑难条目），出一条指标即可，不自动升级。
  - **`:reviewer` 恒为 `operator_id`**，由服务端从本次内部请求已认证的凭据解析得出，**绝不接受请求体传入**——允许传入即任何持凭据者都能冒名判定。取值域、外键与内部身份形态见 `operations/internal-tools.md`。
  - **租约回收一并置空 `claimed_by`**：留着旧值会让「谁在办」这一列在 `Pending` 行上说谎，而它是审计要读的列。（迟到提交被拒不依赖这一点——`state` 已变即命中 0 行。）
- **入队去重落成数据库不变式**：`UNIQUE (account_id) WHERE state IN ('Pending','Claimed')` ——同一账号在办至多一条。同一玩家反复改名撞复核级会连开多条条目、让人工对同一账号重复判定；应用层「先查再插」挡不住并发，与 `export_task` 的部分唯一索引、`session` 的活跃会话上限 1 是同一手法。命中冲突 ⇒ **更新既有在办条目的提交串 / 词表版本 / `requestId` 为最新一次**，不新插行（判定要针对当前值）。
- **终态条目按批 `DELETE`**，挂既有周期通道，保留期 180 天（条目含玩家提交的昵称串，属可关联到个人的行为数据，不宜永久）。**注销执行时按 `account_id` 硬删。**

### `nickname_scan`：一行一账号，不分区、无到期过期

- **独立表，不给 `account` 加列。** 两条理由：① `account` 行是全库唯一的并发单元，扫描任务批量更新 `last_scanned_at_utc` 会与 `signin` / `push` / `bind` 争同一把行锁——把一条纯离线批处理塞进玩家热路径的锁竞争里；② 六个字段里有五个只有扫描链路读写，与 `account` 的读频次差若干数量级。
- **不分区、无到期过期。** 体量 = 账号数，每账号恒一行、原地更新，**不随时间增长**。生命周期跟账号：**注销执行时硬删**（含 `last_accepted_nickname`，属可关联到个人的数据）。
- **`account_id` 主键**，同时是 T1 的点查键：解 `playerDiff` 顶层键后一次主键点查 + 一次字符串比较。
- **两条索引对应 T2 / T3**：`(reviewed_wordlist_version)` 取落后于最新词表版本的批——词表版本基数极低，一次发布后选择率接近 100%，故它主要服务**发布后期**的收尾扫描，发布初期规划器自行选顺序扫描是正确的选择；`(last_scanned_at_utc)` 供 T3 的兜底全量取批并推进水位，天然分页、可错峰、可中断续跑。
- **`review_state` 存 `text`，不用数据库 enum**（同 `kind` 清单可增量的纪律）：加一个档位不应当是一次 DDL 迁移。
- **行的创建时点**：建号骨架不建行（新账号无昵称）；**首次经改名端点接受时插入**。T1 在无行时视为「从未经端点接受过昵称」⇒ 若 push 带来非空 `nickname` 即判绕过，这与 T1 的既有语义一致。

### 过期方向不是全库通则

`receipt_idem` 必须**显式关闭**任何 TTL 并在部署时断言（`operations/purchase-ops.md` §3c）。本节四张表却有三张必须过期——**两者方向相反不是矛盾，判据是代价的不对称性**。这条判据必须写明，否则那条 TTL 断言会被当作全库通则照抄。

| 表 | 过期方向 | 少留的代价 | 多留的代价 |
|---|---|---|---|
| `receipt_idem` | 永不过期（断言拒绝启动） | 一次**不可发现的重复发放** | ≈ 0 |
| `risk_event` · `nickname_review` | **必须过期** | 最多一条晚到的判定 / 一次审计线索（保留期已是最长累计窗口的两倍） | **个人信息超期留存**——合规风险，且体量随时间线性增长 |
| `deletion_audit` | **3 年后过期，注销不删** | 一条**不可举证**的删号客诉 | ≈ 0（不含个人信息，表几乎为空） |
| `nickname_scan` | 无到期过期（一行一账号，不随时间长） | — | ≈ 0；随注销硬删 |

**`risk_event` 的分区裁剪滞后量是「个人信息超期留存」唯一的机制发现面**——同 `operations/compliance-ops.md` 的「到期扫描滞后量」是同一手法、同一理由：裁剪任务默默失败三个月不会有任何人发现，除非有这条数。`nickname_review` 的对偶指标是待办积压量与最老 `Pending` 条目年龄（前者是人工处置容量是否够的信号，后者防「某条目永远排不到」）。探针口径见 `operations/observability.md`。

| # | 输入 | 期望 |
|---|---|---|
| M1 | 注销申请端点成功返回 | `account_deletion` 行与一条 `DeletionRequested` 条目**在同一事务内**落 `deletion_audit`；杀死进程于两者之间 ⇒ 两者都不存在 |
| M2 | 撤销端点成功返回 | `account_deletion` 行已删 · `status` 已恢复 `previous_status` · 一条 `DeletionCancelled` 条目已落 `deletion_audit`，三者同事务 |

| M4 | 分区裁剪任务跑过一轮 | 最老活分区的上界不早于 `now() − 风控事件保留期 − 31 天`；无任何单条 `DELETE` 语句执行 |
| M5 | 写入落在尚无分区的月份 | 分区维护任务已预建 ⇒ `INSERT` 成功；人为删除预建分区后 `INSERT` 失败并告警（**不静默丢**） |

| M8 | 同一账号连续两次撞复核级词表 | `nickname_review` 中该账号在办条目恒为 **1** 条，提交串 / 词表版本更新为最新一次 |

| M10 | push 检出 `NicknameBypassed` | 事件与复核队列条目**同事务**落库；不存在「事件已落、未入队」的可达状态 |
| M11 | 新词表版本发布后 | `reviewed_wordlist_version` 落后的账号被重扫；已是最新版本的账号不重扫（S3 的索引支撑） |
