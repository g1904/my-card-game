# ADR-0141 — overlay 打包工具须产出机读产包证明与按在架版本归档的基线快照

- **状态：** Accepted
- **日期：** 2026-09-05
- **来源：** handoffs/2026-09-05-backend-batch-client-obligations.md · handoffs/2026-09-06-baseline-superset-and-pack-proof.md

## 背景

overlay 的合并期校验已有两条闸 + `LoadAll()` 路径，但它跑在**打包侧**，发布侧无从核对「这个产包到底跑没跑过闸、跑的是哪个基线」——整条链因此只能停在评审级信任。更硬的一处：同一份 overlay 会被多个在架客户端版本消费、**各自基线不同**；只对最新基线跑过闸，老版本玩家启动即 `PushError`——恰是闸要防的事发生在闸的盲区里。而跑老基线需要老基线的内容快照，快照若归档在发布侧够不着的地方，闸对老基线**根本跑不了**。

## 决策

**overlay 打包工具须产出两样东西：① 机读产包证明；② 按在架版本归档的基线内容快照。校验规则本身不变、不外移。**

- **① 机读产包证明**，字段下限四项（工具版本 · 基线 `appVersion` · 断言项计数 · 逐文件 `path` + `sha256`）；字段形态归本库自定。证明须**与产包同批产出、同批上传，并内嵌在产包的唯一路径上**。
- **② 基线内容快照按在架版本归档**，存放位置与生命周期归本库自决，但**归档到发布侧可达处是硬约束**。
- **打包工具不自持在架版本清单**：跑哪几个基线由发布侧按其兼容矩阵决定，作为输入喂进来。
- **首个客户端版本即内置 active + standby 两把内容签名公钥**（报文零改动）。

字段集、归档形态与校验路径 → `systems/services/content-service.md`。

## 理由

- **「记得再跑一下」的步骤等于没跑。** 证明若可单独补产出，整条链退回评审级——同批产出 + 内嵌在唯一路径上，才使它成为产包的固有部分。
- **可达性是硬约束而非建议**：闸跑不了老基线，逐基线校验这条决策当场落空。
- **打包工具不该持有兼容矩阵**：兼容矩阵是发布侧的判定输入，须与判定逻辑同处。既有的「客户端不持有兼容矩阵的任何副本」指的是**运行时客户端**，这条须就地澄清，否则两句会打架。
- **校验规则不外移**：本项只把既有闸的**产出物**变成可被发布侧核对的东西，不动判定本身。
- **两把公钥的价值全在「首版就做」**：等到需要轮换时才加第二把就已经晚了，届时只能靠强更且事后无法补救。

## 备选方案

- **只对最新基线跑闸** — 否决：老版本玩家启动即 `PushError`，闸的盲区恰好覆盖它要防的事。「更高版本基线是更低版本的 `Id` 超集」由内容发版纪律保证并由快照归档步机械核对（`systems/services/content-service.md`「内容发版纪律」），但该简化仍不成立——存在性判据在 `Id` 最少的最旧在架基线上最严，且合并校验含值敏感断言、其结果依赖各基线自身字段值；逐基线各跑一遍是长期形态。
- **证明作为一个独立的补充步骤产出** — 否决：可被跳过的步骤会被跳过，整条链退回评审级信任。
- **产包证明加「按类型的条目计数」一格** — 本次不纳入：它服务于对侧一条**尚未采纳**的优化路径，且须与对侧同批落地。
- **打包工具内置在架版本清单** — 否决：制造兼容矩阵的第二副本，与判定逻辑分离即漂移。

## 后果

- 发布侧自此可机械核对产包与断言留痕，overlay 分发链脱离评审级信任。
- 快照的存放位置与生命周期成为本库须自行明写的一项；可达性缺失即视为闸失效。
- 「高版本基线是低版本 `Id` 超集」由内容发版纪律（随包基线只增不删）保证，并由基线快照归档步机械核对；**但它不把逐基线各跑简化为只跑最新**——存在性判据在最旧在架基线上最严（overlay 触到新版本才有的 `Id`，对老基线即非法新增），且值敏感断言依赖各基线自身取值，任何单基线运行都覆盖不了其余。逐基线各跑一遍是长期形态。
- 因此必须这么写的文档：`systems/services/content-service.md`（两项产出 · 四项字段下限 · 可达性硬约束 · 不自持在架版本清单 ·「不持有兼容矩阵副本 = 运行时客户端」的就地澄清 · 首版内置两把公钥）。
