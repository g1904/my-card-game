# ADR-0080 — refresh token 落 `user://cache/refresh-token.json` 归 `AuthManager` 私有；续期软信号不做任何本地时钟判断

- **状态：** Accepted
- **日期：** 2026-08-22
- **来源：** handoffs/2026-08-22-refresh-token-client-storage.md, handoffs/2026-08-23-refresh-lifetime-cap-client-half.md

## 背景

启动期静默续期要求 refresh token 跨进程持久化。而「什么时候该让玩家重新登录」这个问题，客户端本可以自己算——按距上次 `signin` 的天数，或按后端下发的到期时刻。两者都依赖**设备时钟**，而设备时钟不可信。

## 决策

**refresh token 落 `user://cache/refresh-token.json`**（明文、带 `schemaVersion`、原子写、**不上云**），归 **`AuthManager` 私有、不出任何服务的 API 面**。**任何日志只写 path 与判定结果，绝不写凭据值。**

**本文件刻意不沿用 `deviceId` 的「必须先落盘成功、内存里才认」（承重）**——判据是「**失败症状是否自愈**」，不是「是不是凭据」。

续期软信号 `reauthRecommended` 的客户端形态三条：**只在内存持有绝不落盘** · **不做任何时间判断**（收到即真，不推算不比对本地时钟） · 反应 = 启动期静默续期成功后呈现一次**可跳过**的登录屏（失败即忽略）。API 面零改动、不新增阻塞点、不使任何 token 失效。

→ `systems/services/account-service.md`；文案键 → `ux/error-and-blocking-ux.md`。

## 理由

把「是否该重新登录」整个判断交给后端，客户端只做一个布尔的搬运工——这样设备时钟错乱不会造成任何后果。反过来，任何本地推算都会在时钟错乱时把玩家锁在外面或永远不提醒。

两份本地文件的落盘顺序相反，是因为失败症状不同：`deviceId` 落盘失败后若内存里认了，下次启动会生成一个新的 ⇒ **白挤掉一次会话，不自愈**；refresh token 落盘失败后内存里认了，最坏是下次启动要重登 ⇒ **自愈**。**这条须与规则同处，否则读者会误以为两处不一致是漏改。**

## 备选方案

- **与四份既有本地文件合并** — 否决；其中「不与 `device-id.json` 合并」是既定硬约束，两者失效口径恰好相反。
- **存 `refreshExpiresAtUtc` 过期时刻** — 否决：设备时钟不可信，读取即丢弃。
- **存 access token / 渠道便利字段** — 否决：access token 短命且可重取；渠道字段属账号信息。
- **客户端按距上次 `signin` 的天数强制回登录屏** — 否决：撞「设备时钟不可信」。
- **仅在无进行中轮回的主菜单触发续期提示** — 否决：需一个「有没有进行中轮回」的判断点与一处新触发接线，而软信号提前量足以覆盖至少一次冷启动。
- **提示文案附一句「为保障账号安全…」原因句** — 否决：把后端可调旋钮写进翻译条目，改值时静默失准。

## 后果

- 明文落盘 + 平台密钥库后置评估——代价正面写下。「后置」的兑现物（四端能力矩阵 · 升级触发条件穷举五条 + 四条非触发 · 不引入平台分支）见 `systems/services/account-service.md`「refresh token 的持有与失效」。
- 启动期静默续期使 `Account.Init` 上提到登录屏之前。
- refresh 失败拆两条路径：网络失败 → 缓冲通道；`auth.session_revoked` → 硬阻塞重登 + 暂停退避。
