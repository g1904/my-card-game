# ADR-0133 — 两种货币跨篇章结转，与寿元同形

- **状态：** Accepted
- **日期：** 2026-09-05
- **来源：** handoffs/2026-09-05-currency-acquisition-and-pricing.md

## 背景

灵石与仙玉此前在多处被写作「每章重置」。给这两条曲线做产出量与定价标定时才发现：这条措辞在全库**零机制承载**——篇章边界原先没有货币清零职责、存档点清单里没有这个落点、`CharacterProfile` 上也没有篇章维的货币字段。措辞与机制必须对齐，二选一：要么给 `ChapterManager` 真加一项清零职责，要么改措辞为结转。

同时，定价表「不设篇章维」这条既有取向此前只有「省事」这一类理由，缺一条承重论证。

## 决策

**两种货币（`SpiritStone` / `ImmortalJade`）与寿元同形：只随轮回清理，跨篇章结转，篇章边界不做任何清零动作。**

- 货币结转**不构成 `ChapterManager` 的一项职责**，也不需要对应的存档点——结转在这里是「什么都不做」的结果。
- 标定分母随之有两个，并用：`I(c)` / `J(c)` 校准「本章掉多少」，`I_cum(c)` / `J_cum(c)` 校准「玩家此刻买得起什么」。**四者与「占本章可用预算的百分比」同性质：作者标定用的书写口径术语，不是运行期字段，也不是新枚举。**
- 定价表**不设篇章维**由此获得承重理由：跨章结转要求价格跨章稳定，否则攒下的余额被通胀稀释。篇章间的经济差异改由「掉落多少货币」承载。

口径与逐格取值 → `systems/balance.md`「货币产出与定价」、`systems/character-profile/currency.md`、`systems/services/life-cycle-service.md`。

## 理由

- **改措辞的代价为零，加机制的代价不为零。** 「每章重置」在全库没有任何一处机制承载它，改为结转即让措辞与机制对齐，`ChapterManager` 一行代码都不用加；反向选择要新增一项篇章边界职责、一个存档点落点与一份篇章维状态。
- **它使「省着花有跨篇章回报」对货币逐字成立**，与寿元结转同一条激励结构（`life-cycle-service.md`：寿元结转「是一条贯穿整个轮回的资源线，而非每章重置的计时器」）。
- **它给「定价表不设篇章维」换了一条更强的理由**：跨章结转 ⇒ 价格必须跨章稳定。原先这条只是书写便利。
- **推论一并成立且不需新机制：**「顶档仙玉商品 = 一次轮回至多一件」由产出量与定价的算术保证（`J_cum(ch3) ≈ 10` 对 Tier5 的 8 枚）。

## 备选方案

- **每章重置（草稿推荐项 A）** — 否决：需要为一条无人承载的措辞新增篇章边界职责、存档点与篇章维字段；且它与寿元的结转形态不一致，玩家要同时持有两套心智。用户在 2026-09-05 的评审中裁决取结转。
- **只让灵石结转、仙玉每章重置** — 未权衡（两币在存档与篇章边界上走同一条路径，分叉只增不减复杂度）。

## 后果

- `ChapterManager` 的篇章边界职责表**不含任何货币项**，存档点清单也不新增落点 → `systems/services/life-cycle-service.md`。
- 定价表**永久不设篇章维**；篇章缩放只能落在「给多少」（`S(c)`）→ `systems/balance.md`、`systems/adventure-event/exchange/_index.md`。
- 购买力校验一律按 `I_cum` / `J_cum` 而非 `I` / `J` 写；「刻意屯攒则 ch3 可一次拿下 Tier5」是**预期行为不是漏洞**。
- 放弃了「每章清零以强制花完」这一节奏控制手段——节奏改由产出量与定价的算术承载。
