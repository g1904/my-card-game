# ADR-0057 — 共有属性的定义写在其全部挂载面的最小公共祖先，恰好一份；每个落点只写一段投影

- **状态：** Accepted
- **日期：** 2026-08-14
- **来源：** handoffs/2026-08-14-common-properties-layering.md

## 背景

`systems/` 是一棵树，同一个共有字段（`Id`、`Rarity`、`ContentEnabled`、`ExclusiveSource`…）会挂在多个子树的多个类上。若每个落点各写一遍定义，同一字段在库里就有多份说法；若只写顶层、子树完全不提，读一份子树文档的人不知道这个字段存在。

## 决策

**定义（权威）恰好写在其全部挂载面的最小公共祖先一层，恰好一份。**

每个实际落点只写一段 **≤5 行的投影**：落点 · 本层合法子集 / 默认值 · 本层消费点 · 回链。**投影不得复述定义。**

**同一字段的定义级内容在两份 `common-properties.md` 中同时出现即为违规。**

判据卡与逐字段归属 → `systems/common-properties.md`。

## 理由

最小公共祖先是唯一一个**可机械算出**的落点：给定挂载面集合，答案唯一，不需要每次讨论。而「投影不得复述定义」这条限制是防漂移的承重——一旦允许复述，两份说法就会各自演化，而本库没有任何机制能发现它们不一致（与 `ADR-0005` 的副本判据同源）。

投影仍然必须存在：读者从子树文档进入时需要知道「这里有这个字段、本层允许哪些值」，只是不需要知道它的完整语义。

## 备选方案

- **列一张完整的字段归属表作为答案** — 否决：表本身是第二权威，且新增字段时要同时改表与文档。
- **一切共有字段只写顶层、子树不留投影** — 否决：子树读者不知道字段存在。
- **按「是否落存档 / 是否内容定义」分层** — 否决：与挂载面正交，切出来的组跨越多棵子树。
- **为对称补齐中间层 `common-properties.md`** — 否决：中间层若无独有字段，补出来的就是空壳。
- **顶层拆成两个文件** — 否决：拆分轴不明确。

## 后果

- 例：`ExclusiveSource` 只覆盖 `PowerData` / `ItemData` 两个类，但这两个类的落点横跨 `character-profile/` 与 `player-profile/` 两棵子树 ⇒ 最小公共祖先是**顶层**。
- 这条判据同样约束 `content/` 层：条目文档只写「填了什么值 + 回链」（→ `ADR-0058`）。
- 新增共有字段时，第一步是算最小公共祖先，不是选一个方便的文件。
