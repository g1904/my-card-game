# ADR-0058 — `content/` 与 `systems/` 平级（类 ↔ 实例）；条目文档直喂 `/blueprint`，本层不定义字段

- **状态：** Accepted
- **日期：** 2026-08-14
- **来源：** handoffs/2026-08-14c-content-authoring-layer.md

## 背景

`systems/` 描述「这类内容怎么运作」，但具体有哪些卡牌、哪些敌人、哪些事件，此前无处安放。三个候选落点：塞进 `systems/` 对应子树、每类内容一个技能、或另开一层。

## 决策

**内容条目实例层 `content/` 与 `systems/` 平级开张**——二者是**类 ↔ 实例**关系，故平级而非嵌套：`content/` 持有「有哪些条目」，`systems/` 持有「这类内容怎么运作」。

**条目文档直接喂 `/blueprint`，不经 `requirements/FR-*`。**

**硬边界：本层不定义字段。** 每个字段只写「填了什么值 + 权威回链」——**一律不复述字段的类型定义、取值域、枚举成员表、数值 code 或完整校验语义**。违反即制造第二权威。

登记表、id 约定与依赖链 → `content/_index.md`。

## 理由

类与实例是平级关系，不是包含关系——把实例塞进类的子树会让 `systems/card/` 里同时有「卡牌怎么运作」和三百张卡，两种阅读目的混在一起。

跳过 `requirements/` 的理由是**条目本身就是规格**：一张卡的验收标准就是它的字段值，再写一遍 FR 只是把同一张表抄进另一个模板。

不定义字段这条硬边界与 `ADR-0057` 同源：本库没有机制能发现两份字段表不一致。

## 备选方案

- **每类内容一个技能** — 否决：会把十几份字段清单复制进 `.claude/skills/`，直接违反 `ADR-0005`。
- **写进 `systems/` 对应子树** — 否决：类与实例混在同一棵树。
- **每类一个大文件** — 否决：一个类型几百个条目时无法维护，且并发编辑必冲突。

## 后果

- **代价明写：内容不进 `requirements/_index.md` 台账**，完成度追踪落在 `content/_index.md` 自己身上。
- 内容流水线因此是 `/scaffold-content-type` → `/author-content` → 签核 → `/blueprint` → `/implement`，`/audit-content` 对账。
- 类型档案 `content/<类型>/_index.md` 持字段核对清单，但清单只列「要填哪些格」，不列每格的语义。
