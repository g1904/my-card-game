# ADR-0052 — CDN 域的 4xx 按「入口对象 / 入口之后的对象」两分

- **状态：** Accepted
- **日期：** 2026-09-07
- **来源：** handoffs/2026-09-07-manifest-schema-path-branch-and-cdn-failure-codes.md

## 背景

CDN 域三端点不返回契约错误体，客户端只能按 HTTP 状态码判定。此前契约层只有「按状态码判定」这一条纪律，具体状态码与客户端处置未钉死，导致同一个 404 既可能被读成「配置没配好」也可能被读成「已发布的内容被动过」。

## 决策

CDN 域失败面按对象在下载链中的位置两分：

- **入口对象（`manifest`）的 4xx = 环境 / 配置面** —— 跳过更新用基线 + 本地 `PushWarning`，**不上报**；
- **入口之后的对象（`.sig` / `blobs/<sha256>`）的 4xx = 发布原子性被违反** —— `Validation` + 上报一次，且**不进退避重试**；
- **408 / 429 / 5xx / 连接失败 / 超时 = 传输面** —— `Network`，照既有降级与既有重试；
- **「版本已被回滚 / 撤下」这一失败面结构性不存在** —— 回滚 = 前滚，manifest 被更大的 `contentVersion` 覆盖而非删除，历史 blob 永不删除。

逐端点逐行的状态码、可否负缓存与客户端处置见 `contracts/content-manifest.md`「失败面」表。

## 理由

- manifest 404 的最可能成因是 `contentRoot` 配置错或环境尚未首发内容，客户端无从区分，且它**不代表已发布的内容被动过**；映成 `Validation` 会在开发 / 测试环境刷出持续告警。
- `.sig` 或 blob 的 404 只可能发生在 **manifest 已被读到之后**，那一刻服务端保证 A 组第 3 条已承诺「它列出的文件必须已可下载」⇒ 收到 404 即证明发布纪律被破坏（或负缓存命中），这正是值得上报的一类。
- 对一个明确的 404 跑三次退避重传是纯浪费——重试语义是为传输抖动准备的。
- 「回滚 / 撤下」那一格逐字写下，是为了让「回滚了要不要给客户端一个信号」此后不再被问。

## 备选方案

- **全域 4xx 统一映成 `Validation` 并上报** — 会把「环境没配好」刷成持续告警，且开发 / 测试环境上噪声最大。
- **为未知 `manifestSchema` 分支另定 `400`** — 在一个不返回契约错误体的域里，客户端只拿到裸状态码、读不到理由；路径分支已把它天然合并为 404（`ADR-0051`）。

## 后果

- **不新增任何 `envelope.md` §6 台账条目**：台账每条都要给出 `code` · `class` · `detail` 形状 · `message` 必含值，而 CDN 域结构上产不出这四样；新增条目会造出永不下发的 `code`，并让 P-1 的双向机检断言在「台账有、正文无」这一侧永久失衡。
- **负缓存要求逐字扩到三端点**（原只覆盖 `/blobs/*`）：某边缘在首发或新分支上线之前被探测过一次并缓存了 404，则 TTL 内命中该边缘的客户端稳定拿不到一个已经发布的 manifest。见 `operations/content-delivery-ops.md`。
- 客户端承接义务一项（对 CDN 域 4xx 按两分处置，其中「不对 4xx 走 3 次退避重传」是对既有下载重试语义的一次收窄），落 `game-design-documents/systems/services/content-service.md`。
