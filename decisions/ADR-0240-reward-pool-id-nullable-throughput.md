# ADR-0240 — `EncounterSpec.RewardPoolId` 明确可空；奖励吞吐量的节流落在「哪些战斗挂池」

- **状态：** Accepted
- **日期：** 2026-09-09
- **来源：** handoffs/2026-09-09d-combat-rarity-and-reward-scale.md · answer-logs/log-combat-rarity-and-reward-scale.md

## 背景

战后奖励改为逐项领取 / 跳过后（→ `ADR-0082`），到手数由 0–3 变成玩家说了算——**吞吐量因此整体抬高**。如果每场战斗都开奖励面板，一个轮回拿到的东西会远超卡组规模预算所能容纳的量。

节流可以落在机制侧（改抽数、改领取规则），也可以落在内容编排侧。

## 决策

**`EncounterSpec.RewardPoolId` 明确为可空。** 空 ⇒ **本场不开可选奖励面板**：`activeCombat.reward` 恒为 `null`，决策点 `D6` 本场不出现（`D0`–`D5` / `D7` 不变），呈现层不渲染空面板。

**「固定 3 项候选」的射程是挂了池的战斗。**

**编排初值：≈30% 的 Combat 条目挂池**（`Finale` 恒挂 · `Standard` 约三成 · `Practice` 偏低）⇒ ≈10 次面板 / **≈30 候选槽** / 轮回。

→ `systems/services/combat-service.md`（语义）· `systems/balance.md`（编排口径）· `systems/adventure-event/combat/_index.md`。

## 理由

节流落在**内容编排面**而非机制面，因为机制侧的每一条改法都要动既有定案：改抽数与「优势档只影响稀有度权重、不影响候选数量（恒 3）」冲突，且牵动战后奖励屏的三项逐项领取布局。

**`ADR-0082` 一字不改**——它的「合法池不足时显式降级为实际项数」本就能表达 0 项，可空只是把这条能力用在编排上。

## 备选方案

- **`Practice` 抽 2 / `Finale` 抽 4** — 否决：与「候选数量恒 3」直接冲突。
- **改领取规则（限领 N 项）** — 否决：把逐项领取的取舍语义又收回去一半。

## 后果

- **代价明写并接受：约七成的普通战斗打完只有 `BaseReward`。**
- 「挂不挂池」是**频率轴**，「挂哪个池」是**厚薄轴**（→ `ADR-0241`），两者都落在 `RewardPoolId` 这一格里、互不覆盖。
- 免费奖励通道的次数正比于挂池的战斗场数——这是回寿法宝 L-0 排除（→ `ADR-0066` 后果）赖以成立的量级依据。
