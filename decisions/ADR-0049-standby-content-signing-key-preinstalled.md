# ADR-0049 — 首版即内置 active / standby 两把内容签名公钥

- **状态：** Accepted
- **日期：** 2026-09-03
- **来源：** handoffs/2026-09-03-content-delivery-ops.md · answer-logs/log-content-delivery-ops.md

## 背景

内容 manifest 走 ES256 detached 签名，客户端内置 `keyId → publicKey` 的**一组**映射（契约写的就是复数）。公钥的内置面随发版分发——**只有首版能免费做满，错过就永久失去**。而紧急轮换（私钥疑似泄漏）的代价完全取决于此。

## 决策

**首版即内置 active + standby 两把内容签名公钥**。standby 私钥 = **同一密钥服务内的独立密钥**：独立密钥 ID、独立权限策略、独立审计线，且 **standby 的签名权限平时不授予任何身份**。

紧急轮换因此**立即切到 standby**，跳过等覆盖率。见 `operations/content-delivery-ops.md`（签名私钥判据与 `keyId` 轮换）；报文侧零改动（`contracts/content-manifest.md` 本就写「一组映射」）。

## 理由

只内置 active 时，紧急轮换要走「先发新公钥版本 → 等覆盖率 → 切私钥」，从发现泄漏到能切钥有**数周窗口**，期间唯一的止血手段是为一次密钥事故**强更全体玩家**；且切了 active 后，未内置该公钥的客户端连 flags 也验签失败，**秒关通道对这部分玩家失效**。预置 standby 后，紧急轮换退化为服务端切一个字符串，分钟级完成、零客户端动作。

成本仅一把密钥对与几十字节。

standby 私钥不挪到离线或另一保管方：威胁模型逐字只到「防误 / 防随手改」，跨保管方隔离防的那一档不在模型内，而离线保管几乎必然引入「人可直接签」的旁路。

## 备选方案

- 只内置 active，紧急时走「发新公钥 → 等覆盖率 → 切钥」 — 数周窗口，且期间秒关通道对未更新玩家失效。
- standby 私钥放离线 / 另一保管方 — 引入「人可直接签」的旁路，与密钥服务的护栏相抵。
- 日后再补 standby — 它的全部价值在「首版就做」，公钥内置面随发版分发。

## 后果

- 客户端首版必须内置两把公钥——这是一条**跨库、一次性、错过即永久失去**的承接义务，已在客户端库对称登记。
- 密钥服务的能力判据因此含「能并存多把密钥（active + standby）」。
- 契约报文零改动：它只是把契约早已写下的「一组映射」用满。
