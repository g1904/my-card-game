# ADR-0025 — 未知取值宽容的判据边界：有判定权的字段不适用

- **状态：** Accepted
- **日期：** 2026-09-03
- **来源：** `handoffs/2026-09-03-schema-bump-ledger-authority.md` · `answer-logs/log-schema-bump-ledger-authority.md`

## 背景

`ADR-0017` 立了一条宽容纪律：零判定权字段的取值清单不是校验闸，未知取值记录原值、不改写、不拒收。但它写得口吻相当普适，而 `reason` 与 `schemaVersion` 在上行负载信封里恰是**相邻的两个字段、同一张表的两行**——读者按就近类推把宽容推广过去是很可能的，而那会把版本闸门本身拆掉。

## 决策

**宽容与否的判据是「该字段对后端有无判定权」。`schemaVersion` 是版本闸门本身的输入 ⇒ 未知 `schemaVersion` 照常拒绝，判定不放松。**

- `contracts/profile-sync.md` §4 补一条**显式的不对称声明**；`reason` 那条的措辞**一字未改**。
- 配一条阈值 0 的探针（未知 `schemaVersion` → `sync.payload_schema_unsupported`），**按与已登记集合的大小关系二分**：值 > 已登记最大值 ⇒ 工程告警叫人（登记漏了，改旋钮即修复）；值 < 已登记最小值 ⇒ 信息级、只上看板（旧客户端，是既定下线纪律的预期产物）。
- 探针形态 → `operations/observability.md`。

## 理由

两者在报文里相邻，但**判据不同**：`reason` 对后端**零判定权**（只作日志与聚合维度），宽容的后果只是聚合维度里多一个孤儿取值；`schemaVersion` **是闸门的输入**，宽容接受等于把一份后端不保证能正确解读的负载写进云端，而**下一次 pull 还会把它发给可能更旧的另一台设备**，且透明路径的位置不再有保证（`contracts/profile-sync.md` §4）。

把限定语抬成一条显式判据，是本库已经行使过一次的手法——`envelope.md` §4a 把「例外仅限 auth 域」改写为一条判据，即 `ADR-0016`。**判据把「够不够格」变成一次必须通过的检验，而就近类推不会。**

告警分级的依据：一律工程级会让正常下线后的存量旧客户端持续制造以周计的预期告警，**那是把整张探针表训练成「可以忽略」的最快途径**；本库已有「带前提才告警」的同款先例（透明路径缺失那行）。**拒绝语义不变**，分级只作用于告警口径。

## 备选方案

- **未知 `schemaVersion` 宽容接受、原样存起来（照 `reason` 那条办）** — 让一份不保证可解读的负载进云端，并把它 pull 给别的设备。
- **在 pull 侧也判一次 `schemaVersion`** — 已被「pull 侧不做版本闸门」明确否决（两个闸门、两套阈值）。
- **把兼容判定前移到 `signin`（与强更闸门合并）** — 需在登录请求额外声明 `schemaVersion`，且覆盖不到会话中途升级负载结构。
- **后端解不透明段做 diff 自行探测 schema 变化** — 违反 pillar #1 与三段可见性分界，且后端拿不到「应有形状」这个参照物。
- **不设告警，靠客服工单发现** — 客户端对该错误的处置是非模态提示 + 暂停重试，玩家可能整个会话都不明确感知；工单量与故障量不成比例。
- **未知 `schemaVersion` 一律工程级告警（不分级）** — 存量旧客户端会持续制造以周计的预期告警。

## 后果

- `contracts/profile-sync.md` 自此有一条显式的「宽容不可外推」判据：**任何未来的「未知取值宽容」提案必须先过「有无判定权」这一关**。
- 本条与 `ADR-0017` 是**同一判据的正反面**，互为边界——`ADR-0017` 定「零判定权 ⇒ 宽容」，本条定「有判定权 ⇒ 不适用」；两条一起才是完整判据。
- 客户端与后端的发版顺序自由度因此**不对称**：`reason` 有（新取值可先发），`schemaVersion` 没有（须先动矩阵，见 `ADR-0024`）。
- `operations/observability.md` 的契约语义探针 +1 行；它是 `ADR-0024` 漏登的**唯一机制发现面**。
- **报文零改动**，不 bump `openapi.yaml` 的 `info.version`。
