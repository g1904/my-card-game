# ADR-0057 — 注销审计单独成表，保留 3 年，注销执行时不删

- **状态：** Accepted
- **日期：** 2026-09-08
- **来源：** handoffs/2026-09-08-risk-ledger-storage-shapes.md · answer-logs/log-risk-ledger-storage-shapes.md

## 背景

`DeletionRequested` / `DeletionCancelled` 两个 `kind` 原与其余八个同处风控事件流，因而沿用 180 天保留期与「注销执行时按 `account_id` 硬删」。但注销申请与撤销是**账号是否被删除**这条路径的唯一库内留痕（撤销即删 `account_deletion` 行），而删号客诉往往在半年、一年后才到（玩家想回来玩时才发现）。

## 决策

两值**不写 `risk_event`，另落 `deletion_audit` 表**：不分区、按 `account_id` 点查、按批 `DELETE` 的保留期取 **3 年（1095 天）**，且**注销执行时不删**——它是「执行时删什么」清单的唯一例外。写入仍与 `account_deletion` 行的插入 / 删除**同事务**。

其余八个 `kind` 的 180 天保留期与整分区 `DROP` 裁剪**一字不改**。

## 理由

- **过期代价的不对称性**（与 `receipt_idem` 永不设 TTL 同一条判据的第二次应用）：多留的代价是一张几乎为空的表（每账号一生零到少数几行），少留的代价是一条**不可举证**的删号客诉。
- 保留期取 3 年，与交易记录法定保存期同量级。
- **长留不构成个人信息超期留存**：`context` 已明写「不含任何个人信息」——与 `account` 墓碑同一性质（`ADR-0035`），因此不需要任何删除路径。
- **不给整张 `risk_event` 统一提到 3 年**：其余八个 `kind` 是可关联到个人的行为数据，「不宜永久」的判断对它们仍然成立。
- 分表而非在同一张表上按 `kind` 分保留期：两者不在同一条时间轴上（一个随时间增长、一个随账号数增长），且删除语义相反（一个随注销硬删、一个注销时保留）——同表会让分区裁剪与注销删除各自都要开一个例外分支。

## 备选方案

- **沿用 180 天、两值留在 `risk_event`** — 客诉窗口远长于 180 天，且注销执行会连同证据一起删掉。
- **整张 `risk_event` 提到 3 年** — 其余八个 `kind` 含可关联到个人的行为数据，不宜长留。

## 后果

- `operations/compliance-ops.md`「执行时删什么」表写明 `deletion_audit` **不在**删除清单内及其理由；`systems/account.md` 的注销执行事务行同改。
- 服务端保证 M1 / M2（申请与撤销各自与状态变更同事务）与 M3（注销执行后该账号在 `risk_event` · `nickname_review` · `nickname_scan` 中零行，而 `deletion_audit` 条目仍在）成为可断言的验收行。
- 该表的写入是 `ADR-0059` 中「不走旁路缓冲、必须同事务」的两类例外之一——丢一条 = 一次客诉在服务端零证据。
- 客户端零影响。
