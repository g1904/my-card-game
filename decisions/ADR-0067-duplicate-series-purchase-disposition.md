# ADR-0067 — 重复购买一个已拥有的角色系列：接受写入 + 风控事件，绝不拒绝、不自动退款

- **状态：** Accepted
- **日期：** 2026-09-11
- **来源：** handoffs/2026-09-12-premium-character-series-unlock.md

## 背景

`kind == CharacterSeries` 的 SKU 一律配置为非消耗型商品，Google Play 与 App Store 在平台层即拒绝重复购买 —— 这是主防线。但**微信支付没有「非消耗型商品」这一概念**，且多设备并发能绕过客户端「已拥有即置灰」的前置。于是存在一条真实路径：验票通过、该 `seriesId` 已在账号的 `characterSeries` 内、且本次 `receiptId` 是新的（不是幂等命中）。后端必须为这一刻定下处置 —— 而这一刻的特殊之处在于**钱已经扣了**。

## 决策

**接受写入，绝不拒绝。** 集合追加保证唯一 ⇒ 实际无变化；`cloudRevision` 仍 `+1`；回 `deduplicated = false`；**打一条风控事件**（账号 · `seriesId` · 两个 `receiptId` · `requestId`）；退款处置**走人工工单**。

**不自动发起渠道退款。** 退款整体留在人工侧，退款态只记在幂等记录的运维侧字段上，不进 `GET receipt` 的 `status` 枚举。

**玩家面为空 ⇒ 不新增 `code`。** 处置形态与 `profile-sync.md` §7a **逐字同构**（接受写入 + 打风控事件、不拒绝、不改写），不新开处置语义。

→ `contracts/purchase.md` §3c · `operations/purchase-ops.md` §5

## 理由

- **付款之后是整条链上最糟的失败时机。** 客户端侧反复引用的「把失败点挪到掏钱之前」在这里已经挪不动，只能不失败 —— 回一个 `Fatal` 只会让玩家在扣款后撞失败面。
- **不新开处置语义**：`profile-sync.md` §7a 对「复算不一致」已定下「接受 + 记账 + 风控、不拒绝」的形态，本情形逐字同构，沿用即可。
- **自动退款是纯加法，现在不做不欠账**：它要求后端持有三家渠道的**退款 API 写权限凭据**（当前凭据面只覆盖查询 / 核销，`purchase-ops.md` §1），是一次显著的攻击面扩大，还要引入一条异步补偿状态机；而本情形触发率在可预见期内近乎为零（主防线是平台侧非消耗型商品，微信渠道首版不开通）。**若实测触发率超预期，改为自动退款不需要回头改任何契约条款。**
- **玩家面为空者不应独立成码**（`envelope.md` §6 台账下方三条判据）。

## 备选方案

- **回一个新的 `Fatal` code 拒绝本次验票** — 钱已扣，付款后撞失败面是最糟的失败时机；且玩家面为空者不应独立成码。
- **自动发起渠道退款** — 需三渠道退款写权限 + 一条异步补偿状态机，成本远高于它要解决的问题频次。
- **折价抵扣 / 转为账号级货币** — 前提（账号级可支配货币）已被客户端侧明确关死。
- **静默丢弃本次写入、不记任何痕迹** — 会让这条路径在线上永远不可见，而它恰恰是微信渠道与多设备并发的症状面。

## 后果

- `contracts/purchase.md` §3c 必须写成「接受写入 + `revision` 仍 `+1` + `deduplicated = false` + 风控事件」的完整四项，且如实记下代价：**玩家要主动找客服，而客服可达面只有 `#requestId` 一条**。
- `operations/purchase-ops.md` §5 承担工单处置形态与触发率预期。
- `contracts/envelope.md` §6 台账**零加行**。
- 放弃了「自动止损」——本决策把一笔重复扣款的收口交给人工工单；这是一条明知的、以低触发率换攻击面收敛的取舍。
