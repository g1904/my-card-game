# ADR-0140 — `OpError` 增一档 `Purchase`，只由 `purchase.*` 域映入；不建逐 `code` 表

- **状态：** Accepted
- **日期：** 2026-09-05
- **来源：** handoffs/2026-09-05-backend-batch-client-obligations.md

## 背景

后端把购买失败分列为一条独立的处置轴，而客户端既有的错误档里没有一档表达「这笔购买没成」——`Validation` 说的是报文不合法，`Network` 说的是够不着服务端，两者都不承载「钱的事没办成」这层含义。付费面是玩家最不能容忍含糊的地方，映到一个语义不对的档上，处置与文案都会跟着错。

同时有一个诱人但错误的做法：在客户端补一张 `code → (OpError, 处置)` 的逐条表。**本库从来没有逐 `code` 表**，只有按 `class` 的默认表；开一张只有购买几行的半张表，即在对侧台账之外制造第二权威，两份各自漂移而本库无机制发现。

## 决策

**在 `OpError` 枚举上增一个成员 `Purchase`，且只由 `purchase.*` 域的 `code` 映入；不新建逐 `code` 表，购买失败的呈现与处置全部落 `systems/monetization.md` 的购买流程段。**

- `systems/architecture.md` 只改一行枚举 + 一句「`Purchase` 只由 `purchase.*` 域映入，别的域一条也不映」；
- **购买域并非每一条都映 `Purchase`**：报文格式错误那一类仍是上行校验失败，照常映 `Validation`；逐 `code` 的归档权威在 `backend-design-documents/contracts/envelope.md`，本库不复述清单；
- 四种情形的呈现与待兑现态联动、长等待的软提示分岔、客服可达面复用既有 `#requestId` → `systems/monetization.md`；
- 长等待**不新增阻塞屏变体、不设硬超时**；等待期间收到的可重试 `code` 只改写文案，不改变它是否进变体表。

## 理由

- **不新增枚举成员即与对侧的处置轴台账对不上**——对侧把「购买没成」明确列为独立一格，客户端没有对应档就无法逐格兑现。
- **处置落发起它的那份主题文档**，与合规三条的落法同构：谁发起这条流程，谁的主题文档持有它的处置。
- **不建逐 `code` 表**是防第二权威：本库的既定形态是按 `class` 的默认表 + 需要时回链对侧台账。
- **客服可达面复用 `#requestId`**（一句 `STORE_` 文案 + 长按复制的编号 + 一行提示），不新增独立客服入口、不引入客服地址配置面；**玩家尚未付款的那一类不出这条通道**——没有钱需要申诉。
- **变体表准入判据不变**（由已知 `code` 触发且玩家无自愈路径，二者缺一即不进），承 `decisions/ADR-0131-upgrade-error-non-blocking.md` 的同一条纪律。

## 备选方案

- **在客户端补一张 `code → (OpError, 处置)` 逐条表** — 否决：本库无此形态，且与对侧台账构成第二权威。
- **购买失败复用 `Validation` 或 `Network`** — 否决：两者都不表达「这笔购买没成」的处置轴，付费面的含糊代价最高。
- **为长等待新增一个阻塞屏变体或设硬超时** — 否决：既有的软提示按两种情形分岔文案已足够，硬超时会把一笔仍在处理的订单单方面判死。

## 后果

- `OpError` 值域扩容一格；`systems/architecture.md` 的按 `class` 默认表结构不变。
- 待兑现态的四种联动（处理中保持 · 收据无效终态失败解除 · 已在另一账号核销解除 · 渠道未开通不进）成为购买流程的一部分。
- 购买流程另补两个显式步骤：渠道要求商户侧下单时先经下单端点取支付参数与收据标识并随待兑现态持久化（**首版微信不开通，该步首版不发生、不阻塞上线**）；Apple 侧 `finish()` 只能在验票成功或幂等命中后调用，**不挂在 UI 回调的顺手处**。
- 因此必须这么写的文档：`systems/architecture.md`（枚举一行 + 映入约束）· `systems/monetization.md`（四种情形的呈现与处置 · 两个流程步骤 · 客服可达面）· `ux/error-and-blocking-ux.md`（长等待软提示的两种分岔文案，变体表不扩容）。
