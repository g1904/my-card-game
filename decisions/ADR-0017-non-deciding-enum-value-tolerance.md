# ADR-0017 — 零判定权字段的取值清单不是校验闸：未知取值宽容接收，清单增量不 bump 契约版本

- **状态：** Accepted
- **日期：** 2026-08-28
- **来源：** `handoffs/2026-08-28-save-point-reason-inventory-changed.md` · `handoffs/2026-08-12-grant-source-code-contract.md`

## 背景

上行负载信封的 `reason` 取值清单随客户端 `SavePointReason` 增员而扩（本次追加 `"InventoryChanged"`）。这类增员今后还会反复发生，而契约里逐字列出了取值清单——于是必须回答一个会一直复现的问题：**清单是不是一道校验闸？** 若是，则每次增员都要求两侧成对发版、并 bump 契约版本；若不是，则清单只是文档，两侧可各自独立发版。

同一形状此前已在 `sourceCode` 上出现过一次（§5a），当时只就那一个字段作了处置，未上升为通则。两侧在强制在线架构下独立发版，这个问题不能每加一个成员就重问一次。

## 决策

**取值清单逐字列出的字段中，凡不驱动任何判定者，其清单不构成校验闸：未知取值一律照常处理、原样记账、不改写、不拒收；取值清单的增量不 bump 契约版本。**

- `reason` 对后端是日志与聚合维度，**判定只看 `baseRevision` 与 `pushId`**；收到清单外取值时照常处理该次 push，把未识别值原样记入日志与聚合维度。
- 该处置与 `sourceCode` 的既有条款是同一形状的两个实例，**按同一措辞书写**，不另立一套。
- 由此得出的发版自由度是决策的一部分：**客户端先上线带新成员的版本、后端稍后补清单，期间不产生故障**；反向本就无害。
- 增量与宽容语义合起来即向后兼容 ⇒ **不 bump `schemaVersion`、不 bump URL 主版本**。
- 代价一并写死：**清单因此发现不了拼错的成员名**，孤儿取值只在聚合看板上显形。

逐条兑现 → `contracts/profile-sync.md` §2（`reason`）· §5a（`sourceCode`）。

## 理由

因一个**零判定权**的字段取值不认识就拒收一次合法的进度上行，等于让它获得阻断玩家进度的能力，与「它不驱动任何判定」这条定位直接矛盾（`contracts/profile-sync.md` §2 逐字）。

它与本库既有的两条纪律同向：ADR-0005 的「异常必须可见，但不在同步热路径上做裁决」，以及 ADR-0012 对未知 `sourceCode` 的「记录原值、不改写、不拒收」——后者的反面（归一为 `Unknown` 并回写）会推翻客户端的承重不变式。

两侧独立发版是强制在线架构的现实，而成员语义的权威在客户端库（`game-design-documents/systems/services/sync-service.md`），本库不复述——若清单是闸，本库就成了客户端枚举增员的发版阻塞点。

## 备选方案

- **未知取值 → 拒收该次 push** — 让一个零判定权的日志维度获得阻断玩家进度的能力。
- **未知取值 → 归一为 `Unknown` 并在下行回写** — 已在 `sourceCode` 上被否决（压低 `x`、残卷档位回跳，见 ADR-0012）。
- **每次增员按破坏性变更处理：两侧成对发版 + bump 契约版本** — 把纯表格增量抬成契约版本事件，且使本库成为客户端枚举增员的发版阻塞点。

## 后果

- **同类增员的通道就此定形**：后续再加取值成员不再需要成对发版，后端补清单降为纯观测侧的跟进动作。
- 放弃「用契约清单机械发现成员名拼写错误」的能力——检出改由运维看板承担（孤儿取值可见），落 `operations/`。
- 判据是**该字段是否驱动判定**，不是「它长得像枚举」。驱动判定的枚举（如 `platform`、`OpError.code`）不适用本条，其取值域仍是封闭的契约面。
- 契约文本形态受约束：这类字段的取值清单旁必须写明「不驱动判定 + 未知取值处置」，否则清单会被后来者当成闸 → `contracts/profile-sync.md` §2 · §5a。
- 成员名的最终拼写以客户端侧冻结时的成员名为准（第一批存档写下前冻结），权威在 `game-design-documents/systems/services/sync-service.md`。
