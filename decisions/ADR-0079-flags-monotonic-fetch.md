# ADR-0079 — flags 收紧为「增大即拉、增大即应用」：成功路径不设最小间隔，护栏移到失败路径

- **状态：** Accepted
- **日期：** 2026-08-22
- **来源：** handoffs/2026-08-22-flags-fetch-throttle.md, handoffs/2026-08-23-flags-version-client-gate.md

## 背景

flags 是内容的放量开关（灰度 / 分批放量 / 线上秒关）。触发拉取的判据最初是「版本**不同**即拉」——但「不同」包含变小，而变小的批次要么是回滚、要么是乱序到达，两者都不该被应用。

同时需要一条护栏防止拉取风暴。直觉方案是最小拉取间隔。

## 决策

拉取与应用统一收紧为**「增大即拉、增大即应用」**：

- **拉取闸**：观测到的 `flagsVersion` **严格大于**内存值才拉。
- **应用闸**：拉回的那一批，`flagsVersion` **≤ 内存值即整批丢弃** + `PushWarning`（带拉回值与内存值）+ 上报一次（本会话去重）。等值同样丢弃。

**成功路径不设最小间隔**（护栏 = 单飞 + 尾随一次的显式封顶）；**护栏移到失败路径**（闸门式退避、无定时器、无放弃阈值）。

**内存 `FlagsVersion` 冷启动一律归零。**

→ `systems/services/content-service.md`；退避 cap → `systems/balance.md`。

## 理由

两个闸是**同一条判据的两次兑现**，这使「应用」这一步只有一条判据（严格增大）——没有「有时应用更小的版本」这种需要解释的情形。

最小间隔被否是因为它**会把秒关延迟从分钟级抬到间隔级，恰在运营连发多批时最伤**——而秒关正是 flags 存在的理由。

冷启动归零是「增大即拉」的**爆炸半径闸**：内存值若持久化，一个错误的高版本号会让设备永久停拉。

## 备选方案

- **最小拉取间隔** — 否决：抬高秒关延迟，恰在最需要时失效。
- **沿用抖动** — 否决：观测触发已天然错峰。
- **为 flags 另开重试通道** — 否决：破坏「零轮询」这条立身理由。
- **应用一批更小的 flags** — 否决：没有任何一侧的取向支持它。

## 后果

- **对「`flagsVersion` 单调递增」的行为依赖已明写**：**flags 回滚须以更高 `flagsVersion` 发布**。
- 该对位条款在 `backend-design-documents/contracts/content-manifest.md` 的「服务端保证」中**尚未成文**——这是一条在办的跨边界欠账，缺它的症状是设备**永久停拉 flags**。
- 单飞 + 尾随一次是显式封顶：超出即**停并告警**，不排队、不累积。
