# ADR-0035 — mana 不设曲线：每回合恢复至 `manaLimit`；上限由事件推拉，另在每次大境界提升时 `+1`

- **状态：** Accepted
- **日期：** 2026-07-30
- **来源：** handoffs/2026-07-30b-combat-level-intent-and-decision-point-saves.md, handoffs/2026-08-22-mana-baseline-realm-jump.md

## 背景

早期方案是「mana 有上限、战斗内逐步恢复」（借自同类作品的能量曲线）。它在本作里带来两个问题：回合内的可用量成为第三条需要平衡的曲线，且「这一回合能打几张牌」不再可由玩家一眼读出。

另一侧，`manaLimit` 若完全只由事件推拉，玩家在三个境界里的出牌节奏就没有任何结构性成长。

## 决策

**mana 不设曲线**：战斗中每回合开始由归属方**恢复至 `manaLimit`**。

`manaLimit` 只由两条通道改变：① 事件的 cost / reward 推拉；② **每次大境界提升 `+1`**（进入筑基 `+1`、进入金丹 `+1`，元婴是轮回终点不给），由 life-cycle-service 在篇章边界施加一次。

② 走**既有的 `CostKey.ManaLimit` 增量语义**——**不引入置值语义、不新增境界基线表**。**不设下界护栏。**

## 理由

无曲线使「这一回合能打几张牌」恒等于 `manaLimit`，是一个玩家可直读的数；曲线模型下它取决于回合数，需要玩家心算。

② 之所以走增量而非「基线表 + `max(当前, 基线)` 置值」：置值语义要么迫使每个消费点分辨「这次是置值还是加值」，要么在玩家已通过事件累积到基线之上时产生**跃升反而压低上限**的荒谬结果。

下界护栏被否是因为 `manaLimit` 下降极罕见，不值得为它专门设计一套机制。

## 备选方案

- **上限 + 回合内逐步恢复** — 否决（07-30b 推翻 07-23 旧案）：引入第三条平衡曲线，且可用量不可直读。
- **境界基线表 + `max(当前, 基线)` 置值** — 否决：见上，两种失败模式各自成立。
- **`manaLimit` 下界护栏 + 死牌转化** — 否决：下降极罕见，不值得专门设计。

## 后果

- `CostKey.ManaLimit` 是 `manaLimit` 的**唯一**写入通道，境界提升不例外。
- 「卡牌费用曲线是否随境界整体上移」是这条决定唯一的翻盘前提，仍是 `systems/balance.md` 的待决项。
- 存档面零新增字段：境界提升的 `+1` 是一次普通的 `ProfileChangeSpec` 施加。
