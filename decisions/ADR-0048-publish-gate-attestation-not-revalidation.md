# ADR-0048 — 发布侧校验闸只验背书，不在本库复制任何一条内容校验规则

- **状态：** Accepted
- **日期：** 2026-09-03
- **来源：** handoffs/2026-09-03-content-delivery-ops.md · answer-logs/log-content-delivery-ops.md

## 背景

内容校验规则的权威在客户端侧的打包工具：它保证「凡是打包工具产出的包，都过了闸」。但它**没有也无力**保证「凡是被发布出去的文件集，都是打包工具产出的」——后者是本库的义务，也是这条链上唯一还敞着的口子。

## 决策

后端发布流水线那一半**不是「再跑一遍内容校验」**，而是：**拒绝任何没有打包工具背书的文件集**。以步 ⓪「产物认证核对」实现——证明存在，且逐文件 `sha256` 与待推集**一一对应**，失败即非零退出、无补偿。

配套四条：闸的位置**最前**（先于推 blob）· **无跳过开关、无紧急免检参数** · **校验先于签名** · 非零退出无补偿。

见 `operations/content-delivery-ops.md`「发布侧内容校验闸」C1–C5。

## 理由

在后端再跑一遍校验会造出**第二份实现**，与对侧规则随时漂移——而本库没有任何机制能发现两份规则不一致。用一次 hash 比对把对侧的闸**延伸到发布面**，规则权威仍归客户端。

闸放最前，是因为 blob 是内容寻址 + `immutable` 长缓存的永久对象，不合格产出一个字节都不该落到分发面；闸在最前则阻断天然等于「什么都还没发生」，不需要补偿逻辑。

先验后签，是因为「已签名但不合格」的产物一旦离开流水线，在密码学上与合法产物无法区分。

**人可以跳过的闸不是闸。**

## 备选方案

- 在后端流水线里再跑一遍内容校验 — 造出第二份实现，与对侧规则随时漂移。
- 把闸放在推 blob 之后 — 不合格产物已落到永久分发面，且需要补偿逻辑。
- 先签后验 — 已签名的不合格产物与合法产物在密码学上无法区分。
- 设跳过开关 / break-glass 参数 — 人可以跳过的闸不是闸；日后确需时须与 O5 同构留痕并告警。

## 后果

- 跨库校验责任的切分线就此划定：**规则权威归客户端，背书验证归后端**；本库永不复制校验规则。
- 它是逐基线合并校验（`ADR-0050`）与产包证明字段形态这两条跨库义务的挂接点。
- 客户端侧的对位权威见 `game-design-documents/systems/services/content-service.md` 与其纪律可执行性 ADR。
