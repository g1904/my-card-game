# ADR-0138 — 未过审昵称的「须改名」是启动链内一道 fail-open 的一次性流程门

- **状态：** Accepted
- **日期：** 2026-09-05
- **来源：** handoffs/2026-09-05-backend-batch-client-obligations.md

## 背景

后端合规批量评审给客户端落下一项义务：昵称未过审的账号，登录后须先改名才能继续。落屏方式有两个绕不过去的边界。其一，**本库没有独立的改名屏**——昵称编辑本就是 PlayerProfile 屏内的一个区，任何「进改名屏」的写法都是臆造。其二，本库已把硬阻塞穷举为四处（`sync-service.md`「三条不变式」①）；若把须改名写成第五处阻塞点，它与「本次不新增阻塞点、不新增阻塞屏变体」的声明会当场互相矛盾。同时，驱动它的合规 status 是一次**可降级**的请求——取不到时若卡住启动链，等于把一个呈现性失败升级成登不上游戏。

## 决策

**把「须改名」实现为启动链内、主菜单之前的一道 fail-open 全屏模态，而不是第五处硬阻塞点，也不进 `BlockingNoticeScreen` 变体表。**

- 形态 = 全屏模态，复用 PlayerProfile 屏内昵称区的输入与提交路径，**不新增屏**；
- 时机 = 与既有合规检查**同一次 status 读取**，不新开请求；由应答里的 `nicknameChangeRequired` 布尔驱动，**不由任何后端 `code` 触发**；
- **取不到 status 即放行**：本次会话不拦，下次会话再拦；
- `BlockingNoticeKind` 一格不动；提交失败沿用既有的 `auth.nickname_rejected` + `detail.reasonKey` 映射，不新增处置路径，且「须改名」这个标记本身不带二级原因键。

四处阻塞点与本门的消歧、逐条判据复核 → `systems/services/account-service.md`、`ux/error-and-blocking-ux.md`。

## 理由

- **准入判据两条皆不成立。** `BlockingNoticeScreen` 变体表的准入是「由已知后端 `code` 触发」**且**「玩家在当下没有任何自愈路径」。须改名由布尔驱动、玩家改个名当场就过——两条都不满足，塞进变体表即污染该表的判据。
- **它与四处阻塞点不同类。** 那四处是**失败态**阻塞，玩家只能去更新 / 重登 / 重试；本处是一次性、可自愈、请求取不到即放行的**流程门**。不明写这条边界，「下次会话再拦」与「不新增阻塞点」会被读成互相矛盾。
- **真正的强制力不在客户端。** 它在后端的存量扫描与复核通道，客户端只是把它呈现出来；fail-open 因此不削弱合规效力。
- **模态复用有先例**：与购后等待期的全屏模态进度态同款形态。

## 备选方案

- **复用「既有的改名屏」，以必须完成才能继续的模式进入** — 否决：本库根本没有这样一屏，该写法是对库内形态的臆造。
- **作为第五处硬阻塞点 / 新增一格 `BlockingNoticeKind`** — 否决：准入判据两条都不成立，且与本批次「不新增阻塞点、不新增阻塞屏变体」的声明相抵。
- **status 取不到时阻塞启动** — 否决：把一个可降级的呈现性失败升级成登不上游戏。

## 后果

- 零新增屏、零新增阻塞点、零新增 `BlockingNoticeKind` 变体、零存档 schema 改动；结构增量仅在启动链内多一道模态。
- 「拦」在会话粒度上是尽力而为的：一次 status 失败即本会话不拦，这是被明确接受的代价。
- 因此必须这么写的文档：`systems/services/account-service.md`（读取源 · 落屏形态 · 与四处阻塞点的消歧 · 提交失败映射）· `ux/screen-flow.md`（启动链内的位置）· `ux/error-and-blocking-ux.md`（变体表准入判据的逐条复核，表本身不扩容）。
