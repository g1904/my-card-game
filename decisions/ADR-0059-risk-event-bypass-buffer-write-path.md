# ADR-0059 — 风控事件默认走有界旁路缓冲批量写入，三类例外必须同事务

- **状态：** Accepted
- **日期：** 2026-09-08
- **来源：** handoffs/2026-09-08-risk-ledger-storage-shapes.md · answer-logs/log-risk-ledger-storage-shapes.md

## 背景

`push` 的应答不等待事件落盘，且全库无消息队列（`ADR-0021` 与「明确不引入」四条）。风控事件的写入路径因此只剩一种形态可选，但「只追加」与「不在同步热路径上裁决」两条纪律的**字面**读法会与「同事务留证」「按账号硬删」互相打架，需要一次性写死各自禁的到底是什么。

## 决策

**默认形态：进程内有界缓冲 + 后台批量 `INSERT`。** 缓冲有界（`riskEventBufferRows`），**溢出即丢弃并计数，绝不反压请求路径**。

**三类例外不走缓冲、必须与状态变更同一次事务：** `DeletionRequested` · `DeletionCancelled`（写 `deletion_audit`，与 `account_deletion` 行的插入 / 删除同事务，见 `ADR-0057`）· `NicknameBypassed`。

两条纪律的边界同批写死：

- **「只追加」禁的是**：业务路径上条目永不改写、永不因业务原因单条删除。**恰有两条删除路径且都不是业务路径**——到期的整分区 `DROP`、注销执行时按 `account_id` 的硬删。除此之外没有任何删除 SQL。
- **「不在同步热路径上裁决」禁的是裁决**（阈值判定、处置升级），**不是记一行账**——同事务写一行 `INSERT` 不违反它。

## 理由

- 应答不等落盘 + 无消息队列 ⇒ 有界缓冲 + 后台批量是唯一剩下的形态。**反压等于把旁路做回热路径**，而带累计阈值与窗口的概率信号容得下极少量丢失。
- **例外的判据是「有没有累计冗余」**：`DeletionRequested` / `DeletionCancelled` 丢一条 = 一次删号客诉在服务端零证据；`NicknameBypassed` 是确定性检出、没有累计冗余，且与复核入队是同一次检出的两个落点。**没有累计冗余的信号不能走可丢弃的通道。**
- 不写死两条纪律的边界，「只追加」会被读成「裁剪任务与注销硬删都违规」，「不在热路径裁决」会被读成「同事务写一行账也违规」——两处都会让已定的机制无法落地。

## 备选方案

- **全部事件同事务写** — 把一条旁路做回热路径，`push` 应答时延与失败面直接挂上风控写入。
- **缓冲满时反压请求路径** — 同上；且被反压的是玩家的正常请求，代价与收益完全不成比例。
- **引入消息队列承载事件流** — 与「明确不引入」相抵；且同事务留证的要求本就不可能由队列满足。

## 后果

- `operations/moderation.md` 落写入路径与三类例外；`riskEventBufferRows` 作为旋钮登记进 `operations/environments.md`，**改值不发版**，上线后按真实事件速率标定（取值仍在 `open-questions/06-platform-stack.md`）。
- 溢出丢弃计数是该缓冲唯一的机制发现面，探针口径见 `operations/observability.md`。
- `systems/_index.md`「明确不引入 · 消息队列」一节的收尾句改写为「风控事件落同库 `risk_event` 表（旁路批量写入），告警走指标出口——两者都不需要消息队列」：**结论与论证一字不动**，改的只是会被读成「风控事件不落库」的字面表述。
- 客户端零影响。
