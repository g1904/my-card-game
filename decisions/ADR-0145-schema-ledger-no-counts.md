# ADR-0145 — 逐版 schema 登记表不写任何计数（形态纪律第 ⑥ 条）

- **状态：** Accepted
- **日期：** 2026-09-05
- **来源：** handoffs/2026-09-05-schema-ledger-v1-coverage.md

## 背景

逐版登记表是存档 schema 的**唯一登记面**——照它写迁移器。表内写下过一个「22 格」：它既不来自任何字段表，也无法被 golden 快照核对，**没有任何文档能推出这个数**。而形态纪律 ① 要求本表与快照逐行对得上，快照能逐行对，对不了一个数。

后果不是「多一个无用的数」。规划中的护栏 `ProfileShapeCheck` 一旦落地，这一行会**必然**对不上，成为它的第一条假阳性——而假阳性正是护栏最容易被关掉的死法。计数同时是随字段族增长的第二真值：一处漂移会同时误导两侧（读表写迁移器的人、读快照做核对的人）。

## 决策

**逐版登记表不写任何计数（格数 / 条数 / 行数），立为形态纪律第 ⑥ 条；指代一组字段一律用不带计数的措辞 + 指向字段表的回链。**

- 表内既有计数一次性清除——否则新纪律在自己表内当场不成立；`decisions/ADR-0127-life-merged-into-lifespan.md` 的两处同源计数同批订正，结论一字不变。
- **纪律带一条射程限定：约束的是字段计数，不及于纪律与清单自身的条目编号。**

纪律全文与逐行落点 → `systems/services/profile-schema-versions.md`。

## 理由

- **计数不可机检**：形态纪律 ① 的可机检判据是「本表与 golden 快照逐行对得上」，一个数没有对应的可比对象；写下即制造一处结构上无法验证的断言。
- **假阳性是护栏的死法**：`ProfileShapeCheck` 落地后这行必然报错，而首条假阳性最容易换来「把护栏关掉」。
- **本库已有两条同款先例**：`ProfileChangeSpec` 的「列表数不进承重表述」、全部 Codex 顶层键用不带计数的措辞。本表比那两处更需要它——它是**唯一登记面**，一处漂移会同时误导两侧。
- **射程限定是必要的**：不写它，规则会吃掉自己——纪律自身的编号、清单的行号全是「数」。

## 备选方案

- **保留计数、只在漂移时手工同步** — 否决：手工同步的第二真值正是本表要消除的东西，且无任何机制发现漂移。
- **让 `ProfileShapeCheck` 提前落地以覆盖此类问题** — 否决：它比对的是**代码形状 ↔ golden 文件**那一段，本次这类空缺一条也抓不到；提前落地是付出排期换一个不对症的护栏。

## 后果

- 登记表与 `decisions/ADR-0127-life-merged-into-lifespan.md` 内的全部字段计数一次性清除，改为回链两层 Profile 字段表；结论与形状均不变。
- 同批补齐 v1 行的覆盖空缺，并订正一处错归属。**零 bump、零迁移、对后端零义务**——后端兼容矩阵的触发点是登记表**新增一行版本**，v1 行内补条目不构成触发。
- `achievement` 不补形状，只留一句有承载的占位：其条目 schema 仍是 `systems/services/profile-service.md` 的待决问题，在唯一登记面上写推测形状会被照抄进迁移器。
- 条目维度另补一条第 3 级旁证：`/sync-knowledge` 增一条对账项——v1 清单的条目集合与两层 Profile 字段表的行集合双向核对。该断言写进登记表，不改技能文件。
- 因此必须这么写的文档：`systems/services/profile-schema-versions.md`（纪律 ⑥ + 射程限定 · v1 行补齐 · 计数清除 · 对账断言）· `decisions/ADR-0127-life-merged-into-lifespan.md`（两处同源计数订正）。
