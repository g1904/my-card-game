# ADR-0006 — 开发顺序：框架 → 内容 → 平衡与体验 → 社交及其他

- **状态：** Accepted
- **日期：** 2026-07-27
- **来源：** handoffs/2026-07-16-ux-flow-login-and-dev-order.md · handoffs/2026-07-27-content-gating-offline-resilience-and-rng-persistence.md · handoffs/2026-08-25-numeric-philosophy-and-balance-anchors.md

## 背景

项目在零行代码的状态下已积累大量设计文档。「先做什么、后做什么」若不定，两类风险立刻显形：把测试 / 平衡 / 美术整体押到末段，数值手感会反过来逼系统 API 返工；纯瀑布式自顶向下则把端到端验证推得太晚，架构风险要到很后面才暴露。同时需要一个可引用的口径来回答「这个东西现在该不该做」——`content-service` 的 `contentVersion` 冻结、每日种子 / 排行挑战、平台内购结构预留都反复撞上这个问题。

## 决策

按**系统层次**排四个阶段：**框架 → 内容 → 平衡与体验 → 社交及其他**。

1. **框架** —— 服务骨架、核心循环、存档 / 同步、内容管线。
2. **内容** —— 五类 AdventureEvent、卡牌、敌人、剧本；阶段内部**优先打磨第一篇章（ch1）**，切入点是起始角色的 starter deck。数值标杆（卡牌道念产 / 削量纲、`lifeTotal` 回复幅度、`lifeSpanCost` 分档）**先定形状、后定数值**：本阶段只立形状锚点——各旋钮之间的相对关系与量纲比例，不定任何具体取值。形状锚点见 `systems/balance.md`。
3. **平衡与体验** —— 数值标杆的取值定标归此阶段：内容铺开且游戏可运行后，由实测样本统计校准。
4. **社交及其他** —— 每日种子、排行挑战归此阶段，**当前不为其预留任何结构**。

横切各阶段的**工程方法**：**设计先行（自顶向下）→ 垂直切片先跑通端到端 → 贯穿式用占位数据做轻量平衡 → 美术挂点占位、末段替换**。垂直切片的第一条链路钉为「登录 → 主菜单 → 炼气一场战斗 → 存档」。

两节是**同一路线的两个视角**（一个按系统层次、一个按工程方法），不冲突：框架阶段内部同样走垂直切片优先。

**「设计密度远超实现进度」是已知且接受的状态**，不中断设计去先落一个最小可跑的战斗回路；悬空的数字先由形状锚点框住相对关系，具体取值留待内容扩充后的统计校准。

细节见 `vision/scope.md`「开发顺序（已采纳的改良版）」。

## 理由

- **平衡完全押末段会反噬系统 API 设计。** 数值手感（能量曲线、伤害、掉率）会改变接口形状；系统全部成型后才首次平衡，必然返工。系统落地即用占位数值 + 数据驱动配置（平衡值落 `.tres`，见 `.claude/rules/data-resource-rules.md`），使后期平衡是「调数据」而非「改结构」。
- **垂直切片最早暴露架构风险**，也让美术挂点在真实链路里被验证。
- **先定形状、后定数值，比在机制讨论中拍脑袋更可靠。** 数值标杆需要完整的内容上下文与可统计的样本量，二者都要等内容铺开、游戏跑起来；机制阶段先立形状锚点即可框住设计——这是「机制阶段不必先把数字定死」这条推论的依据。
- **第 ④ 阶段不预留结构**：预留即臆造。若将来引入挑战模式，正确做法是让该模式内的轮回绑定一份冻结的 `contentVersion` 快照，把例外局部化，而非回退全局的「以 overlay 为准」决策。

## 备选方案

- **设计 → 系统全成型 → 末段一次性测试 / 平衡 / 美术** — 否决：平衡押末段反噬 API 设计；纯瀑布推迟端到端验证。
- **中断设计、先落一个最小可跑的战斗回路以证伪悬空数字** — 否决：与「设计先行」正面冲突；且悬空数字的回归依赖内容铺开后的实测样本，一个提前拼凑的最小回路给不出可据以定标的样本量。

## 后果

- 约束了每一次「这个东西现在该不该做」的裁决：不在中期路线图内的功能**不预留结构**（`systems/services/content-service.md` 的 `contentVersion` 不冻结、`systems/services/plot-manager.md` 的分支路径不落存档、`systems/monetization.md` 的通行证 / 赛季不做，均直接引用本 ADR 的阶段划分）。
- `DrawPool<T>` 与 `LocalizedText` 的排期钉在「第二阶段开工前、第一份内容 FR 之前」，正是本 ADR 的阶段边界给出的窗口（见 `systems/services/content-service.md`）。
- 放弃了「先做出一个可玩 demo 再补设计」的路径；接受当前设计密度远超实现进度。
- 影响文档：`vision/scope.md`（权威）· `systems/services/content-service.md` · `systems/balance.md` · `systems/monetization.md`。
