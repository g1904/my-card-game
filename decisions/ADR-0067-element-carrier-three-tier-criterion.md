# ADR-0067 — 新施加语义的落点按三级问法自上而下取第一个成立者：新增一列 → 同列内新增 `Op` → 配表加一列

- **状态：** Accepted
- **日期：** 2026-08-17
- **来源：** handoffs/2026-08-17g-element-carrier-gaps.md

## 背景

`ProfileChangeSpec` 是所有 Profile 写入的统一载体。每当出现一种新的施加语义（禁用一个能力、置换、记一次图鉴解锁…），就要回答它落在哪：新开一列？在既有列里加一个 `Op`？还是在配表里加一列属性？

没有判据时，这个问题每次都要重新讨论，且不同的人会给出不同答案。

## 决策

**三级问法，自上而下取第一个成立的落点：**

1. **新增一列** — 当它在六个面上与既有列**全不对齐**时。
2. **同列内新增 `Op`** — 当它属于既有列的对象，只是动作不同。
3. **配表加一列** — 当它是该类型的一个**属性**，而非一次施加。

**反判据：逐次取值可变的性质必须逐条带在 element 上**（不能进配表）。**唯一恒成立的例外**：「谁有权改写它」永远是类型属性、永远配表。

判据全文与逐次应用 → `systems/architecture.md`「共享核心类型」；`profile-service.md` 只回链。

## 理由

三级是按**信息量从大到小**排的：新增一列改变 spec 的形状（最大），加 `Op` 改变一列的动作集（中），配表加列只改变一张静态表（最小）。自上而下取第一个成立者，等于「能小则小」——而每一级都有可判定的条件，不靠判断力。

反判据是防止把可变的东西塞进静态表：配表是按类型查的，一旦某个值需要逐次不同，配表就查不出来。

## 备选方案

- **每次遇到新语义时逐案讨论** — 否决：同一问题不同答案，且答案不可追溯。
- **一律新开一列** — 否决：spec 会长成几十列，且大多数列恒空。

## 后果

- 例：`activeCombat` 收在既有列内、不另开一列——它在六面上与 `activeEvent` 全部对齐，**而判据明文要求六面全对齐即不分列**。
- 例：`HiddenStatGrant` 的第三格 `HiddenStatDirection` 按判据落不进配表（逐条目可变），故带在 element 上。
- 这条判据是 `systems/architecture.md` 反复引用的裁决工具，不复述在其他文档。
