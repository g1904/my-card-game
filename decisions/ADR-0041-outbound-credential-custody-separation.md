# ADR-0041 — 向外调用类凭据取云 Secrets 条目，按轮换驱动方分立托管

- **状态：** Accepted
- **日期：** 2026-09-06
- **来源：** handoffs/2026-09-06-iap-channel-integration.md · handoffs/2026-09-06-external-provider-selection-dr.md · answer-logs/log-iap-channel-integration.md · answer-logs/log-external-provider-selection-dr.md

## 背景

后端持有多类秘密材料：内容签名私钥、会话 token 签名密钥、渠道验票凭据、外接能力凭据。`ADR-0023` 已为签名私钥定了「KMS 只保管被包裹私钥、不进签发热路径」的形态。渠道与外接能力的凭据看上去也是秘密，但它们的性质不同——它们是**向外调用时出示的客户端凭据**，轮换由外部方驱动。

## 决策

渠道验票凭据与外接能力凭据一律托管为**云 Secrets（SSM）条目**，**不复用签名密钥的「KMS 包裹 + 启动解包」形态**。条目粒度：渠道凭据 = 渠道 × 环境；外接能力凭据 = 能力 × 供应商 × 环境。secret 载荷内以 **`credentials[]` 数组承载新旧并存**，轮换 = 先追加新项、渠道方切换确认后删旧项，**不设「秒级双活切换」机制**。

**判据是轮换的驱动方**：同一驱动方的材料可共用一份托管配置，驱动方不同即各自独立——凭据类别增员时按此判据落位，不回头改一个写死的个数。各类凭据**各有一条独立审计线**。公开材料（Apple 根证书 / 微信平台证书）不占 Secrets。

形态见 `operations/purchase-ops.md` §1 与 `operations/external-providers.md`「凭据托管」；指路见 `operations/environments.md`。

## 理由

签名私钥那套形态的取舍点是「KMS 不在签发热路径上」；而渠道 / 外接凭据形态杂（`.p8` 文本 · 服务账号 JSON · 对称密钥 · 商户 RSA 私钥），且轮换由**外部方**驱动、需要新旧并存窗口。Secrets 的条目版本化天然承载这两点，信封形态则要自管存储与版本并存逻辑。

共用一份托管配置会让**最慢的那条轮换节奏绑架其余**——这正是各类钥匙分立的同源理由。

## 备选方案

- 复用签名密钥的 KMS 包裹形态 — 要自管存储与新旧并存逻辑，而外部驱动的轮换正需要并存窗口。
- 秒级双活切换机制 — 渠道方的轮换窗口以天计，追加 → 确认 → 删除三步足够。
- 把公开材料也塞进 Secrets — 判据是「是不是秘密」，公开材料随镜像 / 配置分发或从官方接口拉取。
- 外接能力凭据并入其余任一类钥匙的托管配置 — 轮换驱动方不同，最慢的一条会绑架其余。

## 后果

- 秘密材料的类别数不再被写死在任何一处文本里，增员时按驱动方判据落位。
- 审计线数量随类别增长，各自独立；`ADR-0023` 的签名密钥审计线不受影响。
- 微信的 Secrets 条目随资质开通再建（→ `ADR-0042`），契约面与托管结构零变更。
