# ADR-0104 — `Immediate` flush 是一次「尝试」、软阻塞闸门是一个「状态」，flush 失败绝不挡玩家

- **状态：** Accepted
- **日期：** 2026-08-09
- **来源：** handoffs/2026-08-09-sync-revision-cas-and-immediate-flush-nonblocking.md

## 背景

`PushPolicy.Immediate` 的 flush 点之一正是「进入战斗前」。断线时这次 flush 必然失败，于是产生一个问题：它该不该把玩家挡在战斗外？把「一次 push 尝试」与「同步落后到什么程度算超限」混为一层，就会得出「Immediate 意味着必须成功」这个错误结论。

## 决策

**flush 是一次「尝试」，闸门是一个「状态」。** `Immediate` 只声明「这一批不等防抖窗口，立刻发」，**不声明「发不出去就停下」**；它与 `Debounced` 在失败处置上完全一致——进待发队列、指数退避、不阻塞玩家。

flush 对软阻塞的**唯一**影响是：成功则清空闸门，失败则闸门计数不变。阻塞与否始终只由闸门在**既定时机**判定——下一次 AdventureEvent 选择前。

**进入战斗前 flush 失败不加任何额外提示**，仅沿用常驻的「离线 · 待同步 N」指示；前提是该指示在战斗屏内也必须可见。

既定的两处硬阻塞（启动 pull 失败、被后端明确挤下线）不受本条影响。完整的失败语义与两个闸门 → `systems/services/sync-service.md`。

## 理由

四条既有定案各自独立地指向同一个答案：断线降级表已规定 push 通道「不阻塞玩家」且该行为不按 `PushPolicy` 分叉；软阻塞的定案措辞是「不打断进行中的事件」，而玩家选中 Combat 的那一刻事件已经开始（`SelectCost` 已施加、`eventStart` 已进入），挡在战斗外就是打断；`SelectCost` 不回滚这条纪律把代价说死了——付了成本却拿不到事件，比丢一次同步严重得多；D0 不参与闸门判定已是定案，而 D0 就是「进入战斗前」这个 flush 点，同一个点不能一边被排除在计数外、一边又能独立触发模态。

这个 flush 点的意图本就不是 flush D0 自己那点 diff，而是**趁着即将进入一段长时间无事件级存档点的区间，尽力把队列里已有的变更送出去**——正因为目的是「尽力」，失败就更不该有阻塞力。

不弹 toast：断线期间每一场战斗入口都会命中这条路径，在此提示等于把一次性的网络状态变成逐场重复的打扰，且时机恰是玩家最专注处。

## 备选方案

- **进入战斗前 flush 失败即挡住玩家（软阻塞前移到战斗入口）** — 否决：与上述四条既有定案冲突。
- **flush 失败 → 回滚 `SelectCost` 并退回选择界面** — 否决：与「`SelectCost` 不回滚」直接冲突，且会开出「不满意就断网重选」的窗口。
- **进战斗前弹一次非阻塞 toast** — 否决：逐场重复打扰，时机最差。
- **完全静默、连常驻指示也不要求可见** — 否决：静默就变成了失联。

## 后果

- `systems/services/sync-service.md` 是权威；`PushPolicy` 枚举不改，只明写两档在失败处置上一致。
- `ux/combat-ux.md` 因此背上一条硬要求：常驻「离线 · 待同步 N」指示在战斗屏内必须可见。
- 战斗结束后闸门自然对齐——事件结算给闸门 +1，若达阈值则模态在下一次事件选择前弹出（既定时机）。滞留计时不因战斗进行而暂停，这是正确行为。
- 闸门的计数口径 → `ADR-0102`。
