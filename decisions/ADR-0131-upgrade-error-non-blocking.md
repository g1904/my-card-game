# ADR-0131 — `Upgrade` 类错误只在两处硬阻塞；缓冲闸门口径不变、只换文案与选项

- **状态：** Accepted
- **日期：** 2026-08-11
- **来源：** handoffs/2026-08-11b-contract-boundary-and-flags-client-side.md

## 背景

后端错误码里有一整类 `Upgrade`——典型情形是 `sync.payload_schema_unsupported` 在**轮回中途的 push** 上返回，且它**重试永远不会成功**。既有的断线降级通道假设「可能会好」，退避重试在这里只是空耗电量与流量；而既定的软阻塞闸门（缓冲超限）如果原样触发，玩家会看到一个带「重试」的模态，点它必然失败。

## 决策

**`Upgrade` 类错误只在登录 / 启动 pull 构成硬阻塞，其余时机一律降级为非阻塞。硬阻塞仍然只有两处，且只由已知 `code` 触发——一个未知 `code` 永远不得新增第三处硬阻塞。**

非闸门点的四条处置：**本地缓冲保留、不丢弃**（绝不回退存档点）· UI 出一条**非模态**提示 · **暂停自动退避重试** · 恢复点 = 玩家更新并**重新登录**后先 pull 后 flush。**暂停退避的唯一解除条件是「重新登录成功」**，不因时间流逝、不因应用重启自动恢复。

**与「缓冲超限 → 软阻塞」的衔接：两个闸门的口径完全不变**（未同步的事件级存档点数与最早一条待发变更的滞留时长），仍在下一次 AdventureEvent 选择前弹软阻塞模态。**变的只有文案与选项**——这是同一处模态的**第二种变体**，选项为「去更新 / 退出到主界面」，**没有「重试」**。

UI 区分两种变体走 sync-service 新增的只读属性 **`bool UpgradeRequired { get; }`**（收到事件后单点查询），**不新增 `SyncState` 值**；置位于收到任一 `class: Upgrade` 错误，清零于重新登录后的一次成功 pull。逐条处置与文案落点见 `systems/services/sync-service.md` 与 `ux/error-and-blocking-ux.md`。

## 理由

- **闸门机制不该变，只有文案与选项该变**：同步在本会话内**永不恢复**，继续玩只会累积必然无法上行的进度——软阻塞的本意正是拦住这一点。冻结闸门会让玩家整轮回打完才发现全部进度无处可去。
- **暂停退避是因为前提不成立**：退避的前提是「可能会好」，这里不会。
- **保留缓冲不丢弃**：承 `decisions/ADR-0032-save-point-never-rewinds.md` 的「绝不回退存档点」。
- **未知 `Upgrade` 不得硬阻塞**：代价是一个真失效的会话可能多跑一小会儿（下一次操作仍会被拒），收益是**一条后端新加的错误码不可能打断玩家进行中的轮回**。
- **取只读属性而非新增 `SyncState` 值**：既定的 `SyncStateChanged(SyncState, OpError)` 分辨不出「`Failed` + `Validation`」到底是哪一种；单点查询与既定的 `PendingCount`、`CapabilitiesChanged` 空负载完全同构。
- **沿用既定的「不打断进行中的事件」时机**，无需另立第三种阻塞时机。

## 备选方案

- **冻结闸门、只留常驻非模态提示** — 否决：玩家可能整轮回打完才发现进度无处可去。
- **只在轮回结束时阻塞** — 否决：引入既定机制里不存在的第三种阻塞时机。
- **`Upgrade` 在任何时机都硬阻塞** — 否决：会让一次中途的 schema 不兼容直接打断进行中的轮回。
- **新增一个 `SyncState` 值以区分变体** — 否决：见理由，与既有的单点查询范式不一致。
- **保留「重试」选项** — 否决：重试必然失败。

## 后果

- 版本协商的两条通道自此互不兼职：**内容维度**（manifest 内的 `minAppVersion`，客户端自行比对，低于它只是跳过本次 overlay、永不阻塞）与**协议维度**（服务端判定，登录 / 启动 pull 点被拒才硬阻塞）。**内容太新只是不更新内容；协议不兼容才拦人。**
- 客户端**不持有兼容矩阵的任何副本**——它是服务端判定的输入，必须与判定逻辑同处。
- sync-service 的 API 面增一个只读属性；`SyncState` 值域不变。
- **仍未答**：两条「去更新」提示（软提示 vs `Upgrade` 态非模态提示）的呈现形态与去重——两条都指向同一个动作，不该在屏上叠成两个（归 `ux/`）· 强更硬阻塞屏的形态（是否跳应用商店 / 各渠道差异如何吸收，归 `ux/`）。
- 因此必须这么写的文档：`systems/services/sync-service.md`（承重纪律 + 四条处置 + 第二种变体 + `UpgradeRequired`）· `ux/error-and-blocking-ux.md`（三档提示表与常驻指示）· `systems/architecture.md`（`code → OpError` 映射表的 `Upgrade` 默认路径）。
