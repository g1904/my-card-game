# ADR-0142 — 灰态是视觉降级而非引擎级禁用：灰格必须继续接收触控

- **状态：** Accepted
- **日期：** 2026-09-05
- **来源：** handoffs/2026-09-05-barter-grayed-state-keys.md

## 背景

本库对灰态定了一条纪律：**灰格点按要给一条说明**（配合「无 hover-only 可供性」这条移动端纪律，说明只能靠点按拿到）。但纪律只写了呈现意图，没写实现边界——落地时一个 `Button.Disabled = true` 看起来完全合理，而 Godot 的 disabled 控件**不发按下信号**，说明通道就此静默消失。症状是「点了没反应」：不报错、不打日志、测不出来，是一种**线上不可见的失败**。

本次补 Exchange barter 灰态判据行时，这条边界必须一并写死，否则新补的两个说明键从一开始就可能拿不到。

## 决策

**灰态一律是视觉降级，不是引擎级禁用：灰格必须继续接收触控。**

- 以降低饱和度 / 透明度表达不可用；
- **触控接收位与可用态完全一致，触控目标尺寸不缩水**；
- 该条对灰态判据表的**全部**项成立——礼包入口、主菜单「开始新轮回」、Exchange 刷新按钮、Exchange 买不起格、Exchange barter 格。

判据表与逐项说明文案键 → `ux/error-and-blocking-ux.md`。

## 理由

- **它兑现的是两条既定纪律**：「点按给一条说明」与移动端的「无 hover-only 可供性」。做成 disabled 控件会把前者静默取消，而后者意味着说明**没有第二条通道**。
- **失败模式不可见**：disabled 控件不发 `pressed`，没有任何一层会报错，只有玩家会遇到；一条只能靠人工试点发现的缺陷不该留给运行期。
- **触控目标尺寸不缩水**是移动优先的直接推论——不可用不等于难点中，缩小接收位会让说明更难拿到。

## 备选方案

- **用引擎级 disabled 表达灰态** — 否决：它静默取消「点按给一条说明」，且失败在线上不可见。
- **不呈现不可用项（按持有面过滤）** — 否决：barter 格与买不起格的判据是**可变状态**（轮回内可买到、可由事件产出、可售出），隐藏会让玩家看不到「攒够了就能换」这条信息；只有恒真不可用才走不呈现。

## 后果

- Exchange 屏的 barter 格与买不起格、Exchange 刷新按钮、礼包入口、主菜单「开始新轮回」的灰态实现一律受此约束，`/blueprint` 与 `/implement` 不得以 `Disabled = true` 落地。
- 灰态说明文案键一律走**所属分区**的普通键、不占 `ERR_` 前缀（本地业务拒绝、无后端 `code`），`ERR_` 的反向审计不受影响。
- 零机制增量：`Holds(...)` 签名与语义不动 · `CanAfford` 不动 · `ApplyResult` 不新增字段 · 存档 schema 与 `schemaVersion` 不动 · 分区表不新增分区 · 后端零配合。
- 因此必须这么写的文档：`ux/error-and-blocking-ux.md`（判据表两行 + 说明键 + 本条边界）· `systems/adventure-event/exchange/_index.md`（键的回链指向该文档）。`decisions/ADR-0126-exchange-barter-payment.md` 的「不持有支付物 → 灰显而非不呈现」由本条给出实现边界。
