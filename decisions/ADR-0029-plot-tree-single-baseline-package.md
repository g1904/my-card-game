# ADR-0029 — 剧本树不按篇章分包：整体随 `res://` 基线发布，更新走 overlay 文件级增量

- **状态：** Accepted
- **日期：** 2026-08-22
- **来源：** handoffs/2026-08-22-plot-tree-chapter-packaging.md（配套三项的正式裁决见 answer-logs/log-0823.md 第二节，逐条移出见 answer-logs/log-plot-tree-chapter-packaging.md）

## 背景

剧本内容是全库唯一一类「按篇章天然可切」的大宗文本：`PlotArcData.ChapterScope` 早被点名为「日后分包边界的天然切分键」，而内容层已现成的文件级事务与逐文件 hash 比对又使「增量下载」看起来几乎零成本。于是悬着一道取舍题——三篇章的完整剧本树该不该按篇章分包、按进度增量下载。它不定，`plot-manager.md` 的剧本载体形态与 `content-service.md` 的分发面都留着一个可能被推翻的前提。

## 决策

**剧本树不按篇章分包：三篇章的完整剧本树整体随 `res://` 基线发布，更新走 overlay 既有的文件级增量热更。**

- 不按 `PlotArcData.ChapterScope` 分包、不按 `PlotTier` 分包、不把剧本正文外置为独立文本类型只分包正文、不重开云端按需请求。
- **采纳结果是零机制增量**：manifest 不加字段、`manifestSchema` 不提升、`ContentUpdateManager` 不加运行时下载路径、不新增第三处硬阻塞、`PlotArcData` / `PlotNodeData` / `PlotKeyPoint` schema 全不动、不新增任何失败语义或降级分支。
- **本条不横跨库边界**：由客户端的内容合并与打包决定，服务端不感知内容类别、报文无变化 ⇒ `backend-design-documents/contracts/content-manifest.md` 零改动、不留承接。
- 保留一道**零成本复核闸**（第二阶段第一批真实剧本条目写完后实测字节占比，双门槛越线才重开讨论），以及一句**方向性记录**（真要缩初装包，落点是平台原生按需资源而非 manifest 分包）。

承重理由全文、代价明写、复核闸与方向性记录 → `systems/services/plot-manager.md`「剧本树不按篇章分包」；对内容服务的零增量结论 → `systems/services/content-service.md`。

## 理由

- **分包与「合并后全量强校验」在结构上冲突（最重的一条）。** 剧本侧的加载期校验是全量的（四类悬空校验 + 层级 + 可达性 / 含环 + `PlotTriggerId` 双向）。某一包未下载时跨包引用当场悬空 ⇒ 启动即 `PushError` + 抛。要让分包成立只有三条路，每条都在拆一件承重件：放宽悬空校验为 `PushWarning`（真编排错误与「包还没下」在日志里长得一模一样）· 造第三种状态「未下载」（内容层出现既非存在也非不存在的态，立刻传染到 `Get(id)` / `AllEnabled()` / `newIds` 双闸 / 悬空 key point 降级四处）· 把边界切在无跨包引用处（但 Story arc 按定义贯穿三篇章、`SideStory` 按定义跨篇章、`PlotTriggerId` 按定义跨到档位表——**跨包引用不是可避开的编排问题，是剧本层级模型本身的形状**）。
- **强制在线消解的是分包的收益侧。** 启动即须登录 + 跑一次 pull（两处硬阻塞）⇒ 玩家必然有网，「先玩起来、剩下的慢慢下」这条离线优先产品的核心动机在本作没有对应场景。反过来分包会造出一个既有设计里不存在的失败态：「推进到第 2 篇章却没网」在不分包下完全无害（剧本在盘上，`plot-manager.md`「剧本读取没有网络失败路径」），分包下要么成为第三处硬阻塞，要么成为「整章剧本静默缺席」。
- **量级不成立。** 剧本文本落在包体的百分之一量级（落地增量不足 1 MB，约等于一首 BGM，而引擎基线与卡面美术是数十 MB 级）；且 overlay 侧本就已是文件级增量下载，本题真正问的只剩「随包基线要不要拆」。

## 备选方案

- **按 `ChapterScope` 分 3 包** — Story arc 与 `SideStory` 落不进任何一包 ⇒ 边界实为 3 + 1，且「哪些进公共包」成为一条要逐条目维护的新编排纪律；仍撞上全量强校验。
- **按 `PlotTier` 分 2 包** — 同样存在跨包引用（Chapter → 所属 Story、`PlotTriggerId` 跨到档位表），未回避核心冲突。
- **剧本正文外置为独立文本类型、只分包正文** — 重新打开「正文内嵌节点」已关上的口子：拆开后 overlay 新增一条 arc 时写不出它的正文，剧本例外当场失效。
- **重开云端按需请求** — 08-11 已定案否决的四条理由原样成立。
- **保留为「已倾向不分包、待实测复核」而不关闭** — 结论不依赖任何未知量（结构冲突与强制在线论证是纯推演），它不是信息不足型待答项；复核闸以零成本补上「相对结论的前提可能变化」这一风险。

## 后果

- **初装包永远包含全部三篇章的剧本文本**，包括玩家可能永远打不到的第 3 篇章。这笔浪费换来「剧本读取没有网络失败路径」这条结构性事实无例外地成立——它正是「不设剧本事务前置 / 不设 `user://cache/plot/` 与 LRU 预取 / `sync-service.md` 降级表无剧本一行」三条既有结论的前提。
- **`content/plot-arc/_index.md` 与 `content/plot-node/_index.md` 开张时**，须在「条目台账」小节记一行口径「条目数 + 字节总和」作为体积护栏；**不加任何加载期校验**（那需要定两个当前没有依据的数字）。两个类型档案尚未开张，本项随开张落地。
- **不预留任何分包结构**，但保留路标：真要缩初装包时该动的是美术 / 音频 + 平台原生按需资源（Android Play Asset Delivery / iOS On-Demand Resources，属发行侧打包配置），不是 manifest 分包——免得日后有人因为「manifest 已经现成」而回退全局决策。
- **后端零参与**：`backend-design-documents/contracts/content-manifest.md` 既有条款「剧本文本是一类普通内容文件、契约层无需新增字段」由本决策维持而非改动，对侧不写承接。
