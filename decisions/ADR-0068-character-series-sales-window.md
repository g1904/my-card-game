# ADR-0068 — 角色系列的上架窗口只约束「能不能买」，不进 profile、不进任何封闭表

- **状态：** Accepted
- **日期：** 2026-09-11
- **来源：** handoffs/2026-09-12-premium-character-series-unlock.md

## 背景

付费角色系列引入**限时销售**：某个系列只在一段时间窗内可购。限时销售一旦进来，立刻带出两个方向相反的诱惑：把窗口下发给客户端（好让 UI 能自己判断）、把窗口写进 profile（好让「我买过」和「还能不能买」在同一处）。两者都会把一条纯运营配置抬成契约面 —— 而窗口关闭与「玩家失去已购内容」是完全不同的两件事，混淆它们的代价是玩家付过钱的东西被收回。

## 决策

**每个 `kind == CharacterSeries` 的 SKU 在 SKU 表上带一格上架窗口**：可空的 `[startAtUtc, endAtUtc)`，**空 = 常驻商品**。验票时该 `productId` 不落在其上架窗口内 ⇒ **`purchase.receipt_invalid` + 风控事件**，与「`productId` 不在 SKU 表」同码，**不新增 `code`**。

三条语义：**不绝版**（窗口可重开，或转常驻仅失去限时优惠价）· **已购玩家永久可用**（下架的只是购买入口）· 限时的是价格与销售节奏，不是可得性。

**窗口不进 profile、不进 `/entitlement/characterSeries`、不进 §5 的任何封闭表，也不下发给客户端作判据。** 主防线仍在平台侧（窗口外的 SKU 在各渠道商店后台下架），后端这一道是兜底，覆盖「下架动作未及时同步」与商户侧下单渠道。

→ `contracts/purchase.md` §3a「上架窗口」· `operations/purchase-ops.md` §1a

## 理由

- **窗口约束的是「能不能买」，不是「拥有什么」** —— 这条区分是本决策的全部承重点：它使窗口关闭与 `purchase.md` §6 保证 8「只增不删」互不干涉，已写入的解锁元素永不被移除。
- **进 profile 会让一条纯运营配置占一格存档**，并因此背上透明路径的稳定性约束（移动或重命名即破坏性契约变更，`profile-sync.md` §5）。
- **窗口外与「不在 SKU 表」对玩家是同一件事** —— 这个商品此刻不可售；`purchase.receipt_invalid` 的 `message` 必含项已覆盖「判定失败的那一项 = SKU」（`envelope.md` §6）。独立成码只会让客户端处置表多一行走同一条路径。
- 发版前核对清单要求**窗口起止时刻与商店后台的上下架排期对齐（时区一律 UTC）** —— 两侧不对齐时的症状正是「商店里买得到、后端拒收」，即玩家在付款之后撞失败面。

## 备选方案

- **把上架窗口下发给客户端 / 写进 profile** — 它约束「能不能买」而非「拥有什么」；进 profile 会让一条纯运营配置占一格存档并背上路径稳定性约束。
- **窗口外购买新造一个 `code`** — 与「`productId` 不在 SKU 表」的客户端处置逐字相同，多一行映射表换零收益。
- **窗口关闭 = 绝版（不可重开）** — 会把一条销售节奏工具变成对已购玩家的可得性威胁；三条语义正是为排除这一读法而写死的。
- **只靠平台侧下架、后端不做窗口校验** — 覆盖不到「下架动作未及时同步」与商户侧下单渠道。

## 后果

- `operations/purchase-ops.md` §1a 的 SKU 表须有「上架窗口」列与三条语义，「发版前核对清单」须含窗口 ↔ 商店排期对齐一项。
- `contracts/purchase.md` §3a 须写窗口外的 verify 处置并明写「不进 profile、不进封闭表」；§6 保证 8 须逐字含「包括其上架窗口关闭的情形」。
- `contracts/envelope.md` §6 台账与 §3 端点全集表**均零加行**。
- **一处已知的未决面**：窗口校验现只落在 verify（付款**之后**）。前移到 `POST /v1/purchase/order` 更合「把失败点挪到掏钱之前」，但下单端点没有语义合身的既有 `code` —— 该问题留在 `open-questions/01-contracts.md`，**本决策不预判它**；微信渠道首版不开通 ⇒ 不阻塞首版。
