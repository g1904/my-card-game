# ADR-0021 — 后端运行时形态：单主关系库承载全部权威状态，玩家读路径全走写入区

- **状态：** Accepted
- **日期：** 2026-09-03
- **来源：** `handoffs/2026-09-03-backend-stack-and-hosting.md` · `answer-logs/log-backend-stack-and-hosting.md`

## 背景

六份契约全部成文、再无取值留白之后，全库唯一的结构性前置就是技术栈与托管形态。契约刻意把一批实现语义停在语义层并挂账到运维侧（`revision` CAS 的存储、幂等记录的事务边界、跨区拓扑、会话存储与同事务吊销、`signin` 回放记录、token 密钥保管、四条探针……），且明写「落定后进 `operations/`、**不回头改契约**」——这些不是九个独立的选型，而是**同一个选型的九个侧面**。

## 决策

**栈与托管形态落定为 C# / ASP.NET Core · 腾讯云托管容器 · 云数据库 PostgreSQL（单主）· 云 Redis · 云 KMS · CDN；单区域部署、不做跨区域多活；玩家读路径全部走写入区。**

- **单库 PostgreSQL 承载全部权威状态**（账号 / identity / 会话 / profile / 幂等记录同处一库）⇒ 契约要求的「幂等记录与计数器自增同一次事务」是**一次普通的本地事务**，零分布式事务、零两阶段提交。
- **Redis 只做限流计数器，不持任何权威状态。**
- **只读副本只承担灾备与离线分析，不承接任何玩家读路径**；flags 读路径不受读己所写约束这条自由度**保留但当前未使用**，不引入按端点分档的例外表。
- **灾备只写能力要求，不写副本数**——部署形态须满足 `ADR-0009` O3 的可演练恢复；副本数 / 可用区分布 / 备份保留期是成本模型的输出。
- 环境实体取**两套云上（testing + production）+ 本地 docker-compose 承担 feature**。
- 六条筛选闸、逐项淘汰过程与全部旋钮 → `operations/environments.md` · `operations/deployment.md` · `systems/_index.md` · `systems/profile-store.md`。

## 理由

**存储侧由契约反向选定，不由规模判断选定：**

- **不做多主 / 跨区域双写**——账号级严格单调计数器在多主下无法维持，而**云端权威的全部力量建立在它上面**（`operations/environments.md`）。这是契约层面的排除。
- **排除任何单条记录硬上限 < 512 KB 的 KV**——那条软告警阈值是「正常账号预期会接近并越过」的观测线，把它抬成硬失败等于给正常账号造一条「push 永远失败」的路径，失败面是玩家进度。
- **浅合并不交给存储原语**——可用的原语要么正是被否决的 JSON Merge Patch、要么是递归合并；选它就得在应用层手写，即把一条承重契约语义从**存储不变式降级为代码纪律**。
- **读全走主是 `ADR-0013` 读己所写的最简兑现**（会话粘滞的极端形态）。在契约定义的流量形状下主库同时承担读写毫无压力，因此不必引入 `revision` 下界等待这类更复杂的机制。

语言取 C# 的承重理由：它在**唯一一处不容差错的地方（SplitMix64 逐位复算）**上摩擦最小，而 `ADR-0003` 的护栏本就写明**同语言不解锁共享 DTO**。

## 备选方案

- **多主写入 / 跨区域双写 `revision`**（含全球多活、多区强一致、CRDT） — 账号级严格单调计数器在多主下无法维持。
- **DynamoDB 及任何单条记录硬上限 < 512 KB 的 KV** — 把软告警阈值抬成硬失败，失败面是玩家进度。
- **靠 MySQL 的 JSON 合并原语承担浅合并** — 原语语义不对，浅合并须应用层手写，承重语义降级为代码纪律。
- **MongoDB / 文档数据库承载 profile** — 三处写入跨集合、要求全局唯一键；分片集群上多文档事务代价高于单库关系型。
- **Serverless 函数 + 托管 Postgres** — 连接数需代理层、冷启动使 push 的 p99 不可控、长时 / 定时任务需另接调度。**保留为取向的备选，不是硬淘汰。**
- **单台 VM 自建全栈** — 备份 / 时间点恢复 / 故障切换全部自建，无法满足 `ADR-0009` O3 的可演练恢复。
- **Go** — 枚举名逐字对齐要手写四套常量与映射，与客户端两套心智。
- **Node / TypeScript** — SplitMix64 的 `uint64` 环上运算必须走 `BigInt`，而契约要求逐位一致且已用测试向量把「差一位」定为红线。
- **引入消息队列做 push 异步落库** — 当场破坏线性化读改写与「push 应答必须回新 `revision`」的同步语义。
- **把 `push_idem` / `receipt_idem` 放独立 KV** — 违反「须与计数器自增同一次事务」，引入分布式事务或「`revision` 已 `+1` 但幂等记录未落」这一失败态。
- **按账号分片以求水平扩展** — 契约定义的流量形状下不需要；分片会让全局唯一 `receiptId` 变难。
- **读写分离：pull 打只读副本** — 直接违反 `ADR-0013`；失败形态即「玩家付了钱、客户端判定无待兑现且不再重试」。
- **用 `revision` 下界等待兑现读己所写** — 契约允许，但要求读路径携带并理解下界、副本暴露复制位点、失败时退化回主；「读全走主」是同一条要求更简单的兑现。
- **三套云上环境与三条分支一一对应** — 必须与生产同构的是 testing，不是 feature；换来固定成本减少约三分之一。

## 后果

- 全部权威状态单库 ⇒ **零分布式事务**；`ADR-0013` 的「同一次事务」与 `ADR-0008` 的 CAS 判定都落在本地事务上。
- **扩展方向被锁死为纵向扩容 + 按 `accountId` 单主分区**；放弃水平扩展预支、跨区多活与读写分离的成本收益。海外扩展是另一套独立部署 + 独立 `accountId` 空间，不是本套的跨境拉伸。
- 后端也用 C# 会诱发对 `ADR-0003` 的复议压力，故在 `operations/deployment.md` **显式引一次**「同语言不解锁共享 DTO」的护栏，且**只挂一处**。
- **报文零改动、无客户端义务**——本决策不产生任何跨库承接项。
- 解锁 `systems/`（3 份）与 `operations/`（8 份）的展开；仍待成本模型的只剩副本数 / 保留期这一类数值 → `open-questions/06-platform-stack.md`。
