# ADR-0102 — sync 缓冲闸门的「存档点」口径 = 事件级存档点

- **状态：** Accepted
- **日期：** 2026-08-06
- **来源：** handoffs/2026-08-06-ch1-band-widening-cross-realm-crush-and-chapter-retry.md

## 背景

断线缓冲的软阻塞闸门写作「未同步的自动存档点数 ≥ 3」。而决策点存档落地后，一场战斗的决策点密度估算约 **31 点**——按字面口径，一场战斗打到第三个决策点就会触发软阻塞模态。这显然不是该闸门的本意。

## 决策

闸门中的「存档点」**口径收窄为事件级存档点**：轮回开始 / 每个 AdventureEvent 结算后 / 篇章边界 / 轮回结束这四类，**不含事件推进过程中的决策点存档**。

口径与两个闸门的完整形态 → `systems/services/sync-service.md`「缓冲上限（两个闸门，先到先触发）」。

## 理由

它把「存档点与 push 解耦」这条既定分工贯彻到闸门口径上：既有定案已说「每个点立即原子写本地缓存，受频率约束的只是网络 push」，本条进一步明确**闸门计的是 push 单位，不是本地写入单位**。

决策点存档因此回归其本职——纯本地的崩溃恢复与防重掷手段：不驱动 push、不计入缓冲闸门、不影响断线判定。

两个闸门的语义就此对齐：另一个闸门（最早待发变更滞留 ≥ 180 秒）本就是时间口径，事件级口径下二者都以事件级 push 为单位。软阻塞的触发时机也自动对齐——事件级口径下闸门只可能在事件边界被撞上，规则与触发时机不必再各说一次。

## 备选方案

- **保留「一切存档点都计数」的字面口径、把阈值从 3 抬高到覆盖决策点密度** — 否决：阈值随决策点密度浮动，而决策点密度是玩法设计的自由度；这会把一条网络策略绑死在战斗设计上。
- **让决策点存档也驱动 push** — 否决：与「存档点与 push 解耦」直接冲突，且 31 点/场的 push 频率不可接受。

## 后果

- `systems/services/sync-service.md` 是闸门口径的权威；`systems/services/life-cycle-service.md` 的存档点清单与之对位。
- 「决策点粒度决定 push 防抖压力」这句话作废——粒度只影响本地写入频率（毫秒级、无流量顾虑）。
- 软阻塞模态的呈现时机 → `ux/error-and-blocking-ux.md`。
- 批次层的储物袋操作是事件之外的第三类提交，其 push 调度另行定义 → `ADR-0122`。
