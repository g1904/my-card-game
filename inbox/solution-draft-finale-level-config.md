# 方案草稿 — Finale 等级改配置表（值取当前行为）

## 问题

`systems/balance.md` 在 `combatTier` 三档参数一节里**自己写下并加了 ⚠ 标记**：

> **⚠ Finale 的难度不再有专属旋钮（明写，避免有人去找一个不存在的旋钮）。** 两重压迫都不可单独调：(a) 动 `baseMomentum` 会同时改变全部战斗的起跑线，(b) 是二值的。`WinMargin` 在该档恒为 0；剧本侧的 `EncounterTighten` 对该档**整档豁免**…故剧本也够不着这一档。**校准 Finale 难度只有三条替代手段**…**① 天劫的赋级带位置**（`±2` 带内的权重偏移）· **② 天劫定制卡组的强度** · **③ `TurnLimit`**。

**其中手段 ① 事实上是死的。** 同一份文件在赋级分布权重一节写着：

> **Finale 不掷骰**（天劫是指派，恒为 `diff = +1` 且必然越阶）。

**不掷骰就没有权重可偏移。** 两处并存导致：三条校准手段实际只剩两条（卡组强度、`TurnLimit`），而后者一动就要连带重估「12 回合是给 build 表达自己的窗口」那条论据。**Finale 是全作压迫顶点、又是篇章推进的唯一闸门，却是三档里校准余地最小的一档。**

## 约束（来自既有设计）

- **Finale 的等级已经是「指派」而非掷骰** —— `systems/balance.md`：「Finale 不掷骰（天劫是指派，恒为 `diff = +1`）」。本方案不改变通道，只改变取值的来源。
- **`±2` 是无例外的硬规则** —— `decisions/ADR-0044-enemy-leveling-band.md`：赋级函数不接受任何区间覆盖参数，**天劫亦不例外**。其最强论据即「全作最凶的天劫都不享有等级规则上的例外」。
- **`ADR-0018` 的「扣寿元不设上限截断」以 `±2` 封住最坏落差为前提** —— 「一次惨败打穿耐久已由赋级规则在规则层封住…扣减侧不必再加第二道护栏」。
- **平衡资源是唯一配置层** —— `decisions/ADR-0074-balance-resource-is-the-only-config-layer.md`；赋级带边界已住 `EnemyLevelingData`，「服务配置」这一层在本库不存在。
- **有跨字段不变式的同住一份** —— `systems/balance.md` 对 `AiWeightMin/Max` 与默认向量的既有判据。
- **`diff = +1` 承载着一条自洽性验证** —— 角色在境界巅峰（13 / 17 / 21），天劫在下一境界初期（14 / 18 / 22），故「渡劫 = 突破到下一境界」这句叙事不需要为它开任何规则口子。
- **先定形状、后定数值** —— `vision/scope.md:52`：本阶段只立形状锚点，取值留待内容扩充后的统计校准。

## 建议方案

### 1. 等级来源 = 配置值，不是硬编码常数

`[既有推演]`

在 `EnemyLevelingData` 的既有 `EnemyLevelRange` 行上**增一格 `FinaleLevel : int`**（该篇章天劫的**绝对全局等级**）。物化 Finale 时读这一格指派，取代当前硬编码的「角色等级 `+1`」。

- **落点推演，不是选择**：`ADR-0074` 定死平衡资源是唯一配置层；而 `FinaleLevel` 与同行的带边界之间**有跨字段不变式**（见建议 3 的校验），按本库既有的「有跨字段不变式的同住一份」判据，它**不容拆成第二份资源**。
- **通道不变**：Finale 本就是指派、不掷骰，本方案只把被指派的值从常数换成配置。**赋级函数仍不接受任何区间覆盖参数**——`FinaleLevel` 不是传给赋级函数的参数，而是 Finale 这条既有旁路自己的取值来源。

### 2. 值取当前行为，行为零变化

`[既有推演]`

| 篇章 | `FinaleLevel` | 对应境界 | 角色在境界巅峰时的 `diff` | 开局落差（道念） |
|---|---|---|---|---|
| ch1 | **14** | 筑基初期 | +1 | **5** |
| ch2 | **18** | 金丹初期 | +1 | **13** |
| ch3 | **22** | 元婴初期 | +1 | **25** |

三个值**恰好等于今天的运行结果**（`systems/balance.md`：「通过 Finale 所需追回的道念点数…ch1 5 / ch2 13 / ch3 25」）。

- **`diff = +1` 的自洽性验证原样成立**——「渡劫 = 突破到下一境界」的叙事不受任何影响。
- **本次改动因此是纯结构性的：装上旋钮，不拧它。** 玩家侧零可感知变化，平衡侧零重算。

### 3. 取值域由加载期校验锁死在 `±2` 带内 —— 让「零冲突」成为机械保证

`[既有推演]` · **承重**

**只装表不设界，等于开了一个「可以调到带外」的口子，即使今天没人拧它。** 本库对这类口子的既定收口方式是不给。故：

> `FinaleLevel` 须落在 **`[该篇章末级 − 2, 该篇章末级 + 2]`** 内（ch1 末级 13 → `[11, 15]`；ch2 17 → `[15, 19]`；ch3 21 → `[19, 22]`，全局序 1–22 截断），越界 **`PushError` + 抛**，带篇章号与取值。

- **`ADR-0044` 因此一个字都不用改。** 「任何调制源都不得产出带外 `diff`」在本方案下**仍然成立**——校验把它变成了加载期可机械核对的事实，而不再只是一句约定。
- **`ADR-0018` 的护栏论证同样不动**：最坏落差仍由 `±2` 界定。
- **代价明写**：这条校验把本方案的调节幅度限制在 `±2` 带内。想把天劫调到带外（例如做成 Balatro ante 式的绝对递增线）**必须先改 `ADR-0044`**——那是一次显式的、有实测数据支撑的决策，不是顺手改个数。**这正是本方案要的：把「日后可能想做的事」与「今天要做的事」切开。**

### 4. 顺带消解 `balance.md` 的一处内部不一致

`[既有推演]`

三条校准手段中的 **① 改述为「调本篇章的 `FinaleLevel`」**，它从此是一条真手段。「Finale 不掷骰」那句保持不变（本方案不引入掷骰），两处不再互相抵消。

`balance.md` 的 ⚠ 段落随之由「Finale 的难度不再有专属旋钮」改写为「**Finale 有一个专属旋钮 `FinaleLevel`，其余两条 (a)(b) 仍不可单独调**」。

## 具体形态（可 derive 的落地面）

在 `EnemyLevelingData` 的既有行类型上增一格（其余字段与语义**保持原样，本方案不触碰**）：

```csharp
[GlobalClass]
public partial class EnemyLevelRange : Resource   // 既有类型，本方案只增最后一格
{
    // ── 既有字段（带边界 + 带内逐档权重）原样保留 ──
    [Export] public int   FinaleLevel { get; set; }   // 本篇章天劫的绝对全局等级；初值 ch1 14 / ch2 18 / ch3 22
}
```

**加载期校验（`PushError` + 抛，均带篇章号与取值）：**

| 违规 | 理由 |
|---|---|
| `FinaleLevel` 落在 `[该篇章末级 − Upper, 该篇章末级 + Upper]` 之外 | 建议 3 的承重纪律；越界即 `ADR-0044` 失效而无人察觉 |
| `FinaleLevel` 不在全局序 `[1, 22]` 内 | 无对应 `baseMomentum` |
| 某篇章行缺 `FinaleLevel`（未赋值 / 为 0） | 静默取 0 会让天劫 `baseMomentum` 读不出 |

> **校验的上界直接读同一行的 `Upper`，不写字面量 `2`**——两者同住一份正是为此；写死 `2` 会在日后调整带宽时静默失配。

**物化侧**：`systems/services/future-event-service.md` 中 Finale 的赋级措辞由「恒为 `diff = +1`」改为「读本篇章的 `FinaleLevel` 指派」。伪码与十步管线其余部分不变。

## 后果

**改动面（三份文档，均为措辞与表格）：**
- `systems/balance.md` —— 增 `FinaleLevel` 一格与初值表；⚠ 段落改写；校准手段 ① 改述。
- `systems/adventure-event/combat/_index.md` —— 「天劫同受赋级约束，无等级规则上的例外」一句需补明「其等级由 `FinaleLevel` 指派，取值受同一条 `±2` 纪律约束」。
- `systems/services/future-event-service.md` —— Finale 赋级来源的一句措辞。

**明确不需要的（这是本方案的全部价值所在）：**

| 项 | 状态 |
|---|---|
| `CharacterProfile` 新字段 / 存档 schema bump | **不需要** |
| 存档迁移 | **不需要** |
| 新的内容条目（事件 / 敌人） | **不需要** |
| `eventPriority` 抬升清单变更 | **不需要** |
| `ADR-0044` / `ADR-0018` 订正 | **不需要**（由建议 3 的校验保证） |
| 平衡数值重算 | **不需要**（值取当前行为） |
| 玩家侧可感知变化 | **无** |

**风险面**：接近于零。唯一的实质风险是 `FinaleLevel` 被误填而绕过校验——已由加载期三条校验覆盖，且违规即启动期大声失败。

## 备选方案（已考虑并否决）

- **维持硬编码 `+1`** —— 否决：`balance.md` 已自陈这是一个缺口并加了 ⚠；且校准手段 ① 会继续是一条死手段，日后有人照它去找权重偏移会白跑一趟。
- **整体上调 `baseMomentum` 表** —— 否决：会同时改变全部战斗的起跑线，`balance.md` 已明确点名不可用。
- **改 `TurnLimit` 校准 Finale** —— 不否决（它是既有手段 ③），但一动就要连带重估「12 回合是 build 的表达窗口」那条论据，代价高于调一个等级值。
- **扩成完整的绝对递增阶梯**（篇章内增设对位 small / big blind 的必经节点、等级出 `±2` 带、新增篇章计数器）—— **本次不做**。它需要订正 `ADR-0044`、重述 `ADR-0018` 的护栏、bump 存档 schema、新增 6 个内容条目，并放宽 `eventPriority` 抬升判据 (c)。**它解决的是「篇章中段的难度是一条平的跑步机」这个问题，而该问题是否真实存在须由 ch1 可运行后的实测回答**（`vision/scope.md:53`：数值定标归第 3 阶段）。本方案是它的严格子集，**不构成阻碍**：日后若实测确认需要，改的是建议 3 那条校验的上界，而不是推翻本方案。

## 与既有决策的张力

**无。** 建议 3 的取值域校验使 `FinaleLevel` 恒落在 `±2` 带内，`ADR-0044` 的「无例外硬规则」与 `ADR-0018` 的护栏论证**均不受影响**；`diff = +1` 的自洽性验证在初值下原样成立。

## 前置依赖

**无。** 本方案不引入任何待校准数值——三个初值取当前行为。日后要拧这个旋钮时，其取值与本库多条初值同一处前置依赖（卡牌道念量纲、`lossPerMomentum` 的 ch2 / ch3 系数），但**那是调值时的依赖，不是落地本结构的依赖**。

## 仍需用户决定

**无。** 本方案的每一项均由既有决策推演得出：落点由 `ADR-0074` 加「跨字段不变式同住一份」判据定死，取值由「值取当前行为」定死，取值域由「不给口子」这条既定收口方式定死。
