# 方案草稿 — flags 拉取的频次护栏

## 问题

`X-Flags-Version` 随**任意一次应答**下发（后端 `envelope.md` §4b），客户端既定规则是：共享应答头处理点观察到它**与内存值不同**即拉一次全量 flags（`systems/services/content-service.md`）。稳态下上行约每分钟一次，代价可忽略——但「不同即拉」这条规则**对失败与异常没有任何护栏**：

- 拉取**失败**时内存值不变 ⇒ 下一次任意应答**再次**触发拉取 ⇒ 在后端持续不可用时形成一条**紧跟每次业务请求的失败重试链**（一次 push 一次 flags，且每次都白费）。
- 观测值**小于**内存值时（灰度分桶串号、中间层缓存了旧应答——正是契约点名要防的那类事故）当前会**触发一次回退拉取**，且**静默发生**，线上无任何痕迹。
- 运营在几分钟内连发数批 flags 时，每一批都会被拉一次；这本身是**正确行为**（每一批都是真实变更），但没有任何一处声明过它是有意的。

## 约束（来自既有设计）

- **`flagsVersion` 单调递增**——由后端契约钉死（`backend-design-documents/contracts/content-manifest.md` flags 报文表：「本批开关的版本，**单调递增**；由信封搭载给客户端做变更检测」）。
- **秒关的实际延迟 = 该玩家的下一次上行，分钟级以内**；这是 flags 通道存在的**全部理由**（`content-service.md`）。
- **零轮询、不引入长连接 / 第三方推送**（同上）。
- **flags 拉取失败绝不阻塞**：`PushWarning` + 降级到 `user://cache/flags.json`（无缓存则用 overlay 的 `ContentEnabled`）（同上，API 面表）。
- **验签失败 / `keyId` 未知 → `PushError` + 拒绝该批 + 保留上一批 + 上报一次**（同上）——与拉取失败是两条不同的路径。
- **判断在服务内，不在观测者**：`OnFlagsVersionObserved(int)` 的既定纪律是「观测者不判断要不要拉，判断在本服务内——否则每个 backend 各写一份判断」。
- **可调数值不硬编码**，归 `systems/balance.md`「同步 / 内容管线旋钮」（既有 9 行，含 overlay 下载重试 3 次 / 1s·2s·4s）。

## 建议方案

### 1. 成功路径的护栏 = **单调闸门**（只在观测值 **>** 内存值时拉），**不设最小拉取间隔**

`[既有推演]`

`flagsVersion` 由契约保证单调递增 ⇒ 「不同」与「增大」在正常情况下**等价**，而在异常情况下**不等价**。把规则从「不同即拉」收紧为「**增大**即拉」，收益是三条、代价是零：

- **回退拉取被关死。** 观测到更小的版本只可能来自事故（灰度串号 / 中间层缓存旧应答）；按旧规则会把一个**已经正确的本地 flags** 换成一批过时的，即**已被秒关的内容当场复活**——这正是 flags 通道要防的那件事本身。
- **异常获得可见性（本子项最有价值的一条）：** 观测值 **<** 内存值 ⇒ **不拉** + `GD.PushWarning` 带两个数值。它把一类**只在放量时显形且极难定位**的事故（契约原话）从静默行为变成一条日志。**建议按会话去重、只报一次**，避免旧应答持续到达时刷屏。
- **等值不拉**（既定，不变）。

**不设最小拉取间隔（成功路径），三条理由：**

1. **单调闸门已经界定了上界：** 每一次拉取都对应一个**真实的、更高的**版本批次，拉取次数不可能超过运营发布批次数。稳态是**每天个位数**，而节流要防的是「每分钟数十次」——**那个形态在单调闸门下不可达**。
2. **节流直接伤害通道的唯一价值。** 秒关延迟被定为「分钟级以内」；一个 N 分钟的最小间隔就是把秒关延迟抬到 N 分钟，**且恰好在运营连发多批（= 正在处理线上事故）时最伤**。
3. **一次 flags 拉取是一个小 JSON + 一次验签**，与它守护的东西（线上放量开关正确性）不在同一量级。

### 2. 单飞（single-flight）+ 尾随一次

`[通行做法]` 这是「不设间隔」的必要配套，也是**真正会发生**的并发面：一次拉取在途时又观测到更高版本（上行频次高于一次 flags 往返时）。

> **同一时刻至多一次在途的 flags 拉取。** 在途期间观测到更高版本 → **不发第二次请求**，只记下「最高已观测版本」；本次拉取结束后，若内存值仍低于它 → **再拉一次**（尾随一次，不排队、不累积）。

- 不设队列：中间被跳过的版本**无需补拉**——flags 是**全量快照**（`disabledIds` 是已按当前账号解析完毕的完整结果），最新一批天然覆盖此前所有批次。
- 这条同时消化了「运营连发多批」的场景：连发 5 批只会产生 2 次请求（首次 + 尾随一次）。

### 3. 失败路径才是护栏该在的地方：**指数退避**

`[既有推演]` 拉取失败时内存值不变 ⇒ **每一次后续应答都会重新触发**。这不是理论问题：后端不可用期间，客户端每分钟一次上行就是每分钟一次必然失败的 flags 请求，且**每一次都白费**。

> **flags 拉取连续失败时进入指数退避；退避窗口内的版本观测只更新「最高已观测版本」，不发请求。一次成功即清零阶梯。**

- **形态沿用既有的 overlay 下载退避**（`1s · 2s · 4s`，见 `balance.md`），**但不设放弃阈值**：flags 是长期在线的通道，「放弃」意味着这台设备此后再也不同步开关。**改为以上限封顶**（建议 60 s），与 push 退避「无放弃阈值、以上限封顶」同构。
- **退避期间不降级、不改变行为**：已定的降级（用 `user://cache/flags.json` 的上一批）在**首次失败时**就已生效，退避只影响**重试节奏**，不影响生效值。
- **验签失败不走退避**：它已定「拒绝该批 + 保留上一批 + `PushError` + 上报一次」。重发同一批必然再次验签失败 ⇒ 建议**该 `flagsVersion` 在本次会话内不再重试**（与 `Upgrade` 类错误「重试必然失败 ⇒ 暂停退避」同一条判据），直到观测到**更高**的版本。**这是与网络失败的关键区别，须明写。**

### 4. 首次拉取与切账号：由内存初值自然覆盖，不新增分支

`[既有推演]`

- **内存 `FlagsVersion` 初值 = `0`**（契约的 `flagsVersion` 是正整数），故启动后的首次观测必然「增大」⇒ 必拉。**这与既定的「首次拉取排在登录之后、由 Bootstrap 显式调用」不冲突**：那是启动链的显式一步，本条只保证「即使它没跑，第一次应答也会补上」。
- **切账号：`flags.json` 带 `accountId` ⇒ 丢弃 / 重建**（既定）⇒ 内存值归 `0` ⇒ 下一次观测必然增大 ⇒ 必拉。**flags 是按账号解析的结果，切账号后旧值一秒都不该继续生效**，本条保证了这一点，无需新增分支。
- **退避阶梯与「最高已观测版本」在切账号时一并清零**——它们是账号维度的运行态。

## 具体形态（可 derive 的落地面）

**`OnFlagsVersionObserved(int observed)` 的完整判定（判断全在本服务内，既定纪律不变）：**

```
observed == FlagsVersion            → 什么都不做
observed <  FlagsVersion            → PushWarning(observed, FlagsVersion)【本会话去重，只报一次】；不拉
observed >  FlagsVersion            →
    记 _highestObserved = max(_highestObserved, observed)
    若 有拉取在途                    → 返回（结束时若 FlagsVersion < _highestObserved 则尾随一次）
    若 在退避窗口内                  → 返回（窗口到期时若仍落后则拉）
    若 observed 已因验签失败被拒绝    → 返回（等更高版本）
    否则                            → 拉一次
拉取结束：
    成功  → FlagsVersion = 新值；退避阶梯清零；若仍 < _highestObserved 则尾随一次
    网络失败 → PushWarning + 保持既有降级值 + 退避阶梯 +1
    验签失败 → PushError + 上报一次 + 拒绝该批 + 保留上一批 + 记下该 flagsVersion 本会话不再重试
```

**API 面：零改动。** `RefreshFlagsAsync` / `OnFlagsVersionObserved` / `FlagsVersion` 三者签名与既定语义一字不变；新增的三样运行态（`_highestObserved`、退避阶梯、验签失败版本记忆）**全部是 `ContentService` 私有**，不出 API 面、不落盘、不进 Profile。

**`systems/balance.md`「同步 / 内容管线旋钮」新增两行：**

| 旋钮 | 初值 | 归属 |
|---|---|---|
| flags 拉取失败退避（底数 / 因子） | **1 s 起 · ×2** | `systems/services/content-service.md` |
| flags 拉取失败退避上限（cap） | **60 s**（无放弃阈值） | 同上 |

**存档 schema / 缓存文件 / 后端：零影响。** `flags.json` 字段面不变；后端零新增义务（`flagsVersion` 单调递增本就是契约既有条款，本方案只是**开始依赖**它）。

## 后果

- 「不同即拉」这句在 `content-service.md` 中被改写为「**增大即拉**」，并补上三条（单飞 / 退避 / 回退观测告警）。
- **客户端开始依赖「`flagsVersion` 单调递增」这条契约条款。** 该条款已成文，但此前客户端行为不依赖它；采纳后**后端非单调地发布一批 flags = 客户端不再更新开关**，且症状是「秒关不生效」。建议在 `content-service.md` 明写这条依赖并回链契约，**无需后端改动**。
- 退避与单飞是三样纯私有运行态，不触及任何契约、缓存或存档。

## 备选方案（已考虑并否决）

- **成功路径加最小拉取间隔（节流）** — 直接把秒关延迟从「分钟级」抬到「间隔级」，且恰好在运营连发多批（= 正在处理线上事故）时最伤；而单调闸门已经把拉取次数上界压到发布批次数。
- **保留「不同即拉」** — 观测到更小的版本会把已生效的正确 flags 换成过时的一批 ⇒ **已被秒关的内容当场复活**，且静默发生。
- **观测到更小版本时静默忽略（不告警）** — 那正是契约点名「只在放量时显形且极难定位」的事故类型，静默等于放弃唯一的发现机会。
- **失败后不退避、靠下一次应答自然重试** — 后端不可用期间会形成「每次业务请求跟一次必然失败的 flags 请求」的链，白费流量与电量。
- **失败退避设放弃阈值** — 放弃 = 这台设备此后永不同步开关；与 push 退避「无放弃阈值、以上限封顶」的既定形态不一致。
- **验签失败也走网络退避** — 重发同一批必然再次失败，与「`Upgrade` 类错误重试必然失败 ⇒ 暂停退避」同一条判据。
- **缓存中间被跳过的版本 / 排队补拉** — flags 是全量快照，最新一批天然覆盖此前全部；补拉是纯浪费。
- **把判断挪到共享应答头处理点** — 违反既定纪律「观测者不判断要不要拉，判断在本服务内」（否则每个 backend 各写一份）。

## 与既有决策的张力

**无。** 三条既定语义（零轮询 · 秒关分钟级 · 失败不阻塞）全部原样成立，本方案只在其内部补护栏。唯一新增的是**对契约条款「`flagsVersion` 单调递增」的行为依赖**——它是既有条款而非新要求，故不构成跨库变更，只需在本库明写依赖并回链（见「后果」）。

## 前置依赖

**无。** 本问题整体属客户端侧（判定发生在 `ContentService` 内部），后端无承接项。

## 仍需用户决定 → **已全部裁决（2026-08-22 · 批量评审）**

> 逐条裁决（`/batch-provide-solution-draft` 合并 interview · 两项均为轻级，用户在打包轮中一并按推荐裁定）：
> 1. 退避上限取值 → **A · 60 s**（与 push 退避 cap 同值）`[采纳推荐 — 待复核]`
> 2. 观测到更小版本时的告警去重口径 → **A · 本会话只报一次** `[采纳推荐 — 待复核]`


1. **退避上限取值**（`[取向选择]`，轻）
   - **A（推荐）—— 60 s**：与 push 退避 cap 同值，便于记忆与统一配表；flags 通道的延迟容忍度本就以分钟计。
   - **B —— 更短（如 30 s）**：后端恢复后开关生效更快，代价是不可用期间多打一倍请求。
   - 二者均属**待实测校准的初值**，落 `balance.md` 可随时调，不影响任何结构。
2. **观测到更小版本时的告警去重口径**（`[取向选择]`，轻）
   - **A（推荐）—— 本会话只报一次**：中间层缓存了旧应答时，旧值可能持续到达数十次，逐次告警会淹没日志。
   - **B —— 每次都报**：便于从日志估算事故规模。
   - **C —— 按 (observed, FlagsVersion) 对去重**：折中，但多一层状态；对一个诊断日志而言不划算。
