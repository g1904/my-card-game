# 方案草稿 — 存档 schema bump 的登记（后端半：兼容矩阵的输入、触发点与漏登护栏）

## 问题

`schemaVersion` 是**上行负载自身的版本**，其结构权威在客户端（`envelope.md` §8 明写「契约不把 Profile 的字段表抄进本库」）。后端对它只做一件事：**判定它在不在兼容集合内**（`profile-sync.md` §4，越出即 `sync.payload_schema_unsupported`），而兼容集合的落点是 `operations/version-matrix.md`。

今天这一格是**空的**：

| 项 | 当前值 |
|---|---|
| `schemaVersion` 集合 | **待客户端清单补齐** |

而对侧那份「客户端清单」本身**已被证实存在大量漏登**（数量与逐条内容见 counterpart，本库不复述）。于是形成一个双向账目漏洞：

- 后端把 bump 的登记权威指向客户端（`profile-sync.md` §189 明写「bump 清单的权威在客户端 `sync-service.md`，本库只声明须与之同批」）；
- 客户端那份清单不完整，且客户端库内另有 11 处平行自称；
- **两侧都以为对方在记。**

本库要答的三问是：① 矩阵的 `schemaVersion` 集合**从哪里、在什么时点**取得输入，而**不复述**客户端的清单内容；② 登记的责任人是谁；③ 客户端 bump 了却没有触发本库登记时，**后端靠什么机制发现**（而不是靠玩家报障）。

> **一处事实更正（供评审核对）。** 派单摘要称「`envelope.md` §7e 的版本兼容矩阵内容全空」。**核实后并非如此**：§7e 是一条**指路条款**（「兼容矩阵由后端单点维护 · 落点 `operations/` · 至少含四项 · 客户端不持有任何副本」），内容完整且不需要改写。真正为空的是 `operations/version-matrix.md`「当前矩阵」表格里的两格（`appVersion` 下界 = 待定 · `schemaVersion` 集合 = 待客户端清单补齐）。本方案因此**不动 §7e 的语义**，只建议补一句指向本方案新增的登记流程。

## 约束（来自既有设计）

1. **后端对 Profile 半透明，且明确拒绝抄客户端 schema。** `envelope.md` §8：「契约**不把 Profile 的字段表抄进本库**——那会当场制造两份真值，并违反『不复述另一侧的设计』」。⇒ 矩阵里能出现的只有**版本号与下线计划**，不可能出现「第 N 版含哪些字段」。
2. **矩阵由后端单点维护，客户端不持副本**（`envelope.md` §7e · `version-matrix.md`「形态」）。
3. **矩阵的数据形态即旋钮表的一员，落 `config_knob`，改值不发版**（`version-matrix.md`「形态」· `environments.md`）。
4. **`schemaVersion` 闸门的判定位次已定**：`schemaVersion` 闸门 → 信封形状 → CAS → 回声校验 → 写入；**越界不消耗 revision**（`profile-sync.md` §4）。
5. **越界的错误码与 class 已定**：`sync.payload_schema_unsupported`（`class: Upgrade`，`detail.supportedSchemaVersions`），且按 `envelope.md` §7c **不硬阻塞**——客户端保留待发队列 + 非模态提示 + **暂停退避重试**。
6. **下线一版是既定纪律**：先把下界提上去，等存量会话自然翻转，再删实现分支（`version-matrix.md`「运维流程」）。
7. **契约变更的完成判据已成文**（`contracts/_index.md`）：**变更内原子**（只改一边视为未完成）· **责任人 = 发起该次变更的那一侧** · 不设周期性对账（理由：周期性对账允许漂移窗口存在，而那个窗口正是两侧按不同真值编码的时期）。
8. **错误码台账已有同构的登记流程**（`operations/_index.md`）：新增 `code` 是契约变更，**先文档 → 后 spec → 后实现**，且「台账 ⇔ spec 枚举双向一一对应」是一条机检断言，**理由是它的漂移形态是静默的**。
9. **跨边界承接分片的形态已定**（`open-questions/cross-boundary.md`）：固定四段式 `客户端权威文档路径#小节 | 客户端定案日期 | 本库需改的文档 | 一句话摘要`，**只回链、不复述**，关闭条件 = 本库落笔完成。
10. **观测面已有一张探针表**（`observability.md`），且已有一行阈值 = 0 的「不可能态即告警」先例（`sync.revision_ahead`）与一行「只记账不拒绝 ⇒ 告警是唯一可见面」先例（透明路径缺失）。

## 建议方案

### 1. 矩阵的 `schemaVersion` 集合改成一版一行的子表，只登**数字与运维事实**

`[既有推演]`（约束 1 + 2 + 6）

`version-matrix.md`「当前矩阵」里的单格「`schemaVersion` 集合」建议展开为一张子表——**四列全部是本库自己持有真值的东西**，一列都不描述该版本「含什么字段」：

| `schemaVersion` | 接受起始 | 下线计划 | 客户端登记回链 |
|---|---|---|---|
| （待首个版本产生） | — | — | `game-design-documents/systems/services/sync-service.md`#`schemaVersion` 登记表 |

- **第四列是回链，不是摘要。** 想知道第 N 版改了什么 → 点过去看客户端登记表。本库**一个字段名都不写**。判据即约束 1 —— 这与 §5 白名单的处理方式**不同且刻意不同**：白名单里的 JSON path 是后端**自己要读**的东西（复算输入），故它进本库；而「第 N 版新增了 `pastItemUse` 列」后端根本不读（不透明段），抄进来只会多一份必然漂移的真值。
- **「接受起始」记的是本库开始接受该版本的时刻 / 配置版本**，不是客户端发版时刻——后者是对侧的事实。
- **下线计划照既定纪律填**（先提下界、等存量会话翻转、再删实现分支），不新增语义。

### 2. 登记触发点 = 对侧登记表新增一行时，经既有的跨边界承接分片成对触发

`[既有推演]`（约束 7 + 9）

- **触发信号：** 客户端的 `schemaVersion` 登记表新增一行（= 一次 bump 定案）。
- **承载：** 在本库 `open-questions/cross-boundary.md`「待承接」区落一条标准四段式条目。**这是零新增机制** —— 该分片存在的全部理由就是承接这类「对侧已定案、本库尚未落笔」的事，而它今天恰好是空的。
- **责任人（两段，不是一段）：**
  - **开条目**归**发起该次变更的那一侧**（约束 7）。schema bump 的发起方**恒为客户端**（Profile 是客户端定义的类模型），故恒由客户端在本库开承接条目。
  - **落笔矩阵**归后端 —— 矩阵是本库单点维护的对象。
- **关闭条件照分片既定：** 矩阵已登记该版本（对应 handoff `distilled`）后从「待承接」移除、记进 `answer-logs/`。
- **建议同时把这条纳入 `operations/_index.md`「已有具体对象的运维面：版本兼容矩阵与错误码台账」一节**，与已有的「错误码台账的登记流程」并列成第二条 —— 那一节此刻只写了 `code` 那一半，矩阵那一半只有形态没有流程。

### 3. 发布顺序纪律：**矩阵先加、客户端后发**

`[既有推演]`（约束 3 + 5 + 8）

后端补一个 `schemaVersion` 只需**改一次旋钮值、不发版**（约束 3）；而客户端发出一个后端不认识的 `schemaVersion` 的代价是**那批玩家的进度暂时上不去**（约束 5：不硬阻塞、但暂停重试、直到玩家更新并重新登录）。两边成本极不对称 ⇒ 顺序唯一合理：

> **新 `schemaVersion` 必须先进矩阵、再随客户端版本放量。**

这与错误码台账的「先文档 → 后 spec → 后实现」（约束 8）**是同一条纪律的第二个实例**，也与既定的下线纪律（先提下界、再删分支）方向一致——**加与减都是先动矩阵**。

### 4. 「客户端 bump 了但没告诉我」的处置：**照常拒绝 + 阈值 0 告警**

`[既有推演]`（约束 4 + 5 + 10）+ `[通行做法]`

分两条，必须一起读：

**4a. 判定不放松 —— 未知 `schemaVersion` 照常拒绝，绝不宽容接受。**

需要明写理由，因为本库**紧邻一条形态相似而结论相反**的条款：`profile-sync.md` §3 对未知 `reason` 取值是「记录原值、不改写、**不拒收**」。两者的判据差别是清晰的：

| | `reason` 未知取值 | `schemaVersion` 未知取值 |
|---|---|---|
| 该字段的判定权 | **零** —— 只作日志与聚合维度 | **有** —— 它是版本闸门本身的输入 |
| 宽容接受的后果 | 聚合维度里多一个孤儿取值，靠看板发现 | **一份后端不保证能正确解读的负载被写进云端**；下一次 pull 会把它发给可能更旧的另一台设备；且透明路径（复算输入）的位置不再有保证 |
| 结论 | 宽容 | **拒绝** |

⇒ 建议在 `profile-sync.md` §4 或 §3 的宽容语义旁补一句**明确的不对称声明**，避免日后有人把 `reason` 那条宽容推广过来。

**4b. 可见性 —— `observability.md` 探针表新增一行，阈值 0。**

| 探针 | 指标形态 | 告警口径 | 为什么是这个口径 |
|---|---|---|---|
| **未知 `schemaVersion`** `sync.payload_schema_unsupported` | 计数器，标签 `schema_version` + `app_version`（均低基数） | **阈值 = 0，任一次即告警**（首次出现某个未登记的 `schema_version` 值即叫人） | 它**唯一的合法成因**是「玩家用了一个已下线的旧版本」，而那种情形我方**本就知道自己下线了哪一版**；出现一个**从未登记过的新值**只可能是登记漏了 —— 与 `sync.revision_ahead` 同构（不可能态，不该有基线） |

- **告警内容须含 `schema_version` 与 `app_version` 两值**，因为处置完全分岔：值 > 已登记最大值 ⇒ **登记漏了，改旋钮即修复**；值 < 已登记最小值 ⇒ 旧客户端，属预期下线路径，**下调告警级别**。建议告警规则就按这条二分给出两级。
- **这条告警是本方案里唯一「机制发现」的兑现。** 没有它，漏登的表现是：一批玩家安静地上不去进度、客户端只出一条非模态提示（约束 5），**后端侧零信号** —— 与「透明路径缺失只记账不拒绝 ⇒ 告警是唯一可见面」那行是同一种失明。

### 5. 不在本方案范围内的两项（明写以免范围蔓延）

`[既有推演]`

- **`appVersion` 下界 = 「待定」不是设计缺口，是待落值** —— 无在架版本时它没有可填的值，且其运维流程已成文（闸门只在签发时判定 · 覆盖上限 = refresh 链绝对寿命上限）。本方案不动它。
- **`manifestSchema` 集合**同理，且它与 `schemaVersion` 的登记通道不同（内容管线侧，`content-manifest.md`），不并入本方案。

## 具体形态（可 derive 的落地面）

**① `operations/version-matrix.md`「当前矩阵」改动：** 单格「`schemaVersion` 集合 = 待客户端清单补齐」→ 展开为上文第 1 节的四列子表 + 一句「本表只登版本号与运维事实，该版本含什么结构改动见客户端登记表（回链），**本库不复述**」。

**② `operations/_index.md`「已有具体对象的运维面」段新增一条：**
> **`schemaVersion` 集合的登记流程。** 触发点 = 对侧登记表新增一行；承载 = `open-questions/cross-boundary.md` 待承接条目（四段式，只回链）；责任人 = 开条目归客户端（发起方）、落笔矩阵归后端；顺序 = **矩阵先加、客户端后发**（补一版只需改旋钮不发版，而反序的代价由玩家承担）。与错误码台账的登记流程并列。

**③ `operations/observability.md` 探针表新增一行**（形态见上文 4b），并在告警口径列写清「值 > 已登记最大值 ⇒ 工程告警（登记漏了）；值 < 已登记最小值 ⇒ 信息级（旧客户端，预期）」。

**④ `contracts/envelope.md` §7e 补一句**（**不改语义**）：兼容集合的**登记流程与触发点**见 `operations/version-matrix.md` 与 `operations/_index.md`。§7e 保持为指路条款。

**⑤ `contracts/profile-sync.md` 补一句不对称声明**（落在 §3 `reason` 宽容语义旁或 §4 拒绝面四类表下）：**`reason` 的宽容不适用于 `schemaVersion`**，判据 = 该字段有无判定权（对照表见上文 4a）。

**⑥ `open-questions/cross-boundary.md`：** 本方案被采纳时，「待承接」区落入的**不是**一条 schema 条目（此刻还没有任何 bump 需要承接），而是把上述①–⑤作为一次本库自己的落笔完成；此后每次对侧 bump 各落一条。**建议在该分片的说明区补一句**：`schemaVersion` bump 是本分片的一类**常规**触发源，条目形态照既定四段式。

## 后果

- **报文形态零改动**：不新增字段、不新增端点、不新增错误码（`sync.payload_schema_unsupported` 与其 `detail.supportedSchemaVersions` 原样够用）。⇒ **不需要 bump `openapi.yaml` 的 `info.version`**，也不触发 `contracts/_index.md` 的三条机检断言。
- **`config_knob` 多一项 / 一项的形状变化**（`schemaVersion` 集合由一个标量变为一张小表）。属既有旋钮表的一员，改值不发版。
- **观测面 +1 条告警规则**，需在 `deployment.md` 的告警配置里落地（栈已定，但本方案不指定具体实现）。
- **对侧同批采纳后**，本库的 `schemaVersion` 集合才第一次有值 —— 在此之前矩阵仍是「待首个版本产生」，但**流程已就位**，不再是「待客户端清单补齐」这种指向一份不存在之物的悬空表述。

## 备选方案（已考虑并否决）

- **把客户端的 bump 清单内容镜像进 `version-matrix.md`（每版含哪些字段）** — 直接违反 `envelope.md` §8 的「不把 Profile 字段表抄进本库」，且这正是本问题要修的病（第二权威）。
- **未知 `schemaVersion` 宽容接受、原样存起来**（照 `reason` 那条办） — 见 4a 对照表：`reason` 零判定权，`schemaVersion` 是闸门输入；宽容等于让一份不保证可解读的负载进云端，并把它 pull 给别的设备。
- **在 pull 侧也判一次 `schemaVersion`** — 已被 `profile-sync.md`「pull 侧不做版本闸门」明确否决（两个闸门、两套阈值）。本方案不重开。
- **靠周期性对账（每月比对两侧清单）发现漏登** — `contracts/_index.md` 已明确否决周期性对账：它允许漂移窗口存在，而那个窗口正是两侧按不同真值编码的时期。本方案改用「变更内原子 + 阈值 0 告警」。
- **把 `schemaVersion` 兼容判定前移到 `signin`（与强更闸门合并）** — `envelope.md` 备选清单已否决（需在登录请求额外声明 `schemaVersion`，且覆盖不到会话中途升级负载结构）。
- **后端自行探测客户端 schema 结构变化（解不透明段做 diff）** — 违反 pillar #1 与三段可见性分界，且技术上后端拿不到「应有形状」这个参照物。
- **不设告警，靠客服工单发现** — 客户端侧对该错误的处置是**非模态提示 + 暂停重试**（约束 5），玩家可能整个会话都不明确感知；工单量与故障量不成比例。

## 与既有决策的张力

**一处，程度轻，建议按「补充判据而非开例外」处理。**

`profile-sync.md` §3 的未知 `reason` 宽容语义写得相当有普适口吻（「因一个零判定权的字段取值不认识就拒收一次合法的进度上行，等于让它获得阻断玩家进度的能力」）。本方案第 4a 节对 `schemaVersion` 给出相反结论。

- **不构成真冲突** —— 该条款自己的论证里就写着限定语「**零判定权的**字段」，而 `schemaVersion` 有判定权。
- **但它今天没有明写「这条不适用于 `schemaVersion`」**，而两者在报文里恰好是负载信封的相邻两字段（`profile-sync.md` §3 同一张表的第 3、4 行）。读者按就近类推推广过去是很可能的。
- **建议的处置**是上文形态⑤：补一句显式的不对称声明 + 判据（有无判定权），**不改 `reason` 那条的任何措辞**。这与 `envelope.md` §4a 把「例外仅限 auth 域」改写为一条判据是同一种手法 —— 本库已行使过一次。

**不构成张力的两处（供评审确认）：** ① 本方案不改 `envelope.md` §7e 的任何语义；② 不改 `profile-sync.md` §4 的判定顺序与四类拒绝面。

## 前置依赖

## 仍需用户决定

**一条。**

### ① 未知 `schemaVersion` 告警的**分级判据**：按「与已登记集合的大小关系」自动二分，还是一律工程级？

- **选项 A（推荐）· 按大小关系二分。** 值 > 已登记最大值 ⇒ 工程告警叫人（登记漏了，改旋钮即修复）；值 < 已登记最小值 ⇒ 信息级、只上看板（旧客户端，是既定下线纪律的预期产物）。
  - **后果：** 告警噪声低，叫人的那一条几乎必然是真事故。代价是多一条规则逻辑，且**依赖矩阵是有序集合**（当前形态成立）。
- **选项 B · 一律工程级、阈值 0。** 与 `sync.revision_ahead` 那行逐字同款，最省事。
  - **后果：** 每一次正常的版本下线之后，存量旧客户端会持续制造工程告警，直到它们全部翻转（覆盖上限 = refresh 链绝对寿命）。**这段时间可能以周计**，而这类"预期中的持续告警"是把整张探针表训练成"可以忽略"的最快途径。
- **推荐 A，理由：** 本库已有一条同样处置的先例 —— 透明路径缺失那行的告警口径不是"任一次即告警"，而是带前提的「某条 `path` 的缺失率由近零跳到显著非零、且集中在某个 `app_version`」，**并附了一段 ⚠ 说明"不带这个前提，每一次普通 push 都会误报"**。旧客户端制造的 `schema_version` 越界与那里的"顶层键本就常常不出现"是同一类**预期噪声**，处理手法应当一致。

→ 已裁决（2026-09-03 · 批量评审）：**取选项 A —— 按与已登记集合的大小关系二分**。值 > 已登记最大值 ⇒ 工程告警叫人；值 < 已登记最小值 ⇒ 信息级、只上看板。**拒绝语义（4a）不变**，本裁决只作用于告警口径。
