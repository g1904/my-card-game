# 方案草稿 — 回寿法宝的总量护栏（内容编排面三格口径）

## 问题

储物袋不设容量上限之后，`ADR-0066` 原本的三道软闸少了一道（「补天丹占储物袋九格中的一格」整条作废，见 `answer-logs/log-0823e.md`），回寿法宝能囤多少被整体交给内容编排面：**出现频率 · 商店库存深度 · 定价**。三格至今全空。

它为什么承重：合并后寿元是角色**唯一的那条命**，同时承接「走路要花」与「打输要花」两个消耗面。规则层已明确不设持有上限，两道加载期校验（`Scope == Player` 且产 `LifeSpan` → 拒；产 `LifeSpan` 且 `UsableScene` 含 `InCombat` → 拒）管的只是条目合法性、不约束持有量。因此这三格是这条压力线的**唯一剩余数量闸**。

它卡住了什么：`systems/character-profile/life-span.md` 的回复侧验收断言无法先于它落案；`systems/balance.md` 的 λ 反推式里 `R_c`（本章回寿产出）当前**整格挂在事件侧**，道具侧一点预算都没有分到。

## 约束（来自既有设计）

- **不得引入计数器 / 存档字段 / 篇章配额。** 两处已定案的取向同向否决：`ADR-0066`「每篇章回寿总量硬上限 → 否决：需新存档字段与新校验」；`systems/balance.md:850`（`IgnoresProtection`）「**只有这两条规则，不加篇章配额 / 轮回内次数上限 / 加载期核对表**……完全落在内容编排层，不落代码」。本方案因此只用**内容编排口径 + 取池侧过滤**两种既有形态。
- **全库当前没有任何「某类条目在某通道至多出现 N 次」的机制**（既无 `OncePerRun`、无池内配额、无标签配额）。想要频率闸，只能落在**池占比 · `RarityTier` 档 · `SlotCount` · 定价**这四个既有旋钮上。
- **定价不得新开旋钮。** 「商品族 × 稀有度」25 格定价表已定（`ADR-0133` 不设篇章维），`ItemData` 上明写不加 `Price` / `Purchasable`。
- **补天丹只能以灵石计价。** 仙玉一格都不落 `CharacterItem` 族（`systems/balance.md`「仙玉一格都不落 `CharacterItem` 族」），这是关闭「售出产仙玉」的结构性手段。
- **回寿量三档 = 占本章可用预算 5% / 10% / 20%，ch1 折算 50 / 100 / 200**（`systems/balance.md`「回寿量」表）。
- **λ 反推式的 `R_c` = 100 / 116 / 317**，注解写「每章 2 次小档（5% × 本章预算）」——**全部记在事件侧**。它是 21 格 `lifeSpanCost` 定价表的输入之一。
- **`ItemChargeElement.Delta > 0` 当前是 `PushError`**（次数补充机制未设计）⇒ 回寿法宝的 `Charges` 不可被补充。
- **`PickMany` 无放回**是既定契约 ⇒ 同一批库存内不出现重复商品。
- 支柱侧的正面约束：`vision/pillars.md`「玩家权衡的是同一把尺子上的取舍（多走一步 vs 赌一场硬仗 vs **买回容错**）」——这一格不能被收到形同虚设。

## 建议方案

### 0. 先把账分清：`R_c` 拆成两格，Σ 不变

`[既有推演]`

**这是三格口径的共同分母，建议先落它。** 当前 λ 反推式里 `R_c` 整格挂在回寿事件上（「每章 2 次小档」），道具侧回寿因此是**账外增量**——一颗补天丹进来，篇章时长就超出 `lifeSpanCost` 定价表反推时的假设，而那张表存在的唯一理由就是旋钮精度。

建议把 `R_c` 拆成两个**书写口径格**（标定台账，不进 `.tres`、不进任何 `Resource`，与 `t(type)` 耗时台账同档）：

```
R_c = R_event,c + R_item,c            （Σ 不变 ⇒ λ 与 21 格定价表零改动）
```

| | ch1 | ch2 | ch3 | 来源 |
|---|---|---|---|---|
| `R_c`（既定，不动） | 100 | 116 | 317 | `systems/balance.md` λ 反推式 |
| `R_event,c` 事件侧 | **50** | **58** | **159** | 回寿事件 outcome + 点名给补天丹的事件产出，合并计一本账 |
| `R_item,c` 道具侧 | **50** | **58** | **158** | 商店购入 + 池抽产出的期望回寿量 |

- **道具侧是事件侧的替代品，不是补充品。** 两者在玩家语言里是同一件事（「买回容错」），只是一个当场兑现、一个可以攒着。故建议按替代关系分账、Σ 不变，而不是加总。
- **代价明写：** 回寿事件从「每章 2 次小档」降为「每章 1 次小档」，其在事件流中的密度进一步下降。`systems/balance.md` 已把该密度记为待实测复核点（「回寿事件在事件流中的密度较此前下降约 28%，随三档绝对点数的待决问题一并实测复核」），本条把它再下调一档，同批复核。
- 备选（加总并重算 λ）见「仍需用户决定」第 1 条。

### 1. 出现频率：封掉第四条通道，其余三条按池占比编排

`[既有推演]`

**先如实报告一个缺口：回寿法宝当前有四条获取通道，而三格口径只覆盖得住其中两条。**

| # | 通道 | 次数量级 / 章 | 定价闸 | 现状 |
|---|---|---|---|---|
| ① | 开局强制事件的法宝三选一 | ≤ 1 次 / **轮回** | 无（免费） | 天然有硬上限，不需要闸 |
| ② | Exchange 商店库存 | ≈ 10 / 10 / 12 次 Exchange | **有** | 三格口径的主战场 |
| ③ | 事件产出（`AbilityElements` 的 `Grant`，点名或池抽） | 由编排决定 | 无 | 建议并入 `R_event,c` 计账 |
| ④ | **战后奖励池** | ≈ 11 / 11 / 14 场战斗 × 3 项候选 | **无** | **完全无闸** |

`systems/services/combat-service.md` 的战后奖励池是 `CardData` / `ItemData` / `CultivationTechniqueData` / `PowerData` 四类混合，取池链含 `AllEnabled()` · `Pool != Enemy` · 稀有度权重 · `Practice` 档排除 `PowerData` · 功法与神通的已持有排除 · 成员卡排除——**没有任何一条针对「产出 `LifeSpan` 的道具」**。三项候选各自独立可领（不是择一）⇒ 一章约 33 个免费候选位。

**建议：在战后奖励池的取池链上加一条排除——含 `(CostKey.LifeSpan, BaseValue > 0)` 产出的 `ItemData` 不进战后奖励池。** 四条依据：

1. **定价这一格在它上面整条失效。** 三格护栏里唯一的硬闸是货币，而战后奖励是免费的。
2. **它的次数正比于战斗场数**（≈ 11–14 / 章，是 Exchange 的 1.1–1.2 倍且每次给 3 个候选位）⇒ 一个池占比旋钮要同时满足两条量级差数倍的通道，必然一头松一头紧。
3. **它让「打输一场」的代价被「打赢下一场」直接抵消。** 与 Travel 禁令「换图的代价不得被同一事件抵消」逐字同构；寿元合并后战斗失败正是这条压力线的第二个消耗面，抵消口开在战斗奖励上是最直接的一处。
4. **形态零新概念。** 奖励池按族排除已有既成实例（`Practice` 档整族排除 `PowerData`），排除条件的写法与「成员卡不从散牌产出侧发放」同款（加载期反建一份索引 + 取池时套用），**不新增字段、不新增存档、不加任何计数器**。

**代价明写（被接受）：** 内容侧从此编排不出「打赢一场硬仗掉一颗补天丹」这一风味；回寿法宝只能靠买、靠事件给、靠开局那一次三选一。

**通道 ①③ 的处置：** ① 有天然硬上限（一轮回至多一件），**不设任何额外闸**；③ 与回寿事件同性质（占事件位、付 `selectCost`），建议**并入 `R_event,c` 同一本账**，不单列旋钮。

**通道 ② 的频率口径（可 `/audit-content` 机械核对，只报告不阻断）：**

> 含 `(CostKey.LifeSpan, BaseValue > 0)` 产出的 `ItemData`（`Scope == Character`），在**每一个 `RarityTier` 档内**的条目数占该档 `Scope == Character` 条目总数的比例 **≤ 6%**。

- **逐档核算，不按整池核算**——与 Exchange 闸 ①「逐 `Kind` 逐 `RarityTier` 档位」同一条理由：整池够而某档扎堆同样失控，而抽取恰恰是在档内进行的。
- **等价的整数形态（首批唯一需要执行的那一句）：** `floor(该档条目数 / 17)`。首批内容量级远小于 17 ⇒ **每档至多 1 条**。
- **落点是 `/audit-content` 的一项汇总，不进加载期校验**——它是编排口径不是数据合法性，与「负向 `OnFailureRules` 占比 ≤ 10%」「条目级偏移 ≈ ±15%」同款处理。

### 2. 库存深度：一条免费成立，一条建议口径

`[既有推演]` + `[通行做法]`

- **「同一家店至多一件同 `Id` 回寿法宝」免费成立**——`PickMany` 无放回是既定契约。不同 `Id` 的两件同店的概率在 6% 口径下 ≈ 1.2%，量级可忽略，**不为它加规则**。
- **建议口径：单个 Exchange 条目内 `CharacterItem` 族的 Σ`SlotCount` ≤ 3**（槽位总数上界建议 ≤ 8、五族共享，见 `systems/balance.md`）。同样落 `/audit-content` 汇总。
- **不为回寿法宝单设 stock rule、不给它专属的 `RarityFilter` 例外。** 一旦开出「这家店专卖补天丹」的编排位，池占比口径就被绕过，而校验无从判断作者是不是故意的——与「售出准入写成代码级常量而非内容可配的族白名单」同一条判据。

**推导出的期望遇到次数**（`p` = 档内占比 6%，`CharacterItem` 族每店平均约 2 槽）：

```
P(某店至少含一件回寿法宝) = 1 − (1 − 0.06)² ≈ 11.6%
期望遇到次数 = Exchange 事件数 × 11.6%
             ch1 10 次 → 1.16   ch2 ≈ 10.4 → 1.21   ch3 ≈ 12.4 → 1.44
```

### 3. 定价：零新增旋钮，由既有两张表的外积直接给出

`[既有推演]`

**建议把回寿档与 `RarityTier` 档一一绑定**，定价随之从既有 25 格表读出，不新开任何格：

| 回寿档 | 绝对回寿量 | `RarityTier` | 定价（`CharacterItem` 行 · 恒灵石） | 单位价 |
|---|---|---|---|---|
| 小 | **50** | **Tier2** | **40 灵石** | 0.80 灵石 / 点 |
| 中 | **100** | **Tier3** | **80 灵石** | 0.80 灵石 / 点 |
| 大 | **200** | **Tier4** | **160 灵石** | 0.80 灵石 / 点 |

- **两条 ×2 曲线天然对齐**：回寿量三档 50 / 100 / 200 是 ×2 递进，`CharacterItem` 行的稀有度基价 20 / 40 / 80 / 160 / 320 同样 ×2 递进 ⇒ 绑定后**单位价恒定 0.80 灵石 / 点寿元**，玩家在三档之间读不出套利。不需要任何新表、不需要 `PriceOffset`。
- **Tier1 / Tier5 留空不编排**：Tier1（20 灵石）碎到没有决策感；Tier5（320 灵石）单件即吃掉 ch1 全章灵石收入的 2.5 倍，作为一件消耗品定价失真。
- **绝对点数，三章通用，不按篇章分条目。** 道具是**跨篇章持有物**（`magicPack` 随轮回清理、不随篇章清理），`OutOfCombatUseOutcome.Elements` 的 `BaseValue` 是定值、读不到篇章 ⇒ 「占本章预算百分比」这个口径在道具侧结构上就用不了。取 ch1 折算值作为三档绝对值。

**由此得到两条结构性推论，建议一并落笔：**

- **囤积自然贬值（有利，且是这条护栏最强的一段）。** 一颗 50 点的补天丹在 ch1 值 5% 的本章预算，攒到 ch3 只值 1.6%（预算 3000 + 结转）。「囤到 ch3 一次性解围」这条策略被算术自动削弱，**不需要任何新规则**——这正好接住「储物袋不设容量上限」留下的那个口子。
- **价格闸随篇章自动松开（代价，须明写）。** 定价表不设篇章维（`ADR-0133`）而灵石收入 `I(c)` ≈ 127 / 300 / 480 ⇒ 40 灵石在 ch1 是本章收入的 31%、在 ch3 只有 8%。**定价这一格只在 ch1 是有效闸；ch2 / ch3 由出现频率与库存深度承接。**

### 4. 条目形态：`Charges = 1`

`[既有推演]`

建议三档补天丹一律 `Charges = 1`（一次性）：

- **次数补充机制未设计**，`ItemChargeElement.Delta > 0` 当前是 `PushError` ⇒ 多次数的条目是一个不可续的消耗池，与它的字段语义不对齐。
- **`Charges > 1` 会把价格闸按次数稀释**——一颗 `Charges = 3` 的小档丹等于 40 灵石买 150 点寿元，单位价掉到 0.27，与上表的恒定单位价直接冲突。
- **一颗 = 一档回寿**是最可读的映射；储物袋按 `ItemId` 堆叠 `×N` 已经让「买三颗」在呈现上是 `×3`，不需要用 `Charges` 表达数量。
- `Charges == -1`（无限）在这一族上本就被 `I-12` 挡死（无限次可用的战斗外道具）。

## 具体形态（可 derive 的落地面）

**首批内容 = 全库恰 3 条回寿法宝**（Tier2 / Tier3 / Tier4 各一条），字段取值：

| 字段 | 小档 | 中档 | 大档 |
|---|---|---|---|
| `Scope` | `AbilityScope.Character` | 同左 | 同左 |
| `UsableScene` | `OutOfCombat` | 同左 | 同左 |
| `ManaCost` | `0`（`I-8` 要求） | 同左 | 同左 |
| `Charges` | `1` | `1` | `1` |
| `MaxUsesPerCombat` | `-1`（不限；本族恒不进战斗，该格无消费点但不得为 `0`，见 `I-7`） | 同左 | 同左 |
| `Rarity` | `Tier2` | `Tier3` | `Tier4` |
| `CombatUseEffects` | 空（`I-3` 要求） | 同左 | 同左 |

| 商店基准价（读 25 格表，条目不填） | 40 灵石 | 80 灵石 | 160 灵石 |

> 字段的类型 / 取值域 / 校验语义一律以 `systems/character-profile/item/_index.md` 为准，本表只填值。

**三条编排口径（落 `/audit-content` 汇总，只报告不阻断）：**

| 编号 | 口径 | 首批等价形态 |
|---|---|---|
| **L-1** 出现频率 | 含 `(LifeSpan, +n)` 产出的 `ItemData(Scope == Character)` 在每个 `RarityTier` 档内条目占比 ≤ 6% | 每档至多 1 条 |
| **L-2** 库存深度 | 单个 Exchange 条目内 `CharacterItem` 族 Σ`SlotCount` ≤ 3；不为回寿法宝单设 stock rule / `RarityFilter` 例外 | 同左 |
| **L-3** 定价 | 回寿档 ↔ `RarityTier` 一一绑定，单位价恒 0.80 灵石 / 点；不填 `PriceOffset` | 40 / 80 / 160 |

**一条取池侧排除（机械，落加载期反建索引 + 取池过滤，形态照「成员卡不从散牌产出侧发放」）：**

> **L-0：** 战后奖励池的 `ItemData` 部分排除含 `(CostKey.LifeSpan, BaseValue > 0)` 产出的条目。日志形态建议沿用既有约定：
> `[ContentRegistry-Validate] lifespan items excluded from combat reward pool: count=<n> ids=<...>`

**收支回代（标定台账 · 待实测校准的初值）：**

```
期望回寿量 R_item,c = 期望遇到次数 × 该章典型档位点数 × 购买转化率
购买转化率 ≈ 0.7   ⚠ 纯假设，与 λ 反推式里的败率 20% / E[道念差] 同款处置——
                    写在这里是为了让三格口径可复算，不得被引为任何设计的承重依据。
```

| | ch1 | ch2 | ch3 |
|---|---|---|---|
| 期望遇到次数 | 1.16 | 1.21 | 1.44 |
| 典型档位点数（依赖库存 `RarityTier` 分布） | ≈ 50 | ≈ 70 | ≈ 150 |
| 期望回寿量 `R_item,c` | ≈ **41** | ≈ **59** | ≈ **151** |
| 目标（`R_c` 的一半） | 50 | 58 | 158 |
| 偏差 | −18% | +2% | −4% |

- 三章均落在 ±20% 内，量级自洽。**ch1 偏低 18%** 是可接受的一侧——ch1 的价格闸本就最紧（40 灵石 = 本章收入 31%），且 ch1 恰是玩家最需要学会「买回容错」这条取舍的一章，供给略紧不构成失衡。
- **本表的「典型档位点数」一列依赖商店库存的 `RarityTier` 分布**（ch1 主要遇到低档、ch3 遇到高档）。该分布尚未定案，见「前置依赖」。

## 备选方案（已考虑并否决）

- **每篇章回寿总量硬上限（存档字段 + 加载期校验）** — 否决：`ADR-0066` 已明确否决过，且 `systems/balance.md:850` 的 `IgnoresProtection` 先例同向（「不加篇章配额 / 轮回内次数上限」）。推翻它需要一次独立决策。
- **给 `ItemData` 加一格 `MaxPerCycle` / `OncePerRun`** — 否决：全库不存在这类机制，加它要连带回答「谁有权用它」「四条通道各自怎么计数」「计数落哪里」，而计数必然落存档 ⇒ 回到上一条已被否决的形态。

- **给回寿法宝一个专属的低 `SelectionWeight` / 专属权重表** — 否决：`SelectionWeight` 是**事件条目**的档位映射，不作用于道具池；为道具另开一张权重表则与「分表维度按用途、不按 `(CarrierKind, Scope)`」正面冲突。
- **按篇章分条目（ch1 丹 / ch2 丹 / ch3 丹）以贴合百分比口径** — 否决：道具池没有篇章维过滤器，一件 ch3 规格的丹在 ch1 商店被抽到即失控；且它把 3 条内容变成 9 条，而「囤积自然贬值」这条推论恰恰要求同一件东西跨章保持绝对值不变。

## 与既有决策的张力

**一处，需用户点头：`ADR-0066` 写的是「护栏 = 三道软闸 + 一条结构性禁令，不设硬上限」，而本方案建议再加一条结构性禁令（L-0 战后奖励池排除）。**

- 冲突的严格程度：`ADR-0066` 否决的是**硬上限**（带存档字段与计数的那一类），L-0 不是上限、不计数、不落存档，它是一条**取池侧过滤**，与该 ADR 已经容纳的 Travel 禁令同族。故这是**扩写**而非推翻。
- 但它确实让「护栏落在内容编排面、规则层不设限」这句话不再完全为真——L-0 是代码侧的。**不加它的替代方案**：把战后奖励池的回寿法宝也纳入 L-1 的池占比口径，靠内容侧「不把回寿法宝挂进任何 `RewardPoolId`」的编排纪律承接。代价是这条纪律无机制保证、一个条目挂错就静默打开一条免费通道，且**能上线、线上不可见**——正是本库反复要求提到「写不出来」那一级的情形。
- 若采纳 L-0，`ADR-0066` 的「后果」一节需补一行；若不采纳，`ADR-0066` 不动。

### 1. 道具侧回寿的预算，是从 `R_c` 里分账，还是在 `R_c` 之上另加？

- **选项 A（推荐）· 分账，Σ 不变。** `R_c = R_event,c + R_item,c`，ch1 = 50 + 50。
  - 后果：λ 与 21 格 `lifeSpanCost` 定价表**零改动**；代价是回寿事件从「每章 2 次小档」降为「每章 1 次」，其在事件流中的密度进一步下降（该密度已被记为待实测复核点）。
  - 理由：事件侧回寿与道具侧回寿在玩家语言里是同一件事（「买回容错」），是替代关系而非叠加关系；且它把改动限制在一张标定台账内，不动任何已通过七条自校验的表。
- **选项 B · 另加预算并重算 λ。** ch1 `R_1` 由 100 抬到 150，`λ₁ = (1000 + 150 − 105 − 150) / 55 ≈ 16.3 → 16`，21 格全部按 `round(t × λ)` 重算。
  - 后果：回寿事件密度保持不变（每章仍 2 次），道具侧是真正的净增供给；代价是 21 格定价表整体上移约 7%，七条自校验与 ch1 的 35 批次收支校验表须全部重跑，`C1` 结转与 N = 2 容错量台账连带复核。
  - 它并非不可行——`systems/balance.md` 本就写明「重定价时改 λ 或改 `t`，整张表自动重算」——但为一条内容编排口径去动三旋钮联立的输出，代价与收益不成比例。

→ **已裁决（2026-09-09 · 批量评审）：选项 A —— 分账，Σ 不变。** `R_c = R_event,c + R_item,c`，ch1 拆成 50 + 50；λ 与 21 格 `lifeSpanCost` 定价表零改动。已接受的代价：回寿事件由「每章 2 次小档」降为「每章 1 次」，在事件流里更罕见。
