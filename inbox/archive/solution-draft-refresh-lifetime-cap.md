# 方案草稿 — refresh 链绝对寿命上限的客户端对位

> **本文件只写客户端这一半**：新增 `reasonKey` 的玩家措辞落点，以及（仅当后端 A-3 采纳）软着陆信号 `reauthRecommended` 的客户端反应形态。
> **机制本身——绝对寿命上限是什么、取几天、报文长什么样、`reasonKey` 叫什么、软信号如何判定——全部归 `counterpart`，本文件不复述，只回链。**
> **本方案不改变本库任何一条既定纪律**：不新增阻塞点、不做任何本地时钟比较、不持有任何过期时刻、API 面零改动、存档 schema 零影响。

## 问题

本库已于 2026-08-22 落笔并明确**不自收口**：客户端自加「距上次 `signin` 超过 N 天即强制回登录屏」会撞「设备时钟不可信」这条既定纪律，收口手段全在后端侧（`systems/services/account-service.md`「refresh token 的持有与失效」末段）。

后端侧现有一份方案草稿承接它（`counterpart`），其推荐形态会给客户端带来**两项**（第二项可被后端侧独立否决）：

1. **`auth.session_revoked` 多一个 `reasonKey` 取值**——玩家会因「登录链到期」而被要求重登，这与「被挤下线」「被运营吊销」共用同一个 `code`，措辞必须可分辨。
2. **（仅当后端 A-3 采纳）一个软着陆信号**：后端在续期应答里告知「这条链快到期了」，客户端据此在**自然时机**主动走一次登录，避免到期落在轮回中途。

## 约束（来自既有设计）

- **UI 文案一律走 `res://text/` 翻译键，`ERR_*` 键由 `code`（+ `reasonKey`）机械变换而来、不得手写**；`reasonKey` 的取值清单**由后端契约给出，本库不维护第二份**（`ux/error-and-blocking-ux.md`「`detail.reasonKey`：二级措辞的键」）。
- **未知 `reasonKey` 回落到一级文案**，后端新增取值**不要求客户端同批发版**（同上）。⇒ 第 1 项**不阻塞任何发版**。
- **阻塞点是穷举的四处，没有第五处**（`systems/services/sync-service.md`「三条不变式」①）。本方案**不新增阻塞点**——到期重登走的是既有的「被后端明确挤下线」那一处（同一个 `code`、同一条处置）。
- **设备时钟不可信；本库不持有任何过期时刻**（`account-service.md`：不存过期时刻、`refreshExpiresAtUtc` 读取即丢弃）。⇒ 客户端**不得**据任何下行时间戳自行判断「该重登了」。
- **登录屏不是阻塞屏**（`account-service.md`「消费点 = 启动期静默续期」）；启动期的续期失败一律落回登录屏，不走会话期内的两条分流。
- **`AuthManager` 私有，不提供公开取值方法**；refresh token 的读写与应答处理全在 `AuthManager` 内。
- **`Session` record 与 `account-service` 的 API 面已封定**，本方案不得改动其中任何一条签名。

## 建议方案

### 1. 新 `reasonKey` 的落地 = 一条翻译条目，无代码改动

`[既有推演]`

本库的二级文案键是**机械变换**的产物，`ErrorText.For(code, reasonKey, error)` 已吃三个参数、已有未知回落、反向审计已放宽为前缀匹配。因此后端新增取值时，本库**需要且只需要**：

- 在 `res://text/` 的 `ERR_` 分区新增一条二级键的翻译条目（键名由 `code` + 取值机械得出，取值以 `counterpart` 为权威，**本库不复述**）；
- `ux/error-and-blocking-ux.md` 的取值回链处**无需改动**——它本就写着「取值表权威在后端契约、本库不复述」。唯一可能要动的是该处提到的**取值条数**（若正文里写死了数目）。

**措辞取向**：这一句必须与「被挤下线」在情绪上明确区分——到期重登是**完全正常的例行事件**，玩家没有做错任何事、也没有第二台设备在动他的账号。建议是最平淡的一句「登录状态已过期，请重新登录」，**不带任何异常暗示、不带诊断编号以外的额外信息**。→ 取向项 B-1（措辞基调）。

**本项不依赖后端 A-3**：只要后端采纳绝对上限（A-1 选项 1），本项即成立；且因未知回落存在，**两侧发版顺序任意**。

### 2.（仅当后端 A-3 采纳）软着陆信号的客户端反应

`[取向选择]` + `[既有推演]`（三条形态约束）

后端在续期应答里给一个**已经算好的布尔**（判定与阈值归 `counterpart`）。客户端侧的形态：

- **只在内存里持有，绝不落盘。** 它是**本次进程内**的一次性提示，落盘就变成一个「过期了还在生效」的本地状态，且 `refresh-token.json` 的字段集已按「只放鉴权材料」收敛过（`account-service.md`），加一格便利字段会破坏那条判据。
- **客户端不做任何时间判断。** 收到即为真、未收到即为假；**不推算、不折算、不与任何本地时钟比较**。这是「设备时钟不可信」在本项上的直接兑现，也是后端把它做成布尔而非时间戳的原因（见 `counterpart`）。
- **反应 = 在下一个自然时机主动走一次 `signin`，而不是任何阻塞。** 「自然时机」的候选与各自后果见 B-2。
- **归属 = `AuthManager` 私有，API 面零改动**：不新增方法、不改 `Session`、不改任何签名。与 `deviceId` / refresh token 同款——一个公开取值口就把「挂个本地判断」变成一行代码的距离。
- **失败即忽略**：主动走的这一次 `signin` 若被玩家取消或失败，**当前会话仍然有效**，照常继续游戏。它是一次邀请，不是一道门；真正的强制力在后端的绝对上限（`counterpart`）。

### 3. 明确不做的三件事（写进文档，防日后被"补全"）

`[既有推演]`

- **不新增阻塞点。** 到期重登复用既有的 `auth.session_revoked` 硬阻塞路径，软信号则完全不阻塞。**四处阻塞点的穷举清单一字不改**（`sync-service.md`「三条不变式」①）。
- **不持有、不推算、不展示任何「还有几天到期」。** 没有一处 UI 需要它，而持有它就等着被人拿去做本地判断。
- **不因软信号丢弃或改动 `user://cache/refresh-token.json`。** 六条失效路径已穷举（`account-service.md`），软信号**不是**第七条——它不使任何 token 失效，只是提前去换一条新链。

## 后果

- **发版耦合：无。** 未知 `reasonKey` 回落已定，后端可先上线；软信号缺席时客户端行为与今天完全一致（可选字段缺省即 `false`）。
- **存档 schema、迁移、`user://cache/` 文件集：零影响。**
- **玩家可见变化**：每隔一个上限周期多一次登录（次数与周期归 `counterpart`）；采纳软信号后，这次登录**绝大多数落在启动期的登录屏**，而不是轮回中途的阻塞屏。

## 备选方案（已考虑并否决）

- **客户端自行按「距上次 `signin` 的天数」强制回登录屏** — 撞「设备时钟不可信」；一台时钟偏了的设备会凭空强制重登或永不重登。**这条已于 2026-08-22 否决，此处只是不重开它。**
- **把后端下发的到期时刻存进 `refresh-token.json` 供客户端判断** — 撞既定的「不存过期时刻」（`account-service.md`：存一个不允许被读的字段，只会等着被人读）。
- **软信号触发一次阻塞屏 / 模态弹窗** — 会新增第五处阻塞点，且它根本不需要阻塞：会话此刻完全有效。
- **软信号触发时立即中断当前轮回去登录** — 直接撞 pillar「不阻塞玩家」；软信号存在的全部意义就是**等一个不打扰的时刻**。
- **本库自建一份 `reasonKey` 取值清单以便穷举文案** — 撞「不维护第二份清单」，而那份表按契约设计会持续扩张。

## 与既有决策的张力

**无。** 本方案不推翻本库任何一条既定纪律：阻塞点清单不变、时钟纪律不变、`refresh-token.json` 的六条失效路径不变、API 面不变。**唯一被改写的一句**是 `account-service.md` 末段「收口手段全在后端侧、本库不代为决定」——它是一句**指向待办的占位**，收口定案后本就该改写为回链，这不是张力。

## 前置依赖

- **本方案的全部内容依赖 `counterpart` 的裁决结果，且须成对采纳：**
  - `counterpart` 的 **A-1** 若选「不收口」→ **本方案整份作废**；
  - `counterpart` 的 **A-4**（取值命名）决定本方案第 1 项的翻译键名——**在它定下来之前，翻译条目无法落笔**；
  - `counterpart` 的 **A-3** 若选「不引入软信号」→ **本方案的第 2 项整节作废**，只剩一条翻译条目（届时请一并确认本草稿是否还值得单独走一次 `/analyze-new-ideas`）。
- **单侧采纳即两侧不一致**：后端下发一个本库没有二级文案的取值虽有兜底（回落到一级键，不报错、不崩），但玩家会在一次完全正常的例行到期上，看到一句为「被挤下线」准备的措辞——**静默的错文案，没有任何报错会提示到它**。

## 仍需用户决定

### B-1 到期重登的玩家措辞基调

- **选项 1（推荐）：最平淡的例行口吻** —— 「登录状态已过期，请重新登录」。不解释原因、不带任何异常暗示。
- **选项 2：附一句原因** —— 如「为保障账号安全，登录状态会定期过期」。更能安抚，但**引入一句会随后端旋钮漂移的解释**（周期改了、这句话的暗示就不准了）。
- **推荐**：选项 1。理由与本库既定的「`message` 不给玩家看、文案按 `code` 取」同源——**玩家需要知道要做什么，不需要知道机制**；而一句解释性文案会在后端调一次旋钮后静默变得不准确。

→ **已裁决（2026-08-23 · 批量评审）：选项 1 —— 最平淡的例行口吻，不附原因句。** 对侧同批裁定 `reasonKey` 取 `SessionExpired`，故本库二级文案键为 `ERR_AUTH_SESSION_REVOKED_SESSION_EXPIRED`。

### B-2（仅当后端 A-3 采纳）「自然时机」取哪一档

- **选项 1（推荐）：启动期静默续期成功且收到软信号 → 直接呈现登录屏**（会话仍有效，玩家取消 / 失败则照常进游戏）。落点最早、最不打扰；**复用既有的登录屏路径，零新增屏幕**。代价：玩家会在启动时多看到一次登录屏，且它此刻是「可跳过的」——与登录屏平时的语义略有差异。
- **选项 2：仅在「无进行中轮回的主菜单」时机触发**。永不打断任何流程，但需要一个「有没有进行中轮回」的判断点与一处新的触发接线。
- **选项 3：选项 1 + 选项 2 都取**（启动期优先，错过则等主菜单）。覆盖最全，接线最多。
- **推荐**：选项 1。启动期是唯一一个**必然经过、必然空闲、且已有现成屏幕**的时刻；后两者的增量覆盖面很小（软信号提前量足以覆盖至少一次冷启动，判据见 `counterpart`），却要新增触发点。

→ **已裁决（2026-08-23 · 批量评审）：选项 1 —— 启动期续期成功即呈现可跳过的登录屏。** 前置的对侧 A-3 同批裁为「引入，body 可选布尔」，故本条生效（非作废分支）。
