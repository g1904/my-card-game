# 方案草稿 — 静默续期绕过强更闸门的收口手段（后端侧）

> **本文件只写后端这一半**：refresh token 链的绝对寿命上限、到期时的报文与 `reasonKey`、会话记录字段、软信号的下行形态与旋钮初值。
> **客户端如何反应（二级文案键、软信号落地的时机与屏幕、启动期与会话期的分流）→ 见 `counterpart`，本文件不复述。**
> 技术栈未定 ⇒ 全文停在协议与语义层，不指定语言 / 框架 / 存储实现。

## 问题

`contracts/auth.md` §5 定了两条互相咬合的承重条款：

- **强更闸门（协议维度）只在 `POST /v1/auth/signin` 判定**，`refresh` 永不返回 `client.version_unsupported`；
- §2 的 refresh token 是 **30 天滑动续期**——每次 rotation 顺延，活跃玩家永不被动重登。

两条叠加的连带后果：**一个只走 `refresh` 的客户端，在下一次真正 `signin` 之前永远不会被 `client.version_unsupported` 拦到。** 而客户端已把静默续期落到启动链第二步（`InitializeAsync` 内先续期，续期成功即跳过登录屏），所以「下一次真正 `signin`」在活跃玩家身上**可以永不到来**：只要设备不换、缓存不清、不主动登出、不被挤下线，链条可以无限延长。

结果是**强更闸门对最需要被闸掉的那一类玩家（长期在线的老版本）失效**，且失效是静默的——运营提升 `minAppVersion` 后，后台看到的仍是这批客户端在正常刷新。

客户端侧已于 2026-08-22 落笔并**明确不自收口**：客户端自加「距上次 `signin` 超过 N 天即强制回登录屏」会撞它「设备时钟不可信」这条既定纪律。权威见 `game-design-documents/systems/services/account-service.md`「refresh token 的持有与失效」（**本库不复述其形态**）。**收口手段归本库。**

## 约束（来自既有设计）

- **`refresh` 永不判定版本闸门**（`auth.md` §5，承重）。任何以 `clientVersion` 为输入、在 `refresh` 上做判定的形态都是这一条的变相推翻。
- **闸门在签发 token 时判定一次，会话期内不因阈值提升而中途变严**（`envelope.md` §7b）。运营动作不得打断进行中的会话。
- **`pull` 侧也不判定闸门**——「pull 也判定强更闸门」已在 `contracts/profile-sync.md` §2 与其备选方案段**明确否决**（造出第二个闸门与第二套阈值）。**本方案不重开这一条。**
- **`POST /v1/auth/refresh` 的错误清单只有两条**（`auth.session_revoked` · `server.unavailable`），刻意如此——客户端「刷新失败按有无明确应答分两条路径」的判据靠它在报文层面无歧义（`auth.md` §8 §10、`envelope.md` §6、ADR-0004 后果段）。**新增第三条错误码要付这条纪律的代价。**
- **`auth.session_revoked` 的客户端处置已定**：硬阻塞重登、重登后先 pull 后 flush、暂停退避重试；**本地缓冲保留、不丢弃**（丢弃是 `sync.conflict` 的处置，不是本条）。
- **`reasonKey` 形态 PascalCase 锁死；未知取值退回一级键，后端新增取值不要求客户端同批发版**（`auth.md` §10）。
- **客户端不持有任何过期时刻、不做任何本地时钟比较**（既定纪律，权威在 `counterpart` 指向的客户端文档）。⇒ **任何下行的「该重登了」信号不能是时间戳。**
- **pillar #4「不阻塞玩家」**；`envelope.md` §7b「仅两处硬阻塞」。
- **`profile-sync.md` §9 的 `pushId` 保留时长 30 天，其推导依据是「超过 30 天未登录的设备必须重登」**——即**闲置**失效口径。本方案不改闲置口径，故该旋钮零连带（已核对）。

## 建议方案

### 1. 收口机制 = refresh token 链的**绝对寿命上限**（不随 rotation 顺延）

`[既有推演]` `[通行做法]`

给会话增加一个**在 `signin` 时锚定、rotation 永不顺延**的绝对截止时刻。refresh token 的有效性变为：

```
有效  ⇔  now < min(refreshExpiresAtUtc（30 天滑动，每次 rotation 顺延）,
                   absoluteExpiresAtUtc（signin 时 = issuedAtUtc + 绝对上限，永不顺延）)
```

超过 `absoluteExpiresAtUtc` 的 `refresh` → 吊销该会话 → 回 `auth.session_revoked`。玩家在下一次 `signin` 上**必然**经过强更闸门与合规判定。

**为什么是它而不是另外三个候选**（四个候选的完整代价见「备选方案」）：另外三个各撞一条既有承重款——按 `clientVersion` 定向失效等于在 `refresh` 上判闸门（§5）；运营触发的周期性 / 批量强制 re-signin 等于阈值提升在会话期内生效（§7b）；只下发软信号则闸门退化为客户端可忽略的建议。**绝对上限是唯一一个不与任何既有条款相撞的形态**：它是**时间维度**的收口，与 `clientVersion`、与运营阈值**完全无关**——服务端不因为「你版本旧」而终止你，只因为「这条链够老了」。**这一点必须写进契约正文**，否则它会被日后的读者读成 ④ 的委婉说法。

`[通行做法]` 「sliding refresh + absolute lifetime cap」是 OAuth 2.0 / OIDC 实现里的标准双旋钮组合（Auth0 / Keycloak / IdentityServer 皆有这两个独立参数），其存在理由与本作一致：滑动续期让活跃用户不被打扰，绝对上限保证**任何凭据链都有一个确定的终点**，使凭据泄漏面与策略变更的兑现窗口都有界。本作把「策略变更」具体化为强更闸门，形状不变。

### 2. 到期的报文 = 复用 `auth.session_revoked` + 新增一个 `reasonKey`

`[既有推演]`

**不新增错误码。** `refresh` 的错误清单保持两条，客户端的「有没有收到明确应答」判据一字不动。到期在报文上与「被挤下线」「运营吊销」完全同形：

```
auth.session_revoked
  class  : Reauth
  detail : { revokedAtUtc, reasonKey: "SessionExpired" }
```

- `auth.session_revoked.detail.reasonKey` 取值表由**七值扩为八值**（`auth.md` §10）；`envelope.md` §6 台账那一行的「七值」计数同批改为八值（台账不复述取值表，只有计数一处）。
- 会话记录的 `revokedReason` 写同一取值（§4a 已定 `revokedReason` 即下行的 `reasonKey`）。
- **客户端零阻塞式欠账**：`reasonKey` 的未知值兜底已定（退回一级键 `ERR_AUTH_SESSION_REVOKED`），故本取值**不要求客户端同批发版**；它只欠一条二级文案（归 `counterpart`）。

**取值命名建议 `SessionExpired`**（备选 `LifetimeExceeded`），理由：既有七值全部是「事件的过去式 / 完成态」（`SignedInElsewhere` · `SessionSuperseded` · `PlaytimeEnded` · `TokenReuseDetected`），`SessionExpired` 与之同形，且它要驱动的玩家措辞是最平淡的一句「登录状态已过期，请重新登录」——**与「被挤下线」「被封禁」在情绪上必须可区分**，这正是 `reasonKey` 存在的理由。→ 取向项 A-4。

### 3. 绝对上限的初值 = **60 天**（可调旋钮，落后端配置）

`[取向选择]`（初值本身）+ `[既有推演]`（上下界）

进 `auth.md` §8 的数值初值表新增一行：

| 旋钮 | 初值 | 推导 |
|---|---|---|
| refresh token 绝对寿命上限 | **60 天** | 见下 |

**下界 ≥ 30 天（滑动 TTL）**：若上限 < 滑动 TTL，滑动这个旋钮就永远不起作用，等价于「把 TTL 直接改短」——那会同时惩罚**闲置**玩家（§2 明写要覆盖「两周不玩、回来仍在登录态」），而闲置玩家恰恰不是本问题的对象（他们回来时自然走 `signin`）。**本问题的对象只有一类：连续活跃、从不重登的单设备玩家。**

**上界 ≤ 一次强更的可接受排空窗口**：强更闸门用于协议不兼容的破坏性变更，运营需要一个**有界且可预告**的最坏排空时间。一个季度太长（老版本会横跨两次内容大版本）；一到两个月是移动游戏强更公告的常见量级。

**取 60 天 = 2 × 滑动 TTL**：滑动旋钮对闲置口径继续完整生效；活跃玩家一年被要求重登约 6 次（`WeChat` 一次点按；`Phone` 一条短信——短信是**有成本且被刷**的通道，§8 已如此认定，这是选大值的一个实在理由）；强更最坏排空 60 天。

三档并列见 A-2。

### 4. 落地时刻与最坏延迟

`[既有推演]`

- **判定点只有一处：`refresh` 请求到达时**，比较 `now` 与 `absoluteExpiresAtUtc`。**不主动扫表吊销**——批量吊销就是 ② 的形状（备选方案），且服务端主动推送在 `vision/scope.md` 边界之外（`auth.md` 已否决）。
- **最坏延迟 = access token TTL（15 分钟）**：在截止时刻前一刻签发的 access token 仍有效至多 15 分钟。这与 §2 已定的「被挤下线最坏延迟 = access token TTL」是同一句话，**不新增任何延迟面**。
- **`signin` 重置链**：一次真正的 `signin`（含同设备重登的原地替换）产生新的 `absoluteExpiresAtUtc`。**60 秒幂等回放窗口内的重复 `signin` 不重置**——它回放上次结果、不签发（§4a），链的锚点因此不动。
- **`refresh` 的 60 秒宽限窗口与本上限的关系**：宽限窗口内的回放返回**上次那一对** token，不再轮换；若该次回放发生在 `absoluteExpiresAtUtc` 之后，**按到期处理**（回 `session_revoked` / `SessionExpired`）。**先判到期、再判宽限回放**——反过来会让一条已到期的链靠重放多活 60 秒，而那 60 秒没有任何玩家价值。

### 5. 会话记录新增一格；下行**不新增时间字段**

`[既有推演]`

`auth.md` §4a 会话记录表新增一行：

| 字段 | 说明 |
|---|---|
| `absoluteExpiresAtUtc` | `signin` 时锚定 = `issuedAtUtc` + 绝对上限；**rotation 永不更新它**（这半句是承重，必须与字段同处） |

**下行报文不新增字段**：`signin` / `refresh` 应答里已有的 `refreshExpiresAtUtc` 改为下发 **`min(滑动截止, absoluteExpiresAtUtc)`**——它本就声明「这个 refresh token 用到什么时候」，下发一个链条已注定活不到的时刻是**一句假话**。零字段成本、零客户端义务（客户端读取即丢弃该字段，见 `counterpart`）。

### 6. 软着陆信号 `reauthRecommended`（推荐引入，独立可否决）

`[取向选择]`（是否引入 + 承载位置）+ `[既有推演]`（形态**只能**是服务端算好的布尔）

**问题**：到期时刻落在轮回中途的概率不为零（refresh 每 ~15 分钟一次，玩家在线时段占一天的一小部分，但 60 天里总有一次落点）。落在中途时玩家会在战斗中被弹去登录屏——虽然**本地缓冲不丢**（`session_revoked` 的处置是保留缓冲、重登后先 pull 后 flush），但「战斗中途去收短信」是 pillar #4 上一个货真价实的痛点。

**建议**：`refresh` / `signin` 应答增加一个**可选布尔**字段：

| 字段 | 类型 | 必填 | 语义 |
|---|---|---|---|
| `reauthRecommended` | boolean | 可选 | 服务端判定「本链距绝对截止已进入尾段」。缺省即 `false`（`envelope.md` §2「不下发 `null`」，与 `isNewAccount` 同形） |

- **判定 = 服务端算好的布尔，绝不是时间戳。** 这是**推演出的唯一形态**，不是取向：客户端既定纪律是「不存过期时刻、不做任何本地时钟比较」（设备时钟不可信）。下发 `reauthAfterUtc` 一类时间戳，客户端合法地无法消费它；一台时钟偏了一个月的设备会得到完全错误的结论。**服务端持有唯一可信的时钟，判定就必须发生在服务端。**
- **它不是闸门，是着陆坡。** 强制力全部由第 1 项的绝对上限承担；`reauthRecommended` 只决定玩家**在哪个时刻**被请去重登。改包客户端忽略它 → 上限照样到期照样吊销。**因此它不构成「闸门变成可忽略的建议」**——单用它才会（见备选方案）。
- **旋钮初值：剩余 ≤ 3 天时置 `true`。** 推导：需覆盖至少一次冷启动机会（移动游戏玩家 2 天内几乎必有一次冷启动），3 天留一天余量；同时远小于 60 天，不至于让玩家在链的大半程里被反复送去登录屏。
- **承载位置建议 body 字段而非应答头。** 它是**按账号算出的会话级判定**，只在两个签发 token 的端点上有意义；`envelope.md` §4b 的应答头是「任意应答都带」的传输信封，把一个只有两个端点会填的值放进去会造出一个大部分应答里恒缺的头。→ 取向项 A-3。

## 具体形态（可 derive 的落地面）

**会话记录（`auth.md` §4a 表增行）**

| 字段 | 说明 |
|---|---|
| `absoluteExpiresAtUtc` | `signin` 锚定，rotation 永不顺延 |

**求值顺序（`auth.md` §4a / §4 的 refresh 侧，本方案新增的两步以 ★ 标出）**

```
refresh 请求到达
  ├─ ★ now ≥ absoluteExpiresAtUtc  → 吊销会话（revokedReason = SessionExpired）
  │                                  → auth.session_revoked { revokedAtUtc, reasonKey: "SessionExpired" }
  ├─ 该 refresh token 已被轮换且在 60 秒宽限窗口内 → 回放上次那一对，不再轮换
  ├─ 该 refresh token 已被轮换且在窗口外 → 判泄漏 → 吊销全部会话（TokenReuseDetected）
  ├─ now ≥ refreshExpiresAtUtc（滑动）→ auth.session_revoked（reasonKey 沿用既有口径）
  └─ 正常 → rotation：签发新对；refreshExpiresAtUtc 顺延；absoluteExpiresAtUtc 不动
       ★ 若 absoluteExpiresAtUtc - now ≤ 软信号阈值 → 应答带 reauthRecommended: true
```

**应答字段（`signin` / `refresh` 同形，`auth.md` §8）**

| 字段 | 变化 |
|---|---|
| `refreshExpiresAtUtc` | 语义收紧为 `min(滑动截止, absoluteExpiresAtUtc)`（字段本身不新增） |
| `reauthRecommended` | **新增**，boolean、可选、缺省 `false`（仅当 A-3 采纳） |

**数值初值表新增两行（`auth.md` §8）**

| 旋钮 | 初值 | 推导 |
|---|---|---|
| refresh token 绝对寿命上限 | **60 天** | ≥ 滑动 TTL（否则滑动旋钮失效）；≤ 一次强更的可接受排空窗口；2× 滑动 TTL 使闲置口径完全不受影响 |
| 软信号提前量 | **3 天** | 覆盖至少一次冷启动机会 + 一天余量；远小于上限，避免长期反复提示（仅当 A-3 采纳） |

**`reasonKey` 取值表新增一行（`auth.md` §10，七值 → 八值）**

| 取值 | 触发 | 依据 |
|---|---|---|
| `SessionExpired` | refresh token 链达到绝对寿命上限 | 本方案 |

## 后果

- **契约文档**：`contracts/auth.md` §2（TTL 表补绝对上限列 / 行）· §4a（会话记录表 + 求值顺序）· §5（把「待办」段改写为定案，并**明写「时间维度而非版本维度」**）· §8（refresh 报文 + 两个旋钮）· §10（`reasonKey` 八值）· 备选方案段追加四条。
- **`contracts/envelope.md`**：§6 台账 `auth.session_revoked` 行的「七值」计数改八值。**其余一字不动**——不新增 `code`、不新增 `class`、不新增 `OpError`。
- **客户端**：一条二级文案键 + （若 A-3 采纳）对 `reauthRecommended` 的反应形态。**均归 `counterpart`，两份须成对采纳。**
- **存档 / profile schema**：零影响。`schemaVersion` 不动，`profile-sync.md` 不改一字。
- **`profile-sync.md` §9 的 `pushId` 保留时长（30 天）零连带**（已核对）：其推导依据是**闲置**失效口径（「超过 30 天未登录的设备必须重登」），而本方案不改闲置口径——绝对上限只对连续活跃链生效，且取值 ≥ 30 天。
- **§2 的一句既有论证被本方案部分收回**：「滑动续期使活跃玩家永不被动重登」将不再成立，改为「永不因**闲置**而被动重登」。这句改写必须与绝对上限同批落笔，否则契约内自相矛盾（见「与既有决策的张力」）。
- **ADR**：`ADR-0004` 讲的是幂等与宽限窗口，本方案不触动它的任何一条。是否值得为「凭据链必须有确定终点」单立 ADR，倾向**不立**——它是 §5 既有承重条款的一个连带收口，写在契约正文即可。

## 备选方案（已考虑并否决）

- **② 运营触发的周期性 / 批量强制 re-signin**（如「提升 `minAppVersion` 时吊销全部旧会话」）— **直接撞 `envelope.md` §7b**：阈值提升在会话期内生效，会把正在玩的玩家成批踢出，且是**同时**踢出（一次运营动作 = 一次全量硬阻塞脉冲）。绝对上限之所以不撞这一条，正因为它的截止时刻**在 `signin` 那一刻就已确定**、按玩家天然错峰，且与运营的任何动作无关。
- **④ 服务端按 `refresh` 请求携带的 `clientVersion`（`X-App-Version`）做定向失效** — **等于在 `refresh` 上判定版本闸门**，`auth.md` §5 明写「`refresh` 永不返回 `client.version_unsupported`，无论 `X-App-Version` 多旧」，而 §6 的头表把它标为「**仅日志，不判闸门**」。换一个 `code` 下发不改变实质：它仍是「因为你版本旧所以中途终止你的会话」，§7b 禁的就是这件事。**且它同时打开一个更坏的门**——一个客户端自报、可伪造的头成为会话存续的判定输入。
- **③ 只下发软信号、不设任何上限** — 闸门退化为**客户端可忽略的建议**：强制力全部押在客户端自觉上，而改包客户端与老版本客户端恰恰是闸门要处理的对象。软信号只有在有硬上限兜底时才是着陆坡；单用它时它是一句没有下文的提醒。
- **给 `refresh` 新增第三条错误码**（如 `auth.reauth_required`）— 要付 `auth.md` §8 §10 那条纪律的代价：客户端「刷新失败按有无明确应答分两条路径」的判据靠「报文层面只有两种可能」才无歧义（ADR-0004 后果段）。而复用 `session_revoked` + `reasonKey` 拿到完全相同的表达力，**且客户端已有的兜底使它不要求同批发版**。
- **下发 `reauthAfterUtc` 一类时间戳让客户端自己判断** — 客户端既定纪律禁止任何本地时钟比较（设备时钟不可信），这个字段落地即成为一个「存下来等着被人读」的陷阱。
- **缩短 refresh 滑动 TTL（如 30 天 → 7 天）** — 惩罚的是**闲置**玩家（回来即重登，而他们本就会走 `signin`、本就经过闸门），对**连续活跃**的目标人群一点约束都没有：链条照样无限顺延。它治的是另一个病。
- **让 `pull` 或业务端点判定强更闸门** — **已在 `contracts/profile-sync.md` §2 与其备选方案段否决**（造出第二个闸门与第二套阈值，违反 `envelope.md` §7b）；业务端点另撞「仅两处硬阻塞」与 pillar #4。**本方案不重开这一条。**
- **服务端主动推送「请重新登录」** — 需长连接 / 推送通道，在 `vision/scope.md` 边界之外（`auth.md` 已否决同形方案）。
- **接受缺口、不收口** — 是一个正当的产品取向（成本为零），但代价是**强更闸门对最需要闸掉的那一类玩家永久失效**，且失效静默。列为 A-1 的一个选项，不在此处单方面否决。

## 与既有决策的张力

1. **与 `auth.md` §2「滑动续期使活跃玩家永不被动重登」直接冲突。** 本方案有意收回这句话的一半：改为「永不因**闲置**而被动重登；连续活跃链有一个确定终点」。**松动的理由**：那句话的完整成立恰恰就是缺口本身——「永不被动重登」与「闸门只在 `signin`」两条同时为真时，闸门必然可被无限规避。**不松动时的替代**：只剩 ②③④ 三条，各撞一条更重的既有条款（见备选方案）。**代价照录**：活跃玩家每 60 天重登一次；`Phone` 渠道每次重登多一条短信成本。
2. **与 pillar #4「不阻塞玩家」的张力（可控）。** 到期落在轮回中途 → 一次硬阻塞重登。三点缓解：① 它复用**既有**的 `auth.session_revoked` 路径，**不新增第三处硬阻塞**（`envelope.md` §7b 的「仅两处」讲的是版本闸门，而 `session_revoked` 的硬阻塞重登是既定路径，`PlaytimeEnded` 已是同形的另一个触发源）；② **本地缓冲保留、不丢弃**，重登后先 pull 后 flush，玩家不丢进度；③ 软信号（A-3）把绝大多数落点移到启动期。
3. **与 §4 rotation 纪律无冲突**：绝对上限不改变「同一凭据链上永远只有最新的一对有效」，只给这条链加一个终点。

## 前置依赖

- **`refresh` 的滥用面与限流形态（`open-questions/01-contracts.md` · 待 `06`）—— 同在 refresh 面上，须一并看，但不互相阻塞。**
  两者动的是同一条纪律的两侧：那一条若认定 `refresh` 必须限流，就要给 `refresh` 加 `rate.limited`（**第三条错误码**）并同时给出客户端的第三条失败路径；**本方案刻意不新增错误码**，故它**不消耗**那条纪律的额度、也不预设那一条的答案。两条互不阻塞，**采纳顺序任意**。
  两点实质关联，供那一条决策时取用：① 绝对上限使任何一条 refresh 链的**总刷新次数有界**（60 天 × ~4 次/小时在线），滥用面收敛一档，是「是否必须限流」的一个输入；② 若两条都松动，客户端将同时面对**第三、第四条** refresh 失败路径——**两条都松动的总代价必须一起评估，不能各自单独评估后累加**。
- **无其他前置。** 本方案不依赖 `06-platform-stack.md`：绝对上限的存储落点（会话记录多一格）与 `auth.md` §4a 已移交实现层的三项同处，栈落定后一并承接。
- **与 `counterpart` 成对采纳（强制）：** 本方案的「新 `reasonKey`」与（若采纳）「`reauthRecommended` 下行字段」两部分，须与 `counterpart` 的「二级文案键」「软信号的客户端反应形态」同时采纳。**单侧采纳即两侧不一致**——后端下发一个客户端不认识的取值虽有兜底（退回一级键，不报错），但玩家会在一次完全正常的到期重登上看到一句为「被挤下线」准备的措辞。

## 仍需用户决定

### A-1 是否收口，以及收口路线

- **选项 1（推荐）：采纳绝对寿命上限（本方案）** — 唯一不与既有承重条款相撞的形态；代价是收回 §2 的半句承诺 + 活跃玩家周期性重登。
- **选项 2：接受缺口、不收口** — 零成本、零改动；代价是强更闸门对长期在线的老版本客户端**永久且静默地**失效。
- **选项 3：② 周期性 / 批量强制 re-signin** — 撞 `envelope.md` §7b。
- **选项 4：④ 按 `clientVersion` 定向失效** — 撞 `auth.md` §5，且把可伪造的客户端自报头变成会话存续的判定输入。
- **推荐**：选项 1。理由：闸门是协议破坏性变更的唯一兜底，而当前它对目标人群失效；另三条路各自推翻一条比「§2 的半句承诺」更重的条款。

→ **已裁决（2026-08-23 · 批量评审）：选项 1 —— 采纳绝对寿命上限。** 连带确认：§2「活跃玩家永不被动重登」收窄为「永不因**闲置**而被动重登」，须与上限同批落笔。

### A-2 绝对上限取值

- **选项 1：30 天**（= 取消滑动，`refreshExpiresAtUtc` 在 `signin` 时固定） — 闸门最快兑现；但滑动旋钮就此失去意义，且闲置玩家的口径与活跃玩家合并，`Phone` 渠道短信成本最高。
- **选项 2（推荐）：60 天** — 2× 滑动 TTL；滑动对闲置口径完整生效；强更最坏排空 60 天；活跃玩家约每两月重登一次。
- **选项 3：90 天** — 玩家侧最轻；但老版本可横跨两次内容大版本，强更公告的最坏兑现窗口拉到一个季度。
- **推荐**：选项 2。**它是待实测校准的初值、落后端配置而非代码常量**，改值不需要契约变更、不需要客户端配合。

→ **已裁决（2026-08-23 · 批量评审）：选项 2 —— 60 天**（可调初值，落后端配置）。

### A-3 是否引入软着陆信号 `reauthRecommended`，及其承载位置

- **选项 1（推荐）：引入，作为 `signin` / `refresh` 应答的可选 body 布尔字段** — 绝大多数到期落点被移到启动期；代价是一个新下行字段 + 一条客户端义务（`counterpart`）。
- **选项 2：引入，作为应答头（如 `X-Reauth-Recommended`）** — 任意应答都能捎带，客户端可更早得知；但它是按账号算出的**会话级**判定，放进「任意应答都带」的传输信封会造出一个大多数应答里恒缺的头。
- **选项 3：不引入** — 后端零新增字段、客户端**只欠一条文案**；代价是每 60 天有一次到期，其落点可能在轮回中途（缓冲不丢，但玩家要在战斗中途去收短信）。
- **推荐**：选项 1。**注意：选项 3 会让 `counterpart` 缩到只剩一条文案键**——若选它，请在裁决时一并确认 `counterpart` 是否仍值得单独走一次提炼。

→ **已裁决（2026-08-23 · 批量评审）：选项 1 —— 引入，作为可选 body 布尔字段**（服务端算好的布尔，**不得是时间戳**）。`counterpart` 的客户端反应时机同批裁为「启动期续期成功即呈现可跳过的登录屏」（见 `counterpart` 的 B-2）。

### A-4 新 `reasonKey` 的取值命名

- **选项 1（推荐）：`SessionExpired`** — 与既有七值的「事件完成态」构词一致；二级文案键 `ERR_AUTH_SESSION_REVOKED_SESSION_EXPIRED`。
- **选项 2：`LifetimeExceeded`** — 更贴近机制本身；键 `ERR_AUTH_SESSION_REVOKED_LIFETIME_EXCEEDED`。
- **推荐**：选项 1。取值面向的是**玩家措辞的分辨**，不是机制的自述——「过期」是玩家能理解的词，「寿命超限」不是。

→ **已裁决（2026-08-23 · 批量评审）：选项 1 —— `SessionExpired`。** 对应文案取**最平淡的例行口吻**，**不附原因句**（附原因会把 60 天这个后端可调旋钮写进翻译条目，改值时两处不同步即静默失准；见 `counterpart` 的 B-1）。
