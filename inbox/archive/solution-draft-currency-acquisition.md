# 方案草稿 — 两种货币的获取渠道与掉落权重

## 问题

`currency.md:38-39` 与 `deferred-content.md:15-16` 登记的两条：

> **灵石的获取渠道与掉落权重未设计（承重）。** 消耗侧已有形态，**产出侧一片空白**：哪些事件给灵石、给多少、随篇章如何缩放均未定。它同时卡住定价表——每格填多少无法在获取渠道答定前反推。
>
> **仙玉的获取量与花销价格量级未设计。** 通道形态已定，仍欠取值：一轮回预期能拿到多少、高阶商品该标多少、定价表中哪些格填仙玉。它与上一条**互相约束**。

`open-questions.md:185` 把它列为「最短解锁路径」第 3 项，`balance.md:734` 是全库唯一显式自陈被它阻塞的待决条。

**一处措辞需先修正：产出侧并非「一片空白」。** `balance.md:368-372` 的胜侧单价表已给出 `rewardPerMomentum[SpiritStone]` 三章取值（ch1 `1 / 点` · ch2 `1 / 2 点` · ch3 `1 / 4 点`），且 `:374` 已定案「单价表只列灵石，不列仙玉」。真正空着的是**基线量**（`BaseReward` 与事件 outcome 给多少）与**渠道口径**（哪些事件给），不是整条通道。

## 约束（来自既有设计）

**结构面（全部已成文，本方案零结构增量地建立在它们之上）**

- 两币**都是轮回级**，归 `CharacterProfile` 顶层相邻两格 `spiritStone` / `immortalJade`（`int`），写入通道 `Elements`，`CostKey.SpiritStone` / `CostKey.ImmortalJade` — `currency.md:8`、`character-profile/_index.md:126-127`、`:160`。
- `ResourceElements` 两行同形：`Min = 0` / 无 `Max` / 无终态 / 两个修正列**恒 null** / 仅 `Add` — `currency.md:12`、`profile-service.md:250-251`。
- **完全不可兑换（正面纪律、零机制）**，售出同币回收因而不产生事实汇率 — `currency.md:27-28`。
- 产出主通道 = `OutcomeRule.FixedResource`，可写 key 白名单 `{ LifeSpan, ManaLimit, SpiritStone, ImmortalJade }` 且 `Magnitude >= 0`，`Direction` 取负在物化时施加 — `adventure-event/common-properties.md:160`、`:139`；物化后可出现的 key 表 `future-event-service.md:413`。
- 战斗侧唯一货币通道 = `EncounterSpec.BaseReward : ProfileChangeSpec`（胜败都发 — `combat-service.md:19`）+ 支路 A 线性加成；**可选奖励池是内容条目池（三类混合），结构上装不下资源 element** — `combat-service.md:591`、`balance.md:364-366`。
- **仙玉唯一主动获取通道 = 稀有 AdventureEvent 产出**；不由付费 / 不由成就 / 不由 Finale / 不新增事件类型 — `currency.md:18-22`。付费面五项排除含「消耗型货币 / 硬通货」 — `monetization.md:139`。
- **Research 明令不给任何货币产出，也不另收货币代价** — `research/_index.md:50`、`:63`。
- **定价表 = 「商品族 × 稀有度」，格值 `(CostKey Currency, int BasePrice)`，篇章维不设**；币种由格决定、内容侧零书写位；「同一稀有档有的收灵石有的收仙玉」与「专收仙玉的商贾」是**已接受的编排不能** — `balance.md:279-290`。
- 可售出 ⟺ `ExchangeGoodsKind == CharacterItem`（**代码级常量判据**）— `exchange/_index.md:89-92`。
- 硬校验 `SellEnabled == true && SellRatePercent <= PackSellRatePercent → PushError` — `balance.md:306`。
- 刷新**恒以灵石计价**，首批一律填 0（关闭）— `exchange/_index.md:66`、`:84`。
- barter **一枚货币都不动** — `exchange/_index.md:29-30`。
- 掉落全部是**轮回级**随机（`RngStream.Reward` / `Shop`），不经 `AccountRng`；任何让篇章重试换掉落结果的设计都撞 `common-properties.md:46`。

**可作标尺的分母（本方案的反推底座）**

- ch1 参考构成 25 批次：`Finale` 1 · `Practice` 3 · `Standard` 3 · `Research` 3 · `Explore` 3 · **`Exchange` 8** · `Travel` 4 — `balance.md:245-260`。
- 逐章事件数 ch1 ≈ 25 / ch2 ≈ 26 / ch3 ≈ 32（`balance.md:506`）；常规战斗 6 / 7 / 7 + 每章 1 Finale = **7 / 8 / 8 = 23 场**（`balance.md:232`、`:598`）。
- **ch2 / ch3 的逐类型构成表零承载**——只有总数。
- ⚠ λ 反推式的败率 20%、`E[道念差]` 5 / 12 / 18 是**待实测格且明令不得引为承重依据**（`balance.md:240`）。本方案凡用到它们的地方逐处标注。

**方法论先例**

- `lifeSpanCost` 21 格定价表 + `LifeSpanCostTableData` 的形状（三章各一行的具名字段 + 内嵌 `Resource` 行类型 + 加载期校验表）— `balance.md:134-176`。
- 平衡资源**按三问判据逐份切、不设 `GlobalBalanceData` 兜底大表**；完整清单尚未定，逐份随消费者定名 — `balance.md:694-707`。
- 回寿量三档：**「占本章可用预算的百分比」是书写口径术语、不是运行期字段**，且⚠**不是新枚举** — `balance.md:262`、`:274`。

## 建议方案

### 1. 先补上缺失的分母：「本章预期灵石收入 `I(c)`」作为书写口径

`[既有推演]` 全库不存在「本章预期货币收入」这个概念（零承载），而消耗侧的每一次校准都需要它作分母——这正是「产出侧空白则无从反推消耗侧」那句话的机械含义。

建议**照回寿量的先例**引入一个**书写口径术语、不是运行期字段**（`balance.md:262` 的同款处置）：

```
I(c) = Σ 本章战斗的 BaseReward 灵石量
     + Σ 本章战斗的 道念差 × rewardPerMomentum[SpiritStone][c]
     + Σ 本章事件 outcome 的灵石产出
```

作者按它标定定价表，运行期不读取。它与「本章可用预算」（寿元侧）并列，构成经济侧的第二条书写口径。

**裁决①之后的连带（货币贯穿轮回、不每章重置）：** 货币与寿元自此**同形**——都是跨篇章结转的资源线。故标定分母有两个，须并用：

```
I(c)      = 本章新增收入（上式）
I_cum(c)  = Σ_{k ≤ c} I(k) − 已花销          ← 购买力的真实分母
```

`I(c)` 用于校准「本章掉多少」，`I_cum(c)` 用于校准「玩家此刻买得起什么」。寿元侧的「省着花有跨篇章回报」（`life-cycle-service.md:13`）自此对货币逐字成立。

### 2. 灵石的渠道口径：**战斗是主产出口，非战斗事件默认不给**

`[既有推演]` 由三条既有定案夹出，几乎没有自由度：

| 事件类型 | 灵石产出 | 依据 |
|---|---|---|
| `Combat`（三档） | **主产出口**（`BaseReward` + 支路 A 线性加成） | `combat-service.md:19`、`balance.md:364-372` —— 这是全库唯一已给出取值的货币通道 |
| `Research` | **不给**（已定案，非本方案裁量） | `research/_index.md:50` |
| `Exchange` | **不给**（建议） | 它是消费点；在消费点发钱等于自我折价。与 `ExperienceGrade` 档位偏置口径把 Exchange 定为 `None`（`game-progression.md:50`）同构、同理由 |
| `Travel` | **不给**（建议，并补一条禁令，见 §3） | 换图的代价是寿元（`travel/_index.md:58-60`）；顺带给钱会把这条代价抵消掉 |
| `Explore` | **不单独给** | 它解析为真身（`Combat : Exchange : Travel ≈ 5 : 3 : 2`），产出随真身走，本身再给一份即双记 |

⇒ **灵石 ≈ 战利品**。这条口径的好处是它把灵石收入钉在「战斗场数」这个已知且近似恒定的量上（7 / 8 / 8），而定价表**无篇章维**恰恰要求收入的形状是可控的。

**保留但收窄事件 outcome 通道**：`OutcomeRule.FixedResource(SpiritStone)` 白名单**不改**（改它会连带动仙玉的唯一通道），但编排口径写明「非 Combat 类型默认不填灵石，例外须在条目注释中给理由」，并落一条加载期**软**校验（见 §7）。

### 3. Travel 补一条货币产出禁令

`[既有推演]` `common-properties.md:111` / 校验 6 `:169` 已有「Travel 条目不得产出 `LifeSpan`」的禁令，理由是换图代价不得被同一事件抵消。**同一条理由对货币逐字成立**，而当前禁令只覆盖 `LifeSpan` —— 这是一处结构敞口（Travel 结构上可以给灵石，全库无一句禁止，也无一句允许）。

建议把校验 6 的谓词由 `ResourceKey == LifeSpan` 扩为 `ResourceKey ∈ { LifeSpan, SpiritStone, ImmortalJade }`。**纯加法，零字段增量。**

### 4. 货币量**不引入档位枚举**，就写绝对整数 —— 且这不是疏漏

`[既有推演]` 全库「内容侧不落裸数字、走枚举 × 平衡表映射」的先例有三处（`ExperienceGrade` / `HiddenStatGrade` / `SelectionWeightGrades`），而货币目前是白名单里唯一既无档位映射、又无书写口径的 key。看起来像漏网，**但推演下来它是对的**：

- 三处先例要枚举，是因为**同一个数在不同篇章意义不同**，必须先归一化再映射（经验要对齐逐章阈值 55 / 114 / 138；隐藏属性标定在 `[0,100]`；寿元预算逐章 1000 / 2000 / 3000+，故回寿量走百分比口径）。
- **货币恰恰相反：定价表明令不设篇章维**（`balance.md:284`、`:287`）⇒ 「40 灵石」在三个篇章买到的是同一格商品 ⇒ **绝对值本身就是跨章可比的**。再套一层「档 × 篇章标准值」只是把一个已经可比的数拆成两个书写位，反推口径不增加任何分辨率。
- 这与回寿量的处置**同向**：`balance.md:274` 明写三档「是量值口径，不是新枚举」，理由正是「走资源 element 路径的绝对量值套不进档位映射」。货币与寿元同为资源 element。

⇒ **不新增 `CurrencyGrade` / `RewardGrade`（全库零承载，勿臆造），`Magnitude` 与 `BaseReward` 保持裸整数**，改以「书写口径 + 加载期软校验」约束（§7）。

### 5. 篇章缩放由「给多少」承载，给出书写口径表 `S(c)`

`[既有推演]` `currency.md:16` 已把话说死：「**篇章间的经济差异应由「掉落多少货币」承载**，而不是让同一件东西在第三篇章更贵」。故缩放落在 `BaseReward`，不落定价表。

建议**篇章标准战斗灵石给予量 `S(c)`**（书写口径，非字段）与三档偏置：

| | ch1 炼气 | ch2 筑基 | ch3 金丹 |
|---|---|---|---|
| **`S(c)` 标准场（`Standard`）** | **15** | **35** | **60** |
| `Practice` ≈ 0.5 × S | 8 | 18 | 30 |
| `Finale` ≈ 2.0 × S | 30 | 70 | 120 |

ch1 收支校验（用 `balance.md:245-260` 的参考构成）：

```
BaseReward   3×8 + 3×15 + 1×30                    =  99
支路 A 加成   E[道念差] 5 × 1/点 × 胜场 5.6        ≈  28   ⚠ 用到两个待实测格
I(ch1)                                            ≈ 127
```

ch2 / ch3 无逐类型构成表，按 8 场战斗与 `S(c)` 粗算：`I(ch2) ≈ 300` · `I(ch3) ≈ 480`。三章比 ≈ **1 : 2.4 : 3.8**。

### 6. 定价表的灵石格：族系数 × 稀有度基价

`[通行做法]` 表是 5 族 × 5 档共 25 格，逐格拍值既无依据也无法维护。建议以**两个一维向量的外积**给出初值，落表时仍写 25 个独立整数（表结构不变，只是初值的来源可解释）：

- 稀有度基价（灵石）：`Tier1 20 · Tier2 40 · Tier3 80 · Tier4 160 · Tier5 320`（逐档 ×2）
- 族系数：`Card 0.75 · CharacterItem 1.0 · CharacterPower 1.5 · CultivationTechnique 2.0 · PlayerItem 2.5`
  - 依据：`Card` 是单张、`CultivationTechnique` 是整组替换的构筑单位（`deck/_index.md`）、`PlayerItem` 是**账号级**留存物，价值随留存期放大。

购买力校验（按裁决①的结转口径，用 `I_cum`）：ch1 `127`，主要遇到 Tier1–Tier2（20–40）⇒ 约 **3–4 次购入**，落在 8 次 Exchange 里 ⇒ 「常去逛、偶尔买」。ch2 新增 300、ch3 新增 480，若逐章基本花完则节奏稳定在每章 4–5 次；**若刻意屯攒，ch3 可一次拿下 Tier5（320）** —— 这正是结转口径下「省着花有跨篇章回报」的兑现形态，与寿元侧同构，属预期行为而非漏洞。

**结转口径反过来加固了「定价表不设篇章维」。** 原理由（「货币每章重置」）已被裁决①推翻，但结论仍成立，且有一条更强的支撑：**跨章结转要求价格跨章稳定**——若同一件东西在 ch3 更贵，攒下来的余额会被通胀稀释，「省着花有回报」这条激励当场失效。建议提炼时用这条替换 `balance.md:287` / `currency.md:16` 的旧理由。

### 7. 加载期软校验（新增两条，纯加法）

`[通行做法]` 书写口径若无任何机械护栏，会在内容铺开后静默漂移（这正是 `balance.md` 反复为其余旋钮设校验的理由）：

- **C-1**：单个 `EncounterSpec.BaseReward` 的灵石量 > `2.5 × S(该篇章)` → `PushWarning`（含条目 id 与实际值）。
- **C-2**：`eventType != Combat` 的条目携带 `FixedResource(SpiritStone | ImmortalJade, Gain)` → `PushWarning`（§2 的编排口径，例外允许但须被看见）。

两条都取 `PushWarning` 而非 `PushError`：口径是编排目标、不是结构不变式，硬失败会挡住合理的例外条目（与 `deck/common-properties.md` 第 20 条软检查同性质）。

### 8. 仙玉：每章 1–2 次、单次 1 / 2 / 4 枚

`[通行做法]` 约束极强（唯一通道 = 稀有事件产出、不得涓流化 `balance.md:374`、不得跨层输血），可自由度只剩「多稀有」「一次给几枚」。

- **出现频次**：每篇章期望 **1–2 次**携带仙玉产出的事件。载体是既有的 `SelectionWeightGrades` 的 `Rare` 档（`balance.md:330-339`），**不加字段、不加校验**——这与「稀有事件的稀有度由内容侧出现权重承载」的既有口径一致。
- **单次给予量**：`1 / 2 / 4` 枚（小 / 中 / 大），三章统一（同 §4，绝对值跨章可比）。
- **每章新增仙玉 `J(c)` ≈ 2 / 3 / 5 枚**（频次 × 均量，随篇章事件数 25 / 26 / 32 微升）；按裁决①结转，**累计 `J_cum` ≈ 2 / 5 / 10 枚**。

⇒ 与 §9 的仙玉基准价（`PlayerItem` `1 / 2 / 3 / 5 / 8`）恰好对齐成一条递进曲线：ch1 只够 Tier1–Tier2、ch2 够到 Tier3–Tier4、**ch3 攒满才够 Tier5（8 枚）**。「顶档仙玉商品 = 一次轮回至多一件」由算术本身保证，不需要任何新机制。这条对齐是裁决①（结转）带来的净收益——每章重置口径下 ch1 仅 2 枚、顶档商品在整个轮回内不可达。

### 9. 仙玉计价的格：**排除 `CharacterItem` 一族**，使净产出敞口结构性归零

`[既有推演]` `balance.md:376` 把「免费取得的仙玉计价法宝售出即净产出」写成**被接受的敞口**，交给统计校准把关。但把它与另一条既有定案并排看，敞口可以被**结构性关掉**：

> 可售出 ⟺ `ExchangeGoodsKind == CharacterItem`（代码级常量判据，`exchange/_index.md:89-92`）

⇒ **只要仙玉一枚都不落在 `CharacterItem` 行，「售出产仙玉」就不可能发生**，无需任何新机制、无需统计盯防。在仙玉预期收入只有个位数（`J(c) ≈ 2–5`）而回收价有 `Clamp >= 1` 下限的量级上，这条尤其要紧：3 枚定价 × 40% = 1.2 → 1，任何一件免费掉落的仙玉法宝都稳产 1 枚，占一章收入的 20–50%。

建议的币种分布（其余 18 格全部收灵石）：

| 格 | 币种 | 理由 |
|---|---|---|
| `PlayerItem` × 全五档 | **仙玉** | 账号级留存物，是「标志性」的天然落点；且它不可售出 ⇒ 零敞口 |
| `CharacterPower` × `Tier4` / `Tier5` | **仙玉** | 神通高档位，不可售出 |
| `CultivationTechnique` × `Tier5` | **仙玉** | 顶档功法 = 整组卡替换，不可售出 |
| `CharacterItem` × 全五档 | **恒灵石** | 唯一可售出族，一格仙玉都不给 |

仙玉基准价（与 `J(c) ≈ 2–5` 对齐）：`PlayerItem` `1 / 2 / 3 / 5 / 8` · `CharacterPower` T4 `3` / T5 `5` · `CultivationTechnique` T5 `6`。

⇒ **一章能且仅能兑现约一件仙玉商品**，与「不随每场战斗涓流发放，只在少数标志性事件上出现」（`currency.md:18`）逐字对齐。

**代价如实写下**：从此**编排不出「以仙玉计价的法宝」**。这是在既有的「币种与族 × 档绑死」代价（`balance.md:290`）之上再收一格。

### 10. 两档回收率取值

`[通行做法]` 区间已给（商店档 30–50%、随售档「显著低于」、硬校验 `SellRatePercent > PackSellRatePercent`）。建议初值：

- `SellRatePercent`（逐条目）默认 **40%**，可编排区间 30–50%。
- `PackSellRatePercent`（全局单值）**15%**。

15% 使「清仓不构成经济来源」（`balance.md:307` 的论证基底）成立：一件 Tier2 法宝（40）随售得 6，不足半次购入；而商店收购（16）恒显著更优，硬校验保证之。

## 备选方案（已考虑并否决）

- **引入 `CurrencyGrade` 枚举 × 篇章标准值**（照 `ExperienceGrade` 范式）—— 否决理由见 §4：定价表无篇章维 ⇒ 绝对值已跨章可比，枚举只增书写位不增分辨率；且与回寿量「量值口径不是新枚举」的同类处置相抵。

## 与既有决策的张力

- **🔴 裁决①推翻了 `currency.md:21`「不由 Finale 发放」的理由，该否决须重立。** 原文的论证是「轮回级货币在篇章收口处发放、随后即被清理，玩家拿到手也几乎无处可花」——**结转口径下这句整条失效**：Finale 发的货币可以带进下一篇章正常花掉。
  否决**结论**建议保留，但换一条能站住的理由：**Finale 的 `BaseReward` 本就是战斗货币通道的一部分**（§5 给它 `2.0 × S`），另设一条「篇章收口发放」等于对同一场战斗重复记账，且会让 ch3 Finale（轮回终点）的发放彻底无处可花——**理由由「全都无处可花」收窄为「重复记账 + 末章确实无处可花」**。此处需在 `/analyze-new-ideas` 提炼时明确落笔，不要让旧理由留在文档里。
- **`balance.md:376` 的「净产出敞口是被接受的取舍」**：§9 把它由「接受并盯防」改为「结构性关闭」。这不是推翻该决定的**判断**（敞口确实不需要新机制去堵），而是发现了一条**零成本的关闭路径**；代价是失去「仙玉计价的法宝」这一编排手段。需用户确认这个交换划算。
- **`currency.md:38` 的「产出侧一片空白」措辞**与 `balance.md:368-372` 已给出的灵石单价表相抵。建议在提炼时把该句改为「基线量与渠道口径未定」。

**① 货币究竟是「每章重置」还是「贯穿整个轮回」？——两处文档已写成事实，但全库零机制承载。**

`currency.md:16` 与 `balance.md:287` 逐字写着「货币随轮回清理、**每章重置**，与寿元的跨篇章结转不同」，`currency.md:21` 亦以「篇章收口处发放、随后即被清理」为由否决 Finale 发货币。但：

- 存档点清单里没有这个落点；`CharacterProfile` 上也没有任何篇章维的货币字段。

⇒ 这条要么是**既定设计而机制未落笔**（则须补一条 ChapterManager 职责 + 一个存档点），要么是**措辞漂移**（则须改这两处 + `currency.md:21` 的否决理由）。它改变经济的闭合单位，因而改变本方案的全部标定：

| 选项 | 后果 |
|---|---|
| **A（推荐）· 确认每章重置** | 经济逐章闭合，`I(c)` 就是完整分母，本方案数值原样成立。代价：章末剩余归零，玩家需要一个「花掉」的提示；且 `J(c) ≈ 2` 的 ch1 几乎买不起任何仙玉商品（表中最低 1 枚，仅够 `PlayerItem` Tier1）。 |
| **B · 改为贯穿轮回不重置** | 与寿元结转同形、少一条特例规则；仙玉可跨章攒（ch3 累计 ≈ 10 枚 ⇒ 能兑现 Tier5），「稀有」的表达更连贯。但 `currency.md:16` / `balance.md:287` / `:21` 三处措辞须改写，且定价表「不设篇章维」的**理由**（其依据正是「每章重置」）需要换一条支撑。 |
