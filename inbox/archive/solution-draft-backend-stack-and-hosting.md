# 方案草稿 — 后端技术栈 · 托管 · 同步与会话的实现落地 · 可观测性

## 问题

后端尚未开工（`backend-feature-branch/` 只有 README），而**六份契约全部成文**且再无取值留白。全库唯一的结构性前置就是本条：`systems/`（三份服务文档）与 `operations/`（六份运维文档）的全部展开、以及 `requirements/` 的推导，都以「栈落定」为条件（`open-questions.md`「最短解锁路径」第 2 条）。

契约刻意把一批实现语义停在语义层并显式挂账到本分片，且**明写「落定后进 `operations/`、不回头改契约」**：`revision` CAS 的存储与并发控制 · `(accountId, pushId)` 幂等记录的存储与事务边界 · push 滥用阈值的实现 · 跨区域拓扑 · profile 体积软告警 · 会话记录的存储与同事务吊销 · `signin` 幂等回放记录 · token 签名密钥的保管与轮换 · 三条同步探针与一条透明路径缺失告警。

**它们不是九个独立的选型，而是同一个选型的九个侧面**——本草稿先立筛选判据、再用判据淘汰候选、最后只把真正无客观最优的三项交回用户裁决。

## 建议方案

### A. 先立判据：从 C1–C19 推出的六条筛选闸

`[既有推演]`

一个候选组合只要在下面任一条上不成立，就**直接出局**，不进取向。

| 闸 | 内容 | 依据 |
|---|---|---|
| **G1 事务闸** | 存储必须能在**一次事务**内原子地写：profile 文档 · `revision` 计数器 · 幂等记录（三处，跨表） | C2 · C4 |
| **G2 线性化闸** | 同一 `accountId` 上的读改写必须可线性化，且计数器严格单调 ⇒ **多主 / 最终一致复制的写入拓扑出局** | C2 · C3 |
| **G3 读路径闸** | 玩家读路径不得无条件落在滞后副本上 ⇒ **「读写分离、pull 无条件打异步只读副本」形态出局** | C1 |
| **G4 合并语义闸** | 存储或应用层必须能表达**顶层键整键替换、不递归**的浅合并，且不得退化为 RFC 7386 | C6 |
| **G5 类型化闸** | 必须能把白名单内的路径还原成**类型化值**再比较（时间按时刻、数组有序逐元素） | C7 |
| **G6 体积闸** | 单条 profile 记录必须能安全承载 **> 512 KB**（512 KB 是软告警不是上限，正常账号会接近它） | C15 |

### B. 用判据淘汰：三条唯一淘汰的否定结论（不进取向）

`[既有推演]`

- **多主写入 / 跨区域双写 `revision` —— 出局。** 账号级严格单调递增计数器在多主下无法维持，而云端权威的全部力量建立在它上面（契约已在 `profile-sync.md` §8 与「备选方案」中直接否决，本条只是把它带进选型）。**推论：全球多活、Spanner 式多区域强一致写、CRDT / 最终一致复制，全部不在候选集内。** 跨区域延迟由客户端的非阻塞 push 通道吸收（pillar #4）。
- **DynamoDB（及任何单条记录硬上限 < 512 KB 的 KV）—— 出局（G6）。** DynamoDB 单 item 硬上限 400 KB，而 `profile-sync.md` §12 把 **512 KB 定为软告警**——即正常账号预期可以接近并越过 512 KB。一个把软告警阈值抬成硬失败的存储，会在正常账号上产生「push 永远失败」，且失败面是玩家进度。**这不是容量调优问题，是判据不满足。**
- **MySQL 的 JSON 合并原语 —— 不可用于承担 C6（不是「MySQL 出局」，是「不能靠它的原语」）。** `JSON_MERGE_PATCH` 实现的正是 RFC 7386（以 `null` 删除），而契约**明确否决**它；`JSON_MERGE_PRESERVE` 是递归合并，同样不符。若选 MySQL，浅合并必须在应用层手写——把一条承重的契约语义从存储不变式降级为应用代码纪律。**这是选型的一个实质差别，不是口味差别。**

同样已被既有决策排除、不必再议的形态（逐条回链，不展开）：托管身份服务作身份主体（`ADR-0010`）· 渠道回调直接写库（`ADR-0007`）· 后端主动推送 / 长连接通道（`ADR-0013` · `auth.md` 备选）· flags 放 CDN 域（`ADR-0002`）· 共享 DTO 程序集（`ADR-0003`）· gRPC / Protobuf（`ADR-0003`）。

### C. 规模形状：为什么「不需要分片」是一条判据而不是乐观估计

`[既有推演]`

契约已经把写入频率钉死了（C18）。设**峰值同时在线账号数 = C**：

```
push   ≈ C / 60      req/s      （稳态每账号 1 次 / 分钟，profile-sync §10）
refresh≈ C / 900     req/s      （access token TTL 15 分钟，auth §8）
pull   ≈ 启动一次 + 购后一次     （远小于 push）
verify ≈ 每账号个位数 / 年        （purchase §7）
```

| C（峰值同时在线） | 写 QPS ≈ C/60 |
|---|---|
| 1 000 | ≈ 17 /s |
| 10 000 | ≈ 167 /s |
| 50 000 | ≈ 833 /s |

每一次 push 是一个**小事务**（更新一行 jsonb + 插入一行幂等记录）。一台托管的中等规格单主关系库在这个形状下，到**同时在线万人量级都不需要分片**。

**这条推导有两个直接后果，都是承重的：**

1. **G3（读路径闸）的最简兑现是「玩家读路径全部走写入区」**——它是「会话粘滞」的极端形态（粘滞到主）。在上述量级下，主库同时承担读写毫无压力，因此**不必**引入 `revision` 下界等待这类更复杂的机制。只读副本因此**只承担灾备与离线分析，不承接任何玩家读路径**。
2. **不要为水平扩展预支复杂度。** 分片、多主、读写分离全部与 G2 / G3 相抵；而它们要解决的规模问题，在契约定义的流量形状下不存在。**规模真的到来时，纵向扩容 + 按 `accountId` 的单主分区（每个分区内仍线性化）是保住 G2 的唯一扩展方向**，不是本次要做的事。

> **DAU 预期未知**（不在本库范围），故本节只给算式与量级判断，**不定实例规格**——那需要成本模型（`06` 的最后一条，不在本批）。

### D. 数据库：托管 PostgreSQL（单主 + 同城/跨可用区同步副本）

`[既有推演]` + `[通行做法]`

**推荐 PostgreSQL**，因为它在六条闸上逐条成立，且其中三条是**用数据库不变式直接兑现契约承重条款**，而不是靠应用代码纪律：

| 闸 | PostgreSQL 的兑现 |
|---|---|
| G1 事务 | 三张表一次事务，零分布式事务 |
| G2 线性化 | 单主 + 行级锁；CAS = 一条 `UPDATE … WHERE account_id = ? AND revision = ?`，**受影响行数即三分支判据** |
| G3 读路径 | 玩家读走主；流复制副本只做灾备 / 分析 |
| G4 合并语义 | **`jsonb` 的 `\|\|` 运算符恰好是「顶层键整键替换、不递归」**——与 `profile-sync.md` §3a 逐字吻合，且它**不是** RFC 7386（无 `null` 删除语义），与 C6 的否决面天然不冲突 |
| G5 类型化 | `jsonb` 按路径提取 + 应用层按 §5c 的四行口径类型化比较；不透明段一字不动 |
| G6 体积 | `jsonb` 走 TOAST + 压缩，单值上限 1 GB，512 KB 毫无压力 |

**另外三处它把契约条款变成数据库不变式：**

- **活跃会话上限 1**（C13）= 部分唯一索引 `UNIQUE (account_id) WHERE revoked_at_utc IS NULL`。
- **`(accountId, deviceId)` 唯一**（C13）= 普通唯一约束。
- **`receiptId` 全局唯一、不带账号前缀**（C5）= 全局唯一索引；「已被其他账号核销」因此是一次索引冲突而不是一次应用层查重。

**明确不引入的东西：** 不引入独立的文档数据库（profile 已是 `jsonb`）；不引入消息队列（本域没有需要削峰或跨服务解耦的写入——风控事件与告警走日志 / 指标出口即可）；不引入分布式事务协调器（G1 已在单库内满足）。

**引入一个托管 Redis**，用途**收敛为两项**：① 限流计数器（见 F）；② 日后 flags 按账号解析结果的缓存（**归 `04` / W4 裁决是否引入**，本方案只声明「若引入，缓存键必须含 `flagsVersion`」，权威 `ADR-0009`）。**Redis 不持有任何权威状态**——它挂掉时限流退化为不限流（记告警），不影响任何正确性语义。

### E. 表结构与事务边界（可 derive 的落地面）

`[既有推演]`

> 字段名用 `snake_case`（库内约定，与报文的 lowerCamelCase 在序列化边界一次映射）。这里只给**承重列**，不是完整 DDL。

```
account (account_id PK, created_at_utc, status)
identity (account_id FK, channel, channel_user_id, id_kind, bound_at_utc,
          UNIQUE (channel, channel_user_id),          -- auth.md §1a
          UNIQUE (account_id, channel))               -- 同一 channel 最多一条

profile (account_id PK/FK, revision BIGINT, schema_version INT,
         doc JSONB, updated_at_utc)                   -- doc 含透明 + 不透明两段

push_idem (account_id, push_id, new_revision, accepted_at_utc,
           PRIMARY KEY (account_id, push_id))         -- 按 accepted_at_utc 月分区
receipt_idem (receipt_id PK, account_id, bundle_grant_ordinal,
              revision, verified_at_utc, status)      -- 全局唯一键，永不删除

session (sid PK, account_id, device_id, refresh_key_id, generation,
         issued_at_utc, refresh_expires_at_utc, absolute_expires_at_utc,
         revoked_at_utc, revoked_reason,
         UNIQUE (account_id, device_id),
         UNIQUE (account_id) WHERE revoked_at_utc IS NULL)
signin_replay (channel, identifier_mac, device_id, sid, generation, created_at_utc,
               PRIMARY KEY (channel, identifier_mac, device_id))   -- 60 秒窗口

config_knob (key PK, value, updated_at_utc, updated_by)  -- 见 H
```

**事务边界表（每一行都是一次事务，并发单元一律是 `account` 行）：**

| 操作 | 同一事务内的写入 | 并发获取 |
|---|---|---|
| `push` | `profile.doc` 浅合并 · `revision += 1` · `push_idem` 插入 | 条件 `UPDATE … WHERE revision = :baseRevision` |
| `verify` | `profile.doc` 的 `/entitlement/bundleGrantOrdinal += 1` · `revision += 1` · `receipt_idem` 插入 | `SELECT … FOR UPDATE` on `account` |
| `signin` | **①先**吊销其余会话 · **②后** upsert 本设备会话 · `signin_replay` 插入 ·（新账号时）建 `account` + `identity` + profile 骨架且 `revision = 1` | `SELECT … FOR UPDATE` on `account`（新账号时靠 `identity` 唯一索引兜住并发建号） |
| `refresh` | `session.generation += 1` · `refresh_expires_at_utc` 顺延（`absolute_expires_at_utc` **不动**） | `SELECT … FOR UPDATE` on `session` |
| `bind` / `unbind` | `identity` 增删 · `profile.doc` 的 `/accountInfo/identities` 更新 · **`revision += 1`** | `SELECT … FOR UPDATE` on `account` |

**四条承重的实现纪律（写错任一条都会在正常账号上产生故障）：**

1. **`signin` 的两步必须与契约伪码相反地执行：先吊销其余、再写本设备。** 契约 `auth.md` §4a 的伪码是「先写入本设备、后吊销其余」，但只要用**部分唯一索引**兑现「活跃会话上限 1」，先写入就会在语句间瞬时出现两行活跃会话而当场违反索引（Postgres 的部分唯一**索引**不能声明为 `DEFERRABLE`）。**两步在同一次事务内 ⇒ 中间态不可观测 ⇒ 反序不改变任何外部语义**，契约无需改动，但实现者不得照抄伪码顺序。
2. **CAS 用受影响行数分支，不要先 `SELECT` 再 `UPDATE`。** `UPDATE profile SET … WHERE account_id = ? AND revision = ?` 返回 0 行时，再读一次当前 `revision` 来区分 `sync.conflict`（落后）与 `sync.revision_ahead`（领先）。这一条自然满足 C2 的「禁止两步非原子」。
3. **判定顺序照契约写死**：`schemaVersion` 闸门 → 信封形状 → CAS → 回声校验 → 写入（`profile-sync.md` §4）。回声校验读的是**本事务内已加锁的当前值**，不是事务外的一次预读。
4. **`reason` 与 `sourceCode` 这类零判定权字段，必须在校验中间件里显式关闭 enum 严格校验**（C8 / `ADR-0017`）。多数 Web 框架的 schema 校验默认对 enum 严拒——那会让客户端一次枚举增员变成一次线上故障，且**后端会成为客户端的发版阻塞点**，与 `ADR-0017` 正面冲突。**驱动判定的枚举（`platform` · `channel` · `code`）反之仍是封闭校验面**——校验策略在字段级分成两类，不能一刀切。

### F. 同步侧实现语义的逐条落地

`[既有推演]`

- **`(accountId, pushId)` 幂等记录**：`push_idem` 表，与 `revision` 写入同一事务（C4）。命中 = 主键冲突 ⇒ 读出 `new_revision` 回 `{ newRevision, deduplicated: true }`，**不再 `+1`、不重写 profile、不做 body 深比对**。
- **两个保留旋钮取「先到者」，且实现只执行时间那一半。** 契约给了两个旋钮（最近 200 条 · 30 天）。稳态下 30 天内的 push 数远超 200，故**活跃账号恒由 200 条先到、闲置账号由 30 天先到**——两者都是上界，不冲突。**建议实现只做按 `accepted_at_utc` 的月分区滚动（30 天），把 200 条降级为观测指标而非实时裁剪**：按账号排序删除代价高，而**放宽记忆量只会让幂等窗口更长，即更安全**（契约 §9 已明写「窗口过期不会造成错误接受，只会把一次重试变成一次进度丢失」）。体量估算：活跃账号 30 天约 1 200 行 × ~120 B ≈ 144 KB/账号。
- **push 滥用阈值 60 次 / 分钟 / 账号**：Redis 计数器 `INCR` + `EXPIRE`，**键必须是 `accountId` 维度，不是 IP**（移动网络 NAT 下 IP 维度会误伤整个小区）。触发 → `rate.limited`（`Retryable`）+ `Retry-After`。**绝不映 `Conflict`**（`envelope.md` §6 台账承重项）。Redis 不可用 → **放行并记一条告警**，不阻断玩家（限流是防滥用，不是正确性的一部分）。
- **⚠ 网关层不得对 `/v1/auth/refresh` 施加任何返回 `rate.limited` 的限流**（C11）。契约刻意把 refresh 的错误清单收紧为两条，以保客户端两条处置路径在报文层面互斥；网关默认的全局限流会静默破坏它。建议对 refresh 只做**记账 + 告警**，不返回限流码。若日后确认必须限流，须按 `auth.md` Open questions 回改契约**并给客户端第三条路径**——见「与既有决策的张力」。
- **跨区域拓扑**：**单区域部署，不做跨区域多活**（C3 已定单写入区）。副本形态：主库 + **同城跨可用区同步/半同步备**（RPO≈0 的故障切换）+ 一份跨区域异步副本仅作灾备与备份恢复演练。**任何副本都不承接玩家读路径**（C1 / G3）。海外扩展（`ADR-0003` 第三档渠道尚未展开）届时是**另一套独立部署 + 独立 `accountId` 空间**，不是本套的跨境拉伸。
- **单账号 profile 体积软告警（512 KB）**：每次 push 写入后取 `pg_column_size(doc)`，出一个 histogram 指标 + 「超阈值账号数」gauge。**软告警绝不拒绝上行**（契约无拒绝语义）。阈值是可热调旋钮（见 H），待实测校准。

### G. 会话记录与 token 密钥

#### G-1. 会话表的并发语义

`[既有推演]`

见 E 的表结构与事务表。三条要点：

- **`(accountId, deviceId)` 唯一 ⇒ 每个 (账号, 设备) 恰一行，同设备重登是原地 `UPDATE`**，不产生第二条记录、不留 `revoked` 堆积（契约 §4a 明写这正是该约束的目的）。
- **「上限 1」由部分唯一索引承担**，不靠应用层检查——它是并发下唯一可靠的形态。
- **并发单元统一为 `account` 行**：会话写入与 profile 写入争用同一把锁，因此「一台设备正在 push、另一台正在 signin」这一情形有确定的串行顺序，不需要第二套并发模型。

#### G-2. 「回放完全相同的那一对 token」的落地（C12 的实现闸）

`[通行做法]` + `[既有推演]`

契约在**三处**要求回放**完全相同**的 token 对：`refresh` 的 60 秒宽限窗口 · `signin` 的 60 秒幂等回放窗口。朴素实现会被迫**把活凭据明文缓存 60 秒**——这是一个可以避免的安全代价。**两条推论直接约束选型：**

1. **access token 的签名算法必须是确定性的，且 `iat` / `exp` 必须从会话状态派生而非从 `now` 取。**
   - **推荐 EdDSA（Ed25519）**：签名确定性（同输入同输出）· 非对称（网关可用公钥离线验签，兑现 C10，私钥只在签发服务）· 密钥与签名体积小。
   - **ES256（ECDSA）不满足**：其签名含随机 `k`，同一 payload 两次签名字节不同 ⇒ 回放拿不到「完全相同」的 token。**这同时是 C9 的一个具体注脚：内容签名用 ES256 是因为要与客户端内置的验签实现对齐，而会话 token 的约束完全不同——两把钥匙连算法都不该相同。**
   - HS256 也确定性，但对称密钥必须分发给每个验签点，与 C10 的「网关离线验签」组合起来会把签发密钥铺开。作为备选保留。
2. **refresh token 做成可确定性重算的派生串，而不是纯随机串。**
   建议形态 `<sid>.<generation>.<mac>`，其中 `mac = HMAC-SHA256(refreshSecret[kid], sid || ':' || generation)` 截断编码。它满足契约对 refresh token 的全部要求（不透明、高熵不可预测、必须查库才能吊销——服务端仍要读 `session` 行判定吊销态），同时：
   - **宽限窗口回放** = 用 `generation - 1` 重算并比对，命中即回放同一对，**无需保存任何明文**；
   - **窗口外重放判泄漏** = 收到的 `generation < 当前 generation - 1` ⇒ `TokenReuseDetected` → 吊销该账号全部会话；
   - `session` 表因此**不必存 `refresh_token_hash`**（存也可以，但比对靠重算更省一次索引查找）；表里只需 `refresh_key_id` 与 `generation` 两列。
   - **备选（更简单、代价明写）**：Redis 缓存上一代 token 对 60 秒。省掉派生逻辑，代价是活凭据明文在缓存里存活 60 秒，且 Redis 失效 = 弱网重试的玩家被赶回验证码输入框。**推荐派生式。**
3. **`signin` 幂等回放记录放 Postgres 而非 Redis。** 频率极低（每玩家每绝对寿命周期一次），而它需要**与会话写入同一事务**才能保证「回放与吊销不打架」；且它的键含**手机号 / 邮箱这类个人信息**，必须以 `identifier_mac = HMAC(identifierSecret, identifier)` 存储、**绝不明文落库落日志**（C19 / PIPL）。保留期 = 窗口 60 秒 + 余量，建议**行保留 10 分钟后清理**（一次轻量定时删除即可，不必分区）。

#### G-3. token 签名密钥的保管与轮换

`[通行做法]`

| 项 | 建议 | 与内容签名密钥（`04`）的差别 |
|---|---|---|
| 保管 | 云 KMS 托管，**私钥不落盘、不进环境变量、不进镜像**；签发走 KMS Sign API（签发频率 ≈ `C/900` req/s，极低，KMS 调用成本与延迟可忽略，换来完整审计） | 同为 KMS，但**是两个独立密钥、两套权限、两条审计线** |
| 标识 | JWT header 带 `kid`；`envelope.md` §6 已为 `auth.token_invalid` 写下 `message` 必含「未知 kid」⇒ **`kid` 概念已隐含在契约里** | 内容 manifest 的 `keyId` 是另一套命名空间 |
| 轮换窗口 | **旧 `kid` 只需保留 ≥ access token TTL（15 分钟）+ 时钟偏移余量；建议 1 小时后退役**。轮换**纯服务端、零客户端义务、不需要发版** | **须跨一个完整客户端发版周期**（先发内置新旧两把公钥的客户端版本 → 覆盖率足够后才切私钥） |
| 频率 | 建议 90 天例行轮换 + 疑似泄漏时立即轮换（立即轮换的代价上限 = 15 分钟内的在途请求） | 例行轮换受发版节奏支配，无法「立即」 |
| refresh secret | 同 KMS 管理，带自己的 `kid`（写进 `session.refresh_key_id`）；轮换时旧 secret 保留至最长 refresh 链自然到期（绝对寿命上限 60 天） | — |

> **这张表本身就是把「不要混为一谈」写成可核对的东西**：两把钥匙的算法、轮换窗口、是否牵动客户端发版，三项全不相同。

**版本兼容矩阵**（`envelope.md` §7e）落 `operations/version-matrix.md`，**其数据形态即这张旋钮表的一员**（支持的 `appVersion` 下界 · 并存 URL 主版本 · 并存 `manifestSchema` / `schemaVersion` 集合 + 各自下线计划）。它必须与判定逻辑同处，且**客户端不持有任何副本**。运营提升 `appVersion` 下界的生效点是玩家**下一次登录**，运维流程须据此说明「提升下界后多久覆盖存量会话」，而非假定即时生效——上限即 refresh 绝对寿命 60 天（`auth.md` §5b 的收口正是为这条服务的）。

**发布流程：**

- 镜像 tag = commit sha，**不可变**；三环境跑同一个 artifact，只有配置不同。
- **DB 迁移与代码发布分离，走 expand → deploy → contract 三步**：强制在线 + 云端权威 ⇒ 没有停机窗口。
- **迁移只前滚、不回滚**——与 flags 的 O4「回滚 = 一次以历史内容发起的更大版本发布」同构（`operations/_index.md`）。代码可回滚镜像 tag，**schema 不回滚**。
- **契约变更的完成判据六条 + 三条机检断言**（`contracts/_index.md`）挂在 CI 上；**承载位置本身是 `01` 的一条待答项，不在本批**，但本方案的 CI 形态天然能承接它（见「越界发现」）。
- **⚠ 发布前置清单 —— 首个真实账号建号之前必须完成的不可逆项**（`ADR-0014` 的前提①「线上无真实账号数据」在那一刻永久失效）：
  1. 全部透明路径的命名定稿（此后重命名不再能一次性切换）；
  2. `Source` / `AccountStream` 的成员名与整数值冻结（`ADR-0012` · `ADR-0006`）；
  3. `accountId` 形态定稿（ULID / 26 位 base32，`ADR-0010`）；
  4. 微信开放平台资质 + 以 `unionid` 建 identity（`auth.md` §3a，**归 `06` 但不在本批**）。
  **这四项共用同一个不可逆时刻，应作为一份清单一起过闸，而不是各自记在各自的文档里。**

### I. 区域与合规托管

`[既有推演]` + `[通行做法]`

- **主区在中国大陆境内**（C19 / C14）。个人信息（手机号 / 邮箱 / 实名信息 / 验证码记录）**不出境**；`identity` 与 `profile` 建议**分表分权限**（甚至分库），使注销与数据导出（`compliance.md`）能按数据类别定位，且日常玩法路径不需要触达个人信息表。
- **备案**：域名 ICP 备案 + 面向国内发行的游戏资质，是**上线时序的前置**而非技术选型的自由度。它与上面的「发布前置清单」同批推进。
- **日志脱敏是强制项，不是「有更好」**：`envelope.md` §5a 已定 `message` 不得含 token / 完整凭据 / 密钥，账号与 `pushId` 按前缀截断。**建议在日志中间件里统一实施**（一处白名单式序列化），而不是各处自觉——`operations/_index.md` 已把它列为运维范围。手机号一律以 `identifier_mac` 或掩码出现。
- **不做跨境多活**（B 已论证）；海外扩展是另一套独立部署。

### J. 可观测性口径

`[既有推演]` + `[通行做法]`

**基座**：结构化 JSON 日志 + OpenTelemetry（指标 / 追踪，栈中立）。`X-Request-Id` ↔ 错误体 `requestId` ↔ 服务端日志 `trace_id` 三者贯通——它是**跨进程边界唯一的定位标识符**（`envelope.md` §5 · `operations/_index.md`）。

**三条同步正确性探针 + 一条告警，逐条给口径与阈值：**

| 探针 | 指标形态 | 告警口径 | 依据与理由 |
|---|---|---|---|
| **本地领先** `sync.revision_ahead` | 计数器，标签 `app_version`（**不以 `accountId` 作标签**——高基数；账号维度落日志） | **阈值 = 0，任一次即告警** | 契约 §8 明写它的服务端含义是「客户端信封被改写**或后端发生过回滚**」，后者是**后端自己的事故信号**。它是不可能态，不该有基线 |
| **`pushId` 去重命中率** | `deduplicated = true` / 总 push，滑动 1 小时 | 相对基线突增（建议 3×）即告警 | 它度量的是「应答丢失率」。突增 = 客户端重试风暴或链路劣化 |
| **复算不一致率** | 分子**必须按校验类型拆成三个**（① `roll` 逐位比对 · ② 单向蕴含「未命中却新增」· ③ 结构不变式），分母 = `finaleWinOrdinal` 递增的 push 次数 | **① / ③ 的全局率突增 ⇒ 疑似我方实现差一位或客户端 bug（工程告警）；② 的长尾单账号累计 ⇒ 作弊嫌疑（风控入口，归 `02`）** | 不拆类型这条指标就没用：①③ 与 ② 的**处置完全不同**。`profile-sync.md` §7 已把三条校验分列，指标应逐条对位 |
| **透明路径缺失** | 计数器，标签 `path`（白名单仅十三条，**低基数、可安全作标签**）+ `app_version` | 某条 `path` 的缺失率由 ~0 跳到显著非零、且集中在某个 `app_version` ⇒ 告警 | 契约 §5 明写「后端对缺失的透明路径记告警级台账、**不拒绝上行**」，这条告警是**路径漂移唯一的可见面** |

**⚠ 透明路径缺失的判定必须带前提，否则告警会被噪声淹没：** §3a 的浅合并 diff **常常不含** `accountInfo` 或 `entitlement` 顶层键。**只有当某个顶层键出现在本次 `playerDiff` 中时，才检查该键下的白名单路径是否缺失**——这正是 §3a 末尾那条推论（「该顶层键出现」⟺「这些透明字段本次有新值」）的直接用法。不带这个前提，每一次普通 push 都会误报。

**其余最小集合**（按域列，不展开）：

- **RED 三件套**：每端点的请求率 / 错误率 / 时延分位（p50 / p95 / p99）。
- **按 `code` 的错误分布**——`envelope.md` §6 台账的 21 个 `code` 各一条时间序列。**新增一个未登记的 `code` 会在这里显形**，这是台账 ⇔ 实现一致性的一条廉价旁证（正式的机检断言归 `01`）。
- **CAS 冲突率**（`sync.conflict`）与**回声校验拒绝率**（`sync.conflict` + `detail.field` 非空）**必须分开计数**：前者是正常的多设备 / 弱网现象，后者是客户端 bug 或改包（`profile-sync.md` §5c 要求它同时打一条风控事件）。共用一个 `code` 是契约的刻意选择，但**指标层必须能分辨**——否则 §5c 的可观测性设计落空。
- **会话面**：活跃会话数 · 挤下线率（`SignedInElsewhere`）· `TokenReuseDetected` 计数（**任一次即值得看**）· 各 `revokedReason` 分布。
- **`reason` 聚合维度的孤儿取值告警**：`ADR-0017` 明写「清单不是校验闸，拼错的成员名只会在聚合维度里多出一个孤儿取值，靠看板发现」——**这条告警就是那个「看板」的兑现**，缺了它 `ADR-0017` 接受的代价就无人承接。
- **数据面**：主备复制延迟 · 连接池饱和度 · 最长事务时长 · `profile.doc` 体积分布（见 F）。

## 备选方案（已考虑并否决）

- **Serverless 函数（FC / SCF）+ 托管 Postgres** — 与低 QPS 形状本身相容，但三处摩擦：① 「读全走主」下每个实例都要连主库，函数实例数波动会打爆连接数，必须再引一层连接代理；② 冷启动使 p99 时延不可控，而 push 是玩家进度的唯一出口；③ 长时 / 定时任务（幂等分区滚动、体积扫描、日后的注销冷静期状态机）需另接调度器。收益（免运维）在只有一套小服务时并不显著。**保留为取向的备选，不是硬淘汰。**
- **单台 VM 自建全栈** — 成本最低，但备份 / 时间点恢复 / 故障切换全部自建，且 `ADR-0009` O3 明确要求「备份恢复后取 `max(恢复值, 高水位)` 并强制跳号，且『版本号未倒退』列为恢复演练的必检项」——一个没有可演练恢复流程的部署形态无法满足它。
- **引入消息队列做 push 的异步落库** — 会当场破坏 C2（线性化读改写）与「push 应答必须回 `newRevision`」的同步语义，且需要第二套顺序保证。契约 §10 已按同一理由否决过「服务端合并窗口」。
- **读写分离：pull 打只读副本** — 直接违反 C1 / G3。失败形态在契约里写得极具体：玩家付了钱、客户端判定「无待兑现」且**不会再重试**（`purchase.md` §6）。
- **用 `revision` 下界等待兑现读己所写**（读副本 + 等待副本追上某个 `revision`） — 契约允许，但在本方案的量级下是纯粹的复杂度：它要求读路径携带并理解 `revision` 下界、要求副本暴露复制位点、且失败时要退化回主。**「读全走主」是同一条要求更简单的兑现。** 规模真到需要它时再引入不迟。
- **MongoDB / 文档数据库承载 profile** — 单文档事务够用，但 C4 的三处写入跨集合（profile · 幂等 · 会话），且 C5 要求全局唯一键；多文档事务在分片集群上的代价与限制反而高于单库关系型。G4 的浅合并也需应用层手写。
- **把 `push_idem` / `receipt_idem` 放独立的 KV 存储** — 直接违反 C4（须与计数器自增同一次事务），会引入分布式事务或「revision 已 `+1` 但幂据未落」这个契约点名的失败态。
- **access token 用 ES256 签名（与内容签名同算法，共用一套工具链）** — 省一套密钥心智，但 ECDSA 签名含随机 `k` ⇒ 无法满足 C12 的「回放完全相同的那一对」，只能退回缓存活凭据。**两把钥匙的约束不同，共用算法是把一个不相干的相似性当成理由。**
- **refresh token 用纯随机串 + Redis 缓存 60 秒明文** — 可行且更简单，但让活凭据明文在缓存里存活 60 秒，且 Redis 失效会把弱网重试的玩家赶回验证码输入框（正是 `ADR-0004` 要消除的那一幕）。**保留为 G-2 的明写备选。**
- **`signin` 幂等回放记录放 Redis** — 它需要与会话写入同一事务（否则「回放了但会话没落」或反之），且键含个人信息。频率极低，放关系库更稳。
- **按账号分片以求水平扩展** — C 节已论证在契约定义的流量形状下不需要；且分片会诱导「跨分片的全局唯一 `receiptId`」这一 C5 明确要求的东西变难。
- **跨境多活 / 全球读写** — C3 直接否决（多主下账号级严格单调计数器无法维持）。
- **网关统一限流覆盖全部端点** — 会给 `/v1/auth/refresh` 返回 `rate.limited`，静默破坏 C11 保证的「两条失败路径在报文层面互斥」。

## 与既有决策的张力

1. **`bind` / `unbind` 的后端写入是否推进 `revision`——契约未明写，本方案建议「推进」，并建议采纳时补一句澄清。**
   `profile-sync.md` §5 的后端写入表列了 `/accountInfo/identities`（建号 / bind / unbind 时写入，反复），但只有 `purchase.md` 明写了 verify 时 `revision += 1`；bind / unbind 没有对应措辞。
   **建议推进的理由**：`revision` 是「profile 的写入计数器」这一不变式，是 C1（读己所写以 `revision` 为下界表达）、CAS 三分支、以及副本一致性判据的共同地基。若某些后端写入不推进它，`revision` 就不再唯一标识 profile 状态，而客户端在 bind 后若漏 pull，会直接撞 §5c 的回声失败（`identities` 有序逐元素比较）⇒ 一次改昵称丢一次进度。
   **松动代价**：需要在 `profile-sync.md` §5 或 `auth.md` §8 补一句「后端对 profile 的任何写入均推进 `revision`」。这是**一句澄清，不是决策变更**，但它改的是契约文件，故列在此处交用户裁决而非直接落笔。
2. **`signin` 的两步执行顺序与 `auth.md` §4a 伪码相反。**
   见 E 的纪律 1。**语义等价（同事务内中间态不可观测），契约无需改动**；但伪码会被实现者照抄，建议采纳时在 `operations/` 侧记一句实现纪律，或在 §4a 伪码旁加一条「两步顺序在事务内可交换」的注。**本条不需要用户裁决，仅提示。**
3. **`refresh` 的限流真空。** C11 是契约刻意留的：`refresh` 不给 `rate.limited`。本方案的处置是「只记账 + 告警，不返回限流码」，这在滥用面上是可接受的（refresh token 是高熵凭据，rotation + 60 秒宽限窗口已把重放收益压到近零，且窗口外重放会**自证泄漏并吊销全部会话**——这本身就是一道比限流更强的闸）。**但它意味着一个持有有效 refresh token 的攻击者可以高频打这个端点。** 若用户认为必须限流，须按 `auth.md` Open questions 回改契约并给客户端第三条路径——**本方案建议不改，理由如上。**
4. **选 C# 会诱发对 `ADR-0003` 的复议。** `envelope.md` §1 与 `ADR-0003` 明写「明确否决共享 DTO 代码——**即使后端最终也选 C#**」。选 C# 不与该决策冲突（它否决的是共享**编译期依赖**，不是同语言），但**它会让「都用 C# 了，不如共享 DTO」被反复重新提出**。建议：若选 C#，在 `systems/_index.md` 或 `operations/deployment.md` 显式引一次这条护栏，使复议必须先驳倒它。

### ① 语言与框架

| 选项 | 后果 |
|---|---|
| **C# / ASP.NET Core**（**推荐**） | ✅ `ulong` 原生 + `>>` 逻辑右移与 SplitMix64 伪码**一一对应**，`ADR-0006` 逐位复算的三个易错点（`+1` 全零防御 · 环上运算 · 符号扩展）零转换风险；✅ 契约的「枚举值与客户端 C# 成员名逐字相同」可直接用同名 `enum`，省掉一张最易写漏的映射表；✅ 与唯一开发者的 Godot C# 心智一致。❌ 会诱发对 `ADR-0003` 的复议（见张力 4）；❌ 容器镜像与内存占用高于 Go |
| **Go** | ✅ 单二进制、镜像小、部署与并发模型简单；✅ `uint64` 语义明确。❌ 枚举名逐字对齐要手写常量与映射（`Source` · `AccountStream` · `SavePointReason` · `reasonKey` 四套）；❌ 与客户端两套心智 |
| **Node / TypeScript** | ✅ 开发速度快、生态广。❌ **判据上明显更差**：SplitMix64 的 `uint64` 环上运算必须走 `BigInt`，而契约要求**逐位一致**且已用测试向量把「差一位」定为红线；❌ 数字类型还要处理 `revision`（`long`）与 `accountSeed` 超 2⁵³ 的两处判据 |

**推荐 C#**，理由是它在**唯一一处不容差错的地方（逐位复算）**上摩擦最小，而 `ADR-0003` 的护栏本就写明了同语言不解锁共享 DTO。

→ **已裁决（2026-09-02 · 批量评审）：C# / ASP.NET Core。** 张力 4 随之生效——采纳时须在 `systems/_index.md` 或 `operations/deployment.md` 显式引一次 `ADR-0003` 的「否决共享 DTO」护栏。

### ② 云厂商与部署形态

| 选项 | 后果 |
|---|---|
| **腾讯云 + 托管容器（TKE / 弹性容器）+ 云数据库 PostgreSQL + 云 Redis + KMS + CDN**（**推荐**） | ✅ 微信登录（`unionid`）与微信支付同生态，接入与对账摩擦最小，而这两条都在 MVP 内；✅ 境内节点满足 C19 / C14；✅ 托管容器无冷启动、连接数可控、定时任务好挂。❌ 成本高于 Serverless 的空闲期 |
| **阿里云 + 同构组合** | ✅ 关系数据库与 KMS 产品成熟度高、文档好；✅ 同样满足境内要求。❌ 微信侧接入是纯外部 API，无生态便利（**这不是技术劣势，只是少一份便利**） |
