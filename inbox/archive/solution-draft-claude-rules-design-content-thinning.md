# 方案草稿 — `.claude/rules/*` 中设计性表述的边界判据

## 问题

ADR-0005 已定**主从关系**（`.claude` 是工程层；设计性内容以设计库为准、工程性约束以 `.claude/rules/*` 为准），并对 `.claude/knowledge/*` 给出了可执行的**副本判据**（凡在设计库里已是代码形态的东西 → 只留链接，不留副本）。

但它对 `rules/` 只留下一句形态描述——「形态只能是**一句话承重纪律 + 回链**，不得展开为设计说明」——**没有给出可机械检查的边界**：一句话到底多长？举一个例子算不算展开？以及**谁来查**。

结果是三件事同时悬着：

1. **边界不可判定。** `data-resource-rules.md` 的 `AllEnabled()` 那段有 6 行、含默认值、含 `[Obsolete(error: true)]` 的过渡期安排；`state-save-rules.md` 的「确定性边界」有完整论证（含「数值可随时线上修正的价值高于跨版本复现」这句权衡）。它们是「一句话」的合理放宽，还是已经越界？现在没有判据可以回答。
2. **漂移已实际发生（有实证，不是假设）。** `state-save-rules.md` 写「CycleState 拥有全部单次轮回数据（deck、**relic**、灵玉、地图位置、**ante/楼层**、当前遭遇战）」——`relic` / `ante` / `楼层` 都是本作**不使用**的泛体裁词（本作是神通 / 法宝 / 篇章 / 境界，见 `terminology.md`），且轮回状态的持有者已定为 `life-cycle-service.CycleStateManager`，不叫 `CycleState`。这段话正是 ADR-0005 预言的「副本 = 下一次漂移的唯一来源」的现场。
3. **无执行者。** `/sync-knowledge` 的对账范围是 `.claude/knowledge/*`，**不含 `rules/`**。ADR-0005 对 knowledge 的副本判据有 `/sync-knowledge` 兜底，对 rules 的那句形态描述**没有任何兜底**——它停在阶梯第 4 级（评审清单），而第 2 点已经证明第 4 级在这里失效了。

## 约束（来自既有设计）

- **ADR-0005 总纲**：`.claude` 只承载工程配置 / 规则与技能；设计内容只做「引用与轻描述」。冲突裁决判据 = **「这句话的权威在哪一侧」**（讲游戏是什么 → 设计库；讲代码怎么写 → `.claude`）。
- **ADR-0005 的两类分界**：`standards/{csharp-conventions, godot-scene-conventions, mobile-portrait-ui}.md` 讲的是**引擎 / 语言实践**，在设计库中无权威，**保留实质**、不构成副本。这条分界对 `rules/` 同样适用。
- **08-14 判据卡**（`systems/common-properties.md` `## 内容共有字段` 节首）：**定义在最小公共祖先、恰好一份；每个落点写一段投影；投影不得复述定义。** 硬边界是「同一字段名在两份文件中同时出现枚举成员表 / 数值 code / 完整校验语义任一者 ⇒ 违规（第二权威）」，理由是**两份表会各自漂移而本库没有任何机制能发现不一致**。
- **纪律的可执行化四级阶梯 + 两条选级判据**（`systems/architecture.md`）：能上线且线上不可见 → 必须第 1 / 2 级；只在开发期显形且会累积 → 第 3 级足够。第 4 级 = 「零成本、零保证」。
- **设计库中多条 `Source: .claude/rules/*` 的指认**（`common-properties.md` 的「稳定 Id 键」「字段命名与类型一致性」「Null / 结果校验」「日志约定」「原子写入」）——这些条目的权威**确实在 rules 侧**，本方案不得把它们一并瘦掉。
- **`.claude/rules/*` 的加载时机**（工程事实，`Context.md` + harness）：`Context.md` 每 session 起手即注入；其余规则文件「当任务触及相应领域时加载」。这与 `knowledge/*` 的「按需去读」不是同一种加载模型——本方案的核心推演即建立在此差异上。

## 建议方案

### 1. 结论先行：当前形态**合法，不应瘦身到纯链接**——但需要一条可机械检查的边界

`[既有推演]`

**推荐答案：「一句话承重纪律 + 回链」是正确形态，不进一步瘦身到「只留链接」。**

依据不是折中，而是 knowledge 与 rules **加载模型不同**这一工程事实：

| | `.claude/knowledge/*` | `.claude/rules/*` |
|---|---|---|
| 加载方式 | Claude **主动去读**（导航后按需展开） | **前置注入**（起手 / 触及领域即在上下文里） |
| 那段文字的职责 | 告诉 Claude **去哪找** | 在 Claude **还没有理由去读设计库时**就阻止它写错 |
| 纯链接是否够用 | **够** —— 读它的那一刻本就在找东西，多跳一次即可 | **不够** —— 写错代码的那一刻，往往正是「没觉得需要查设计库」的那一刻 |

ADR-0005 的原文本身已经隐含了这个刻度差：对 knowledge 写的是「**只留链接，不留副本**」，对 rules 写的是「**一句话承重纪律 + 回链**」——两处措辞不同不是笔误，本方案是把这个差异显式化并给出阈值。

**因此本方案不是在 ADR-0005 的两个选项里挑一个，而是补上它缺的第三样东西：阈值 + 执行者。**

### 2. 边界判据（两步，逐句可套用）

`[既有推演]`（形式直接套用 08-14 的「定义 / 投影」判据卡）

把 rules 里的每一句话当作设计库某条定义的**一段投影**来判，两步：

**第一步 · 归属分类**（沿用 ADR-0005 的判据，不新增）：

| 这句话讲的是 | 归属 | 受本判据约束吗 |
|---|---|---|
| 游戏是什么（机制、数值、字段语义、契约、流程） | 设计库 | **是** —— 它是投影，受第二步约束 |
| 代码怎么写（命名、生命周期、热路径、null 校验、日志、原子写入、工具 / PATH、目录纪律） | `.claude/rules/*` **自身即权威** | **否** —— 原样保留，写多长都不算副本 |
| 引擎 / 语言实践（C# 语法、Godot 节点 API、Container 布局） | 引擎，设计库无权威 | **否** —— 与 ADR-0005 对 `standards/` 三份的处理同理 |

**第二步 · 投影形态（仅对第一类）**：一段合法的投影**恰好由四件东西构成**，缺一不可、多一即越界：

1. **一句祈使**（写代码时会改变写法的那句）；
2. **该纪律涉及的标识符名**（方法名 / 字段名 / 类型名，允许出现——名字正是"改变写法"的载体）；
3. **一句代价说明**（违反了会怎样。这是让 Claude 不去绕过它的唯一理由，删掉它这条就退化成可商量的口味）；
4. **一条回链**（指向设计库的**权威文档**）。

### 3. 硬边界（可机械检查，对齐 08-14 的写法）

`[既有推演]`

> **一条设计性投影出现下列任一者 ⇒ 违规（第二权威）：**
>
> - **代码块**（与 ADR-0005 对 knowledge 的「零代码块」同）；
> - **表格**；
> - **枚举成员清单 / 字段清单**（两个以上并列的成员名）；
> - **具体数值 / 阈值 / 默认值**（`默认 true`、`五档`、`10 回合`、`9 格`……）；
> - **完整取值域或分支穷举**（「分三种情况：A / B / C」）；
> - **≥3 步的编号流程**；
> - **超过 3 行**。

理由与 08-14 判据卡逐字同构：**两份表会各自漂移，而本库没有任何机制能发现它们不一致**——`rules/` 的处境更糟，因为它连 `/sync-knowledge` 那样的兜底都没有（见第 5 项）。

**一条实用的自检问句**（给写的人用，不入正式判据）：**「把这句话删掉，Claude 会不会写错代码？」**——会 → 它是承重的，留（并压进上面四件东西）；不会 → 它是背景说明，删。投影只留**行为后果**，不留**定义**。

### 4. 三条附带的机械规则

`[既有推演]`

- **4a · 回链一律直指设计库，不经 `knowledge/` 中转。** 现状里 `csharp-godot-rules.md` 的 EventBus 那条回链的是 `.claude/knowledge/standards/signal-eventbus.md`，而该文件在 ADR-0005 之后**自己也只是一份薄引用** ⇒ 二跳才到权威，且中间那一跳是一个额外的失效点。设计结论的回链只写 `game-design-documents/...`。
- **4b · 已被阶梯第 1 / 2 级手段强制的纪律，rules 里不再写条款、只留一句「由 X 强制」+ 回链。** 直接推论自可执行化阶梯：`AllEnabled()` 一旦落地为「仓储上不存在 `All()` + `[Obsolete(error: true)]` 占位」，**编译器已经在强制它**，rules 里那 6 行属第 4 级（零保证）的重复投入，且是漂移源。**这条会随 `DrawPool<T>` 落地而自动生效，是本方案里唯一有时间性的部分。**
- **4c · 没有回链的设计性表述一律视为违规。** 缺回链与「还没想」不可区分——与 08-14「必须明写『本层无规则消费点』而不是省略」同一条理由。

### 5. 执行者：把 rules 纳入 `/sync-knowledge` 的对账范围

`[已裁定 · 2026-08-14]` **采纳：扩 `/sync-knowledge` 的对账范围到 `.claude/rules/*`。**

判据来自阶梯本身：本纪律**只在文档层显形、且违反后会累积**（第 2 点的 `relic` / `ante` 已经积了一处），按选级判据属「第 3 级足够」——但文档没有编译期，这里的「第 3 级」等价物就是**一个会定期跑的对账技能**。留在第 4 级（人工评审）已被实证证伪。

`/sync-knowledge` 是天然落点：它已经有「**副本化**」这一首要漂移类型、已经有 `### Thinned` 报告段，rules 的漂移与 knowledge 的漂移是**同一种**。成本 = 改一份技能文本 + 它的名字含义略微变宽（对账对象从 knowledge 扩为整个 `.claude` 的设计投影面）。

**技能不更名**（`/sync-knowledge` 已被 `Context.md`、`README.md`、`design-library-routing.md` 的「不在双库范围内的技能」表三处引用，更名的连带修改多于收益）；改为在技能描述与正文首段写明**对账对象 = 整个 `.claude` 的设计投影面（`knowledge/*` + `rules/*`）**。落地形态见 `## 执行清单（按顺序）` 第 4 步。

### C · `design-library-routing.md` 判为显式例外 `[已裁定 · 2026-08-14]`

它复述的是两库 README 的**目录结构**，不是设计内容——按第 2 步第一类判据，「哪个文件夹在哪个库」讲的是**工程层的路由**，不是「游戏是什么」。且它是技能执行的**前置信息**：把它换成回链等于每次跑设计流水线技能都要先读两份 README，而路由判错的代价是**把后端意图写进客户端库**（污染事实来源）。

**采纳：保留结构表 + 显式标注为「路由用副本」。** 待插入的一句（放在「两库的结构差异」表下方）：

```markdown
> **本表是「路由用副本」（显式例外 · 已裁定 2026-08-14）。** 两库结构的权威在各自 README；此处保留一份是因为它是技能路由的前置信息，
> 换成回链等于每次跑设计流水线技能都要先读两份 README，而路由判错的代价是把一侧的意图写进另一侧的库。
> **两库结构变更时此表须同改**，由 `/sync-knowledge` 对账兜底。
```

这样它是一份**已知的、有理由的、被审计覆盖的**副本，而不是一处漏网——与「未标注即违规」的判据不冲突。

## 备选方案（已考虑并否决）

- **rules 里的设计结论一律只留回链、不留内容**（严格照搬 knowledge 的处理）—— 否决：撞加载模型差异（第 1 项）。rules 是前置注入层，它的职责是在 Claude 尚未去读设计库时就改变写法；只留链接会让「抽取要走 `AllEnabled()`」这类**能上线且线上不可见**的纪律退回到「Claude 恰好想起来去查」才生效，与阶梯的选级判据正面冲突。
- **把设计性表述从 rules 全部移除，改由设计库直接被注入**（让 harness 加载 `game-design-documents/` 的若干文档）—— 否决：设计库是给人读的完整文档（`common-properties.md` 单份就 270+ 行），注入它等于每 session 付一大笔上下文，且它随设计演进持续膨胀；rules 的价值恰在于**它是被压缩过的、稳定的行为约束面**。
- **新开一个 `/audit-rules` 技能**（而非扩 `/sync-knowledge`）—— 倾向否决但列为可选（见 `## 仍需用户决定`）：两者对账的是同一种漂移（副本化），拆成两个技能意味着两份几乎相同的技能文本各自演化，正是本方案在反对的那种第二权威。
- **给 rules 里的设计性句子加统一前缀标记**（如 `> 设计投影：`）以便机械 grep —— 未采纳为强制项：收益仅在审计工具侧，代价是每条都要加装饰；第 3 项的硬边界（代码块 / 表格 / 数值 / 行数）已经足够被机械检查。**若第 5 项采纳，可由技能自行判定，不必加标记。**

## 与既有决策的张力

**表面张力一处，经核**不构成冲突**，但必须写下来避免日后误读：**

ADR-0005 对 knowledge 的判据是「**只留链接，不留副本**」，本方案对 rules 取「**一句话 + 标识符 + 代价 + 回链**」——看起来是同一条 ADR 里两个不同的严格度。裁定：**它们是同一判据在两种加载模型下的两个刻度**，且 ADR-0005 总纲原文对 rules 写的本就是「一句话承重纪律 + 回链」（Decision 第 0 节末句），本方案是把那句话量化，**不是放宽它**。

**`[已裁定 · 2026-08-14]` ADR-0005 必须补上这条对照**，否则日后读 ADR 的人会以为 rules 侧被网开一面。待插入文本（放在新增的「### 2. 规则层的具体形态」节首，先于判据本身）：

```markdown
> **两个刻度，同一条判据。** 知识层「只留链接」、规则层「一句话 + 回链」，不是 rules 被网开一面，
> 而是**加载模型不同**：`knowledge/*` 是 Claude 主动去读的（读它的那一刻本就在找东西，多跳一次即可），
> `rules/*` 是前置注入的（它要在 Claude **还没有理由去读设计库时**就改变写法）。
> 纯链接在注入层失效——写错代码的那一刻，往往正是「没觉得需要查」的那一刻。
> 本节是把总纲第 0 节那句「一句话承重纪律 + 回链」**量化**，不是放宽它。
```

其余：无。本方案不推翻任何既有决策。
