# 方案草稿 — flags 回滚即前滚的对位条款

## 问题

`contracts/content-manifest.md` 为 `contentVersion` 写下了「严格单调递增，不允许回退；回滚 = 前滚」（ADR-0001），但**没有为 `flagsVersion` 写下对位条款**。

客户端已于 2026-08-22 把 flags 的拉取规则由「版本不同即拉」收紧为「**增大**即拉」，并**开始依赖 `flagsVersion` 单调递增**——语义、失败症状与它自己的爆炸半径闸（内存 `FlagsVersion` 冷启动归零）权威在 `game-design-documents/systems/services/content-service.md`「flags：`ContentEnabled` 的第三层」，本库**只回链、不复述**。

于是本库欠两件事：

1. **条款本身**——准确措辞与落笔位置；`flagsVersion` 的**取值空间与来源**是否需要一并约束（它直接决定多区域下这条能否兑现）。
2. **运营兑现**——flags 是**按账号计算**的（与 manifest 的静态对象不同），「前滚一批新 flags」到底指什么动作、留什么痕。

这条与 `open-questions/04-content-delivery.md` 的「flags 数据源与灰度分桶的运营形态」「多区域内容分发的一致性」两条同源，边界处理见 `## 前置依赖`。

## 约束（来自既有设计）

- **ADR-0001**：`contentVersion` 严格单调递增，回滚即前滚。本条款是它对 flags 的对位，**措辞应与之同构**。
- **ADR-0002**：flags 只能覆盖 `ContentEnabled` 这一个布尔，不得携带数值 / 文案 / 新 `Id`。⇒ 本方案**不得**通过新增报文字段来解决问题（那会扩大载荷面）。
- **分桶规则留在服务端、不下发**（ADR-0002 / `contracts/content-manifest.md`「灰度分桶留在服务端」）。⇒ 不得把「区域」「桶」「规则集指纹」一类概念泄漏给客户端。
- **`X-Flags-Version` 随任意应答下发**（`envelope.md` §4b）。⇒ 版本号会被**任意一个 API 实例、任意区域**读到，它不能是某个实例 / 区域的局部计数。
- **pillar #5「线上可干预」**：关条目不需要发版。⇒ 方案不得让一次误关的撤销退化为「等下一次内容发布」。
- **`operations/_index.md`「发布流程（顺序即正确性）」⑤** 现写着「秒关 / 灰度不走本流程——改 flags 数据源即可」。本方案与这句有张力，见 `## 与既有决策的张力`。
- **技术栈未定**：全文停在协议与语义层，运营那一半只写「须满足什么性质」，不指定语言 / 框架 / 存储 / 工具。

## 建议方案

### 1. 条款本体：`flagsVersion` 严格单调 + 回滚即前滚

`[既有推演]`（ADR-0001 的同构对位 + 客户端已定的「增大即拉」）

建议的**成品句**（可直接粘贴，落点见子项 4）：

> **`flagsVersion` 严格单调递增，不允许回退。** 服务端保证：任意应答携带的 `X-Flags-Version`、以及 `GET /v1/content/flags` 应答体内的 `flagsVersion`，取自**同一个全局单调序列**——它不按区域、不按实例、不按账号分别计数。
>
> **回滚 = 前滚。** 撤销一批误关没有「把版本号退回上一批」这个动作：以被回指批次的规则内容为源，发布一个**更大**的 `flagsVersion`。flags 是**全量快照**（`disabledIds` 是结果的全集，不是增量），故前滚与首次发布走完全相同的一条路径，成本为零。
>
> **同一 `flagsVersion` 的解析结果恒定。** 对固定的账号，同一 `flagsVersion` 必须始终解析出相同的 `disabledIds`；**任何会改变解析结果的改动（规则增删、分桶比例调整、白名单增删、分桶盐值变更）都必须提升 `flagsVersion`**。分桶函数须是 `(accountId, 规则集版本)` 的纯函数，不得依赖实例本地随机、当前时间或请求属性。
>
> 允许版本回退、或允许同版本内容漂移，都会使客户端「观测到增大才拉」的闸门失效：前者让已观测到更高版本的设备**在当前会话内此后不再拉取 flags**，后者让改动对已在线设备**永不生效**、只对新会话生效。两者的线上症状都是「秒关不生效 / 误关的内容不恢复」，且只有客户端一条本地告警 + 一次上报作为线索。客户端侧的观测规则、降级与爆炸半径闸见 `game-design-documents/systems/services/content-service.md`「flags：`ContentEnabled` 的第三层」。

三处措辞的承重点：

- **「同一个全局单调序列」** 不是修辞。`X-Flags-Version` 搭任意应答的车，设备在一次会话内会从多个实例（可能是多个区域）读到它；按区域 / 按实例计数当场违反条款。
- **「同一 `flagsVersion` 的解析结果恒定」是第二半，不可省。** 客户端「等值不拉」——这条纪律使**内容变了而版本没变**成为一个静默失效模式，其危害不亚于版本回退，且更难定位（见子项 3 的失效来源③）。`contentVersion` 那条不需要这半句，因为 manifest 是静态对象、内容寻址天然保证同版本同字节；flags 是**按账号计算的结果**，没有这层保护，**必须显式写下**。
- **「全量快照」是前滚零成本的理由**，与 ADR-0001 的「内容寻址」平行但不同源——故本条款不宜简单挂进 ADR-0001（见子项 6）。

### 2. `flagsVersion` 的取值空间与来源

`[取向选择]` → 见 `## 仍需用户决定` B-2。倾向：**单一全局递增计数**（每次**发布动作** +1）。

| 形态 | 单调性从哪来 | 主要代价 |
|---|---|---|
| **① 单一全局递增计数**（推荐） | 一个全局唯一的分配点 + 持久化高水位 | 需要一个跨区域共享的分配点；发布传播到各区域有时延（见子项 3 失效来源②） |
| ② 时间戳派生（epoch 秒 / 分钟） | 服务端时钟 | 把单调性押在时钟上：NTP 回拨、多实例时钟偏差即回退。本库已有「设备时钟不可信」的同族纪律，服务端时钟可信度更高但不是零风险；且若沿用 `int`，秒级 epoch 在 2038 溢出 |
| ③ 每区域独立计数（可带区域前缀） | 各区域各自单调 | **直接违反条款**：区域切换即观测到回退。要让它成立，须下发区域标识让客户端按区域分别记忆版本——那等于把区域概念泄漏给客户端，与「分桶规则哪也不放在客户端」同向被否 |

附带明确（无论选哪个）：`flagsVersion` 的 JSON 类型仍是 `int`，**取值空间不写进报文层的新字段**——它是服务端内部的分配纪律，客户端只做大小比较。

**号只由发布动作分配，草稿态编辑不占号。** 否则版本号被未发布的编辑抖动推高，审计读起来全是空洞。

### 3. 三个现实的失效来源，逐个堵

`[既有推演]` + `[通行做法]`

| # | 来源 | 破坏形态 | 客户端症状（「增大即拉」下） | 本方案如何堵 |
|---|---|---|---|---|
| ① | **数据库回滚 / 备份恢复** | 版本计数器倒退，已用过的号被重新分配（更糟：同号承载不同规则） | 恢复前观测过更高版本的设备，本会话内**再不拉 flags**；新会话的设备则拿到「同号不同内容」的一批 | **分配点持久化一条单调高水位**，且高水位与规则集存储**同一事务边界**（避免只恢复其一）。恢复后取 `max(恢复值, 高水位)` 并**强制跳号**（留一段安全余量，具体数值属运维取向）。恢复演练把「版本号未倒退」列为恢复后必检项 |
| ② | **多区域各自计数 / 发布传播时延** | 区域 A 已到 42，区域 B 仍在 41；设备跨区路由即观测到更小值 | **不拉 + `PushWarning` + 上报一次**（客户端已定，且它保留当前那批 flags）——**是良性的，但会产噪**；真正危险的是若某条路径把较旧的一批**应用**上去，被秒关的内容会当场复活（见 `## 与既有决策的张力` 第 3 条） | 条款钉死**单一全局序列**（子项 1）；区域差异降格为**传播时延**而非独立计数。再加一条运维 SLO：**新批次须在窗口 T 内在全部区域可见**，窗口内的「观测到更小」是已知良性态，代价是一次告警 + 一次上报（客户端已按会话去重，噪声有界）。**T 的数值待 02 / 04 的多区域一致性答定**，见 `## 前置依赖` |
| ③ | **手工改规则**（直接改存储 / 控制台绕过发布动作） | 内容变了，版本号没变 | 已在线设备「等值不拉」⇒ 改动**永不生效**；新会话设备拿到新结果 ⇒ **两批设备行为分裂**，且没有任何一侧报错 | **规则集不可变**：没有原地编辑路径，任何改动只能产出一个新版本（子项 4）。可选加固：把规则集内容指纹与版本号绑定，服务端自检到「同版本不同指纹」即告警——**指纹不下发给客户端**（ADR-0002 的载荷边界） |

第 ③ 条是本方案相对「只写一句单调递增」的主要增量：**单调递增只堵住回退，堵不住原地改**，而按账号计算的 flags 恰恰给了原地改一条极自然的路径。

### 4. 回滚的运营兑现：规则集不可变版本化

`[通行做法]`（配置发布的通行形态：不可变版本 + 指针前移）+ `[既有推演]`（与 ADR-0001 的前滚同构）

flags 不是静态对象，「发布一批」发布的是**规则集**，端点按账号解析它得到 `disabledIds`。建议的具体形态：

- **规则集是不可变的版本化快照。** 每次发布产出一个新版本，`flagsVersion` 即该版本号。既有版本**只读**，不存在编辑。
- **回滚的语义写死为一次发布：** `rollback(to: v_k)` ≡ 以 `v_k` 的规则内容为源，创建 `v_new = 当前最大版本 + 1`，其规则内容逐字等于 `v_k`。**不存在把「当前生效版本」指针退回 `v_k` 的操作**（若实现上有一个「当前版本指针」，它只能单向前移）。
- **保留一份可回指的历史规则集。** 回滚的输入是历史版本的**内容**，不是操作日志的复述——只留变更日志、靠人工重建规则，等于把事故时的止血动作变成一次手工编辑（而手工编辑正是失效来源③）。保留期见 B-4。
- **审计留痕的最低要求（四项，缺一不可）：**

  | 项 | 内容 | 为什么是最低要求 |
  |---|---|---|
  | 操作者 | 谁发布的这一版 | flags 是**唯一一条能绕过发版直接改变玩家可见内容**的通道 |
  | 时间 | RFC 3339 UTC | 与线上事故时间线对齐；本库全局时间约定 |
  | 来源版本 | `derivedFrom: v_k`（回滚时即被回指的版本；正常发布时为上一版） | 使「这一版是不是一次回滚、回指的是哪一版」可机读，而不是靠备注措辞 |
  | 变更摘要 | 相对来源版本的规则差异 + 生效范围（全量 / 分桶） | 事故复盘要能回答「是谁在什么时候关掉了 `card_x`、覆盖多少比例」 |

- **flags 有自己的发布流程，但它同样是一次「带版本号的发布」**，只是不触碰 blob 与 manifest（见 `## 与既有决策的张力` 第 1 条）。

### 5. 若存在按账号计算的缓存层：缓存键必须含版本

`[既有推演]`（本条款的直接推论）

「`GET /v1/content/flags` 的按账号计算是否需要缓存层」是 `04-content-delivery.md` 的独立待答项，**本方案不裁决它**。但本条款对它施加一条**现在就能定**的约束：

> 若引入按账号的解析结果缓存，**缓存键必须包含 `flagsVersion`**，且缓存条目**不得跨版本复用**、不得在版本提升后继续被读到。

理由：缓存键只按 `accountId` 时，版本提升后设备拉到的仍是旧结果——但版本号已经增大 ⇒ 客户端认为「已同步到最新」，此后「等值不拉」⇒ **这一批秒关对该账号永不生效**。这与失效来源③同一病理，只是发生在缓存层。

### 6. ADR 落点

`[取向选择]` → B-5。倾向：**新开一条 ADR**，不并进 ADR-0001。

理由：ADR-0001 的核心论证是「**内容寻址**让前滚零成本」，这条论证对 flags **不成立**（flags 不是内容寻址的静态对象）；flags 的前滚零成本另有理由（**全量快照**）。并进去会让 ADR-0001 的理由段承载两条不同的论证；而这里真正值得固化的是「不可变版本化 + 同版本结果恒定」——ADR-0002 的载荷边界也覆盖不到它。

## 具体形态（可 derive 的落地面）

**报文层：零新增字段、`flagsSchema` 不变。** 本方案全部落在语义条款与运营形态上。

契约侧新增/明确的条款（逐条可核对）：

| # | 条款 | 落点 |
|---|---|---|
| C1 | `flagsVersion` 取自单一全局单调序列，不按区域 / 实例 / 账号分别计数 | `contracts/content-manifest.md`（落点见 B-1） |
| C2 | 严格单调递增，不允许回退；回滚 = 以历史规则内容发布更大的版本 | 同上 |
| C3 | 同一 `(flagsVersion, 账号)` 的 `disabledIds` 恒定；任何影响解析结果的改动必须提升版本 | 同上 |
| C4 | 分桶函数是 `(accountId, 规则集版本)` 的纯函数，不依赖实例本地随机 / 当前时间 / 请求属性 | 同上 |
| C5 | 若有解析结果缓存层，缓存键含 `flagsVersion` 且不跨版本复用 | 同上（一句），展开在 `operations/` |
| C6 | 新批次须在窗口 T 内在全部区域可见；窗口内客户端观测到更小版本是已知良性态 | 同上（T 待前置答定） |

| # | 要求 |
|---|---|
| O1 | 规则集不可变、版本化；无原地编辑路径 |
| O2 | 版本号由单一全局分配点分配，只在发布动作时分配；持久化单调高水位 |
| O3 | 备份恢复后取 `max(恢复值, 高水位)` 并强制跳号；「版本号未倒退」列为恢复后必检项 |

## 后果

- `contracts/content-manifest.md`：新增条款段（结构改动幅度取决于 B-1）；`## Open questions` 移除本条。
- `operations/_index.md`：「已有具体对象的运维面：内容分发」新增 flags 的发布 / 回滚流程；**同批改写既有发布流程的 ⑤**（见张力 1）。
- `decisions/`：新增一条 ADR 候选（B-5）。
- **`flagsSchema` 不提升、报文不变、客户端无需任何改动**——客户端侧已按本条款成立的前提落笔完毕（2026-08-22），本方案是补上它所依赖的那一半。
- 与 `04-content-delivery.md` 两条相邻待答项的关系：本方案对它们**施加约束但不裁决它们**（见前置依赖）。

## 备选方案（已考虑并否决）

- **在 flags 报文中新增 `flagsRulesetHash` / `region` 一类字段，让客户端自行判断** — 扩大 flags 载荷面，与 ADR-0002 的硬边界相抵；且会把区域 / 规则集概念泄漏给客户端，推翻「分桶规则哪也不放在客户端」。
- **允许 `flagsVersion` 回退，改由客户端按「不同即拉」兜底** — 等于要求客户端撤回 2026-08-22 的定案；而那条定案的存在理由（旧规则会把一个已经正确的本地 flags 换成过时的一批 ⇒ 已秒关内容当场复活）不因后端条款而消失。**本方案不改客户端规则。**
- **时间戳派生版本号**（B-2 选项②的独立形态） — 把单调性押在服务端时钟上；且无法表达「同一时刻发布两批」。
- **每区域独立序列 + 客户端按区域记忆版本** — 见子项 2 表格③行。
- **只留变更日志、不留历史规则集快照** — 回滚时须由人工按日志重建规则，而手工编辑正是失效来源③。
- **把本条款并进 ADR-0001** — 两者的「前滚零成本」理由不同源（内容寻址 vs 全量快照），并入会让该 ADR 的理由段承载两条论证。

## 与既有决策的张力

1. **`operations/_index.md` 发布流程 ⑤「秒关 / 灰度不走本流程——改 flags 数据源即可」** 与本方案的「规则集不可变、任何改动必须发布新版本」相抵。那句话现在读起来像是「随手改数据源」，而这正是失效来源③。**建议同批改写**为：flags 不触碰 blob 与 manifest、不走 ①–④，但它有自己的发布流程，同样产出一个更大的 `flagsVersion` 并留痕。—— 提请用户确认这属于「补齐措辞」而非「推翻既有决策」。

2. **`contracts/content-manifest.md` 的「服务端保证（三条，仅此三条）」的封闭措辞。** 「仅此三条」是一句承重的否定（下一段「不提供的」依赖它），而那三条全部是 **overlay / CDN 静态对象**维度的。把 flags 的条款塞进去会让这个封闭集跨到 API 域。落点因此是一个真取向 → B-1。

3. **客户端侧的一处缺口（本方案不修，只如实记下）。** 客户端已明写的单调闸门在**观测 `X-Flags-Version` 头**这一处；`GET /v1/content/flags` **应答体里的 `flagsVersion` 是否也过同一道闸门**，客户端文档未明写（它只写了「拉回版本 > 拉取前内存值」用于**是否尾随**的判断，那是节流规则，不是应用与否的规则）。在失效来源②的传播窗口内，设备可能拉回一批**版本更小**的 flags——若被应用，被秒关的内容当场复活。
   **归客户端裁决**，本方案不代为改客户端规则；后端侧能做的缓解已在 C6（传播窗口）与 C5（缓存键含版本）里。同步记入报告的「越界发现」。

4. **无张力、明写以免被误读：** 本方案**不新增任何报文字段、不提升 `flagsSchema`**，与 ADR-0002 的载荷硬边界完全相容。

## 前置依赖

- **「多区域内容分发的一致性」**（`open-questions/04-content-delivery.md`，与 `02-account-compliance.md` 耦合）。**边界划法：** 本方案**现在就定**「区域间共享单一全局序列、不各自计数」这一条（B-3）——它是本条款能否成立的前提，不能等；**留给该问题的**是①是否真的多区域托管、②传播窗口 T 的数值上界、③区域间发布时序差的运营处置。⇒ **C6 的 T 在该问题答定前无法填数**，条款可先写成「窗口 T（数值待多区域一致性答定）」。
- **「flags 数据源与灰度分桶的运营形态」**（同分片）。**边界划法：** 本方案只对它施加约束（O1–O7 与 C5），**不裁决**规则存在哪（配置表 / 数据库 / 控制台）、由谁改、是否引入缓存层。「是否需要审计留痕」这一小问**本方案主张答『是』**并给出四项最低要求——若用户希望把它整体留给该问题一并裁决，O5 可降级为建议项（提请在 interview 中一并确认）。

## 仍需用户决定

### B-2 `flagsVersion` 的取值空间与来源（先答——它是 B-3 / B-1 的前提）
- **选项 1：单一全局递增计数**，每次发布动作 +1，持久化高水位 — 后果：需要一个跨区域共享的分配点；数值小、可读、`int` 充裕；恢复演练须检查高水位。
- **选项 2：时间戳派生**（epoch 秒 / 分钟） — 后果：无需分配器，但单调性押在服务端时钟上（NTP 回拨 / 实例偏差即回退），且同一时刻的两批发布无法区分；`int` 秒级在 2038 溢出。
- **选项 3：不在契约里约束来源**，只写「必须单调」 — 后果：条款仍成立但**不可核对**，实现时按区域计数也不违反字面，等于把失效来源②留在门内。
- **推荐：选项 1** — 唯一能同时兑现「单调」与「多区域一致」的形态；代价（一个全局分配点）在 flags 的发布频次下（稳态每天个位数）微不足道。

→ **已裁决（2026-08-23 · 批量评审）：选项 1 —— 单一全局递增计数 + 持久化高水位。**

### B-3 多区域下的一致性口径
- **选项 1：全局单一序列 + 允许传播窗口 T** — 同一 `flagsVersion` 在全部区域承载相同规则集；窗口内某区域可能仍返回较小版本，客户端「不拉 + 告警 + 上报一次」，是已知良性态。后果：条款可核对，代价是窗口内的告警噪声（客户端已按会话去重）。
- **选项 2：flags 规则集从单一区域计算，其余区域跨区读** — 无传播窗口、无更小观测。后果：跨区延迟进入 `GET /v1/content/flags` 的响应路径，且该区域故障即全球 flags 不可用（客户端会降级到上一批，不阻塞，但秒关全球失效）。
- **选项 3：按区域独立序列 + 客户端按区域记忆版本** — 后果：须下发区域标识，泄漏区域概念给客户端，与「分桶规则哪也不放在客户端」相抵；**倾向否决**。
- **推荐：选项 1** — flags 的可用性优先级高于「零告警噪声」；且客户端对「观测到更小」已有确定的、安全的处置。

→ **已裁决（2026-08-23 · 批量评审）：选项 1 —— 全局单一序列 + 允许传播窗口 T。** T 的数值上界仍留给 `04` 分片的「多区域一致性」，条款先写「窗口 T（数值待定）」。

### B-1 条款写进 `contracts/content-manifest.md` 的哪个位置
- **选项 1：追加为「服务端保证」的第 4 条**，标题由「三条，仅此三条」改为「四条」 — 后果：可发现性最好；但把 CDN 静态对象的封闭集与 API 域的 flags 混进同一枚举，下一段「不提供的」那句否定的边界变含混。
- **选项 2：只写进「flags 通道」一节**，「服务端保证」处加一句指路 — 后果：与 `contentVersion` 单调条款的落点同构（它本就写在「版本化」而非「服务端保证」里）；代价是「服务端保证」不再是服务端义务的完整清单。
- **选项 3：把「服务端保证」重构为两组小标题**（overlay 分发三条 · flags 通道两条），三条的封闭性保留在第一组内；**同批把 `contentVersion` 严格单调那条也提为 overlay 组的一条** — 后果：单点可发现 + 封闭性不破 + 该节成为服务端义务的完整清单；代价是本节结构改动最大，且是一次跨 ADR-0001 落点的**位置迁移**（内容不变）。
- **推荐：选项 3** — 「服务端保证」是后端实现者唯一会当成义务清单读的一节，两条单调纪律都不在里面是本次欠账的根因之一；重构一次即根治。若用户偏好最小扰动 → 退到选项 2。

→ **已裁决（2026-08-23 · 批量评审）：选项 3 —— 重构为两组小标题**（overlay 分发 · flags 通道），并**同批把 `contentVersion` 严格单调那条提上来**。该位置迁移不改 ADR-0001 的内容，仅改其在契约中的落点。与本批 M-1 的裁决同批执行（消掉「三条，仅此三条」的计数写法）。

### B-4 历史规则集的保留期与回滚输入形态
- **选项 1：保留最近 N 个版本**（建议 N ≥ 50，覆盖数周的发布批次） — 后果：存储可预测；极旧的版本无法直接回指，但那类回滚在实践中不存在。
- **选项 2：按时间保留**（建议 ≥ 90 天） — 后果：与事故复盘窗口对齐；发布频次异常时存储不可预测。
- **选项 3：永久保留** — 后果：flags 规则集体积极小（一批 `Id` 集合 + 分桶规则），永久保留的成本近似为零，且与 `purchase.md` 收据幂等窗口「永久保留」的既有取向同向。
- **推荐：选项 3** — 数据量级不构成理由，而「能回指到任意历史版本」正是回滚即前滚的输入面；本库已有一次同形取舍。

→ **已裁决（2026-08-23 · 批量评审）：选项 3 —— 永久保留。**

### B-5 ADR 落点
- **选项 1：新开一条 ADR**（「flags 规则集不可变版本化 · `flagsVersion` 单调 · 回滚即前滚」） — 后果：论证独立成篇；`decisions/` 多一条。
- **选项 2：扩写 ADR-0001**，把标题泛化为「版本严格单调递增」涵盖两个版本号 — 后果：一处即读到两条纪律；但 ADR-0001 的理由段要同时承载「内容寻址」与「全量快照」两条不同论证。
- **选项 3：不立 ADR**，契约条款足够 — 后果：日后「flags 能不能就地改一下规则」这类提议没有可指的固化依据（而 ADR-0002 的先例说明这类边界会被反复重新提出）。
- **推荐：选项 1** — 与 ADR-0002 的经验一致：**能被反复重新提出的边界值得固化**，而「同版本结果恒定」尤其容易被一次「临时改个比例」的运营需求撬开。

→ **已裁决（2026-08-23 · 批量评审）：选项 1 —— 新开一条 ADR。** ADR-0001 不做泛化改写（其「内容寻址 ⇒ 前滚零成本」的论证对 flags 不成立）。

### B-6 审计留痕在哪一题定案（合并 interview 中提出并裁决）

`04` 分片的「flags 改动是否需要审计留痕」原本悬在运营形态那一侧。

→ **已裁决（2026-08-23 · 批量评审）：在本题定案**，采纳本草稿给出的四项最低要求（操作者 · RFC 3339 UTC 时刻 · `derivedFrom` 来源版本 · 变更摘要与生效范围）。理由：`derivedFrom` 是「回滚 = 以历史规则内容发布更大版本」这条能被机读核对的唯一凭据，脱离本题就失去判据。
