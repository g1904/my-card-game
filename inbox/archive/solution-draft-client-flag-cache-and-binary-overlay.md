# 方案草稿 — flags 缓存的报文侧对位 · blob 通道不承载二进制（后端半）

> **本草稿只写归后端的那一半：报文形态、服务端义务边界、契约层的能力声明。**
> 客户端的缓存策略 / 失效语义 / 断网降级、以及 overlay 合并期对二进制的处置与随包基线约束，**全部归对侧**，见 front matter 的 `counterpart`。**下文凡涉及客户端语义处一律写路径回链，不复述。**
> 本库技术栈未定，故本草稿**不指定语言 / 框架 / 库 / 存储形态**，停在协议与语义层面。

## 问题

`contracts/content-manifest.md` 的 Open questions 里有两条**把球踢给了对侧、而对侧未接**的条目——它们的危险不在于难，而在于两侧都可能把它当成对方的责任：

1. **「flags 是否落地客户端本地缓存以支撑离线开局 —— 归客户端侧裁决，本库不代为决定。」**（同款登记另见 `open-questions/04-content-delivery.md`「已推给别处的」表末行，标为「本定案唯一未闭合的语义缺口」。）
2. **「blob 通道是否向二进制资产开放（承接项）」** —— 报文层对文件类别无区分，但当前实际被消费的只有 `.tres`；本契约明写「不代为裁决」，等对侧的答案。

对侧本次给出了这两条的答案（见 `counterpart`）。**本草稿是它的后端半**：把两条 Open question 关掉，并补上**只有本库有权威**的那几句——它们不是复述，是本库自己的义务声明与能力声明。

## 约束（来自既有设计）

**A. flags 归 API 域、`no-cache`。** `contracts/content-manifest.md` 端点表与 `contracts/envelope.md` §3：`/v1/content/flags` 需鉴权、按账号计算、`no-cache`；**放在 CDN 域会诱导中间层按静态对象缓存，导致灰度分桶串号**。

**B. 服务端保证分两组，各自封闭。** A 组四条只覆盖 CDN 域静态对象（稳定 URL · 字节不可变 · manifest 与其文件发布原子 · `contentVersion` 严格单调）；B 组三条覆盖 flags（单一全局单调序列 · 严格单调递增 / 回滚即前滚 · **同一 `(flagsVersion, 账号)` 解析结果恒定**）。

**C. B 组第 7 条已写明它防的是什么：** 「客户端『等值不拉』——这条纪律使**内容变了而版本没变**成为一个静默失效模式」；且「flags 是**按账号计算的结果**，没有内容寻址那层保护」。

**D. 载荷边界。** `contracts/content-manifest.md` 在「手工改规则」一行已援引 **`ADR-0002` 的载荷边界**（规则集内容指纹**不下发给客户端**）；「灰度分桶留在服务端……端点按账号计算后只给结果」。

**E. `enabledIds` 是已立好的保留字段、初期恒空**，其存在的目的正是「避免日后启用时提升 `flagsSchema`」。

**F. A 组对文件类别不作区分，且这一点已被剧本文本一节验证过一次。** 「剧本文本：一类普通内容文件」明写：它以 `.tres` 出现在 `files[]` 中，与卡牌 / 事件 / 敌人条目**在报文层完全同形**——**服务端不区分内容类别**，三条服务端保证原样覆盖它，**契约层为此无需任何新增字段**。

**G. A 组的三项否定有一条带前提。** 「A 组不提供的：断点协商、下载令牌、客户端进度记录、差量清单……**字节级 Range 不写进契约、客户端也不依赖**（CDN 若默认支持属免费能力）」——这条与客户端「不做字节级断点续传」互为对位，而对侧那条的理由段带一个**量级前提**（见 `counterpart`）。

**H. 完整性保护与文件类别无关。** 「防篡改」一节：后端私钥签 manifest（ES256 detached），**逐文件完整性由已签名 manifest 内的 hash（SHA-256）保证**——一次验签 + N 次 hash。签的是 manifest 的原始字节，与它列出的文件是什么格式无关。

## 建议方案

### 1. 关闭 Open question 「flags 是否落客户端本地缓存」，改为回链 + 一处措辞纠正
`[既有推演]`

对侧已裁决（形态、字段、失效语义与降级口径见 `counterpart`）。本库侧的动作是**关闭**，不是复述。**但关闭时必须改掉问句里的一个错误前提：**

- 现问句写的是「flags 是否落地客户端本地缓存**以支撑离线开局**」。**「离线开局」这个用途在对侧不成立**——对侧的启动 pull 是硬阻塞，强制在线下不存在「断网启动并进入轮回」这条路径（口径与理由见 `counterpart`）。
- **若照原措辞关闭，会把一个错误前提一并固化进本库的契约文档**——日后读到的人会以为后端曾为「离线开局」承担过什么。

**建议改写为一行陈述性回链：** flags 的客户端持久化形态、失效语义与降级值口径**已由对侧裁决**，权威在 `game-design-documents/systems/services/content-service.md`「flags：`ContentEnabled` 的第三层」；**本契约不复述、不代为约束**。

### 2. 明写 `no-cache` 是**传输层**缓存指令，不约束客户端的应用层持久化
`[既有推演]` + `[通行做法]`

**这是本节唯一真正新增的语义，也是本草稿在后端侧最有价值的一句。** 端点表里的 `no-cache`（约束 A）约束的是 **HTTP 缓存层**：中间层 / 代理 / CDN 不得把这份按账号计算的应答当作可复用的对象存起来——它防的是**灰度分桶串号**。它**不是**、也无力约束「客户端把已应用的结果自己存一份用于降级」这件事——那发生在应用层，且存的是**这台设备这个账号自己的结果**，与串号无任何关系。

**不写清这一层区分，两个方向的误读都会发生：** 有人据 `no-cache` 反对客户端落盘（把一条防串号的传输指令当成禁止持久化的禁令），或反过来以为后端应当下发某种缓存策略字段（TTL / max-age 语义）来指挥客户端。**两者都错，且都只会在实现期才显形。**

建议落在 `contracts/content-manifest.md`「flags 通道」一节，措辞如：

> **`no-cache` 的适用面是 HTTP 缓存层，不是客户端的应用层持久化。** 它禁止的是中间层复用一份**按账号计算**的应答（防灰度分桶串号）；客户端把**已应用**的那批结果自行持久化以作降级值，属应用层行为，本契约不约束、也不为其下发任何缓存策略字段。其形态权威在 `game-design-documents/systems/services/content-service.md`。

### 3. 后端对客户端缓存的义务 = **零**，且报文零改动
`[既有推演]`

逐条声明（这些是**否定性义务**，写下来是为了让「后端要不要为此做点什么」这个问题此后不再被问）：

| 项 | 结论 | 理由 |
|---|---|---|
| 下发 TTL / `max-age` 语义字段指挥客户端缓存寿命 | **不下发** | 客户端已定不设时间 TTL（判据：设备时钟不可信，回链见 `counterpart`）；下发一个无人消费的字段是纯负债 |
| 在应答体里下发 `accountId` 供客户端给缓存打标 | **不下发** | 客户端用它自己的会话身份打标即可；下发是冗余，且与 `ADR-0002` 的载荷边界（约束 D）同向——端点只给**结果**，不给推导过程与身份回声 |
| 提升 `flagsSchema` | **不提升** | 零新增字段 |
| 新增服务端保证 | **不新增** | B 组三条已足够（见下条） |

### 4. 明写 B 组第 7 条是客户端缓存**可复用性**的服务端支撑（依赖登记，非新增条款）
`[既有推演]`

对侧的缓存之所以能作为降级值使用，其正确性前提正是 B 组第 7 条：**同一 `(flagsVersion, 账号)` 的解析结果恒定**（约束 B / C）。若允许同版本内容漂移，客户端盘上那批就**不再等于**服务端同版本的那批，而客户端没有任何手段发现这件事（它只比版本号）。

- 本条**不新增义务**——第 7 条早已存在，且它已经因为「等值不拉」而被登记为承重条款。
- **要新增的只是一行依赖登记**：让「谁在依赖第 7 条」这份名单**从一项变成两项**（等值不拉 · 客户端降级缓存的可复用性）。理由与本库既有做法一致：条款的依赖方写清楚，日后有人想放宽它时才看得见代价。

### 5. blob 通道**不承载二进制资产**（按对侧裁决），**契约零改动**
`[既有推演]`

对侧答「不开放」（理由与客户端侧形态见 `counterpart`）。本库侧的动作因此是：

- `files[]` **继续只承载 `.tres` 内容文件**；A 组四条保证、`manifest schema` 字段表、签名形态**一字不改**；`manifestSchema` **不提升**。
- 「blob 通道是否向二进制资产开放」这条 Open question **关闭**，改为一条陈述 + 回链 + 下一条的条件化记录。

### 6. 关闭时必须写清：**这不是契约能力不足**
`[既有推演]`

**这句是本草稿在后端侧的第二个承重点。** 若只写「不开放」，日后读到的人会合理地推断「大概是 CDN / 契约做不到」，然后在复议时把力气花在错误的地方。事实相反——**报文层对文件类别中立，这一点已经被剧本文本一节验证过一次**（约束 F）：

| 能力 | 对非 `.tres` 是否成立 | 依据 |
|---|---|---|
| 内容寻址（`<contentRoot>/blobs/<sha256>`） | **逐字成立** | 寻址键是字节的 hash，与格式无关 |
| URL 字节不可变 · 稳定 URL | **逐字成立** | 内容寻址的直接推论 |
| manifest 与其列出文件的发布原子性 | **逐字成立** | 发布顺序（先推全部 blob、后推 manifest）与文件类别无关 |
| 完整性 / 防篡改覆盖面 | **逐字成立** | 一次验签 manifest + N 次 SHA-256（约束 H），签的是 manifest 原始字节 |
| `files[].path` 的路径穿越校验面 | **逐字成立** | 校验的是路径串，与文件内容无关 |

⇒ **限制来自对侧的字段形态与其资源引用模型，不来自本契约。** 建议在关闭那条 Open question 时把这张判断原样写进去（表可精简为两三句），使日后的复议从正确的位置起步。

### 7. 若日后开放，本库须核对的三点（条件化记录，不是待办）
`[既有推演]`

| # | 核对项 | 为什么它不是自动成立的 |
|---|---|---|
| ① | **`files[].size` 的口径与磁盘预检** | 字段语义不变，但量级从 KB 级跃到 MB 级；「下载前预检」这件事仍成立，**运维侧的首包体积与增量下载量上界**要重估——与本库既有的「剧本内容的体积与分发形态」是同一类问题（`open-questions/04-content-delivery.md`） |
| ② | **A 组「字节级 Range 不写进契约」这条否定** | 它与对侧「不做字节级断点续传」互为对位，而**对侧那条的理由带一个量级前提**（约束 G，前提本身见 `counterpart`）。前提变了，两侧须**同批**重估，不能只改一侧 |
| ③ | **CDN 缓存与成本模型** | blob 的 `public, max-age=31536000, immutable` 对 MB 级对象仍正确，但**回源与流量成本模型**与 KB 级完全不同；归 `open-questions/04-content-delivery.md` 与 `06-platform-stack.md` |

**这三点是条件化的：只在「日后开放」这个假设成立时才需要做。** 现在写下它们不是给自己派活，而是让复议者知道要核对什么——**不写，则复议时最可能被漏掉的恰是 ② 那条跨库对位**。

## 后果

- **本库两条 Open question 关闭**，`contracts/content-manifest.md` 的 Open questions 由四条降为两条（余下：多区域一致性 · flags 数据源与分桶的运营形态）。
- **`open-questions/04-content-delivery.md` 不再有「唯一未闭合的语义缺口」这一标注**——协议侧与语义侧同时闭合，该分片余下的全部是运维形态与选型（共同前置仍是 `06-platform-stack.md`）。
- **契约报文零改动 ⇒ 已成文的四份契约无一处需要同步，`openapi.yaml`（尚未落笔）不受影响。**
- **新增的全是「否定性义务」与「能力声明」**——它们不增加实现负担，只减少日后被反复追问的次数；这与本库既有的「A 组不提供的……」那一段是同一种写法。
- **B 组第 7 条的分量被显式抬高**（依赖方从一项变两项）：日后若有人以「临时改个比例」为由要撬它，代价表上会多一行。
- **若日后开放二进制**，本库已备好三点核对清单，其中 ② 明确要求两侧同批重估——**这是本次唯一防住的跨库漏项**。

## 备选方案（已考虑并否决）

- **照原措辞关闭 flags 缓存那条（保留「以支撑离线开局」）** — 否决：把一个在对侧不成立的前提固化进本库契约，日后读者会以为后端曾为离线开局承担过义务。
- **在 flags 应答里新增缓存策略字段（TTL / `maxAgeSeconds`）** — 否决：客户端已定不设时间 TTL（判据：设备时钟不可信）；新增一个无人消费的字段是纯负债，且会诱导实现方去「遵守」它。
- **在 flags 应答体里回显 `accountId`** — 否决：客户端用自身会话身份打标即可；与 `ADR-0002` 的载荷边界同向（端点只给结果，不给身份回声与推导过程）。
- **为「客户端缓存的可复用性」新写一条服务端保证** — 否决：B 组第 7 条已逐字覆盖它。新写一条 = 同一义务两处表述，两份各自漂移而无机制发现——本库反复否决的形态。
- **把「blob 通道不承载二进制」写成一条服务端保证（A 组第 5 条）** — 否决：**它不是服务端的义务，而是对侧的合并纪律**。写进 A 组等于声称后端会拒绝二进制文件，那既非事实（报文层不区分类别）、也无人执行（CDN 直接服务静态对象）。正确落点是陈述 + 回链。
- **只关掉两条 Open question，不写「能力对文件类别中立」那几句** — 否决：省下三句，换来日后复议从错误的位置起步（误以为契约做不到）。
- **把三点核对项登记为待办** — 否决：它们条件化于一个当前答「否」的假设；登记为待办会让 `04-content-delivery.md` 的清单虚长，而该分片的其余条目都是真待办。

## 与既有决策的张力

**无。**

本草稿不与本库任何已定条款冲突：A 组四条、B 组三条、schema 字段表、端点与域划分、签名形态全部原样。新增内容全部是**澄清（`no-cache` 的层次）、依赖登记（B 组第 7 条的依赖方）与能力声明（文件类别中立）**，三者都只是把已经成立的事实写出来。

> 唯一需要留意的**非冲突性重叠**：建议 2 的层次澄清与 `contracts/envelope.md` §3 的「flags 归 API 域、不在 `contentRoot` 下」谈的是**同一个 `no-cache`**。两处不重复写——§3 说的是**它为什么在 API 域**，本次新增说的是**它约束到哪一层为止**。建议在 `content-manifest.md` 侧落笔并回链 §3，不在 `envelope.md` 侧复制。
