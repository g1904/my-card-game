# 方案草稿 — 灵根（`Affinity`）与功法属性

> **本稿已经过 2026-08-29 的批量评审裁决，形态与初稿有实质差异。** 初稿提出的「契合度三态 + 可达层数折减 + 取池权重因子 + `SpiritRootTuningData` 平衡资源」整套机制**已被用户否决**，改为**硬性修习准入**（见「已裁决的形态」）。裁决逐条记录在末节。

## 问题

修仙题材里，**灵根**（角色的先天资质）与**功法属性**（一门功法走的是哪一路）是这个世界观最基本的两个分类轴，而本库**一格都没有**：

- `CharacterData`（角色模板）**至今没有任何字段表**——全库已定的只有「一个绑定神通 + 两门绑定功法 + 稳定 `Id` + `ContentEnabled` + 可挂 `Artwork`」这几句语义，没有一条成文字段。
- `CultivationTechniqueData`（功法）**只有两条可筛维度**：`Pool`（敌我池划分）与 `Rarity`（稀有度档）。**没有任何流派 / 属性 / 门派轴。**

它悬着，卡住的是三件具体的事：

1. **角色之间除了「神通 + 两门功法各不相同」之外没有第二条辨识轴。** 而角色模板池此前裁决为**全池指定**，该裁决**自陈接受了一条代价**：「ch1 无限重试下，角色强度差会塌缩为『只有一个角色被玩』」，并明写「这条代价不得删掉——它是日后重估角色池设计的判据起点」。本稿正是那次重估的输入。
2. **功法的「构筑决策」目前只由 `Rarity` 一条轴承担。** `deck/_index.md` 要求「一门稳定的低稀有度 + 一门 build-around 的高稀有度必须是一个真实的构筑决策」，而次类型清单已归零，缺一条与角色身份挂钩的构筑条件。
3. **`content/cultivation-technique/` 与 `content/character/` 都还没开张。** 一旦第一批 `.tres` 写下，再往这两个类型上加分类维度就要重扫全部条目。**这个加法窗口现在敞开，写下第一批条目那一刻开始收窄。**

## 约束（来自既有设计）

### 一、新增一条分类维度的准入门槛（两条锋利判例）

- **`ADR-0002`：** 「共有一套结算形状与呈现形状的，归为一类；类内的差异用参数 / 档位表达，而非新增枚举值」；**风味差异一律不给枚举值**。
- **判例甲 · `Creature`（灵宠）主类型被整条删除**（`handoffs/2026-08-11c`）：「灵宠与阵法的规则差别本就为零……与其为一个没有规则差异的主类型保留一格枚举，不如删掉」；**备选的「保留概念占位」与「降为次类型」均不采用**。
  ⇒ **一条没有规则后果的分类维度，本库连概念占位都不给。**
- **判例乙 · 18 行次类型清单初值整体作废**（`handoffs/2026-08-15`）：准入判据 **① ≥3 个内容条目共享 ② ≥1 处目标筛选引用（存在 payoff）**；「没有 payoff 的次类型就是展示标签」。

> **本稿已过这两道门**：修习准入是一条可机械判定、直接改变候选池的规则后果（见「已裁决的形态」§3）。

### 二、决定形态的四条硬事实

- **战斗内完全不感知功法**（组装时已展开为卡牌集合；存档存「功法 `Id` + 层数」而非展开后的牌）。→ `deck/_index.md`、`terminology.md`。
- **一张卡可被多门功法引用**；成员关系的**唯一权威在功法侧，卡牌侧不带功法标记**——`ADR-0054` 明确否决「两侧都写」，理由是**制造第二权威**。
- **`MaxTier` 就是「已写了几套卡牌定义」**（`ADR-0054`：每门功法 × 每层各一套）。
- **`DeckElements` 恒不经 modifier pipeline**。

### 三、落点与结构纪律

- **`ADR-0068` 抽取原语只有两级，不设第三级**；分界判据 = 这道过滤需不需要读 `Profile`。权重表归 `systems/balance.md`，**不落 `DrawPool<T>`**。
- **`ADR-0073`：候选短缺的三段处置**；三格取池余量 `GrantPoolMargin` / `ResearchPoolMargin` / `ExchangePoolMargin`。
- **`ADR-0019` / `ADR-0012`：静态字段不落存档**；`XxxData : Resource` 是共享只读单例，运行时不得写。
- **`ADR-0058` / `content/_index.md`：`content/` 层不定义字段**，只写「填了什么值 + 权威回链」。
- **必填枚举的缺失检测**：`CardType` / `Pool` / `UsableScene` 均「必填、无默认、缺失 `PushError`」；`Source` 以 `Unknown = 0` 防御性成员兜底。
- **命名硬约定的三处先例**：`Tier` vs `RarityTier` 不得复用；`TechniqueTier` vs `level` 必须一眼可分；`EnemyLevelRange` 刻意不写成 `LevelBand`。

### 四、平衡与范围的边界

- **`vision/scope.md`「范围之外（暂时）」明写：支撑「Reigns」式平衡张力的完整属性模型。** ——本稿已裁定不落在该排除项内（末节裁决 ②）。
- **支柱 7「直觉化系统」· 支柱 8「渐进式复杂度」· 反目标「不是 MTG 那样规则繁重的系统」。**
- **先定形状、后定数值**（`ADR-0006` + `scope.md`）。

## 已裁决的形态

### 1. 两层：灵根挂角色、属性挂功法；**卡牌侧一格不加**

`[既有推演]`

| 层 | 载体 | 形态 | 落存档 |
|---|---|---|---|
| **灵根** | `CharacterData.Affinities` | `Affinity[]`，**首批长度恰为 1**（五个角色各一个单灵根） | ✗ |
| **功法属性** | `CultivationTechniqueData.Affinities` | `Affinity[]`，功法要求角色**具备的**灵根属性（首批每门一个；**允许为空 = 无属性要求的通用功法**） | ✗ |
| **功法的灵根数量要求** | `CultivationTechniqueData.MaxAffinityCount` | `int`，角色灵根数量上限；**`1` = 单灵根专属**，`0` = 不限 | ✗ |
| **卡牌** | `CardData` | **不加任何格** | — |

**卡牌不加属性，是结构性的、不是取舍：**

- **一张卡可被多门功法引用**（`ADR-0054`）。若卡牌也带属性，同一张卡在火系功法与水系功法里属性必然打架 ⇒ 两个权威，且**本库没有任何机制能发现它们不一致**——这正是 `ADR-0054` 否决「两侧都写」的逐字理由。
- **战斗内不感知功法** ⇒ 卡级属性无法与角色灵根建立任何战斗内关系，剩下的只有卡面上的一个风味标记，而那正是判例甲、判例乙删掉的那种东西。
- **负面边界（须随本稿落笔）：** 日后若确要做「战斗内五行相克」，**载体只能是既有次类型 `CardSubtypeData` + `EntryFilter.RequiredSubtypes`，且必须照常过准入判据（≥3 条目共享 + ≥1 处筛选引用）**；不得以「灵根已经有五行了」为由绕过，也不得在 `CardData` 上新开一格。

### 2. `Affinity` 枚举：五行五值 + 一个哨兵，**为日后扩展留成员位**

`[取向选择 → 已裁决]`（定名 `Affinity` 由用户裁定；`Element` 与 `Phase` 均已被本库占用，见备选）

```csharp
public enum Affinity
{
    Unspecified = 0,   // 防御性哨兵：唯一作用是让「漏填」可被加载期检出；照 Source.Unknown = 0 的先例
    Metal = 1,         // 金
    Wood  = 2,         // 木
    Water = 3,         // 水
    Fire  = 4,         // 火
    Earth = 5,         // 土
}
```

- **`Unspecified = 0` 是必需的**：Godot 的 `[Export]` 枚举未填即取 0，没有哨兵就无法把「漏填」与「填了金」区分开——`Pool` / `CardType` 必填纪律的全部理由正是「默认值会让漏填悄悄落进某个池」。
- **首批只有五行五值。** 用户已明确日后可能加**五行以外的灵根**（雷 / 冰 / 风一类）。**追加成员的成本为零**：`Affinity` 不落存档、不进上行负载 ⇒ 加成员**不 bump `schemaVersion`、无迁移、后端零影响**。这一点须写下来，使今天的不做不构成明天的债。
- **首批不做相生相克。** 无契合度、无三态、无相克环——五行之间**在首批没有任何规则关系**，关系只存在于「角色灵根 ⊇ 功法要求」这一条包含判定上。相生相克的位置留着，日后要开是纯加法。
- **风味标注走描述文本**（`LocalizedText`）。

### 3. 关联规则：**硬性修习准入**（唯一的规则后果）

`[取向选择 → 已裁决]`

```
CanLearn(character, technique) :=
      technique.Affinities ⊆ character.Affinities
  && (technique.MaxAffinityCount == 0
      || character.Affinities.Length <= technique.MaxAffinityCount)
```

不满足 ⇒ 该功法**不进入**该角色的任何玩家侧候选：四个取池点（闭关三选一 · 开局构筑三选一 · 商店 `CultivationTechnique` 族 · 战后奖励池功法族）与 `UpgradeTechnique` 候选一律过滤掉。

**两格字段各自的职责（用户裁决原意）：**

- **`Affinities`（要求角色包含的灵根属性）** —— 决定「这门功法属于哪一路」。首批每门功法一个属性；**未来可能多个**（例：一门功法要求同时具备水与火）。**空数组 = 无属性要求**，任何角色都能修（题材上即「凡人皆可修的基础法门」）——空集是任何集合的子集，故这一档**不需要判定式上开任何特例**。
- **`MaxAffinityCount`（角色灵根数量上限）** —— **单灵根专属功法池的承载**。多灵根角色天然能修更多属性的功法（池更宽 = 更强），故必须有一批**只有单灵根角色能修**的功法来对冲；`MaxAffinityCount = 1` 就是这批功法的标记。**首批五个角色全是单灵根，这一格暂时不产生差异，但它必须现在就在**——否则日后引入多灵根时，对冲手段要靠给全部既有功法补一格来实现，那正是加法窗口关闭后的高成本形态。

**首批（五个角色全为单灵根）判定式实际展开成什么样，须写清楚：** 对 `Affinities = [Fire]` 的角色，可修池 = **`[Fire]` 的功法 + 无属性要求的通用功法**，两档合成**一个**池；而 `MaxAffinityCount` 那一条对它**完全不产生过滤作用**——角色灵根数 1 是最小可能值，功法填 `0` 还是 `1` 都放行。**`MaxAffinityCount` 是为多灵根角色预备的字段，在首批不生效**，这不构成「无 payoff 的字段」（它的 payoff 在同一条判定式里、随第一个多灵根角色即时生效），但它意味着**首批不需要刻意去铺 `MaxAffinityCount = 1` 的条目**。

**接入点：** 这道过滤**需要读 `Profile`**（经 `characterDataId` 取到 `CharacterData.Affinities`），故按 `ADR-0068` 的分界判据，它**不进 `DrawPool<T>`**——`DrawPool<T>` 仍只认内容侧过滤（`ContentEnabled` / `ExclusiveSource` / `Rarity`）。准入由**调用方**（future-event-service 物化侧 / combat-service 收口侧）在把候选交给 `PickMany` **之前**筛掉。**零新原语、零签名变更。**

**敌人侧一律不做准入**：`EnemyData` 逐条引用功法 `Id`，走**读取侧** `Get(id)` 而非取池（`deck/_index.md` 原文）；敌方功法照常带 `Affinities`，纯作图鉴 / 呈现价值。

### 4. 准入是**硬收缩**，这带来三条必须一起落笔的后果

`[既有推演]`（这是裁决的必然推论，不是可选项）

1. **三格取池余量须按收缩后的池重估。** `GrantPoolMargin` / `ResearchPoolMargin` / `ExchangePoolMargin` 现在的口径是「全池减去已持有」；准入后每个角色实际可见的池**只有全池的一个子集**。余量阈值必须按**最小的那个子集**（即可修功法条目最少的那个灵根）来定，否则某个角色会频繁撞上候选短缺。
2. **`ADR-0073` 的候选短缺三段处置会被更频繁触发**，须按新口径复核三段的边界是否仍然合适。
3. **内容编排从「建议」升级为硬约束：** 每个在册灵根的可修功法条目数（`Pool != Enemy` 且该角色通得过准入的）必须 ≥ 取池余量阈值。`/audit-content` 加一条**阻断级**核对（不是告警）：任一在册角色的可修功法数低于阈值 → 报错，因为它意味着该角色**开不出局**。

> **这一条是整份方案的真正成本所在。** 初稿曾以「取池不因角色收缩」为由否决硬禁学；用户裁决改为硬准入，故该理由不再成立，代价改由上述三条承接。它不是缺陷，是这个形态的必然账单——但必须显式记在设计里，不能等到内容铺开才发现某个角色只有两门功法可修。

### 5. 负面边界：灵根**只接修习准入这一处**，此外一格不碰

`[既有推演]`

**灵根不影响：** `mana` / `manaLimit` · 道念（产出与削减）· 生命 / 寿元与 `lifeSpanCost` · 商店价格 · 隐藏属性（道心 / 煞气）· 经验值 · `baseMomentum` · 敌人赋级 · 功法可修层数（`MaxTier` 一律不折减）· 任何卡牌数值 · 任何战斗内规则。

逐条依据：**战斗侧那一批根本看不见功法**；其余每一项都已有指定的唯一旋钮（寿元定价表 / 商店「族 × 稀有度」表 / `HiddenStatGrade` / `ExperienceGrade` / `EnemyLevelingData`），往上叠第二个输入正是本库反复否决的「第二条强度曲线」。

**特别是不折减 `MaxTier`：** `MaxTier` 就是这门功法**已经写了几套卡牌定义**，任何「按灵根多修 / 少修一层」的做法要么要求一套不存在的卡，要么让已写好的一套卡对某些角色永远不可见。**灵根的表达完全落在「能不能修」，不落在「能修多深」。**

### 6. 呈现：三处，全部落在既有屏内，不新增任何屏

`[通行做法]` + `[既有推演]`（约束来自 `.claude/rules/ui-input-rules.md`）

| 位置 | 呈现 | 依据 |
|---|---|---|
| **角色选择屏**（5 张卡竖屏一屏内） | 每张卡一行**灵根图标 + 名称**（例「灵根：火」）。**不写品级标签**（无「天灵根」说法）、不写数值 | 该屏既定「不展示数值，与『给方向不给数字』一致」 |
| **功法候选卡**（闭关 / 开局构筑 / 商店 / 战后奖励，四处同一套卡片） | **属性图标**；不可修的功法本就不出现，故**无需灰显态**。`MaxAffinityCount = 1` 的功法带一枚「单灵根专属」角标 | 玩家需要的是结果不是公式；**常驻标记，无 hover-only 可供性** |
| **功法图鉴 `TechniqueCodex` 词条** | 词条增「属性」一格 +（若有）「单灵根专属」标注 | 词条现为「功法名 / 描述 / `Rarity` / 路数概括 + 可选 `CodexFlavor`，不列卡牌清单」（`ADR-0095`）——属性是路数概括的天然一部分，**不泄露卡表** |

- **卡面上不加任何属性标记**（`ADR-0083`：full art，唯一文字是 `manaCost`；且卡牌本就不带属性）。
- **UI 文案一律走 `res://text/` 翻译键**；功法 / 角色的显示文本走 `LocalizedText`。

## 具体形态（可 derive 的落地面）

### A. 字段面

**`CultivationTechniqueData` 增两格：**

| 字段 | 类型 | 必填 | 默认 | 缺失 / 违规处置 |
|---|---|---|---|---|
| `Affinities` | `Affinity[]` | 是（**可为空数组** = 无属性要求） | **空数组** | 含 `Unspecified` / 含重复 → `PushError` + 功法 `Id` + `.tres` 路径 |
| `MaxAffinityCount` | `int` | 否 | **0**（= 不限） | `< 0` → `PushError`；`> 0` 且 `< Affinities.Length` → `PushError`（自相矛盾：要求的属性数已超过允许的灵根总数，该条目对任何角色都不可修） |

**`CharacterData` 增一格：**

| 字段 | 类型 | 必填 | 默认 | 缺失 / 违规处置 |
|---|---|---|---|---|
| `Affinities` | `Affinity[]` | **是** | **无** | 空数组 / 含 `Unspecified` / 含重复 → `PushError` + `characterId` |

**一律不落存档、不进上行负载、不进任何运行时实例类型（`CardInstance` / `EnemyInstance` / `EventOption` 均不加格）。**

> **功法侧允许空数组的一条代价，须明写：** 空 `Affinities` 既表示「有意的通用功法」，也是「整格漏填」的形态 —— 这两者**不可区分**（`Unspecified` 哨兵只能检出「填了但填错」，检不出「没填」）。本库对 `Pool` / `CardType` 的必填纪律正是为防这类漏填悄悄落进某个池。**这里接受该风险**，理由：漏填的后果是「一门功法对所有角色可见」，属于**可见性放宽**而非「敌方内容混进玩家池」那种越界（`Pool` 仍在独立把关）；且 `/audit-content` 会汇总通用功法的条数与占比（见下），异常膨胀一眼可见。**若日后觉得不够，正确的收紧方式是加一格显式的 `NoAffinityRequired` 布尔标记，而不是把空数组重新变成非法。**

> **首批的实际取值：5 个角色，`Affinities` 各为 `[Metal]` / `[Wood]` / `[Water]` / `[Fire]` / `[Earth]`（长度恒为 1）。** 「长度恰为 1」是**内容编排口径，不是字段约束**——字段本身即为数组，日后加多灵根**零结构变更**。

### B. 存档与后端

**存档 schema 增量 = 0。** `CharacterProfile` 字段数不变、`Status` 不变、`TechniqueEntry(TechniqueId, Tier)` 一字不改、`ProfileChangeSpec` 不加列、`StatusKey` 不加成员、**不 bump `schemaVersion`、无迁移**。**后端零影响**（无新透明段 JSON path、无新报文、无回声约束字段）⇒ 本稿**不构成跨库改动**。

**没有新增平衡资源。** 初稿的 `SpiritRootTuningData` 随契合度一并取消——准入是布尔判定，无可调数值。唯一受影响的数值是既有的三格取池余量（§4.1），它们住在已有的落点。

### C. 加载期校验（六条，全部带定位上下文）

| # | 违规 | 处置 |
|---|---|---|

### D. 内容编排口径

- **角色池 5 个，各持一个不同的单灵根**（金木水火土全覆盖）——这既是题材上的整齐，也保证每个 `Affinity` 成员都有至少一个持有者，从而让校验 6 的告警有意义。
- **功法池的形状 = 五份小池 + 一份共享池。** 每个角色的可修池 = 「自己属性的功法」+「无属性要求的通用功法」。通用功法是压低首批内容量的主要手段（否则五个不相交的池各要独立铺够）。
- **功法条目的属性分布**：每个角色的可修池（含通用功法）须满足校验 5；`/audit-content` 汇总五档条目数、通用功法条数与占比，并列出每个角色的可修池大小。
- **通用功法的占比须控制。** 它对全部角色一视同仁 ⇒ 占比过高会把灵根的辨识度稀释回「五个角色抽到的东西差不多」，那正是本方案要解决的问题。**建议把 build-around 的高稀有度功法一律带属性、通用功法偏向低稀有度的底盘**，使「底盘共享、亮点分化」——但这是编排口径的建议，不是字段约束。
- **`MaxAffinityCount = 1` 的「单灵根专属」功法首批可以为空**（五个角色全是单灵根，不需要对冲）。它的内容义务在**引入第一个多灵根角色的同一批**产生，须与那批角色同批铺。

### E. 边界情形：overlay 在轮回中途改了灵根或功法属性

`[既有推演]`（与「读档宽 / 入口严」+「确定性边界只到同一 `contentVersion` 内」同款）

**已持有的功法若因内容更新而不再通过准入：读档不拒绝、不没收该功法、不告警玩家**，只是它此后不再出现在 `UpgradeTechnique` 候选中。理由：功法已写进 `CharacterProfile.technique` 且已展开为实际卡组，没收它等于在轮回中途拆掉玩家已获得的构筑；这落在既有的「不承诺跨内容版本复现」之内，**不构成新的例外**。

## 备选方案（已考虑并否决）

- **契合度三态（契合 / 中平 / 相冲）+ 可达层数折减 + 取池权重因子 + `SpiritRootTuningData`（初稿的推荐方案）** — **用户裁决否决**。它用一套连续的软性偏好表达灵根，代价是引入一份平衡资源、一条五行相克环、一个三态枚举与四张数值表，而其中「层数折减」还与 `MaxTier` 的定义（已写了几套卡）相抵。硬准入用一条布尔判定表达同一件事，机制面小得多。
- **五行下放到卡牌（`CardData` 加一格），做战斗内相克倍率** — 否决，四条独立理由任一成立即足够：① 一张卡可被多门功法引用 ⇒ 卡级与功法级属性必然打架（`ADR-0054` 逐字否决过的「第二权威」）；② 战斗内不感知功法 ⇒ 相克无法与角色灵根挂钩；③ 相克倍率是**乘区**，而卡牌道念量纲尚未校准，加乘区即不可平衡；④ 5×5 矩阵与支柱 7、反目标「不是 MTG 那样规则繁重」正面冲突。
- **在组装卡组时把功法属性烙进 `CardInstance`** — 否决：同一张卡在不同功法下会变成不同的东西，玩家无法从卡面读出因果；且 `CardInstance` 会进决策点存档，等于把静态属性塞进存档面。
- **契合度抬升 `MaxTier`（契合 = 可多练两层）** — 否决：`MaxTier` 是已写了几套卡牌定义，抬升它就是要求一套不存在的卡。这条最符合直觉的做法在结构上不可能。
- **把灵根惩罚放在 `lifeSpanCost`（相冲功法更费寿元）** — 否决：`lifeSpanCost` 挂在**事件**上、在玩家看到槽内候选**之前**就已支付，够不着单个候选；而在槽内操作上另收代价被 `ADR-0022` 明确关死。
- **用取池权重代替硬准入（同灵根功法更常见，但都抽得到）** — **用户裁决否决**。它保住了取池余量不变（初稿正是以此否决硬禁学），但表达不出「单灵根专属功法」这件事：权重再低，多灵根角色仍能拿到专属功法，对冲机制当场失效。硬准入是「单灵根专属池」成立的前提。
- **`SpiritRoot` 做成五格权重向量（每元素一个 0–100 的资质值）** — 否决：表达力提升有限，却把判定从布尔变成连续量，需要映射表 + 一套呈现；且它正是 `scope.md`「范围之外」的那种「完整属性模型」。
- **`Element` 作为五行的类型名** — 否决：与 `ChangeElement` / `DeckChangeElement` / `AbilityChangeElement` / `ItemChargeElement` / `ProfileChangeSpec.Elements` 整个 element 家族同页两义，正是 `Tier`/`RarityTier`、`Band`/`LevelBand` 两处先例所防的失败模式。
- **`Phase` 作为五行的类型名**（五行 = Five Phases 的标准译法） — 否决：本库在回合结构处**刻意不借 `main phase` 一词**、统一以 `step` 收尾；把 `phase` 以另一种含义重新引进同一个战斗相邻的代码库，是同一条失败模式。
- **`Wuxing` / `Aspect` 作为类型名** — 均未被否决，但**用户裁定取 `Affinity`**。`Wuxing` 零歧义但会是本库第一个拼音标识符；`Aspect` 是泛化英文词，日后有撞车风险。
- **修仙品级标签（天灵根 / 三灵根 / 五灵根）** — **用户裁决否决**：本作没有「天灵根」说法。品级隐含「单灵根最强」，而机制上它只是「池更窄但有专属功法」，标签会制造预期落差。
- **给 `EnemyData` 加灵根** — 否决：敌人逐条引用功法 `Id`、走读取侧而非取池，准入对它无处作用 ⇒ 一格无规则消费点的字段 = 判例甲。
- **把灵根做成账号级的元进程解锁 / 付费点** — 否决：`vision/scope.md` 明写「元进程解锁」出范围；`systems/monetization.md` 的负面边界五项已关死付费解锁。

### 2. 🔴 硬准入使功法取池按角色收缩 —— 初稿否决「硬禁学」的理由已被裁决推翻

### 3. 🔵 角色模板池裁决「已接受的代价」需要改写（不是冲突，是触发）

`solution-draft-character-template-pool.md` 自陈：「ch1 无限重试下，角色强度差会塌缩为『只有一个角色被玩』……提炼时不得把这条代价删掉——它是日后重估角色池设计的判据起点」。

**本稿正是那次重估的输入。** 灵根把角色差异从「谁更强」推向「能修哪一路功法」，从而部分——**但不完全**——化解该代价：仍可能存在一个综合最优的属性池。**建议提炼时把那条代价改写为「已由灵根部分缓解，仍待实测」，而不是删除它。**

### 4. 🔵 多灵根引入时的平衡对齐尚无解法（用户已明确留待未来）

多灵根角色的可修池天然更宽。对冲手段（`MaxAffinityCount = 1` 的单灵根专属功法）**结构已就位**，但「多宽的池 = 多强的专属功法」这条换算**没有答案**，且它依赖尚未定的道念量纲。**首批全为单灵根，故该问题在首批不发生**；引入第一个多灵根角色时必须先答它。
