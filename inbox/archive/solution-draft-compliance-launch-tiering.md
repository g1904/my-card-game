# 方案草稿 — 合规能力的上线分级

## 问题

`contracts/compliance.md` 的**契约面已完全成文**——六个端点、报文字段表、`complianceTicket` 机制、四条拦截码及其求值顺序、三条端点自身错误码、四个旋钮初值；`operations/compliance-ops.md` 的**运维形态亦已完全成文**——可信时钟、时段规则集与节假日日历、三个失败面的降级语义、注销冷静期的长时状态机、导出的任务 / 产物 / 链接签发。

**悬着的不是「怎么做」，而是「什么时候做」：** 四项能力里哪些必须在首次上线前具备、哪些可以后置。数据导出已定首版必做（`contracts/compliance.md` §8），其余三项此前被记为「与国内渠道过审、备案排期耦合」而未分级。从属项：**第三方昵称审核首版是否启用**——判定链第④级已留出适配器位，但 `operations/moderation.md` 与 `operations/external-providers.md` 给的是**默认形态**（首版不启用 · 透传恒放行），两处都自陈「是否启用取决于本条分级」，因此是默认而非裁决。

**它卡住三处：**

1. `operations/deployment.md` 的上线前置清单——四项合规能力一项都没进去；
2. `vision/scope.md` 的 In scope——它自陈「合规能力的上线分级……决定首版实际启用哪几项」；
3. `contracts/auth.md` / `systems/account.md` / `operations/moderation.md` **三处判定链第④级的 derive 验收面**——因「占位机制不构成 ready」而被整体排除。

## 约束（来自既有设计）

### 已定案、本方案不得触碰的形态

- **数据导出首版必做**，取最简形态（`contracts/compliance.md` §8）。理由原句：「合规要求通常在过审阶段才显形，**届时补做会挤在发版窗口里**」。
- **注销 / 导出必须在 App 内可做**（`contracts/compliance.md` §1）：「PIPL 明确要求删除权与可携带权，**国内应用商店审核亦查『App 内可注销』**」。「走站外（官网 / 客服）」已在同文件的备选清单中被明确否决。
- **未成年判定的数据源是实名核验返回的出生日期**（`contracts/compliance.md` §7），不单独存年龄。
- **四条拦截码的求值顺序写死、逐级短路**（`contracts/compliance.md` §5 · `ADR-0037`），`compliance.playtime_blocked` 恒为第④级。
- **拦截只在 `signin`**（`contracts/compliance.md` §4 · `contracts/auth.md` §5a）。
- **形态与上线时点是两件事**（`operations/compliance-ops.md`「上线分级」）：「形态在此定死……分级落定后，在上面各节标注所属档次即可——**不需要改动任何形态**」。**本草稿严格照此，一个形态字段都不动。**

### 既有设计中已经以「四项在线」为前提的五处

这五处不是本方案的主张，是**直读到的现状**。它们共同构成本方案最强的依据：

| # | 出处 | 它以什么为前提 |
|---|---|---|
| 1 | `operations/environments.md`「区域与合规」：「**主区在中国大陆境内。** 面向国内渠道（登录 / 支付 / **实名 / 防沉迷**）反向约束存放地」 | 实名与防沉迷被列为**选定主区的理由**之一 |
| 2 | `operations/deployment.md`「启动自检」：「启动自检解析时段规则集的时区名……解析失败即**拒绝启动**」 | 一条**无条件**的启动断言，其对象是防沉迷的时段规则集 |
| 3 | `operations/environments.md`「限流的实现分层」把「**未成年时段判定**」列为 fail-closed 三条例外之一（`ADR-0031`），理由原句「**错误放行一个未成年账号是合规事故（渠道下架 / 监管处罚），不可回收**」 | 一条已 Accepted 的 ADR 为该判定路径定了降级语义 |
| 4 | `ADR-0039` 决定正文：「首版：**短信 2 家 · 邮件 0 家 · 实名核验 1 家 · 昵称审核 0 家**」 | **本库已经做过一次同形的首版分级**，并把实名核验放在了「首版接入」那一侧，而 `Email` 与昵称审核明确记 0 |
| 5 | 客户端 `game-design-documents/vision/scope.md`：「须正面处理**实名 / 防沉迷 / PIPL / 渠道审核 / 账号注销 / 数据导出**等合规」 | 对侧范围文档把六项**并列**，未作任何首版 / 后置区分 |

### 与之对称的反证（列出以免本方案显得是单向凑证据）

库内确实存在**支持后置**的机制性依据，且不止一条：

- `ADR-0015` —— 未知 `reasonKey` 回落一级键 ⇒ 后端扩取值表**不要求客户端同批发版**；
- `ADR-0044` —— 第三方审核判「待复核 / 不可达」与「未启用」走**同一个出口**（`204` + 入复核队列），`reasonKey` 表不加第四值 ⇒ 启用与否**无契约面差异**；
- `ADR-0038` —— 换 / 不接服务商是适配层内部的事，**端点侧与契约面零改动**。

**但这三条支持的恰恰只是「昵称审核第④级」，不是四项能力本身。** 它们精确地划出了唯一真正可后置的那一项——与本方案的结论互相印证，而非相反。

### 排期处置的既有先例

`ADR-0042`（微信开放平台资质过闸）已为本域定下唯一一条排期处置：**「审批未在计划上线日前到位 ⇒ 推迟上线」**，后果段「上线日成为一个由外部审批决定的变量，**排期必须把它当硬前置而非风险项**」。本方案建议把同一处置扩到合规四项，**不新造纪律**。

## 建议方案

### 一、分级框架：三档 + 一条判据

`[通行做法]` + `[既有推演]`

建议按**驱动力**分档，而非按「重要程度」这种没有判据的直觉：

| 档 | 定义 |
|---|---|
| **T0 · 法规硬下限** | 缺失即不合法运营，与具体渠道无关 |
| **T1 · 渠道过闸下限** | 法条之外，国内应用商店 / 渠道审核会实测的项，缺失即被打回 |
| **T2 · 可后置增强项** | 不影响 T0 / T1 过闸，上线后纯增量补齐 |

**建议把「能否落 T2」的判据收敛为一条：**

> **后置之后再补，是否需要对存量账号做一次追溯动作？需要 → 不得后置。**

这条判据不是新造的——它正是 `operations/deployment.md` 发布前置清单四项所用的既有判据（「首批真实账号落地的那一刻，『线上无真实账号数据』这个前提永久失效」）。`operations/compliance-ops.md` 已用同一判据把年度日历录入**排除在**那份清单之外（「本条每年重来一次」，不共用那个不可逆时刻）。**判据的正反两个用例都已在库内**，本方案只是把它复用到合规域。

### 二、推荐分级：四项能力全部首版必备

`[既有推演]`

| 能力 | 建议档 | 依据 |
|---|---|---|
| **实名核验** | **T0** | ① 它是防沉迷的**唯一**数据源（§7）——不上实名，防沉迷在结构上不成立；② **后置需要追溯动作**：首版不上 ⇒ 积累一批未实名存量账号 ⇒ 启用之日 `compliance.realname_required` 对全体存量**同时**成立，是一次全量拦截潮，而拦截只在 `signin`、求值顺序写死，**没有任何灰度旋钮**；③ 约束表第 1、4 两处已以它在线为前提 |
| **防沉迷时段** | **T0** | ① **建议不与实名拆档**：实名一旦在线，服务端就**已经知道**某账号是未成年（`isMinor` 由核验回传）——知情而不限制，其合规敞口**大于**两项都不上；② 约束表第 2、3 两处（启动断言 · `ADR-0031` 的 fail-closed 例外）均以它在线为前提；③ 它是四项里**唯一会在会话中途生效**的能力（§7 的五步映射），后置意味着这条路径首版全程是死代码 |
| **账号注销** | **T1**（建议与 T0 同批过闸） | ① 理由由 `contracts/compliance.md` §1 **直接给出**（PIPL 删除权 + 商店审核查 App 内可注销），且「走站外」已被明确否决；② **后置有不可逆连带**：`ADR-0035` 后果段原句「墓碑行的存在使『`account_id` 存在』**不再等价于**『账号可用』，**读路径须以 `deleted_at_utc` 判定**」——越晚做，需要回头改的读路径越多；③ 形态全部成文（`ADR-0033` / `0034` / `0035`），冷静期 15 天是纯配置，边际成本 ≈ 三张表的一次 expand + 一条周期扫描（`ADR-0034`：零新增组件） |
| **数据导出** | **T0 · 已定，本草稿不重开** | `contracts/compliance.md` §8 |
| **第三方昵称审核适配器** | **T2 · 建议首版不启用** | 见「三」 |

**一句话结论（建议）：四项能力不分档，全部首版必备；可后置的是各项的「增强项」，不是能力本身。**

**建议的 T2 增强清单**（后置这些均不产生追溯动作）：

- **实名**：证件类型扩展（首版仅中国大陆居民身份证；§10 已明写扩展 = 追加一个可选字段，**非破坏性变更**）· 第二家核验供应商（`ADR-0039` 已定单供，另有一家完成合规评估但不接入）。
- **防沉迷**：节假日日历的第三方交叉核对（已定**不作判定输入**）· `MinorCurfew` / `MinorDailyLimit` 在监管口径拆开后的差异化（`playtime_ruleset` 表结构已能分别表达）。
- **注销**：无（形态完整）。站外申诉通道不在本库范围。
- **导出**：产物内容扩类（白名单是**正列**，扩项是纯增量 + 同批改一条断言）。
- **昵称第三方审核**：整项。

### 三、从属项：建议第三方昵称审核首版不启用，并补一条启用触发器

`[既有推演]`

**建议维持「不启用」，依据链五条，全部来自本库既有文本：**

1. `contracts/auth.md` §8 已论证昵称在本作**没有任何玩家间可见性**（单人游戏、无排行榜 / 分享）⇒ 残留风险面**只剩合规抽查**一项。
2. 抽查面已由**本地词表两档分级 + T1/T2/T3 存量扫描 + 三档处置阶梯**完整承接（`operations/moderation.md`），**不依赖第④级**。第④级是增强，不是承重。
3. 启用需要一对以**真实人工判定样本**标定的阈值（`moderation.md`：「能力未启用 ⇒ 不定值……启用之日以真实样本标定」）。首版无样本 ⇒ 启用即等于上一对未标定阈值；其误拒会以 `SensitiveWord` 告诉玩家「你的昵称违规」——而这正是 `systems/account.md` N9 与 `external-providers.md`「把外部抖动伪装成明确拒绝会让玩家以为自己的昵称违规」明令避免的那种体验。
4. 启用的边际成本明确且非零：一家服务商过 H1–H4 · 一份**独立审计线**的凭据轮换 · **同步路径上 800 毫秒的玩家等待预算** · 一条要监控的曲线。`ADR-0039` 对 `Email` 的否决理由逐字适用：「接入即产生一份要轮换的凭据、一次模板报备与一条要监控的曲线，**全是负债**」。
5. **后置成本 ≈ 0，由 `ADR-0044` / `0038` / `0015` 三条共同担保**（见「约束」的反证段）：启用 = 一次选型 + 一次阈值标定 + 一次配置，不改任何契约报文、不新增任何 `code`、不要求客户端发版。

**但建议改写它的形态：从「悬而未决的默认」改为「有触发器的默认」。**

拟议措辞：

> 首版**不启用**。**触发启用的唯一条件：渠道过审点名要求接入第三方内容审核能力。** 触发时以真实人工判定样本标定 `rejectThreshold` / `reviewThreshold`（服务商 × 环境维度），并登记进 `operations/moderation.md` 的数值初值表。

理由：`moderation.md` 与 `external-providers.md` 现在写的是「取决于上线分级」。分级一旦定案而**不补触发条件**，这个留位就会变成**没有任何人会再想起来的空位**——本项目已有同型先例（跨边界意图拆成两半后，第二半经常不会发生，见 `.claude/rules/design-library-routing.md` 的改写说明）。

## 具体形态（可 derive 的落地面）

### 形态 1 —— `operations/deployment.md`：建议拆成**两份**上线前置清单

`[既有推演]`

现有那份清单的成立前提被文档自己写死为「下列四项**共用同一个不可逆时刻**」，而 `operations/compliance-ops.md` 已依同一判据把年度日历录入排除在外。按该判据落位：

- **实名 + 防沉迷 → 绑「首个真实账号建号」**（存量拦截潮 / 知情不限的敞口，自第一个真实账号起即成立）；
- **注销 + 导出 → 不绑那个时刻**（后加不产生存量追溯动作），绑的是「**首次面向公众发行**」这个渠道闸。

#### ① 现有清单「首个真实账号建号之前」建议追加两项

过闸断言的体例照第 4 项——**必须是可验证的运行时事实，不是「已完成开发」**：

| # | 项 | 建议的过闸断言 |
|---|---|---|
| 5 | **实名核验能力在线** | 在 `backend-testing` 环境完成一次真实核验，`realnameStatus` 落 `Verified`，`isMinor` 由核验回传的出生日期算得；且 `realName` / `idNumber` 在应答、日志与 `response_snapshot` 中**零出现**（对位 `systems/account.md` C6） |
| 6 | **防沉迷时段判定在线** | 时段规则集与**当年**日历已发布至 `version ≥ 1` 且含 `WorkingWeekend` 条目；启动自检解析时区名通过；对一个已判未成年的测试账号，在非允许时段 `signin` 得 `compliance.playtime_blocked` + `detail.resumeAtUtc` |

#### ② 建议新增第二份清单：「首次面向公众发行之前」

与域名备案 / 国内发行资质同批推进（`operations/environments.md` 已定二者是上线时序的前置）：

- **注销两端点**（`POST /v1/compliance/deletion` · `POST .../deletion/cancel`）可用，且 **App 内有可达入口**（客户端侧对位——**回链客户端库，本库不复述**）；
- **导出两端点**（`POST /v1/compliance/export` · `GET .../export/{taskId}`）可用，且产物白名单三条断言（`operations/compliance-ops.md`）在流水线上绿灯；
- 域名备案与国内发行资质到位（已在 `operations/environments.md`，此处只回链）。

#### ③ 未就绪的处置：建议沿用既有那一条——推迟上线，不降级放行

`ADR-0042` / `deployment.md` 第 4 项已为微信资质定死该处置。判据：**合规项没有「先上线后补」的形态**——拦截只在 `signin`、四码求值顺序写死、无灰度旋钮。

### 形态 2 —— `vision/scope.md`：In scope **内容不改**，只改「时点」的措辞

### 形态 4 —— derive 排除面如何收缩（本条的主要产出）

## 备选方案（已考虑并否决）

- **实名 / 防沉迷首版不上，上线后补** — 需同时推翻或加条件于四处：`ADR-0031`（未成年时段判定的 fail-closed 例外）· `ADR-0039`（首版供应商盘子已含实名核验 1 家）· `deployment.md` 的时区启动断言（无条件、拒绝启动）· `environments.md` 的选主区推导。且补上之日是一次对全体存量账号的全量拦截潮，**无灰度旋钮**。这不是分级，是重构。
- **只上实名、不上防沉迷** — 服务端已知 `isMinor` 却不加限制，敞口**大于**两项都不上；且同时悬空 §7 的会话中途映射与 `ADR-0031` 的例外。
- **注销 / 导出走站外（官网 / 客服）** — `contracts/compliance.md` 的备选清单**已否决**（商店审核查 App 内可注销，且站外流程需另一套身份核验，成本高于一个端点）。此处只作重申，不重开。
- **首版即启用第三方昵称审核** — 无人工判定样本 ⇒ 阈值无从标定；未标定阈值的误拒会以 `SensitiveWord` 误告玩家违规（`systems/account.md` N9 明令避免）；而后置成本 ≈ 0。
- **在现有那份前置清单里直接追加注销 / 导出，不新开第二份** — 会破坏该清单写死的成立前提（「四项共用同一个不可逆时刻」），而 `compliance-ops.md` 已用同一判据把年度日历排除在外。**更低成本的替代做法**是同一份清单内分两节——成本确实更低，但会稀释那句承重前提，且读者仍要判断哪一节管哪个时刻。**倾向新增第二份**，因为两份的过闸时刻确实不同。
- **把「哪几项后置」当成一个排期旋钮来调** — 本库结构上不提供这个旋钮：拦截只在 `signin`、四码求值顺序写死、无灰度。唯一真正可调的是第三方昵称审核，而它本就默认不启用。
- **为「首版不上某项」新增一个能力开关旋钮** — 会造出一条「合规能力可被配置关闭」的路径，而该路径在任何时候被误置都是合规事故；且四条拦截码的求值顺序是写死的，关掉其中一级会让求值顺序出现一个未定义的空档。

## 与既有决策的张力

### 1. 与问题措辞本身的张力（**请评审者先看这一条**）

`open-questions/02-account-compliance.md` 与 `open-questions.md`「当前焦点」都把本条写成「哪些必须在首次上线前具备、**哪些可后置**」——**措辞预设了会分出后置项**。而本方案的推演结论是**不分**（四项同档）。

这不是回避问题，是把问题答成了否定式。**因此必须明说：若本条的真实意图是「找出一项可以砍掉以赶排期」，本方案给不出那一项。** 结构上真正可砍的只有第三方昵称审核第④级，而它本就已经默认不启用——也就是说，**排期上能省下的量，等于零**。

若这与评审者的排期预期冲突，请在评审时直接否决本方案的核心结论，而不是接受它然后在实施时悄悄砍项——后者会撞上「拦截只在 `signin`、无灰度旋钮」这条结构性限制。

### 取向 1 —— 首版的发行市场与渠道形态（外部事实）

本方案的整个分级框架建立在「首版 = 面向中国大陆、经国内应用商店 / 微信渠道正式发行的网络游戏」这一前提上。该前提在本库**只是间接可推**（`environments.md` 的主区与「个人信息不出境」· `contracts/purchase.md` 三渠道含**微信支付** · 客户端 `vision/scope.md` 的登录渠道优先级「移动端优先 → 微信 / QQ 其次 → **海外与跨平台最后**」），**两库都未显式陈述首版发行范围**。

| 选项 | 内容 | 后果 |
|---|---|---|
| **A** | 中国大陆正式发行（iOS / Android 国内渠道 + 微信） | 本方案原样成立 |
| B | 中国大陆小规模测试 / 内测，不公开上架 | 注销的**渠道过闸**理由消失（PIPL 理由仍在），实名 / 防沉迷的理由不消失 ⇒ 注销可推迟至首次公开上架前；且客户端须在首版隐藏 PlayerProfile 屏的注销入口（一条跨库承接项） |
| C | 首版含海外 | 出现第二套监管口径与第二套部署（`compliance-ops.md` 明写「海外扩展是另一套独立部署 + 独立 `accountId` 空间」）⇒ 本条只覆盖国内那一套，海外须另开问题 |

**推荐 A**：它是最保守的一档——按 A 定级而实际走 B，只是多做了一项（注销），**不产生返工**；反向则会在过审时缺项。

**→ 已裁决（2026-09-07 · 批量评审）：选项 A —— 首版 = 中国大陆正式发行（iOS / Android 国内渠道 + 微信）。** 四项全首版必备的分级原样成立；不触发选项 B 的客户端承接项，不触发选项 C 的海外第二套部署问题。本草稿其余部分已按此前提写就。
