# 方案草稿 — `Priority = 1` 的抬升条件与同档共现规则

## 问题

`eventPriority` 是**唯一**约束玩家选择权的字段，取值域两档（`0` / `1`），置位方唯一（future-event-service 在物化时置位，PlotManager 不得改），字段形态已答定（保留 `int` + 物化后断言 `Priority ∈ {0, 1}`、不设加载期校验）。**已知两个抬升条件**：配额用尽后的 Travel 闸门、起始批次里的开局构筑事件（Research）。

仍待定两件事：

1. 本服务**还依什么条件**把某个选项抬到 `1`；
2. **同批出现多个 `1` 档时**是否需要额外收窄规则（当前语义：同档内自由择一）。

## 约束（来自既有设计）

- **取值域两档 ⇒ 不存在「优先级 2 压过 1」的层叠语义**；Travel 闸门用的「最高优先级」就是 `1`，与其它强制事件**共用同一档**。→ `systems/adventure-event/common-properties.md`
- **有效可选集 = 本批中最高优先级档的全部事件，同档内自由择一**；`EffectivePriority` 由本服务算好放进 batch，呈现层不自算。→ `systems/services/future-event-service.md`
- **置位方唯一 = future-event-service；PlotManager 只调内容不调约束**——它不能通过抬优先级强制玩家做某件事，剧本的强制性只能靠**收窄候选池**表达。这是承重边界。→ 同上
- **本批的每一项都是必做项**（跳过通道整体移除）；`EventOptionBatch` 不设「至少一个必做项」的不变式；1 项的批次合法。→ `systems/adventure-event/common-properties.md`
- **Travel 段的物化伪码已定**（`ComputeEventOptions` 内，闸门分支**整批替换**）：

  ```
  若 LocationEventCount >= 当前 location.EventCountLimit：
      该批 = 这些邻接各物化一个 Travel EventOption，Priority = 1
  否则：
      Travel 与其余四类一同按 location 的类型修正加权抽取，Priority = 0
  ```
  → `systems/services/future-event-service.md`
- **开局构筑事件**：Research 的一个条目，两槽 `AllowDecline = false`，`lifeSpanCost` 取 0 覆盖，`eventPriority = 1`；**它可以缺席**（池前置拦下时首批退化为常规批，轮回照常开始）。→ `systems/adventure-event/research/_index.md`
- **Finale 的出现条件是一条等级条件**（角色已达本境界巅峰，全局 13 / 17 / 21），与 location 无关，不绑定「渡劫场」地域；每篇章只有一个 Finale，失败后不可在同一篇章内再战。→ `systems/game-progression.md`、`systems/adventure-event/combat/_index.md`
- **满级后经验直接丢弃**（不结转、不开兑换通道）；卡级的后果 = 寿元耗尽而等级未满 → `defeated`。→ `systems/balance.md`
- **产出侧不做过度保护**：不欠「至少一个可负担 / 可战胜选项」的保证；「输」是这个游戏的一个正常出口。→ `systems/services/future-event-service.md`
- **重算依据 = 角色整体历程，不承接上一批**；批与批之间唯一的信息通道是 CharacterProfile 本身（本服务无记忆）。→ 同上

## 建议方案

### ① 写一条判据取代一张清单（承重）

`[既有推演]`

本库对这类问题的一贯收口方式是**给判据不给枚举**（物化判据、快照判据、`Source` 的组装者判据、终态判据皆是）。建议：

> **抬升当且仅当：不抬升会使一条结构性规则失效。**

三条子判据，逐条可机械核对，**与门**：

| # | 子判据 | 它挡住什么 |
|---|---|---|
| **(a)** | 该选项是某条**结构性规则的唯一出口**——不选它，那条规则就无法兑现 | 挡住「这个事件很重要 / 很稀有 / 很贵」这类**风味性**抬升 |
| **(b)** | 收窄由**产出侧可确定判定的条件**给出（配额计数 · 批序 · 角色等级），**不读隐藏属性、不读剧本状态** | 挡住 PlotManager 借道本服务抬升——它要读的正是剧本状态 |
| **(c)** | 抬升表达的是**结构**，不是**难度**或**叙事** | 挡住「本批全是打不过的战斗，抬一个安全选项」这类过度保护 |

**(b) 是这条判据最值钱的一半**：它把「PlotManager 只调内容不调约束」从一句纪律变成一条可机械核对的准入条件。剧情线关键节点之所以不能抬升，不是因为「我们不想」，而是因为它的触发条件必然读剧本状态、直接被 (b) 拒。

### ② 依判据得出的清单（当前闭合为 2 + 1 待裁）

`[既有推演]`

| 条件 | 判定式 | (a) | (b) | (c) | 结论 |
|---|---|---|---|---|---|
| **配额闸门 Travel** | `LocationEventCount >= location.EventCountLimit` | ✅ 离开当前 location 的唯一出口 | ✅ 读计数器 | ✅ | **保留（已定）** |
| **开局构筑事件** | 首批 且 新角色 | ✅ 开局底盘的唯一来源 | ✅ 读批序 + 角色来源 | ✅ | **保留（已定，建议收窄措辞见下）** |
| **Finale** | `level == 该境界末级`（13 / 17 / 21） | ✅ 篇章边界的唯一出口（且不可重战） | ✅ 读等级 | ✅ | **建议抬升 —— 取向题，见「仍需用户决定」第 1 项** |

**开局构筑事件的判定式建议收窄为**：

```
Priority = 1  ⟺  这是本轮回的第一批（StartCycle 写的那一批）
                 且 CycleStartSpec.SourceCharacterId == ""   // 炼气新角色
```

依据：**篇章继承 = 全部继承** ⇒ ch2 / ch3 读档续章时角色已有完整卡组与法宝，「开局底盘」这条结构性规则在续章上**不存在**，(a) 不成立。不收窄的话，续章首批会被一个不必要的强制构筑事件占满一整批。**篇章重试同理**（`RetryChapter` 从该篇章起始存档带回全部信息）。

### ③ 明确否决的候选（写下来，防止日后被逐个加回）

`[既有推演]`

| 候选 | 被哪条子判据拒 | 说明 |
|---|---|---|
| **剧情线关键节点** | **(b)** | 触发条件必然读剧本 / 隐藏属性状态。剧本的强制性**只能靠收窄候选池**表达——这是承重边界，不是本条可以松动的 |
| **寿元 Band 2 时强制某类事件**（如强制一个回寿事件） | **(b)** + 承重取向 | Band 是**呈现门控**，推进规则层从不读它；且「明知是死路仍然走」是明写的承重取向，抬升等于用规则把它取消 |
| **稀有 / 高价值 / 高 `RarityTier` 事件** | **(c)** | 纯风味。稀有度已有它自己的表达位（抽取权重） |
| **「本批全是打不过的战斗」时抬一个安全选项** | **(c)** + 承重定案 | 产出侧明写不做过度保护、不欠可战胜保证；难度的界由 `±2` 赋级带给出已经足够 |
| **篇章重试后的首批** | **(a)** | 篇章继承使底盘完整，无结构性规则需要兑现 |
| **付费礼包 / 账号级持有状态触发的抬升** | **(b)** + 分层 | 账号级持有改写轮回级的选择约束，与「一条法则不得改写轮回级定稿实例」同源同重 |

### ④ 同批多个 `1` 档：不新增任何收窄规则

`[既有推演]`

**先给一个此前没被指出的事实：在当前伪码下，「同批多个 `1` 档」是一条结构上不可达的分支。**

- **闸门分支整批替换**：`LocationEventCount >= EventCountLimit` 时「该批 = 这些邻接各物化一个 Travel」——**这一批里没有别的类型**，任何第二类抬升项都进不来。
- **开局构筑事件只出现在首批**，而首批 `LocationEventCount == 0` ⇒ 必走非闸门分支 ⇒ 与 Travel 闸门**互斥**。
- **Finale（若采纳抬升）只出现在非闸门批**，与 Travel 闸门同样互斥；而它与开局构筑事件在时间上互斥（首批时角色 level = 1）。

**⇒ 结论：不需要额外收窄规则**，三条独立依据：

1. **不可达**（上述结构分析）——为一条不可达的分支写规则是纯负债；
2. **两档语义已明写「同档内自由择一」**，它零成本、且在日后新增抬升条件时自动生效，**保留它作为兜底**而不是删掉；
3. **任何「1 档内再排序」的规则事实上等于引入第三档**，而「两档 ⇒ 不存在层叠语义」是明写定案；同时它会立刻长出「谁有权用这个排序」这个口子——本库对这类口子的收口方式是不给。

**连带明写一条代价（Finale 若抬升时成立）**：角色满级的那一刻若恰逢配额用尽，本批只有 Travel（闸门分支整批替换）⇒ **玩家须先 Travel 一次再渡劫**，渡劫延后一步、多花一格 Travel 的低价寿元。这不是缺陷：Travel 定价本就是全类型最低一档，且「篇章边界不绑定 location」的既有定案保证换图不会把 Finale 弄丢（下一批等级条件仍成立，照常抬升）。

### ⑤ 落地面：零结构增量

`[既有推演]`

- **不新增字段、不新增枚举、不 bump 存档 schema。** 三条抬升条件全部读既有状态（`Status.LocationEventCount` · 批序 · `CycleStartSpec.SourceCharacterId` · `realm` + `level`）。
- **物化后断言不变**（`Priority ∈ {0, 1}`，`PushError` + `EventId`）；**加载期仍不设校验**（`Priority` 从不是模板字段）。
- **建议补一行物化日志**（既有 `[FutureEvent-Materialize]` 已带 `prio=<n>`，此处只加抬升原因，便于回溯「这一步为什么被封锁」）：

  ```
  [FutureEvent-Priority] batch=<BatchId> elevated=<InstanceId> reason=<QuotaGate|InitialBuild|Finale>
  ```

  `PastEventEntry.Priority` 已落存档，配合本行日志即可回答「这一步是不是被闸门收窄的」——**不需要把 reason 也存进快照**（它可由 `Priority` + 当时的 `LocationId` / `Seq` / 等级重算得出，按快照判据不存）。

## 具体形态（可 derive 的落地面）

```
ComputeEventOptions 内的置位段（伪码，落在既有物化流程中，不新增方法）：

  若 LocationEventCount >= location.EventCountLimit：
      闸门分支（既有）：整批 Travel，Priority = 1，reason = QuotaGate
      返回

  常规分支：全部选项 Priority = 0
  若 本批是 StartCycle 写的第一批 且 SourceCharacterId == ""：
      开局构筑事件（若已进批）Priority = 1，reason = InitialBuild
  若 level == 该境界末级（13 / 17 / 21） 且 本篇章尚未结算过 Finale：
      Finale 选项 Priority = 1，reason = Finale        ← 取向题，见「仍需用户决定」

  EffectivePriority = Max(o.Priority)                  ← 既有
  物化后断言 Priority ∈ { 0, 1 }                        ← 既有
```

**「本篇章尚未结算过 Finale」的读取源**：`pastEvent` 中是否存在一条 `EventId` 指向本篇章 Finale 条目的痕迹——`pastEvent` 已是本服务的一等输入，**不新增字段**。（Finale 失败后不可在同一篇章内再战，故该判定同时兑现「败后不再抬升」。）

## 备选方案（已考虑并否决）

- **列一张穷举的抬升条件表，不给判据** —— 否决：清单会随内容增长而不断被追加，而每次追加都要重开「这一条该不该进」的辩论；判据一次性把辩论收敛为三次机械核对。
- **给 `EventOption` 加一个 `PriorityReason` 字段并落存档** —— 否决：它可由既有状态重算得出，按快照判据不存；且新增落存档字段要 bump schema，换来的只是日志已能给出的东西。
- **开第三档 `Priority = 2` 给 Finale** —— 否决：「两档 ⇒ 不存在层叠语义」是明写定案，加第三档要连改 `EventOption.Priority` / `PastEventEntry.Priority`（落存档）/ `EffectivePriority` 三处，而两档已完全够用（Finale 与 Travel 闸门结构上互斥）。
- **为同批多个 `1` 档写一条「Travel 闸门优先于其余 `1` 档」的收窄规则** —— 否决：该共现分支在当前伪码下不可达（闸门分支整批替换），且这条规则本身就是第三档的变体。
- **让 Finale「保证必现但 `Priority = 0`」** —— 否决：那需要产出侧新增一条「某条目必进本批」的机制，而 `eventPriority` 正是本库用来表达这件事的唯一字段；新增等于造第二条约束轴，直接违反「选择约束只有一条轴」。

## 与既有决策的张力

**一处，且只在 Finale 采纳抬升时成立。** `systems/game-progression.md` 明写：「Finale 不绑定特定 location，否则『必须先走到某地才能渡劫』会与『Finale 之前必须升满』形成**两条互相牵制的进度闸**，任一条卡住即卡死轮回」——它体现的是对**多重进度闸**的明确警惕。抬升 Finale 会在等级闸之上再加一层「满级即封锁其余选项」的约束闸。

**为什么本方案仍推荐抬升**：这两者不同类——location 闸是**另一条独立的进度轴**（可能与等级轴互相卡死），而抬升是**同一条等级轴上的收口**，不引入第二个可卡死的变量。抬升之后仍只有一个闸（等级），且它必然会被跨过（经验供给 / 需求比 1.15–1.20 已按「按标准路线走能在预算内升满」反推）。**但这条张力必须由用户裁决**，因为它触及的是同一份文档明写的警惕。

## 前置依赖

- **批次规模区间两端由什么驱动**（🔴，同分片相邻问题）—— **不阻塞本条**：抬升发生在选项已被物化之后，与「这批有几项」正交。唯一的接触点是闸门批的规模 = 邻接数（已由出度 ≤ 5 封住）。
- **类型修正的运算形态**（🔴）—— **不阻塞本条**：它决定 Finale / Research 条目**以什么权重进池**，而抬升只在「它已经在批里」之后生效。
  - ⚠ **但有一条弱依赖须写明**：若 Finale 采纳抬升，则「满级后 Finale 必须能进批」成为一条**产出侧的隐含要求**——加权抽取若把它抽漏，抬升就没有对象。建议在生成 / 加权那一条落定时，把「满级后 Finale 条目恒进候选池（不参与类型加权）」作为一条并列输入带过去。这不是本条能单独定的。
- **`experiencePoint` 阈值曲线** —— 已给出初值（`threshold(L) = 4 + floor((L−1)/2)`，L=12 特例 10），不阻塞。

   - **选项 A（推荐）**：**抬升**。角色达境界巅峰后，本批有效可选集收窄为 Finale（配额闸门同时触发时先 Travel 一次）。
     - 后果（正）：篇章边界成为**确定的**必经节点，与 Travel 闸门同形；不必为「Finale 必现」另造机制；满级后经验作废、寿元照流的浪费段被消掉。
     - 后果（负）：**取消了「先补一补 `lifeTotal` 再渡劫」的备战窗口**，而 Finale 已有三重压迫叠加（开局落后 5/13/25 · `WinMargin` 门槛 · 失败时扣 `lifeTotal` 最狠），这是第四重。
     - **退让位（属实测调整，不是重新裁决）**：若实测过苛，退让顺序为 ① 下调 `WinMargin`（既定的「双向第一旋钮」）② 内容侧编排「满级前一批必有一个带 `Recuperate` 的 Research」——**而不是**回退抬升。
   - **选项 B**：**不抬升**，Finale 与其余选项并列（`Priority = 0`）。
     - 后果（正）：保留备战窗口，压迫感不再叠第四重。
     - 后果（负 · 承重）：**Finale 落入加权抽取，「想渡劫却抽不到天劫」成为可能**——篇章边界被交给随机；且若靠加权保证必现，它就会每批占掉 1 / 3 个槽位直到章末，把有效选择从 3 缩到 2。
   - **理由**：B 的负面后果直接踩在「篇章边界闸门 + ADR-0004 锚点 + 残卷唯一兑现点，这三处都需要一个**可机械判定**的判据」这条既有论证上——把它交给加权抽取正是该论证要避免的形态。A 的代价是手感层面的，且有两级现成退让位。

2. **开局构筑事件的抬升是否收窄为「新角色首批」（排除 ch2 / ch3 续章与篇章重试）？**
   - **选项 A（推荐）**：**收窄**。判定式 = 首批 且 `SourceCharacterId == ""`。后果：续章 / 重试的首批是一个普通批次；`research/_index.md` 里「起始批次中必有一个强制事件」一句需改为「**炼气新角色**的起始批次」。
   - **选项 B**：**不收窄**，每个篇章的首批都强制一个构筑事件。后果：每章开头给玩家一次确定的构筑机会（节奏上是个正向锚点）；代价是它与「篇章继承 = 全部继承」的语义相冲——底盘已经完整，这个事件表达的不再是「开局底盘」而是「每章送一次构筑」，那是**内容编排口径**，用一个高权重的普通 Research 条目即可，不需要占用约束轴。
   - **理由**：(a) 子判据在续章上不成立（没有「唯一出口」可言）；且 B 想要的效果有一条不动约束面的现成实现路径。

3. **「不抬升会使一条结构性规则失效」这条判据要不要连同三条子判据一起写进主题文档、作为日后新增抬升条件的准入闸？**
   - **选项 A（推荐）**：写进 `future-event-service.md`，与物化判据 / 快照判据并列成为第三条判据。后果：日后每一个「能不能抬这个」的提议都要过三次机械核对，辩论收敛。
   - **选项 B**：只写清单（当前三条），不写判据。后果：文档更短；但每次新增都要重开辩论，且 (b) 那条对 PlotManager 的机械拒绝会失去载体。
   - **理由**：本库已有四条同形判据（物化 / 快照 / 组装者 / 终态），它们的共同收益都是「新增一项时走判据即可，不必每次重开『清单闭合了吗』」——本条形状完全相同。**列为取向而非直接采纳**，是因为它会给本服务再加一条必须被后来者遵守的纪律，密度是有成本的。
