# 方案草稿 — 死亡 / 轮回结束屏

## 问题

`DefeatReason` 是三值封闭枚举 `{ Discarded, LifeSpanExhausted, FinaleFailed }`（`systems/architecture.md`），三条路径的观感与叙事分量差别很大：主动弃置是玩家自己按下的，寿元耗尽是一条慢慢走完的预算线，渡劫失败是全作叙事上最重的一刻。

全库对角色终结的呈现**只有一句「寿元归 0 即角色终结」**：状态机、清理、统计计数、重试计数全都齐备，唯独**没有任何一屏**。`ux/screen-flow.md` 甚至已经在引用一个尚不存在的东西——「**终态死亡屏**对 `DefeatReason` 的呈现照常保留」。「渡劫身死」的**文案载体已定**（内容层定性文案条目），**呈现它的那一屏未定**。

三问：**是否分别呈现** · **呈现在哪一屏** · **承载什么信息**（本轮回回顾 / 结算 / 到下一轮回的路径）。

## 约束（来自既有设计）

## 建议方案

### 1. 一屏三变体，不是三屏

`[既有推演]`

三因走完之后的**结构完全相同**：角色 `defeated` → 数据清理 → 重试计数已减 → 回主菜单。差别只在**这一次为什么结束**，那是一句话的差别，不是一条流程的差别。

- **先例明摆着**：需更新 / 被挤下线 / 存档读取失败三种终局态形态同构，已经收敛为**一个 `BlockingNoticeScreen` + 一张变体表**。本条是同一条判据的第二次应用。
- **三变体的差异恰是三格**：标题键 · 定性文案条目 · （无第三格——出路、信息行、按钮全同）。
- **明确否决为三因各做一屏**：三份布局要各自维护、各自适配竖屏与安全区，而它们会长得一模一样；差异一旦只靠版式表达，就必然漂移成三种不一致的观感。

屏名建议 **`CycleEndScreen`**（承载 `defeated` 三因）。**篇章通关 `completed` 与整轮回通关不走本屏**，见「前置依赖」。

### 2. 呈现位置 = 结算流程之后、返回主菜单之前的一屏全屏

`[既有推演]`

- **载体 = 一屏全屏**（安全区内），**不进屏幕栈、无返回路径**——与战斗前确认页同款载体形态。**不是弹层**：弹层意味着它浮在一个仍然有效的轮回界面之上，而这个轮回已经不存在了。
- **时点**：`DefeatCharacter(reason)` 提交完成（含既定的 `Immediate` flush 与 `TotalCyclesDefeated +1`）之后立即呈现；玩家点主按钮 → `TeardownCycle` → 回主菜单。**阶段 5 的既定顺序一个字不改**（见下方「数据源」）。
- **不新增存档点**：本屏是**已提交事务之后的一次纯呈现**，自身不产生任何写入。
- **无自动跳转、无倒计时**：等玩家自己点。一个会自己消失的死亡屏，等于玩家还没读完就被推回主菜单。
- **常驻同步指示照常可见**（`离线 · 待同步 N` / `需更新 · 待同步 N`）。这一刻恰好发生一次 `Immediate` flush，若失败它会进待发队列——隐藏指示就是把「失联」伪装成「已保存」。

### 3. 承载什么：定性文案 + 结果三行 + 剩余重试 + 一个主按钮

`[通行做法]` + `[既有推演]`

竖屏形态（单列、纵向自上而下）：

```
┌─────────────────────────────────────┐
│ [安全区]                    离线·待同步 2 │  ← 常驻同步指示（既有形态）
│                                     │
│              <标题>                  │  ← 三变体之一，走 CYCLE_ 分区翻译键
│                                     │
│      <定性文案 · 一段，居中弱化>       │  ← 内容层 LocalizedText，按 DefeatReason 取
│                                     │
├─────────────────────────────────────┤
│   止步于  炼气七层 · 第一篇章          │  ← 结果三行（标签走翻译键，值来自摘要）
│   修行    37 个事件                   │
│   寿元    0                          │
├─────────────────────────────────────┤
│   本篇章剩余重试：2 次                 │  ← 只读一行；ch1 显示「无限」
├─────────────────────────────────────┤
│                                     │
│          [  返回主菜单  ]             │  ← 唯一主按钮，底部拇指可达区、安全区内
└─────────────────────────────────────┘
```

- **结果三行取的都是既有数据**：境界与篇章（`CharacterProfile` 现成）、事件数（`pastEvent.Count`）、寿元余量（`Status.lifeSpan`，恒精确展示，`LifeSpanExhausted` 变体上恒为 `0`）。**不新增任何字段。**
- **剩余重试次数照实展示**：`CharacterDefeated` 负载里的 `RetriesLeft` 就是为被读而带的；玩家要决定下一步（再来一次 / 换个篇章 / 收手），这是他唯一需要的事实。ch1 上限为无限 → 单独一个键显示「无限」，**不显示一个假的大数**。
  - **它不是推销面**：既定纪律只禁止在此提示购买，不禁止告知剩余次数。**本屏无任何付费入口、无任何指向礼包的文字**（结构上也不可行——购买流程只能在主菜单发起且待发队列为空）。
- **残卷零呈现**：不给文案、不给暗示、不给进度条、不给百分比。**`FinaleFailed` 变体尤其吃紧**——它恰是残卷累积发生的那一刻，本屏一个字都不能提。

### 4. 定性文案挂 `DefeatReason`，由本屏呈现

`[既有推演]`（**带一条张力，见下**）

- **挂状态转换、不挂触发它的事件**——与跨档叙事「挂档位不挂事件」、「渡劫身死」文案「挂状态转换、与触发它的事件无关」逐字同构。
- **载体不变**：仍是内容层的定性文案条目（`res://content/` 基线 + overlay，照旧只改不增），仍是「一条文案、不做随机二选一、不按篇章 / 隐藏属性分化」。**改的只是定位键**：从「随 `ResolveOutcome` 传到结算面板」改为「按 `DefeatReason` 查表，由结束屏呈现」。
- **为什么必须改**：`ResolveOutcome` 覆盖不到三因中的两因——
  - **`Discarded`**：主动弃置根本不经事件收口，没有 `ResolveOutcome`；
  - **`LifeSpanExhausted`**：它可能在**终态判定 ①**（支付 `selectCost` 后短路）命中，那一路事件**未结算、没有 `eventEnd`、没有结算面板**（只留一条 `Outcome = Aborted` 的痕迹）。
  挂 `ResolveOutcome` 的方案在这两条路径上会静默无文案，三因的呈现分量当场不等——而这正是本待答项要解决的问题。
- **`Discarded` 变体建议不配定性文案**（内容条目留空 = 该变体只有标题 + 结果行）。主动弃置是玩家自己的决定，不需要叙事替他解释；给它写一句挽留式或惋惜式的文案，反而像在评价玩家的选择。**这一条属内容编排取向，可由内容侧随时补上，不改结构。**

### 5. 出路只有一个：返回主菜单

`[既有推演]`

**明确否决在本屏放「再试一次 / 再来一局」按钮**，两条独立理由：

1. **它会绕过主菜单的既有闸门。** 主菜单是既定的唯一开局入口，「开始新轮回」上挂着三道闸：待兑现购买时置灰 + 说明、每篇章至多一个 `ongoing`、篇章解锁 / 重新锁定门禁。第二个开局入口要么把三道闸各复制一份（两份闸必然漂移），要么绕过它们（待兑现购买时开出新轮回 = 已定纪律当场失效）。
2. **两个篇章的重试路径形态不同**：ch1 重试 = 重走角色选择屏、新建 `CharacterProfile`；ch2 / ch3 = `RetryChapter(characterId)`。一个按钮要在最低情绪点上分叉出两条流程。

**返回主菜单后玩家看到的正是他需要的**：可挑战篇章、剩余角色、开始新轮回——全是既有面。

### 6. 数据源 = 提交时刻组装的一份只读摘要

`[既有推演]`

**承重的实现约束**：`defeated` 会清理该角色数据，而本屏要显示的正是那个角色的东西。

- **`DefeatCharacter` 内、清理之前，组装一份只读值摘要**（只含值类型 + 内容 `Id` + 文案条目 `Id`，**不持有 `CharacterProfile` 引用**——与事件负载「绝不带 `CharacterProfile` 引用」同一条纪律），交给呈现层持有。
- 收益：**清理与 `TeardownCycle` 的时点不被结束屏牵制**，阶段 5 的既定顺序一个字不改；呈现层拿着一份不会被清理动作抽掉的快照。
- 它是**呈现层的瞬时值对象，不落存档、不进 `PlayerProfile`**——本屏不需要任何持久化（回看历史轮回不在本方案内，见「前置依赖」）。
- ViewModel 的结构契约（依赖方向、生命周期、只读性、重组装时机）归 `systems/viewmodel.md`，本草稿不越界规定。

### 7. 文案分区

`[既有推演]`

分区表是开放表、随屏幕落地增补。新增一行：

| 分区前缀 | 文件 | 覆盖 |
|---|---|---|
| `CYCLE_` | `cycle.csv` | 轮回结束屏：三个标题、结果行标签、剩余重试行（含「无限」）、主按钮 |

- **不复用 `EVENT_`**（那是事件选项框架）、**不复用 `MENU_`**（本屏不属主菜单）、**不占 `ERR_`**（它没有后端 `code`，是一次正常的游戏结果）。
- **定性文案不进 `cycle.csv`**——四问皆是，它是内容层（`ux/_index.md`）。

## 备选方案（已考虑并否决）

- **三因各一屏。** 否决：三份等价布局必然漂移；差异只有一句话。
- **复用 `BlockingNoticeScreen`。** 否决：那三个变体的共同点是「**主按钮永不是『继续游玩』**」——它们是阻塞态，玩家没做错什么也没走完什么。轮回结束是一次**正常的游戏结果**，共用会让「角色死了」和「存档读不出来」在观感上同级。**借它的形态（一屏 + 变体表），不借它的屏。**
- **在结束屏内直接给「再试一次」。** 否决：绕过主菜单的三道既有闸门；且 ch1 与 ch2/3 重试路径形态不同（见第 5 节）。
- **把「渡劫身死」文案留在结算面板、其余两因由结束屏承担。** 否决：三因的呈现分量当场不等，而本待答项问的正是这个；且同一类文案会有两个呈现面。
- **本屏承载成就 / 图鉴 / 统计的本轮回收获。** 见「仍需用户决定」第 2 条（真取向，未替用户拍板）。
- **本屏提供「本轮回历程回看」入口。** 否决为默认形态：角色数据在 `defeated` 时被清理，做回看要么改清理时点、要么另建一份持久化摘要——两者都在为一个中期路线图之外的展示需求付结构成本。见「仍需用户决定」第 1 条。

## 与既有决策的张力

> → **已裁决（2026-09-02 · 批量评审）：松动，死亡文案改按 `DefeatReason` 定位。** 理由如本节所述——`ResolveOutcome` 覆盖不到 `Discarded`（不经事件收口）与走终态判定 ① 的 `LifeSpanExhausted`（无 `eventEnd`），三因里只有一因有叙事，而那正是本待答项要解决的问题。**跨档叙事的 `ResolveOutcome.BandNarrativeIds` 通道原样保留**，只有死亡文案换定位键——提炼时须写清这一点，否则易被读成整条叙事通道被拆。

**一条：「渡劫身死」文案的落点由 `ResolveOutcome` 改为按 `DefeatReason` 定位。**

- **冲突的是哪一条**：`plot-manager.md` 明写该文案「落点是本处而非 `ux/screen-flow.md`……走同一条落点（`ResolveOutcome` → `eventEnd` 阶段），**不新增结构**」。
- **为什么方案需要它松动**：`ResolveOutcome` 这条通道覆盖不到 `Discarded`（不经事件收口）与走终态判定 ① 的 `LifeSpanExhausted`（事件未结算，只留 `Aborted` 痕迹）。挂在它上面，三因里只有一因有文案。
