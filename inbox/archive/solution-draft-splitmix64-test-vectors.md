# 方案草稿 — SplitMix64 账号级随机源的测试向量

## 问题

`contracts/profile-sync.md` §6 已把账号级掷骰的随机源定为**契约定义的纯函数 SplitMix64**，算法、常量、三参数混入顺序、`stream` 取值冻结、`mod 10000` 的取模方式全部封定；§6 同时要求本契约**必须附一张 8 组的测试向量表**（含 `accountSeed = 0` 与全 `F` 两个边界），并已定数值权威落在 `contracts/vectors/splitmix64.json`。

悬着的只有**数值本身**与**那份 JSON 的字段形态**。它不是设计未决，是待落笔项——但按 §6 自己的措辞，它是「跨语言逐位一致」这条纪律**唯一可执行的检查点**：不填即等于没有这条纪律，而这条纪律失效的后果是**静默的作弊窗口**（两侧算出不同的 `roll`，复算校验①在部分账号上稳定失败或稳定放行，两侧都不报错）。

现行措辞把填值时机推到「任一侧首次实现 SplitMix64 时」。本草稿主张**提前填**：算法既已冻结，向量就是算法的函数，可由一份独立参考实现算出，无须等待任一侧动手——先填反而把它变成两侧实现的**验收前置**。

## 约束（来自既有设计）

- **算法与常量已冻结**（`profile-sync.md` §6）：标准 SplitMix64 finalizer 两常量 `0xBF58476D1CE4E5B9` / `0x94D049BB133111EB`，`GOLDEN = 0x9E3779B97F4A7C15`；初态为 `state = accountSeed` 后逐级 `Mix(state + GOLDEN * (stream + 1))`、`Mix(state + GOLDEN * (ordinal + 1))`；`Next()` 为 `state += GOLDEN; return Mix(state)`；`roll = Next() mod 10000`，**不做拒绝采样**。向量必须严格按这个定义算，**方案不得顺手"改进"算法**。
- **`stream` 取值冻结**：`PowerFragment = 0` · `PremiumBundle = 1`，一经写入契约即不可复用、只能追加（§6）。向量只能用这两个取值。
- **表的形态已定**：8 组，字段为 `(accountSeed, stream, ordinal) → 前 3 个 Next() 输出 + roll`，含 `accountSeed = 0` 与全 `F` 两个边界（§6）。**本草稿不改这个形态。**
- **超 2⁵³ 的整数一律 hex 字符串**（`envelope.md` §2 判据 + `profile-sync.md` §2）：`accountSeed` 与三个 `Next()` 输出都是 `ulong`，在 JSON 里必须是 **16 位小写 hex 字符串**；`roll`（`[0,9999]`）、`stream`、`ordinal` 是小整数，走 JSON number。
- **数值权威单点在 `contracts/vectors/splitmix64.json`**，markdown 表格是人类可读对照，**两侧测试直接读该 JSON**（§6）。不得让两侧各抄一份进代码。
- **该文件不属 OpenAPI spec**（不是报文形态），故单开 `vectors/` 而非 `schemas/`（`_index.md` 目录形态）。
- 后端技术栈未定 ⇒ **不指定语言 / 框架 / 测试工具**，只给数值与文件形态。

## 建议方案

### 1. 8 组用例的选取：2 组边界 + 3 组判别对 + 3 组现实取值

`[既有推演]` §6 硬性要求 `accountSeed = 0` 与全 `F` 两个边界。其余 6 组的选取依据是**这张表要抓什么**——它抓的不是"随机性好不好"（那是 SplitMix64 自身的既有结论），而是**两侧实现的对齐**。最容易差一位的地方恰好是 §6 已经点名的三处：`+1` 防御、`stream` 与 `ordinal` 的**混入顺序**、以及溢出回绕。因此建议：

| 用途 | 组 |
|---|---|
| 全零边界（验 `+1` 防御：不塌缩为纯 `Mix(accountSeed)`） | `seed=0, stream=0, ordinal=0` |
| 全 `F` 边界（验 `uint64` 环上运算与逻辑右移，抓有符号右移 / 溢出异常） | `seed=ffffffffffffffff, stream=0, ordinal=0` |
| **顺序判别对**（把 `stream` 与 `ordinal` 的混入顺序写反即失败） | `seed=0, stream=0, ordinal=1` ↔ `seed=0, stream=1, ordinal=0` |
| **相邻 ordinal 对**（验 `finaleWinOrdinal` 逐次 `+1` 不产生相关序列，也抓"少混一级"） | `seed=9f2c…, ordinal=1` ↔ `ordinal=2` |
| 现实取值 + `stream = 1`（`PremiumBundle` 域也被覆盖一次） | `seed=0123456789abcdef, stream=1, ordinal=1000` |
| 大 `ordinal`（客户端 `finaleWinOrdinal` 是 `int`，取 `int.MaxValue`，抓 `(uint64)` 转换处的符号扩展） | `seed=ffffffffffffffff, stream=1, ordinal=2147483647` |

选 `9f2c1a77b30e45d1` 作现实种子是刻意的：它就是 `profile-sync.md` §2 里那个初始 profile 骨架的示例 `accountSeed`，**同一个值在两处出现**，读者一眼能把向量表与报文示例接上。

- `roll = next[0] mod 10000`（§6 的万分比掷骰只消费**第一个** `Next()`；后两个输出在表里的作用是钉住**流的连续性**，供「一次派生、连续抽多条」的场景）。
- 组 2 与组 3 的 `next[0]` 完全不同 ⇒ 把两级混入写反的实现会当场失败。
- 组 3 的 `roll = 30` 是个 `< 100` 的值：顺带覆盖了"客户端把 roll 当百分比"这类单位错误（若某侧误用 `mod 100`，组 3 会**碰巧对上**而组 1 不会——两组同表，不会同时通过）。

### 3. `contracts/vectors/splitmix64.json` 的字段形态

`[既有推演]` 字段名 lowerCamelCase（`envelope.md` §2）；64 位值一律 hex16 小写字符串（同上）；把算法常量也写进文件——它们是**向量的前提**，同文件放置使"照着 JSON 写实现、再拿 JSON 验实现"成为一次完整闭环。

```json
{
  "$comment": "契约定义的账号级随机源 SplitMix64 的测试向量。数值权威在本文件；contracts/profile-sync.md §6 的表格是人类可读对照。两侧测试直接读本文件，不得各抄一份进代码。",
  "algorithm": "AccountRandom/SplitMix64",
  "specSection": "contracts/profile-sync.md#6",
  "constants": {
    "golden": "9e3779b97f4a7c15",
    "mix1": "bf58476d1ce4e5b9",
    "mix2": "94d049bb133111eb",
    "rollModulus": 10000
  },
  "streams": { "PowerFragment": 0, "PremiumBundle": 1 },
  "vectors": [
    {
      "name": "zero-boundary",
      "accountSeed": "0000000000000000",
      "stream": 0,
      "ordinal": 0,
      "next": ["238275bc38fcbe91", "f89a2566b5822c54", "47200e1d9780fa44"],
      "roll": 2433
    }
  ]
}
```

- `vectors` 为**数组**（有序，与 markdown 表逐行对位），每项带 `name` —— 测试失败时报出的是名字而不是下标，定位快一级。八项的 `name` 建议：`zero-boundary` · `zero-ordinal-1` · `zero-stream-1` · `max-boundary` · `max-stream1-ordinal-intmax` · `sample-seed-ordinal-1` · `sample-seed-ordinal-2` · `mixed-seed-stream1-ordinal-1000`。
- **`streams` 映射写进文件**：`stream` 的整数取值是冻结项（§6），把它与向量放在一处，使"新增域只能追加"这条纪律在唯一被机器读取的地方有个落点。
- **不加 schema 校验文件**：它不是报文形态，`_index.md` 的 `schemas/` 拆分判据两条都不满足。

### 4. 填入的时机：**现在填**，而非等首次实现

`[取向选择 → 已裁决 2026-08-14：取 A（现在填）]`。同批把 §6 那句「向量值在任一侧首次实现时填入」改为「向量值由独立参考实现预先算出并落 `vectors/splitmix64.json`；两侧各自实现后**逐位对表**，对不上以本文件为准」。

依据：向量是已冻结算法的**函数**，不含任何设计自由度 ⇒ 等待没有换来更多信息；而先有表意味着两侧实现是**对着验收物写**的，而不是写完再互相校对——后者的失败形态是"两侧都实现完了才发现差一位，且不知道谁错"。

采纳后需要的改动，共两处：

1. **新建 `contracts/vectors/splitmix64.json`** —— 形态见上节，`vectors` 填满 8 项。

## 后果

- **对 spec 的三条机检断言无影响**：断言 ①②③ 校验的分别是 spec 合法性、错误码台账双向覆盖、端点集双向覆盖，向量文件三者都不沾。可考虑（**不在本草稿主张范围内**）日后追加第四条断言「markdown §6 表格 ⇔ `vectors/splitmix64.json` 逐值一致」——它与②同形（两处真值的双向覆盖），但需 `06` 落定自动化承载后才有意义；在此之前作为人工清单第 2 项（承重纪律段落）的一次具体检查。
- **对客户端跨库欠账第 6 点（`AccountRng` 换随机源）**：它自此有了可直接消费的验收物——客户端实现 `AccountRandom` 后跑一遍这 8 组即可，无须等后端动手。**建议在客户端那份 handoff 里回链本文件**。
- 无存档迁移、无契约版本变更、无运行时影响。

## 备选方案（已考虑并否决）

- **只给 `roll`、不给三个 `Next()` 输出** — 只验第一格。`roll` 是 `mod 10000` 后的值，把 64 位输出压成 4 位十进制，**约 2⁵⁰ 分之一的错误实现会碰巧对上**；且完全不覆盖"连续抽多条"时的流状态推进。
- **只给 1 组或 2 组（"边界够了"）** — 顺序判别对与相邻 `ordinal` 对正是最易差一位的两处，都不是边界值能覆盖的。
- **把向量写进两侧各自的测试代码，不建共享文件** — 已被 §6 明确否决（"抄错即静默失效"），本草稿不重开。
- **向量随机生成、每次实现时重算** — 那不是验收物，是同义反复：两侧各自重算只会各自自洽。
- **`accountSeed` / `Next()` 在 JSON 中走十进制数字或十进制字符串** — 数字形态超 2⁵³ 静默丢低位（`envelope.md` §2 已就此立判据）；十进制字符串不定长、与"种子是一段比特"的语义不符，且与 §2 已定的报文 hex 表示不一致，等于在同一个值上放两种写法。
- **把向量文件塞进 `contracts/schemas/`** — 它不是报文形态，`_index.md` 已就此定 `vectors/` 单开。
- **同时冻结一个 `Mix()` 单函数的向量表** — 与「跨语言逐位一致」这条纪律的检查点重复：`Next()` 的输出已经完全暴露 `Mix` 的正确性，多一张表多一处需要同步维护的真值。（作为**非规范性**的调试提示，可在 §6 顺带记一句"标准 SplitMix64 以 0 为初态的前三个输出为 `e220a8397b1dcdaf` / `6e789e6aa1b965f4` / `06c45d188009454f`，实现者可先用它自测 `Mix` 与 `GOLDEN`"——它是公开的既有事实，不构成本契约的第二份真值。）

## 与既有决策的张力

**一处，且是措辞层面而非语义层面；已由用户于 2026-08-14 裁决松动（取 A）。** `profile-sync.md` §6 与 `open-questions/01-contracts.md` 都写「向量值在**任一侧首次实现时**填入并同批两侧逐位复核」，而本草稿主张现在就填。

- 松动的是**时机**，不是**复核要求**：本草稿保留并强化"两侧逐位对表"，只是把表从"实现的副产物"改成"实现的前置验收物"。
- 松动的代价：本表由一份**第三方参考实现**算出，而非项目两侧中的任何一侧 ⇒ 若这份参考实现本身有误，两侧会被一起带偏。缓解见下节的复核方式（已用公开的标准 SplitMix64 向量钉住 `Mix` 与 `GOLDEN`）；**并建议保留一条纪律**：两侧任一方首次实现时若与表不符，**先复核实现、再复核表**，两者都复核完仍不符则以"重算并同批改 markdown + JSON"处理，不得单方面改表迁就实现。
- 不松动时的替代方案：本草稿的 8 组用例选取与 JSON 字段形态**照常采纳**（这两项与时机无关），数值列留空待首次实现时填。信息量的损失是"两侧对着验收物写"这一条。

## 产出与复核方式（供评审核验，非契约内容）

数值由一份独立的 C# 参考实现按 §6 定义逐字实现后算出（`ulong` 环上运算、逻辑右移）。**该实现已用公开的标准 SplitMix64 向量钉住**：以 `state = 0` 起、`state += GOLDEN; Mix(state)` 的前三个输出为 `e220a8397b1dcdaf` / `6e789e6aa1b965f4` / `06c45d188009454f`，与公开值逐位一致 ⇒ `Mix` 的两个常量、两次异或移位量、最后的 `>> 31` 以及 `GOLDEN` 均正确。本表之上的部分（三参数逐级混入 + `+1` 防御）是 §6 独有的，无外部参照，其正确性只靠"逐字实现 §6 伪代码"——**这是评审时最该盯的一处**：请对着 §6 的五行伪代码复核，而不是对着数值。

## 前置依赖

**无。** 本项不依赖 `02`、`06`、也不依赖客户端任一待答项——算法与 `stream` 取值已冻结，向量是它们的函数。反过来，客户端跨库欠账第 6 点（`AccountRng` 换随机源）**依赖本项**才能验收。

## 用户裁决（2026-08-14）

1. **填值时机 = A（现在填）。** 8 组数值随本次提炼一并落 `contracts/vectors/splitmix64.json` 与 `profile-sync.md` §6 表格，并同批把 §6 的时机措辞改为「向量值由独立参考实现预先算出并落 `vectors/splitmix64.json`；两侧各自实现后**逐位对表**，对不上以本文件为准」。配套纪律一并生效：**两侧实现与表不符时，先复核实现、再复核表；两者都复核完仍不符则重算并同批改 markdown + JSON，不得单方面改表迁就实现。**
