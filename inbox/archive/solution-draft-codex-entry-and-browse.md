# 方案草稿 — 图鉴的入口与浏览形态

## 问题

图鉴族共**七本**（Enemy / CharacterPower / PlayerPower / CharacterItem / PlayerItem / Location / Technique），存档面已 ready（`CodexEntry(string Id)` 单格 + `CodexKind` 七值 + `CodexElements` 写入通道 + 词条深度按本分野），**但呈现面整块 blocked**：

- `ux/screen-flow.md` 的**主菜单入口表只有五项**（PlayerProfile / PlayerPower / Achievement / Settings / Store），**没有图鉴**——而图鉴已被定为元进程的**第三条积累线**（与法则、成就并列），另两条各有一等入口。这一格空着，七本图鉴目前在游戏里**没有任何可达路径**。
- 七本各自的列表页与词条页的竖屏排布未定。
- **功能性抬高**：意图机制已由 `ADR-0059` 整条移除，敌人图鉴因此是**事前敌人知识的唯一通道**（`enemy-codex.md`「⚠ 敌人的行动不作任何事前预告」）。浏览形态不是装饰面——读不到就等于那条通道没有。

## 约束（来自既有设计）

| # | 约束 | 来源 |
|---|---|---|

## 建议方案

### ① 入口 = 主菜单一个「图鉴」一等入口，不逐本开七个

`[既有推演]`

**建议**在主菜单入口表新增一行 `Codex（图鉴）`，位置 = **PlayerProfile / PlayerPower / Achievement 之后、Settings 之前**，Store 仍恒在末位。主菜单变六项：

```
PlayerProfile（玩家档案）
PlayerPower（法则）
Achievement（成就）
Codex（图鉴）        ← 新增
Settings（设置）
Store（礼包）         ← 恒末位，纪律不动
```

三条依据：

- **约束 1 直接给出结论。** 一族的立论就是「七本差别只在收录对象」；在**最显眼的那一层**把它拆成七个平行入口，等于在 UI 上否掉自己的抽象——而收益为零（七个入口不比一个入口更快到达任何一本，只是把选择从二级页搬到一级页）。
- **主菜单是账号级视图的落点（约束 7），图鉴是账号级的。** 三条元进程积累线里另两条（PlayerPower / Achievement）都持一等入口；只有图鉴降级为二级页，没有依据。
- **竖屏容量。** 六行按钮在主流竖屏比例下仍在单手可及区内；十二行（五项 + 七本）会把 Store 推到需要滚动才可见的位置，与约束 8「安静、可预期、永远在同一个位置」相抵。

**呈现纪律沿用 Store 那条：入口是纯标签，不带红点 / 角标 / 动效。** 完成度数字放在索引页内，不上主菜单（见「仍需用户决定 ①」）。

**入口无条件可见、无门禁。** 首玩时七本全空——空图鉴本身就是「有东西可收集」这句话的呈现，藏起来反而要新增一条解锁判据。

### ② 三层结构：索引页 → 单本页 → 词条

`[既有推演]` + `[通行做法]`

```
主菜单 ──▶ CodexIndexScreen（七格索引）──▶ CodexBookScreen（单本）──▶ 词条
                                                                  ├ 敌人本：CodexEntryScreen（全屏页）
                                                                  └ 其余各本：半屏 bottom sheet
```

**屏清单净增 3 屏 + 复用 1 个既有控件**（bottom sheet 不是新屏，是「随身」抽屉同款控件，约束 9）。

**为何不做「一屏七页签（TabBar）」**：七个页签在窄屏必然溢出成可滑动页签条，标签被截断，且页签栏本身要吃掉一条纵向空间——而每本的完成度是索引页最想给的信息，页签条放不下它。索引页多一次点击，换来七格各带完成度 + 稳定位置记忆。

### ③ CodexIndexScreen（索引页）= 七格纵向网格 + 每格一条完成度

`[通行做法]`

```
┌─────────────────────────────────────┐
│ [安全区]   ←        图鉴            │
├─────────────────────────────────────┤
│  ┌───────────┐   ┌───────────┐      │
│  │   敌人    │   │   神通    │      │  ← 窄屏 2 列 / 平板 3 列
│  │  12 / 48  │   │   3 / 20  │      │     GridContainer.columns 随宽度
│  └───────────┘   └───────────┘      │
│  ┌───────────┐   ┌───────────┐      │
│  │   法则    │   │   法宝    │      │
│  │   5 / 16  │   │  22 / 60  │      │
│  └───────────┘   └───────────┘      │
│  ┌───────────┐   ┌───────────┐      │
│  │   古宝    │   │   地域    │      │
│  │   4 / 18  │   │   9 / 31  │      │
│  └───────────┘   └───────────┘      │
│  ┌───────────┐                      │
│  │   功法    │                      │
│  │  17 / 55  │                      │
│  └───────────┘                      │
└─────────────────────────────────────┘
```

- **七格顺序固定，与 `CodexKind` 的成员序一致**（Enemy / CharacterPower / PlayerPower / CharacterItem / PlayerItem / Location / Technique），不做「按完成度排序」「最近解锁置顶」——**位置恒定**是收集面的一部分，跳动的格子让玩家每次都要重新找。
- **完成度形态 = `已收录 / 总数` 两个整数，不是百分比条。** 分母口径已定案（约束 5）；整数比百分比多给一个信息（还差几条），而进度条在只有个位数解锁时几乎不可读。
- 七本本名走 `PROFILE_CODEX_BOOK_*` 翻译键（约束 11，不新增分区）。
- 每格满足最小触控目标；点按进入单本页。**无 hover-only**——完成度常驻可见，不靠悬停。

### ④ CodexBookScreen（单本页）= 纵向滚动网格，未解锁留灰格

`[既有推演]` + `[通行做法]`

**六本（敌人 / 神通 / 法则 / 法宝 / 古宝 / 功法）共用同一份布局**（约束 1 + 2）：

```
┌─────────────────────────────────────┐
│ [安全区]   ←    敌人图鉴   12 / 48  │  ← 顶部常驻本名 + 完成度
├─────────────────────────────────────┤
│  ▣    ▣    ▣    ▢                   │  ← 窄屏 4 列 / 平板 6 列
│  ▣    ▢    ▣    ▢                   │     ▣ 已收录：Artwork + 名称
│  ▢    ▢    ▣    ▢                   │     ▢ 未收录：锁形图标，无名称
│  ▣    ▣    ▢    ▢                   │
│              ⋮ 纵向滚动，不分页      │
└─────────────────────────────────────┘
```

- **窄屏 4 列 / 平板 6 列、纵向滚动不分页**——逐字复用储物袋已定的 `GridContainer.columns` 随宽度调整这一条，**不发明第二种网格语汇**。分页在触控上多一次操作、需要页码控件，而「第几页」对图鉴条目毫无语义。
- **格内容 = `Artwork` + 名称**（`Artwork : Texture2D` 是共有字段，**仅 `PowerData` / `ItemData` 两类有**——功法与敌人两本的格用统一占位图 + 名称；功法无视觉资产已明写在 `common-properties.md` 与 `art/visuals/_index.md`）。
- **未收录 = 灰态占位格，只有一个通用锁形图标：不显示名称、不显示剪影。**
  - **不给名字**：名称是内容信息；**首遇的信息差是首遇的风险定价**（`codex/_index.md` 承重条）。给出全部敌人名等于把这份定价从入口处泄掉一半。
  - **不做剪影**：剪影要为每个条目另出一份美术资产，而 `art/` 的资产类目表里没有这一项——一条纯装饰需求换一整批新资产。
  - **点按灰格给一条「尚未收录」提示**（`PROFILE_CODEX_LOCKED`），**触控等价、非 hover**。
  - **占位格不与「战斗前确认页未解锁 → 不留灰占位」冲突**，两处判据不同、须显式写明边界：确认页的空槽是**每场战斗重复一次**的提醒（故不留），图鉴屏的灰格是**收集面的分母框**（而分母本就已由顶部完成度公开）。不写明这条，后来者会把确认页那条推广过来，把图鉴做成「只列已解锁」。
- **条目呈现序 = 按 `Id` 升序（稳定序）**，不按解锁时间。理由与索引页七格同一条：**位置恒定**才使灰格有意义、才形成「填格子」的收集感；按解锁时间排会让每次解锁都重排整张网格。**不新增 `SortOrder` 内容字段**——那要内容侧全量回填，而 `Id` 已是稳定唯一键。
- **首批不做筛选 chip、不做排序切换。** 「只看未收录」在六本上得到一屏无差别灰格（零信息），「只看已收录」用滚动即可；储物袋需要 chip 是因为它筛的是 `UsableScene` / `Charges` 这类**可变**状态，图鉴只有二值解锁态。

### ⑤ 词条载体按词条深度分野：敌人本全屏页，其余六本半屏 bottom sheet

`[既有推演]`

**「词条深度按本分野」已定案（约束 3），载体随之分野是它的直接推论**，不是新增一种取向：

| 本 | 词条构成 | 载体 |
|---|---|---|
| **EnemyCodex** | 五项结构化文案 150–280 字 + 关键卡 3 张 + 功法词条入口 | **`CodexEntryScreen` 全屏页** |
| 神通 / 法则 / 法宝 / 古宝 / 功法（五本） | 名称 · 描述 · 稀有度（· 立绘 · 属性行）+ 可选 `CodexFlavor` | **半屏 bottom sheet**，可下滑关闭 |
| 地域 | 词条深度未定 → 见「前置依赖」 | 随其深度定，本方案不裁决 |

- **敌人词条给全屏，是把「一屏读完不需滚动」这条写作规格真正兑现**：150–280 字五项 + 3 张关键卡 + 一个功法入口塞进半屏 sheet 必然要滚动，而写作规格正是按「一屏」定的长度区间。
- **五本词条短**（几行 + 一段 40–80 字风味），半屏 sheet 恰好，且直接复用约束 9 已经点名的那套控件语言。
- **敌人词条页的排布与战斗前确认页的摘要区逐字同构**：五项各一段连续文本、不分行不用项目符号；词条②的功法名由引用字段在呈现层渲染、**可点入功法词条**，功法词条以**半屏 bottom sheet** 叠在词条页上、可下滑关闭、**不离开本页**。两处共用同一份渲染，**不另切一套摘要规格**。
- **两处的唯一差异：等级页眉。** 战斗前确认页有一行「我 · 筑基中期 ⟶ 敌 · 筑基后期」（本场遭遇的实例信息）；**图鉴屏内的词条页没有这一行**——词条挂模板、跨轮回持久，同一模板以 5 个等级出场，图鉴屏没有「本次实例」可标（`enemy-codex.md`「词条正文绝不写等级」的直接落点）。
- **`CodexFlavor` 为 `null` 即不渲染该段、不留空槽、不告警**（已定的字段语义）。

### ⑥ LocationCodex：只有「单本页的内容区」不套用，其余四层全部套用

`[既有推演]` —— **这一条按分派要求显式给出**

| 层 | 地域本是否套用统一形态 |
|---|---|
| 主菜单入口 | **套用**（它不是第八个入口，是索引页七格之一） |
| 索引页格 + 完成度口径 | **套用**（`已解锁顶点 / AllIncludingDisabled()` 的 location 条目数，已定案） |
| **单本页的内容区** | **不套用** —— 其余六本是滚动网格，它是**一张逐步显影的图**（三态：已解锁 / 边缘 / 不可见，已定案） |
| 词条载体 | **待定**，随 ②-3 的词条深度定（见「前置依赖」） |
| 文案分区 · 触控纪律 · 无 hover-only · 安全区 | **套用**（三态标签走 `res://text/`、边缘顶点须有触控等价查看反馈，已明写） |

**本方案不裁决它的图怎么画**（缩放 / 平移 / 顶点布局 / 是否可拖动），那与「除连边外词条还写什么」是同一条待答项 ②-3，归用户。

**一处必须写明的族级例外：** 地域本的**边缘态显示真实地名**（已定案，「提前看见地名不是泄露」），这是全族**唯一**给出未解锁对象名字的地方。**这条例外不推广到其余六本**——理由已在两侧各自写明：地名之外什么都不给，而敌人名 / 功法名一给出去就把首遇的风险定价泄掉。不写明这条边界，后来者会把地域本的三态推广成全族口径。

### ⑦ 轮回内不设图鉴入口（首批）

`[取向选择]` → 见「仍需用户决定 ②」。**推荐：不设。** 理由与代价在那一节。

### ⑧ 工程面：零新增存档字段、零后端配合

`[既有推演]`

- 两个 ViewModel（`CodexIndexViewModel` / `CodexBookViewModel`）**随屏出生、随屏消亡**，读 `PlayerProfile.<x>Codex` + `ContentRegistry` 的 `AllIncludingDisabled()` 现算完成度与灰格；**开屏组装一次并缓存至离屏**，不进 `_Process` 热路径（约束 12）。
- **订阅翻译变更即重新组装一次**（既定纪律：内容层 `LocalizedText` 不经 `TranslationServer`，切语言不会自己变）。
- **不新增存档字段、不新增 `ProfileChangeSpec` 列、不新增提交点、不新增缓存文件**；Codex 不进透明路径白名单 ⇒ **后端零配合**（约束 6）。
- 内容条目解析不到 → **可选缺失**：`PushWarning` + 跳过该格（沿用读档校验「保留条目、不阻断」与 `Frontier` 顶点解析失败的同款处置），**不 `PushError`**——一条读不出的旧条目不该让整屏起不来。

## 具体形态（可 derive 的落地面）

### 屏 / 控件清单

| 名称 | 形态 | 归属 | 说明 |
|---|---|---|---|
| 主菜单 `Codex` 入口 | 按钮，第 4 位 | `ux/screen-flow.md` 入口表 +1 行 | 纯标签，无角标 / 红点 / 动效 |
| `CodexIndexScreen` | 全屏，进屏幕栈，有返回 | 新增 | 七格纵向网格（2 / 3 列）+ 每格完成度 |
| `CodexBookScreen` | 全屏，进屏幕栈，有返回 | 新增 | 顶部本名 + 完成度；纵向滚动网格（4 / 6 列）；地域本此处换为图 |
| `CodexEntryScreen` | 全屏，进屏幕栈，有返回 | 新增 | **仅敌人本**：五项词条 + 关键卡 3 张 + 功法入口 |
| 词条 bottom sheet | 半屏抽屉，**不进屏幕栈**，下滑关闭 | **复用**「随身」同款控件 | 其余各本词条；亦作为功法词条叠在敌人词条页上 |

### 翻译键（`PROFILE_` 分区 / `profile.csv`，**不新增分区**）

| 键 | 用途 |
|---|---|
| `PROFILE_CODEX_TITLE` | 索引页标题「图鉴」 |
| `PROFILE_CODEX_BOOK_ENEMY` / `_CHARACTER_POWER` / `_PLAYER_POWER` / `_CHARACTER_ITEM` / `_PLAYER_ITEM` / `_LOCATION` / `_TECHNIQUE` | 七本本名 |
| `PROFILE_CODEX_PROGRESS` | 完成度格式串（`{0} / {1}`） |
| `PROFILE_CODEX_LOCKED` | 灰格点按提示「尚未收录」 |
| `PROFILE_CODEX_SECTION_BACKGROUND` / `_TECHNIQUE_BRIEF` / `_HOW_IT_WORKS` / `_TRAITS_WEAKNESS` / `_KEY_CARDS` | 敌人词条五项的**项目标签**（战斗前确认页已明写「摘要区内图鉴族的项目标签复用 `PROFILE_` 既有键」——两处共用同一批键，不各写一套） |
| `PROFILE_CODEX_FLAVOR` | 风味段的段标签（`CodexFlavor` 为 `null` 时该标签同样不渲染） |

**词条正文 / 条目名 / 风味文案一律不走翻译键**——它们是内容层 `LocalizedText`（四问皆是），由 ViewModel 组装时 `Get()`。本路径**不产生任何 `ERR_*` 键**（无后端 `code`）。

### 触控与安全区

- 索引页格、网格格、bottom sheet 的抓取条、返回按钮**全部满足最小触控目标下限**；返回按钮落顶部左上安全区内，并响应系统返回键。
- **零 hover 通道**：完成度、本名、锁态、词条正文全部常驻可见或点按 / 下滑展开。
- bottom sheet **下滑关闭**为主手势，另有点按遮罩关闭作为等价通道。
- 敌人词条页纵向滚动时，底部返回 / 功法入口不随之移出视野。

## 备选方案（已考虑并否决）

- **逐本七个主菜单入口** — 在最显眼的一层否掉「一族」的抽象；主菜单撑到十二项，把 Store 推出可及区，与「安静、可预期、永远在同一个位置」相抵；且到达任何一本并不更快。
- **一屏七页签（TabBar）** — 七个页签在窄屏溢出成可滑动页签条、标签被截断；页签栏吃掉纵向空间后放不下每本的完成度，而完成度正是索引层最该给的信息。
- **图鉴收进 PlayerProfile 屏的二级页** — 三条元进程积累线里另两条持一等入口，唯独图鉴降级没有依据；且 PlayerProfile 屏已承载绑定列表 / 昵称 / 持有的古宝三区，再塞七本会让它变成杂物屏。
- **单本页只列已解锁、不留灰格** — 完成度分母本就公开，藏占位不藏分母；且「玩得越多图鉴越厚」需要一个恒定的框才读得出厚度。
- **未解锁格显示剪影或灰名** — 剪影要为每个条目另出美术资产（`art/` 无此类目）；灰名把首遇的信息差在入口处泄掉一半。
- **按解锁时间倒序排列条目** — 每次解锁重排整张网格，灰格失去位置语义，「填格子」的收集感消失。储物袋取「获得时间倒序」是因为它是持有物列表、有「刚拿到的想看看」这一高频意图，图鉴没有。
- **给单本页加筛选 chip / 排序切换** — 图鉴只有二值解锁态，「只看未收录」是一屏无差别灰格（零信息）；徒增表面积。
- **敌人词条也用半屏 bottom sheet** — 150–280 字五项 + 3 张关键卡必然要滚动，直接破掉「一屏读完不需滚动」这条写作规格所依据的前提。
- **为图鉴另开 `CODEX_` 翻译分区** — `PROFILE_` 分区表已明写覆盖「图鉴族、成就」；另开一个分区还会让战斗前确认页复用的那批项目标签落在两个文件里。

## 与既有决策的张力

> → **两条均已按标准默认采纳（2026-09-02 · 批量评审），未作为取向题呈交用户。** 判据：两条都不改变任何机制，只改措辞与边界表述。
> ① 主菜单计数：把「Store 排在既有四项之后」改写为「Store 恒排末位」——Store 的承重纪律（末位 · 安静 · 无角标 · 全游戏唯一付费路径）一字不动。
> ② 灰占位划界：在图鉴屏与战斗前确认页**两侧各写一句边界**（确认页的空槽是每场重复的提醒；图鉴屏的灰格是收集面的分母框，而分母已由完成度公开）。

**① 主菜单「五项」是写死的计数，本方案使其变六项。**
- 冲突的是：`screen-flow.md`「商业化入口」段的「排在**既有四项**之后」，以及角色选择屏段的「不新增主菜单入口，**上表五项不动**」。
- 为什么需要松动：图鉴目前**没有任何可达路径**，而它是已定案的第三条积累线、且是敌人事前知识的唯一通道。
- 松动的代价：**只是措辞** —— Store 的承重纪律（末位 · 安静 · 无角标 · 全游戏唯一付费路径）**一字不动**，把「既有四项之后」改写为「恒排末位」即可；角色选择屏那句的原意是「角色选择不新增入口」，它本身不受影响。
- 不松动时的替代：把图鉴收进 PlayerProfile 二级页（否决理由见「备选方案」）。**建议松动。**

**② 「未解锁 → 不留灰占位」在两处判据相反，须显式划界。**
- `screen-flow.md` 战斗前确认页明写「未解锁 → 摘要区不出现，不留灰占位、不做『尚未收录』空槽」；本方案在图鉴屏**留灰格**。
- 两处不冲突（确认页的空槽是每场重复的提醒；图鉴屏的灰格是收集面的分母框，而分母已由完成度公开），**但必须在两侧各写一句边界**——不写明，后来者会把确认页那条推广过来，或反过来在确认页加空槽。这是提请用户确认的一条**表述性**要求，不是机制变更。

## 仍需用户决定 → **已全部裁决（2026-09-02 · 批量评审）**

### ① 主菜单「图鉴」入口上是否显示收集完成度（如「图鉴 34%」）

| 选项 | 后果 |
|---|---|
| **A. 不显示，纯标签**（**推荐**） | 主菜单入口一律纯标签，与 Store「永不带数字角标」的克制取向在**整屏上一致**；完成度在索引页内逐本给出，玩家点进去就看得到。代价：少一处「还差多少」的被动提醒，收集驱动全靠玩家主动进入。 |
| B. 显示总完成度百分比 | 一个恒定可见的进度数是有效的回访钩子。代价：它是一个**引导性数字**，与「图鉴不与奖励挂钩、靠『看着它变厚』自持」的立论方向相反；且同屏上 Store 明令无角标而图鉴有数字，两条纪律并存需要一句解释。 |

**推荐 A，理由**：图鉴的设计立论明写它靠「看着它变厚」自持、不与任何发放挂钩；主菜单上的数字是把这条动机往外部激励挪一步。但**这是产品取向、无客观最优**——若希望强化收集驱动，B 的代价也只是一句纪律说明。

→ **已裁决（2026-09-02 · 批量评审）：选项 A —— 不显示，纯标签。** 完成度只在索引页内逐本给出。

### ② 轮回内（EventOption 选择界面）是否给图鉴入口

| 选项 | 后果 |
|---|---|
| **A. 不设，图鉴只在主菜单可达**（**推荐**） | 零新增入口、零新增拦截点；与「主菜单入口全是 PlayerProfile 级」的分层一致（角色状态条上现有的「袋」「卡组」都是轮回级）。代价明写：**玩家在轮回进行中无法主动翻阅图鉴**，想查得退到主菜单再进来。 |
| B. 角色状态条上加一个图鉴入口（战斗内仍锁死） | 玩家随时可查已积累的知识。代价：角色状态条上首次出现一个**账号级**入口，打破「袋 / 卡组 = 轮回级」这条已成立的分层；且「战斗中不可查」的边界从「屏的有无」变成「按钮的灰不灰」，多一处判据。 |

**推荐 A，理由**：既定纪律只锁死**战斗内**，轮回内可查在信息分层上是**可以开的**——这与「战斗中不可查是一个正面的体验取向、不是分层的要求」是同一种性质，因此**它是取向而非推演，交由用户**。倾向 A 的实际依据是：战斗前确认页会**自动**呈现已解锁敌人的词条，轮回内主动查图鉴的高频用途因此已被覆盖；而 EventOption 卡片本就不揭示敌人身份，玩家在选择时并没有可查的对象。

→ **已裁决（2026-09-02 · 批量评审）：选项 A —— 不设，图鉴只在主菜单可达。** 战斗内一律锁死这一条不变。
