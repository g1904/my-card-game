# 方案草稿 — 内容分发的运维形态（flags 数据源 · 签名私钥与 CI · 发布侧校验闸）

## 问题

`open-questions/04-content-delivery.md` 的协议侧四条已于 2026-08-11 全部答结，余下三条**不是协议问题，而是运维形态**。它们悬着的共同原因是「共同前置 `06-platform-stack.md`」，但这三条里有相当一部分**与栈无关**——它们由已定的契约条款与 ADR 逻辑上推得出，只是从未被写下来。本草稿把这部分推完，把真正取决于栈的部分单独列进 `## 前置依赖`。

三条各自卡住的东西：

1. **flags 规则集存在哪、由谁改、按账号计算是否需要缓存层。** 分桶留服务端、只下发结果已定（ADR-0002）；不可变版本化与留痕四项已定（ADR-0009 / `operations/_index.md` O1–O7）。缺的是这些要求落到什么形态上，以及「若引入缓存层，缓存键必须含 `flagsVersion`」这条硬约束（`contracts/content-manifest.md`「服务端保证」B 组）到底要不要被触发。
2. **ES256 私钥的保管形态与 CI 签名环节。** 它**反向约束**托管选型——即它不能等 `06` 落定再谈，否则选型时不带着这条要求，选完才发现不满足。`keyId` 轮换的机制已定（先发内置新旧两把公钥的客户端版本、覆盖率足够后切私钥），但**触发条件与节奏**未定，且「覆盖率足够」没有口径。
3. **发布侧内容校验闸的运维形态。** 客户端已把这道闸定为「内嵌在打包工具本身、不通过就不产出包」，并明写发布侧是唯一能在事故发生前拦住的地方；本库欠的是执行时点在发布流程上的那一半：闸在哪一步跑、由谁触发、失败如何阻断、是否留痕、与签名的先后。

## 约束（来自既有设计）

- **O1–O7 与留痕四项**（`operations/_index.md`）：规则集不可变、无原地编辑路径；版本号由单一全局分配点在**发布动作**时分配并持久化单调高水位；备份恢复取 `max(恢复值, 高水位)` 并强制跳号；回滚 = 以历史版本内容发起的一次新发布；每版留痕操作者 · 时间 · `derivedFrom` · 变更摘要与生效范围；历史规则集永久保留；可选的内容指纹自检。
- **B 组三条服务端保证**（`contracts/content-manifest.md`）：`flagsVersion` 取自单一全局单调序列 · 严格单调递增回滚即前滚 · **同一 `(flagsVersion, 账号)` 解析结果恒定**，分桶函数须是 `(accountId, 规则集版本)` 的纯函数；**若引入按账号的解析结果缓存，缓存键必须含 `flagsVersion` 且不得跨版本复用**。
- **A 组四条服务端保证**：稳定 URL · 字节不可变 · **manifest 与其列出的全部文件在发布上原子**（故顺序固定为先推全部 blob、后推 manifest，manifest 是服务端侧的提交点）· `contentVersion` 严格单调递增、回滚即前滚。
- **发布流程五步**（`operations/_index.md`）与**两类对象两种 TTL**（blob `immutable` / manifest · flags `no-cache`）。
- **签名形态已定**（`contracts/content-manifest.md`「防篡改」）：ES256 detached、签 manifest **原始字节**、信封 `{alg, keyId, sig}`、客户端内置**一组** `keyId → publicKey` 映射、固定公钥不引入 PKI、防回放靠 `contentVersion` 单调性；验签失败 / `keyId` 未知 → 客户端拒绝该 overlay + 回退 `res://` 基线 + 上报一次事件。
- **ADR-0002 的载荷边界**：端点只给结果，不给推导过程；分桶规则、指纹一律不下发。
- **pillar 5「线上可干预」**：改数值 / 关条目不需要发版，且这优先于跨版本可复现。
- **客户端侧硬前提（回链，不复述）**：合并期校验集与它的「客户端天花板只到启动期 `PushError`」判定 → `game-design-documents/systems/services/content-service.md`；「纪律的可执行化」四级阶梯与「**成立的前提是校验内嵌在打包工具本身（产包的唯一路径），而非一个『记得跑一下』的独立步骤**」→ `game-design-documents/systems/architecture.md`「纪律的可执行化」与 `game-design-documents/decisions/ADR-0013-discipline-enforceability-ladder.md`；`files[]` 只承载 `.tres` 与打包工具硬闸 → `game-design-documents/decisions/ADR-0125-no-binary-over-overlay.md`、本库 `contracts/content-manifest.md`「blob 通道不承载二进制资产」。

## 建议方案 A —— flags 规则集的存储形态与变更通道

### A1. 存储形态：规则集是后端主事务性存储中的一条不可变版本化记录

`[既有推演]`

O2 要求版本高水位与规则集**在同一事务边界内**（否则备份恢复只恢复其一）。这一条单独就把候选砍到只剩一类：**规则集必须与高水位住在同一个支持原子多记录写入的存储里**，即后端的主事务性存储。它当场排除了：

- **随发版走的配置文件 / 代码仓库里的配置表**——与高水位不在同一事务边界；更致命的是改一次规则要发一次版，直接违反 pillar 5 与 flags 存在的全部理由（秒关延迟从分钟级退回发版级）。
- **控制台自带独立存储**——同上，且天然给出一条「在控制台里改一改」的原地编辑路径，正是 O1 要堵的那条。

建议的记录形态（栈中立，字段名沿用 lowerCamelCase 便于与契约面对齐；**这些字段全部是后端内部形态，一个都不下发**）：

| 字段 | 类型 | 语义 |
|---|---|---|
| `flagsVersion` | `int64`，主键 | 由分配点分配；**只在发布动作时分配** |
| `rules` | 不可变内容（结构由后端自定） | 规则集本体：`disabledIds` 的规则来源、分桶比例、白名单、篇章档位 |
| `bucketSalt` | 字符串 | **分桶盐值，是 `rules` 的一部分、随版本冻结**（见 A2） |
| `derivedFrom` | `int64`，可空 | 正常发布 = 上一版；回滚 = 被回指的版本。**留痕四项之一** |
| `publishedBy` | 字符串 | **具名人类身份**，不是共享服务账号（见 A4） |
| `publishedAtUtc` | RFC 3339 UTC | 留痕四项之一 |
| `summary` / `scope` | 字符串 / 枚举（全量 · 分桶） | 变更摘要与生效范围，留痕四项之一 |
| `contentFingerprint` | 字符串（SHA-256 hex） | O7 的可选加固，建议**直接开启**（见 A5） |

另一条单行记录承载高水位：`flagsVersionHighWater`（`int64`），插入规则集与推进高水位**在同一次事务内**。

### A2. 分桶盐值必须是规则集的字段，不得是部署配置

`[既有推演]` · **承重**

B 组第 7 条逐字点名「分桶盐值变更」必须提升 `flagsVersion`。若盐存在环境变量 / 部署配置里，那么改一次环境变量就改变了全体账号的解析结果，**而版本号一动不动**——这与「手工改规则」是同一个静默失效模式，只是换了一个入口，且更隐蔽（改配置这个动作在多数团队里根本不被当作「改规则」）。

推论还有一条：**规则集不可变 ⇒ 盐随版本冻结 ⇒ 分桶函数天然是 `(accountId, 规则集版本)` 的纯函数**，B 组第 7 条的后半句因此不需要额外机制去保证，它是存储形态的直接后果。这是把契约条款做成「结构上不可能违反」而非「实现时记得遵守」的一处。

### A3. 变更通道：唯一写入面是一个发布动作，控制台 / CLI 都只是它的调用方

`[既有推演]` + `[通行做法]`

形态（栈中立，两个动作）：

```
publish(draft, summary, scope)  →  分配 flagsVersion = 高水位+1，插入记录，推进高水位（同一事务）
rollback(to: v_k)               →  publish(rules = v_k.rules, derivedFrom = v_k, summary = "rollback to v_k")
```

- **`rollback` 不是第二条路径，是 `publish` 的一个调用**——O4 已把回滚定义成「一次以历史版本内容发起的发布」，实现上让它复用同一个函数，可使「回滚会不会漏掉留痕 / 漏掉版本推进」这类问题不存在。
- **数据库直连写规则集必须在权限上被禁止**，而不只是「不建议」。O1 说的「不存在原地编辑路径」，如果只体现在应用层 API 上、而运维仍持有可写的库凭据，那这条纪律就停在评审级——与客户端「纪律的可执行化」判据同源（`game-design-documents/systems/architecture.md`）。可执行形态：应用身份对规则集表只有 `INSERT` + `SELECT`，无 `UPDATE` / `DELETE`；人类身份只有 `SELECT`。
- **草稿态不占号**（O2）：草稿存在另一张表 / 另一个键空间，`publish` 时才分配号。

### A4. 由谁改：单一具名发布者即可，但操作者必须是人而不是流水线身份

`[通行做法]`

按本项目当前规模（单人维护），**不设强制第二人审批**——四眼原则在只有一双眼时是纯摩擦。真正承重的是另一条：**`publishedBy` 必须解析到一个具名的人类身份**。若发布经由 CI 触发而留痕记成 `ci-bot`，留痕四项里最贵的那一项（操作者）当场归零，而 flags 是唯一一条能绕过发版直接改变玩家可见内容的通道（`operations/_index.md` 已写明这正是留痕是最低要求的理由）。

配套建议一条**爆炸半径闸**：单次发布使 `disabledIds` 的解析结果规模较上一版增长超过阈值时，要求发布调用显式带一个确认参数。初值建议 **新增关闭条目 > 20 条 或 > 该类型可抽取池的 5%**，取两者先到者；**待放量后按实际内容规模校准**。理由是这条通道的误操作（一个写错的规则关掉半个卡池）与它要止血的事故同量级，而分钟级生效意味着没有观察窗口。

### A5. 直接开启 O7 的内容指纹自检

`[既有推演]`

O7 写作「可选加固」，建议直接开启：规则集不可变 ⇒ 指纹在插入时算一次即永不重算，成本是一次 SHA-256；收益是把「同版本不同指纹」这个**唯一无法被单调性堵住的失效模式**变成一条可告警的机检断言。ADR-0009 已明确指纹**只作服务端自检、不下发客户端**（越过 ADR-0002 的载荷边界），故它零报文成本。

### A6. 缓存层：建议**不引入按账号的结果缓存**；改为缓存规则集本身

`[既有推演]` · **本节是 A 的核心结论**

**先看真实负载。** flags 的刷新时机已定为「搭车信封、零轮询」，客户端只在 `X-Flags-Version` **增大**时才拉一次全量。因此该端点的请求量 ≈ **活跃账号数 × （每日 flags 发布批次数 + 每会话首次）**，而**不是** × 事件推进次数。与 `/v1/profile/push`（每个 AdventureEvent 一次）相比低一到两个数量级。**这是零轮询设计已经买下的东西，再叠一层缓存是重复付账。**

**再看单次成本。** 一次请求要做的是：取规则集（按 `flagsVersion`）→ 对该账号跑纯函数分桶 → 得出 `disabledIds`。规则集体积极小（O6 已据此判定永久保留成本近似为零），分桶是 O(规则条数) 的内存运算。**唯一可能有成本的是「取规则集」这一次存储读取。**

**故建议缓存的对象是规则集，不是解析结果：**

- 键是 `flagsVersion`，值是不可变的规则集对象。**因为规则集不可变，这个缓存永不需要失效逻辑**——版本提升后旧条目自然不可达，LRU 回收即可。
- 命中率接近 100%：绝大多数请求打的是当前最大版本那一条。
- **它使 B 组的硬约束（缓存键必须含 `flagsVersion`）成为结构上不可能违反的事**——键就是版本号本身，不存在「忘了把版本加进键」这个失误面。而按账号的结果缓存把这条约束变成一句需要实现者记住的话，其失效形态（版本已增大、拉到的仍是旧结果、客户端此后「等值不拉」⇒ 这一批秒关对该账号**永不生效**）在契约里已被逐字写明是「与手工改规则同一病理」。
- 穿透与惊群：冷启动 / 新版本发布后的第一波请求会同时回源，用**请求合并（single-flight）**收敛为一次读取即可；规则集不可变意味着这次读取的结果可被无条件复用。

**何时才该引入按账号的结果缓存（触发判据，避免「日后再说」变成「日后没人知道该看什么」）：** 当 `GET /v1/content/flags` 的服务端处理时延 p99 > **50 ms**，或该端点占后端 CPU > **5%**，且已确认瓶颈在分桶计算而非存储读取时。初值待实测校准。一旦引入，键**必须**是 `(flagsVersion, accountId)`——同样因为键含版本，版本提升后旧条目自然不可达，无需主动失效。

### A7. flags 的读路径不受「读己所写」约束

`[既有推演]`

`06-platform-stack.md` 记有一条承重约束：读己所写要求「验票写入后立即读到」，滞后的只读副本不能无条件承接 pull。**这条不覆盖 flags**，须明写以免被误扩：flags 的写入者是运营发布动作、读取者是玩家请求，二者之间**没有「同一主体写后立刻读」的语义**；只读副本的滞后在 flags 这里表现为**传播时延**，已被 B 组第 5 条（单一全局序列）与运维 SLO 窗口 T 覆盖，且客户端观测到更小版本已被定义为**已知良性态**。

推论：**flags 端点可由只读副本 / 多区域实例承接**；只有 A1 的分配点与高水位写入必须是单点。这对托管拓扑是一条实质放宽，值得在选型时带上。

## 建议方案 B —— ES256 私钥的保管、CI 签名步骤与 `keyId` 轮换

### B1. 保管形态：五条能力判据（不点名产品）

`[通行做法]` + `[既有推演]`

| # | 判据 | 不满足的后果 |
|---|---|---|
| B1-1 | **私钥不可导出**：签名以「把字节交给密钥服务、拿回签名」的形式发生，私钥永不出现在仓库、CI 变量、构建机磁盘或日志里 | CI 环境变量存 PEM 是最常见做法，但它把私钥暴露给每个能改流水线的人；泄漏后只能靠轮换，而轮换要跨一个发版周期 |
| B1-2 | **签名操作可审计**：谁、什么时候、用哪个 `keyId`、签了哪个摘要 | 与 flags 留痕四项同构；签名是客户端唯一的信任根，不可审计等于事故后无第一现场 |
| B1-3 | **原生支持 ECDSA P-256 + SHA-256**，且能**并存多把**密钥（active + standby，见 B4） | 已由 `contracts/content-manifest.md` 的签名形态钉死，不是选择项 |
| B1-4 | **签名权限授予发布流水线的身份，而非个人**；人触发流水线，但拿不到签名能力之外的任何东西 | 「人能直接签一份 manifest」这条旁路会让 B3 的整条流水线纪律退化为评审级 |
| B1-5 | **可用性要求低一档即可**（见下） | 若误按热路径依赖去选型，会为它付不必要的多区域 / 高可用成本 |

**B1-5 值得单独论证，它是本节最有用的一条：内容签名私钥不在任何请求路径上。** 客户端验签用的是**内置公钥**，服务端不参与验签；已发布的 manifest 与 `.sig` 是 CDN 上的静态对象。因此密钥服务停机的后果只有一个——**这段时间不能发布新内容**，线上玩家完全无感。这与 `06` 里那把 **token 签名密钥**形成鲜明对比：那把在每次签发 token 的热路径上，停机即全体无法登录。**两把钥匙的可用性档位不同、轮换窗口不同、爆炸半径不同，选型时不要合并考虑，也不要为省事让它们共用同一把。**

### B2. CI 签名步骤在发布流程中的插入位置

`[既有推演]`

在 `operations/_index.md` 已定的五步之上细化（**新增的三步是 ⓪、④、⑤**，其余是既有五步的原样保留）：

| 步 | 动作 | 失败时 |
|---|---|---|
| ⓪ | **产物认证核对**（发布侧校验闸的本库那一半，见方案 C） | 中止；此时尚未推任何 blob，无补偿动作 |
| ① | 计算全部 overlay 文件 SHA-256，推送缺失 blob（幂等：已存在的 hash 跳过） | 中止；已推的 blob 是孤儿但无害（内容寻址、不可达） |
| ② | 生成 manifest 字节，`contentVersion` = 内容版本高水位 + 1 | 中止 |
| ③ | **调用密钥服务对 manifest 原始字节做 ES256 签名**，产出 `{alg, keyId, sig}` | 中止 |
| ④ | **自验（sign-then-verify）**：用**客户端内置的那份公钥**（不是从密钥服务现取的）在流水线内验一次签名 | **中止**——见下 |
| ⑤ | 确认全部 blob 可读（对 `files[]` 的 hash 逐一或抽样探针 GET） | 中止 |
| ⑥ | 原子发布 `.sig` 与 manifest（`.sig` 先于或与 manifest 同一次切换） | — |
| ⑦ | 写内容发布留痕（见 C5） | — |

**④ 是本节最值得加的一步。** 验签失败在客户端的后果是「拒绝 overlay + 回退基线 + 上报一次事件」——它不会崩，只会**静默地让全体玩家收不到这次内容更新**，且症状与「网络不好」难以区分。把验签提前到流水线里，等于把一个只在玩家设备上暴露的失败拉到发布期。用**客户端内置的那份公钥**而非密钥服务导出的公钥，是为了让这一步真正验的是「玩家手里那把钥匙能不能验通」。

**`contentVersion` 的分配点与 flags 同构但是两个独立序列。** A 组第 4 条要求它严格单调不回退，其形态与 A1 完全一样（单调高水位 + 只在发布动作时分配 + 备份恢复后强制跳号）。两条序列**不得合并**——它们的发布节奏完全不同，合并会让一次 flags 秒关白白推高 `contentVersion`，而客户端对后者有「更大即增量更新」的判据。

### B3. `sig` 的编码格式须明确为 IEEE P1363（契约侧建议补一句）

`[通行做法]` · **本条是一个具体的踩坑面**

ECDSA 签名在实践中有**两种编码**：IEEE P1363（`r‖s`，各 32 字节定长拼接，共 64 字节）与 ASN.1 DER（变长）。JOSE 的 `ES256` **定义为 P1363**，而客户端侧 .NET 的 `ECDsa.VerifyData(data, sig, HashAlgorithmName.SHA256)` 默认也期望 P1363；但**多数密钥服务的签名 API 返回 DER**。

后果是一个典型的「两侧各自都没错、合起来不通」：签名生成毫无报错，客户端 100% 验签失败，且只在真机集成时才暴露。

- **建议**：流水线在 ③ 之后、④ 之前做一次 **DER → P1363 转换**（若所选密钥服务返回 DER），并由 ④ 的自验兜住这一步。
- **建议契约侧补一句**：`contracts/content-manifest.md`「防篡改」的 `{alg, keyId, sig}` 处注明 `sig` 为 **base64 编码的 P1363 `r‖s`（64 字节）**。`alg: ES256` 已隐含这一点，但它隐含得不够显眼，而代价是一个只在集成期暴露的失败。**本草稿不改契约文档**，此项列进 `## 后果`。

### B4. 从第一个客户端版本起就内置 active + standby 两把公钥

`[通行做法]` + `[既有推演]` · **承重**

契约已写「客户端内置**一组** `keyId → publicKey` 映射」——复数是已支持的，只是从未被用来预置。建议把它用满：

**首个版本即内置两把**：`content-2026a`（active，服务端在用）与 `content-2026b`（standby，私钥在**另一处独立保管**、平时不参与任何签名）。

理由是把轮换机制里最贵的那一段拿掉。既定机制「先发内置新旧两把公钥的版本 → 覆盖率足够后切私钥」有一个隐含前提：**新公钥的分发要等一个客户端发版周期**。在计划轮换里这没问题；但在**泄漏 / 紧急轮换**里，这意味着从发现泄漏到能切钥有数周的窗口，期间的止血手段只剩强更闸门（`contracts/envelope.md` §7a 的 `client.version_unsupported`）——为一次密钥事故强更全体玩家，代价与事故本身不成比例。

预置 standby 后，紧急轮换退化为**服务端切一个字符串**，分钟级完成，零客户端动作。成本是：多生成一把密钥对、客户端内置多几十字节、多一处保管。**这个成本与它买下的东西完全不成比例，建议直接采纳。**

配套：**旧 `keyId` 永不主动从客户端移除**（保留成本近零，且它是回切的输入面）。唯一必须移除的情形是旧私钥确认泄漏——那时移除需要发版 + 强更，这恰恰是 standby 存在的理由：泄漏时切到 standby，移除工作可以慢慢随常规发版做。

### B5. 轮换的触发条件、节奏与覆盖率口径

`[通行做法]`（阈值为初值） + `[既有推演]`（口径与观测面）

**触发条件分三类，处置完全不同：**

| 类别 | 触发 | 处置 |
|---|---|---|
| **计划轮换** | 周期到期。节奏初值 **12 个月** | 走完整四阶段（下表），不急 |
| **紧急轮换** | 疑似泄漏 · 持签名权限的人员离职或权限变更 · 密钥材料跨保管方迁移 | **立即切到 standby**（B4），跳过等覆盖率——standby 的公钥早已内置 |
| **不构成触发** | 客户端发版加入了新 `keyId` 的公钥 | 只是为下一次轮换预置条件，服务端不动 |

**12 个月的推导：** 威胁模型已明写只到「防误 / 防随手改」，不引入 PKI、不承诺防作弊；私钥不可导出且不在任何请求路径上（B1-5）⇒ 暴露面极小。另一侧，每次计划轮换要跨一个客户端发版周期 + 等覆盖率，运营成本不低。年度轮换是这两者的常见折中点，**待运营实际节奏校准**。

**计划轮换四阶段：**

| 阶段 | 动作 | 判据 |
|---|---|---|
| T0 预置 | 生成新密钥对；公钥进入**下一个**客户端版本的内置映射 | 服务端**仍用旧 `keyId` 签名** |
| T1 等覆盖 | 观测覆盖率 | 达到阈值（见下） |
| T2 切签名 | 服务端 active `keyId` 切为新的。**历史 manifest 不重签** | 切换后进入观察窗口 |
| T3 退役 | 旧 `keyId` 保留在客户端内置映射里，**不主动移除**（B4） | — |

**覆盖率口径（零新增契约面）：** 后端在每个 API 请求上**已经**收到 `X-App-Version`（`contracts/envelope.md` §4a）。故覆盖率 = **过去 N 天有过请求的账号中，`appVersion ≥ 引入新公钥的那个版本` 的比例**。N 初值 **7 天**（移动游戏的常见活跃回访窗口）。数据已经在手，不需要任何新报文、新埋点。

**阈值初值 95%，推导如下：** 未覆盖的那部分玩家在 T2 之后会验签失败 ⇒ 拒绝 overlay + **回退 `res://` 基线 + 照常开局**（客户端已定）。也就是说轮换的爆炸半径是「一部分玩家暂时收不到内容热更」，**不是「玩不了」**——这比强更闸门的爆炸半径低一整档，故阈值不必按强更的标准取。若取 99%+，尾部是长期不更新的设备，可能永远等不到，轮换被无限期推迟；若低于 90%，受影响人群规模开始与一次内容事故本身相当。取 95%，**待实测校准**。

**另两条配套：**

- **T2 前先在非生产环境用新 `keyId` 走完整条流水线并用真实客户端验通一次**——B3 那类编码形态错误若在切换当天才暴露，代价是一次全量内容更新中断。
- **T2 后设 48 小时观察窗口**，监控客户端验签失败上报量（客户端已定「验签失败上报一次事件」）；异常即**回切 active `keyId` 到旧的**。**签名密钥的回切是安全的**——旧公钥仍内置于全部客户端，且 `keyId` 没有任何单调性约束。这与 `contentVersion` / `flagsVersion` 的「回滚即前滚」形成对照：那两者的回退被禁止是因为客户端有单调判据，而 `keyId` 只是一个查表键，**不要把单调纪律误扩到它身上**。

## 建议方案 C —— 发布侧内容校验闸的运维形态（只写本库那一半）

### C0. 分工的准确切法

客户端已把闸定在**打包工具内部**：校验必须内嵌在产包的**唯一路径**上，否则退化为「记得跑一下」的评审级（权威：`game-design-documents/systems/architecture.md`「纪律的可执行化」·`game-design-documents/decisions/ADR-0013-discipline-enforceability-ladder.md`；校验集与其判据：`game-design-documents/systems/services/content-service.md`、`game-design-documents/decisions/ADR-0125-no-binary-over-overlay.md`）。**本库不实现、不复述这些规则。**

那么本库那一半到底是什么？把客户端的保证反过来读一遍就清楚了：

> 客户端保证「凡是打包工具产出的包，都过了闸」。
> 它**没有**保证、也**无力**保证「凡是被发布出去的文件集，都是打包工具产出的」。

**后者正是本库的义务，也是这条链上唯一还敞着的口子。** 一个手工塞进目录的文件、一次「就改一个字、不重新产包了」的热心操作，会绕过整道闸而客户端毫无察觉。因此本库那一半的正确形态**不是「在流水线里再跑一遍校验」**（那是复述对侧规则，且会造出第二份实现随时漂移），而是：

> **发布流水线拒绝任何没有打包工具背书的文件集。**

### C1. 形态：产物认证核对（步 ⓪）

`[既有推演]`

- **打包工具产出一份机读的产包证明**（与 overlay 文件集同批产出），至少含：工具版本 · 所用**基线的 `appVersion`** · 校验通过的断言项计数 · **文件集的逐文件 `path` + `sha256` 清单**。（证明的具体字段形态归客户端——本库的要求只是「它存在、机读、含上述四类信息」。）
- **步 ⓪ 做两件事**：① 证明存在且自洽；② 证明里的文件清单与**待推文件集逐文件 hash 完全一致**（一一对应，不多不少）。
- 不一致 / 证明缺失 → **中止，非零退出**。

这样「手工改一个文件再发」这条路径被堵死：改了字节，hash 就对不上证明；重新产包，就必然过闸。**它用一次 hash 比对，把对侧的闸延伸到了发布面，而没有在本库复制任何一条校验规则。**

### C2. 流水线位置：在推 blob 之前，即最前

`[既有推演]` · 三条理由，逐条独立成立

1. **完整文件集在产包结束即具备**——闸的输入不需要等推 blob，没有理由后置。
2. **blob 是永久对象**。内容寻址 + 字节不可变 + 长缓存 `immutable` 意味着推上去的 blob 事实上永久占用分发面。闸在最前，不合格的产出**一个字节都不落到分发面**。
3. **失败时无需任何补偿动作**——见 C3。

### C3. 触发方与阻断形态：流水线无条件执行，无跳过参数

`[既有推演]`

- **触发方 = 发布流水线自身，无条件。** 不是「发布前人工跑一遍的清单项」。这直接承接对侧那条判据：闸必须在产出路径上，人可以跳过的闸不是闸。
- **不设跳过开关。** 紧急发布走**同一条**路径——紧急场景恰恰是最容易出引用图错误的场景，为它开后门等于在最需要闸的时刻把闸拆了。
- **阻断形态 = 该步非零退出，后续步骤（①–⑦）全部不执行。** 因为闸在最前，「阻断」天然等于「什么都还没发生」：无孤儿 blob、无 manifest、无签名、无留痕需要撤销。**这是把闸放在最前的第三个、也是最实用的理由**——它使阻断路径不需要任何补偿逻辑，而补偿逻辑正是这类流水线里最容易写错、最少被测试的部分。

### C4. 与签名步骤的先后：校验在签名之前，且中间隔着推 blob 与生成 manifest

`[既有推演]`

顺序是 **⓪ 校验 → ① 推 blob → ② 生成 manifest → ③ 签名 → ④ 自验 → ⑤ 确认可读 → ⑥ 原子发布**（表见 B2）。

**签名必须在校验之后，理由不是「顺手」而是承重的**：签名是客户端唯一的信任根，一份被签名的 manifest 就是本库对它的背书。先签后验会产生「**已签名但不合格**」的产物——而一旦这样的产物离开流水线（哪怕只是落到某个中间存储），它在密码学上与合法产物无法区分。**永远不要签一个还没通过闸的东西。**

推论：**签名应当是流水线上最后一个产生可分发产物的动作**（⑤ ⑥ 只做探针与切换，不产生新产物）。

### C5. 留痕：需要，且与 flags 留痕同构但**不合并**

`[既有推演]`

`operations/_index.md` 的留痕四项是为 **flags 发布**定的。内容发布是**另一条轴**（另一个版本序列、另一种爆炸半径、另一套回滚语义），两者留痕同构但应各存各的——合并会让「这一版是内容发布还是秒关」需要靠字段是否为空去猜。

建议内容发布留痕字段（步 ⑦ 写入）：

| 字段 | 语义 |
|---|---|
| `contentVersion` | 本次发布的版本 |
| `publishedBy` | **具名人类身份**（同 A4） |
| `publishedAtUtc` | RFC 3339 UTC |
| `derivedFrom` | 正常发布 = 上一版；**回滚（A 组第 4 条的「前滚」）= 被回指的版本** |
| `summary` | 文件增 / 改 / 删计数 + 本次 `minAppVersion` |
| `manifestSha256` | manifest **原始字节**的 SHA-256——它是「这一版到底签的是什么」的唯一凭据 |
| `keyId` | 本次签名所用的 `keyId`（轮换期排查的第一现场） |
| **`gateAttestation`** | **闸的结果**：打包工具版本 · 所用基线 `appVersion` · 断言项计数 |

**`gateAttestation` 值得单列理由**：闸的规则由客户端实现且**会随客户端版本演进**（ADR-0125 就是一次加闸）。事后追一次事故时，「这一版内容是被**哪一版规则**校验过的」是唯一能把内容与当时的纪律对上的凭据；不记它，日后只能靠发布日期去猜工具版本。

### C6. 基线漂移：闸的输入必须是玩家实际持有的那份基线

`[既有推演]` · **本节是本库对发布运维提出的一条实质新要求**

闸的规则里有「必须存在于**基线**」这一类判据（权威在对侧，不复述）。这意味着闸的输入**不只是待发 overlay，还有一份基线内容集**。于是本库这边冒出一个对侧看不见的问题：

> **闸校验时用的基线，和玩家设备上的基线，是同一份吗？**

不必然。一次 overlay 会被多个仍在架的客户端版本消费；每个版本的 `res://` 基线内容各不相同。**若闸只对最新基线跑过，而某个较老的在架版本的基线里缺少某个被引用的 `Id`，那么闸通过、老版本玩家启动即 `PushError`**——恰恰是闸要防的那件事，发生在闸的盲区里。

- **建议**：闸对**兼容矩阵内每一个 ≥ 本次 `minAppVersion` 的在架客户端基线各跑一遍**，全部通过才算通过。成本 = 版本数 × 一次校验，而并存版本数是个位数（`operations/_index.md` 的版本兼容矩阵本就要维护这份清单），成本可忽略。
- **配套要求**：发布侧必须**能取到每个在架版本的基线内容快照**。这是选型时容易漏掉的一条——它意味着基线快照要随客户端发版一起归档到发布侧可达的地方，而不是只存在于某次构建的产物里。
- **`minAppVersion` 在这里是一个真正的旋钮**：提高它即缩小需要校验的基线集合（低于它的客户端会跳过本次 overlay，契约已定）。这给了发布方一个明确的处置——某个老基线过不了闸时，提高 `minAppVersion` 是合法且已被契约支持的解法，代价是那批玩家本次不更新内容。
- **「更高版本的基线是否总是更低版本基线的超集」不由本库裁决**（内容条目可能被客户端删除），故不采用「只跑最新基线」这个简化。见 `## 前置依赖`。

## 具体形态（可 derive 的落地面）

**发布流水线（内容发布，栈中立）：**

```
⓪ 产物认证核对   证明存在 ∧ 逐文件 hash 与待推集一一对应        失败→非零退出，无补偿
① 推 blob        SHA-256 内容寻址，幂等跳过已存在
② 生成 manifest  contentVersion = 内容高水位+1（独立序列）
③ 签名           密钥服务对 manifest 原始字节做 ES256
③b 编码归一      DER → IEEE P1363（若密钥服务返回 DER）
④ 自验           用客户端内置公钥验签，失败即中止
⑤ 确认 blob 可读  探针 GET
⑥ 原子发布       .sig 先于或与 manifest 同一次切换
⑦ 留痕           C5 的八个字段
```

**flags 发布流水线：**

```
publish(draft, summary, scope)
  ├─ 爆炸半径闸（新增关闭 > 20 条 或 > 池 5% ⇒ 需显式确认）
  └─ 同一事务：分配 flagsVersion = 高水位+1 · 插入不可变规则集（含 bucketSalt、contentFingerprint）
                · 推进高水位 · 写留痕四项（publishedBy 为具名人类身份）
rollback(to: v_k) ≡ publish(rules = v_k.rules, derivedFrom = v_k)
```

**存储与权限（栈中立的能力要求）：**

| 要求 | 为什么 |
|---|---|
| 支持规则集插入与高水位推进的**原子多记录写**（关系库的事务；若为文档库则须单文档承载或条件写 + 单调 CAS） | O2 / O3 |
| 应用身份对规则集表只有 `INSERT` + `SELECT`；人类身份只有 `SELECT` | O1 的可执行化（A3） |
| flags 端点**可由只读副本承接**；只有分配点是单写入点 | A7 |
| 发布侧可取到**每个在架客户端版本的基线内容快照** | C6 |
| 密钥服务满足 B1-1…B1-5 五条；可用性档位低于 token 签名密钥 | B1 |

**数值初值一览（全部待实测校准）：**

| 旋钮 | 初值 | 推导所在 |
|---|---|---|
| flags 爆炸半径闸 | 新增关闭 > 20 条 或 > 池 5% | A4 |
| 结果缓存的引入触发 | p99 > 50 ms 或端点 CPU > 5% | A6 |
| `keyId` 计划轮换周期 | 12 个月 | B5 |
| 覆盖率统计窗口 N | 7 天 | B5 |

| T2 后观察窗口 | 48 小时 | B5 |

## 后果

- **`operations/_index.md`** 的三节（内容分发运维面 · flags 发布流程 O1–O7 · 签名私钥保管）需扩写：新增 A1–A7、B1–B5、C1–C6 的要求。栈落定后整体展开为 `operations/content-delivery-ops.md`。
- **`contracts/content-manifest.md`** 需一处**补注**（B3）：`sig` 的编码固定为 base64 的 IEEE P1363 `r‖s`。这是澄清而非变更（`alg: ES256` 已隐含），**报文零改动、`manifestSchema` 不提升**。本草稿不改契约文档。
- **`06-platform-stack.md`** 收到三条反向约束（选型时不满足即出局）：存储须支持 A1 的原子多记录写 · 密钥服务须满足 B1 五条 · 发布侧须能取到各在架版本的基线快照（C6）。同时收到一条**放宽**：flags 读路径不受读己所写约束（A7）。
- **客户端侧承接项**（本草稿不代为决定，不写对侧草稿）：产包证明的字段形态与产出时机 · 基线内容快照的归档形态。见 `## 前置依赖`。
- **无 ADR 候选**。三条都是既有 ADR（0001 / 0002 / 0009）与已定契约条款的运维落地，不产生新的方向性决策。

## 备选方案（已考虑并否决）

- **flags 规则集存在代码仓库的配置表里，随发版走** — 与 O2 的同事务要求不相容；更根本的是改一次规则要发一次版，秒关延迟从分钟级退回发版级，pillar 5 与 flags 存在的全部理由当场失效。
- **控制台自带独立存储、可直接编辑生效** — 天然是一条原地编辑路径（O1 明确要堵的那条），且与高水位不同事务。控制台作为**发布 API 的调用方**则完全可以。
- **分桶盐值放部署配置 / 环境变量** — 改配置即改变全体解析结果而版本不变，与「手工改规则」同一病理（A2）。
- **引入按账号的 flags 结果缓存** — 零轮询设计已把该端点负载压到与 push 差一到两个数量级；缓存规则集即可覆盖真实成本，且键含版本这条硬约束在那里是结构性满足而非纪律性满足（A6）。
- **强制第二人审批 flags 发布** — 当前单人维护，四眼原则是纯摩擦；真正承重的是 `publishedBy` 解析到具名人类身份（A4）。团队扩张后可加。
- **私钥存 CI 环境变量 / 加密后进仓库** — 违反 B1-1，暴露面等于「所有能改流水线的人」，且泄漏后的止血要跨一个发版周期。
- **私钥离线保管、发布时人工签名** — 违反 B1-4：人能直接签一份 manifest 这条旁路，会让 C 的整条流水线纪律退化为评审级（与对侧「记得跑一下即第 4 级」同源）。
- **内容签名密钥与 token 签名密钥共用一把 / 共用一套轮换** — 可用性档位、轮换窗口、爆炸半径三者全不同（B1-5）。
- **只在客户端内置一把 active 公钥，轮换时再发新版本** — 紧急轮换的止血窗口被拉到一个发版周期，期间唯一手段是强更全体玩家（B4）。
- **`keyId` 也套用「回滚即前滚」的单调纪律** — `keyId` 只是查表键、无客户端单调判据，回切安全且是 T2 观察窗口唯一的处置手段（B5）。
- **在发布流水线里重新实现一遍内容校验规则** — 制造第二份实现，与对侧规则随时漂移，且违反「校验逻辑归客户端、本库不复述」。产物认证核对（C1）用一次 hash 比对达到同等效果。
- **校验闸放在推 blob 之后 / 签名之后** — 前者产生孤儿 blob 且需要补偿逻辑；后者会产生「已签名但不合格」的产物，而签名即背书（C4）。
- **给发布流水线留一个「跳过校验」的紧急开关** — 紧急场景恰是最易出引用图错误的场景（C3）。若日后确被迫引入，须与 O5 同构留痕并触发告警。
- **闸只对最新基线跑一遍** — 需要「更高版本基线是更低版本基线的超集」这个前提，而它不由本库裁决且不必然成立（C6）。
- **内容发布留痕与 flags 留痕合并成一套台账** — 两条不同的版本轴与回滚语义，合并后要靠字段是否为空去区分（C5）。

## 与既有决策的张力

**没有需要松动既有决策的地方。** 三处曾疑似张力，逐一说明为何不是：

1. **B4 的「常态内置两把公钥」** 看似扩展了 `contracts/content-manifest.md` 的密钥轮换条款，实际是**兑现**它——该条款原文即为「客户端内置**一组** `keyId → publicKey` 映射」，复数从第一天起就在，本建议只是把它用满。报文零改动。
2. **B3 的 `sig` 编码** 不是与契约冲突，而是契约的一处**未明写**（`alg: ES256` 隐含 P1363）。建议以补注澄清，不构成变更。
3. **A5 建议把 O7 从「可选加固」改为直接开启** —— O7 原文即为可选，把可选项做掉不需要推翻任何东西；成本是一次 SHA-256。

一处**需要用户知情的口径收紧**（不构成冲突，但比现有文字严格）：C3 主张发布流水线**不设跳过开关**、紧急发布走同一条路径。`operations/_index.md` 现有文字未就此表态。若日后运营认为需要 break-glass，本草稿的立场是——可以有，但必须与 O5 同构留痕并触发告警，而不是一个静默的命令行参数。

## 前置依赖

- **`06-platform-stack.md`（栈与托管）** —— 下列各项的**具体承载**待它落定，但**要求本身不待**（本草稿已给出栈中立的能力判据，正是为了让选型带着它们做）：存储选型与事务形态（A1）· 密钥服务的具体形态（B1）· CI / 流水线平台（B2、C1）· 控制台的承载（A3）。
- **多区域一致性与传播窗口 T**（`04-content-delivery.md` 的另一条，**不在本草稿范围**）—— A7 的「传播时延而非独立计数」依赖它给出 T 的数值上界；A6 建议的规则集缓存在多区域下的行为也随它定稿。本草稿的其余部分不依赖它。
- **客户端侧两项承接（本草稿不代为决定，也未在对侧落草稿）：** ① **产包证明的字段形态与产出时机**——C1 的核对以它为输入，本库只要求「机读、含四类信息」，形态归客户端；② **基线内容快照的归档形态**——C6 要求发布侧能取到每个在架版本的基线，这需要客户端发版流程配合归档。**两项须与本方案同批落地，单侧采纳即 C 的闸有洞**（有流水线核对，但没有可核对的证明 / 没有可喂给闸的基线）。

## 仍需用户决定

- **flags 规则集的作者入口：运营控制台 UI，还是 CLI / 脚本 + 文本形式的规则草稿。**（两者都建立在 A3 的同一个 `publish` 动作之上——这一层不受影响；分歧只在人机接口。）
