# 方案草稿 — 上行整键回声校验的适用面（客户端侧）

> **本文件只写客户端这一半**：受约束的顶层键、组装规则、值的唯一来源、缺失与钳制的处置、push 前自检。
> **逐条 JSON path 的封闭清单、校验口径（如何算「逐位相同」）、拒绝语义与风控处置的权威全部在后端库**，见 `counterpart` 与 `backend-design-documents/contracts/profile-sync.md` §5。**本文件不复述它们**。

## 问题

`entitlement` 已定：上行组装该键时必须原样回声 pull 下来的 `bundleGrantOrdinal`，客户端永不自行赋值；不一致即整批拒绝并风控（`systems/services/sync-service.md`「后端主动写入的唯一情形 = 购买段」末条）。

但这不是一处孤例，而是一条**通则的第一个实例**。同形的第二处是 `accountInfo`：

| 顶层键 | 后端写入的路径 | 客户端写入的路径 | 客户端提交该键的常规时机 |
|---|---|---|---|
| `accountInfo` | `accountSeed` · `createdAtUtc` · `identities` | `nickname` | **每次改昵称** |
| `entitlement` | `bundleGrantOrdinal` | `bundleRedeemedOrdinal` | **每次兑现** |

diff 语义是**顶层键出现即整键替换**（`systems/services/sync-service.md`「透明路径的稳定性纪律」末条，对齐 `backend-design-documents/contracts/profile-sync.md` §3a）⇒ **客户端只要写一次 `nickname`，就必然把后端写入的三项一并提交上去**。这与兑现时必然提交 `bundleGrantOrdinal` 是同一个形状，且它是**每次改昵称都走一遍的常规路径**，不是异常路径。

悬着的是两件事：① 缺一份「哪些顶层键受约束」的封闭登记，逐键临时判必然漏，而漏掉的那一处正是客户端可以静默改写后端权威字段的口子；② 客户端侧**没有任何一处**在把这些值发出去之前检查过它们——目前全靠「组装代码恰好没碰它们」这条隐含假设。

## 约束（来自既有设计）

- **diff = 顶层键粒度的浅合并，键值以下对后端完全不透明**，本服务不得依赖后端做任何逐元素合并（`systems/services/sync-service.md`）。
- **后端写入字段表是封闭的四行**，措辞是「后端只读，除表内四项外」，扩表须逐条通过「够格进表」两条判据（权威在 `backend-design-documents/contracts/profile-sync.md` §5；本库不复制该表）。
- **`BundleGrantOrdinal` 写入方只有后端，客户端无写入通道**；`Identities` 是只读投影，客户端从不写它（`systems/player-profile/_index.md` 字段表第 1 / 14 行、`account-info.md`）。
- **收到该情形的 `Conflict` 一律走既有处置**（以云端为准、丢弃本地缓冲、重新 pull），客户端侧不新增任何分支（既定）。
- **`Conflict` 的既定处置代价是「丢弃本地缓冲」**——即**丢玩家进度**（`systems/services/sync-service.md` 断线降级）。
- **纪律的可执行化四级阶梯**（`systems/architecture.md`）：能抬到「代码里根本写不出来」就不要停在评审清单。先例：`deviceId` 私有化、`AccountSeed` 不出 API 面。
- **移动或重命名任一透明路径 = 破坏性契约变更**（同上文档）。

## 建议方案

### 1. 封闭清单分两层持有：**顶层键清单在本库，逐条 path 在后端库**

`[既有推演]`

- **受回声校验约束的路径集合 ≡ 后端写入字段封闭表的全部行**，一个不多、一个不少。这不是巧合，是同一件事的两面：一条路径够格进写入表 ⟺ 它的真值只可能在服务端产生且客户端无其他通道取到它 ⟺ 客户端提交的任何值都只能是回声。
  **推论（承重）：日后向写入表加一行，该路径自动进入回声约束，不需要第二次决定、也不需要第二份清单。** 两份清单会各自漂移，而漂移的形态正是「某条路径进了写入表却没进回声表」——那正是本问题要关掉的口子。
- **本库只登记「哪些顶层键受约束」这一层**（当前恰好两个：`accountInfo` · `entitlement`），因为顶层键才是客户端组装 diff 的粒度。逐条 path 的清单**不在本库复制**，需要时回链后端契约。
- **顶层键清单的机械导出规则：** 某顶层键受约束 ⟺ 后端写入表中存在一条以该键开头的 path。写进 `systems/player-profile/_index.md` 字段表的一列即可（当前第 1 行与第 14 行），**不另建一张表**——与「共有属性投影只写落点与回链、不复述定义」同一条纪律。

### 2. 组装规则：回声值的唯一来源是**最近一次 pull 的权威快照**

`[既有推演]`

- 组装含受约束顶层键的 diff 时，该键内**后端写入路径的取值一律取自最近一次 pull 的权威快照**（`ProfileService` 内存态），客户端**永不自行赋值、永不由本地历史推算、永不沿用上一次 push 的值**。
- **不为回声值另存一份缓存文件。** 权威快照本就在内存里且由 pull 覆写；另存一份即第二权威，且它与快照的不一致无任何机制能发现。
- **`ProfileChangeSpec` 对这些路径不提供写入通道**——`ElementSpec` 里没有对应的 `CostKey` / 列，`AllowedOps` 为空。这把「客户端改写后端字段」从纪律抬到**跨服务代码里根本写不出来**（阶梯第 1 级），与 `deviceId` 私有化同款手法。**这条已由 `systems/player-profile/_index.md` 字段表第 14 行的「无客户端通道」兑现，本方案只是把它明确为通则并覆盖第 1 行。**

### 3. 承重：回声路径**不参与读档钳制、缺省补齐与格式归一化**

`[既有推演]`

这是本方案发现的**真实缺陷面**，而不是理论风险。既有两条通则各自都合理，合起来会在正常账号上把 push 打成整批拒绝：

- `account-info.md` 定「字段增删即 schema bump，**老档缺字段以默认值补齐**（空列表 / 默认时间 / 空昵称）」；
- 读档校验对越界值定「钳制 + 告警」。

若这两条作用在回声路径上，客户端会拿一个**自己造出来的值**去回声 ⇒ 与云端不等 ⇒ **整批拒绝 ⇒ 按 `Conflict` 丢弃本地缓冲 ⇒ 丢玩家进度**。玩家侧表现是「改一次昵称丢一场战斗」，且症状完全指不向昵称。

**建议的处置（三条）：**

| 情形 | 处置 |
|---|---|
| 回声路径**缺失**（老档 / 迁移补齐面） | **该顶层键本次不进 diff**（不提交即不校验，浅合并语义下「未出现 = 保持不变」，云端值原样存活）+ `GD.PushError` 带 path + **触发一次 pull 重取权威值** |
| 回声路径**越界 / 不合法** | 同上——**不钳制、不改写**。钳制等于用客户端算出的值覆盖后端权威值 |
| 回声路径**格式需要归一化**（时间串、hex 大小写） | **不归一化**。见子项 4 |

**明确区分：读档校验对客户端自己写的那一半照常生效。** `BundleRedeemedOrdinal` 的 `< 0 → 0`、`> Grant → Grant` 钳制（已定）**不受影响**——它读 `Grant` 只是**读**，不写回，回声不被破坏。

### 4. 序列化往返的稳定性：客户端不得对回声路径做任何再加工

`[既有推演]` + `[通行做法]`

`bundleGrantOrdinal` 是 `int`，往返无损；但另外三条不是：

| path | 客户端内存类型 | 往返风险 |
|---|---|---|
| `accountSeed` | `ulong`（序列化为 hex16） | 大小写 / 补零位数；**已由 `account-info.md` 钉死为 16 位小写 hex**，风险已关闭 |
| `createdAtUtc` | `DateTime` | **真实风险**：`Z` vs `+00:00`、小数秒位数、本地时区往返 |
| `identities` | `IReadOnlyList<BoundIdentity>` | **真实风险**：元素顺序、`boundAtUtc` 同上、未来后端新增字段被客户端强类型往返**丢掉** |

- **客户端侧纪律：对回声路径按 pull 下来的原值提交，反序列化 → 再序列化的往返不得改变它的线上表示。** 具体到实现是「统一的 camelCase 单点策略 + RFC 3339 UTC 输出」已给的保证，本条只是明写它在这四条路径上是**承重**而非风格。
- **未来后端向 `identities` 元素加一格字段时，客户端的强类型 `BoundIdentity` 会静默丢掉它 ⇒ 回声当场失败。** 故：**向受约束顶层键内的对象追加字段，是需要两侧同批落笔的变更**，与「重命名跨边界枚举值」同档。这条须写进 `account-info.md`。
- **比较口径（语义相等 vs 字节相等）的裁定权在后端**（`counterpart` 子项 2），本库只承接「不得再加工」这条义务。

### 5. push 前自检：本地拦截优于让后端整批拒绝（本方案对客户端最有价值的一条）

`[既有推演]`

后端的回声校验是**防线**，但它的失败代价是**丢玩家进度**（整批拒绝 → `Conflict` → 丢弃缓冲）。客户端不该把一个自己完全可以在本地发现的 bug，交给一条代价这么高的路径去发现。

> **建议：`ProfileSyncManager` 组装完 diff、发出请求之前，对每个受约束的顶层键做一次「与权威快照逐字相同」的断言。**

- **不同 → `GD.PushError`（带 path、快照值、组装值）+ 按下方取向处置。** 这是**必需但缺失**级别：它证明本地存在一条不该存在的写入路径。
- 断言点落在 `ProfileSyncManager` 的组装出口**一处**，与「请求头组装与应答头解析收敛到 `src/Core/` 的一处」同构——多于一处必然出现半配置态。
- **它不替代后端校验。** 客户端的自检可以被改包绕过，防篡改仍由后端承担；自检防的是**客户端自己的 bug**，那才是这条路径上概率最高的失败源。
- 与 `revision_ahead` 单列一行「处置相同但必须被观测到」同构：**客户端无法从 `sync.conflict` 分辨「多设备」与「我改写了后端字段」**（两者同码同处置），故可观测性只能由本地自检承担。

### 6. `Conflict` 处置不动，一个分支都不加

`[既有推演]` 既定。回声校验失败在客户端侧表现为一次普通 `sync.conflict`：以云端为准、丢弃本地缓冲、重新 pull，随后按既有判据（两序号之差 / 昵称以云端为准）重新判定。**本方案不新增 `OpError` 取值、不新增 `SyncState` 值、不新增错误码映射行。**

## 具体形态（可 derive 的落地面）

**受约束顶层键登记（本库持有的那一层）：**

| 顶层键 | 键内后端写入路径（**清单权威在后端契约 §5，本表不复制取值语义**） | 键内客户端写入路径 | 客户端提交该键的时机 | 组装规则 |
|---|---|---|---|---|
| `accountInfo` | 3 条 | `nickname` | 改昵称成功后 | 三条取自权威快照原值；只有 `nickname` 用新值 |
| `entitlement` | 1 条 | `bundleRedeemedOrdinal` | 兑现事务内 | 该条取自权威快照原值；只有水位用新值 |

**组装与自检的形态（伪码，非最终签名）：**

```
组装 PlayerProfileDiff 时，对每个受约束顶层键 K：
    若本批没有 K 内客户端路径的变更 → K 不进 diff              // 不提交即不校验
    否则：
        K 的后端写入路径 ← 权威快照中的原值（不反序列化再序列化、不钳制、不补默认）
        若快照中该路径缺失 / 不合法 → PushError + K 不进 diff + 触发一次 pull
发出前（组装出口一处）：
    foreach 受约束顶层键 K in diff:
        foreach 后端写入路径 p under K:
            assert diff[p] 与快照[p] 逐字相同
            否则 → PushError(path, 快照值, 组装值) + 【取向 A/B/C 的处置】
```

**文档改动清单：**

| 文件 | 改动 |
|---|---|
| `systems/services/sync-service.md` | 「后端主动写入的唯一情形」末条由 `entitlement` 单例改写为**通则**（受约束顶层键的机械导出规则 + 组装规则 + 不钳制不补默认 + push 前自检 + 回链后端 §5） |
| `systems/player-profile/_index.md` | 字段表第 1 行的「写入通道」列补「受回声约束」标注（第 14 行已有等价表述，措辞对齐） |
| `systems/player-profile/account-info.md` | ① 「老档缺字段以默认值补齐」一句加**回声路径例外**；② 新增一条「向 `identities` 元素追加字段是两侧同批变更」 |

**存档 schema 影响：无，零迁移。** 本方案不增删任何字段，只约束组装路径与读档处置。

## 后果

- 客户端多一处 push 前断言（每批至多两次对象比较，代价可忽略）。
- **`accountInfo` 的老档补默认值口径被收窄**——受影响的只有回声路径，`nickname` 照旧。
- 「后端向受约束键内追加字段」由纯后端变更升为**两侧同批变更**，这是本方案引入的一条新刚性，如实记下。
- 与 `counterpart` 成对采纳；单侧采纳的后果见「前置依赖」。

## 备选方案（已考虑并否决）

- **把后端写入的路径拆到独立顶层键**（使客户端永不提交它们）—— 能绕开整键替换，但把语义紧邻的字段拆散、与 `PlayerEntitlement` / `AccountInfo` 的类形态直接冲突，且 `accountInfo` 与 `entitlement` **两处同形**说明需要的是通则而不是搬家。`counterpart` 已按同一理由否决。
- **在本库复制一份逐条 JSON path 清单** —— 第二权威，且它与后端写入表的漂移无任何机制能发现，正是本问题的成因。
- **只靠 `revision` CAS 挡住覆写** —— CAS 问「基线对不对」，不问「你有没有权改这个字段」；客户端 bug 在基线正确时会被原样接受。（`counterpart` 已就后端侧同一条给出论证。）
- **回声路径缺失时补一个默认值再上行** —— 用客户端造的值覆盖后端权威值，且会在正常老档上稳定触发整批拒绝。
- **为回声失败在客户端新增一个 `OpError` / `SyncState`** —— 处置与 `Conflict` 完全一致，新增取值只逼 UI 多写一条走向同一处的分支。
- **push 前自检做成「若不同则拒绝本批」** —— 见「仍需用户决定」取向 1：拒绝本批 = 客户端自己制造一次进度停滞，而正确值就在手边。

## 与既有决策的张力

1. **与 `account-info.md`「老档缺字段以默认值补齐（空列表 / 默认时间 / 空昵称）」正面相抵。** 该句在回声路径上会造出一次必然被拒的 push。**建议松动**：把它改写为「客户端写入的字段补默认值；回声路径缺失走必需缺失处置 + 重新 pull」。**代价**：老档在拿到一次成功 pull 之前，`accountInfo` 顶层键不可提交 ⇒ 改昵称在那一刻会失败。考虑到 pull 是启动链的硬阻塞第三步、成功 pull 是进入主菜单的前提，**该窗口在实践中不存在**——但仍须明写，否则读者会认为它是漏洞。
2. **与「客户端侧不新增任何分支」的措辞有表面张力。** 既定句说的是**收到 `Conflict` 之后**不新增分支（子项 6 原样遵守）；本方案新增的是**发出之前**的一次断言，两者不在同一层。**须在改写时把这条判据一并写入**，否则两句读起来互抵——与 `counterpart` 对 `purchase.md` §5 的同类处置同构。
3. **本方案给「透明路径的稳定性纪律」加了一条新刚性**（受约束键内追加字段 = 两侧同批）。该节现有措辞只覆盖「移动或重命名」，不覆盖「追加」。追加一个后端写入字段本来是安全的（不透明段追加已定「不需要后端配合」），**但在回声路径上不是**——因为客户端的强类型往返会丢掉它。这条是新的，请确认是否接受。

1. **push 前自检发现不一致时的处置**（承重，`[取向选择]`）
   - **A（推荐）——强制回声改写 + `PushError` 上报：** 用权威快照的值覆盖组装值，本批照常发出。理由：正确值就在手边，玩家不该为一次客户端 bug 付出任何代价；错误由 `PushError` 台账承担可见性。**代价**：它会「修好」一个 bug 的表现，可能让该 bug 在没人看日志时长期存活。
   - **B —— 剔除该顶层键 + 继续本批：** 该键本次不同步（浅合并下云端值原样存活），其余变更照常上行。代价：客户端写的那一半（昵称 / 兑现水位）本次也丢了，而兑现水位丢失会导致重复兑现判定——**不建议用于 `entitlement`**。
   - **C —— 拒绝本批：** 最严格，但等于客户端自己制造一次进度停滞。
2. **子项 3 对 `account-info.md`「老档补默认值」的松动是否批准**（`[取向选择]`）——见「张力 1」。不松动则该句与回声校验直接冲突，必须二选一。
3. **子项 4 新增的刚性「向受约束顶层键内的对象追加字段 = 两侧同批变更」是否接受**（`[取向选择]`）——见「张力 3」。替代方案是要求客户端对受约束键采用**保留未知字段的松散持有形态**（而非强类型 record），代价是 `AccountInfo` 的类型一致性被打破，与「贯穿整条链路的类型一致性」相抵；**不推荐**。
