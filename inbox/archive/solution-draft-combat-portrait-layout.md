# 方案草稿 — 战斗屏竖屏主视图布局

> **本草稿只答「主视图的分区与容纳形态」。** 叠加元素与二级面板的**具体形状**（道具角标与抽屉内部 · 神通 / 法则条的图标形状 · 埋伏标记形态 · 卡框色与类型角标 · 卡牌详情页 · 战报文案体系 · 疲劳呈现 · 战后奖励面板 · `LineSlot` 成员）归另一份草稿；本草稿为它们逐项给出**槽位契约**（占多少、放哪里、可容纳 N 条时怎么退让），见末节「给叠加元素的槽位契约」。

## 问题

`ux/combat-ux.md` 的待决问题「**竖屏分区整体是否过载（承重）**」自 08-16 起被排期为一场专门 session，理由是「根子是把 MTG 的完整分区模型搬进手机竖屏」。至今累积的同屏容纳清单已达：

战场（敌 / 我两侧）· 栈 · 手牌 · 双方道念位（对比条 + 两端头像与数值）· **双方 mana**（`SideSnapshot` 双方都给 `CurrentMana` / `ManaLimit`）· 回合计数（`CombatSnapshot.TurnIndex` / `TurnLimit`，原文明写「UI 需显示『第 3 / 10 回合』」）· 战报收起态单行 · 神通 / 法则只读层 · 随身角标 · 埋伏计数（双向）· 敌人境界名一行 · 敌人立绘 · 常驻的「离线 · 待同步 N」指示（`ux/screen-flow.md` 明写「它在战斗屏内同样必须可见」）· 飘字层。

其中被本库自己点名为根因的一条是：**栈在零交互下玩家做不了任何事、只能看，它是否必须常驻（而非结算时的临时演出层）值得重估。**

同时挂在这一问题下的还有五个子问题：栈与战场的同屏区分 · 手牌布局 / 敌我分区 / 敌方出牌呈现 · 道念对比的视觉形态与回合进度的组合呈现（含「道念差是否显式呈现」）· **牌堆在竖屏战斗屏上是否有稳定可见面**（`systems/monetization.md` 的卡背品类被这一条事实确认卡住）。

## 约束（来自既有设计）

**规则层（不可动）**

1. **出牌时机唯一：自己回合的行动阶段、且栈为空时**，对双方成立；启动式异能与道具使用窗口完全相同。栈非空时任何一方都不能出牌（`ActionRejection.StackNotEmpty`）。→ `terminology.md`「出牌时机（唯一）」· `systems/adventure-event/combat/_index.md` · `systems/services/combat-service.md`
2. **栈与战场是两个区，两者都必须进入呈现层。** → `ADR-0019` · `systems/services/combat-service.md`
3. **战斗内共六处位置**：卡组 / 手牌 / 弃牌堆 / 栈 / 战场 / 本场可用道具，**明确不引入第七处**。→ `systems/services/combat-service.md`（`Power` 推论 ④）
4. 战场是**单一记录**，条目自带 `OwnerSide`，**呈现层按它分区渲染**。→ `terminology.md`「战场」
5. 对侧 `faceDown` 条目**整条不入 `CombatSnapshot.Battlefield`**，公开面只有 `SideSnapshot.AmbushCount`。→ `ADR-0154`
6. 敌方信息面在类型层即残缺：`HandCardInstanceIds` / `UsableItemIds` / `ActivatableAbilities` 对侧恒空，抽 / 弃只给计数。**布局不得预留「翻开对手信息」的位置。**
7. 起手 4 / 每回合抽 2 / **手牌上限 7**（敌我三项同值）；满手抽不进，**不产生弃牌堆流量**，视觉上不该出现「牌被丢掉」的动作。→ `systems/balance.md` · `ADR-0019`
8. 抽牌堆**不重洗**、弃牌堆不回流 ⇒ 抽牌堆单调递减。起始 15 张，`Standard` 一场流入 14 张 ⇒ **常规遭遇恰好不疲劳**。→ `ADR-0052` · `systems/balance.md`
9. 双方 mana 量级不对称：玩家 `manaLimit` 5 → ch3 末 10~13；**敌方恒 5**（`EnemyManaLimit` 明写例外）。卡面 `manaCost` 值域 0–8，**恒一位数**。
10. 道念读数量级：ch1 约 1~46 · ch2 约 20~90 · **ch3 可达三位数（约 160）**；道念差恒一到两位数。**四位数只出现在寿元，而寿元不进战斗屏。**

**呈现层（已定，本方案必须兼容）**

11. **道念是主视觉**；**双方道念位 = 对比条 + 两端的头像与数值**（玩家侧头像只作道念锚点，不承担图鉴入口）。
12. **敌人不作任何事前预告**（`ADR-0059`）；意图区已整条移除、释放约屏高 8%。
13. **战报收起态常驻**，固定预留 ≈ 屏高 6%，**单行永不换行**，收起 / 展开共用同一格（净增 0 个区）；容器本身不参与布局变化 ⇒ 动画不触发 `Container` 重排。
14. **「元素上移（回收空间）」已排除**——手牌区跳位被明确点名为不可接受。
15. **压缩顺序已定**：先压敌方区（立绘可缩）→ 再压栈 / 战场（**可做浮层而非常驻**）→ 双方道念位最后动。
16. **选目标态**：暗幕 ≈45% 压暗一切非决策必需元素，**双方道念位与栈区豁免不压暗**；指令条位置绝对固定（屏幕中部偏上，道念对比条与栈之间）；合法目标描边呼吸；单点即确认。整套形态**已被裁定不削减**。
17. **随身角标与神通 / 法则条分居己方战场区两侧**；`ux/combat-ux.md` 已明写「⚠ 两侧同时挂会挤压战场可用宽度，须在实际排版时验证」。
18. **卡面 full art**，唯一文字是 `manaCost`；缩略可辨是手牌区认牌的唯一通道。→ `ADR-0083`
19. **手势**：点按手牌 = 详情页，拖出手牌区 = 打出。→ `ADR-0085`
20. **战斗屏不设任何图鉴入口**；礼包入口、更新横幅在战斗内不存在；**不做全局 HUD**，寿元不常驻。→ `ADR-0094` · `ux/screen-flow.md`
21. 「离线 · 待同步 N」指示**必须在战斗屏内可见**（三取值，`UpgradeRequired` 时换词为「需更新 · 待同步 N」）。
22. 既有控件语汇：**半屏 bottom sheet**（随身抽屉 / 详情 / 功法词条）· 纵向滚动网格 · 就地二段确认。**横滑是「事件选择 / 角色选择」层级的专用语汇，不得在战斗屏复用。**
23. 演出节拍 0.35–0.5 s（>4 步压 0.2 s）· 点按 3× 加速、只加速不跳过 · 敌人回合演出总时长 ≤ 4 s。
24. 布局工程形态：`Container` + 锚点重排、尊重安全区、无 hover-only 可供性、尺寸写百分比 / `SizeFlags` 比例**而非像素常量**（`stretch/mode = canvas_items` + `aspect = expand`）。→ `.claude/rules/ui-input-rules.md`

## 建议方案

### 一、根因体检：栈**不必**常驻，建议改为结算期的临时浮层

`[既有推演]` **最强的一条依据，且是纯规则推演。**

**推演**：出牌时机是「行动阶段 **且栈为空**」（约束 1）。取其逆否：

> **玩家能发起任何动作的每一个时刻，栈必然为空。**

因此栈非空的区间**只有两种**：

| 区间 | 玩家状态 | 时长 |
|---|---|---|
| ① 结算演出（弹栈中） | 无输入（「不可暂停」= 无暂停 / 跳过控件） | 单步 0.35–0.5 s；敌人回合整段 ≤ 4 s |
| ② 挂起态 `targetState = AwaitingChoice`（决策点 D4） | **有输入**，但只能 `ProvideTarget` | 一场期望进入 1~2 次 |

两者都是**演出 / 交互时刻**，不是常态。一个常驻的栈区，在玩家做出全部约 31 个出牌决策的**每一刻都恒为空**——它占的是屏高，给的是零信息。

**建议**：栈改为**结算期临时浮层（overlay）**，不占常驻布局预算。

- **不参与 `Container` 布局**：与战报「容器本身不参与布局变化 ⇒ 动画不触发 `Container` 重排」同一条工程纪律（约束 13）。栈层的出现 / 消失**不得挤动任何常驻区**，尤其不得让手牌区跳位（约束 14）。
- **落位**：屏幕中部偏上，**紧贴指令条下方**——指令条位置已被定为「道念对比条与栈之间」（约束 16），故此处正是它既定的位置，不是新落点。
- **在挂起态（②）必然在场** ⇒ 「栈区保持可见且不被压暗」这条承重纪律照常成立（详见「与既有决策的张力」第 1 条）。
- **收益**：释放屏高约 **12–15%**（一条能容纳 3~4 层栈条目的常驻竖列）。加上意图区已释放的 8%，本作竖屏压力最大的那一处第一次有了正的余量。

**代价（明写接受）**：行动阶段看不到「上一次结算留下了什么」。但那本已落账——持续效果落到战场（可见）、增量落进战报（收起态常驻单行 + 展开态因果树）。栈本身在那一刻**已经是空的**，看不到的不是信息，是一个空容器。

**反向风险已被既有定案封住**：若日后引入 instant / 优先权 / 「栈非空时可出牌」，本方案须回退为常驻区。而这三者**已被明确否决**（`ADR-0039`，理由为拉长时长、决策点过多、深度收益小）。

### 二、竖屏分区总表（屏高预算）

`[既有推演]` + `[通行做法]`

**总原则：上敌下我，中轴为共享决策面板。** 依据：玩家可操作的对象（手牌 · 己方战场条目 · 随身 · 启动式异能 · 结束回合）**全部**落在下半屏的拇指可达区；敌方全程零可操作（约束 6），故占上半。

| # | 区 | 屏高 | 内容 | 常驻 |
|---|---|---|---|---|
| 0 | 顶部条 | **5%** | 左：退出入口。右：「离线 · 待同步 N」指示（约束 21） | ✅ |
| 1 | 敌方区 | **20%** | 敌人立绘 · 敌人境界名一行 · 敌方 `CurrentMana/ManaLimit` · 敌方手牌张数角标 · 敌方战场带 · 敌方埋伏计数 · 敌方抽 / 弃计数 | ✅ |
| 2 | **决策面板组** | **16%** | 道念对比条（7%）+ 回合进度（3%）+ 战报收起态单行（6%，约束 13） | ✅ |
| 3 | 己方战场带 | **12%** | 己方战场条目横滚带；左缘 = 神通 / 法则条，右缘 = 随身角标（约束 17） | ✅ |
| 4 | 手牌区 | **28%** | ≤ 7 张，重叠扇 | ✅ |
| 5 | 底部条 | **10%** | 左：己方 `CurrentMana/ManaLimit`。中：抽牌堆 · 弃牌堆。右：**结束回合**键 | ✅ |
| — | 安全区留白 | **9%** | 顶部刘海 + 底部 Home 指示条 | — |
| — | 栈层 | **0%** | 结算期浮层，落在 2 与 3 之间（上叠） | ❌ 临时 |
| — | 飘字层 | **0%** | 全屏叠加 | ❌ 临时 |
| — | 指令条 | **0%** | 选目标态浮层，位置绝对固定（约束 16） | ❌ 临时 |
| — | bottom sheet | **0%** | 随身抽屉 / 详情页 / 启动弹层，上叠 | ❌ 临时 |

合计 100%。**三个数字是初值，须在实际竖屏比例（18:9 / 19.5:9 / 平板）上实测**——`vision/scope.md` 未给目标分辨率或宽高比，故此处只能给比例、不能给像素。

**压缩顺序照既定（约束 15），本方案补一条**：手牌区（#4）**不参与压缩**，它是屏内唯一承载拖拽的区，缩小会直接抬高「拖出手牌区 = 打出」的误判率。补充后的完整顺序：**敌方立绘 → 敌方 / 己方战场带 → 底部条 →（手牌区与双方道念位不动）**。栈已浮层化，从压缩链中退出。

### 三、栈与战场的同屏呈现（三条正交的区分轴）

`[既有推演]` + `[通行做法]`

竖屏小尺寸上区分两个区，**不靠颜色**（色觉可及性 + full art 底色不可控），靠三条同时成立的正交轴：

| 轴 | 战场 | 栈 |
|---|---|---|
| **存在性** | 恒在（两条常驻带） | **只在结算期出现**——这本身就是最强的一条区分 |
| **位置** | 敌方带在 #1 下沿、己方带在 #3 | 屏幕中轴浮层（#2 与 #3 之间） |
| **轴向** | **横向**排列的条目带 | **纵向**堆叠的条目列 |

- **栈的顺序表达**：`CombatSnapshot.Stack` 已定「**栈顶在前**」。竖屏上把**栈顶画在最上**、并在其左侧画一个「↓ 下一个结算」的固定指示。理由：LIFO 下**后触发的先生效**，玩家的自然阅读顺序（自上而下）恰好就是结算顺序，无需教学。
- **未落账气质**：栈条目**半透明 + 悬浮投影 + 无底座**；战场条目**实心 + 贴带底 + 描边底座**。「悬着 vs 落地」是这两个区语义的直接视觉隐喻。
- **弹栈 = 一次可见的位移**：一条栈条目弹出结算时，从栈层**飞向它的落点**——持续效果飞进己方 / 敌方战场带并落座；一次性效果飞向弃牌堆；`Power` 触发的异能飞回左缘的法则条。**「从等待 → 已生效」因此是一个被看见的位移，而不是一次消失加一次出现。**
- **不拖慢节奏**：位移**复用既定节拍**（0.35–0.5 s / >4 步压 0.2 s / 点按 3× 加速，约束 23），**不新增任何停顿**。敌人回合整段 ≤ 4 s 的硬上界因此不受影响；栈深大时由「>4 步压到 0.2 s + 合并同来源同类型连续增量」这条既有护栏次线性收敛。
- **敌人回合期间栈层照常出现**，位置与玩家回合完全相同（同一位置 = 节奏可预期）。

### 四、敌我分区与敌方出牌呈现

`[既有推演]`

**敌方区不做己方的镜像。** 敌方在类型层没有可操作对象（约束 6），故它只承载**读数与观看**：

| 元素 | 形态 | 依据 |
|---|---|---|
| 敌人立绘 | 区内主体，**可缩**（压缩顺序第一位） | 约束 15 |
| 敌人境界名 | 立绘下方一行，「筑基中期」形态；**不并列玩家等级、不做方向标记、全局序 1–22 不出现** | `ux/combat-ux.md` |
| 敌方 mana | 立绘一侧一格 `n/5` | `SideSnapshot` 双方都给 |
| **敌方手牌** | **一个张数角标，不渲染牌背扇形** | `HandCardInstanceIds` 对侧恒空；「对手手牌只给计数」是 AI 输入面的既定对称口径 |
| 敌方抽 / 弃 | 两个小计数，与角标同排 | `DrawPileCount` / `DiscardPileCount` 双方都给 |
| 敌方战场带 | 区下沿一条横滚带 | 约束 4 |
| 敌方埋伏 | 战场带上的**一个计数角标，不占条目位** | `AmbushCount`；对侧 faceDown 条目整条不在列表里（约束 5） |

**敌方出牌的呈现（承接「敌人回合是唯一动态情报通道」这条硬要求）**：

敌人打出的牌**不从手牌角标飞出**（那里没有牌），而是**在敌人立绘前方放大呈现该卡面一拍（0.35–0.5 s），再落入栈层**。

- 理由：卡面是 full art、**无卡名无规则文字**（约束 18），玩家认牌完全靠插画。若敌方出牌只是一张缩略图一闪，等于取消这条唯一情报通道。**给它一拍足够大的呈现，是 full art 决策的直接对价。**
- 该拍**照常受 3× 加速手势约束**，不设不可跳过的节拍（这条已被 08-15d 明写）。
- 后续「它做了什么」由飘字（注意力跟随对象）+ 战报收起态单行承担，不重复。

### 五、手牌布局

`[通行做法]` + `[既有推演]`

- **形态 = 水平重叠扇（overlap fan），不做弧形旋转。** 旋转会让 full art 的缩略辨识更难（主体不再正立），且拖拽命中区变成不规则形。竖屏单手拇指的拖起动作也更适合水平带。
- **重叠量动态**：≤ 4 张不重叠（稳态手牌 = 4，见 `systems/balance.md`「抽 2 出 2」）；5–7 张按可用宽度均分重叠，**每张至少露出 40% 宽度**（初值，须与美术侧「缩略可辨」阈值一并实测）。
- **手牌区高度固定、不随张数变化**——与战报同一条纪律（约束 13、14）。撞上限的 7 张与稳态的 4 张占同样的高度，只是重叠更密。
- **被点按 / 被拖起的那张：上浮 + 放大 1.1× + 描边。** **复用栈条目来源指示的同一套视觉**（约束 16 已为选目标态定义了这一套），不新造视觉语言。
- **「拖出手牌区 = 打出」需要一条可见的边界**：拖起后，手牌区上沿浮现一条**释放线**（0.15 s 淡入），越过即高亮。理由：拖拽阈值若不可见，玩家无法预判「拖多远才算数」，而这是本作最高频的操作。释放线是临时浮层，不占布局。
- **满手抽不进的反馈落在这里**：第 8 张牌从抽牌堆抬起一半后**退回抽牌堆**（0.3 s），手牌区上沿同步闪一次上限标记。**不出现任何「牌被丢掉」的动作**（约束 7）。手牌上限的常驻可读形态：手牌区右上角一格 `n/7`（`HandCount` / 生效手牌上限；上限由 `EncounterSpec.HandLimit` 覆写驱动，**不写死 7**）。

### 六、道念对比的视觉形态

`[既有推演]` + `[通行做法]`

**建议形态 = 横贯屏幕的一条「对峙条」（单条双向，中点为分界），两端各挂头像与数值。**

```
┌────────────────────────────────────────────────┐
│ (敌头像) 42   ███████████│▌  ▏░░░░░░░  57 (我头像) │   ← 对峙条（7%）
│                     ▲初始中点        +15 ▏      │
│  ●─●─●─●─◍─○─○─○─○─○      第 5 / 10 回合        │   ← 回合进度（3%）
├────────────────────────────────────────────────┤
│ 我方打出「叠嶂符」  对方道念 −5                    │   ← 战报收起态（6%）
└────────────────────────────────────────────────┘
```

- **分界线位置 = `myMomentum / (my + enemy)`**。谁领先 = 分界线偏向哪边，**不读数字即可读出局势**；这直接兑现「玩家任何时刻都应一眼看出我现在领先还是落后」。
- **两端 = 头像 + 数值**，满足「双方头像与数值分居对比条两端」这一已定落位（约束 11）。数值按 **三位数**排版（ch3 可达约 160，约束 10）——不按四位数，四位数是寿元的排版口径，而寿元不进战斗屏。
- **固定的初始中点刻度**：一个细刻度标在条的正中，使「分界线相对中线的偏移量」= 道念差的视觉长度。
- **变化反馈**：数值滚动 0.2 s + **增量段闪一次**（我方增长 = 己方色向对侧推进并高亮；被削减 = 对方色侵入己方段）。数据源是既有的 `SideSnapshot.MomentumDeltaThisTurn` 与 `CombatFeedEntry` 的逐次 `MomentumDelta`，**不新增字段**。
- **不做压暗豁免以外的任何特殊处理**：选目标态下它与栈层一并豁免压暗（约束 16）。

**「道念差是否显式呈现」→ 建议显式呈现**，形态 = 分界线上方一枚小徽标 `+15` / `−15`（带方向色）。三条理由：

1. **道念差是三个消费点的共同输入**：胜负判据（`d >= WinMargin`）· 胜侧奖励厚度（线性单价 + `advantage` 三档）· 负侧寿元扣减。玩家真正需要的那个量就是差，不是两个绝对值。
2. **ch3 起跑线 45–75、战中可达三位数**，要求玩家自己做三位数减法不符合「明快、单手」的基调（`vision/pillars.md`）。
3. `open-questions/01-combat.md` 记的削弱论据是「负侧换算要先乘一个逐章系数，比逐点对应多一步心算」——**它削弱的是「差 → 寿元」这一步，不是「差本身要不要显示」**。

**⇒ 本项不被 `lossPerMomentum` ch2 / ch3 未定案阻塞。** 那个未定案只影响「是否在差值旁再附一层 `≈ −N 寿元` 的二级换算」，而该子项**已被既有决策独立否决**（「寿元不常驻战斗屏、战斗内没有任何手段改变这个值，常驻显示只增噪音并诱导『留血打』」，见 `answer-logs/log-life-lifespan-merge.md`）⇒ 无残留阻塞，差值显示是纯净的胜负 / 奖励刻度。

### 七、回合进度与道念差的组合呈现

`[既有推演]`

**建议：空间邻接式组合，而非语义合成。** 二者是决策面板组内**紧邻的两行**，一次扫视读全；**不合成一个「还追得回来吗」的复合指示**。

否决合成的理由：一个「追得回吗」的指示需要一个**每回合期望产出模型**才能算。而该模型的输入（`momentumPerMana = 1`、摆幅 `P`、`E[道念差]`）在 `systems/balance.md` 中被明令标注为「**可复算的初值，不是设计结论**」「⚠ 待实测校准的标定假设，**不得被引用为任何设计的承重依据**」。把它焊进 UI 等于让一个待校准的数字变成玩家读到的结论。且它会**替玩家算掉那本账**——而「我落后 8 点、还剩 2 个回合」这本**玩家自己算**的账，正是本库反复点名的紧张感来源。

**回合进度的形态**：`TurnLimit` 个小格的一排点，敌 / 我交替着色，已过的填实、当前格高亮呼吸；右侧并列文字「第 `TurnIndex` / `TurnLimit` 回合」（`CombatSnapshot` 原文明写 UI 需显示这一对）。

- **格数由 `EncounterSpec.TurnLimit` 驱动，绝不写死 10**（`Practice` 8 / `Standard` 10 / `Finale` 12）。格宽自适应，8–12 格在竖屏宽度下均可容纳。
- **「轮到谁」由这一排承担**：当前格的着色即回合归属方，**不新增部件**。同时对应一端的头像加一圈呼吸描边作冗余编码（小格在小屏可能读不出色差）。

### 八、牌堆：**有稳定可见面**（答 `07-codex-monetization.md` 的事实确认）

`[通行做法]` + `[既有推演]`

**结论一句话：建议抽牌堆在战斗全程有一个固定的实体呈现——一叠牌背朝上的牌，落在底部条（#5）中部；因此牌背在竖屏战斗屏上确有稳定可见面，卡背可以排进首批付费外观。**

四条依据：

1. **既有设计已经预设了它的存在。** `ux/combat-ux.md` 明写「卡组构成查询不在此收口，**复用抽牌堆信息面**」——一个「抽牌堆信息面」必须有一个入口，而那个入口的自然宿主就是抽牌堆本身。
2. **抽牌动画需要一个起点。** 每回合开始阶段抽 2 张、起手抽 4 张，是一场里稳定发生 6 次的动作；牌若从屏幕边缘凭空飞出，则「抽牌」这一节拍（三步结构给的三个可呈现节拍之一）失去落点。
3. **弃牌堆同理需要一个终点**：一次性效果结算完、业障被打出、`DiscardEffect` 触发，都需要一个可见的去处。**弃牌堆的填充通道只有两条**（打出后进 / 显式弃牌），量少且明确。
4. **不新增位置。** 卡组与弃牌堆本就是六处位置中的两处（约束 3）；给它们一个可见面是**呈现既有的位置**，不是第七处。

形态建议：

- **抽牌堆**：牌背朝上的一叠，厚度**随剩余张数递减**（不重洗 ⇒ 单调递减 ⇒ 厚度是一个诚实且零文字的余量指示）。
- **弃牌堆**：与抽牌堆并列，**面朝上显示最近进入的那张**（`Power` 永不产生弃牌堆流量，故这里不会出现受保护条目）。
- **敌方牌堆不给实体**，只在敌方区给两个计数（约束 6，且敌人不应获得卡背外观位）。
- **卡背外观只作用于玩家侧的抽牌堆顶与己方埋伏的背面**——这两处即卡背的可见面。

> **交给 A2 的部分（本草稿不裁定）**：抽牌堆上是否叠一个**数字**计数、见底前是否给**预警**、疲劳飘字如何与「被对手削减」区分。本草稿只保证「有一个固定宿主可挂这些」。补一条对 A2 有用的量：**起始 15 张、`Standard` 一场流入 14 张 ⇒ 常规遭遇恒不见底**；疲劳只在天劫（16 张流入）与轻量敌人卡组上现身。

### 文案

全部 UI 文案走 `res://text/combat.csv` 的 `COMBAT_` 分区键（「第 N / M 回合」「结束回合」「还有 N 项待结算」「离线 · 待同步 N」等）。**战报条目存结构化数据、渲染期才套翻译键**。卡面 / 条目正文走内容层 `LocalizedText`，不进 `text/`。

### 一处布局必需但库内至今无表述的部件：**结束回合键**

`[通行做法]` **行动阶段需要一个出口。** 「打完手上想打的牌」不是一个可被系统检测的状态（玩家可能故意留牌避免撞手牌上限、或留 mana 无用），故必须有一个玩家主动结束回合的动作——`ActionResult.Kind` 已含 `EndTurn`、决策点 D2 的定义也预设了它。

建议：**底部条右端的主按钮**，满足最小触控目标；**不做二次确认**（与库内「不在最高频操作上加模态」一致）；敌人回合 / 结算中 / 选目标态置灰（与随身角标同规格）。

## 备选方案（已考虑并否决）

- **栈保持常驻窄条（例如高 6% 的一行横向队列）** — 玩家能操作的每一刻它恒为空，占屏高换零信息；且横向排列会与两条横向战场带撞轴，反而更难区分。
- **栈与战场合并成一个「场上」区，用边框区分等待 / 生效** — 与 `ADR-0019`「栈与战场是两个区」相抵；且两者的语义差（等待 vs 生效）恰恰是触发连锁可读性的根，混住即读不懂。
- **道念用双独立数值 / 双独立进度条** — 读得出各自的量，读不出对比。与「主视觉 = 双方道念的**对比**」直接相抵。
- **天平隐喻** — 旋转角与数值不成比例，小屏上 5 点与 15 点的差看起来一样；且它占的是方形面积，横贯屏幕的条在竖屏里更省高度。
- **回合进度与道念差合成一个复合指示** — 需要一个尚未校准的期望产出模型，且替玩家算掉了本作明写的紧张感来源。见「七」。
- **手牌做弧形扇（卡牌旋转）** — full art 的缩略辨识依赖主体正立；旋转后拖拽命中区不规则。
- **敌方渲染牌背扇形表示手牌** — 类型层只给 `HandCount`，画扇形是把一个计数伪装成信息，且白占约 8% 屏高。
- **敌方也给实体牌堆** — 只有计数可用，且会给敌人一个卡背外观位（无付费意义）。
- **在道念差旁附「≈ −N 寿元」的二级换算** — 与「寿元不进战斗屏」已答结的决策直接相抵。
- **「元素上移回收空间」以容纳栈** — 已被明确排除（手牌区跳位不可接受）。
- **横滑作为手牌 / 战场带的翻页手势** — 横滑已是「事件选择 / 角色选择」层级的专用语汇，复用会让两个层级的操作读成同一件事。
- **重新引入任何形式的敌人事前预告以缓解可读性**（含「敌人本回合将打出 N 张牌」这类极简替代） — `ADR-0059` 已整条否决，且极简替代「会重新引入一个需在竖屏常驻的元素」。

## 与既有决策的张力

1. **「栈区保持可见且不被压暗」（选目标态承重条）↔ 栈浮层化。**
   本方案主张**不冲突**：挂起态（D4）必然发生在结算过程中，此时栈层必然在场且必然非空（否则不会有 `PendingTarget`）。但该条的措辞是「栈**区**」，读起来像是在指一个常驻区。
   **需要用户确认的是一个措辞读法**：把它读作「**选目标态期间栈层必然在场，且在该态下豁免压暗**」。若用户认为该条本意就是「栈必须是一个常驻区」，则本方案的第一条建议整条不成立，须回退为常驻窄条（后果：屏高预算表全表重算，约 12–15% 需从别处扣，最可能扣在手牌区或敌方立绘）。
   **松动的代价**：若确认为上述读法，`ux/combat-ux.md` 该句须同改，避免日后读者把浮层化读成漂移。

2. **压缩顺序「先压敌方区 → 再压栈 / 战场（可做浮层而非常驻）→ 双方道念位最后动」↔ 本方案把「栈做浮层」提前为默认形态。**
   既有条文把栈浮层化列为**第二顺位的压缩手段**（即排不下时才用）。本方案主张它**不是压缩妥协，而是语义正确**——常驻一个在玩家可操作时恒空的区，本身就是错的形态，与排不排得下无关。
   **需用户确认是否接受这一重新定性**。若接受，该条须改写为：栈本就是浮层，压缩链上只剩战场带。

3. **`ux/combat-ux.md` 未提及「结束回合」键，本草稿新增了一个常驻部件。**
   它不与任何既有决策冲突（`ActionResult.Kind.EndTurn` 已存在），但它是本方案唯一新增的常驻可交互部件，占底部条约 4% 屏高。若设计意图其实是「mana 耗尽或无可打之牌时自动结束回合」，本项应删除——但那会剥夺「主动留牌 / 留 mana」的合法策略，且撞上「手牌上限是一条会真实咬合的紧约束」（玩家有时必须主动出牌以免撞上限，也就有时必须主动**不**出）。**本草稿按「必须有手动结束回合键」落笔，并在此点名该文档缺口。**

4. **`ux/combat-ux.md` 第 57 条已警告「己方战场区左右两侧同时挂法则条与随身角标会挤压战场可用宽度，须在实际排版时验证」。**
   本方案维持两侧对称落位（不改既定），但把己方战场带的高度定为 12%、两侧挂件各占约 8% 屏宽 ⇒ 战场带净可用宽度约 84%。**这一格必须在实测中验证**；若不足，退让位是把随身角标上移进底部条（它是抽屉入口、不是战场内容），而**不是**动神通 / 法则条（它贴战场是因为 `Power` 就住在战场上）。

## 前置依赖

## 仍需用户决定

### ① 栈是否改为结算期临时浮层（不再常驻）—— 本次专场的核心裁决

这是用户明确排期由专场答疑的那一条根因，且它一旦定下就决定整张屏高预算表，故不由本草稿代拍。

| 选项 | 后果 |
|---|---|
| **A · 浮层化（推荐）** | 释放屏高约 12–15%；手牌 / 战场 / 决策面板全部宽裕；行动阶段看不到空栈容器（无信息损失）；`ux/combat-ux.md` 的「栈区保持可见」与压缩顺序两句须改写措辞 |
| B · 常驻窄条（高约 6%，横向队列） | 栈位置恒定、无出现 / 消失动画；代价是玩家可操作的每一刻它恒为空，且横轴与两条战场带撞轴、更难区分；屏高预算须从手牌区或敌方立绘扣回 6% |
| C · 折中：常驻一个「栈深 N」的极小指示，栈体仍为浮层 | 保留一个恒在的锚点（≈2% 屏高）；但栈深在玩家可操作时恒为 0，该指示的常驻值恒为 0 ⇒ 实为 A 加一个恒零读数 |

**推荐 A。** 依据是纯规则推演（出牌时机 = 行动阶段**且栈为空** ⇒ 玩家能动的每一刻栈必空），不是排版偏好；且既有压缩顺序本就把「栈可做浮层」写为合法手段，本方案只是把它从退让位提升为默认。

→ **已裁决（2026-09-08 · 批量评审）：A · 浮层化。** 屏高预算表按本草稿的推荐值成立。连带定下：`ux/combat-ux.md` 的「栈区保持可见且不被压暗」改写为「选目标态期间栈层必然在场且豁免压暗」；压缩顺序一并改写，「栈可做浮层」由退让位提升为默认形态（本草稿「与既有决策的张力」①②两条随之关闭）。

### ② 敌方立绘在屏高中的分量

纯产品 / 美术基调取向，无客观最优。

| 选项 | 后果 |
|---|---|
| **A · 紧凑半身像（敌方区 20%，推荐）** | 与上表一致；把余量给手牌与战场；符合「敌方区是压缩顺位第一」的既定判断 |
| B · 大立绘（敌方区 28–30%） | 遭遇的压迫感与美术投入（参考三国杀 / 弈仙牌的绘画感）更足；代价是须从战场带或底部条扣回 8–10%，而战场带一旦低于 12% 就装不下满足最小触控目标的条目 |
| C · 立绘作为半透明背景铺满上半屏，不占独立分区 | 零屏高成本、气氛满；代价是与战场带、埋伏角标、战报叠在一起，读数与可辨性下降，且 full art 卡面飞过时背景会干扰识别 |

**推荐 A。** 依据：本作已把敌方区列为压缩顺位第一，且敌人立绘在**战斗前确认页**（一屏全屏、含图鉴词条全文）已有一次充分呈现的机会——战斗屏不必再承担一次美术展示职能。但「这场遭遇有多凶」的体感确实主要由立绘承载，故此项留给用户。

→ **已裁决（2026-09-08 · 批量评审）：A · 紧凑半身像，敌方区 20% 屏高。** 栈浮层化释放的 12–15% 余量全部流向手牌区与己方战场带。
