# 方案草稿 — 主动弃置的发起入口

## 问题

`DefeatReason.Discarded`（主动弃置）自 07-22 起就是终结三因之一，规则侧完整：它走终态判定之外的一条显式旁路，落 `CycleEndScreen` 的 `Discarded` 变体（标题键 `CYCLE_END_TITLE_DISCARDED`、定性文案留空）。**但玩家怎么发起它，全库一个字都没有**——没有入口所在的屏、没有交互形态、没有确认形态、没有调用形状。

它卡住的东西：`DefeatCharacter(Discarded)` 目前是一条**没有调用方**的规则路径。`CycleEndScreen` 的三分之一变体、`chapterRetry` 的一部分记账、以及「某篇章无可挑战角色时重新锁定」的一条触发来源，都挂在这条无人调用的路径上；`/derive-requirements` 无法为它切出任何可验收的行为。

**它不阻塞轮回收尾族两屏**——不论从哪里发起，弃置都经 `DefeatCharacter(Discarded)` 落到同一屏的同一变体（`decisions/ADR-0148-cycle-end-screen.md`）。本方案只答「发起侧」。

## 约束（来自既有设计）

- **终结原因恰三种，`Discarded` 走显式旁路。** 它无对应 `CostKey`、`ResourceElements` 表里没有它的行，不由表驱动 —— `systems/services/life-cycle-service.md`「终结原因恰三种」。
- **状态机只有 `ongoing → completed | defeated`。** 没有 `completed → defeated` 这条转移 —— 同上「状态机」。
- **`defeated` 的既定记账：** 清理该角色数据 · 该篇章重试记账 · `TotalCyclesDefeated +1` —— `program-overview.md` 阶段 5、`ux/screen-flow.md`「轮回结束屏」触发行。
- **「角色 `defeated`」本就在强制 `Immediate` flush 的五项清单内** —— `systems/services/sync-service.md`。`Immediate` 声明的是「不等」，不是「必须成功」；失败进待发队列、不阻塞玩家。
- **主菜单是唯一开局入口**，三道闸（待兑现购买置灰 / 每篇章至多一个 `ongoing` / 篇章解锁门禁）全挂在「开始新轮回」上；不允许出现第二个开局入口 —— `ux/screen-flow.md`、`decisions/ADR-0143`、`ADR-0148`。
- **「哪个角色、哪个篇章」的选择面本就在主菜单侧** —— `ADR-0143`；`program-overview.md` 阶段 3 写作「玩家选『炼气 · 新角色』或『筑基存档角色 · 续章』」。**但该面的完整形态本库未成文**（见「前置依赖」）。
- **设置屏 = 三段 + 一行只读诊断**，且账号级不可逆操作被明令挡在它之外（「账号级不可逆操作会撑破它已定的三段结构」）—— `ux/screen-flow.md`。
- **主菜单入口全是 PlayerProfile 级**（储物袋因含轮回级持有物而不进主菜单）—— 同上。
- **本库只有一种确认语言：就地二段确认，不新开屏、不新增弹层**（解绑 · 储物袋售出 · Exchange 兑换 · 账号注销），且明写「不发明第三种确认语言」—— 同上。
- **全库没有「暂停屏」。** 轮回内的退出是**静默退出、不做二次确认弹窗**，`ct` 只在决策点被观察 —— `systems/services/life-cycle-service.md`「取消语义」。
- **灰态是视觉降级、不是禁用，灰格必须继续接收触控** —— `decisions/ADR-0142`。
- **UI 文案一律走 `res://text/` 键；`MENU_` 分区 / `menu.csv` 覆盖「主菜单、篇章切换」**；本地业务提示不占 `ERR_` 前缀 —— `ux/error-and-blocking-ux.md` 分区表。
- **`DefeatCharacter` 现签名为 `OpResult DefeatCharacter(DefeatReason reason)`**，无 `characterId`；`TryGetActiveCharacter` 明写「主菜单无进行中轮回是正常态」—— `systems/services/life-cycle-service.md` 契约表。

## 建议方案

### 1. 入口落在主菜单「切换篇章」面上，挂在该篇章那一行 `ongoing` 角色旁

`[既有推演]`

**推演链：** 弃置在规则上唯一能达成的效果，是把一个 `ongoing` 角色变成 `defeated`，从而**释放「每篇章至多一个 `ongoing`」这道闸**（角色数据本就会随轮回结束被清理，弃置不额外省下任何东西）。而那道闸恰恰挂在主菜单「开始新轮回」上 ⇒ **玩家读到「这一章被占着」的那一处，就该是他解除它的那一处**。入口与闸同屏，零跳转、零心智落差。

**形态（不新增屏、不新增主菜单入口）：** 篇章切换面上，每个篇章**至多一行** `ongoing` 角色（「每篇章至多一个 `ongoing`」保证了这一点）⇒ 全游戏至多三行，不构成一份需要滚动或筛选的列表。弃置是这一行上的一个**次级动作**，与该行的主动作「继续」并列。

**本方案不规定该选择面的其余部分。** 它的完整形态本库未成文（见「前置依赖」），本方案只规定「弃置键挂在它的 `ongoing` 行上、形态如下」——不臆造一份角色管理屏，也不臆造该行还应显示什么。

### 2. 不在轮回内设第二个入口（推荐项，属取向 → 见「仍需用户决定 ①」）

`[取向选择]`

推荐**不设**。三条理由，其中第一条是工程性的：

- **轮回内发起在实现上必须先走一遍退出路径。** `ct` 只在决策点被观察，而弃置要在一个没有进行中的 `AdvanceEventAsync` 的时刻提交事务。轮回内入口因此等于「取消到最近决策点 → `Immediate` flush → 弃置」，与「退出到主菜单再弃置」是**同一条链**，多的只是省玩家一次点击。对照被动死亡：寿元归 0 是 `eventEnd` 终态判定 ② 内的一步，本来就在事务里；主动弃置没有这个位置可站。
- **没有承载它的屏。** 全库无暂停屏；设置屏已被明令排除（三段结构 + 无角色上下文）；轮回内退出是静默退出，为弃置在它上面加一次确认会推翻那条既定手感。
- **它没有解决任何新问题。** 想弃置的玩家的下一步动作恒是「换个角色 / 换个篇章重开」，而那一步只能在主菜单发生。

代价（如实写）：玩家在轮回内认定这局没救时，要多一次「退出 → 主菜单」才能弃置。

### 3. 可弃置对象 = 仅 `ongoing` 角色（推荐项，属取向 → 见「仍需用户决定 ②」）

`[取向选择]`

推荐**只对 `ongoing` 开放**。`completed` 的可挑战角色不提供弃置：状态机没有 `completed → defeated` 这条转移；且可挑战角色不占任何闸、不阻塞任何东西，弃置它没有可达成的效果，只有「误删一个存档角色」这一种后果。

### 4. 就地二段确认，不新开屏、不新增弹层

`[既有推演]` + `[通行做法]`

弃置不可逆且损失一个完整角色 ⇒ 值一次确认（不可逆动作要二次确认是通行做法）。形态**逐字复用本库既有的唯一确认语言**：第一段「弃置」→ 就地在该行内展开第二段（一行后果 + 「确认弃置」），与解绑 / 售出 / 兑换 / 注销同款，**不发明第三种确认语言**。

**第二段的一行后果必须含三项事实：** 角色名 · 弃置之后该篇章的**剩余重试次数** · 不可撤销。理由：这是玩家做这个决定唯一需要的事实（与轮回结束屏「剩余重试行不是推销面、玩家要决定下一步」同一条判据）。ch1 上限为无限 ⇒ 走**另一条不含次数的说明键**，**不显示一个假的大数**（与 `CycleEndScreen` 剩余重试行同口径）。剩余次数取「记账之后」的值，与 `CycleEndScreen` 同口径，本方案不新增记账口径。

**弃置键恒可用、不置灰**：重试次数已耗尽不构成拒绝（角色照常终结，该篇章随后按既定判定重新锁定）；待兑现购买的置灰只挂「开始新轮回」，弃置不开局、不进付费流程、不要求待发队列为空 ⇒ **不新增拦截点**。

### 5. 无冷静期、无撤销通道

`[既有推演]`

冷静期在这里**自相矛盾**：冷静期内角色仍是 `ongoing` ⇒ 闸仍占着 ⇒ 弃置在整个冷静期内什么都没做成，而它的**全部目的**就是释放那道闸。此外它要新增一个持久字段 + `schemaVersion` bump + 一个撤销入口 + 「冷静期内能不能继续这个角色」的新口径。

**与账号注销的冷静期不对称，判据清楚：** 注销由后端定义（天数与生效时刻一律取自应答）、损失的是账号本身、且发生在一条玩家可能被误导进入的合规流程里；弃置是纯本地、单角色、玩家为解除自己遇到的阻塞而主动发起。误触的兜底由二段确认 + 明写后果承担，与「解绑」同级。

### 6. 触控与竖屏形态

`[既有推演]`

- 次级「弃置」按钮**常驻可见**（不是滑动删除、不是长按菜单）：破坏性动作藏在手势后是隐藏可供性；且横滑已是角色选择与 eventOptions 的语汇，在篇章行上复用会让两个层级的操作读成同一件事（与 Exchange 屏「不做横滑」同判据）。**零 hover 通道。**
- 该行与两段按钮**各自满足触控目标尺寸下限**；主动作「继续」与次级「弃置」在视觉层级上分开（次级按钮弱化色 / 描边，不与主按钮同重），降低误触；第二段展开后「确认弃置」不与「继续」重叠落位。
- 全部落在安全区内；篇章行区可纵向滚动时，展开的第二段随行滚动、不做浮层固定。

### 7. 调用点、签名与时序

`[既有推演]`

**签名扩一格：`OpResult DefeatCharacter(DefeatReason reason, string characterId)`。** 现签名隐含「当前角色」，而主菜单侧恒无 active（`TryGetActiveCharacter` 的可选缺失在主菜单是正常态）。规则侧两个既有调用点（终态判定的表驱动一路、Finale 旁路一路）传当前角色 `Id`。**不加重载、不加可空默认值**——两个入口名会各自漂移出一份记账。

**时序（一次事务、零新增存档点、零新增字段、零 `schemaVersion` bump、后端零配合）：**

```
玩家按下第二段「确认弃置」
  → life-cycle-service.DefeatCharacter(DefeatReason.Discarded, characterId)
      ① 在清理之前组装既定的只读结束摘要
         （境界 + 篇章 · pastEvent.Count · Status.lifeSpan · DefeatReason · RetriesLeft）
      ② 一次 ProfileChangeSpec → ProfileManager.TryApply
         （status = defeated · 该篇章重试记账 · TotalCyclesDefeated +1）→ 一次本地原子写
      ③ sync-service.Push(reason, PushPolicy.Immediate)
         ——「角色 defeated」本就在强制立即 flush 五项内，不新增 flush 点；
            失败照既定进待发队列、不阻塞、由常驻同步指示告知
      ④ 角色数据清理（时点一格不动，摘要已在 ① 取走）
  → CycleEndScreen（Discarded 变体：CYCLE_END_TITLE_DISCARDED + 定性文案留空）
  → 玩家按「返回主菜单」→ 成就结算 → 回主菜单
```

- **`TeardownCycle()` 在主菜单发起时是空操作**（没有进行中的轮回场景可拆：无实例化节点、无待断信号）。这是主菜单入口与轮回内入口在实现上的**唯一**结构差别——也是「轮回内入口 = 退出路径 + 弃置」这条等式的另一面。
- **「无可挑战 / 可重试角色 ⇒ 该篇章重新锁定（隐藏）」的既定判定照跑**，不为弃置另写一条。已知后果：弃置该篇章唯一的角色后，该篇章会在同一次返回主菜单时从篇章切换面上消失——这是既定语义（解锁是动态状态），不是本方案新增的行为。
- **`CycleEndScreen` 从主菜单升起时语义仍成立**：该屏「不进屏幕栈、无返回路径、出路只有『返回主菜单』」，从主菜单进、回主菜单出，屏清单一格不动。

### 8. 文案与翻译键

`[既有推演]`

框架文案全部走 **`MENU_` 分区 / `menu.csv`**（分区表已写明它覆盖「主菜单、篇章切换」）⇒ **不新开分区**。**不占 `ERR_` 前缀**（本地业务提示，没有后端 `code`）；此路径不产生 `ERR_*` 键。角色名是内容层 `LocalizedText`（`CharacterData` 显示名），由呈现层作**格式参数**插入，**一个字不进 `menu.csv`**。

## 备选方案（已考虑并否决）

- **入口放设置屏** — 否决：`ux/screen-flow.md` 已明令设置屏 = 三段 + 一行只读诊断，账号级 / 不可逆操作会撑破它已定的三段结构；且设置屏没有角色上下文（它在轮回内外是同一屏）。
- **入口放 PlayerProfile 屏** — 否决：主菜单入口全是 PlayerProfile 级，而角色是轮回级对象——与「储物袋含轮回级持有物 ⇒ 不进主菜单」同一条判据。
- **新开一屏「角色管理」** — 否决：至多三行的东西不值一屏，且要把篇章解锁门禁的呈现复制一份（两份必然漂移）。
- **冷静期 + 撤销通道** — 否决：见 §5（冷静期内闸仍占着，功能在冷静期内等于没做）。
- **输入角色名以确认（重度确认）** — 否决：本库无此确认语言，移动端打字成本高，而二段确认 + 明写三项后果已把误触挡住；重度确认留给账号级（那里已有冷静期兜底）。
- **滑动删除手势 / 长按菜单** — 否决：隐藏可供性，且横滑是选择面的语汇，复用会让两个层级的操作读成同一件事。
- **弃置不消耗重试次数（做成免费逃生门）** — 否决：`defeated` 的记账是既定的，为 `Discarded` 开特例等于给 ch2 / ch3 一条绕过重试上限的通道（把一局必输的轮回弃置掉、不计数地重来），而重试上限是本作的核心稀缺（`ADR-0004`）。
- **在 `CycleEndScreen` 上放弃置入口** — 否决：该屏出现在角色**已经**终结之后，此处无可弃置对象。

## 与既有决策的张力

- **`DefeatCharacter` 的签名。** `systems/services/life-cycle-service.md` 契约表现写 `OpResult DefeatCharacter(DefeatReason reason)`（隐含「当前角色」）。本方案需要它多一格 `characterId`。**它未进任何 ADR**，故不是 ADR 级冲突，但它是已成文契约 ⇒ 明写。**不松动时的替代：** 主菜单侧先把目标角色设为 active（Hydrate 一次）再调用——**否决**，那是为一次销毁做一次完整水合，且会让「当前角色」在主菜单出现一个只为删除而存在的瞬时态，撞「主菜单无进行中轮回是正常态」。
- **术语碰撞：「弃置」一词已被功法弃置占用**（`terminology.md` 功法行、`ADR-0055`「绑定功法可弃置」、Research 的 `ForgetTechnique`）。角色侧与卡组侧同词不同物，玩家在同一局里会两处都读到。**建议**：角色侧的中文措辞与功法面区分（如「放弃此角色」），并在 `terminology.md` 记一行；**键名与结构不受影响**（`MENU_DISCARD*` 与 `DefeatReason.Discarded` 照旧）。措辞本身属落笔时的文案层一格，本方案不替它拍板。

## 前置依赖

- **主菜单「切换篇章」面的完整形态本库未成文。** `program-overview.md` 阶段 3 与 `ADR-0143` 都断言「哪个角色、哪个篇章的选择面本就在主菜单侧」，但 `ux/screen-flow.md` 只写了主菜单入口按钮表与 ch1 的角色选择屏，**没有写这个面本身**。本方案只规定「弃置键挂在它的 `ongoing` 行上」；该行的其余版式（是否显示事件数 / 缩略像 / 寿元）随该面成文时定。**不阻塞**——弃置的语义、确认形态、调用时序与翻译键均不依赖该版式。
- **`completed` 是否清理角色数据**（同分片 09-05 新增的待答项）。若最终收口为「`completed` 不清理」，则可挑战角色是长期存活对象，「仍需用户决定 ②」（是否允许弃置 `completed` 角色）的分量会上升。**不阻塞推荐项**（推荐项只对 `ongoing` 开放，两种读法下都成立）。

## 仍需用户决定

### ① 是否在轮回内也设一个弃置入口

- **A（推荐）· 只在主菜单。** 轮回内不设任何弃置入口；玩家在轮回内想弃置 ⇒ 先按既有的静默退出回主菜单，再在篇章行上弃置。
  **后果：** 零新增屏、零新增确认形态、不推翻「轮回内退出是静默退出、不加二次确认」这条既定手感；实现上只有一条路径。**代价**：认定这局没救的玩家多一次「退出」点击。
- **B · 轮回内再加一处。** 需要为它指定一个承载屏——本库既无暂停屏，设置屏又被明令排除 ⇒ **B 实际意味着先新增一个暂停 / 轮回菜单屏**。
  **后果：** 新增一屏 + 一处确认 + 一条与主菜单侧并行的调用路径（两条路径的记账与摘要组装必然要各写一次或强行共用）；且它在实现上仍要先走取消到决策点，收益仅为省一次点击。
- **推荐 A 的理由：** 弃置的下一步动作恒在主菜单（换角色 / 换篇章重开），入口与那一步同屏；B 的全部收益是一次点击，成本是一屏 + 一条并行路径。
- **→ 已裁决（2026-09-06 · 批量评审）：选 A —— 只在主菜单设弃置入口，轮回内不设第二处。**

### ② 是否允许弃置 `completed` 的可挑战角色

- **A（推荐）· 只允许弃置 `ongoing`。**
  **后果：** 状态机一格不动（无需新增 `completed → defeated` 转移）；可挑战角色只能通过「用它开下一篇章并失败 / 弃置」退出。**代价**：玩家攒下一堆再也不想玩的存档角色时，没有清理通道（但它们不占任何闸、不阻塞任何东西，只是列表变长——而每篇章至多一个可挑战角色行的前提下，列表长度有天然上界）。
- **B · 也允许弃置 `completed`。**
  **后果：** 需要新增 `completed → defeated` 转移（改状态机，是本方案里唯一会动机制形状的一项）；并要回答「弃置一个 `completed` 角色是否也消耗重试次数」（它还没开始那一章，扣什么次数？）——这条问不出干净答案本身就是 A 的一条证据。
- **推荐 A 的理由：** B 要改状态机、且引出一个没有自然答案的记账问题，换来的只是一条「整理列表」的便利。
- **→ 已裁决（2026-09-06 · 批量评审）：选 A —— 只允许弃置 `ongoing` 角色，不新增 `completed → defeated` 转移。**
  裁决时用户已被告知两条**新前提**（来自同批 `solution-draft-completed-data-retention.md` 的裁决，它们本使天平偏向 B）：① ch3 `completed` 档**永久保留完整档** ⇒ 通关档会长期堆积；② 续章存档取「单记录 + 起始快照」⇒ `completed → ongoing` 已是合法转移，「终态收敛」不再能作为反对 `completed → defeated` 的理由。用户在此前提下仍选 A。
  **被接受的代价（须在落笔时如实写进主题文档）：** 已通关角色档没有任何清理通道，会随游玩时长在主菜单篇章切换面上持续累积。
