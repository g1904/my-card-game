# 方案草稿 — 昵称审核 · 存量扫描 · 风控落地

## 问题

三条待答项共用同一个挂接点 `account.status`（`active` · `restricted` · `banned` · `pendingDeletion`），必须一起答，否则会各立一套「是否可玩」的真值。

1. **敏感词词表与审核口径。** `auth.nickname_rejected.detail.reasonKey` 的取值表已封定（`contracts/auth.md` §10 三值：`SensitiveWord` · `TooFrequent` · `Malformed`），但 `SensitiveWord` 的**判定输入**是空的——词表来源、审核口径分级、是否叠加第三方审核。**它直接卡着 `POST /v1/auth/nickname` 的验收断言**：判定链未定，「什么输入应当返回 `SensitiveWord`」写不出来。
2. **未过审昵称的存量扫描。** 改名端点只判定「这一次提交」，而昵称的写入方是客户端（`contracts/auth.md` §8 已如实记下改包可绕过的代价）。扫描的触发形态、频率与处置（改写 / 置空 / 标 `restricted`）待定。
3. **风控与滥用面。** 处置口径已定（复算不一致 → **接受写入 + 打一条结构化风控事件，不拒绝、不改写**，`contracts/profile-sync.md` §7a），且有一条已知残留通道（`lastEffectiveChance` 后端无法验真）。仍待定：是否建风控系统 · 风控事件的字段与落地形态 · 累计到什么程度算异常 · 异常账号如何处置。从属项：三档处置向玩家的可见粒度。

## 约束（来自既有设计）

- **`reasonKey` 三值已封定、形态锁死 PascalCase**，客户端二级文案键由 `code` + `reasonKey` 机械变换；未知取值退回一级键，**新增取值不要求客户端同批发版**。→ `contracts/auth.md` §10、`decisions/ADR-0015`、`contracts/envelope.md` §5b。
- **`POST /v1/auth/nickname` 只判定、不写 profile**；`/accountInfo/nickname` 是**透明只读**路径，写入方是客户端。→ `contracts/auth.md` §8、`contracts/profile-sync.md` §5。
- **后端写入字段表封闭（四行），措辞是例外式而非列举式**，扩表是破坏性契约变更；且**扩表即自动进入 §5c 回声约束**（恒等式）。→ `contracts/profile-sync.md` §5 §5c、`decisions/ADR-0008`。
- **客户端有权写的路径越界 → 记账 + 风控事件，不拒绝、不改写**（判据是所有权，不是严格程度）。→ `contracts/profile-sync.md` §7a、`decisions/ADR-0005`。
- **`compliance.*` 不打到同步通道**，合规拦截只在 `signin`。→ `contracts/profile-sync.md` §11、`contracts/auth.md` §5a。
- **`account.status` 不跨边界**；`restricted` / `banned` 共用 `compliance.account_restricted`，靠 `reasonKey` 分辨；客户端处置 = 阻塞屏 + **申诉走站外，不占端点**。→ `contracts/auth.md` §1a、`contracts/compliance.md` §5、`contracts/envelope.md` §6。
- **`status` 变更连带吊销全部会话**，下行 `auth.session_revoked` + `reasonKey = "OperatorRevoked"`。→ `contracts/auth.md` §10。
- **零判定权字段的取值清单不是校验闸**：未知取值记录原值、不改写、不拒收，清单增量不 bump 契约版本。→ `decisions/ADR-0017`。
- **规则集不可变版本化**（O1–O7：无原地编辑路径 · 单调版本号 · 回滚 = 以历史内容发起新版本 · 留痕四项 · 历史永久保留）。→ `operations/_index.md`、`decisions/ADR-0009`。
- **可调旋钮落后端配置而非代码常量**；契约层只声明语义，实现与实际阈值归 `06`。→ `contracts/auth.md` §8、`contracts/profile-sync.md` §12。
- **只有三个后端服务**（`account` · `profile-store` · `content-delivery`），对位三个跨边界的客户端成分。→ `systems/_index.md`。
- pillar #1 后端不重跑玩法 · pillar #4 不阻塞玩家 · pillar #5 线上可干预（改数值 / 关条目不发版）。→ `vision/pillars.md`。
- 客户端侧硬前提（**本库不复述**）：昵称合法性不由客户端判定、客户端只做长度与空白约束、判定通过后由客户端写 `AccountInfo.Nickname` 走既有 push。→ `game-design-documents/systems/services/account-service.md`。

## 建议方案

### A. 昵称判定链：四级短路，顺序即语义

`[既有推演]` `[通行做法]`

`POST /v1/auth/nickname` 的判定是**同步、即时、幂等**的（auth 域纪律），四级短路求值，**第一个失败级决定 `reasonKey`**：

```
① 形态校验（本地 · 确定性）        失败 → auth.nickname_rejected { reasonKey: "Malformed" }
② 频次校验（本地 · 计数）          失败 → auth.nickname_rejected { reasonKey: "TooFrequent" }
③ 词表判定（本地 · 版本化配置）    命中「禁止级」→ auth.nickname_rejected { reasonKey: "SensitiveWord" }
                                   命中「复核级」→ 落 ⑤
④ 第三方审核适配器（可选 · 外接）  判「拒绝」→ SensitiveWord ；判「待复核」→ 落 ⑤ ；不可达 → 见下
⑤ 接受                            204，并按需入复核队列（accept-then-review）
```

**四条承重的顺序 / 口径决定：**

- **短路顺序固定为 ①→②→③→④，不可颠倒。** 它使「既超长又含敏感词」这类输入的应答唯一（`Malformed`），验收断言因此无歧义；同时把唯一有外部成本的一级（④）放在最后，被频次闸挡住的刷子不产生外部调用。
- **频次计数只对「被接受的一次改名」`+1`。** 若拒绝也计数，一个玩家试错三次就把自己锁死在 `TooFrequent` 上，而他一次都没有改成。与「幂等重复提交同一昵称回 `204`」（`auth.md` §7）配套：**重放不消耗配额**。
- **④ 不可达时的降级 = 按「待复核」处理并接受（`204`）**，不返回错误。理由与 `auth.md` §3a「渠道不可达 ≠ 明确拒绝」同源：把外部服务抖动报成 `SensitiveWord`（`Fatal`）会让玩家以为自己的昵称违规；而昵称**零玩家间可见性**（`auth.md` §8 已论证），先接受的风险窗口成本极低，复核队列会兜住它。
- **判定输入是归一化串，`Malformed` 判定用原串。** 匹配前对提交串做：NFKC 规范化 → 剥离零宽 / 控制 / 变体选择符 → 大小写折叠 → 繁简折叠 →（可选）同形字与拼音变体折叠。**长度与字符集判定必须在原串上做**，否则玩家看到的字数与服务端判定的字数不一致。不做归一化即等于把词表变成摆设——插一个零宽空格就绕过，这是最通行的规避手法。

### B. 「待复核」不进报文：accept-then-review

`[既有推演]`

三值 `reasonKey` 表已封定，其中没有「待审」；而给它加一个取值意味着：端点从**即时判定**变成一台**长时状态机**——而 `contracts/compliance.md` §1 正是以「长时状态机 vs 即时幂等判定」这条相反纪律把合规域从 auth 域拆出去的。把待审塞回 auth 域，等于当场推翻那次拆分的判据。

**因此：复核级一律先接受（`204`），昵称照常由客户端 push 写入，后台把它排进复核队列；复核判违规 → 走 §D 的存量扫描处置通道。** 这条同时把问题 1 与问题 2 缝在一起——**复核队列与存量扫描是同一条处置通道的两个入口**，不是两套机制。

### C. 词表：后端配置 · 不可变版本化 · 两档分级

`[既有推演]` `[通行做法]`

- **词表是后端配置数据，不是代码常量，不下发客户端、不进任何报文。** 前半承 `auth.md` §8 的旋钮纪律与 pillar #5（补一句禁词不该发版）；后半承 `channelUserId` / `sid` / `status` 那条「服务端内部键不跨边界」，且客户端自带一份词表就是第二权威（`auth.md` §8 已否决）。
- **词表发布形态逐条复用 flags 规则集的 O1–O7**（`operations/_index.md`，`ADR-0009`）：每次发布产出新版本 · 既有版本只读、**不存在原地编辑路径** · 版本号单一分配点且单调 · 回滚 = 以历史内容发起更大版本 · 留痕四项（操作者 / 时间 / `derivedFrom` / 变更摘要）· 历史永久保留。
  **不是「顺手抄一套」：存量扫描必须能回答「这个昵称当初是按哪一版词表放行的」**，而「随手改一下数据源」正是 O1 要堵的那个静默失效模式。词表体积与 flags 同量级，永久保留成本近似为零。
- **两档分级**，与判定链一一对应：

  | 档 | 判定 | 应答 | 后续 |
  |---|---|---|---|
  | **禁止级** | 政治 / 涉恐 / 色情 / 极端辱骂等无争议违禁 | `SensitiveWord`（`Fatal`） | 无 |
  | **复核级** | 擦边、谐音变体、疑似冒充官方 / 客服 | `204` | 入复核队列（§B） |

  两档而非三档：**「放行」不是一档，是补集**——与「白名单的补集即不透明段」（`profile-sync.md` §5）同一条措辞纪律，避免第三份清单漂移。
- **词表来源三条通道**：① 监管 / 行业公开基础表导入为初始基线；② 人工复核队列的判定结果回灌（复核判违规的词进禁止级或复核级）；③ 渠道过审反馈与工单。三条都收敛到**同一次发布动作**，不存在旁路写入。

### D. 是否接第三方审核

`[既有推演]`（服务商与阈值归 `06`，本节只定**要不要留这一级、以什么形态留**）

**建议：首版不启用第三方，但判定链 ④ 这一级的适配器位必须先留出，实现为透传（恒「放行」）。**

- 「C 层原子能力一律外接、以适配器隔离使服务商可换」已是既定纪律（`auth.md` §1a / `06`），本级天然属于 C 层，形态无须新议。
- 昵称**零玩家间可见性**（单人游戏、无排行榜 / 分享）⇒ 敏感词的唯一驱动是**合规抽查**，不是社区治理。本地词表 + 归一化已覆盖抽查关注的那一类。
- 改名是低频动作，但第三方每次调用有成本与延迟，且它引入一个新的外部不可达面（已由 ④ 的降级语义兜住）。
- **留位的代价近乎为零、补位的代价是一次判定链改造**：过审受阻时能当场换实现，而不是当场改流程。
- **首版是否启用**取决于「合规能力的上线分级」（归 `02`，**不在本草稿范围**）与渠道过审要求 → 见 `## 前置依赖`。

### E. 存量扫描：三个触发源，事件驱动是主力

`[既有推演]`

**扫描范围恒为单字段 `/accountInfo/nickname`**——它已在透明白名单内、后端有权读（`profile-sync.md` §5），后端不解不透明段（pillar #1）。

| # | 触发 | 覆盖面 | 频率 |
|---|---|---|---|
| **T1** | **push 事件驱动**：`playerDiff` 含 `accountInfo` 顶层键 | 全部活跃改名 | 每次（零额外成本） |
| **T2** | **词表版本更新驱动**：新词表版本发布后 | `reviewedWordlistVersion < 新版本` 的账号 | 每次发布一轮 |
| **T3** | **定期兜底全量** | 全部账号 | **30 天 / 轮**（初值，待校准） |

- **T1 是抓 `auth.md` §8 那条残留通道的确定性手段，不是抽查。** 后端本就要按 §3a 解 `playerDiff` 的顶层键，比对「本次提交的 `nickname`」与「该账号最近一次经端点接受的昵称」：**不等 ⇒ 该账号绕过了改名端点**。改包路径因此**必然被检出**，只是检出时刻推迟到下一次 push。这把「存量扫描」从概率性抽查升级为确定性检出，而成本是一次字符串比较。
  `/accountInfo/nickname` **明确不受 §5c 回声校验约束**（恒等式：它不在后端写入表，客户端有权写它）⇒ **T1 只记账 + 判定，绝不拒绝上行、绝不改写**，与 §7a 逐字同构。在 push 上拒绝会同时撞 §11、§7a 与 pillar #4。
- **T2 的增量面是明确的**，正因为词表不可变版本化（§C）：每个账号记着「上次按哪一版词表通过」，新版本发布后只需重扫落后的那批。**没有 §C 的版本化，T2 只能退化为每次发布跑一次全量。**
- **T3 的 30 天初值推导**：它只兜 T1 / T2 的实现缺陷与边角（长期不上行、不改名的沉睡账号），不是主力；30 天与 `pushId` 保留期 / refresh 滑动 TTL 同量级，使三处窗口不互相穿帮；合规抽查本身是月度节奏。它是纯离线批处理、可错峰。**待实测校准。**
- **扫描台账落后端内部存储，不进 profile。** 字段：`accountId` · `lastAcceptedNickname` · `acceptedAtUtc` · `reviewedWordlistVersion` · `reviewState` · `lastScannedAtUtc`。不进 profile 的理由与 `sid` / 会话记录同源——它是后端内部状态，且 §5 写入表封闭。

### F. 处置：改写与置空**明确否决**，只落 `status`

`[既有推演]`——三选一里的两个由既有决策直接封死，这不是取向。

**后端改写 / 置空 `/accountInfo/nickname` 明确否决**，两条独立的理由各自足够：

1. 它不在**封闭的**后端写入字段表内，且 `profile-sync.md` §5 把它逐字点名为「**反例一**」（真值是玩家输入的，第 ① 条判据即不满足）。要改写就得扩表，而扩表须显式引用护栏、逐条通过判据——它通不过。
2. 更致命的是**扩表的连带**：由 §5c 的恒等式，**进写入表 ⇒ 自动进回声约束**。届时客户端每次改昵称提交 `accountInfo` 顶层键，都会回声一个「后端改写过、客户端不知情」的值 ⇒ 回声失败 ⇒ **整批拒绝 ⇒ 玩家丢一次本地缓冲**。症状是「所有被改过名的玩家每次改名都丢一次进度」。

**因此处置只能落在 `account.status` 上**——这也正是 `02` 抬头那句「三条共用同一个挂接点」的兑现。两条候选主线：

| | **P1 · 零契约新增** | **P2 · 可登录先改名**（推荐） |
|---|---|---|
| 处置 | 直接 `status = restricted` | `status` 不变；在 `GET /v1/compliance/status` 的应答中带一项「须改名」标记 |
| 玩家体验 | `signin` 被拦 → 阻塞屏 + **站外申诉** | 正常登录 → 进入游戏前强制走一次改名流程 |
| 出路 | **无自助出路**（见下） | 改一个合规昵称即解除 |
| 契约成本 | 0（可能扩一个 `reasonKey`） | `compliance.md` 六端点报文字段表**本就未落笔**，加一项即可 |
| 跨库成本 | 0 | 需客户端侧配套呈现（归客户端库） |

> **P1 的死锁是真实的，必须写明。** `restricted` 拦在 `signin` ⇒ 玩家进不去 ⇒ 改不了昵称（昵称的写入方是客户端，须登录后 push）⇒ 永久 `restricted`。既有设计给出的唯一出口是**站外申诉**（`envelope.md` §6 已定）+ 运营带外处理。**自助解除路径在既有分工下不成立**——即便给 `POST /v1/auth/nickname` 开一个 `complianceTicket` 无鉴权入口（`compliance.md` §3 的第三处签发），该端点也**只判定不写 profile**，玩家仍然改不了。这条推演本身回指了 `auth.md` §8「昵称由客户端写入」那次判断的代价。

**推荐 P2**，四条依据：pillar #4 不阻塞玩家 · `envelope.md` §7b「仅两处硬阻塞」· 昵称零玩家间可见性 ⇒ 把玩家整个挡在门外与危害不成比例 · P2 的承载点（`compliance/status` 字段表）**本就在待落笔清单上**，采纳它不推翻任何已定条款。**`restricted` 在 P2 下不废弃**，降为升级档：拒不改名 / 恶意反复 → `restricted`。**这条是取向（见 `## 仍需用户决定` 第 1 条）。**

**处置阶梯（两条主线共用）：**

| 档 | 判据 | `status` | 玩家可见 |
|---|---|---|---|
| **观察** | 复核级命中；T1 首次检出绕过写入 | 不变（`active`） | **无** |
| **改名 / 限制** | 禁止级命中；复核判违规 | P2：不变 + 须改名标记 · P1：`restricted` | P2：改名流程 · P1：`compliance.account_restricted` + `UnderReview` + 站外申诉 |
| **封禁** | 恶意反复；申诉驳回 | `banned` | `compliance.account_restricted` + `Banned` |

`status` 变更连带吊销全部会话、下行 `reasonKey = "OperatorRevoked"`（`auth.md` §10 已定，**不新增任何机制**）。

### G. 是否建独立风控系统

`[取向选择]` —— 见 `## 仍需用户决定` 第 2 条。**推荐「轻量档」**：事件流 + 规则化累计计数 + 阈值生成工单，**处置须人工确认才动 `status`**。

**组织形态上它不是第四个服务。** `systems/_index.md` 已定「只有三个后端服务，对位三个跨边界的客户端成分」，而风控不跨边界、无客户端对位。建议落点：**事件产出**在 `account` / `profile-store` 内部（旁路，不在热路径）；**聚合、阈值与处置流程**落 `operations/`（与 `06` 已登记的可观测性同处）。

### H. 风控事件：一张统一的字段表

`[既有推演]` —— **不是取向**：`profile-sync.md` §5c 与 §7a 已各自具名了一半字段，需要的是一个能同时装下两者的形状，而不是两套。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `eventId` | string | ✅ | 事件唯一 id；去重与工单关联的键 |
| `occurredAtUtc` | string (RFC 3339 UTC) | ✅ | `AtUtc` 后缀（`envelope.md` §2） |
| `accountId` | string | ✅ | — |
| `kind` | string enum (PascalCase) | ✅ | 事件类别，取值见下 |
| `severity` | string enum (PascalCase) | ✅ | `Info` \| `Warn` \| `Critical` |
| `subject` | string | 可选 | 被判定对象的定位串：JSON path（`/entitlement/bundleGrantOrdinal`）或字段名 |
| `expected` | string | 可选 | 期望值。**一律字符串序列化**——取值域跨类型，且 `ulong` 类的值超 2⁵³ 会静默丢低位（`envelope.md` §2 判据） |
| `actual` | string | 可选 | 实收值，同上 |
| `requestId` | string | 可选 | 回显 `X-Request-Id`，把两侧日志接起来（`envelope.md` §5） |
| `deviceId` | string | 可选 | **只作观测维度，永不参与判定的可信输入**（`auth.md` §4a 逐字同构：它是客户端自报可伪造值） |
| `appVersion` · `contentVersion` | string | 可选 | 取自请求头；**熔断判据的分组维度**（见 §I） |
| `context` | object | 可选 | 按 `kind` 取固定形状的补充（同 `detail` 按 `code` 定形的纪律） |

**`kind` 取值（PascalCase · 清单可增量 · 未知取值不驱动判定，同 `ADR-0017`）：**

| `kind` | 来源 | `subject` / `context` |
|---|---|---|
| `RollMismatch` | `profile-sync.md` §7 校验① | `context: { finaleWinOrdinal }` |
| `ChanceInconsistent` | §7 校验②（谎报命中） | 同上 |
| `InvariantViolated` | §7 校验③；含 `bundleRedeemedOrdinal > bundleGrantOrdinal`（§5c 服务端保证末行） | `subject` = 违规 path |
| `EchoRejected` | §5c 回声校验不通过 | `subject` = 违规 path，`context: { cloudRevision }` |
| `NicknameBypassed` | T1 检出绕过改名端点写入 | `context: { wordlistVersion }` |
| `NicknameViolation` | 存量扫描 / 复核判定违规 | 同上 |
| `RevisionAhead` | `sync.revision_ahead`（后端自己的回滚信号） | `context: { cloudRevision }` |
| `RateLimitTripped` | 滥用阈值触发 | `context: { window, count }` |

**四条落地纪律：**

- **只追加的事件流**：条目永不改写、永不单条删除；到期整体过期。
- **绝不在同步热路径上裁决**（`profile-sync.md` §7a 逐字）：事件写入是旁路，push 的应答不等待它落盘。
- **不进 profile**（后端内部状态；§5 写入表封闭）。
- **`06` 的三条线上探针由本事件流聚合得出，不另建第二条采集路径。**「复算不一致率」= `RollMismatch` 的发生率、「本地领先」= `RevisionAhead`——两条采集路径必然漂移，而漂移时没有任何机制会报错。
- 保留期初值 **180 天**（推导：须覆盖两倍于最长累计窗口（90 天），使窗口滑动时历史完整；含可关联到个人的行为数据 ⇒ 不宜永久，与导出产物 7 天 / `receiptId` 永久是三种不同的取舍轴）。**待校准。**

### I. 累计阈值：按 `kind` 分档 + 一条全局熔断

`[既有推演]` `[通行做法]` —— **一律写成可配置阈值，落后端配置而非代码常量**（`auth.md` §8 纪律）。

| `kind` | 观察阈值 | 升级阈值 | 推导 |
|---|---|---|---|
| `RollMismatch` · `ChanceInconsistent` · `InvariantViolated` | **≥1 次 / 90 天** | **≥3 次 / 90 天** 且 **≥2 个不同 `finaleWinOrdinal`** | 正常账号的期望值是 **0**（复算是确定性纯函数）。但迁移期 / 实现差一位会产生噪声，故不能一次即封。Finale 每篇章至多一次、共三篇章 ⇒ 一个轮回周期最多 3 次机会；3 次全不一致远超任何噪声解释。90 天 ≈ 一个内容大版本周期 |
| `EchoRejected` | **≥3 次 / 7 天** | **≥10 次 / 7 天** | 正常客户端**零误报**（§5c 明写判据是所有权）⇒ 阈值可更紧、窗口可更短 |
| `NicknameBypassed` | **≥1 次即进复核** | 无累计档 | 它是**确定性检出**而非概率信号（§E T1），累计计数对它无意义 |
| `NicknameViolation` | ≥1 次 → 改名 / 限制档 | ≥3 次 / 180 天 → 封禁档 | 反复取违规昵称是意图信号，而非失误 |

> **⚠ 全局熔断（承重）：同一 `appVersion` / `contentVersion` 分组内，`RollMismatch` 触发率 > **1%** 账号，或 `EchoRejected` > **0.5%** 账号 ⇒ **一律判为我方实现缺陷，立即暂停该分组的一切自动处置并告警。**
>
> 它防的正是最坏那一类事故：后端复算差一位 / 客户端一次发版 bug ⇒ 全量误判 ⇒ 大批正常玩家被 `restricted`。单人休闲游戏、无玩家间交互、作弊收益是「每篇章至多一次的低价值掉落」——真实作弊渗透率不可能达到 1%，因此 1% 是**「这是 bug」的强信号**，不是「这是作弊潮」。`EchoRejected` 取更低的 0.5%，因为它的误报会**当场丢玩家进度**（整批拒绝）。
>
> 这条与 §7a 那句「用进度丢失去防每篇章至多一次的低价值掉落，比例失衡」是同一种比例感在处置侧的兑现。

**自动化止步于「观察」与「生成工单」；`restricted` / `banned` 一律需人工确认。** 两条依据：`status` 变更连带吊销全部会话（一次误判 = 一次强制下线，撞 pillar #4）；且全局熔断的存在本身就意味着必须有人在回路里判断「这是作弊还是我方 bug」。

### J. 向玩家的可见粒度：首版**不扩**两处取值表

`[既有推演]`（从属项）

- **`auth.session_revoked.reasonKey` 不扩。** 会话被吊销时玩家的动作恒为「重登」，与吊销原因无关；`OperatorRevoked` 已足够。
- **`compliance.account_restricted.reasonKey` 在 P2 路线下不扩。** `UnderReview` / `Banned` 与「限制 / 封禁」两档逐一对应，而昵称违规在 P2 下根本不走 `restricted`。
- **向玩家区分「哪一类异常」没有玩家可执行的差异**——掷骰复算异常与昵称违规在 P1 下的出路都是站外申诉；且告知风控判据的具体维度等于把判据外泄，反向指导规避。
- **唯一例外随取向 1 联动**：**若采纳 P1**，昵称违规的出路（改名可解）与作弊受限（只能申诉）确有差异，届时建议扩 `compliance.account_restricted.reasonKey` **一值**：`NicknameViolation`。**本草稿不改 `auth.md` / `compliance.md`**，仅提议取值。它**不阻塞任何契约**——新增 `reasonKey` 不要求客户端同批发版（`envelope.md` §5b）。

## 后果

- **不新增任何 `code`**；不改任何已封定的 `reasonKey` 取值表（P1 路线下建议扩 `compliance.account_restricted` 一值，仍是纯增量、不要求客户端同批发版）。
- **不扩 `profile-sync.md` §5 的后端写入字段表**，因此 §5c 的回声约束面不变、`schemaVersion` 不 bump、无迁移。
- 若采纳 P2：`GET /v1/compliance/status` 的报文字段表（**本就未落笔**，`compliance.md` Open questions）多一项；需客户端侧配套呈现，归客户端库。
- `operations/` 新增三块运维面：词表的不可变版本化发布（复用 flags 的 O1–O7）· 存量扫描的三个触发源与队列 · 风控事件流与阈值配置。
- `06` 的可观测性口径条目需带上一句：**三条探针由风控事件流聚合，不另建采集路径。**
- 栈落定后 `systems/account.md` 承载判定链 ①–⑤ 的服务内部形态。

## 备选方案（已考虑并否决）

- **客户端内置词表** — 第二权威，且补一句禁词要发版（`auth.md` §8 已否决）。
- **端点返回「待审」态**（扩 `reasonKey` 第四值） — 把长时状态机塞回 auth 域，当场推翻 `compliance.md` §1 的分域判据；且已封定的三值表会因此松动。
- **后端改写 / 置空未过审昵称** — `profile-sync.md` §5 把它逐字点名为「反例一」；扩表还会由 §5c 恒等式自动引入回声约束，导致每个被改过名的玩家每次改名都丢一次进度。
- **在 push 上拒绝未过审昵称** — 同时撞 §7a（客户端有权写的路径只记账不拒绝）、§11（同步通道不承载合规拦截）与 pillar #4。
- **不做归一化、直接对原串匹配词表** — 插一个零宽空格即绕过，词表沦为摆设。
- **在原串上做敏感词匹配、在归一化串上判长度** — 与上一条互换即两处都错：玩家看到的字数与判定不一致。
- **拒绝也计入改名频次** — 玩家试错三次即锁死，而他一次都没有改成。
- **第三方审核不可达时返回 `SensitiveWord`** — 把外部抖动伪装成明确拒绝（`Fatal`），玩家以为自己的昵称违规；与 `auth.md` §3a「渠道不可达 ≠ 明确拒绝」同一条理由。
- **词表可原地编辑（无版本化）** — 正是 `ADR-0009` O1 要堵的「同版本内容漂移」，且会让「这个昵称当初按哪一版放行」永远不可回答，T2 的增量面随之塌陷为每次全量。
- **词表分三档（禁止 / 复核 / 放行）** — 「放行」是补集不是一档，第三份清单必然与前两份漂移（同「白名单的补集即不透明段」的措辞纪律）。
- **存量扫描只做定期抽查、不做 T1 事件驱动** — 放弃唯一一条**确定性**检出绕过写入的手段，而它的成本只是一次字符串比较。
- **把扫描台账 / 风控事件写进 profile** — 后端内部状态跨边界（同 `sid` / `channelUserId` 纪律），且 §5 写入表封闭。
- **为风控处置新增专用 `code`** — 玩家处置与 `compliance.account_restricted` 完全相同，新码只逼客户端多写一条走向同一处的分支（`envelope.md` §6 的一贯理由）。
- **风控指标另建一条采集路径** — 与 `06` 已登记的三条探针制造第二权威，且漂移时无任何机制报错。
- **单次复算不一致即自动封禁** — 没有全局熔断兜底时，一次我方实现差一位会被放大成全量误封。
- **自动处置直接写 `status`（无人工确认）** — `status` 变更连带吊销全部会话，一次误判 = 一次强制下线，撞 pillar #4。
- **给 `POST /v1/auth/nickname` 开 `complianceTicket` 无鉴权入口以解 P1 死锁** — 无效：该端点只判定、不写 profile，玩家仍改不了昵称。
- **把风控做成第四个后端服务** — `systems/_index.md` 已定只有三个服务，对位三个跨边界的客户端成分；风控不跨边界、无客户端对位。

## 与既有决策的张力

1. **运营带外改写 profile ↔ `profile-sync.md` §5「后端只读，除表内四项外」。** P1 路线下，被 `restricted` 的玩家无自助出路，实际解除必然依赖工单里由运营改一个违规昵称。本草稿的立场：§5 的封闭表约束的是**上行 push 合并路径上的自动写入**，带外的人工运营操作是另一回事——但它**必须显式登记为运营例外**（落 `operations/`），且**绝不因此扩写入表**（扩表的连带见 §F 理由 2）。**请用户裁决这条边界的措辞归属**；若不接受带外例外，则 P1 路线实际不可用，取向 1 只剩 P2。
2. **P2 路线的「登录后强制改名」↔ `envelope.md` §7b「仅两处硬阻塞」。** 本草稿认为它不构成第三处硬阻塞：它落在启动链上（不在轮回中途）、是一次性可完成的动作、不因外部状态变化而中途变严。但**「算不算第三处」的措辞裁定权在客户端侧**（那两处硬阻塞是客户端已定案的），本库不代为决定。
3. **`lastEffectiveChance` 无法验真这条残留通道，本方案并未关闭它**，只是让它被 §I 的累计阈值接住——与 `profile-sync.md` §7 那句「这是 pillar #1 下的必然取舍，写清楚好过假装覆盖」同向，不主张关闭。

## 仍需用户决定

1. **未过审昵称的处置主线：P1 还是 P2？**
   - **P1** —— 检出即 `status = restricted`，玩家被拦在 `signin`，出路只有**站外申诉 + 运营带外改名**。契约新增为 0（仅建议扩 `compliance.account_restricted.reasonKey` 一值 `NicknameViolation`），跨库成本 0。代价：一次取名失误升级为一次需要人工介入才能解除的账号阻塞；且依赖「运营带外改写 profile」这条边界（见张力 1）。
   - **P2（推荐）** —— `status` 不变，在 `GET /v1/compliance/status` 的应答里带一项「须改名」标记，玩家正常登录后强制走一次改名流程即自解除；`restricted` 降为升级档（拒不改名 / 恶意反复）。代价：需要给一份**本就未落笔**的字段表加一项，且需客户端侧配套呈现（跨库）。
   - **推荐 P2 的理由**：pillar #4 不阻塞玩家；昵称**零玩家间可见性** ⇒ 把玩家整个挡在门外与实际危害不成比例；P1 的死锁无自助出口是推演出的硬事实；而 P2 的承载点本就在待落笔清单上，采纳它不推翻任何已定条款。
   - → **已裁决（2026-09-02 · 批量评审）：P2**（`restricted` 保留为升级档：拒不改名 / 恶意反复）。**连带两项**：① 「须改名」标记的承载已随同批裁决进入 `solution-draft-compliance-endpoint-payloads.md` 的 `GET /v1/compliance/status` 字段表——两份草稿须**一并**被 `/analyze-new-ideas` 消费，单侧提炼即两半对不上；② 客户端呈现形态已立配套草稿 `game-design-documents/inbox/solution-draft-backend-batch-client-obligations.md`。**张力 1（运营带外改写 profile 的例外边界）随本裁决消失，无需裁定。**

2. **是否建独立风控系统？（成本 vs 收益）**
   - **(a) 不建** —— 风控事件只走可观测性通道（结构化日志 + 指标 + 告警），无累计计数、处置全人工。成本最低。**代价：「累计频次到什么程度算异常」这个问题本身无法回答**——没有计数就没有累计，§I 的阈值表全部落空。
   - **(b) 轻量档（推荐）** —— 事件流（§H 字段表）+ 规则化累计计数（§I 阈值）+ 阈值触发**工单**，`status` 变更须人工确认。落点全在 `operations/` 与两个既有服务内部，**不新增第四个服务**。成本 ≈ 一张事件表 + 一个批处理 + 一块看板。
   - **(c) 完整风控平台** —— 实时规则引擎 + 自动处置 + 画像。
   - **推荐 (b) 的理由**：(a) 无法承载本草稿的任何阈值，等于把问题原样留着；(c) 对「单人游戏、无玩家间交互、作弊收益是每篇章至多一次的低价值掉落」严重过配——`profile-sync.md` §7a 已就同一件事定过比例感（「用进度丢失去防它，比例失衡」）。(b) 的落点几乎全部已在 `06` 的清单上（可观测性 + 存储），增量成本最小。
   - → **已裁决（2026-09-02 · 批量评审）：(b) 轻量档。** 事件流 + 规则化累计计数 + 阈值触发工单；`status` 变更须人工确认；全局熔断（同版本内 `RollMismatch` > 1% 或 `EchoRejected` > 0.5%）随之生效。
