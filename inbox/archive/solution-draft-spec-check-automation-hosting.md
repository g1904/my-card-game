# 方案草稿 — 三条机检断言的工程承载位置

## 问题

`contracts/_index.md`「契约变更的完成判据」已定六条判据、三条机检断言与人工清单四项，落笔规则与核对时机（变更内原子）也已答结。**唯一仍开放的是工程承载**：

- 设计库侧有没有一条自动化流水线？
- 它跑在哪里（哪个分支、什么事件）？
- 失败时阻断什么？
- `contracts/openapi.yaml` 尚未落笔（触发点 = 任一侧首个端点进入实现）期间，三条断言以什么形式执行？
- 从「人工清单前三项」迁到「自动」的切换判据是什么？

悬着的后果：完成判据第 4 条（「三条机检断言通过」）目前**没有可勾选的兑现物**——它只能靠人自己记得读一遍两张表并对一遍集合，而断言②的漂移形态是**静默**的（客户端对未知 `code` 有兜底，漏登记不报错，只让某条错误一直走降级路径）。正是这条最不该靠人眼。

## 约束（来自既有设计）

- **断言的校验对象是 markdown + YAML + JSON，与后端栈无关**（`contracts/_index.md`「契约变更的完成判据」）。故它不等技术栈、不等镜像构建。
- **部署形态已具备承接能力**：断言「可作为普通检查步骤挂在同一条流水线上，与镜像构建互不依赖」（`operations/deployment.md`「契约变更的完成判据与机检断言」）。
- **工具刻意不点名，只立能力要求**：能校验 OpenAPI 3.1 / JSON Schema 2020-12，且**能在设计库侧运行**（`contracts/_index.md`）。
- **核对时机 = 变更内原子，责任人 = 发起变更的那一侧**；不设周期性对账——周期性对账允许漂移窗口存在（同上）。
- **spec 尚不存在时，完成判据第 2 条「无对象」**（`contracts/_index.md` 判据 2 的括注）。断言①同理。
- **断言③覆盖 CDN 域端点**（`answer-logs/log-openapi-spec-timing-and-consistency.md` 的 🟠 裁决：CDN 端点进 `paths`，措辞放宽为「每个 `METHOD 路径`」）。
- **`vectors/splitmix64.json` 不属 spec，三条断言不覆盖它**（`contracts/_index.md`）。
- **仓库拓扑**：一个 GitHub 仓库（`origin` = `github.com/g1904/my-card-game.git`）+ 一个本地裸仓中枢 `.repo.git` + 十个 worktree，每个钉一个分支。`backend-design`（设计库）与 `backend-feature`（代码）是**两条独立分支线，从不互相合并**（根约定）。`contracts/` 只存在于 `backend-design`。
- **闸门纪律的既有先例**：`operations/content-delivery-ops.md` 的 C3「触发方 = 流水线自身、无条件，**不设跳过开关**；人可以跳过的闸不是闸」。
- **单人维护**：`content-delivery-ops.md` A4 已裁定「不设强制第二人审批——当前单人维护，四眼原则是纯摩擦」。任何要求「另一个人点同意」的形态与这条相抵。

## 建议方案

### 1. 承载 = 设计库分支自带的一条 CI workflow，不引第二套系统

`[既有推演]` + `[通行做法]`

代码托管在 GitHub。断言的校验对象**零云资源依赖**（不需要腾讯云凭据、不需要镜像仓库、不需要数据库），而镜像构建因需推送到腾讯云侧镜像仓库天然带云凭据。就近原则：**校验挂在代码托管方自带的 CI（GitHub Actions），与镜像构建各自独立**，不为一条纯文本检查再引入第二套 CI 系统。

`deployment.md` 那句「可作为普通检查步骤挂在**同一条流水线**上」应读作**承接能力的陈述**（这类检查在任何 CI 上都是一个普通步骤），**不构成「必须与镜像构建同处一条流水线」的要求**——事实上不可能同处：镜像构建跑在 `backend-feature`，而 `contracts/` 只存在于 `backend-design`。建议采纳时把该句改写为「作为设计库分支上的一条独立 workflow，与镜像构建无依赖」。（见「与既有决策的张力」）

### 2. 跑在哪：`backend-design` 分支，push + 手动，带路径过滤

`[既有推演]`

| 项 | 建议 |
|---|---|
| workflow 文件落点 | `backend-design` 分支根的 `.github/workflows/contract-spec-check.yml`（本地即 `backend-design-documents/.github/workflows/`） |
| 触发事件 | `push`（分支 `backend-design`）+ `workflow_dispatch`（手动重跑 / 首次验证） |
| 路径过滤 | `contracts/**` · `tools/spec-check/**` · 该 workflow 文件自身 |
| runner | GitHub 托管的 Linux runner，**不需要 .NET / 不需要 Godot** |
| 校验脚本落点 | **库根的 `tools/spec-check/`，不放进 `contracts/`** |

两点理由：

- **workflow 必须与被校验对象同分支。** GitHub Actions 的 `push` 事件读取**被推送那个 commit 自身**的 workflow 文件；把它放在 `main` 或 `backend-feature` 都取不到 `contracts/`，会退化成一次跨分支 checkout（多一个可漂移的引用）。分支线互不合并这条根约定同时保证了它不会被误带进别的分支。
- **脚本不放 `contracts/`。** `contracts/_index.md` 的目录形态图把 `contracts/` 下每个文件都登记为契约产物；混入可执行脚本会破坏「`contracts/` 下的东西都是契约」这个读法，也会让断言③的 markdown 扫描把工具文档里的示例路径当成端点。

**`backend-feature` 侧不挂本 workflow。** 后端实现分支上没有 `contracts/`。日后若实现侧要从 spec 生成 / 校验 DTO，那是另一条独立的需求（跨分支取 spec 的形态），不在本方案内。

### 3. 失败时阻断什么：阻断「变更被视为完成」，不阻断 push

`[既有推演]`

当前工作流是直推（根级 `push-all.cmd` 一次推全部分支），没有 PR 环节。因此 CI **在物理上无法阻断一次 push**——它只能在推送之后判定。据此把「阻断」的对象讲清楚：

- **绿灯 = 完成判据第 4 条已兑现**，即该 commit 上的 workflow 结论就是「三条机检断言通过」这个可勾选物。此前它没有兑现物。
- **红灯 = 该次契约变更未完成**（判据 6 条是合取），须补一次修复提交把它转绿。红灯期间**不得**据该契约推进实现或跨库 handoff——「变更内原子」这条纪律的落地形态就是这个。
- **不设跳过开关**，与 `content-delivery-ops.md` C3 同构：无条件触发、无 `[skip ci]` 例外、无「紧急改契约免检」参数。
- **但 C5 的「阻断 = 什么都还没发生」在这里不成立**：内容发布流水线的闸拦在产物生成之前，而此处提交已进入历史。差异要写明，避免读者按 C5 的心智以为红灯等于回滚。修复形式是**前滚一次提交**，与「迁移只前滚」同向。
- **通知形态**：GitHub 默认的失败通知即可，**不新建告警通道**。`operations/observability.md` 的告警面是线上服务的，CI 失败不进那套——把工程流水线的红灯混进线上告警会稀释后者。

### 4. spec 未落笔期间的降级形态：②′③′ 立刻可机检，①明确「不适用」

`[既有推演]`

现状是 `openapi.yaml` 与 `schemas/*.json` 尚未落笔。若把三条断言原样理解，**三条全都没有对象**（①校验 spec 本身、②③各有一半在 spec 里）。「以人工清单前三项执行」在这个阶段实际是空转——人对着不存在的 spec 勾三个框。

建议把降级期的三条**收缩为 markdown 内部的双向核对**，它们**现在就有对象、现在就能机检**，且与将来的完整形态是同一段提取逻辑：

| # | 降级期（spec 不存在） | spec 落笔后 |
|---|---|---|
| ① | **不适用**，输出 `skipped: no spec yet`（**不是** `pass`） | spec 自身合法（OpenAPI 3.1 + 全部 `$ref` 可解析） |
| ②′→② | `envelope.md` §6 台账首列的 `code` 集合 ⇔ 六份契约 markdown 中出现的 `code` 字面量集合，**双向** | 台账 ⇔ **spec 错误码枚举**，双向（②′ 保留并存，它约束的是 markdown 内部自洽） |
| ③′→③ | 六份契约 markdown 中出现的 `METHOD 路径` 集合 ⇔ `envelope.md` §3 端点清单，**双向**（含 CDN 域三端点） | markdown 的 `METHOD 路径` ⇔ **spec 的 `paths` 键**，双向 |

- ①输出 `skipped` 而非 `pass` 是承重的：把「没有对象」记成「通过」会让判据 4 在 spec 落笔那天**从绿变绿**，谁也看不出承接面变了。
- ②′③′ 不是过渡品、**落笔后不删**：它们校验的是 markdown 内部一致（台账 ⇔ 各契约正文、`envelope.md` §3 端点清单 ⇔ 各契约正文），而②③校验的是 markdown ⇔ spec。两者对象不同，同时保留才能定位漂移出在哪一侧。
- **人工清单四项不受影响，永远保持人工**——它们是机检覆盖不到的语义面（`contracts/_index.md` 已言明）。本方案迁移的只是前三项。

### 5. 切换判据 = 文件存在性驱动，不靠人记得翻开关

`[既有推演]`

**判据：`contracts/openapi.yaml` 在被检出的树中存在。** 存在 → ①②③ 全跑且必须绿；不存在 → ①报 `skipped`，②′③′ 照跑。

这样「从人工迁到自动」不是一个需要有人记得执行的动作，而是**首落 spec 那次提交的自动后果**——而首落本身已有明确触发点（任一侧首个端点进入实现，`envelope.md` §1）。用开关表达则必然出现「spec 已落、开关忘了开」的静默窗口，那正是本库反复拒绝的漂移形态。

同理，`schemas/*.json` 逐个新增时，①的 `$ref` 解析自动把它们纳入，无需改配置。

### 6. 工具形态：只立能力要求 + 一条「本地可单命令复跑」的硬要求

`[通行做法]`

- **能力要求（沿用契约侧已立的）**：能校验 OpenAPI 3.1 / JSON Schema 2020-12。契约文档层**继续不点名具体工具**——workflow 与脚本里当然会出现具体包名，那不违反纪律：纪律约束的是**契约文档**不得把某个工具写成契约的一部分。
- **追加一条要求：同一套检查必须能在本地以一条命令跑完**（`tools/spec-check/` 下的单入口），CI 只是这条命令的无人值守执行。理由：变更内原子要求作者**在提交前**就能自查；只能在 CI 上跑的检查会把「原子」拖成「推上去再说」。
- 脚本以 runner 预装的解释器写成、**零第三方依赖安装**（提取逻辑只是正则 + 集合比较）；唯一需要装的是 OpenAPI 3.1 校验器，且**只在 spec 存在时才装**。
- 语言不在本方案定死——它是设计库侧的一次性工具，任何在本机与 runner 上都现成的解释器都满足。

### 7. 两条护栏：让机检真的能提取到东西

`[既有推演]`

断言②③是**正则提取 + 集合比较**，其最常见失败模式不是漏检而是**假阳性**与**提不出来**。两条护栏应随本方案一并落笔：

| # | 护栏 | 不立的后果 |
|---|---|---|
| P-1 | **`envelope.md` §6 台账的首列必须是裸 `code` 字面量**（反引号包裹、无附加文字、无换行、无合并单元格）。它自此是**机器读取面**，改表格结构须同批改提取脚本 | 首列一旦加注释文字，②当场提不出集合；而它的失败会表现为「少了一条」而非「解析失败」 |
| P-2 | **排除清单落在 `tools/spec-check/` 的配置里，每条必须带一行理由**；新增排除项须在该次契约变更中**显式提及**，不得静默追加 | 排除清单是消灭断言的最省事路径——一条假阳性加一条排除，几次之后断言就空了。已知的首条排除：`compliance.md` 的 `downloadUrl` 指向外部对象 URL、不是本 API 端点（`contracts/_index.md` 已言明） |

## 后果

- **完成判据第 4 条自此有了可勾选物**：某次契约变更是否完成，可由该 commit 的 workflow 结论回答，不再依赖记忆。
- **`envelope.md` §6 台账升格为机器读取面**（P-1）：此后改动该表结构是一次会牵动脚本的变更。
- **设计库分支新增两类此前没有的文件**（`.github/` 与 `tools/`）。本库「先有设计再建文件」的纪律要求它们**在本方案被采纳后**才落笔；本草稿不建任何文件。
- **对 `06-platform-stack.md` 无新增依赖**——本条自此与栈彻底脱钩，`06` 余下各条不受影响。
- **不需要 ADR。** 这是工程承载的落位，不是与既有架构决策相抵的取舍；权威落 `contracts/_index.md` 与 `operations/deployment.md` 即可。
- **无存档 / 报文 / schema 影响**，不涉及任何 `schemaVersion` / `/v1/` / `info.version` 的 bump。
- **无跨库对侧义务**：断言校验的是本库的 `contracts/`，客户端侧无承接项。故本次**不写客户端库的 counterpart 草稿**。

## 备选方案（已考虑并否决）

- **挂在腾讯云侧、与镜像构建同一条流水线** —— 被校验对象在 `backend-design` 分支、零云资源依赖，而镜像构建在 `backend-feature` 分支且需云凭据。为一条纯文本检查跨系统取源码，多引入一套 CI 的凭据面与配置面。
- **本地 git hook（pre-commit / pre-push）替代 CI** —— hook 不随分支版本控制生效（须另配 `core.hooksPath`），换机器 / 新 worktree 即静默失效；且「本地可绕过」与 C3「人可以跳过的闸不是闸」相抵。**但本方案的「本地单命令可复跑」保留了 hook 的全部实际好处**，缺的只有强制性，而强制性由 CI 承担。
- **周期性对账（每日定时跑一遍）** —— 与已定的「变更内原子，不设周期性对账」直接相抵：定时任务允许漂移窗口存在，而那个窗口正是两侧按不同真值编码的时期。
- **等 `openapi.yaml` 落笔后再挂 workflow** —— ②′③′ 现在就有对象且现在就有价值（台账是全库最易漏项的表）；且先在无 spec 期把提取逻辑跑熟，spec 落笔那次只做扩展，而不是在最忙的那次变更里同时调试脚本。
- **把断言扩到 `vectors/splitmix64.json`** —— 它不属 spec（不是报文形态），`contracts/_index.md` 已明言三条断言不覆盖它。契约侧的断言集合不由工程承载方案扩张。
- **把 CI 失败接进 `observability.md` 的告警面** —— 那是线上服务的告警口径；混入工程流水线红灯会稀释线上告警的信噪比。

## 与既有决策的张力

**一处措辞张力，非实质冲突。** `operations/deployment.md`「契约变更的完成判据与机检断言」写的是断言「可作为普通检查步骤挂在**同一条流水线**上，与镜像构建互不依赖」。本方案给出的是**另一条分支上的独立 workflow**。

- 该句的实质是**承接能力的陈述**（这类检查在任何 CI 上都只是一个普通步骤），且它自己已写明「与镜像构建互不依赖」——与本方案同向。
- 但字面「同一条流水线」在 `contracts/` 只存在于 `backend-design` 这个事实下**不可兑现**。
- **建议采纳时改写该句**，而非在方案里迁就它。松动代价：无（无任何下游依赖该措辞）。**不松动的替代方案**：镜像构建流水线跨分支 checkout `backend-design` 后跑断言——这会让后端代码的每次构建都依赖设计库分支的一次检出，把两条本应独立的分支线在 CI 层重新耦合起来，与根约定「两条分支线从不互相合并」的理由同向相抵。

**另一处需在采纳时说清**：`contracts/_index.md` 的「工具不点名」纪律约束的是**契约文档**，不约束 `tools/spec-check/` 的实现——脚本必然要写具体包名。建议把该纪律的措辞明确为「契约文档不点名具体工具，只立能力要求；工具选择是工程实现，可随时替换而不构成契约变更」。

### 契约变更是否引入 PR 门（`[取向选择]`）

三条断言现在能拦住什么，取决于 `backend-design` 分支是直推还是走 PR。

| 选项 | 形态 | 后果 |
|---|---|---|
| **A（推荐）保持直推 + 事后红灯** | `push-all.cmd` 照旧一次推全部分支；workflow 在推送后判定，红灯 = 该次契约变更未完成，须前滚一次修复提交 | 零工作流改动。代价：**坏契约会在历史里存在一小段时间**——但设计库无消费者（后端未开工、客户端不读本库分支），这段时间没有第二方按错误契约编码 |
| **B 引入 PR 门** | `backend-design` 设为受保护分支，契约变更走 PR，workflow 设为必需检查，红灯即无法合并 | 真正的准入阻断。代价：`push-all.cmd` 的直推模式对该分支失效，每次改契约多一轮 PR 往返；且当前**单人维护**，PR 里没有第二个审阅者 |

**推荐 A，理由**：`content-delivery-ops.md` A4 已就同类问题裁定过——「不设强制第二人审批，当前单人维护，四眼原则是纯摩擦」。PR 门在单人场景下提供的**唯一**增量是「阻断在合并前而非提交后」，而设计库分支的下游此刻是空的（后端未开工），这个增量的现实价值接近零，摩擦却是每次契约变更都要付。

**复议触发点（建议一并写进采纳后的文档）**：后端进入实现、`contracts/` 开始有真实消费者时重估 B——那时「坏契约在历史里存在一小段时间」不再无害。
