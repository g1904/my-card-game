# 方案 — `/breakdown-requirements` 的签核语义与拆解粒度判据

## 问题

`derive → breakdown → blueprint → implement` 这条链路上，`breakdown` 这一环有两处形态当初是**按技能实现先落下来的**，从未被确认：

**① 签核语义。** 父 FR 有 `draft → ready` 的人工签核门。拆出的子需求当前**直接继承父状态**（父 `ready` ⇒ 子 `ready`），理由是「父 FR 签核即覆盖其子需求」。若改为逐个签核则签核负担随子需求数线性增长；若完全不签核，则存在「父签核时没看过的东西被当成已签核」的风险。**需确认当前取法符合意图。**

**② 粒度判据。** 当前判据是三句话：「一次 `/blueprint` 能一口吃下」「1~5 条验收标准」「薄纵切片，能在 Godot 编辑器里跑出来」。第二句是可数的，**第一句与第三句不可判定**——「一口吃下」没有量纲，「能跑出来」对纯数据资源型子需求是否成立没有回答。结果是每次拆解的粒度取决于当次执行者的手感，而拆解结果是 `/blueprint` 的直接输入，粒度失控会一路传导到实现。

两项都卡在同一处：**它们决定拆解产物能不能被下游机械消费**，但现在只有经验、没有判据。

## 约束（来自既有设计）

- **验证靠在 Godot 编辑器里运行游戏观察，不做 CLI 编译检查、不要求单元测试。**（`.claude/rules/environment-rules.md`「构建 / 运行 / 验证」）⇒ 任何粒度判据里的「可验证」都必须落到「人能在编辑器里点出来 / 在输出里看到」，不能借道测试框架。
- **父 FR 模板：`## Open questions` 非空 ⇒ 该 FR 不是 `ready`。**（`requirements/_TEMPLATE.md`）而 `breakdown` 的切分启发式第 4 条要求「把风险与未知隔离到自己的子需求里」——两条叠加会造出「`ready` 但带非空 Open questions 的子需求」。
- **`/blueprint` 第 1 步会对「`status: draft` 或有非空 `## Open questions`」的输入标出并要求确认。**（`.claude/skills/blueprint/SKILL.md`）⇒ 上一条造出的那类子需求，台账上是 `ready`、进 blueprint 时又被当作未签核拦下，**状态词与下游行为不一致**。
- **充实 vs 臆造：拆解不新增父 FR 推不出的验收标准**，推不出的进子需求的 `## Open questions`。（`breakdown` 技能开头）⇒ 子需求的验收标准集合 = 父 FR 验收标准集合的重排，**不是新内容**。这是「父签核即覆盖子」在集合意义上成立的根据。
- **覆盖核对是强制的**：父 FR 每条验收标准必须映射到至少一个子需求，映射表在拆解文件夹的 `_index.md`。（`requirements/_index.md`「两层结构」）
- **数据即资源：坏数据必须在启动期大声失败**，注册表加载时全量校验、违规项以 `GD.PushError` 报出 id / 路径。（`.claude/rules/data-resource-rules.md` + `null-check-rules.md`）⇒ 这条正是「纯数据资源型子需求也能在 Godot 里跑出来」的那把钥匙。
- **ADR-0005：`.claude` 内的设计性投影只留「一句祈使 + 标识符名 + 代价 + 回链」，硬边界禁止表格 / 具体阈值 / ≥3 步编号流程。** ⇒ 阈值表**不能**写在技能文本里，只能落在设计库、技能侧回链。
- **两库通用：** 后端 FR 模板另有 `## Contract touchpoints` 与**强制**的 `## Failure & retry semantics`，且「可验证」读作「给定请求 / 状态 → 期望应答 / 存储结果」。（`.claude/rules/design-library-routing.md`）⇒ 粒度判据必须给出两库同构的两套指标，不能只写客户端形态。
- **本项目当前实况：** `requirements/` 下零个 FR，`.claude/blueprints/` 下零个源自 FR 的蓝图，`game-feature-branch/` 只有 `project.godot` + 图标。⇒ 下面所有数字上界都是**推导出的初值，未经一次实跑校准**。

## 建议方案

### 子项 1 — 签核语义：默认继承 + 一条 Open-questions 例外闸

`[既有推演]`

**当前形态（父签核即覆盖子）在主干上是成立的**，理由是硬的：拆解不新增验收标准（充实 vs 臆造门），且覆盖核对强制每条父标准都被映射 ⇒ 签核的实质对象是**验收标准的集合**，而这个集合在拆解前后同一。逐个签核等于把同一批标准签第二遍。

**但它漏了三样父 FR 里不存在、只在拆解时产生的东西**，这三样当前不经任何人点头就成为 `ready`：

1. **切分本身**——切成几片、边界画在哪、哪片先做。父 FR 里没有这个信息。
2. **`depends-on` 依赖链**，尤其是切分启发式第 6 条允许的**跨库依赖**（客户端子需求 `depends-on` 一个后端 FR）。父 FR 里同样没有，且它可能指向一个尚不存在的 id。
3. **被隔离出来的未决部分**——启发式第 4 条要求把带 Open questions 的部分单独成条。这一条产出的子需求，父签核时**不可能**签过它（父若带非空 Open questions 就进不了 `ready`）。

第 3 条是**实打实的裂缝**，且它已经和 `/blueprint` 第 1 步的行为对不上（台账 `ready`、进 blueprint 被拦）。

**建议形态：**

> **子需求 `status` 继承父 FR 的签核状态；唯一例外——`## Open questions` 非空的子需求一律产出为 `draft`。**

这不是新规则，而是把父 FR 模板已有的那条（「Open questions 非空 ⇒ 不是 `ready`」）**原样下沉一层**。它可机械判定（看一个小节空不空），签核负担只落在真正未决的那几条上（典型 0~1 条），并顺带消掉上面那处状态词与下游行为的不一致。

第 1、2 条（切分与依赖链）**不建议**用新状态词去承载——它们是**工程判断**而非需求内容，评审入口已经现成：拆解文件夹的 `_index.md` 就装着子需求一览、覆盖映射表与构建顺序。建议把它明确为**拆解结构的评审面**（技能报告里点名请用户过一眼），但不新增状态。理由见下方备选 D 的否决说明。

### 子项 2 — 粒度判据：一张可数的上下界卡，超界须写理由

`[既有推演]` + `[通行做法]`

把「一口吃下」换成可数指标。判据分**软上界**（超过任一 ⇒ 该切）与**软下界**（全部低于 ⇒ 该并），并附一条机械处理：**超界不禁止，但必须在拆解 `_index.md` 里写一行理由，否则再切**。软界的价值在于**强制显式辩护**，硬性拒绝会在真有不可分的切片时把技能逼进死角。

指标与阈值见下方「具体形态」的两张表。选这些指标的理由逐条：

- **改动文件数**——`/blueprint` 第 5 步要求逐文件列出、对**每一次**查找 / 加载 / 注册表读取给 null 校验计划、并给逐条对应验收标准的验证步骤。文件一多，蓝图从「计划」退化为「说明书」，而 `/implement` 一次能被人在编辑器里走完的验证路径也就那么长。这是「一口吃下」唯一有量纲的代理指标。
- **跨服务边界数**——七服务是本作**唯一稳定的职责切面**（`systems/services/_index.md`）。一个子需求跨两个以上服务，通常意味着它其实是两条通路，而不是一条通路的两半。
- **新引入 EventBus 信号数**——新信号是**跨系统契约面**，负载 schema 一旦定下就被多方消费。一次只引入一条，蓝图才能把它的负载定死；两条以上几乎总是横跨了两条通路。
- **新增存档 schema 迁移点数**——迁移牵动原子写入与版本化（`state-save-rules.md`），是承重且易错的一点，一次一处。
- **验证前置操作步数**——直接从 `environment-rules.md` 推出：验证靠人在编辑器里游玩。若要点十几下才能到达被验证的状态，说明这片太靠链路末端，应先切出一个能更早观察到的骨架（切分启发式第 3 条「先立骨架、再挂行为」的可数化）。

### 子项 3 — 纯数据资源型子需求：允许，但须过三条闸

`[既有推演]`

**明确回答：允许。** 现行技能的启发式第 2 条已经举了正例（「定义 `XxxData` 资源 + 一个占位 `.tres` + 启动期校验能报出坏 id」是可验证的），但它是**举例**不是判据——执行者无从知道自己手上这片算不算。建议把它升格为三条同时成立的闸：

> 一个不含任何 UI / 玩法行为的子需求可独立成条，**当且仅当**三条同时成立：
> ① 定义了一个 `XxxData : Resource` 类**并**至少一个真实（非空壳）`.tres` 条目；
> ② 该条目经 **DataRegistry 在启动期加载、并能按 `Id` 被查到**（不是只躺在磁盘上）；
> ③ 至少有**一条负向验收标准**：故意坏 id / 缺必填字段 ⇒ 启动期 `GD.PushError` 报出其 id 与路径。
>
> 缺任一条 ⇒ 不独立成条，**并入消费它的那个子需求**。

第 ③ 条正是让它「能在 Godot 中跑出来」的那个东西——玩家看不见一个 `.tres`，但**开发者能在编辑器输出里看见它被加载与被校验**，这就满足了 `environment-rules.md` 的验证形态，无需任何测试框架。依据：`data-resource-rules.md`「坏数据必须在启动期大声失败」+ `null-check-rules.md` 的四个检查点。

反过来说，②③ 缺失的「先把所有数据类建好」正是启发式第 2 条要挡的东西——三条闸把「挡什么」也一并可判定了。

### 子项 4 — 两库同构：后端侧的等价指标

`[既有推演]`

粒度判据必须两库通用（`design-library-routing.md`）。后端库没有文件边界（技术栈未定）、没有 EventBus、没有 Godot，客户端那几个指标直接搬过去是空的。等价映射：

| 客户端指标 | 后端等价 |
|---|---|
| 改动文件数 | **触及的端点 / 报文数**（新端点 ≤ 1，或既有端点上 ≤ 1 组字段） |
| 跨服务边界数 | 跨**持久化对象**数（profile 记录 / `revision` 计数器 / `pushId` 窗口 / manifest，≤ 1 处主写） |
| 新 EventBus 信号数 | 新**契约字段组** ≤ 1（且必须已在 `contracts/` 中定义——derive 已禁止 FR 自造报文，拆解同样不得） |
| 存档迁移点 ≤ 1 | 存储 schema / 版本迁移 ≤ 1 |
| 「能在 Godot 编辑器里跑出来」 | 「能表述为**给定请求 / 状态 → 期望应答 / 存储结果**」 |

另加一条**后端专有的不可切**约束：

> 模板强制的 `## Failure & retry semantics` **必须在同一个子需求内完整**——不得把「正常路径」与「幂等 / 重试 / 冲突语义」切成两个子需求。

理由：半个失败语义不可验证，且弱网幂等是后端 FR 的承重设计（derive 技能第 4 步已把它列为**强制**小节）。先做正常路径、后补重试的切法，会产出一个**验收标准全通过但线上必炸**的中间状态。

## 具体形态（可 derive 的落地面）

### 软上界 —— 超过任一项 ⇒ 应再切；不切则须在拆解 `_index.md` 写一行理由

| # | 指标 | 客户端上界 | 后端上界 | 依据 |
|---|---|---|---|---|
| U1 | 验收标准条数 | 5 | 5 | 现行判据，保留 |
| U2 | 新建 + 修改文件数 | **8**（`.cs` / `.tscn` / `.tres` 合计；同一类型的多个 `.tres` 条目计为 1 处） | 端点 ≤ 1 新增，或既有端点 ≤ 1 组字段 | `/blueprint` 第 5 步的逐文件义务 |
| U3 | 跨服务边界数 | **1**（一个服务 + 它的 UI / 场景对端；跨 2 个以上按服务再切） | 主写持久化对象 ≤ 1 处 | `systems/services/_index.md` 的职责切面 |
| U4 | 新引入 EventBus 信号 | **1** | 新契约字段组 ≤ 1，且须已在 `contracts/` 中定义 | 信号 = 跨系统契约面 |
| U5 | 新增存档 / 存储 schema 迁移点 | **1** | **1** | `state-save-rules.md` 原子 + 版本化 |
| U6 | 验证前置操作步数（到达被验证状态需在编辑器里操作几步） | **3** | —（后端以「一次请求可达」代之） | `environment-rules.md`：验证靠游玩 |

### 软下界 —— 全部成立 ⇒ 应并入兄弟子需求

| # | 指标 | 阈值 | 依据 |
|---|---|---|---|
| L1 | 真实可观察的验收标准条数 | < 1（「建好某层」不算） | 模板：每条须能运行观察 |
| L2 | 在 Godot 编辑器中可观察的结果（含启动期日志 / 报错） | 无 | `environment-rules.md` |
| L3 | 改动文件数 | 1 且该文件不能独立运行（典型：只加一个字段） | 薄**纵**切片，不是横向层 |
| L4 | 完成后项目是否仍可运行 / 服务仍可部署 | 否（半截状态） | 现行判据「自成可提交的增量」，保留 |

### 纯数据资源型子需求的三条闸（客户端）

`① XxxData : Resource + ≥1 真实 .tres` ∧ `② 经 DataRegistry 启动期加载并可按 Id 查到` ∧ `③ ≥1 条负向验收标准：坏 id / 缺必填字段 ⇒ 启动期 GD.PushError 带 id 与路径`
⇒ 三条全成立才独立成条；否则并入消费方子需求。

### 签核状态规则（子需求）

```
父 FR status = ready  ∧  子需求 ## Open questions 为空   ⇒  子 status = ready
父 FR status = ready  ∧  子需求 ## Open questions 非空   ⇒  子 status = draft   ← 新增的例外闸
父 FR status = draft                                     ⇒  子 status = draft
```

## 后果

- **`requirements/_index.md` 从「状态词汇 + 台账」升级为「拆解工艺的权威」**——这与它已经承载「签核语义」「覆盖核对是强制的」两条流程约定形态一致，不是新性质。
- **技能文本变短**：粒度判据从技能正文移出，符合 ADR-0005 对 `.claude` 的形态要求；代价是执行 `/breakdown-requirements` 时必须读 `requirements/_index.md`——而技能第 2 步**本来就把它列为第一份必读**，不增加读取成本。
- **签核例外闸消除一处状态矛盾**：不再出现「台账 `ready`、进 `/blueprint` 被当作未签核拦下」的子需求。
- **存档 schema 无影响**；不牵动任何运行时契约；不影响 FR 台账列结构。
- **两库对称**：后端 `requirements/_index.md` 需落一份**同构但不同指标**的判据（两库台账永不合并——各写各的，互不回链内容，只在形态上同构）。这一半的落笔归后端库，本草稿不代写。

## 备选方案（已考虑并否决）

- **子需求一律 `draft`、逐个签核。** —— 否决：签核负担 O(子需求数)，且同一批验收标准被签两遍（拆解不新增标准）。父 FR 的签核门会退化成形式，真正的评审精力被稀释到重复条目上。
- **子需求一律 `ready`、无任何例外（即维持现状）。** —— 否决：会产出「`ready` 但带非空 Open questions」的子需求，与父 FR 模板的同一条规则相抵，且与 `/blueprint` 第 1 步的行为不一致。
- **新增状态词 `structure-approved`（专签「切分结构」）。** —— 否决：为一件已有评审面的事（拆解 `_index.md` 的覆盖映射表 + 构建顺序）新增一个状态词，会让 FR 状态机从 5 词涨到 6 词、台账多一列，而它带来的信息全部已在 `_index.md` 里可见。评审面不缺，缺的只是「请用户看一眼」的提示——那属技能报告，不属状态机。
- **粒度用硬上界（超界即拒绝拆解）。** —— 否决：真有不可分的切片时会把技能逼进死角，逼出「为过闸而人为切碎」的假子需求。软界 + 强制写理由能拿到同样的约束力，且把判断留痕。
- **粒度判据本体写在技能里、设计库只回链。** —— 否决：违反 ADR-0005 的硬边界（表格 / 具体阈值 / ≥3 步流程），且 FR 的评审面在设计库一侧——判据写在用户不评审的地方等于没有。

## 与既有决策的张力

1. **粒度判据的归属，两条判据都不完全适配（ADR-0005）。** ADR-0005 的分类是「讲游戏是什么 → 设计库；讲代码怎么写 → `.claude` 自身即权威」。**拆解粒度讲的是流水线工艺**，既不是游戏机制、也不完全是编码约束——它落在两类之间。**已定案：判给设计库**（`requirements/_index.md`），理由是它已经在承载同类的流程约定（签核语义、覆盖核对强制），且需求是用户评审面。这是对 ADR-0005 分类表的一次**外延扩展**——把「流水线工艺」归入设计库侧，判据是「用户的评审面在哪一侧」，**该扩展已获批准，须在 ADR-0005 或 `requirements/_index.md` 明写这句判据**。相应地，**不为 `.claude` 开任何具名例外，阈值表不进技能文本**（在不开例外的情况下把阈值表塞进技能是无声违规）。

2. **U2 = 8、U6 = 3 是推导出的初值，本库零实证。** `requirements/` 下零 FR、`.claude/blueprints/` 下零个源自 FR 的蓝图、`game-feature-branch/` 只有 `project.godot` 与图标。这些数字来自「blueprint 第 5 步的逐文件义务」这一约束的合理外推，**不是**从跑过的拆解里统计出来的。建议按数据资源里的平衡数值同等对待：**写成待校准初值**，并在前三次 `breakdown → blueprint → implement` 完整跑通后回看一次。这条张力不阻塞采纳——软界的机制本就允许超界（写理由即可），初值偏了只会多几行理由。

3. **切分启发式第 1 条「按可观察行为切，不按代码层切」 vs 纯数据资源型子需求获准独立成条。** 表面相抵。化解在三条闸的第 ③ 条：**启动期校验报错本身就是一种可观察行为**（开发者在编辑器输出里看得见），所以过闸的数据型子需求仍是纵切片、不是横向层。不过闸的那种（「把所有数据类建好」）正是第 1 条要挡的——两者不冲突，但这层区分必须在文本里写明，否则会被读成「数据层可以横着切」。
