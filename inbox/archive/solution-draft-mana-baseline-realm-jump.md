# 方案草稿 — 更高境界的 mana 基线是否跃升

## 问题

`lifeTotal` 已定为**境界跃升**（进入炼气 / 筑基 / 金丹时一次性抬到 10 / 25 / 40，见 `systems/character-profile/life-total.md`）；
mana 侧只定了**炼气基线 5/5** 与「上限由事件 cost / reward 推拉、单次幅度恒为 1、一章净增 +1~+2」，
**进入更高境界时是否另有一次基线跃升，全库无一处表态**。

它卡住三件事：① `systems/balance.md` 里要不要再加一张「mana 境界基线表」（加了就是一条新的跨境界数值曲线，须与 `baseMomentum` 一并校准）；
② `manaLimit` 的成长预算（一章 +1~+2）在三个境界是否够用；
③ **敌人侧的 `manaLimit` 从哪里来**——`ActiveCombat.sides` 上有这一格（见 `systems/services/combat-service.md`），
但 `EnemyInstance` 没有这个字段、`EnemyData` 也没有，全库没有任何一处说明它取什么值。这一格的答案**取决于本题**，故一并推演。

## 分工先讲清：`lifeTotal` 与 mana 不能互相类推（本方案的地基）

问题陈述里那句「两者分工不同，不能类推」是对的，且**理由可以精确写出来**——两者被完全不同的外生曲线约束：

| | `lifeTotal` | `manaLimit` |
|---|---|---|
| 是什么 | **承伤 / 存活预算**：还能失败几次 | **每回合的行动带宽**：这一回合能打几张牌 |
| 生命周期 | 跨事件累积的容错资源（单值、无上限、无重置） | 每回合重置的节奏资源（`currentMana` 刷满到 `manaLimit`，不结转） |
| **量纲被谁强制拉动** | **`baseMomentum` 表**——扣减 = 道念差 1:1，而道念差的量级随境界放大（最坏开局落差 9 / 23 / 35） | **牌流**——一场流入 14 张（起手 4 + 5×2）、手牌上限 7、己方 5 个回合。`mana.md` 已明写「**牌流是 `manaLimit` 增长的天花板**」 |
| 那条曲线随境界变吗 | **变，且是百倍级**（`baseMomentum` 1 → 100） | **完全不变**：起手 4 / 每回合抽 2 / 手牌上限 7 / 回合数 8·10·12 三章统一，且敌人侧三项同值、明写「不容差异化」（`systems/balance.md`） |
| 所以基线必须跟着跳吗 | **必须**——不跳则筑基的一次惨败直接打穿炼气量级的 10 | **不必然**——约束面三章同形，没有任何外生压力要求它跃升 |

`[既有推演]` 依据：`systems/character-profile/life-total.md`「与 mana 的非对称是有意的」那张表 + `systems/balance.md`「lifeTotal 的境界基线」公式 + `systems/character-profile/mana.md`「篇章预算感」一条。

**更关键的一条既有分工**：本库反复申明「**等级序是一把简单的直尺，跨境界有多难放进战斗数值里**」
（`systems/game-progression.md`、`systems/balance.md` 各写一遍）。放进的**战斗数值**是 `baseMomentum` 与**每张牌的道念产 / 削量**——
即境界跨度由「**一张牌值多少**」承载，**不由「一回合能打几张」承载**。mana 计的是后者。
按这条既定分工，mana 基线**本来就不该是承载境界跨度的那条轴**。

## 约束（来自既有设计）

- **`manaLimit` 不随境界自动成长，由事件 cost / reward 推拉** —— 这是**已答结的决策**（`answer-logs/log-0730b.md` 第 4 条，
  写入 `mana.md` 的「决策」小节）。**任何形式的境界跃升都要先松动这一条**，见「与既有决策的张力」。
- **单次变动幅度恒为 1，不设 ±2 档**；`CostKey.ManaLimit` 行的两个修正列**恒空**（`mana.md`，承重）。
- **不设 `manaLimit` 下界护栏、不做死牌转化**；`ResourceElements` 里的 `Min = 0` 是取值域而非护栏（`mana.md`）。
- **一章净增 +1~+2**（炼气 5 → 第一篇章末 6~7），推导来自牌流（`mana.md`「篇章预算感」）。
- **参战方对称是硬纪律**：`systems/balance.md` 写「敌人侧三项完全同值 …… 敌人回合的可读性依赖对称 …… 这条不容差异化」；
  `combat-service.md` 写「参战方对称」。
- **敌人卡组保持强度中立，不叠第二条强度曲线**，否则 `±2` 带的数值安全性推导立刻失效（`systems/enemies/_index.md`）。
- **`CardData` 的费用格仍是结构占位**（`deck/common-properties.md`「仍为结构占位：费用与触发器两格」），
  **量纲基准归 ch1 数值标杆专场** ⇒ **本草稿只能答结构，任何数字都是待校准初值**。

## 建议方案

### 子项 1 — **定案（2026-08-22 · 批量评审）：`manaLimit` 每次大境界提升 `+1`**
`[用户裁决]` —— **本草稿原主推荐是「不跃升」，用户在知情下作出了相反选择。**

**采纳的形态 = 本草稿的选项 C（象征性跃升），不是选项 B（境界基线表）：**

```csharp
// 落 CombatRulesData / 平衡资源；进筑基 +1、进金丹 +1（元婴是终点，不给）
[Export] public int RealmBreakthroughManaBonus { get; set; } = 1;   // 待 ch1 数值标杆专场校准的初值
```

- **增量语义，不引入「置值」语义。** 走 `ProfileChangeSpec` 的既有通道 `CostKey.ManaLimit`，
  幅度恒为 1（与既定「单次变动幅度恒为 1」不冲突），由 life-cycle-service 在**篇章边界**施加一次。
  **明确不采纳** 选项 B 的 `max(当前, 基线)` 置值形态——`ProfileChangeSpec` 全部是增量语义，
  凭空引入「置值还是加值」的第二套规则是本方案要避开的代价。
- **不新增字段、不新增存档点、不新增 mana 境界基线表、不 bump schema。** 结构面净增 = 一个常量。
- **须同批改写 `mana.md` 的决策小节**：那里按 `log-0730b` 第 4 条写着「`manaLimit` 不随境界自动成长」，
  与本定案按字面直接冲突（见「与既有决策的张力」①，用户已显式推翻该条）。

**用户已知会的代价**（原「不跃升」三条理由所指向的东西，逐条仍然成立，只是被裁决覆盖）：
① 需推翻 `log-0730b` 第 4 条；② 约束面（牌流）三章不变，故这次跃升不是被外生压力要求的，是为**突破的实感**而给的；
③ `manaLimit` 由此有了一个与玩家选择无关的成长来源，`mana.md`「构筑的长期成长体现在 `manaLimit` 的推拉上」一条被稀释。
**换回的是**：三个境界里最直观的资源格数不再几乎不动，突破在 mana 一侧变得可见。

### 子项 2 — 带宽够不够：把校验写出来（问题里点名要求的那一条）
`[既有推演]`

> **本节保留原样呈现的是「不跃升」口径下的校验。** 它是用户作出相反选择时所知会的背景，**不是**对跃升的论证，
> 也**不**因裁决而被删改。采纳跃升后的实际数值见本节末尾的「定案后的三章末推算」。

不跃升时三章末的 `manaLimit` 约为：**ch1 6~7 · ch2 7~9 · ch3 8~11**（每章净增 +1~+2）。
「这个带宽相对三个境界的强度跨度够不够」——**判据不是强度跨度，是牌流上界**，理由见上方分工表。校验：

```
一场战斗己方牌流上界 = 起手 4 + 每回合抽 2 × 己方 5 个回合 = 14 张（Standard 档）
                       且任一时刻手牌 ≤ 7
一场可支配 mana 总量  = manaLimit × 己方回合数 = manaLimit × 5
```

| | `manaLimit` | 一场 mana 总量 | 若平均费用 2，可打出张数 | 相对牌流 14 张 |
|---|---|---|---|---|
| ch1 末 | 6~7 | 30~35 | 15~17 | **已达饱和** |
| ch2 末 | 7~9 | 35~45 | 17~22 | **明显溢出** |
| ch3 末 | 8~11 | 40~55 | 20~27 | **溢出近一倍** |

> ⚠ 表中「平均费用 2」是**为了让校验可算而取的占位量级，不是提案数值**——`CardData` 的费用格仍是结构占位，
> 真实费用曲线归 ch1 数值标杆专场。

**校验结论（对费用曲线的取值不敏感，只对它的"是否随境界上移"敏感）：**
不跃升时的带宽**不是不够，而是在 ch2 / ch3 已经超过牌流能供给的量**。
按此校验，再叠一次境界跃升会把 `manaLimit` 进一步推离天花板，落向 `mana.md` 明写要避免的失效模式：
「**若 `manaLimit` 膨胀过快会出现『有 mana 没牌打』，mana 重新变成沉没成本**」。

> **用户已知会该校验结论，仍选择跃升（2026-08-22 · 批量评审）。** 本节因此保留为定案的背景，而不是被推翻的论证：
> 它记录的是这次裁决**明知的代价**——溢出会更严重。用户的取向是把「突破的实感」置于溢出之上，
> 并接受「若后两章希望 mana 仍是紧约束，正确的旋钮是上调费用曲线或收紧牌流」这条后续口径（见「后果」）。

**这条校验唯一能被真正反转的前提**：若 ch1 专场决定**费用曲线随境界整体上移**（高境界的牌普遍更贵），
上表的「可打出张数」会同比缩水，溢出随之收窄。**这个前提当前未定、也未进待答清单**——见「前置依赖」。
**采纳跃升后它更需要被跟踪**（跃升把带宽又推高了 2）。

**定案后的三章末推算**（在每章净增 +1~+2 之上，进筑基 / 进金丹各额外 +1，合计 +2）：

| | `manaLimit` | 一场 mana 总量（× 5 回合） | 若平均费用 2，可打出张数 | 相对牌流 14 张 |
|---|---|---|---|---|
| ch1 末 | **6~7** | 30~35 | 15~17 | 已达饱和（与不跃升同，跃升发生在进筑基时） |
| ch2 末 | **8~10** | 40~50 | 20~25 | 溢出加重 |
| ch3 末 | **10~13** | 50~65 | 25~32 | 溢出约两倍 |

### 子项 3 — 配套明文：把两者的**境界基线形态差异**写成第二处有意的非对称
`[既有推演]` + `[用户裁决]`（表中 mana 行按 2026-08-22 定案更新）

`life-total.md` 已经为「lifeTotal 单值 vs mana 双字段」写了一张非对称表，并写明理由是
「**否则日后极易被当作不一致而顺手统一**」。**境界基线是同一张表上的第二行**，必须同样写死，否则同一个"顺手统一"会再发生一次：

| | 字段 | 推拉对象 | 上限 | **境界基线** |
|---|---|---|---|---|
| mana | `currentMana` + `manaLimit` | 事件推拉 `manaLimit`（±1） | `currentMana` 每回合恢复到 `manaLimit` | **每次大境界提升 `+1`**（增量，走 `CostKey.ManaLimit`；**不是基线表、不是置值**） |
| 耐久 | `lifeTotal` 一个字段 | 事件 reward / cost 与战斗失败直接加减 | 无上限 | **跃升 10 / 25 / 40**（约束面 = `baseMomentum`，随境界放大） |

### 子项 4 — 顺带答出的结构缺口：**敌人侧 `manaLimit` 的来源**
`[既有推演]` + `[取向选择]`（见「仍需用户决定」②）

**这是一个真实的、此前无人登记的空白**：`ActiveCombat.sides` 每侧持一格 `manaLimit`（`combat-service.md`），
但 `EnemyInstance`（`InstanceId` / `EnemyId` / `Level` / …）**没有这一格**，`EnemyData` 也没有，
而角色侧那格来自 `CharacterProfile.Status.manaLimit`（**一段事件推拉的累积史**，敌人不具备）。
本题不答，敌人侧那一格就没有取值来源。

推荐形态 —— **敌人 `manaLimit` = 一个全局常量，不随敌人等级变化**：

```csharp
// 落 CombatRulesData（与起手手牌 4 / 每回合抽 2 / 手牌上限 7 同住一份平衡资源）
[Export] public int EnemyManaLimit { get; set; } = 5;   // 待 ch1 数值标杆专场校准的初值
```

- **可被 `EncounterSpec` 的可空覆写组承载一格**（`null` = 取平衡资源默认值），与抽牌数 / 手牌上限同一档旋钮
  ——这是给天劫 / 精英敌人留的唯一口子，且与「Finale 的绝境感只能由样本卡组 / item / power / 遭遇参数四个旋钮表达」一致。
- **为什么不随敌人等级查表**：那张表会让高等级敌人每回合多打牌 = **一条独立于 `baseMomentum` 的第二条强度曲线**，
  正是 `systems/enemies/_index.md` 明令禁止的东西（`±2` 带的数值安全性推导建立在它不存在之上）。
- **为什么不镜像角色当前 `manaLimit`**：那会让玩家辛苦攒来的 `manaLimit` 在战斗中被同步抵消
  ——`mana.md` 明写「构筑的长期成长体现在 `manaLimit` 的推拉上」，镜像等于把这条成长线的兑现面清零。
- **诚实写下代价**：这是**参战方对称的一处破口**，与「敌人回合的可读性依赖对称 …… 这条不容差异化」正面冲突。
  见「与既有决策的张力」②。

> **已裁决（2026-08-22 · 批量评审）：采纳 B1**（全局常量初值 5 住 `CombatRulesData`，可被 `EncounterSpec` 覆写）。
> **注意差距比本草稿原估更大**——因子项 1 采纳了境界跃升，ch3 时玩家约 **9~12**、敌人恒 **5**（原估 8~11 / 5）。
> 这处破口须在 `systems/services/combat-service.md` **列名为已知例外**并写明理由，否则日后审计会把它当漂移修回去。

### 子项 5 — 象征性跃升的形态（**已被采纳，即子项 1 的定案形态**）
`[用户裁决]` —— 本节原为折中备选，2026-08-22 裁决后成为**正式形态**，与子项 1 同一件事。

「不跃升」的真实代价不是数值，是**手感**：三个境界里最直观的资源格数几乎不动，
突破的实感全靠 `baseMomentum`（一个玩家看不太懂的起跑数字）与新卡。
若用户重视这一点，**最小代价的形态是一个常量而不是一张表**：

```csharp
[Export] public int RealmBreakthroughManaBonus { get; set; } = 1;  // 进入筑基 / 金丹各 +1；元婴是终点，不给
```

- 走 **`ProfileChangeSpec` 的既有通道**（`CostKey.ManaLimit`，幅度 1，与既定「单次变动幅度恒为 1」不冲突），
  由 life-cycle-service 在**篇章边界**施加一次，**不新增字段、不新增存档点、不新增平衡表**。
- 合计 +2，三章末变为 6~7 / 8~10 / 10~13——仍在牌流天花板之上（子项 2 的溢出问题略微加重，但不构成新的失效模式）。
- **它需要用户先推翻「不随境界自动成长」那半句**（见张力 ①）—— **用户已于 2026-08-22 显式推翻。**

按 2026-08-22 定案（跃升 · 选项 C 形态 + 敌人侧 B1），改动面仍很小、且**没有任何新增存档字段 / 新增境界基线表 / schema bump**：

| 文档 | 改动 |

## 备选方案（已考虑并否决）

- **完整的 mana 境界基线表（如 5 / 8 / 11 / 14，与 `lifeTotal` 表并列）** — 三条否决理由：

- **敌人 `manaLimit` 按等级查表** — 与「敌人不叠第二条强度曲线」正面冲突（子项 4）。
