# 方案草稿 — `manifestSchema` 双发分流机制 + CDN 三端点失败状态码

## 问题

`contracts/content-manifest.md` 的就绪切片已覆盖 CDN 域三端点 + `/v1/content/flags` 的完整协议面，**余下两条卡点**使该文档停在 `partial`：

1. **双发分流机制仍是二选一。** 正文原文：「破坏性变更时，服务端**同时保留 N-1 与 N 两版 manifest 端点**一段时间（按 `appVersion` 或显式 `?manifestSchema=` 分流）」——机制未裁、**保留时长未定**。若走 query 变体，它还会成为 `envelope.md` §3 端点全集（机器读取面 P-3）之外的一个未登记形态。
2. **CDN 三端点的失败状态码未在契约层钉死。** 现有的只有两样：一条纪律「CDN 侧三个静态对象**不返回契约错误体**，客户端按 HTTP 状态码与本地校验结果判定」，以及 `operations/content-delivery-ops.md` 对 `/blobs/*` 的负缓存要求（隐含存在 404）。失败面五行处置表里**只有 `5xx` 那一格**，`4xx` 整片空白 —— 而「按状态码判定」的前提正是状态码本身有约定。

两条紧耦合：分流形态直接决定「未知 `manifestSchema` 的请求」落在哪个状态码上（路径分支 → 404，query 变体 → 需要 400，而 400 在一个不返回错误体的域里客户端读不到理由）。故一并推演。

## 建议方案

### 一、分流的判定方只能是客户端 —— 路径 (a)「按 `appVersion` 分流」结构上不成立

`[既有推演]`

正文里那两个候选中的 (a)，经直读**不成立**，理由是两条独立的硬事实：

- **K1 + K2：** 三个 CDN 端点无鉴权、不是 API 请求，服务端在这条请求上既没有 token 也没有 `X-App-Version`。要让它拿到，只能让 CDN 对该头 `Vary` ——而那要求客户端在静态对象请求上带一个 §4a 从未要求的头，并把 manifest 的缓存键按版本串碎（`manifest` 虽是 `no-cache` 尚可忍，但这条形态一旦立下就会被套到 `/blobs/*` 上，那里的 `immutable` 长缓存正是整条链的成本基石）。
- **K3：** manifest 拉取排在**登录之前**。哪怕日后给 CDN 加了鉴权，那一刻也不存在可供服务端判定的会话身份。

**推论（承重）：分流不可能是「服务端按谁来了给不同的东西」，只能是「客户端按自己支持什么去请求不同的 URL」。** 客户端是唯一同时知道「我支持哪个 `manifestSchema` 集合」（内置于二进制）与「我正在发这个请求」的一方。这条推论直接淘汰 (a)，并把 (b) 与推荐的 (c) 重新定性为**同一件事的两种编码**：把「要哪一版结构」编进 query，还是编进路径。

### 二、推荐：把 `manifestSchema` 编进**路径**，不用 query 变体

`[既有推演]` + `[通行做法]`

形态（推荐子形态 A，「现在就统一」）：

| 端点 | 说明 |
|---|---|
| `GET <contentRoot>/s<manifestSchema>/manifest` | 该结构版本的 manifest 原始字节 |
| `GET <contentRoot>/s<manifestSchema>/manifest.sig` | 对应的 detached 签名 |
| `GET <contentRoot>/blobs/<sha256>` | **不变**，与 `manifestSchema` 无关 |

- **blob 不分支是关键收益。** blob 是内容寻址的字节，与 manifest 的**结构**无关（K11）。故 N-1 / N 双发的真实成本 = **两个小 manifest 对象 + 两次签名**，blob 一个字节都不重复推、不重复存、不重复回源。这使「双发」从一个要限期止损的负担，降为一条可以从容执行的常规发布动作。
- **未知 schema 天然是 404**，不需要 `400 Bad Request` —— 而 400 在一个不返回契约错误体的域里，客户端只能拿到一个裸状态码、读不到理由（K1）。路径分支让「你要的那一版结构不存在」与「对象不存在」合并为同一格，卡点②的表因此少一行、少一条客户端分支。
- **URL ↔ 字节的不变量向 manifest 侧延伸一步。** 同一个 URL 此后只承载同一种结构，与内容寻址的心智同向。
- **零迁移成本的窗口就在现在**（K15）：无在架客户端、`manifestSchema` 集合待定。此形态若不在首发前定，日后 `1` 就会成为一个永久特例（见「仍需用户决定」的子形态 B）。

对 `envelope.md` §3 的连带（**必须同批**，K5）：三行 CDN 端点改为上表形态。§3 的首列是裸 `METHOD 路径`，`<contentRoot>/s<manifestSchema>/manifest` 这种带占位段的写法与既有的 `<contentRoot>/blobs/<sha256>`、`GET /v1/compliance/export/{taskId}` 同构，**不改变本表结构、不需要改提取脚本**。这是路径分支相对 query 变体的第二个结构性优势。

### 三、否决 query 变体 `?manifestSchema=N` 的三条理由

`[既有推演]`

1. **它会污染 §3 的机器读取面。** 首列要么写 `GET <contentRoot>/manifest`（则变体形态在契约里**无处登记**，正是就绪度评估点名的那个「未登记形态」），要么写成带 query 的串（则 P-3 的「路径以 `/` 或 `<contentRoot>` 起始、列内不加任何附加文字」需要重新定义，且**须同批改提取脚本**）。
2. **CDN 缓存键默认不含 query 是常见配置**，两个变体会互相污染。manifest 是 `no-cache` 时症状轻，但这条形态的正确性押在一项边缘配置上，而它出错的表现是「一部分玩家拿到另一版结构的 manifest → 验签通过、解析失败」—— 只在破坏性变更当天、只在部分边缘上出现。
3. **形态天然不对称且不可修复：** 老客户端不带 query，故裸路径必须**永远**是 N-1 的语义。分流只对新的一方生效，老的一方靠「省略」表达，这个不对称会一直留在契约里。

### 四、双发的保留时长：不是一个裸天数，而是「覆盖率条件 ∧ 时间下界」的合取

`[既有推演]`

下线 N-1 分支的完整序列（逐步挂在既有纪律上，不新造机制）：

```
T0  发布 manifestSchema N        两个路径分支并存；矩阵的 manifestSchema 集合 = {N-1, N}
T1  覆盖率 ≥ 95%                 口径复用 K10：过去 7 天有请求的账号中
                                 appVersion ≥「首个支持 N 的客户端版本」的比例
    → 按 K7 把 appVersion 下界提到该版本，并在矩阵里给 N-1 填下线计划
T2  = T1 + 60 天                 K8/K9：提下界只在下一次登录生效，覆盖存量会话
                                 所需时间的上限 = refresh 链绝对寿命上限
    → 停发 N-1 分支、删实现分支
```

**保留时长 = (T1 − T0) + 60 天，绝对下界 60 天。** 60 天这个数**不是本方案新起的旋钮**——它是 `auth.md` §8 的 refresh 绝对寿命上限，随那个旋钮走；本库对「旧客户端最长能活多久」已经答过一次（K8 的原句），此处逐字复用，不另立一套。

- **为什么必须等到 T2 而不是 T1：** T1 之后仍有存量会话在只走 `refresh`、从不 `signin`，它们不经过闸门（`auth.md` §5b 的原缺口），仍会去请求 N-1 分支。绝对寿命上限是让这批会话必然翻转的**唯一**机制。
- **超期未下线的代价近乎为零**（两个小对象），故这套判据的偏向刻意取「宁可多留」。真正要防的是**过早**下线：它让一批还能正常游玩的客户端从此收不到任何内容热更，而客户端侧对此**不报错、不阻塞**（K6），症状与「最近没发内容」不可区分。
- **旋钮位置：** `operations/version-matrix.md` 的「`manifestSchema` 集合」行 + 「下线计划」语义（该矩阵已定为 `config_knob`，改值不发版）；覆盖率阈值 95% / 窗口 7 天在 `content-delivery-ops.md` 已有条目，**不复制第二份**。三项均为**待实测校准的初值**。

### 五、发布流水线的连带（双发期）

`[既有推演]`

双发期内，`operations/content-delivery-ops.md` 的流水线需按下列方式读，**顺序纪律一字不改**：

- **步②③④** 对两个 schema 分支**各生成、各签名、各自验一次**（自验仍必须用客户端内置的那份公钥）。
- **步⑥ 原子发布**：两个分支各自满足「`.sig` 先于或与 manifest 同一次切换」；**两个分支之间不要求原子**——它们服务不相交的客户端集合，任一分支单独可读都不违反 A 组第 3 条（该条约束的是 manifest 与**它列出的文件**，而 blob 集合是共享且早已推完的）。
- **步⑦ 留痕**：八字段中的 `manifestSha256` 在双发期承载**每个分支各一个摘要**（它是「这一版到底签的是什么」的唯一凭据，只记一个等于另一个分支事后无从追）。这是本方案对留痕形态的唯一增量。
- `contentVersion` **仍是单一序列、单一分配点**：两个分支描述的是同一个内容版本，不各自计数（否则客户端的「更大即增量更新」判据在跨分支升级时当场失效）。

### 六、CDN 三端点失败状态码：4xx 分两类，判据是「manifest 是否已可读」

`[通行做法]` + `[既有推演]`

现有失败面表只有「网络不可达 / 超时 / 5xx → `Network`」一格，4xx 整片空白。建议补齐，判据一句话：

> **入口对象（manifest）的 4xx = 环境 / 配置面** —— 跳过更新用基线 + 本地告警，**不上报**；
> **入口之后的对象（`.sig` / blob）的 4xx = A 组第 3 条发布原子性被违反** —— `Validation` + **上报一次**，且**不进退避重试**；
> **408 / 429 / 5xx / 连接失败 / 超时 = 传输面** —— `Network`，照既有降级与既有重试。

理由：manifest 404 的最可能成因是 `contentRoot` 配置错、环境尚未首发内容——客户端无从区分，且它**不代表已发布的内容被动过**，映成 `Validation` 会在开发 / 测试环境刷出持续告警。而 `.sig` 或 blob 的 404 只可能发生在**manifest 已经被读到之后**，那一刻 K12 已承诺「它列出的文件必须已可下载」——收到 404 即证明发布纪律被破坏（或负缓存命中，见下），这正是值得上报的一类。同理，对一个明确的 404 跑三次退避重传是纯浪费（K13 的重试语义是为传输抖动准备的）。

## 具体形态（可 derive 的落地面）

### 状态码表（契约层钉死；`OpError` 一列为客户端处置的对位，权威在对侧）

| 端点 | 失败面 | HTTP | 可否负缓存 | 客户端处置 |
|---|---|---|---|---|
| `manifest` | 对象不存在（`contentRoot` 配置错 · 环境未首发 · 未知 `s<N>` 分支） | **404** | **否**（关闭或 TTL ≤ 数秒） | 跳过更新、用现有层开局；本地 `PushWarning`，**不上报** |
| `manifest` | 访问被拒（防盗链 / 权限误配） | **403** | 否 | 同上 |
| `manifest` | 回源失败 / 上游故障 | **502 / 503 / 504** | 否 | `Network`，既有断网降级 |
| `manifest` | 边缘限流 | **429** | 否 | `Network`；有 `Retry-After` 则尊重 |
| `manifest` | 非 `GET` / `HEAD` | **405** | — | 不发生（客户端只发 GET）；仅为形态完备 |
| `manifest.sig` | 对象不存在 | **404** | **否** | **`Validation`** + 上报一次 + 拒绝该 overlay + 回退基线；**不重试** |
| `manifest.sig` | 403 / 5xx / 429 | 同 manifest 各行 | 否 | 同 manifest 各行 |
| `blobs/<sha256>` | hash 未发布 / 对象缺失 | **404** | **否**（K14 已有此要求） | **`Validation`** + 上报一次 + 本次更新整体不提交（清空 staging）；**不进 3 次退避** |
| `blobs/<sha256>` | 403 | **403** | 否 | 同上 |
| `blobs/<sha256>` | 5xx / 429 / 超时 | **502/503/504 · 429** | 否 | `Network`，**进**既有的 3 次退避重传 |
| `blobs/<sha256>` | 字节与 manifest 内 hash 不符 | **200** | — | `Validation`（既有行，不变） |

**「版本已被回滚 / 撤下」这一失败面在本设计里结构性不存在。** 回滚 = 前滚（K11 · A 组 4）：manifest 被更大的 `contentVersion` 覆盖而非删除，历史 blob 永不删除。故不产生 404、无需为它定状态码。**逐字写下这一格，是为了让「回滚了要不要给客户端一个信号」此后不再被问。**

### 负缓存要求扩到三端点（`operations/` 增量）

`content-delivery-ops.md` 现有的负缓存要求只覆盖 `/blobs/*`。建议**逐字扩到 `manifest` 与 `manifest.sig`**：同一病理——某边缘在首发（或双发新分支上线）**之前**被探测器 / 人工排查请求过一次并缓存了 404，则在负缓存 TTL 内，命中该边缘的客户端**稳定拿不到一个已经发布的 manifest**。`no-cache` 约束的是成功应答的复用，**不自动约束错误应答的负缓存**，必须显式配置。

### 契约正文的落点

1. 「端点」表三行改为路径分支形态（采纳子形态 A 时含 `s1`）。
2. 「版本化：三个版本号的分工」下那条 bullet 改写：分流机制 = **客户端按内置支持集合选择路径分支**（并写下「服务端在该请求上无 token、无 `appVersion`」这条推论，否则日后必然有人重新提出按版本分流）；保留时长 = 上文四之序列。
3. 「与客户端 `OpError` 的映射」表并入上方状态码表的行，并把 4xx 两分判据写成表下的一句承重纪律。
4. `envelope.md` §3 三行同批改（K5）。

## 后果

- **报文零改动、`manifestSchema` 不因本方案提升、flags 通道零影响。** 本方案只动 URL 形态与失败面语义。
- `envelope.md` §3 端点全集三行改写（**机器读取面，须同批**）；`openapi.yaml` 落笔时以 `contentRoot` 为 server 的那三个 `paths` 随之。
- `operations/version-matrix.md`：「`manifestSchema` 集合」行获得可填的下线计划语义；`content-delivery-ops.md`：流水线双产物读法 + `manifestSha256` 双值 + 负缓存扩到三端点 + 「数值初值一览」新增两行（双发保留的覆盖率阈值沿用 95% / 7 天，**不新增旋钮**；绝对下界 60 天挂 `auth.md` §8，标注为派生值而非独立旋钮）。
- **`envelope.md` §6 错误码台账零改动**（详见「与既有决策的张力」）。
- **客户端承接义务两项**（归对侧裁决，本库不代为决定）：① 按内置的 `manifestSchema` 支持集合拼出请求路径（而非固定 `/manifest`）；② 对 CDN 域的 4xx 按上表两分处置，其中「不对 4xx 走 3 次退避重传」是对既有下载重试语义的收窄。
- 无存档 schema 影响、无迁移。

## 备选方案（已考虑并否决）

- **按 `appVersion` 服务端分流（正文原候选 a）** —— K1 + K2 + K3 三条各自独立地否掉它：无鉴权、不带 `X-App-Version`、请求发生在登录之前。要救它需给 CDN 加 `Vary` 头并让客户端在静态对象上带版本头，代价是碎掉 CDN 缓存键、并把这条形态引向 `immutable` 的 `/blobs/*`。
- **`?manifestSchema=N` query 变体（正文原候选 b）** —— 三条理由见上文「三」：污染 §3 机器读取面（要么无处登记，要么须同批改提取脚本）· 缓存键默认不含 query 的边缘配置风险 · 形态永久不对称。
- **`manifestSchema` 编进 `contentRoot` 由服务端下发** —— 与 K3 直接冲突（manifest 拉取在登录之前，此时没有任何已鉴权应答可承载它），且会把 `contentRoot` 这条「域名 / 厂商切换」的自由度与结构版本绑死，违反 K4 的用途界定。
- **根本不做双发**（破坏性变更后老客户端直接停在基线） —— 它并非不可辩护：K6 已定不支持即降级到基线、不阻塞开局，且秒关走 flags 通道不受影响。但契约正文已承诺双发，而路径分支 + blob 共享把双发成本压到「两个小对象」，此时撤回承诺换不到任何东西。
- **给未知 schema 返回 `400` + 契约错误体** —— 撞 K1（CDN 域不返回契约错误体），且路径分支下 404 已经把这一格表达完整。
- **对 CDN 的 4xx 也走 3 次退避重传** —— 对一个明确的 404 重试三次不改变结果，只延后失败判定并多打三次边缘；重试语义应留给传输抖动。

## 与既有决策的张力

- **「不返回契约错误体、按 HTTP 状态码判定」这条纪律：本方案不需要它松动。** 上表全部处置只消费裸状态码，无一处要求 CDN 产出 `{error:{code,...}}`。这与 `envelope.md` §5b 的兜底条款同向（「应答体无法解析为上述形状 → 按 HTTP 状态码降级」）。
- **`envelope.md` §6 错误码台账：不新增条目。** 台账的每一条都要给出 `code` · `class` · `detail` 形状 · `message` 必含值，而 CDN 域**结构上产不出这四样**；客户端在这条通道上映射的是 `OpError` 三档，不经 `code` 表。新增条目会造出一批永远不会被下发的 `code`，并让 P-1 的双向机检断言在「台账有、正文无」这一侧永久失衡。
- **与 `envelope.md` §5b「客户端不得靠 HTTP 状态码分支」的表面冲突：不成立。** 该条约束的是 **API 域的业务错误**（`401` 分不清「静默刷新」与「硬阻塞重登」）；CDN 域本就被 `content-manifest.md` 明文豁免（「客户端按 HTTP 状态码与本地校验结果判定」）。本方案把这条豁免**写细**，未扩大它——建议在契约落笔时把这半句并列写出，否则日后读者会拿 §5b 来质疑本表。
- **§3 端点全集改三行**是一次机器读取面变更（K5）。它不与任何 ADR 冲突，但**必须与契约正文同批落笔**，且若该批次同时有其他端点变更，须核对提取脚本仍能解析。

## 仍需用户决定

### ① 分流机制的最终形态，以及 `manifestSchema = 1` 是否也进路径分支

**背景一句话：** `manifestSchema` 是 manifest **结构自身**的版本（不是内容版本），只在破坏性变更时 +1；「双发」指破坏性变更后一段时间内服务端同时提供旧结构（N-1）与新结构（N）两份 manifest，使老客户端不被立即打断；「分流」指这两份如何被各自的客户端取到。受影响文档 = `contracts/content-manifest.md`「端点」表与「版本化：三个版本号的分工」，以及 `contracts/envelope.md` §3「端点全集」表。

| 选项 | 形态 | 后果 |
|---|---|---|
| **A（推荐）路径分支 · 现在就统一** | 三端点写成 `<contentRoot>/s<manifestSchema>/manifest`（`.sig` 同）；`s1` 从第一天就在。blob 路径不变 | 形态齐整、无永久特例；未知 schema 天然 404；§3 三行**现在**改一次（零在架客户端 ⇒ 零迁移成本，K15） |
| **B 路径分支 · 只在 N ≥ 2 时新增** | `<contentRoot>/manifest` 永远是 schema 1 的规范路径；schema 2 起才出现 `<contentRoot>/s2/manifest` | 今天不动 §3；但 `1` 成为**永久特例**，此后每个读者与每次 spec 落笔都要先学这个例外，且首个 N ≥ 2 的批次仍要改 §3 |
| **C query 变体** | `<contentRoot>/manifest?manifestSchema=N` | 与 §3 的 P-3 机器读取面冲突（无处登记，或须同批改提取脚本）· 依赖「CDN 缓存键包含 query」这项边缘配置 · 形态永久不对称 |
| **D 按 `appVersion` 服务端分流** | 正文原候选之一 | **不推荐提交表决**：经直读判定结构上不成立（无鉴权 CDN · 不带 `X-App-Version` · 请求发生在登录之前）。列出仅为闭合正文里那句「二选一」 |

**推荐：A。** 理由：分流的判定方只能是客户端（已推演，见方案一），而路径是客户端唯一能自主选择、且不依赖任何中间层配置的编码位；零在架客户端的窗口就在现在，错过即永久特例。**若倾向"契约面此刻少动一次"，B 是可接受的次选**——机制与状态码表逐字相同，只是路径字面量与改 §3 的时点不同。

**不在本题内、按推荐直接落笔的项**（如有异议请一并指出）：保留时长的判据（覆盖率 95% / 7 天窗口 ∧ 提下界后再等 60 天）· 状态码表全部行 · 4xx 两分判据 · 负缓存扩到三端点 · 留痕 `manifestSha256` 双发期承载两值 · 不新增 `envelope.md` §6 台账条目。
