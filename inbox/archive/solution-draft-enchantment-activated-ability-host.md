# 方案草稿 — 阵法（`Enchantment`）上启动式异能的 UI 宿主

## 问题

`ActivateAbility(entryId, abilityId, targets)` 的服务契约已于 08-26d 全部答定，且**按战场条目 id 寻址、与 UI 宿主无关**——阵法作为留场永久物与 `Power` 完全平权。灰态预判也已备妥：`BattlefieldEntryView.ActivatableAbilities`（`AbilityAvailability` 列表：`AbilityId` / `ManaCost` / `RemainingUses` / `CanActivate` / `Reason`）**只对 `ViewerSide` 己方条目填充**。

呈现侧却只定了一半：`ux/combat-ux.md` 的「只读层 = 神通 / 法则」一条给了 `Power` 的宿主（图标条 → 长按升起弹层 → 弹层内的启动键），**阵法条目在战场区内没有对应的启动入口**。后果是**没有宿主就没有玩家可发起的路径**——服务算好的那格在阵法上没有消费者，一整类「留场 + 每回合花 mana 启动」的内容（启动式异能的样板形态，`ActivateAbility` 按条目寻址的直接理由）在客户端写不出来。

**本草稿的范围只覆盖这条功能性缺口**：宿主落点、发起手势、可用 / 不可用 / 配额耗尽的表达、需目标时的衔接、禁用窗口。**不重排战斗屏的分区，也不为它规定任何屏面积配额**——那归已排期的竖屏分区专场（条目 17）。

## 约束（来自既有设计）

- **服务契约零改动是硬前提。** `ActivateAbility` 按 `entryId` + `abilityId` 寻址；拒绝理由全部走 `ActionResult`；`abilityId` 悬空是坏数据档。→ `systems/services/combat-service.md`「API 面」。
- **灰态预判由服务算好交给 UI，呈现层不自行重演规则。** 窗口 / mana / 配额三条规则的判定结果在 `ActivatableAbilities` 里；UI 只渲染。→ 同上。
- **启动被拒时不弹 toast**：`Accepted == false` 只回到原态，解释由灰态 + 长按承担；拒绝文案走 `COMBAT_` 分区普通键，不占 `ERR_` 前缀。→ `ux/combat-ux.md`、`ux/error-and-blocking-ux.md`。
- **禁用规格已定且明写「不为它另立一套」**：敌人回合 / 结算中 / 选目标态一律禁用入口。判据 = 「是否与决策面争抢屏幕或语义」——启动键争语义、半屏弹层争屏幕，两种都构成禁用理由。→ `ux/combat-ux.md`。
- **无 hover-only 可供性；UI 文案一律走 `res://text/` 翻译键。** → `.claude/rules/ui-input-rules.md`。
- **卡面是 full art**：阵法卡面上除 `manaCost` 外无任何文字，规则文字 / 卡名 / 关键字一律后置到点按升起的详情页；详情页复用既有 bottom sheet 控件语言。→ `ux/combat-ux.md`。
- **详情入口的手势判据（现行措辞）**：可拖拽的对象（手牌）用点按；不可拖拽的对象（关键字定义、`Power` 详情、灰显道具的不可用原因）用长按。→ `ux/combat-ux.md`。
- **竖屏分区已是本作压力最大处**，且己方战场区左右两侧已挂法则条与随身角标、宽度待实测验证。任何新增常驻区 / 新增边缘挂件都要先过条目 17 的专场。→ `ux/combat-ux.md`、`open-questions/01-combat.md` 条目 17。
- **`Power` 与阵法在战场上是同一张表的两档**（`BattlefieldEntryKind.PermanentPower` / `PermanentCard`），`ActivateAbility` 对二者逐字同构。→ `systems/services/combat-service.md`「战场条目」。
- **玩家主动发起的动作，目标槽位一律在发起前按 `slotIndex` 一次收齐**，入栈即 `targetState = Resolved`；挂起态只来自结算中途回头问的那些。→ 同上。

## 建议方案

### 子项 1 — 宿主 = 己方战场区里的那个阵法条目本身，不新开任何区

`[既有推演]`

发起入口挂在**战场区内该阵法自己的条目**上。理由三条，全部由既有决策直接推出：

1. 服务按 `entryId` 寻址，`ActivatableAbilities` 逐条目填充 ⇒ **数据本就是逐条目的**，宿主与它同构时零映射成本；另立一个集中入口等于在 UI 侧再建一份「异能 → 载体条目」的对应关系。
2. `Power` 的宿主就是它在战场上的呈现物（图标条），**同为战场条目、同一条 API**，阵法另找宿主会让同一个动作有两条心智路径。
3. **零新增区、零新增常驻部件**——这是本方案不与条目 17 的排布取舍冲突的唯一形态。

**明确不做**：不单开「启动式异能条」，不把阵法的启动入口并进随身抽屉（那是按 `UsableScene` 筛出的道具视图，阵法不是道具）。

### 子项 2 — 交互链 = 详情手势升起 bottom sheet →「详情 + 启动」合一的弹层

`[既有推演]`

与 `Power` 那一半逐字同构：**详情与启动键合一，同一个条目上不并存两种手势**。

```
战场区的阵法条目
  └─（详情手势，见「仍需用户决定」）→ bottom sheet 弹层
        ├─ 详情区：卡名 · 规则文字 · 关键字名（长按展开 ReminderText）· 插画
        └─ 启动区：该条目上每条启动式异能一行
              [异能名]  [ManaCost]  [剩余 N 次]   〔启动〕
```

- **弹层复用既有 bottom sheet 控件语言，不另造控件**（先例：随身抽屉、手牌详情页、战斗前确认页的功法词条）。
- **详情区的内容清单与排布沿用卡牌详情页那一份**，不为阵法另设一套——本草稿不裁定它（归专场，见「前置依赖」）；本条只定「启动区是该弹层里多出来的一节」。
- **启动键必须放进弹层，不能直接挂在战场条目上**：战场条目在竖屏上尺寸小，条目上塞不下一个满足最小触控目标尺寸的按钮，而启动是不可撤销的（扣 mana、占掉行动阶段的一个动作位、不做二次确认）。

### 子项 3 — 启动区每一行逐字映射 `AbilityAvailability`，呈现层不重演规则

`[既有推演]`

| 行内元素 | 数据源 | 呈现 |
|---|---|---|
| 异能名 | `AbilityId` → `ContentRegistry` 解析出的 `AbilityData` 显示名 | `LocalizedText` |
| 费用 | `ManaCost` | 与手牌卡面 `manaCost` 同一套 mana 符号，玩家一眼对齐 |
| 剩余次数 | `RemainingUses` | **`-1` 时整格不渲染**（不限次的异能不该显示一个空槽）；`>= 0` 时显示剩余次数 |
| 启动键 | `CanActivate` | `false` → 灰态；**长按灰态启动键给不可启动原因** |
| 原因文案 | `Reason`（`ActionRejection`） | `COMBAT_` 分区普通键，`res://text/`；**不弹 toast** |

- **一个条目挂多条启动式异能是常态**（`ActivatableAbilities` 本就是列表），故启动区是**逐行列表**而非单个按钮；行数极少（内容侧一条阵法挂两三条已属复杂），弹层内不需要滚动分页。
- **`Accepted == false` 时 UI 只回到原态**（弹层保持打开、不关闭、不提示）——与选目标态「不做『点非法目标弹提示』」同一条纪律。灰态预判已经把绝大多数拒绝挡在点击之前，剩下的是服务全量重校验兜底的少数竞态。
- **启动键文案用「启动」不用「使用」**：`Use` 已被道具占用，两个动词在契约面已分给两条来源路径，UI 措辞跟着分。

### 子项 4 — 可发现性 = 战场条目上的静态启动可供性标记，与 `Power` 侧共用同一套视觉

`[既有推演]` + `[通行做法]`

`ux/combat-ux.md` 已为 `Power` 定下「图标条本体保持纯只读，可发现性由图标上一个**静态启动可供性标记**补偿（标记形态待竖屏分区专场）」。**阵法侧复用同一个标记，不另设第二套**——两者是同一条 API 的两个载体，标记分叉会让玩家学两遍。

- **静态**（无动画依赖、无 hover-only），满足触控端可供性要求。
- **建议它带两态**，数据源均在 `ActivatableAbilities` 内、呈现层不重演规则：
  - 常态 =「此条目有启动式异能」（`ActivatableAbilities` 非空）；
  - 强调态 =「此刻至少有一条可启动」（`Any(CanActivate)`）。
  - 理由：只给常态时玩家每回合都得逐个长按去查「现在够不够 mana」，而这份判断服务已经算好了；把它显示出来是零额外规则成本的信息。
- **具体形状（图形 / 位置 / 尺寸）归条目 17 专场**，本草稿不裁定——它要占己方战场区边缘那一圈已经很挤的空间，且与「只读层形状」是同一批取舍。**注意它同时约束 `Power` 侧的那个标记**（专场清单上已有该项），故建议专场把两者并案处理。

### 子项 5 — 需目标的启动：弹层先收起，直接进入既有选目标态

`[既有推演]`

与随身抽屉「点按选中 → 抽屉自动收起 → 若需目标则直接进入选目标态」逐字同构，不另做一套：

1. 点启动键 → **弹层收起**（它是半屏面板，会压住栈区与合法目标，而「栈区保持可见且不被压暗」「合法目标不被压暗」是承重）；
2. 该异能全部 element 的 `TargetSlots` 长度之和 > 0 → **按 `slotIndex` 顺序逐个问、一次收齐**（主动发起的动作，槽位在发起前收齐），指令条按同一顺序点名各槽位类别；
3. 收齐后调用 `ActivateAbility(entryId, abilityId, targets)`。

- **合法目标集合大小为 1 时自动选定、不进入该态**——既有规则层减免照常适用。
- 这一段与结算中途的 `PendingTargetRequest` 是两回事（后者是挂起态），呈现形态相同、来源不同，玩家不需要区分。
- **来源指示**：选目标态的「是谁在问」由该阵法条目的上浮 + 放大 + 描边承担，与栈条目发起时同一套视觉（既有形态，不新增部件）。

### 子项 6 — 己方面朝下的条目（埋伏）照常有启动入口，对手侧仍只见计数

`[既有推演]` + `[通行做法]`

`faceDown` 的语义是**对对手隐藏内容**（`AmbushCount` 双向对称、只给计数不给内容），而 `ActivatableAbilities` **只对己方条目填充**。故：

- **己方战场区照常逐条呈现自己的面朝下条目**（对自己不遮——玩家自己布置的埋伏他当然知道是什么），其启动入口与明置阵法完全同形；
- **对手侧的面朝下条目不渲染任何条目级入口或标记**，只汇总进计数指示。

若不给己方埋伏宿主，服务在这一格上算出的 `CanActivate` 将永久无消费者。（「己方面朝下条目是否逐条渲染」`ux/combat-ux.md` 当前未明写，见「前置依赖」。）

### 子项 7 — 敌方阵法不渲染任何启动可供性

`[既有推演]`

`ActivatableAbilities` 对侧恒为空列表，敌人启动走 EnemyManager 内部路径、不经本 API。UI **不为对侧条目渲染标记、不渲染启动区**——既无消费者，又是一条信息泄漏面（与 `HandCardInstanceIds` / `UsableItemIds` 同一条填充纪律）。敌方启动的可观测性由 `CombatFeedEntry`（飘字 + 战报）承担，已定案。

### 子项 8 — 入口的禁用规格与 `Power` 弹层 / 随身抽屉完全同规格

`[既有推演]`

**敌人回合 / 结算中 / 选目标态：条目上的启动可供性标记置灰、详情手势的启动区入口禁用。** 判据是既有那条「禁用与否看的是是否与决策面争抢屏幕或语义」——启动键争语义（它可能改变局面），半屏弹层争屏幕（压住栈区与合法目标），两种争抢都成立，故**不为阵法另立一套规格**。

- **选目标态下，战场条目的点按语义被该态独占**（`TargetKind.BattlefieldEntry` 使阵法可成为合法目标，该态已定「单点即确认」）——与「选目标态中手牌的点按语义被该态独占」逐字同构。
- **详情本身在敌人回合 / 结算中是否可看**：建议**照常可看**（纯只读、不改变局面），只禁用启动区那一节——与「不可用项灰显 + 长按给原因」同向。这与上一条不矛盾：禁用的是**启动**这个语义，不是**阅读**。

## 具体形态（可 derive 的落地面）

**零服务契约改动、零 schema 改动、零存档迁移。** 本方案完全消费既有契约面：

| 消费的既有契约 | 用在哪 |
|---|---|
| `BattlefieldEntryView.ActivatableAbilities : IReadOnlyList<AbilityAvailability>` | 启动区列表的唯一数据源；非空 ⇒ 渲染标记 |
| `AbilityAvailability.AbilityId / ManaCost / RemainingUses / CanActivate / Reason` | 逐行渲染（子项 3 的表） |
| `ActivateAbility(string entryId, string abilityId, IReadOnlyList<TargetRef> targets)` | 启动键的调用 |
| `ActionResult.Accepted / Rejection / AwaitingTarget` | `false` → 回到原态；`AwaitingTarget` 由结算侧接管 |
| `ActionRejection`（`AbilityNotAvailable` / `AbilityQuotaExceeded` / `InsufficientMana` / 三条通用） | 灰态长按原因的文案键映射 |
| `CombatSnapshot` 按变更广播 + 缓存 | 标记与灰态随快照重渲，不轮询 |

**新增的呈现层部件清单（供 `/derive-requirements` 消费）**：

1. **战场条目上的启动可供性标记**——两态（有启动式异能 / 此刻至少一条可启动）；形状归专场。
2. **阵法详情弹层内的「启动区」一节**——逐行列表；行内 5 个元素见子项 3 的表。
3. **`COMBAT_` 分区的拒绝原因文案键**——由 `ActionRejection` 的成员机械映射（`AbilityNotAvailable` / `AbilityQuotaExceeded` / `InsufficientMana` / `NotYourTurn` / `NotActionStep` / `StackNotEmpty`）；**本地业务拒绝无后端 `code`，不占 `ERR_` 前缀**。
4. **启动键与「启动」动词的文案键**。

**不新增**：区、常驻挂件、手势、控件类型、服务方法、存档字段。

## 后果

- **文档面**：`ux/combat-ux.md` 的「战斗内持有物面板按『可操作 / 只读』分两层」一节需补一条——**启动式异能不是只读层专属**，阵法作为可留场的**战场条目**同样承载它，宿主 = 条目自身的详情弹层。该节现行的两层划分（可操作 = 随身 / 只读 = 神通法则）仍成立，只是「阵法条目」是第三个落点，且它按**载体**而非按层归类。
- **待答清单面**：条目 17 之下的这条子条目可移出；条目 17 本体（竖屏分区整体排布）**不受影响**——本方案零新增区。专场仍需接手的只剩「启动可供性标记的具体形状」，它本就在专场清单上（`Power` 侧那一项），现在多一个共用者。
- **契约面**：无。`systems/services/combat-service.md` 与 `systems/character-profile/deck/common-properties.md` 一字不改。
- **内容面**：内容侧从此可以写「留场 + 每回合花 mana 启动」的阵法——这是启动式异能的样板形态，也是 `ActivateAbility` 按条目寻址（而非按 `Power` 寻址）那条定案的兑现。
- **存档 / 迁移**：无。

## 备选方案（已考虑并否决）

- **战场条目上直接挂一个「启动」小按钮（一步直达）** — 否决：竖屏战场条目尺寸下塞不进一个满足最小触控目标的按钮；己方战场区左右已挂法则条与随身角标、宽度已标 ⚠ 待验证；且启动不可撤销、不做二次确认，入口毫无门槛会把误触代价直接兑现。
- **单开一条「本场可启动异能」的集中条 / 抽屉** — 否决：新增一个常驻区，与条目 17 的排布取舍正面冲突；且要在 UI 侧再建一份「异能 → 载体条目」映射，而服务的数据本就是逐条目的。
- **并进随身抽屉** — 否决：随身是按 `UsableScene` 筛出的**道具**视图；阵法不是道具，`Use` 与 `Activate` 在契约面已是两条路径，UI 合并会把这条分工抹掉。
- **拖拽阵法条目到目标 = 启动** — 否决：「战场条目不可拖拽」是现行手势判据的分母，引入拖拽即推翻该判据，并与手牌的「拖出手牌区 = 打出」抢同一根手指的时间窗。
- **为无目标槽位、不限次的异能开「快捷启动」（双击 / 直接点按跳过弹层）** — 否决：为一类条目另开一套手势，玩家要先学会分辨「这条异能属不属于快捷档」；而启动扣 mana、占动作位、不可撤销，弹层这一步正是唯一的误触护栏（既有纪律：不做二次确认，误触靠入口门槛与目标尺寸化解）。
- **启动前二次确认弹窗** — 否决：与「不做二次确认、误触不做保护」的既有手感取向直接相抵。
- **启动被拒时弹 toast** — 否决：`ux/combat-ux.md` 明确禁止，解释由灰态 + 长按承担。

## 与既有决策的张力

**一条，且它正是下方那项待决的实质。**

- **与「详情入口的手势按『对象是否可拖拽』分化」这条判据的张力。** 该判据的**字面**判给战场条目「长按」（不可拖拽 ⇒ 长按），但它的**理由**是「长按与拖拽起手在同一根手指上争同一段时间窗，而手牌是战斗屏唯一同时承载拖拽的对象」——**这条理由在战场条目上不成立**（战场条目不承载拖拽，点按在非选目标态下无争抢）。故字面与理由在此处第一次分离。

## 仍需用户决定 → **已全部裁决（2026-09-02 · 批量评审）**

**1 项。**

- **发起详情弹层的手势：长按，还是点按？**（本方案的其余部分对两者完全中立——弹层结构、启动区、灰态、目标衔接、禁用规格都不随之改变。）
  - **选项 A（推荐）—— 长按战场条目升起弹层。**
    - 后果：现行手势判据（不可拖拽 ⇒ 长按）字面照旧成立，`ux/combat-ux.md` 一字不改；**战场区内 `Power` 与阵法一套手势**，玩家学一次；战场条目在竖屏上小，长按对误触的容忍度高于点按；点按在选目标态被该态独占，长按与该态的「单点即确认」天然不撞。
    - 代价：启动是**每回合可能重复的动作**，长按（约 0.5 s）× 每回合 × 一场 10 回合的手感成本不为零；「留场 + 每回合花 mana 启动」恰是这类异能的样板形态，即最高频的那一类正好落在最重的手势上。
  - **选项 B —— 点按战场条目升起弹层**（长按保留给弹层内的关键字定义与灰态原因）。
    - 后果：高频动作少一次 0.5 s 等待；与手牌「点按 = 详情」形成「点按即看详情」的统一心智，反而更少一条例外。
    - 代价：**必须同步改写手势判据的措辞**（改为「按是否与既有手势 / 语义争抢分化」），并连带裁定 `Power` 图标条是否也改点按——两处不一致即漂移；战场条目尺寸小，点按误触会弹起半屏面板压住栈区（虽可立即关闭，但在结算节奏中是噪音）。
  - **推荐 A 的理由**：本项目在同类分歧上一贯优先「同一区一套手势 + 文档判据不动」，而 B 的收益（每次省 0.5 s）要用「改写一条被明写为『必须留在文档里』的判据 + 连带重裁 `Power` 侧」来换；且启动式异能的实际频次尚无内容样本支撑（`MaxActivationsPerCombat` 的内容侧取值全空），现在按「它一定很高频」来定手势是超前假设。**若日后实测证明高频且长按碍手，B 是零结构改动的退让位**——只换手势、弹层与启动区一行不动。
