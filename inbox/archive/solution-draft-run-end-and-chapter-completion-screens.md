# 方案草稿 — 轮回收尾族的两屏：`CycleEndScreen`（失败侧）与 `ChapterEndScreen`（成功侧 · 含元婴通关证书）

## 问题

一次轮回走到尽头有两条出口，`open-questions/06-meta-progression.md` 与 `ux/screen-flow.md#待决问题` 各留了一半，合起来是三件事：

1. **轮回结束屏**（分片导航写作「尚无设计」）—— 见下方「前提修正」：**它已在 09-02 落定**，`ux/screen-flow.md`「轮回结束屏（`CycleEndScreen`）= 一屏三变体」是完整规格。失真的只是索引措辞。
2. **篇章通关（`completed`）那一刻的呈现** —— ch1 / ch2 打通、突破境界、解锁下一篇章那一刻的屏，全库无明文。
3. **元婴界面** —— `ux/screen-flow.md` 已定它是「类似通关证书的终局界面」、是寿元 `+5000` 这次最终更新的读者、统计区落「渡劫成功次数 + 总通关数」两个数；**具体字段与形态待定**。

并案的核心待答点：三者是**一个屏 + 变体表**，还是三个独立屏？本库在 `ux/error-and-blocking-ux.md` 已有「三种终局态收敛为一个 `BlockingNoticeScreen` + 变体表」的同型先例，且 `CycleEndScreen` 自己就是一次同型应用，故不能凭「都是结束」就默认合并——**先例同时给出了收敛的门槛**，本案要做的是拿门槛去量。

### 前提修正（评审时请一并处置）

`open-questions.md` 第 ⑥ 行仍写「**死亡 / 轮回结束屏尚无设计**」，而 `ux/screen-flow.md` 自 `handoffs/2026-09-02-cycle-end-screen.md` 起已有完整规格（载体 / 触发 / 数据源 / 结果三行 / 剩余重试 / 商业化零入口 / 残卷零呈现 / 出口 / 触控 / hover / 文案 / 音效 / 存档 + 三变体表 + 六条理由）；`06-meta-progression.md` 分片正文里也已不再列该条。**建议：这半条按「已答结」处置**，索引措辞改为只保留仍待答的两件（篇章通关 · 元婴界面）。台账文件不在本技能写入面内，交回由编排方处置。

## 约束（来自既有设计）

- **`completed` 与 `defeated` 走同一条收尾链。** `program-overview.md`「阶段 5 —— 轮回结束」：两条出口都汇入 `TeardownCycle()` → `AchievementManager` 结算成就进度 → `sync-service.Push()` → 回主界面（阶段 2）。差别只在阶段 5 入口那一格：`completed` 落境界存档点 + 解锁下一篇章可挑战角色；`defeated` 清理角色数据 + 扣减该篇章重试次数。
- **`completed` 由 `CompleteChapter()`（形态 A，`OpResult`）产生**，触发点是 Finale 通过（`d >= 0`）——`CycleStateManager` 的判定分支见 `program-overview.md` 阶段 4；两个出口之外没有第三种走向（`systems/adventure-event/combat/_index.md`）。
- **`CycleEndScreen` 已定且明写边界：**「本屏只承载 `defeated` 三因。篇章通关 `completed` 与整轮回通关（元婴界面）**不走本屏**。」（`ux/screen-flow.md`）
- **`CycleEndScreen` 的两条承重纪律：** 商业化**零入口零文字**；残卷**零呈现**；且**不呈现本轮回的账号级收获**（理由：账号级收获要展示就得把成就结算提到 `TeardownCycle` 之前，且紧邻的残卷必须完全静默，一屏之内两种口径并存会被读成不一致）。
- **元婴界面的既定落点：**「渡劫成功次数」读 `PlayerProfile.PlayerPowerFragment.FinaleWinOrdinal`、「总通关数」读 `TotalCyclesCompleted`，**并列展示且允许不相等**，**落点为玩家档案与元婴界面（通关证书）的统计区**（`ux/screen-flow.md`；判据链见 `answer-logs/log-finale-win-ordinal-vs-statistics.md`）。
- **元婴界面是寿元 `+5000` 这次最终数值更新的读者**（`ux/screen-flow.md`；增量授予口径见 `systems/character-profile/life-span.md`：炼气起始 1000，抵达筑基 `+1000` / 金丹 `+3000` / 元婴 `+5000`）。
- **账号级统计计数在结束那一次事务里就已写完。** `SavePointReason.CycleEnded` / 角色 `defeated` 那一次 `TryApply` 带 `StatDelta(+1)`（`TotalCyclesCompleted` 或 `TotalCyclesDefeated`），与规则字段同批同事务（`systems/services/life-cycle-service.md`）⇒ 屏呈现时这两个数**已是最终值**。
- **成就结算在玩家按下主按钮之后才跑**（阶段 5 的既定顺序）⇒ 任何收尾屏都读不到本轮回的成就推进结果。
- **只读结束摘要的既有形态。** `DefeatCharacter` 在角色数据清理之前组装一份只读摘要，**只含值类型 + 内容 `Id` + 文案条目 `Id`，不持有 `CharacterProfile` 引用**，不落存档、不进 `PlayerProfile`；字段面 = 境界 + 篇章 · `pastEvent.Count` · `Status.lifeSpan` · `DefeatReason` · `RetriesLeft`（`systems/services/life-cycle-service.md`）。
- **篇章边界是强制 `Immediate` flush 点之一**（`systems/services/sync-service.md`）⇒ 收尾屏上常驻同步指示必须可见。
- **变体表的收敛门槛（先例给的判据）。** `BlockingNoticeScreen` 那张表的门槛写在 `ux/error-and-blocking-ux.md`「什么不进这张变体表」；`CycleEndScreen` 那张表的门槛写在 `ux/screen-flow.md`：「**三变体的差异恰是两格**（标题键 + 定性文案条目），**出路 / 信息行 / 按钮全同**」。
- **翻译键：** `CYCLE_` 分区 / `cycle.csv` 现覆盖「轮回结束屏：三个变体标题、结果行标签、剩余重试行（含「无限」）、主按钮」，**明确不含按 `DefeatReason` 取的定性文案——那是内容层**；键形态 `<PARTITION>_<CONTEXT>_<NAME>`、`SCREAMING_SNAKE_CASE`、一分区一 CSV；`ERR_` 前缀禁止手写（`ux/error-and-blocking-ux.md`）。
- **`ux/_index.md` 的四问判据**：定性 / 叙事文案四问皆是 → 内容层 `LocalizedText`；框架文案四问皆否 → 翻译键。
- **移动优先 · 竖屏 · 触控 · 零 hover-only 可供性**（`.claude/rules/ui-input-rules.md`）。
- **主菜单是唯一开局入口**，「开始新轮回」上挂着三道闸（待兑现购买置灰 + 说明 / 每篇章至多一个 `ongoing` / 篇章解锁门禁）——`ux/screen-flow.md` 已用这条理由否掉了结束屏上的「再试一次」按钮。

## 建议方案

### 1. 收敛到**两屏**，不是一屏、也不是三屏

`[既有推演]`

建议成立一个**轮回收尾族**，含两屏，各带一张变体表：

| 屏 | 承载 | 变体轴 | 变体数 |
|---|---|---|---|
| `CycleEndScreen`（**既有，一格不动**） | 角色离场（`defeated`） | `DefeatReason` | 3（`FinaleFailed` / `LifeSpanExhausted` / `Discarded`） |
| **`ChapterEndScreen`（新增）** | 篇章通关（`completed`） | `chapter`（1 / 2 / 3） | 3（ch1 突破筑基 · ch2 突破金丹 · **ch3 = 元婴通关证书**） |

**为什么不是一屏五（或六）变体。** 拿 `CycleEndScreen` 自己写下的门槛去量：变体表要求「差异恰是两格，**出路 / 信息行 / 按钮全同**」。成功侧与失败侧的差异不止两格，且其中两处是**互相否定的承重纪律**——把它们塞进同一张表，正是变体表本要消掉的「一个改了另一个没改」的半配置态：

1. **剩余重试行只在失败侧存在。** 通关不消耗重试次数（`chapterRetry` 只由 `defeated` 与 `RetryChapter` 推动），成功侧那一行**没有可显示的事实**——不是取值不同，是这一行整个不该在。
2. **账号级收获的呈现口径相反。** 失败侧承重纪律是「本屏不呈现本轮回的账号级收获」；而元婴界面**已定**要有统计区（渡劫成功次数 + 总通关数）。同一张变体表内同时写「零呈现」与「必须呈现」，读者无从判断哪一条是这张表的纪律。
3. **演出口径相反。** 失败侧明写「无入场动画强调」（与寿元告警「静态标注、不做跳动」同调）；通关是全游戏唯一的胜利时刻，把它压成同一条静态口径等于用失败侧的克制去否掉本作唯一的高光。
4. **结果行的语义不同。** 失败侧三行答的是「我怎么结束的 + 我还剩几次机会」；成功侧答的是「我到了哪一境 + 解锁了什么」。

**为什么不是三屏（元婴另立一屏）。** 元婴**就是 ch3 的 `CompleteChapter()`**——同一个方法、同一个 `completed`、同一条阶段 5 收尾链、同一套触控与安全区约束。三份等价布局要各自维护、各自适配竖屏，而差异一旦只靠版式表达必然漂移成三种不一致的观感（这句判据逐字来自 `CycleEndScreen` 的「一屏三变体而不是三屏」）。元婴独有的东西恰好可以表达成变体表里的**两格开关**（见下方变体表的「解锁行」与「统计区」两列）。

**本案与既有文字零冲突。** `ux/screen-flow.md` 已写「`completed` 与元婴界面不走本屏」——本案正是把那句话落实成一个具名的兄弟屏，而不是推翻它。

### 2. `ChapterEndScreen` 的形态

`[既有推演]`（逐条对位 `CycleEndScreen` 的既定表）· 差异处标 `[通行做法]`

| 项 | 取值 |
|---|---|
| 载体 | **一屏全屏**（安全区内）——不进屏幕栈、**无返回路径**、非弹层 |
| 触发 | `CompleteChapter()` 提交完成之后（含既定 `ChapterBoundary` 的 `Immediate` flush；与既有事件 `ChapterCompleted(string CharacterId, int Chapter, Realm ReachedRealm)` 同一时点）——**`TotalCyclesCompleted +1` 只在 ch3 那一笔发生**，ch1 / ch2 只落境界存档点 |
| 数据源 | `CompleteChapter` 内、**角色数据清理之前**组装的**只读值摘要**（值类型 + `Id`，无 `CharacterProfile` 引用），与 `DefeatCharacter` 的摘要逐条同纪律；见下方「具体形态」。⚠ `completed` 与 `defeated` **同样会在轮回结束时清理角色数据**（`systems/character-profile/_index.md`），故「清理之前取快照」这条对成功侧**同样是硬要求**，不是照抄 |
| 结果三行 | 境界 + 篇章 · `pastEvent.Count` · `Status.lifeSpan`（恒精确，与寿元恒精确纪律一致）——**字段面与失败侧摘要逐字同构** |
| 解锁行 | 一行「已解锁：<下一篇章>」；**ch3 变体不出现**（无下一篇章） |
| 统计区 | **仅 ch3（元婴）变体出现**：渡劫成功次数（`FinaleWinOrdinal`）+ 总通关数（`TotalCyclesCompleted`）两行并列，**措辞不得暗示二者应当一致**（既定呈现纪律） |
| 商业化 | **零入口、零文字**（承重）。既有纪律禁的是「失败时刻推销」，本屏是相反的时刻——但结构上同样不可行：购买流程只能在主菜单发起且待发队列为空（`systems/services/sync-service.md`），礼包入口在轮回内 / 结算流程内本就不存在 |
| 残卷 | **零呈现**——不给文案 / 暗示 / 进度条 / 百分比（承重；隐含性是设计初衷，见 `answer-logs/log-0815c.md`）。**ch3 上的残卷兑现同样静默** |
| 成就 | **零呈现**——成就结算在按下主按钮之后才跑（阶段 5 既定顺序），本屏读不到结果 |
| 图鉴 | **零呈现**——本轮回新收录的词条在主菜单图鉴面照常可见 |
| 同步指示 | 常驻可见，沿用既有三取值形态（篇章边界是强制 `Immediate` flush 点，隐藏它就是把「失联」伪装成「已保存」） |
| 退出 | 唯一主按钮「返回主菜单」；**无自动跳转、无倒计时、无二次确认**；**不放「继续下一篇章」**（见下条理由） |
| 触控 | 主按钮落底部拇指可达区、满足触控目标尺寸下限、避开 Home 指示条；结果区可纵向滚动时按钮不随之移出视野 |
| hover | 零 hover 通道，信息全部常驻可见 |
| 文案 | 框架走 `CYCLE_` 分区 / `cycle.csv`（分区扩容一行，见下）；定性文案是内容层 `LocalizedText`；此路径不产生 `ERR_*` 键 |
| 音效 / 演出 | `[通行做法]` **允许一次入场演出**（下条）；**无震动**（全库既有纪律） |
| 存档 | **不新增存档点**——本屏是已提交事务之后的一次纯呈现，零写入；**零新增存档字段** |

**出口只有「返回主菜单」，不放「继续下一篇章」。** `[既有推演]` —— 逐字复用结束屏否掉「再试一次」的那条理由：主菜单是既定的**唯一开局入口**，三道闸（待兑现购买置灰 + 说明 / 每篇章至多一个 `ongoing` / 篇章解锁门禁）全挂在「开始新轮回」上；第二个开局入口要么把三道闸各复制一份（两份闸必然漂移），要么绕过它们。附带一条独立理由：`completed` 之后角色进入的是**下一篇章的可挑战角色池**，起手是读档续章，而「哪个角色、哪个篇章」的选择面本就在主菜单侧。

**允许一次入场演出，但复用既有语汇、不发明第二种。** `[通行做法]` —— 通关时刻给一次庆祝反馈是行业默认（有经验的从业者不会为它开会），失败侧的「无入场动画强调」是为失败时刻的克制而写、不推广到胜利时刻。形态建议逐字复用 Explore 揭示转场已定的那一套：**标题淡入 ≈ 1.2s（待实测初值）+ 一次短音效 + 全屏任意触点即跳过 + 无震动**。跳过是全屏任意触点而不是角落小按钮——触控目标尺寸问题在此一次性消失（判据同揭示转场）。演出**只覆盖标题与定性文案的入场**，结果行 / 解锁行 / 统计区不做逐行动画（不做「数字滚动」一类，与寿元「静态标注、不做跳动」同调）。

### 3. 三变体表

`[既有推演]`

**差异恰是四格**（标题键 · 定性文案条目 · 解锁行有无 · 统计区有无），**出路 / 布局骨架 / 主按钮 / 结果三行全同**：

| `chapter` | 变体 | 标题键 | 定性文案条目 | 解锁行 | 统计区 |
|---|---|---|---|---|---|
| 1 | `ChapterCleared` | `CYCLE_CLEAR_TITLE_CH1` | 一条（内容侧待写：突破筑基） | ✅ 「已解锁：第二篇章」 | ✖ |
| 2 | `ChapterCleared` | `CYCLE_CLEAR_TITLE_CH2` | 一条（内容侧待写：突破金丹） | ✅ 「已解锁：第三篇章」 | ✖ |
| 3 | `Ascension` | `CYCLE_CLEAR_TITLE_ASCENSION` | 一条（内容侧待写：抵达元婴） | ✖ | ✅ 两行 |

- **变体轴取 `chapter` 而不是「是不是最后一章」。** 前者是摘要里本就有的一格、可机械判定；后者要在呈现层再写一次「3 是最后一章」的常量。
- **三条定性文案是内容层条目**（`LocalizedText` + 稳定 `Id`），不进 `cycle.csv`——判据同 `DefeatReason` 的定性文案，`ux/_index.md` 四问皆是。**与失败侧对称：`Discarded` 留空是因为「写挽留文案像在评价玩家的选择」，而突破 / 飞升不存在这个顾虑，三格都给。**
- **解锁行的取值不硬编码**：读摘要里 `UnlockedNextChapter` 与下一篇章的显示名，与「重试上限读两行表、不硬编码常量」同一条纪律。

### 4. 竖屏布局

`[既有推演]`（骨架逐条对位 `CycleEndScreen`）

```
┌─────────────────────────────────────┐
│ [安全区]                  ⟳ 已同步   │  ← 常驻同步指示，沿用既有三取值形态
│                                     │
│             〈标 题〉                │  ← 变体格 ①  CYCLE_CLEAR_TITLE_*
│                                     │
│        〈一条定性文案〉               │  ← 变体格 ②  内容层 LocalizedText
├─────────────────────────────────────┤
│  境界        金丹初期 · 第二篇章      │  ┐
│  历程        47 个事件               │  ├ 结果三行（可纵向滚动）
│  寿元        2180                   │  ┘  恒精确；ch3 上含 +5000
├─────────────────────────────────────┤
│  已解锁：第三篇章                     │  ← 变体格 ③（ch3 变体不出现）
├─────────────────────────────────────┤
│  渡劫成功次数      7                 │  ┐ 变体格 ④
│  总通关数          2                 │  ┘ 仅 ch3（元婴）变体出现
├─────────────────────────────────────┤
│                                     │
│         [   返回主菜单   ]           │  ← 唯一主按钮，底部拇指可达区
└─────────────────────────────────────┘
```

- **`寿元` 位按四位数排版**（同角色状态条 `❤` 位的既有告警）：ch3 结转后叠 `+5000` 可达四千量级以上。
- 结果区与统计区同处一个纵向滚动容器，主按钮固定于底部、不随滚动移出视野。
- 竖屏窄栏下四行标签 + 四个数值均为两列左右对齐，不做并排挤压。

### 5. 与战后结算面板 / 经验条的分工边界

`[既有推演]`

**本屏绝不重造战后结算面板。** 三处分工写死：

| 面 | 时点 | 答什么 | 归属 |
|---|---|---|---|
| **战后奖励 / 事件结算面板** | 每个 AdventureEvent 的 `eventEnd` | 「**这一次**我拿到 / 失去了什么」——逐项列出、逐项领取 / 跳过、跨档叙事行、剧本段 | `ux/combat-ux.md` · `ux/screen-flow.md`「事件结算面板的剧本段」 |

### 6. 翻译键：`CYCLE_` 分区扩容，不新开分区

`[通行做法]` + `[既有推演]`

`ux/error-and-blocking-ux.md` 的分区表是**开放表**、**分区划的是界面**。轮回结束屏与篇章结束屏是同一个界面族（同一条阶段 5 收尾链、同一套骨架、共用结果行标签与主按钮），故建议**扩容 `CYCLE_` 分区的覆盖描述**为「**轮回收尾族**：轮回结束屏（三个 `DefeatReason` 变体标题）+ 篇章结束屏（三个 `chapter` 变体标题、解锁行、元婴统计区两行标签）、结果行标签、剩余重试行（含「无限」）、主按钮（**不含定性文案——那是内容层**）」，而**不新开 `CHAPTER_` 分区**——为八个键单开一个 CSV，收益（分工与 diff）为零，代价是结果行标签与主按钮要么跨文件引用要么复制两份。

### 结束摘要（与 `DefeatCharacter` 的摘要同族，第二个成员）

`CompleteChapter()` 在 `TeardownCycle()` 之前、且**在境界寿元增量与等级归位施加之后**组装一份只读摘要交给呈现层。**「在增量之后」是硬要求**：`ux/screen-flow.md` 已定元婴界面「正是寿元 `+5000` 这次最终数值更新的读者，因此终点处的寿元更新不是死写入」。

```csharp
public enum ChapterEndKind { ChapterCleared, Ascension }

public readonly record struct ChapterEndSummary(
    ChapterEndKind Kind,                  // ChapterCleared(ch1/ch2) | Ascension(ch3)
    int            Chapter,               // = CharacterProfile.chapter（1|2|3）—— 变体轴
    Realm          Realm,                 // = CharacterProfile.realm，突破后的新境界
    int            Level,                 // = CharacterProfile.level，突破后恒为新境界初期（1）
    int            PastEventCount,        // = pastEvent.Count，口径同失败侧摘要
    int            LifeSpan,              // = Status.lifeSpan，境界增量施加之后
    bool           UnlockedNextChapter,   // 由 ChapterManager 的解锁结果给出；Ascension 恒 false
    string         FlavorEntryId,         // 内容层定性文案条目 Id（三格各一条）
    int            FinaleWinOrdinal,      // 仅 Ascension 变体读；来源 PlayerProfile.PlayerPowerFragment
    int            TotalCyclesCompleted); // 仅 Ascension 变体读；来源账号级统计计数层
```

**纪律（逐条对位失败侧摘要）：**
- **只含值类型 + 内容 `Id` + 文案条目 `Id`，不持有 `CharacterProfile` 引用**，不落存档、不进 `PlayerProfile`；它是呈现层的瞬时值对象。
- **零新增存档字段、零新增存档点、零 schema bump。** 十个字段全部是已定字段的读取或已定判定的结果——`chapter` / `realm` / `level` / `pastEvent.Count` / `Status.lifeSpan` 在 `CharacterProfile` 上（字段表见 `systems/character-profile/_index.md`），`UnlockedNextChapter` 是 `ChapterManager` 既有职责（「解锁与重新锁定」）的产出，`FinaleWinOrdinal`（`PlayerPowerFragment`，规则字段层）/ `TotalCyclesCompleted`（`PlayerStatistics`，统计计数层，首批恰两项之一）是既有账号级字段，`FlavorEntryId` 与失败侧的「文案条目 `Id`」同族。
- **统计计数层只被 UI 读、绝不被规则读**——本屏是它的合法消费方（既有分层通则）。
- **两个账号级数在本屏呈现时已是最终值**：`StatDelta(+1)` 与 Finale 的残卷 / ordinal 写入都在这次结束事务里、与规则字段同批同事务，早于本屏。
- **后端零配合、零契约变更。**

## 备选方案（已考虑并否决）

- **一屏五 / 六变体（`CycleEndScreen` 吞并 `completed`）** —— 否决：违反该屏自己写下的收敛门槛（「差异恰是两格，出路 / 信息行 / 按钮全同」），且会把「账号级收获零呈现」与「元婴必须有统计区」两条**互相否定的承重纪律**塞进同一张表；这正是变体表要消掉的半配置态。
- **三屏（元婴另立一屏）** —— 否决：元婴就是 ch3 的 `CompleteChapter()`，同方法、同状态、同收尾链；三份等价布局各自维护必然漂移成三种不一致的观感（判据逐字来自结束屏「一屏三变体而不是三屏」）。它的独有内容恰好可表达为变体表里的两格开关。
- **借用 `BlockingNoticeScreen` 的变体表** —— 否决：那张表只收「由已知后端 `code` 触发、且玩家没有任何自愈路径的终局态」，通关一条都不满足。共用会让「我通关了」与「存档读不出来」在观感上同级。
- **在本屏放「继续下一篇章」按钮** —— 否决：制造第二个开局入口，三道闸要么复制一份（必然漂移）要么被绕过。
- **在本屏呈现本轮回的账号级收获（新收录词条 / 成就推进 / 残卷进度）** —— 否决：成就结算在按钮之后才跑（要展示就得改阶段 5 的既定顺序）；残卷必须完全静默（隐含性是设计初衷）；图鉴收录在主菜单图鉴面照常可见。**ch3 的统计区不是例外**——那两个数在本屏呈现时已是最终提交值，不需要提前任何结算。
- **通关证书做站外分享 / 出图** —— 否决：要一套截图渲染 + 平台分享 SDK，并牵出与「去更新」按钮同款的**渠道差异吸收**问题；全游戏目前没有第二个站外通道（唯二的站外跳转是申诉链接与数据导出下载）。
- **新开 `CHAPTER_` 翻译键分区** —— 否决：八个键单开一个 CSV，分工与 diff 的收益为零，而结果行标签与主按钮要么跨文件引用要么复制两份。
- **突破定性文案做多版随机池** —— 否决：一次轮回内各至多出现一次，随机没有对象（与「渡劫身死」两版随机的前提不同）。
- **本屏呈现经验条 / 寿元曲线 / 逐项奖励回顾** —— 否决：见「分工边界」三条。
- **元婴变体展示「本次轮回用时」** —— 否决（除非用户在下方取向 1 选相反项）：库内**无任何已定的耗时字段**，加它要新增存档字段并触发 schema bump，而收益是一个装饰性数字。
