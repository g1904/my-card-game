# 方案草稿 — 战斗屏的叠加元素与二级面板

> **同批产出的姊妹草稿：`inbox/solution-draft-combat-portrait-layout.md`（主视图分区）。** 本草稿刻意**不裁定任何分区问题**——凡形态取决于「主视图给不给这个位置、给多大」处，一律写成**对分区的条件式提案 + 退让位**，并在 `## 前置依赖` 逐条列出。两份须一并评审。

## 问题

`ux/combat-ux.md` 已把战斗屏的**方向**定得很密（道具 = 角标 + 抽屉 · `Power` = 低权重小图标条且长按查看详情 · 埋伏 = 只给计数 · 卡牌类型 = 卡框色 + 类型角标 · full art 把一切文字后置到详情页 · 战报收起 / 展开共用一格），但**九项的具体形态一项都没落**。它们卡住三件事：

1. **可 derive 面缺口** —— `systems/enemies/` 的 `LineSlot` 是一个**空枚举**，`Lines` 因此对任何条目只能是空数组（`enemies/common-properties.md:39`）；`enemies/common-properties.md` 的就绪度是 `partial`，卡点就是这一条。
2. **承重可读性** —— 战报是**唯一**的动态情报通道（敌人不作任何事前预告），它「写什么、写多细」直接决定战斗是否可读；两条硬要求（截断量必须被说明、目标落空必须被说明）在「单行、永不换行、≈ 屏高 6%」的排布约束下**尚无可执行的表达形态**。
3. **竖屏预算** —— 只读层因「神通不设持有数量硬上限」而条目数无上限，形状必须能容纳 N 条；随身角标与法则条同挂己方战场区两侧已被明写为待实测的挤压点。

## 约束（来自既有设计）

**硬约束（不得违反）：**

- **竖屏 · 触控 · 移动优先**；`Container` + 锚点重排、尊重安全区、满足最小触控目标尺寸；**绝无 hover-only 可供性**——长按 / 点按查看 / 常驻标签是唯一合法替代。（`.claude/rules/ui-input-rules.md`）
- **UI 文案一律走 `res://text/` 翻译键，绝不写字面量**；战斗屏框架文案归 `COMBAT_` 分区（`combat.csv`）；**本地业务拒绝不占 `ERR_` 前缀**。内容文案（卡名 / 规则文字 / 台词）是内容层 `LocalizedText`，**一个字也不进 `res://text/`**（`ux/_index.md` 四问 · `ux/error-and-blocking-ux.md` 分区表边界）。
- **敌人的行动不作任何事前预告（承重）。** 任何新增呈现元素都不得成为事前预告的旁路。（`ux/combat-ux.md`）
- **固定预留高度、容器本身不参与布局变化。** 战报那条纪律的理由是「防手牌区跳位干扰拖拽出牌的肌肉记忆」，故它约束的是**一切会出现 / 消失的战斗屏元素**，不只战报。
- **呈现层不自行重演规则。** 灰态、可启动性、`Declared` / `Actual`、`FizzledSlots` 全部取自服务算好的 `CombatSnapshot` / `CombatFeedEntry`，UX 侧不复述字段面。（`systems/services/combat-service.md`）
- **三个消费者读同一条 `CombatFeedEntry` 流**：飘字 · 战报收起态单行 · 战报展开态因果树。**不各自去别处捞。**
- **灰态是视觉降级、不是禁用：灰格必须继续接收触控**，且点按给一条说明。（`ux/error-and-blocking-ux.md`「灰态判据」）
- **详情入口的手势按「对象是否可拖拽」分化**：可拖拽（手牌）用点按，不可拖拽（关键字、`Power` 详情、灰显道具原因）用长按。
- **弹层禁用判据 = 「是否与决策面争抢屏幕或语义」**；纯只读不是豁免理由。争语义（可能改变局面）与争屏幕（半屏面板压住栈区 / 合法目标）都构成禁用理由，但**两者禁用的态不同**——战报展开态（只争屏幕）在结算态**可开**、选目标态禁用；随身抽屉与 `Power` 弹层（争语义）三态全禁。
- **奖励面板：候选恒 3 项、预先算定、逐项领取 / 跳过、已处置不可反悔、无撤销、无「放弃全部」、无 reroll；每次处置是决策点 `D6`；`RewardPickState { Pending, Claimed, Skipped }`；`picks` 一经写入不可增删不可重排。**
- **`Lines` 的三条加载期校验已定**（空数组合法 / 同 `Slot` 重复 → `PushError` / `Text == null` 或默认语言为空 → `PushError` + 抛），本方案**不新增校验、不新增字段**。
- **强制奖励不进 `picks` 块**（`BaseReward` 计算时即固定、随 `Spoils` 一次带走）；**失败侧仍发 `baseReward`，额外惩罚以负向条目包在 reward 内**。

**软约束 / 已定方向：**

- 随身 = 己方战场区边缘**角标**（与法则条分居两侧）+ 点按升起**底部抽屉**（≈ 屏高 40%、横向滚动一行、不可用项灰显 + 长按给原因）。
- 只读层 = 贴己方战场区边缘的**一排小图标**，视觉权重低于常规永久物，长按升起 bottom sheet（详情 + 启动键合一），图标上带**静态启动可供性标记**（两态：有启动式异能 / 此刻至少一条可启动），该标记 `Power` 与阵法条目**共用同一套**。
- 卡面 full art，卡面文字**只有 `manaCost`**；卡框色 + 类型角标是卡面**唯一的非 `manaCost` 呈现元素**，其权重与可辨性因此升格。
- 战报展开态 = 按结算批次缩进、按回合分组的因果树；收起态 = 固定预留高度的**单行**、显示最新一条、**永不换行、超长省略**。
- 疲劳：抽牌堆不重洗、抽空后每抽一张 −1 道念；**疲劳入栈**、`SourceId` / `SourceInstanceId` / `SourceCardId` 三格恒空、`CauseEntryId` 为空、无 `ActionResult`、照常广播 `CombatFeedEntry(Kind = Fatigue)`。
- **中文名不承担层级表达**（`terminology.md`）：法则 / 古宝 / 神通 / 法宝四词不共用词根，**UI 不能靠中文名传达「这是账号级的」**，层级须由界面归属或非文字标识承担。

## 建议方案

### ① 随身：角标形态与抽屉内 `AbilityScope` 两级标识

**`[通行做法]` + `[既有推演]` — 角标形态。**
- **胶囊形容器 = 一枚道具图标 + 一个数字徽章**（本场可用件数）；整体满足最小触控目标尺寸；落己方战场区边缘、与只读层图标条分居两侧（已定落位）。
- **可用件数为 0 时仍渲染，置灰**，不隐藏。两条依据：① `ux/error-and-blocking-ux.md`「不隐藏而是置灰——隐藏会让玩家以为功能消失且无处解释」；② 隐藏会让己方战场区的可用宽度在战斗中途变化，撞「布局不跳位」。灰态按既定纪律**继续接收触控**，点按升起抽屉（抽屉内为空态一行说明，走 `COMBAT_` 普通键）。
- 敌人回合 / 结算中 / 选目标态：角标置灰、抽屉入口禁用（已定，本条不改）。

**`[既有推演]` — 两级标识 = 一枚角标（corner emblem），不是边框色、不是文字。**
- **不能用文字**：`terminology.md` 明写「UI 文案不能靠中文名传达『这是账号级的』」；且「法宝 / 古宝」共用「宝」字根，正是 `combat-ux.md` 否决纯文字类型标识时给的那条理由（「相邻中文名共用字根，只靠文字读不开」）的第二个实例。
- **不能用边框色**：边框 / 卡框色在本作已被**卡牌类型**占用（见 ④）。同一张小卡面上让颜色同时表达「类型」与「层级」两个维度，两套色系必然相撞。
- ⇒ 落在**左上角一枚形状化角标**，两个取值：`Character`（法宝 · 轮回级）/ `Player`（古宝 · 账号级）。**与只读层的两级标识共用同一套形状**（见 ②）——同一个 `AbilityScope` 枚举在战斗屏只学一次。

**`[通行做法]` — 抽屉内按 `AbilityScope` 分段，不交错。**
- 横向滚动一行内分两段：法宝段在前、古宝段在后，段间一道细分隔线。理由：两级的补充与消耗节奏不同（古宝跨轮回、次数珍贵），玩家的取用心智本就是分层的；分段让角标成为**确认信息**而非唯一信息（小尺寸下角标可能被误读，位置不会）。

**`[既有推演]` — 长按 = 详情与原因合一。**
- 长按抽屉内任一条目 → 升起**卡牌详情页那一份 sheet**（见 ⑤），叠在抽屉之上；**不可用时在 sheet 顶部追加一行原因**（mana 不足 / 非行动阶段 / 栈非空 / 次数耗尽）。与 `Power` 弹层「详情与启动键合一，同一对象上不并存两种手势」逐条同构；也避免为「灰显原因」另造一个只有一行字的浮层。

### ② 神通 / 法则只读层：能容纳 N 条的形状

**`[既有推演]` — 形状 = 单行图标条 + 溢出聚合格，不折叠为角标、不做横向滚动。**

- **不折叠为角标**（即不与随身对称）：随身是**可操作层**，角标点开是操作入口；只读层的全部价值是**常驻可读**——`Power` 是开局入场、整场不变的常驻改写，藏进角标等于逼玩家每回合去查。两层本就按「能否被操作」分层（`combat-ux.md`），形状不必对称。且既有文本已多处以「一排小图标」「图标条本体」称呼它。
- **不做横向滚动**：横滑手势已被随身抽屉与 eventOption 选择区占为「浏览候选」的语义；且图标条贴战场区边缘，横滑与「拖出手牌区 = 打出」的起手在同一片区域争同一根手指；滚动条本身也给不出「还有多少条没看到」的常驻表达。

**具体形态：**

- 条内最多显示 **K** 个图标（**K 初值建议 5，待排版实测**）。总条目数 > K 时，**第 K 个位置换成一个 `+N` 聚合格**；点按 / 长按 `+N` 升起半屏 sheet，纵向列出全部条目（复用 bottom sheet 控件语言）。
- **K 不是常量，是派生量**：`K = floor(可用宽度 ÷ (最小触控目标 + 间距))`，且**硬下界 K ≥ 3**（K < 3 时聚合格吞掉的比显示的还多，形状失去意义）。→ 见 `## 前置依赖`。
- **固定序**：神通（`Character`）在前、法则（`Player`）在后；同段内按入场顺序（= 持有列表顺序）。**不按稀有度排**——`RarityTier` 在战斗内没有语义。位置稳定 = 可学习。
- **两级标识复用 ① 的同一套角标**，叠在图标右下（与左上的启动可供性标记不争位）。
- **被禁用的神通 / 法则不入场 ⇒ 不计入 N**（`combat-ux.md` 已定，本条只作回链）。

**`[既有推演]` — 溢出格不得吞掉启动可供性。**
被折进 `+N` 的条目中**只要有一条此刻可启动**，`+N` 格自身即带**强调态**。理由逐字取自既有纪律：「后者服务已经算好，不显示等于逼玩家每回合逐个长按去查够不够 mana」——溢出不能成为这条纪律的漏洞。

**`[既有推演]` — 信息密度：只有图标，无名、无效果文字。**
`combat-ux.md` 已定「气质是技能感、视觉权重应低于常规永久物」，且详情走长按。在 K 个最小触控目标并排的宽度里塞名字必然缩到不可读——那正是「缩略可辨」判据要防的。**可辨性由图标本身承担**（同一条纪律：卡面插画「缩略可辨是玩家认牌的唯一通道」）。

### ③ 埋伏标记：己方逐条渲染，对手侧固定预留位的计数

**`[既有推演]` — 己方埋伏逐条渲染，不折叠。** 这一条有一个硬论据，不是偏好：

- `combat-ux.md` 已定「**己方面朝下条目（埋伏）照常有启动入口**……不给己方埋伏宿主，服务在这一格算出的可启动性将永无消费者」，而启动入口的宿主是「**战场区内该条目自身**」——服务按**战场条目 id** 寻址、灰态预判**逐条目**填充。**折叠成一格就没有可寻址的宿主**，除非再造一层「展开列表」——那是一个新部件，而本条既定纪律是「零新增区、零新增常驻部件」。
- 己方埋伏对己方是**完全公开面**（`faceDown` 隐藏的只是**对手视角**的内容），逐条渲染零信息泄漏。
- 数量天然受限：同名埋伏不可重复布置（`terminology.md`），且埋伏是阵法的次类型，要占 mana 与一个出牌位。

**形态：** 己方埋伏 = 战场条目的一个**面朝下变体**（卡背 + 一枚埋伏次类型角标），**与正面阵法条目同尺寸、同槽位排布**，不另开一行、不另分区。溢出时的处置见 `## 前置依赖`（退让为战场区内滚动，**绝不退让为折叠**——折叠会打断启动入口的寻址）。

**`[既有推演]` — 对手侧 = 固定预留位的「图标 + 数字」计数标记，挂敌方战场区。**

- 已定：只给计数、不给内容、双向对称、挂战场区（不与战报混住）。
- **计数为 0 时整格淡出，容器高度 / 宽度不变**（固定预留），而不是移除该格。理由同战报的固定预留：埋伏的布置与触发在一场里会反复发生，让敌方区随之伸缩会造成布局跳位。
- **判据补齐（须写进文档，否则读者会读成矛盾）：** 随身角标 0 件时**置灰保留**，敌方埋伏计数 0 时**淡出但占位**——分化的判据是「**它是不是一个入口**」。入口必须可点、必须能给说明，故置灰；纯指示无处可点，淡出即答案。两者都不改变布局，这一点没有分化。

### ④ 卡框色 + 类型角标（full art 下卡面的唯二非 `manaCost` 元素）

**`[既有推演]` — 适用面先厘清：手牌区实际只需分辨四类。**
战斗内 `Power` **一律以技能条目呈现**，卡面形态只用于图鉴 / 详情卡 / 奖励与置换选择面（`combat-ux.md` 已定）。⇒ **手牌与战场卡面上会出现的类型是 `Sorcery` / `Enchantment` / `Item` / `Affliction` 四类**；`Power` 的卡框色 + 角标只在奖励 / 图鉴 / 详情面出现。**仍做一套五色**（那三个面要五类并排），但**缩略可辨性只按四类校准**。

**`[通行做法]` — 冗余编码：颜色管「哪一类」，形状管「同一类」。**
两个元素并存的全部意义就是冗余编码；若类型角标只是一块与卡框同色的色块，两者表达同一维度即是浪费。⇒ **类型角标必须是形状化图标，脱色后仍两两可辨**（小尺寸下的颜色分辨率不足与色觉障碍，是移动端通行的无障碍底线）。

**`[既有推演]` — 卡框色 = 外缘细描边 + 一条较厚的**色带**，不整框着色。**
full art 下整框着色吃插画面积，而「缩略可辨是玩家在手牌区认牌的唯一通道」。色带落在**手牌叠放时恒不被遮挡的那一条边**（叠放方向由主视图分区定，见 `## 前置依赖`）；手牌不叠放时落底边。

**`[既有推演]` — `manaCost` 与类型角标分居卡面顶部两角，`manaCost` 占「恒可见」的那一角。**
`manaCost` 是出牌决策的**必读项**、类型角标是**次读项**，故遮挡预算优先给前者。哪一角恒可见取决于手牌叠放方向 → `## 前置依赖`。本条给的是**规则**，不是具体的左 / 右。

**`[既有推演]` — 五色的取值不在本草稿定，但给三条约束。**
色相属美术基调，权威在 `art/`。约束：① 在 GL Compatibility 渲染器下、在手牌区缩略尺寸下两两可辨；② **灰度化后仍两两可辨**（色觉障碍的代理判据，可机械核对）；③ **不与三套既有状态视觉相撞**——合法目标的呼吸描边、来源条目的上浮 + 放大 + 描边、灰态的降饱和。状态色与类型色同处一张卡面，撞色即状态读不出。

**`[通行做法]` — `Affliction`（业障）的角标须最醒目。**
它是唯一「打出无任何正面效果」的类型，在手牌区认错它的代价（一个 tempo + 一次误触，且误触不做保护）高于其余四类。

### ⑤ 卡牌详情页：一屏清单与排布

**`[通行做法]` — 形态 = bottom sheet，内容自适应高度、上界屏高 60%，超出则页内纵向滚动；不分区、不分页、不加 tab。**
分区 / tab 要求内容量稳定到值得分类，而一张牌的详情项数只有 5–7 项；tab 在触控上多一次点击。滚动是移动端母语行为，且与随身抽屉、图鉴词条 sheet 同一套控件语言。关闭 = 下滑 / 点击 sheet 外区域。

**`[既有推演]` — 内容清单（自上而下，缺项即整行不渲染，不留空槽）：**

| # | 项 | 说明 |
|---|---|---|
| 1 | **标题行** | 卡名（`LocalizedText`）+ `manaCost` + 类型角标 + 卡框色带（与卡面呼应，使「这是刚才那张牌」零成本成立） |
| 2 | **插画缩略** | ≤ 屏宽 20% 的小图，只作锚点。**不重复大图**——详情页存在的全部理由是「卡面无文字」，把最不缺的东西放两遍会挤掉规则文字 |
| 3 | **规则文字** | `LocalizedText`；**关键字名以可长按的内联 chip 形态嵌在句中**，长按展开 `KeywordData.ReminderText` |
| 4 | **次类型行** | 如「阵法 · 埋伏」。次类型是内容层机制，「这是一张埋伏」对己方有决策意义 |
| 5 | **目标声明摘要** | 这张牌要选几个目标、各是什么类别；**措辞与选目标态指令条同源**（「摧毁目标阵法」而非「摧毁目标」），避免打出后才知道要指谁 |
| 6 | **启动区**（仅阵法 / `Power` 载体） | 逐行列表，形态已定：异能名 · 费用 · 剩余次数（不限次时整格不渲染）· 启动键（灰态 + 长按给原因）。本草稿不改这一节 |
| 7 | **不可用原因**（仅灰态入口升起时） | 一行，`COMBAT_` 分区普通键，不占 `ERR_` |

- **战斗内详情页不显示 `Rarity`**：稀有度在战斗内没有消费点；奖励 / 置换 / 图鉴面的详情卡显示它。
- **关键字定义仍走长按二级展开，不改为常驻展开。** 一张牌可挂多个关键字，全展开会把规则文字推出屏外，而关键字定义对熟练玩家是零信息。既定机制「永远长按、首次出现不自动展开」原样成立，宿主换成详情页而已。

**`[既有推演]` — 详情页的禁用规格与随身抽屉 / `Power` 弹层**不同档**，与战报展开态同档。**
判据就是既有的那一条「禁用与否看的是**是否与决策面争抢屏幕或语义**」：

| 对象 | 争什么 | 敌人回合 / 结算中 | 选目标态 |
|---|---|---|---|
| 随身抽屉 · `Power` 弹层 · 阵法启动弹层 | 语义 + 屏幕 | 禁用 | 禁用 |
| 战报展开态 | 只争屏幕 | **可开** | 禁用 |
| **手牌详情页（本条提案）** | **只争屏幕** | **可开** | 入口天然不存在 |

- 手牌详情页**纯只读、不可能改变局面** ⇒ 不争语义；它是半屏面板 ⇒ 争屏幕。与战报展开态逐条同构，故随它一档。
- 敌人回合 / 结算中允许查看手牌详情是有实际价值的：玩家在那段「信息与交互双零」的观看里正好在规划下一回合。
- 选目标态下**点按手牌 = 指定目标**（已定，该态独占该手势）⇒ 该态下详情入口不存在，无需另立禁用规则。

### ⑥ 战报的文案体系（承重）

#### (a) 与飘字的分工边界 —— 一条判据

**`[既有推演]`**

- **飘字 = 量与归属**：谁的道念动了多少、动在哪个对象上。**不承载因果，也不承载例外。**
- **战报 = 事实与例外**：谁做了什么、引发了谁、标称量与实际量之差、目标落空。
- **判据一句话：不读也不会错过的归飘字，不读就读不懂的归战报。**

三条推论：

1. **截断量与 fizzle 只进战报，飘字侧不表达。** 飘字转瞬即逝、承载不了括注；更要命的是 `Actual == 0` 时飘字**本就没有数字可飘**——「削减被下限 0 全部吃掉」与「目标落空」在飘字上都表现为「什么也没有」，而那正是两条硬要求要说明的那件事。
2. **飘字取 `Actual`，战报取 `Declared` / `Actual` 一对。** 两者同源同刻（同一条 `CombatFeedEntry`），**不设先后延迟**——延迟会让两个消费者对同一次结算给出错位的画面。
3. **飘字不表达因果。** 因果树是展开态战报的专职（`EntryId` / `CauseEntryId`），飘字不画连线、不做「由 X 触发」的附注。

#### (b) 收起态单行的信息量：主语 + 动作 + 来源 + `Actual` 增量

**`[既有推演]`** 建议采「敌方打出「回风诀」 · 你 −5」这一档，而不是只写「敌方打出 X」。

- 收起态是**常驻**的，且它事实上是战报的**默认视图**——「藏在按钮后等于取消这条硬要求（玩家不会主动开日志）」这句既定判断，同样适用于「把结果藏进展开态」。
- 只写动作不写结果，就把「第 3 回合我的道念为什么少了 3」这个**战报存在的唯一理由**整个推给展开态。
- **与飘字的冗余是刻意接受的**：飘字转瞬即逝，收起态单行是玩家移开视线后唯一的安全网。这不违反 (a) 的判据——(a) 分的是「谁必须说」，不是「谁独占」。

**单行 = 结构化槽位，不是自由文案：**

```
[归属方] [动作动词] [来源名] · [增量]
```

- **超长时的省略顺序是一条规则，不是实现细节：优先省略「来源名」，绝不省略「增量」。** 增量是玩家推不出来的那一半，来源名在展开态可查。不写下这条，「单行 · 永不换行 · 超长省略」这条排布约束会随机吃掉信息量最高的那一段。
- 疲劳条目无来源名（三格恒空）：`[归属方] 疲劳 · −1`。
- 归属方用「我方 / 敌方」措辞，不用侧别代码。

#### (c) 截断量与 fizzle 在单行内的表达：符号标记，括注只在展开态

**`[既有推演]`** 这是本条最实的一格——**在单行、永不换行、≈ 屏高 6% 的约束下，「削减 8（对方仅剩 5，溢出 3 未结转）」必然触发省略，而被省略掉的恰好就是括注本身**，即这条硬要求。故：

| 情形 | 判据（服务已给） | 收起态单行 | 展开态 |
|---|---|---|---|
| **截断** | `Declared != Actual` | 增量后缀一枚**溢出符**：`你 −5▸` | 全文「削减 8（对方仅剩 5，溢出 3 未结转）」 |
| **部分落空** | `FizzledSlots != 0` 且 `Declared != 0` | 来源名后一枚**落空符** | 写明是哪一半没生效 |
| **全条落空** | 全部有目标槽位置位且 `Declared == 0` | 直接写「[来源名] · 目标已不存在」（无增量可显示，字数够） | 同左 + 因果树内的位置 |

- **两枚符号必须是非数字字符，且与飘字的 `+N` / `−N` 不同源**，否则会被读成第二个数值。
- **符号不需要被「理解」即可用**：它只表示「这条还有话说」，语义由展开一次即得。**不做说明浮层**（无 hover 通道，且弹提示在连锁中是噪音——与「不做『点非法目标弹提示』」同一条纪律）。
- 具体字形归美术 / 图标集，本草稿只定三条约束：**非数字 · 单字宽 · 两枚互不相似**。

#### (d) 翻译键形态

**`[既有推演]`** 条目存结构化数据、**渲染期才套翻译键**（已定）。分区 = `COMBAT_`（`combat.csv`），**不占 `ERR_` 前缀**（本地呈现，无后端 `code`）。首批建议：

| 键 | 用途 |
|---|---|
| `COMBAT_LOG_CARD_PLAY` / `_ABILITY_ACTIVATION` / `_ABILITY_TRIGGER` / `_ITEM_USE` / `_FATIGUE` | 五个 `CombatFeedKind` 各一条模板句 |
| `COMBAT_LOG_TRUNCATED` | 截断括注全文（展开态） |
| `COMBAT_LOG_FIZZLED` / `COMBAT_LOG_FIZZLED_ALL` | 部分落空 / 全条落空 |
| `COMBAT_LOG_TURN_HEADER` | 展开态的回合分组行（「第 3 回合 · 我方」） |

- **来源名（卡名 / 异能名 / 道具名）不进翻译键**——它们是内容层 `LocalizedText`，由呈现层作**格式参数**插入。这与 `EVENT_` 分区「事件正文一个字也不进」是同一条边界的第二次兑现。
- 键数**随 `CombatFeedKind` 的成员机械对应**，不建第二张手写对照表（同 `code → ERR_*` 的判据）。

### ⑦ 疲劳的呈现

#### (a) 抽牌堆剩余张数：建议常驻（**但这一项是取向，见 `## 仍需用户决定`**）

推荐**常驻**，理由：疲劳是一条**确定性的、可预算的**失血曲线（抽空后每抽一张 −1，每回合抽牌数固定），玩家能且只能靠剩余张数把它算成「还有 N 个回合开始扣血」。而「我落后 8 点 = 输了掉 80 寿元」这本可算的账正是主视觉的价值所在；疲劳是这本账**唯一的内生扣项**，不常驻就把一条可算的账变成突然发生的事。
**它不需要独立分区**：数字叠在抽牌堆这个对象上即可，零新增区（宿主依赖见 `## 前置依赖`）。

#### (b) 见底预警：给，且只给一档、纯静态

**`[既有推演]`** 形态 = 剩余张数在 `<= DrawPerTurn × 2` 时**转红字**。**不闪烁、不弹提示、不加音效、不写任何预警文案。**

- 这与寿元的既定处置**逐字同构**：「余量低于本章可用预算的 10% 时转红字——那是纯视觉强调，不是一条叙事通道」，且 `ux/screen-flow.md` 已明写「**不做『大限将至』一类的预警文案**：余量既已明文常驻且精确，预警型提示文案没有存在理由」。本条是同一条纪律在战斗屏的第二个实例。
- **阈值写成 `DrawPerTurn × 2` 而非固定张数**：`DrawPerTurn` 可被 `EncounterSpec` 覆写、可被剧本的 `EncounterTighten` 收紧 ⇒ 固定张数在被收紧的遭遇里语义漂移。它是**派生量、不是平衡常量**，故不进 `CombatRulesData`。
- 若 (a) 判为不常驻，本条随之失去载体 → 退让位见 `## 前置依赖`。

#### (c) 飘字侧「疲劳扣减」与「被对手削减」的区分：按**起飞点**区分，不按颜色 / 字形

**`[既有推演]`** 这是本条最强的一格，且**零新增视觉词汇**：

- 既定纪律：飘字**注意力跟随对象**（敌人打出牌 → 牌面飞出 + 道念条上 `+5`）。
- **被对手削减**的那一条**有来源对象**（那张牌 / 那个战场条目）⇒ 飘字**自该对象飞向我方道念位**。
- **疲劳没有任何来源对象**——`SourceId` / `SourceInstanceId` / `SourceCardId` 三格恒空、`CauseEntryId` 为空、栈条目的三格亦恒空 ⇒ 它的飘字**自抽牌堆飞出**。抽牌堆正是疲劳唯一的语义来源，也正是 (a) 要常驻的那个对象。
- 判定完全由 `CombatFeedKind.Fatigue` 给出，**呈现层零规则重演**。
- **颜色不参与归因**：`−N` 的颜色恒为「我方道念下跌」的同一色。归因维度已由起飞点承载；再叠一层颜色会与呼吸描边 / 上浮描边 / 灰态降饱和三套既有状态色争语义（同 ④ 的第三条约束）。

### ⑧ 战后奖励面板的形态

**`[既有推演]` — 形态 = 战斗流程内的全屏一屏**（不进屏幕栈、无返回键、无系统返回绕过），自上而下三段：

| 段 | 内容 | 有无按钮 |
|---|---|---|
| **1 结果段** | 胜负 + 双方最终道念；**失败时如实展示本次寿元扣减量与扣后余量** | 无 |
| **2 强制段** | 一行小标题 + 逐条只读行（图标 + 名称 + 数量 / 增减量） | **无** |
| **3 可选段** | 一行小标题 + **3 行卡片，纵向堆叠** | 每行两个 |

底部一个**全宽主按钮**（见「衔接」）。

**`[既有推演]` — 强制段必须展示（回答「自动计入的部分是否也要展示」）。**
`BaseReward` 是一份 `ProfileChangeSpec`、随物化定稿；玩家不看这一屏就**再也没有地方**知道自己拿到了什么（战报不落存档、`PastEventEntry` 无玩家出口）。更硬的一条：**失败侧的额外惩罚正是以负向条目包在 reward 内** ⇒ 不展示等于让惩罚静默发生，与「结算面板必须如实展示本次扣减量」是同一条诚实性要求。

**`[既有推演]` — 强制 / 可选的同屏区分靠「有没有按钮」这个结构差，不靠颜色 / 图标。**
「有没有可操作」是最不可能被误读的区分；且它与既定的分层判据「按**能否被操作**归两层，而不是按数据归属分」（战斗内持有物两层）同出一辙。小标题只作确认，不作唯一区分。

**`[既有推演]` — 竖屏排布 = 纵向堆叠全宽行，**绝不横滑**。**
逐字取自剧本分支段的既定判据：「纵向堆叠全宽按钮……**不复用横滑区语汇**——横滑是 eventOptions 与角色选择的语言，复用会让两个层级的操作读成同一件事」。此处更严重：横滑正是**择一**的语汇，而「**不是三选一**、三项各自独立可领」恰是这块的承重语义，用错语汇即在视觉上否定它。

**每行的形态：**
- 卡面缩略（**用卡面形态**——`combat-ux.md` 已定卡面形态适用于「奖励与置换选择面」，`Power` 族在此同样以卡面出现，五类角标齐用）+ 名称 + 一行说明 + `[领取]` `[跳过]` 两键。
- **点按行本体 = 升起详情 sheet**（复用 ⑤ 那一份；此处**显示 `Rarity`**）。两键各自独立、不做长按、不做二次确认（与既定的「不在最高频操作上加模态」同向）。

**`[既有推演]` — 两态视觉：**就地置灰保留**，不消失、不移入「已领区」。**
三条理由：
1. **面板长度恒为 3**（既定：「面板长度恒为 3、到手数不恒定」）⇒ 消失或移动会让长度 / 顺序变化，与「已处置不可反悔」要传达的「这已经是事实」正好相反。
2. **`picks` 一经写入不可增删、不可重排** ⇒ 视觉顺序应逐格映射存档顺序；重排等于让 UI 与存档不同构。
3. **退出重进按 `state` 重建面板** ⇒ 就地置灰是唯一能让「重建结果」与「处置过程」看起来一致的形态。

**`[既有推演]` — 已领取与已跳过必须可区分，且两键**移除**而不是置灰。**
- 行尾一枚状态标记：已领取 = 勾、已跳过 = 斜杠（两个非文字符号，形状可辨）。
- **两个按钮同时移除**，不留灰键。这是**灰态纪律的一个显式边界，须写进文档**：`ux/error-and-blocking-ux.md` 的灰态适用于「**暂时不可用 / 必然无结果**」，且要求灰格**继续接收触控并给一条说明**；而此处是「**已成事实、永远不会再可用**」，没有任何说明可给，留一个灰键只会诱导点击。判据一句话：**暂时不可用 → 置灰；已成事实 → 移除控件。**
- 行本体本身仍可点（升详情），只是不再有处置动作。

**`[既有推演]` — 与事件收口的衔接 = 两屏顺接，不合并。**
- 底部主按钮在**仍有 `Pending` 项时置灰**，点按给一行说明「还有 N 项待处置」（`COMBAT_` 普通键，不占 `ERR_`；**灰格继续接收触控**——此处是「暂时不可用」，落在灰态一侧，与上一条不矛盾）。
- 按下 → 离开战斗流程 → **事件结算面板**（`eventEnd` 那一次 `TryApply` 之后的那一屏；跨档叙事行与剧本段追加在其底部）。
- **不合并为一屏**：奖励面板在返回结果**之前**、属战斗流程（既定推论 ①），逐项处置是 `D6`；事件结算面板呈现的是收口后的一次事务结果，是 `D7` / `eventEnd`。合并会让「**计算归战斗、施加归生命周期**」这条分工在 UI 上糊掉。
- **主按钮的措辞与结算面板的「继续」分开**（走 `COMBAT_` 分区自己的键），避免玩家把两次点击读成重复。逐条中文措辞属文案定稿，不阻塞结构。

**`[既有推演]` — 合法池不足 3 条目时：渲染实际项数，不渲染空占位格。**
既定处置是「显式降级：`PushWarning` + 给出实际能给的项数，**不静默给 2 项**」——「显式」的落点是日志与实际项数，不是屏幕上的一个空槽（空槽没有语义，且会被读成「这一项加载失败了」）。与「面板长度恒为 3」的措辞有轻度张力，见 `## 与既有决策的张力`。

**`Practice` 档**：`PowerData` 整族不进候选（已定），面板形状一格不变。

### ⑨ 敌人台词：战斗屏落点 + `LineSlot` 首批成员清单

> `LineSlot` 的成员**不能先于落点定下来**——`enemies/common-properties.md:39` 已明写理由：「先写下一组无消费点的枚举值只会让内容编写者填出永不显示的文本」。故本条先给落点，再给清单。

#### (a) 落点提案：敌人立绘上方的**非常驻浮层气泡**，零新增区、零常驻部件

**`[通行做法]` + `[既有推演]`**

- 形态 = 一个以 anchor 挂在敌方区的 `Control` 浮层，**不进任何 `Container`** ⇒ 出现 / 消失**不触发布局重排**（这是「固定预留高度」那条纪律的另一种兑现方式：干脆不参与布局）。
- 触发时淡入、约 1.5 s 后淡出（初值，待实测）。**不可点、不可关闭、`mouse_filter` 忽略** —— 战斗屏的触控争抢是承重问题，台词绝不能吃掉任何一次点按。
- **与飘字不争位**：飘字跟随对象且短促，台词落在立绘上方的固定锚点。
- **与既定的演出时长上界不冲突：台词与既有节拍并行播放，不新增任何等待节拍。** 敌人回合演出 **≤ 4 s** 的硬上界原样成立——若台词要求额外停留，那条上界就被一条风味元素绕过了。

**`[既有推演]` — 硬纪律：台词永不承载规则信息。**
纯风味。台词一旦能说「我要用大招了」，它就成了「**敌人的行动不作任何事前预告**」这条承重纪律的旁路。此条须与成员清单一起写进文档，否则内容编写者会自然而然地往那个方向写。

#### (b) `LineSlot` 首批成员清单（5 个）与触发时刻

**`[既有推演]`** 五个 slot **全部落在既有的可观测时刻上**（回合边界 / 战斗边界 / 一次结算的收口），**不新造任何时刻**：

| 成员 | 触发时刻 | 依据 |
|---|---|---|
| `OnCombatStart` | 战斗开始、`Power` 入场之后、第一个开始阶段之前 | 战斗前确认页之后的第一个可观测时刻；「首遇的信息差就是这场遭遇的风险定价」——开场一句风味不泄漏规则 |
| `OnFirstEnemyTurn` | 敌方**第一个**回合的开始阶段 | 敌人回合是玩家获取动态情报的唯一时刻，开场白落此最自然。与 `OnCombatStart` 分开，是因为先后手由 `EncounterSpec.FirstSide` 决定，两者不一定相邻 |
| `OnEnemyMomentumLead` | 敌方道念**首次**反超玩家的那次结算收口之后（**一场至多一次**） | 道念对比是主视觉，「反超」是这场唯一有语义的中途分水岭；「首次」封顶避免在拉锯局里刷屏 |
| `OnEnemyDefeat` | 胜负判定为玩家胜之后、奖励面板之前 | 战斗收口的既有时刻 |
| `OnCharacterDefeat` | 胜负判定为玩家负之后、结算面板之前 | 同上 |

**枚举与内容侧纪律：**

- **不新增字段、不新增校验。** `EnemyLine` 保持 `Slot` + `Text` 两格；三条既有加载期校验原样适用（空数组合法 / 同 `Slot` 重复 → `PushError` / `Text` 为 `null` 或默认语言为空 → `PushError` + 抛）。
- **绝不给 `EnemyLine` 加权重 / 条件 / 概率**：那会把稀疏覆写数组变成第二套触发系统，而触发式异能已经是那个系统。
- **新增成员一律追加在枚举末尾**（避免既有 `.tres` 的枚举整数值漂移）；**因此不承诺「声明顺序 = 时间轴」**——首批按时间轴排是为了可读，日后新增的中途 slot 会排在末尾，这一点明写接受。
- **台词是内容层文本，不进 `res://text/`**：它是 `EnemyData` 上的 `LocalizedText`，四问皆是（有 `Id` 的宿主条目、进 ContentRegistry 强校验、需线上可改而不发版）。写作规格归 `enemy-codex`（标为 `[Practice, Standard]` 的条目，其台词须同时说得通「切磋」与「厮杀」）。
- **落点定案后，`enemies/common-properties.md` 的那条待决项即可移出**，`Lines` 从「只能是空数组」解除。

## 备选方案（已考虑并否决）

- **只读层折叠为角标（与随身对称）** — 只读层的价值是常驻可读；`Power` 是整场不变的常驻改写，藏进角标等于逼玩家每回合去查。两层本按「能否被操作」分层，形状不必对称。
- **只读层做横向滚动** — 横滑已被随身抽屉与 eventOption 选择区占为「浏览候选」的语义；且与「拖出手牌区 = 打出」在同一片区域争同一根手指；滚动条也给不出「还有几条没看到」的常驻表达。
- **己方埋伏折叠成一格** — 折叠后没有可寻址的战场条目宿主，服务逐条目填充的启动可供性将永无消费者；要救就得再造一层展开列表，撞「零新增常驻部件」。
- **两级标识用边框色 / 用文字** — 边框色已被卡牌类型占用（同一张小卡面上两套色系必然相撞）；文字撞「中文名不承担层级表达」与「相邻中文名共用字根读不开」两条。
- **战报收起态只写「敌方打出 X」** — 把「我的道念为什么少了 3」这个战报存在的唯一理由整个推给展开态，而玩家不会主动开日志。
- **截断量 / fizzle 在收起态写全括注** — 单行 + 永不换行 + 超长省略下，被省略掉的恰好是括注本身，即那条硬要求。
- **飘字用颜色 / 字形区分疲劳与被削减** — 归因维度已由起飞点承载；再叠一层颜色会与呼吸描边 / 上浮描边 / 灰态降饱和三套状态色争语义。
- **疲劳见底给弹窗 / 音效 / 「大限将至」式预警文案** — `ux/screen-flow.md` 已明写否决同形态（余量既已明文常驻且精确，预警文案没有存在理由）。
- **奖励面板三项横滑** — 横滑是「择一」的语汇，而「不是三选一」是这块的承重语义。
- **已处置项消失 / 移入「已领区」** — 与「面板长度恒为 3」「`picks` 不可增删不可重排」「按 `state` 重建面板」三条同时相抵。
- **已处置项的两键置灰保留** — 灰态纪律要求灰格继续接收触控并给说明，而此处无说明可给；留灰键只会诱导点击。
- **奖励面板与事件结算面板合并为一屏** — 会让「计算归战斗、施加归生命周期」（`D6` 逐次 vs `D7` 一次事务）的分工在 UI 上糊掉。
- **台词加逐动作 slot（`OnCardPlayed` / `OnAbilityActivated`）** — 与飘字 + 战报争同一时刻、吃掉敌人回合 ≤ 4 s 的预算，且会随出牌泄漏规则信息，成为「不作事前预告」的旁路。
- **台词加 `OnLowMomentum`（残血喊话）** — 本作无生命值、道念下限 0 且可回升，「残血」没有对应量；且它天然接近预告下一步。
- **台词加 `OnTurnStart`（每回合）** — 一场触发 5 次，重复度高；稀疏数组的价值恰在「只写要写的那几句」。
- **给 `EnemyLine` 加条件 / 权重 / 概率** — 把稀疏覆写数组变成第二套触发系统，而触发式异能已经是那个系统。

## 与既有决策的张力

1. **「面板长度恒为 3」 vs ⑧ 的「池不足时渲染实际项数、不渲染空占位格」。**
   前者的原句语境是「逐项领取使实际到手项数在 0–3 之间由玩家决定，**面板长度恒为 3、到手数不恒定**」——讲的是**候选算定的项数**与到手数的区别，不是渲染硬约束；而「合法池不足 3 条目时**显式降级**、不静默给 2 项」明确允许候选本身少于 3。
   **建议的松动：** 把该句改写为「**候选项数恒为 3，池不足时显式降级为实际项数**；面板逐格映射 `picks`，不渲染空槽」。**不松动的替代方案：** 渲染一个「本次无第 3 项」的占位行——代价是玩家会读成加载失败，且需要一个新的翻译键与一套空态视觉。**推荐松动**（它只是把既有的降级语义在 UX 侧写清楚，不改任何规则）。

2. **灰态纪律的边界（⑧ 的「已处置项移除控件而非置灰」）。**
   `ux/error-and-blocking-ux.md` 的灰态表整体是「**不隐藏而是置灰**」，本条是它的第一个显式例外。**不构成冲突**——该表的每一行判据都是「暂时不可用 / 必然无结果，但仍是一个入口」，而已处置项**永远不会再可用、也不是入口**。**建议在该表下补一行判据句**：「**暂时不可用 → 置灰并保留触控；已成事实、永不恢复 → 移除控件**」，使后来者不把本条读成漂移。

3. **⑥(b) 收起态带增量 与「飘字为主 + 战报为辅」的轻度冗余。**
   同一个数字在飘字与战报收起态各出现一次。**明写接受**：飘字转瞬即逝，收起态单行是玩家移开视线后唯一的安全网；⑥(a) 的判据分的是「谁**必须**说」，不是「谁**独占**」。

4. **⑤ 的「详情页在敌人回合 / 结算态可开」 vs 随身抽屉 / `Power` 弹层三态全禁。**
   **不构成冲突**，是既有判据（争屏幕 vs 争语义）的一次正常应用，且战报展开态已是同档的先例。**但须把这张三行对照表写进文档**——否则后来者会把它读成「禁用规格不一致」。

## 仍需用户决定

**决定 1 —— 抽牌堆剩余张数是否常驻战斗屏？（`[取向选择]`，与 A1 的分区预算直接相关）**

| 选项 | 后果 |
|---|---|
| **A（推荐）常驻** | 疲劳成为一条**可预算**的账（「还有 N 回合开始扣血」），与「道念差 × 系数 = 掉多少寿元」这本可算的账同调；⑦(b) 的见底预警有载体；⑦(c) 的飘字起飞点有稳定宿主。代价：在压力最大的竖屏上多一个常驻数字（虽然它叠在牌堆对象上、零新增区） |
| **B 不常驻，只在见底前 N 回合出现** | 省下常驻位；但违反「固定预留、不跳位」——一个中途出现的元素正是那条纪律要防的东西；且 ⑦(c) 的飘字起飞点在它出现之前无宿主 |
| **C 完全不呈现** | 竖屏预算最省。代价：疲劳变成突然发生的事；且 ⑦(b)(c) 两条随之作废，飘字侧「疲劳 vs 被削减」的区分要另找方案（只剩颜色 / 字形，而那条已被 ④ 的状态色约束排除） |

**推荐 A。** 但这确是产品取向：以 ch1 起手 4 + 每回合 2 × 5 回合 = 14 张、starter deck 15 张估算，**疲劳在多数场次只在最后一两回合触发甚至不触发** ⇒ 为一个低频但致命的机制花一个常驻位，值不值得由用户定。

→ **已裁决（2026-09-08 · 批量评审）：A · 常驻。** 数字叠在底部条的抽牌堆实体上（该实体由 `solution-draft-combat-portrait-layout.md` 确认存在 ⇒ 本草稿前置依赖 P4 / P5 同时解除，不再需要「并入回合计数区」与「追加静态标签」两个退让位）。⑦(b) 的见底预警与 ⑦(c) 的飘字起飞点按本草稿原文成立。

**决定 2 —— 敌人台词是否进战斗屏？（`[取向选择]`，它决定 `LineSlot` 的成员清单本身）**

| 选项 | `LineSlot` 成员 | 后果 |
|---|---|---|
| **A（推荐）进战斗屏，立绘上方浮层气泡** | 五个（⑨(b) 那张表） | 敌人有了性格，且零新增区、零常驻部件、不吃演出预算。代价：战斗屏多一个会出现 / 消失的视觉对象（虽不进 `Container`、不触发重排），且需要一条硬纪律看住「台词永不承载规则信息」 |
| **B 不进战斗屏，只落战前 / 战后** | 三个：`OnCombatStart`（改落**战斗前确认页**）· `OnEnemyDefeat` · `OnCharacterDefeat`（落**结算面板**） | 战斗屏一格不动，风险最低；`Lines` 同样能解除空数组、`enemies/common-properties.md` 的卡点同样解除。代价：敌人在战斗过程中完全无声 |
| **C 本轮不给落点** | 保持空枚举 | `Lines` 继续只能是空数组，`enemies/common-properties.md` 的就绪度**继续卡在这一条**（本批的一个明确目标因此不达成） |

**推荐 A**（B 是完全可接受的退让位，C 不推荐——它把一个已排期到本专场的阻塞原样退回）。

→ **已裁决（2026-09-08 · 批量评审）：A · 进战斗屏。** `LineSlot` 首批五成员按 ⑨(b) 那张表落笔；立绘**上方**非常驻浮层气泡、≈1.5 s（待实测初值）、不进 `Container`、与既有节拍并行播放，敌人回合 ≤4 s 上界原样成立。硬纪律「台词永不承载规则信息」一并采纳。另一份草稿 `solution-draft-combat-portrait-layout.md` 的槽位契约里写的「立绘旁 / 约 2 s」以本条为准。
