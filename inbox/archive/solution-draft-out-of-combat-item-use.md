# 方案草稿 — `SavePointReason` 增员 `InventoryChanged` 的后端承接

## 问题

`contracts/profile-sync.md` 的上行报文表把 `reason` 定义为 `SavePointReason` 的**枚举名逐字**，并列出五个取值：
`"CycleStarted"` / `"EventResolved"` / `"ChapterBoundary"` / `"CycleEnded"` / `"MetaChanged"`。

客户端侧于 2026-08-28 的批量评审中定案新增第六个成员 `InventoryChanged`（批次层的储物袋操作——战斗外道具使用与随售——
在事件之外发生，没有所在事件的防抖窗口可搭，必须自带一个 reason）。**该枚举以成员名逐字序列化上行**，
故取值清单是两侧共同约定的契约面，**单侧采纳即两侧不一致**。

客户端那一半的完整推演（为什么不复用 `EventResolved`、为什么 policy 是 `Debounced`、它在客户端的触发时机与存档语义）
见 `counterpart`，**本稿不复述**。

## 约束（来自既有设计）

- **`reason` 对后端是日志与聚合维度，不驱动任何判定**——判定只看 `baseRevision` 与 `pushId`（`contracts/profile-sync.md` 明写，
  且明写这一条正是为了防止它日后被拿去做分支）。
- 枚举以**成员名**（非序数）逐字序列化，成员名与 `Source` 同档对待：**第一批存档写下前冻结**。
- 客户端与后端的 `reason` 取值清单**必须逐字一致**，两侧各持 DTO（表达形式 = OpenAPI 3.1 单点）。

## 建议方案

### ① 取值清单扩为六值

`[既有推演]`

`contracts/profile-sync.md` 上行报文表 `reason` 行的取值清单追加 `"InventoryChanged"`，扩为六值。
**这是纯表格增量，不改字段类型、不改必填性、不改任何判定路径**——因为 `reason` 本就不驱动判定。

### ② 未知 `reason` 的识别面：宽容接收 + 记录，不拒绝报文

`[既有推演]` + `[通行做法]`

**建议明写：后端收到清单外的 `reason` 取值时，照常处理该次 push（判定只看 `baseRevision` / `pushId`），
把未识别值原样记入日志与聚合维度，不返回错误、不拒绝报文。**

- 依据是 `reason` 自身的定位——**它不驱动任何判定**。若因一个日志维度取值不认识就拒收一次合法的进度上行，
  等于让一个零判定权的字段获得阻断玩家进度的能力，与该字段的定位直接矛盾。
- 它同时给出客户端 / 后端**发版顺序的自由度**：客户端先上线带新 reason 的版本、后端稍后补清单，期间不产生故障。
  反向（后端先补清单）本就无害。这条自由度在两侧独立发版的强制在线架构下是必需的。
- **代价明写**：清单因此不是一道校验闸，拼错的成员名不会被机械发现，只会在聚合维度里多出一个孤儿取值。
  这是可接受的——`reason` 的消费方是运维观测，孤儿取值在看板上一眼可见，属「只在开发期显形」那一档。

## 具体形态（可 derive 的落地面）

| 项 | 取值 |
|---|---|
| 改动文件 | `contracts/profile-sync.md` 上行报文表 `reason` 行 |
| 改动内容 | 取值清单 5 → 6，追加 `"InventoryChanged"`；另加一句未知取值的处理语义（见 ②） |
| 字段类型 | `string`，不变 |
| 必填性 | ✅，不变 |
| 判定影响 | **无**（`baseRevision` / `pushId` 不受影响） |
| 存储影响 | 无 schema 变更；若 reason 落聚合表，该表需容纳新取值（字符串列，天然容纳） |
| 版本化 | 不 bump 任何契约版本——取值清单增量与「未知值宽容」两条合起来即向后兼容 |

## 后果

- 后端零判定逻辑变更；工作量 = 一处表格增量 + 一句语义补充。
- 采纳后，客户端侧那条「`SavePointReason.InventoryChanged` 须与后端同批确认」的前置依赖闭合。
- **未来同类增员的通道就此定形**：②的宽容语义一旦写下，后续再加 reason 成员不再需要成对发版，
  后端补清单变成纯观测侧的跟进动作。

## 备选方案（已考虑并否决）

- **未知 `reason` → 返回错误 / 拒绝报文** —— 让一个零判定权的日志维度获得阻断进度的能力，与该字段的既有定位矛盾；
  且强制两侧成对发版，在独立发版的架构下是一处不必要的耦合。
- **把 `reason` 改为开放字符串、取消清单** —— 清单虽不是闸，但它是两侧对齐的唯一书面依据，取消后拼写漂移无从对账。
- **后端按 `reason` 分支处理（例如对 `InventoryChanged` 走不同的合并窗口）** —— 直接违反「`reason` 不驱动任何判定」，
  而那条正是为防止此类分支而明写的。

## 与既有决策的张力

无。本方案不触碰任何既有判定路径，且 ② 的宽容语义是对「`reason` 不驱动判定」这条既有决策的直接落地，而非松动。

## 前置依赖

- **本方案的取值清单增量须与 `counterpart` 的 `SavePointReason` 增员同时采纳**——
  单侧采纳即两侧不一致（客户端发出后端清单里没有的取值，或后端登记了一个客户端永不发出的取值）。
- 成员名 `InventoryChanged` 的最终拼写以客户端侧冻结时的成员名为准（**第一批存档写下前冻结**）。

## 仍需用户决定

无。两条建议均可由既有决策直接推出（`reason` 的零判定定位 + 两侧独立发版的现实），不含取向选择。
