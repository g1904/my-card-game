# 定案草稿 — 战斗呈现

> 原始想法记于 2026-08-23，经 2026-08-24 设计讨论逐条裁决定案，2026-08-25 批量 interview 修正两项载体问题、同日二次评审重构第 3 / 4 条。呈现哲学：**卡面极简，信息后置到详情页与战报**。

## 定案

### 1. Gwent 式 full art 卡面
`[用户拍板]` 卡牌为全幅插画，卡面**只显示 `manaCost`**——无规则文字、无名称。规则描述、卡牌名称等一律在点击后的详情页显示。

**与三条要求卡面带文字的既有定案的处理（08-25 裁定）：以 full art 为准，三条换载体不换要求。**
- 「关键字在卡面只印名字，完整定义走长按」→ 关键字名与完整定义**一并移入详情页**，长按对象随之移位。关键字定义「永远长按、首次出现不自动展开」这条机制不变。
- 「多目标槽位的询问顺序 = 卡面文案顺序 = `slotIndex`，卡面文案必须点名各槽位的类别」→ 槽位类别的告知责任**交给选目标态的指令条**（既有部件，已定「必须自解释——交代是哪张牌 / 哪个异能在要求选目标、它要做什么」，且已有固定位置与连锁进度指示）。不新增任何部件。
- `Power` 的「卡面明示」内容侧纪律 → 改为**详情页明示**，纪律与「代码不加硬规则保护、只留软检查」原样成立。
- **不冲突、已核实：** 卡框色 + 类型角标是呈现层 UI 叠加，与插画分开（既有已定「UI 元件与框架与插画分开，UI 需要可九宫格拉伸，不适合整图生成」），与 full art 相容。

**硬约束（随 full art 直接推出）：插画内不得烧入任何文字 / 字符。** 卡名 / 规则文字若烧进插画，等于把语言数焊进美术资产——切语言时静默留中文，且失去热更通道，与「UI 文案一律走翻译键」的承重纪律相抵。这条须写进卡面类 art guide 的公共约束。
**连带：** 既有硬约束「缩略可辨——手牌区的卡面很小，主体必须在缩略尺寸下仍能辨认」在 full art 下**从硬约束升级为唯一识别手段**（无卡名可读，插画是玩家在手牌区认牌的唯一通道）。`art/visuals/art-direction.md` 与 guide 模板中「留白与文字区预留」两处待填占位符，本次填为「**卡面不预留文字区（full art）**」。

### 2. 手势分工：点按 = 详情，拖出 = 打出
`[用户拍板]` 卡面无文字使「点按看详情」成为刚需，必须与出牌手势显式分工：**点按手牌 = 升起详情页；拖出手牌区 = 打出**。符合触控规则「无仅悬停可供性」。

**与既有「长按 = 详情」的关系：按「是否可拖拽」分化。** 卡牌点按开详情；关键字定义 / `Power` 详情 / 灰显道具原因三处仍为长按。判据明写：**可拖拽的对象用点按开详情，不可拖拽的用长按**——卡牌是手牌区唯一同时承载拖拽的对象，长按与拖拽起手在同一根手指上争同一段时间窗；其余三者均不可拖拽，长按无冲突。这是有判据的分化，不是漂移；须在文档中写下该判据，否则日后读者会当成漂移。
**详情页复用既有 bottom sheet 控件语言**（战斗屏已有随身抽屉与图鉴两处），不另造控件；在结算 / 选目标态中的可用性按既有两处同款处理。选目标态中手牌的点按语义被该态独占（`HandCard` 槽位使手牌可成为合法目标）。

### 3. 结算呈现：逐层弹栈 + 短暂强调，不做滚动播报
`[用户拍板 · 08-25 修正载体]` 结算 = 显示栈上的卡牌 / 效果，然后**逐层 LIFO 弹出，每弹一层做一次短暂的视觉强调，弹完即落账**——不可暂停、无滚动播报流，但保留因果顺序的可见性。

**节奏参数直接复用既有那套，不另立：** 单步节拍 0.35–0.5 s（草稿的「几百毫秒量级」正落在此区间）· 超过 4 步后压到 0.2 s 并合并同来源 / 同类型 / 同符号的连续增量（跨来源不合并）· 点按屏幕任意处 3× 加速（只能加速不能跳过）· 永久快速演出为设置项（默认关）。**这三重护栏同时答掉「栈深很大时总时长是否失控」**——栈深大时总时长次线性增长。
**「不可暂停」不推翻挂起态：** 它读作「无玩家侧的暂停 / 跳过控件」；结算中途停下来问「指谁」是规则层的停顿 + 玩家的一次真实输入，不是暂停。既有「结算动画必须能在中途停住、进入可交互的选目标态，再继续弹栈」原样成立。

### 4. 战报（`combatLog`）：ticker 与 stackHistory 收编为同一个对象
`[用户拍板 · 08-25 二次评审重构]` 既有的**结算 ticker** 与草稿提出的 **stackHistory** 不是两个部件，而是**同一份数据的收起 / 展开两个视图**——既有 ticker 本就定义为「默认显示最近一行，点按展开完整日志」，与「显示最近的结算记录、点开看详细」逐字同构。二者**合并定名为「战报」`combatLog`**，此后文档中不再出现 `ticker` 与 `stackHistory` 两个名字。草稿字面的「不做 ticker」据此改读为「**不做滚动播报式的 ticker**」。

- **收起态（常驻）** = 固定预留高度的**单行**，显示最新一条战报条目。
- **展开态** = 本场战报的**因果树**（形态见下）。
- **竖屏净增 0 个区**：合并前后都只占既有 ticker 那一格。
- **由此全部成立且无需改写的承重条目：**「敌人回合的逐步执行呈现是硬要求——飘字为主 + 一条日志为辅，两者都要」「截断量必须被说明」「fizzle 必须被说明」「常驻占固定预留高度，防手牌区跳位干扰拖拽出牌的肌肉记忆」——最后这条正是第 2 条「拖出手牌区 = 打出」所依赖的。`MomentumDelta.Declared` / `Actual` 这对承重字段的载体不变。

**① 条目粒度 = 结算事件，不是卡牌。** 参照炉石的出牌记录区：卡牌结算、触发式异能、疲劳扣减各占一条，保证「我的道念为什么少了 3」有账可查。

**② 展开态是因果树，不是扁平列表（本条是相对炉石的实质升级）。** 按**一次结算批次**分组并缩进——一次出牌与它引发的整条触发连锁归为一组：

```
第 3 回合 · 我方
  打出「叠嶂符」
    └ 触发「山岳共鸣」      对方道念 −5
    └ 削减 8（对方仅剩 5，溢出 3 未结转）
第 3 回合 · 敌方
  打出「回风诀」
    └ 目标已不存在（未生效）
```

- **它顺带答掉 `ux/combat-ux.md` 的待答项「栈与战场的连锁可读性」**：玩家读不懂触发连锁的原因是看不到「谁引发了谁」，扁平列表给不出这一层。
- **实现零新增存档字段**：栈条目本就有 `stackEntryId`，战报条目带一个 `causeEntryId` 指向它，树是白拿的。

**③ 保留本场全部条目，不设 10 条上限。** 战报不进存档（见下），故上限省的是**内存**而非存档体积；一场 `Standard` 是 10 回合、量级不过几十条结构化条目（几 KB）。**设 10 条上限恰好废掉本条自己的理由**——「第 3 回合我的道念为什么少了 3」正是要翻回去才答得出的问题。展开态**按回合分组**、默认定位到最新一条。

**④ 不进战斗存档。** 退出重进后战报从空开始，代价明写接受——「自解释」这条硬要求的承担者是**选目标态指令条**而非战报，它本就不依赖战报。依据既有先例「为一条呈现便利新增一个存档字段不划算」，以及 `ActiveCombat` 的量级护栏与「本块新增的字段只有一格」的克制取向。

**⑤ 展开态随时可开，且不暂停演出。** 结算动画进行中点开战报 → 列表照常流式追加新条目，演出不停、不设暂停控件（与「不可暂停」一致）。
**与「随身抽屉 / 敌人图鉴在结算态与选目标态禁用」的判据分化明写：那两个是可能改变局面的入口（用道具、点按语义与选目标态争抢），战报是纯只读、无任何可供性**，故不禁用。这是有判据的分化，不是漂移。

**⑥ 双方回合都常驻（修正既有适用面）。** 既有 ticker 写的是「**敌人回合**常驻、玩家回合容器内容整体清空」；合并后战报在玩家回合同样有内容（自己打出的牌与触发链）。`ux/combat-ux.md` 相应条目须改写为**双方回合都常驻有内容**；**固定预留高度那条纪律原样保留**（理由是防手牌区跳位干扰拖拽，与归属方无关），只是「玩家回合内容为空」这一句作废。`systems/services/combat-service.md` 侧已写「适用面由敌人回合推广到双方回合」，UX 侧此前漏改。

**⑦ 不上提为跨事件类型的 `eventLog`（承重边界）。** 战报只属于 Combat，**不外延到 Exchange / Research / Explore / Travel**。三条理由：
- **会制造第二权威。** `PastEventEntry`（`SelectCost` / `AppliedChange` / `EventOutcome` / `Unchosen`）已经是「一个事件里发生了什么」的事实来源，且已被剧本调制、履历、诊断三方消费，08-15a 后更升为 future-event-service 的一等输入。再立一份「记录事件中有意义的决策」的日志 = 同一批事实的第二份表，两份各自漂移而无机制发现。
- **非战斗事件没有可记的时间轴。** 其余四类都是单决策点事件（择一 → 结算 → 收口一次 `TryApply`）。战报存在的两条前提——**LIFO 栈使因果链长于 1**、**敌人不作事前预告故事中呈现是唯一情报通道**——一条都不外延。
- **非战斗事件里唯一「值得记」的东西恰好必须隐藏。** 玩家自己选了什么他知道；他不知道的是道心 / 煞气 / 寿元被推了多少、剧本被怎么调制——而 `plot-manager.md` 承重定案是「给方向不给数字，**调制才是隐藏属性的主要显影通道**，中间档跨越对玩家完全无提示」。诚实的 `eventLog` 会掀开这层；不诚实的只剩「你选了 A」这种零信息条目。

> **一句话纪律（写进文档，用来挡住日后复发）：一个权威、两种寿命——事件内的过程态是纯呈现层、不落存档（战报）；事件间的账目归 `PastEventEntry`、落存档。**

**⑧ 术语登记：** 中文定名「**战报**」，标识符 `combatLog`。它记的是**已弹出**的东西，与既有已定名的 `stack`（堆栈，等待结算的队列）是两个对象，不冲突。
**不用 `eventLog` 这个名字**——本作已有三个 "event"（`EventBus` / `AdventureEvent` / `PastEventEntry`），第四个会让 `terminology.md` 无法写清。

### 4b. 战报的工程形态：统一的呈现事件流（feed），不是一个日志实体
`[采纳推荐]` 疲劳需要一条不是 `PlayResult` 的可呈现事件——这个症状说明正确的抽象是**一条喂给呈现层的事件流**，而不是「日志」这个实体。

- **在 `systems/services/combat-service.md` 事件面上定一条统一广播 `CombatFeedEntry`**（`readonly record struct`），**卡牌结算 / 触发式异能 / 疲劳扣减 / fizzle 四类全部走它**。既有承重「疲劳不入栈、不产生 `PlayResult`，是抽牌流程内的一次直接扣减」不改——它只是同样广播一条 feed。
- **三个消费者读同一条流**：飘字 · 战报收起态单行 · 战报展开态因果树。**现状是三处各自从 `PlayResult` 里捞，迟早不一致。**
- **负载只带 `Id` 与值类型，不带 `CardInstance` 引用**——与既有 `CardResolved` 同款理由（热路径 + 不吊住已被移除的实例）。字段面：侧别 · 类别 · `causeEntryId` · `Declared` / `Actual`。
- **条目存结构化数据，不存已格式化的字符串。** 热路径不做 `string` 拼接（`.claude/rules/csharp-godot-rules.md`），且**渲染期才套 `res://text/` 翻译键**——否则战报会成为本作最大的一处文案字面量泄漏源（`ui-input-rules.md`「UI 文案一律走翻译键」）。这条须明写，实现时不写就一定会被写成拼字符串。
- UI 端持一个环形缓冲即可，容量按 ③ 覆盖本场。

### 5. 道念显示位：角色头像下方
`[用户拍板]` 类似 MTGA 对战布局——道念即本作的比分 / 生命值位，双方各随其头像展示。

**与既有「道念对比条」不互斥：** 道念是一条横贯的对比元素，双方头像与数值分居其两端，两者同时成立。既有三处以「道念对比条」为单一元素的布局纪律（结算记录紧贴其下 · 暗幕豁免 · 压缩顺序最后动）**原样保留，只改指称**为「双方道念位」。
**玩家侧需要一个头像位**（既有战斗屏只写了敌人立绘）；玩家侧头像不承担图鉴入口，只作道念的锚点。
