# 方案草稿 — 透明路径的集合字段命名：复数 → 单数

> **本草稿是跨边界承接的对侧那一半。** 客户端侧的字段 schema 本体在 `counterpart`，本文件**只承载归属后端的那一半**（透明路径白名单、复算校验、契约版本化）。
> 客户端的字段语义、层归属、存档形态一律**回链**、不复述——抄过来即制造第二权威。

## 问题

客户端在 2026-08-17 的批量评审中裁决了一条命名取向：**集合字段名全库统一为单数**（`pastEvent` / `achievement` / `disabledAbility` / `plotKeyPoint` 的既有风格，新字段一律沿用）。

这与本库 `contracts/profile-sync.md` §5 已冻结的透明路径直接冲突——该表当前**两种风格并存**：

| 当前形态 | 风格 |
|---|---|
| `/playerPowers[*]/id` · `/playerPowers[*]/sourceCode` | 复数 |
| `/playerItems` | 复数 |
| `achievement` · `disabledAbility`（§5 的「不在透明子集内」清单） | 单数 |

§5 的**透明路径稳定性纪律**明写「移动或重命名任一透明路径 = 破坏性契约变更」⇒ 客户端那条裁决**不能只在客户端落地**。

⚠ **客户端侧已知悉并推翻了相反的推荐。** 该草稿原推荐「以契约为准、库内保留两种风格并存」，理由是「透明路径重命名有硬后果、库内风格没有，两侧硬度不对称」；用户明确选择了改契约。本草稿**不重开这场论证**，只承接后果。

## 约束（来自既有设计）

- **透明路径重命名 = 破坏性契约变更**，须 bump `schemaVersion` 且两侧同批改。权威：`contracts/profile-sync.md` §5。
- **`playerDiff` 顶层键整键替换、键值以下完全不透明**（后端不递归、不比对、不校验）⇒ 改名只影响**白名单里被点名的那几条路径**，不影响不透明段。权威：同上 §3。
- **`/playerPowers[*]/sourceCode` 是 `x = count(sourceCode == "FinaleWin")` 的计数对象**，`/playerPowers[*]/id` 是 `x` 的计数依据 ⇒ 改名直接触及残卷复算链路。权威：同上 §5。
- **复算不一致的处置是「仅记账 + 上报风控，不拒绝、不改写」**（§7a）⇒ 过渡期若两侧不同步，**症状不是报错而是风控噪声**，这正是「静默失效」的具体形态。

## 建议方案

### 1. 白名单逐条改名，一次性、不设兼容期
`[既有推演]`

| 现路径 | 建议路径 |
|---|---|
| `/playerPowers[*]/id` | `/playerPower[*]/id` |
| `/playerPowers[*]/sourceCode` | `/playerPower[*]/sourceCode` |
| `/playerPowers[*]/status`（§5 的排除项） | `/playerPower[*]/status` |
| `/playerItems`（§5 的排除项） | `/playerItem` |

**不设「两个名字都认」的兼容期。** 依据是 §7a 的处置语义：不一致既不拒绝也不改写，**兼容期内没有任何信号能告诉任一侧「对方还没改」**——兼容期在这里不是安全网，而是让不一致变得永久不可见。一次性切换 + bump `schemaVersion` 才有硬信号。

**不影响的部分（明确划界）：** §5 的其余透明路径（`/playerPowerFragment/*` · `/entitlement/bundleGrantOrdinal`）均非集合字段，**一格不动**；不透明段（`characterDiffs` 整体）本就不被后端解析，零影响。

### 2. 顺带消除 §5 内部的风格并存
`[既有推演]`

改完后 §5 内的集合字段全部为单数（`playerPower` / `playerItem` / `achievement` / `disabledAbility`），本库不再需要为「为什么这两个是复数、那两个是单数」写任何解释。**这是本次改动唯一的正收益**，值得在 §5 明写一句命名通则。

### 3. 版本化与切换时序
`[取向选择]` —— **待后端裁决，客户端不代为决定**

`schemaVersion` bump 已是定局；未定的是**切换时序**。两个选项：

- **A（倾向）线上无真实账号 ⇒ 直接切，不写迁移。** 前提是后端确认当前无生产数据。代价：零。
- **B 走一次带版本判别的双读期**（后端按 `schemaVersion` 决定读哪个键名），切换完成后删除旧分支。代价：一段注定要删的代码 + 一条要记得关闭的开关；仅在已有真实账号时才值得。

**判据在后端侧**（只有它知道线上有没有数据），故本草稿不选。

## 第二条承接项 — 残卷侧 `ordinal` 口径确认

`[既有推演]` · **可能无需任何改动，只需一句确认**

客户端同批裁定：残卷侧统一为「**先算 `ordinal = 旧值 + 1` → 掷骰 → 同一次 `TryApply` 写回**」（礼包侧此前已明写，残卷侧此前只是未明写，属补写既有意图）。

核对本库 §7 的复算伪码：

```
lastRoll = AccountRandom(accountSeed, PowerFragment, finaleWinOrdinal).Next() mod 10000
后端在 finaleWinOrdinal 递增的那一次 push 上：① 自算 roll' = SplitMix64(accountSeed, PowerFragment, finaleWinOrdinal) mod 10000
```

⇒ **本库读的正是递增后的 `finaleWinOrdinal`，与客户端补写的口径一致。** 本条**很可能是零改动的确认项**，登记在此只为留下痕迹：客户端此前该口径未明写，两侧曾各自依赖一个未落纸的默认。

**请后端确认**：§7 校验 ①/②/③ 的三条是否确实按「递增后的值」实现与描述。若是 → 本条直接关闭，记进 `answer-logs/`。

## 后果

- `contracts/profile-sync.md` §5 白名单四行改名 + `schemaVersion` bump + 一句命名通则。
- 残卷复算（§7）的字段引用随之改名；**算法与向量表一字不动**（`accountSeed` / `stream` / `ordinal` 三参数派生不受影响，§6a 的 8 组测试向量继续有效）。
- 客户端侧对位改动见 `counterpart`，两份须**同批采纳**——单侧采纳即两侧不一致，且按 §7a 该不一致**不会报错、只会产生风控噪声**。

## 备选方案（已考虑并否决）

- **让客户端在上行组装时做一次名字映射**（库内单数、线上复数）—— 否决：这正是本库反复避免的「同一对象两个名字 + 一层翻译」，且映射表本身会成为第二权威。
- **维持契约不动、客户端保留两种风格并存** —— 否决：这是客户端侧原推荐项，用户已明确推翻。记录于此仅为溯源。

## 与既有决策的张力

**透明路径稳定性纪律 vs 本次改名。** 该纪律的用意是「不要轻易动」，不是「永不可动」——本次是一次**有明确理由、一次性、且线上大概率无数据**的改动，属纪律允许的破坏性变更路径（bump + 两侧同批）。**代价须明写**：这是该纪律成文以来的第一次实际行使，日后若被援引为「改名不难」的先例会侵蚀它，故落笔时应同时写明「本次成立的三个前提」（线上无数据 · 两侧同批 · 一次性不设兼容期），缺一即不成立。

## 前置依赖

- **线上是否已有真实账号数据** —— 决定第 3 节取 A 还是 B。**只有后端能回答。**
- 客户端侧 `counterpart` 草稿的提炼进度：两份须同批落笔，任一侧单独提炼都会制造一段两侧不一致的窗口。

## 仍需用户决定

- **第 3 节的切换时序（A 直接切 / B 双读期）** —— 判据是线上有无数据，归后端。
- **残卷 `ordinal` 确认项**：§7 是否确按「递增后的值」实现？是 → 关闭；否 → 升级为一条真正的契约缺陷（它会在每个正常账号上稳定误报）。
