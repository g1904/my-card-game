# 方案草稿 — 道具族的供给护栏（回寿法宝之外的其余族）

## 问题

`2026-09-09e` 把**回寿法宝**这一族的护栏答全了：四条获取通道逐条给闸（① 开局三选一 ② 商店库存 ③ 事件产出 ④ 战后奖励池），三格编排口径 **L-1 出现频率 / L-2 库存深度 / L-3 定价**，外加取池侧排除 **L-0**。

仍悬着的是同一句话里的另一半：**其余道具族的同三格口径**——

1. 哪些事件给道具、给几件（通道 ③ 的量）；
2. 商店库存里**各族**的深度（L-2 只给了 `CharacterItem` 一族的 ≤ 3，其余四个 `ExchangeGoodsKind` 族空着）；
3. **置换对价**（法宝置换池与 barter 格都没有任何频次 / 价值口径）。

另有一处已登记的待校准：道具侧回寿的期望供给低于 `R_item,c` 分账目标，收口旋钮三选一未择。

**本草稿的主张（先说结论）：** 「其余道具族」这个提法本身需要先被拆开。按本库既有的值域，道具能表达的功能族只有两个来源——战斗外的 `OutOfCombatUseOutcome.Elements` 可写的资源 key，与战斗内的 `CombatUseEffects` 八原语。把**事件侧已经定过的那张可写 key 白名单原样搬到道具侧**之后，战斗外只剩「回寿」一个族（其口径已答定），战斗内的族则由既有的 `itemPowerRatio(Charges)` + 25 格定价表 + 稀有度权重表完整承接、不需要第四套口径。**待答的三格口径因此塌缩成三件具体的事**（事件产出量 / 五族深度分配 / 置换对价），而不是「逐族各写一套 L-1/L-2/L-3」。

## 约束（来自既有设计）

- **道具族的枚举不是自由发明的。** 内容类型登记表里，`ItemData` 只有两个 `Scope`（法宝 `character-item/` · 古宝 `player-item/`），没有第三个道具类型（`content/_index.md`）。族的第二个轴只能是**效果值域**：`UsableScene` 三档 × 两格使用效果面（`systems/character-profile/item/_index.md`）。
- **战斗外效果面只开三列**：`Elements` / `CodexElements` / `Stats`；其余十列恒空 + 加载期 `I-5` 断言（同上）。
- **`Elements` 受 `ResourceElements` 表约束**，但**道具侧目前没有 key 白名单**——`CostKey` 十五个成员里任何一个都写得出来（`systems/architecture.md`）。
- **事件侧有这张白名单，而且是承重表述**：`OutcomeRule.FixedResource` 的 `ResourceKey ∈ { LifeSpan, ManaLimit, SpiritStone, ImmortalJade }`；**`ExperiencePoint` / `Faith` / `Bloodlust` 明确不在内**，只能由物化组装从 `ExperienceGrade` / `HiddenStatGrade` 的平衡表映射展开（`systems/adventure-event/common-properties.md`「模板侧的产出格」校验 2 与其后的承重段）。
- **`ManaLimit` 的单次变动幅度恒为 1**，事件侧另有一条同源闸（校验 3）；`ResourceElements` 该行两个修正列与 `Set` 全部封死（`systems/services/profile-service.md`）。
- **灵石 ≈ 战利品，战斗是主产出口，非战斗事件默认不给**（`systems/balance.md`「货币产出与定价」渠道口径 + 加载期软校验 C-2 / 校验 9）。**仙玉一格都不落 `CharacterItem` 族**，售出侧因此结构上不产仙玉。
- **单个 Exchange 事件的槽位总数上界建议 ≤ 8**（`StockRules` 的 Σ`SlotCount`，加载期校验）；`CharacterItem` 族已占 ≤ 3。闸 ① 逐 `Kind` 逐 `RarityTier` 档位核算，另需 `ExchangePoolMargin`（`systems/adventure-event/exchange/common-properties.md`）。
- **战后奖励的首批条目数矩阵**（全库启用条目数）：法宝 20/11/5/2/1 = 39 · 神通 —/—/—/2/2 = 4 · 散牌 2/1/1/—/— = 4 · 功法 —/—/1/—/— = 1（`systems/balance.md`「战后奖励的内容编排口径」）。
- **置换的同池判据 = `(CarrierKind, Scope)` 全同 + 同 `Rarity` + 排除已持有**，四个独立池，先看后决、拒绝无代价；**「失去能力的频次预算」的三支持久支只含法则置换 / 法则禁用 / 神通置换+禁用，法宝置换不在其中**（`systems/player-profile/player-power/_index.md`）。
- **barter 点名定值、不经池、不读定价表、不参与任何一格核算，且明确不设条数上界**（`systems/adventure-event/exchange/common-properties.md`）。
- **`R_c` 的两格是替代关系、Σ 不变**，`R_event,c` = 50/58/159、`R_item,c` = 50/58/158；λ 与 21 格 `lifeSpanCost` 定价表因此零改动（`systems/balance.md`）。

## 建议方案

### 1. 把事件侧的可写 key 白名单原样搬到道具侧（承重的那一条）

`[既有推演]`

**新增加载期校验 `I-13`：`OutOfCombatUseOutcome.Elements` 中任一行的 `Key ∉ { LifeSpan }` → `PushError` + 条目 `Id` + 报出该 `Key`。**（`ManaLimit` / 两种货币是否加回，见下方 1b / 1c 与「仍需用户决定」。）

三条依据，逐条对应既有承重表述：

- **① 事件侧已经答过同一个问题，答案是白名单而不是「受 `ResourceElements` 约束」。** 「**「物化后可出现的 key」与「模板可声明的 key」是两张表**；写成一张即让内容作者能落裸数字，同一个产出当场有两个书写位」——`OutOfCombatUseOutcome` 是**内容侧模板**（`item/_index.md` 原话），与 `OutcomeRule` 同层同性质，没有理由适用不同的表。
- **② 不补这条白名单，三个已封的口全部从道具侧重开。** 逐条点名：
  - `ExperiencePoint` —— 事件侧只能走 `ExperienceGrade` 枚举档 + 平衡表映射；一件「悟道丹 +30 经验」的法宝当场是裸数字的第二书写位，且直接改写 `G_c` 供给账（该账的 A3 断言当前三章均已跌破下沿 1.09/1.10/1.12）。
  - `Faith` / `Bloodlust` —— 隐藏属性只能走 `HiddenStatGrant(Stat, Grade, Direction)` 的档位映射；道具侧的 `Elements` 是绝对量值，写下即绕开档位表，且逐篇章推拉供给对账（道心携带面 18–20 事件 / 篇章）当场失真。
  - **账号层的六个 `CostKey`**（`PowerFragment*` × 5 · `BundleRedeemedOrdinal`）—— 一件写 `PowerFragmentAccumulated` 的法宝就是一条绕开残卷机制的道统碎片通道，而 `AbilityElements` 恒空那一格封的正是这一类（「一件可购道具若能直接给法则，那两套约束全部旁路」）。**这是当前形态下最严重的一个洞**：它连风味理由都没有，纯属白名单缺失。
- **③ 它让「其余道具族的三格口径」这个问题自己收敛。** 战斗外可表达的功能族 = 白名单的长度；白名单收到 1 ⇒ 战斗外只有回寿一族，而它的三格口径已答定 ⇒ 不需要为不存在的族写口径。这与「不设 `Abilities` 一格」那条的形状完全一致：**把写不出来当作护栏，而不是写得出来再加校验**。

**代价明写（被接受）：** 内容侧从此编排不出经验丹 / 静心符 / 血煞珠 / 碎片袋这四类风味的**道具形态**；同名风味改由事件承载（经验走 `ExperienceGrade`、道心煞气走 `HiddenStatGrants`），两处都在账内。

### 1b. `ManaLimit` 不加回白名单（灵台丹一族不编排）

`[既有推演]`

**建议 `ManaLimit` 同样落在 `I-13` 的拒绝面内**，两条依据：

- **载体判据不成立。** 「什么该做成一件法宝」的判据是「**有明确的使用次数上限、由玩家主动在某一刻花掉**」，`Charges` 是节流阀。而 `manaLimit +1` 是**永久增量**：花掉一次得到一个不再消失的提升，节流阀名存实亡——它在载体判据上属于神通 / 法则那一侧，不属于道具侧。
- **预算已被事件侧铺满。** `manaLimit` 一章的推拉预算是净增 **+1~+2**，且 mana.md 已给出逐事件类型的分档表（含 `Finale` 每篇章一次 +1 的保底）。道具侧再开一条即账外增量，而三章末推算「恰好饱和」正是这条预算被守住的结果——溢出即「有 mana 没牌打」，两条成长通道在后三分之二的游戏里同时失效。

**若日后确要开**（记下条件，免得重开会）：须同时补三样——`|BaseValue| == 1` 的加载期闸（与事件侧校验 3 逐字同构）· `Charges == 1` 强制 · L-0 同构的免费通道排除。三样缺一，`manaLimit` 的推拉预算即不可复算。

### 1c. 货币产出的法宝：建议整族关闭（此项列入「仍需用户决定」）

`[取向选择]`（详见下方「仍需用户决定」第 1 条）

推荐**关闭**（即 `SpiritStone` / `ImmortalJade` 也不加回白名单），三条依据：

- **商店侧结构上无意义。** 定价表 `CharacterItem` 五档恒收灵石 ⇒ 一件产灵石的法宝是「用灵石买灵石」：产出 < 价格则无人买，≥ 价格则是套利。任何定价都落在这两侧之一。
- **免费通道上它是账外的 `I(c)` 增量。** `I(c)` 的式子只含 `BaseReward` + 道念差加成 + 事件 outcome 灵石，道具产出不在其中；而战后奖励一轮回给出 ≈ 18.5 件法宝，量级远大于「非战斗事件默认不给」这条口径所防的那些例外。
- **仙玉尤甚。** `J(c)` 三章仅 ≈ 2 / 3 / 5 枚，一件产 1 枚仙玉的法宝即占一章收入的 20–50%；这与「仙玉一格都不落 `CharacterItem` 族」那条**结构性关闭**同向——那条的理由（这个量级上统计校准把关不可靠）在道具产出侧逐字成立。

**代价：** 编排不出「灵石袋 / 储物锦囊」这类风味；改由 Combat 的 `BaseReward` 与事件 outcome 承载（两处都在账内）。

### 2. 战斗内的道具族不需要第三套口径

`[既有推演]`

`CombatUseEffects` 能表达的族由八原语给出，逐条核对已有的承接者：

| 战斗内功能族 | 原语 | 谁在管它的量 |
|---|---|---|
| 道念产 / 削 | ① `ModifyMomentumEffect` | `itemPowerRatio(Charges)` 判据式 + `baseMomentum` 主刻度 |
| 牌流（抽 / 弃 / 挪） | ② ③ ⑦ | 同上（效果量换算经三张标定台账） |
| 法力 | ④ `ModifyManaEffect`（改 `currentMana`，**不改 `manaLimit`**） | 同上；不触碰 1b 的预算 |
| 持续状态 | ⑤ `ApplyStateEffect` | 同上 + 关键字准入 |
| 移除 / 驱散 | ⑥ `RemoveEntryEffect` | 同上 + `IsProtected` |
| counters | ⑧ | **写不出来**（`I-9` 已封：道具没有宿主 `AbilityData`，键拼不出） |

**判据（把它写下来，日后新增原语时照着核对）：一个道具功能族需要独立的供给护栏，当且仅当它产出的量进入某条已被反推封账的预算线**（λ 反推的寿元账 `B_c`/`R_c` · 货币账 `I(c)`/`J(c)` · 经验账 `G_c`/`D_c` · 卡组规模口径 15 → 18–22）。战斗内的六族一条都不进——它们的产出**随战斗结束一并消失**，不落 Profile、不跨事件、不进任何一本账。故它们由「强度」维度的既有三件套（折价系数 · 定价表 · 稀有度权重表）完整承接。

**推论：三格口径里的 L-1（出现频率）在战斗内族上退化为「族占比 + 条目数矩阵」，那已经是既有物**（法宝一族 39 条、逐档 20/11/5/2/1）；**L-3（定价）退化为「读表、不填 `PriceOffset`」**，也已是既有物。战斗内族**只欠 L-2 的那一半**，即下方第 3 条。

### 3. 商店库存深度：五族的分配表（补齐 L-2）

`[既有推演]` + `[通行做法]`

**单个 Exchange 条目内，逐 `Kind` 的 Σ`SlotCount` 建议上界：**

| `ExchangeGoodsKind` | 建议 Σ`SlotCount` / 店 | 依据 |
|---|:--:|---|
| `CharacterItem` 法宝 | **≤ 3**（已定 L-2，不动） | 既有 |
| `Card` 散牌 | **≤ 2** | 池分母只剩游离散牌（首批 4 条，Tier1/2/3 = 2/1/1）；且卡组规模口径「一轮回全部产出通道合计 +3 ~ +7 张」中战后奖励已占 ≈ 1.9 张 |
| `CharacterPower` 神通 | **≤ 1** | 池只有 4 条（Tier4 / Tier5 各 2）；逐档核算 + `ExchangePoolMargin` 下深度 2 即在启动期被闸 ① 拦住 |
| `CultivationTechnique` 功法 | **≤ 1** | 池首批 1 条，且分母须按**可修条目最少的那个灵根**收缩；另有「一次轮回至多一门功法从任一通道进组」的卡组规模硬约束 |
| `PlayerItem` 古宝 | **0** | 「规则层开放，首批内容不编排」是既定内容口径 |
| **Σ 上界** | **7** | 留 1 格余量给 8 的总上界 |

- **上界之和 7 ≤ 8 是有意的**：总上界那一格是**快照体积**护栏（`sync-service` 已有体积护栏），逐族上界之和顶死它会让两条校验永远同时触发，其中一条从此没有独立信息。
- **它与 L-2 同款处置：`/audit-content` 的一项汇总、只报告不阻断**，理由与 L-2 一字不改（编排口径，不是数据合法性；Σ`SlotCount` ≤ 8 那条硬校验照旧）。
- **不为逐族上界新开字段**：它按 `ExchangeSpec.StockRules` 的 `Kind` 分组求和即得，与闸 ① 的分组是同一次。

### 4. 事件产出侧给道具的量（补齐通道 ③）

`[既有推演]`

载体是既有的 `OutcomeRule.Kind == GrantFromPool` + `PoolKind == CharacterItem`（`PoolKind` 已收窄为能力族两值，`PlayerItem` 直接拒绝）。建议口径：

| 口径 | 建议值 | 依据 |
|---|---|---|
| 期望到手件数 | **≈ 1.5 件 / 完整轮回** | 见下方三条 |
| 每条规则的 `Count` | **恒 1**（编排口径，不改 `Count >= 1` 的既有校验） | 「一颗 = 一档」的可读性纪律；数量语义已由储物袋按 `ItemId` 堆叠 `×N` 承载 |
| 旋钮 | 带 `GrantFromPool(CharacterItem)` 的 `AdventureEventData` 条目数 × 各条的 `SelectionWeight` 档 | 与「失去能力的频次预算」的旋钮形态逐字同构：**零字段、零校验、零状态位** |
| 首批等价形态 | 每篇章 **1 条** `Rare` 档条目 × `Count = 1` | 三章 ≈ 1.5 件（`Rare` 档不保证每章命中） |

三条依据：

- **事件位是全局最稀缺的资源。** 一章约 35 批次、每批至多 5 项候选，而通道 ④ 一轮回已白给 ≈ 18.5 件法宝（族占比 82% × 30 候选槽 × 0.75 领取率）。**占掉一个事件位去发一件消耗品，收益远低于让那个事件承载一次决策或一段叙事。**
- **它与回寿事件的量级对齐。** 回寿事件是每章 1 次小档、明写「在事件流中相当罕见」；同为「事件位换一件消耗品」的形态，两者不该差一个数量级。
- **两条结构性排除已经存在，不必重述、也不必扩大：** `eventType == Travel` 的条目受既有禁令约束（换图的代价不得被同一事件抵消）；`eventType == Exchange` 的条目不应走 `GrantFromPool` 免费发商品——**在消费点白给等于给定价表打一个不可见的折**，与「Exchange 不给灵石」逐字同构。**建议把后者落成一条加载期软校验（`PushWarning`，同 C-2 / 校验 9 的形态），不升格为拒绝**——赠礼式的风味条目是正常例外，本行的职责是让每一个例外被看见。

### 5. 置换对价

`[既有推演]`

置换的**规则形态已全部答定**（同池判据 · 同 `Rarity` · 排除已持有 · 先看后决 · 拒绝无代价 · 继承 `SourceCode` · 空池即空操作 + `PushWarning`）。悬着的只有**编排口径**，逐条给出：

**5a. 法宝置换不进「失去能力的频次预算」，另立自己的口径。**

- 该预算的保护对象是「**构筑投入不被拿走**」这条心理契约，三支持久支按「持久度 × 是否经玩家同意」两轴分配。法宝在两轴上都是最轻的一端：**轮回级** + **有同意**，且储物袋不设容量上限、随售是常态弃置途径 ⇒ 换掉一件法宝根本不构成「失去」。
- 它反而应当**比三支持久支更常见**——「置换是正向设计、是一个决策点」这条推论在消耗品上兑现得最干净。
- **建议目标频次 ≈ 2 次 / 完整轮回**（≈ 法宝总供给 24 件的 8%），旋钮同样是内容侧条目数 × `SelectionWeight` 档，**不进上层的 ≈1.0 合计**（与 `IgnoresProtection` 一支「不计入上层合计、自持口径」同款处置，理由同构：分母不同、控制旋钮不同、不写走 Profile 的持久面）。

**5b. 法宝各档启用条目数 ≥ 2（这条修的是一处现存缺口）。**

- 神通已有这条：「**神通同档条目数 ≥ 2**（否则以该档锚定的置换池恒空）」。同一条判据在法宝上逐字成立——置换池 = 同 `(CarrierKind, Scope)` + 同 `Rarity` + **排除已持有**。
- 而首批条目数矩阵给**法宝 Tier5 = 1 条** ⇒ 玩家一旦持有那一条，Tier5 法宝的置换池恒空，每一次都是空操作 + `PushWarning`。
- **建议：法宝行 Tier5 由 1 提到 2**（矩阵合计 39 → 40），并把「法宝逐档启用条目数 ≥ 2」与神通那条并列登记进 `/audit-content` 的汇总项。

**5c. barter 的价值比与条数口径（当前它一个护栏都没有）。**

barter 点名定值、不经池、不读定价表、不参与闸 ① 与槽位总数核算、也明确不设条数上界 ⇒ 一条「付 Tier1 法宝换 Tier5 神通」的编排**完全合法且不产生任何告警**。建议两格编排口径（`/audit-content` 汇总，只报告不阻断）：

| 口径 | 建议值 | 依据 |
|---|---|---|
| 价值比 = `BasePrice(产出物族 × 档)` ÷ `BasePrice(CharacterItem × 支付物档)` | **≤ 2.0** | 定价表的稀有度基价逐档 ×2 ⇒ 2.0 恰好是「一档跃升」，玩家读得出、也不套利；再高则「以物易物恒优于购买」，最优解退化为专找 barter 格 |
| 单个 Exchange 条目内 `BarterRules` 条数 | **≤ 1** | 与既定表述「barter 是内容作者点名编排的**少数格子**」对齐；且它须就地二段确认、不可逆损失一件具体法宝，一店多格会把这个仪式感稀释成清单 |

- **不落加载期硬校验**：价值比读的是两个族的定价表格值，加载期可得、机械可比——但**它是编排口径不是不变式**（一件低价法宝换一件高价神通正是某些叙事想要的「贵人相赠」），硬失败会挡住合理例外。与 L-1 / L-2 的处置一字不改。

### 6. `R_item,c` 缺口的收口：先修回代式，再择旋钮

`[既有推演]` + `[取向选择]`（旋钮三选一见「仍需用户决定」第 2 条）

**先报一处算术失真（本草稿的推演直接依赖它）。** `systems/balance.md` 的回代式写：

```
P = 1 − (1 − 0.06)² ≈ 11.6%   （0.06 = 逐池逐档条目占比口径；指数 2 = CharacterItem 族每店约 2 槽）
```

它把「逐池逐档占比 6%」直接当成了「某个槽位抽中回寿法宝的概率」，**漏掉一层条件概率**：抽取先按 `RarityTier` 权重选档、再在档内等概率取条目，而回寿只编排 Tier2 / Tier3 / Tier4 三档。补上这一层：

```
p(单槽为回寿) = 0.06 × Σ(Tier2..Tier4 的商店权重)
商店权重取「优胜 Solid 行 × 篇章乘数」：ch1 26+14+7 = 47 · ch2 26+16+9 = 51 · ch3 25+17+12 = 54
⇒ p = 0.0282 / 0.0306 / 0.0324
⇒ P(某店至少含一件, 2 槽) = 5.6% / 6.0% / 6.4%      （原式 11.6%，高估约一倍）
⇒ 期望遇到次数 = × Exchange 事件数 10.0 / 10.0 / 11.9 = 0.56 / 0.60 / 0.76
⇒ R_item,c = 次数 × 典型档位点数(87 / 92 / 99) × 转化率 0.7 = 33.9 / 38.9 / 52.7
```

- **「典型档位点数 87 / 92 / 99」经复算无误**（以 T2/T3/T4 权重为条件反解 50/100/200），只有 `P` 那一格失真。
- **修正后与分账目标（50 / 58 / 158）的缺口：−32% / −33% / **−67%**。** 这与该段自己的结论「低于分账目标、ch3 缺口最大」一致；**而原式的输出（70.6 / 74.7 / 95.6）在 ch1 / ch2 上反而高于目标，与同段结论自相矛盾**——故失真的是 `P`，不是结论。
- **顺带的推论（推翻既有的一个收口方向）：** 旋钮「**高档位多编排一条**」在权重抽取下**会适得其反**——把回寿条目往高档集中，遇到率的跌幅大于单次点数的涨幅（极端情形只编排 Tier4：`p` 降到 0.0072、`R_item,3` 反跌到 ≈ 24）。**该旋钮唯一可用的形态是「向 Tier5 扩一档」而非「在既有三档内上移」**：ch3 的 Tier5（320 灵石）机会成本已从 ch1 的 2.5 倍全章收入降到 0.67 倍，「定价失真」这条留空理由在 ch3 不成立。代入：ch3 开 Tier5（400 点 / 320 灵石，单位价仍 0.80）后 `R_item,3` 由 52.7 升至 ≈ 84，**仍不足 158**。

## 备选方案（已考虑并否决）

- **逐功能族各写一套 L-1/L-2/L-3** —— 否决：族的枚举来自值域，白名单一收窄，战斗外只剩一族；战斗内六族不进任何一本账，写口径即为不存在的问题造旋钮。
- **道具侧沿用 `ResourceElements` 表作为可写面，不另立白名单** —— 否决：那正是当前形态，它让六个账号层 key 与三个「只能走枚举档」的 key 全部可写；事件侧已就同一问题定案为两张表。
- **给 `ItemData` 加一个 `ItemFamily` 枚举字段来承载族口径** —— 否决：族是效果值域的导出量，加字段即第二权威（同 `CardData` 不加「是否功法成员卡」标记的判据）；且它会引出「校验能不能判断作者填错了族」这个无解问题。
- **逐族深度落成加载期硬校验** —— 否决：编排口径不是不变式，硬失败会在铺内容中途持续 `PushError`（同 L-1 / L-2 与族占比的既有处置）。
- **barter 价值比落成加载期硬校验** —— 否决：两个数在加载期都可得、机械可比，但「贵人相赠」是合理例外；与「`SellRatePercent <= PackSellRatePercent` 落硬校验」不同——那一条的坏形态没有任何合理解释，这一条有。
- **把法宝置换并进「失去能力的频次预算」的三支持久支** —— 否决：那份预算的分母与保护对象都不同，并进去会让「构筑投入不被拿走」这条口径被消耗品的置换次数静默重定价。
