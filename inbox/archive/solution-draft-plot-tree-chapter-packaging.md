# 方案草稿 — 剧本树按篇章分包与否

## 问题

2026-08-11 剧本内容从「云端剧本服务」改判为**本地内容层**（`res://` 基线 + `user://overlay/`，经 ContentRegistry 按 `Id` 读取）之后，原云端方案「按需请求一段就下一段」天然回避的那笔成本落回到了包体上：**三篇章的完整剧本树要随包发。**

于是悬着的是一道取舍题：**剧本树该不该按篇章分包、按进度增量下载？**（文件级事务与逐文件 hash 已现成，缺的只是**分包边界**。）

语言维度已于 08-13 排除在外——全语言内嵌同一 `.tres`、不按语言分包，双语封顶 ⇒ 体积上限固定 ×2，「按语言分包」的唯一实质动机消失。故本条回归其原本形态，两者互不牵动。

**本草稿的立场：这是一道「默认答案是否成立」的题，不是一道「怎么分包」的题。** 先把「不分包」的成立条件量化出来（§ 量级估算），再核算「分包」要引入什么（§ 备选方案 A）。

## 量级估算：先把「不分包」的成立条件算出来

> **本节给的是估算方法与依赖的未知量，不是设计数值。** 下面出现的每一个具体数字都标注了它是**已定案的引用值**、**既有设计反推出的上界**，还是**为演示量级而代入的算例参数**。算例参数一律不得被 derive 消费。

### 估算式

```
V_plot ≈ N_arc × S_arc  +  N_node × ( S_node + L_zh × 3 + L_en × 1 )      [bytes, 未压缩]
```

（`3` = UTF-8 下 CJK 每字符 3 字节；`1` = ASCII 每字符 1 字节。这两个是编码事实，不是参数。）

### 逐个量的已知 / 未知状态

| 量 | 状态 | 值 / 依据 |
|---|---|---|
| **结构 arc 数** | **已定** | **4** —— 1 条 Story + 3 条 Chapter（`plot-manager.md`：三个 Chapter 相连组成一个 Story，且「Story 与 Chapter 各恒有一条」） |
| **触发 arc 数** | **已定下界** | **≥ 2** —— 煞气反噬（煞气 Band 3）· 心魔滋生（道心 Band −2）。「大限将至」是终态、不经 `PlotTriggerId`，不占 arc |
| **side arc 库存量 `N_side`** | 🔴 **未知** | 只知**同时** `Active` 的上限是 `MaxConcurrentSideArcs = 2`（平衡数值，初值 2）——**这是并发上限，不是库存量上限**，库里可以有几十条。库存量取决于「每条剧情线的具体内容」，那条仍待答（同分片第一条） |
| **每 arc 的节点数** | **有既有设计反推出的上界，绝对值未知** | 见下方「节点数上界的反推」 |
| **正文字符数 `L_zh`** | 🔴 **未知** | 尚无一条真实剧本条目。**唯一的定性锚点**：本作是 deck building 不是 visual novel，「叙事是点缀不是载体」（`plot-manager.md`「体裁定位」），且节点正文可空（纯调制节点 `Body == null`） |
| **`L_en` / `L_zh` 比** | 估算参数 | 中→英等义文本的字符数通常放大到 1.5–2 倍。**这是行业经验比，用于给上界，不是定案** |
| **`S_node` / `S_arc`（`.tres` 结构开销）** | **有量级口径** | `content-service.md` 已定「`.tres` 是 KB 级」（那是「不做字节级续传」的依据）。节点侧的结构成分 = `Id` + `ArcId` + `PlotEdge[]` + 可空的 `PlotModulation` 子资源 |

### 节点数上界的反推（这一条不是猜，是既有设计的推论）

两条既定纪律把节点数夹住了：

1. **单步推进** —— 「一次 `eventEnd`，每条 arc 至多前进一个节点」（`plot-manager.md`）⇒ 一条 arc 在其 `ChapterScope` 内**被玩家实际走过**的节点数 **≤ 该篇章的事件数**。
2. **篇章事件数已有估算** —— ch1 26–30 · ch2 28–34 · ch3 32–38，一轮回合计约 **86–102** 个事件（`systems/balance.md`）。

⇒ 单条 Chapter arc 的**路径长度**上界 ≈ 26–38；Story arc 的路径长度上界 ≈ 86–102。

树上还有**没走过的分支**，故：

```
N_node(某 arc) ≈ 路径长度上界 × F        F = 分支膨胀系数 = 树总节点数 / 单次路径长度
```

**`F` 未知**——它由「DnD 式选分支的触发点与 UI」那条待答项决定（同分片，仍待答）。定性上：`PlotEdge.BranchLabel` 非空才是对玩家可见的分支，多数边是后台自动推进的单出边，故 `F` 更接近个位数而非两位数。

### 一个算例（**演示量级用，全部输入为假设值**）

代入一组**偏保守（往大了取）**的假设：`F = 3` · side arc 库 30 条 × 每条 15 节点 · `L_zh = 250` 字 · `L_en = 450` 字 · `S_node = 800 B`：

```
结构 + 触发 arc 节点 ≈ (102 + 30 + 34 + 38 + 2×20) × 3   ≈ 740
side arc 节点        ≈ 30 × 15                            = 450
N_node                                                    ≈ 1200

每节点 ≈ 800 + 250×3 + 450×1 = 2000 B
V_plot ≈ 1200 × 2000 B ≈ 2.4 MB（未压缩）
```

`.tres` 是纯文本、压缩率高（APK/AAB 内 3–4× 是常态）⇒ **落地包体增量 ≈ 0.6–0.9 MB**。

**这个量级要拿去和什么比？** 三个同库内可查的参照：

- **一首 BGM。** `art/soundtracks/_index.md` 承认包体预算未定，但一首 3 分钟 128 kbps 的曲子 ≈ 2.9 MB —— **整棵三篇章剧本树 ≈ 一首 BGM**。
- **一次同步上行。** `sync-service.md` 已定 `eventOption` 每事件一次整键替换 ≈ 1–6 KB ⇒ 一次轮回（~100 事件）的上行流量与整棵剧本树同量级。
- **运行时本身。** Godot 4 .NET 移动导出的引擎 + .NET 程序集基线是**数十 MB**，卡面美术又是数十 MB 级。

**结论：即便把每一个未知量都往大了取，剧本文本也落在「包体的百分之一量级」。**

### 这个估算什么时候会失效（判据，不是免责声明）

「不分包」的成立条件可以写成一条**可复核的判据**：

> `V_plot` 占应用总包体的比例 < 阈值 `θ`，且 `V_plot` 的绝对值 < `M` MB。

要翻案，得让 `N_node` 或 `L_zh` 出现**一个数量级**的偏差——即：剧本被写成了 visual novel 级的体量。而那与「叙事是点缀不是载体」这条**已定的体裁定位**直接冲突。**⇒ 翻案的前提不是体积变大，而是体裁定位被推翻。** 那属于另一个决策，不该由分发机制去兜。

（`θ` / `M` 的取值是取向题，列在 § 仍需用户决定。）

## 建议方案

### 1. 不按篇章分包。剧本树整体随包基线发布 + overlay 增量热更。

`[既有推演]`

**这不是「暂缓」，是把这条待答项按「不分包」关闭。** 五条依据：

- **量级不成立**（§ 上）。剧本文本落在包体的百分之一量级，而分包要引入 ≥ 6 条新机制（§ 备选方案 A 逐条列出）。**为百分之一的收益买一整套分发机制是净亏。**
- **分包与 C2（合并后全量强校验）在结构上冲突。** 这是最重的一条，独立成节见 § 2。
- **overlay 侧本就已经是文件级增量下载**（manifest 逐文件 hash 比对，只下 hash 不匹配的文件，C4）。所以本问题真正问的只剩「**随包基线**要不要拆」——热更侧的增量能力早就有了，分包在那一侧买不到任何新东西。
- **MVP 只有一个篇章**（C11）。「三篇章完整剧本树」这个体积在 MVP 阶段**根本不会出现**；等它出现时，第一批真实剧本条目已经写完、`V_plot` 是可实测的数，届时再判比现在拍脑袋准得多。
- **强制在线消解的是分包的收益侧，不是成本侧**（详见 § 3）。

### 2. 承重理由：分包与「合并后全量强校验」在结构上冲突

`[既有推演]`

C2 要求 ContentRegistry 在合并后跑一遍**全量**校验，剧本侧的清单是（`plot-manager.md`）：

| 校验 | 分包后会发生什么 |
|---|---|
| `PlotArcData.EntryNodeId` / `ParentArcId` / `PlotNodeData.ArcId` / `PlotEdge.ToNodeId` 悬空 → `PushError` + 抛 | 第 2 篇章的包没下 ⇒ Story arc 指向第 2 章节点的边**当场悬空** ⇒ **启动即抛** |
| `Tier == Chapter` 而 `ParentArcId` 为空 / 指向非 `Story` → `PushError` | Story arc 不在本包内时同样炸 |
| 从 `EntryNodeId` 出发的可达图含环 / 存在不可达节点 | 半棵树的可达性分析结论全错，`PushWarning` 变成刷屏噪音 |
| `PlotTriggerId` **双向**校验（档位表配了却无 arc 承接同样报错） | 煞气反噬 arc 在第 3 章包里 ⇒ 档位表侧的 `PlotTriggerId` 悬空 ⇒ **`PushError`** |

**要让分包成立，只有三条路，每条都在拆一件承重的东西：**

- **(a) 放宽剧本侧的悬空校验为 `PushWarning`** ⇒ 丢掉「坏数据启动期大声失败」这条纪律在剧本侧的全部效力（`.claude/rules/data-resource-rules.md`）。**代价：一个真的编排错误与一个「这个包还没下」在日志里长得一模一样。**
- **(b) 给剧本条目造第三种状态「未下载」**，让校验按状态分支 ⇒ 内容层出现一个既非「存在」也非「不存在」的态。它会立刻传染到 `Get(id)` / `AllEnabled()` / `newIds` 双闸 / 悬空 key point 降级四处，且与「读取侧不过滤」那条不对称正面打架。
- **(c) 让分包边界恰好切在「无跨包引用」处** ⇒ 但 Story arc 按定义就贯穿三篇章（`plot-manager.md`：三个 Chapter 相连组成一个 Story），`SideStory` 按定义跨篇章，`PlotTriggerId` 按定义跨到档位表。**跨包引用不是可以避开的编排问题，是剧本层级模型本身的形状。**

**⇒ 分包的真实成本不是「多一个下载步骤」，是要在上面三条里选一条来拆。**

### 3. 与「强制在线」的关系：它消解的是分包的**收益**，不是成本

`[既有推演]` —— 这一条是分派 prompt 点名要回答的。

**强制在线**（C10）对本题的作用是**单向的：它让「按进度增量下载」的动机部分消解，而不是让它更有必要。** 三条：

- **「省首次下载量」的收益本就很薄，强制在线把它削得更薄。** 玩家启动即必须登录（硬阻塞）+ 跑一次 pull（硬阻塞，C7）——他**必然**处在有网环境。分包能省下的只有「安装那一刻少下几百 KB」，而他紧接着就要为登录与同步联网。
- **「离线玩家永远下不到后续内容」这一情形不存在。** content-service 已明写「**断网启动并进入轮回这条路径根本不存在**」（flags 缓存那节的原话）。所以分包在离线优先产品里最重要的那条动机（"让用户先玩起来，剩下的慢慢下"）在本作**没有对应场景**——本作压根不允许"先玩起来"。
- **反过来，分包会造出一个既有设计里不存在的失败态。** 「玩家推进到第 2 篇章却没网」在**不分包**下完全无害（剧本在盘上，`TryResolvePlot` 是纯内存查找，`plot-manager.md` 明写「剧本读取没有网络失败路径」）；在**分包**下它变成一个**第三处硬阻塞**（C7 明写硬阻塞只有两处），或者一个「剧本静默缺席」的降级。前者违反既定的阻塞点清单，后者等于把整个第 2 篇章的剧本层悄悄关掉——而那正是悬空 key point 降级规则明写要「不阻塞**其余**剧本线」时刻意限制住的爆炸半径。

**⇒ 强制在线是「不分包」的加分项，不是「按进度下载」的理由。** 唯一残留的分包动机是**初装包大小**——而它有一条更正确的落点，见 § 4。

### 4. 方向性记录：真到了要缩初装包那天，落点是平台原生按需资源，不是 manifest 分包

`[通行做法]` —— **写成方向性记录，不作为现在的决策。**

若将来（美术 / 音频铺开后）确需压缩初装包，业界标准解法是**平台原生的按需资源机制**：Android 的 Play Asset Delivery（install-time / fast-follow / on-demand 三档）、iOS 的 On-Demand Resources。理由：

- 它是**发行侧的打包配置**，不是内容分发契约的成员 ⇒ 不碰 manifest schema（C5：服务端不区分内容类别）、不碰文件级事务的提交点（C4）、不碰 `LoadAll()` 的一次性合并（C3）。
- 平台自己承担下载、缓存、驱逐、续传与失败重试——那正是分包方案要在客户端重新写一遍的东西。
- **它天然选中的资产是美术与音频**（数十 MB 级），而不是剧本文本（百分之一量级）。**换句话说：真到了那天，要拆的也不是剧本树。**

这与既有的「不为每日种子 / 排行挑战预留任何结构」（`content-service.md`）是同一种纪律：**不为一个不在中期路线图内的需求预留结构，但把正确落点记一句，免得将来回退全局决策。**

### 5. 配套：留一道**不需要现在做任何事**的复核闸

`[既有推演]` + `[取向选择]`（阈值取向见 § 仍需用户决定）

关闭这条待答项时，在 `plot-manager.md` / `content-service.md` 留一句复核条件，而不是留一个待答项：

> 第二阶段（内容）第一批真实剧本条目写完后，实测 `V_plot`（`res://content/plot-arc/` + `plot-node/` 的字节总和）与应用总包体之比。**仅当占比 > `θ` 且绝对值 > `M` MB 时**重开分包讨论；届时的首选形态是平台原生按需资源，而非 manifest 分包。

它的成本是零（一次 `du`），收益是把「不分包」从一个未经实测的判断变成一个**有复核点的决定**。

## 备选方案（已考虑并否决）

### A. 按篇章分包（3 包，边界 = `PlotArcData.ChapterScope`）—— 否决

08-16i 已指出 `ChapterScope` 是「日后分包边界的天然切分键」，故这是最像样的一版分包方案。**完整形态写在下面**，让评审能看清否决的到底是什么。分派要求逐条回答的四点：

| 项 | 这套方案必须给出的答案 | 代价 |
|---|---|---|
| **分包边界** | 3 包（ch1 / ch2 / ch3），键 = `PlotArcData.ChapterScope`。**但 Story arc（`ChapterScope` 跨三章）与 `SideStory`（`ChapterScope` 空 = 不限）落不进任何一包** ⇒ 必须再造第 4 个「公共包」 | 边界不是 3 而是 **3 + 1**，且「哪些进公共包」成为一条新的、要逐条目维护的编排纪律 |
| **与既有 manifest / blob / 事务的接口** | **必须新增，复用不了**（这是硬要求上的失败点）。manifest 的 `files[]` 只有 `path` / `hash` / `size`，**没有内容类别、没有包分组**，且后端契约明写「服务端不区分内容类别、不需要标注文件的内容类别」（C5）。要分包必须给 manifest 加分组字段。加**可选**字段虽不提升 `manifestSchema`（契约允许），但**旧客户端会忽略它** ⇒ 旧客户端拿不到分组 ⇒ 要么全下（分包白做）、要么必须提升 `manifestSchema` 走破坏性变更 + 两版端点并存 | **等于第二套分发机制**——分派 prompt 已把这一条定为否决线 |
| **未下载篇章的失败语义** | 三选一，全是坏的：① 推进到 ch2 时**硬阻塞下载** ⇒ 第三处硬阻塞，违反 C7，且撞「强制在线但允许短暂断线缓冲本地操作」（`vision/scope.md`）——玩家在地铁里推进到 ch2 就卡死；② **静默跳过整个 ch2 剧本层** ⇒ 悬空 key point 降级规则被从「不阻塞其余剧本线」放大到「整章剧本静默消失」；③ **启动期就把三包都下完** ⇒ 分包退化为「文件多分了几组」，收益归零 | 三条各自撞一条既定纪律 |
| **overlay 热更与分包的叠加语义** | overlay 可为剧本新增 `Id`（C8），`newIds` 闸 B 要求新增剧本条目的**非剧本外部引用必须存在于基线**——**分包后「基线」这个词分裂成「已下载的基线」与「全部基线」**。取前者 ⇒ 同一份 overlay 在两台设备上校验结论不同（可复现性没了）；取后者 ⇒ 闸 B 要读一份设备上并不存在的清单 | 双闸的可机械检查性被打穿——而它是 08-16i 刚刚买到的东西 |

**另外三条 A 方案绕不过去的**：与 C2 全量强校验的结构冲突（§ 2 的三条路，每条都在拆承重件）· 文件级事务的单一提交点要改成多提交点或部分提交（C4）· `LoadAll()` 从「启动链第一步跑一次」变成「运行时可再跑」（C3），而它是形态 A 的同步方法、且合并后校验会 `throw`。

**⇒ 合计 ≥ 6 条新机制 / 被拆的承重件，换取包体百分之一量级的收益。否决。**

### B. 按 `PlotTier` 分包（Story/Chapter 一包，SideChapter/SideStory 一包）—— 否决

比 A 更差：side arc 是「穿插」，与主线在同一次轮回里**同时** `Active`（`MaxConcurrentSideArcs = 2`），拆开等于把一次轮回必然要用的两半分两次下。且 `PlotTriggerId` 双向校验横跨两包，§ 2 的冲突原样存在。

### C. 剧本回到云端按需请求 —— 否决（已被既有决策封死）

这是原云端方案，它天然没有包体问题。但 08-11 已定案不设云端剧本服务，四条理由（判据循环 · manager 跨边界 · 云端一侧要背整套网络失败复杂度 · 后端少一个服务一份协议）在 `plot-manager.md`「不设云端剧本服务的理由（承重）」逐条写着。**本方案不试图重开它。**

### D. 剧本正文外置为独立文本类型、只分包正文 —— 否决

「正文内嵌节点（`PlotNodeData.Body`）」是 08-16i 的定案，理由是**拆条目会让 overlay 新增一条 arc 时写不出它的正文，剧本例外当场失效**（`plot-manager.md`）。拆出去分包 = 重新打开那个已被关上的口子，且正文恰是唯一可压缩的部分，拆完剩下的结构开销还在。

### E. 现在就加一条「一条 arc 的节点数上限」硬校验 —— 不建议（降级为取向项②）

作为体积护栏它是过度设计：`PlotNodeData` 的加载期校验清单已有 11 条，再加一条依赖一个**没有依据的数字**。若要护栏，`PushWarning` 级的软提示足够。见 § 仍需用户决定 ②。

## 与既有决策的张力

**无实质张力——本方案的方向是维持既有决策，不是松动任何一条。** 三点值得评审时确认的**表述层**问题：

1. **`plot-manager.md` 与 `content-service.md` 都把这条列在「待决问题」，且后者注明权威归前者。** 采纳后两处要同改，且**只在 `plot-manager.md` 写决策本体**，`content-service.md` 留回链——避免制造第二权威（`.claude/rules/design-library-routing.md`「回链而非复述」）。
2. **`vision/scope.md` 的「美术资源策略」承认包体预算未定。** 本方案给出的是「剧本文本相对包体可忽略」这一**相对**结论，它**不依赖**包体预算的绝对值（相对结论在任何绝对预算下都成立，只要美术 / 音频确实是数十 MB 级）。但若日后包体预算被定成一个极小的数（例如微信小游戏那类首包限制），这条相对结论要重算——**复核闸正是为此而留**。
3. **本方案不触碰「三篇章剧本的具体内容」那条待答项。** 它只回答「怎么分发」，不回答「写多少」。
