# 方案草稿 — 竖屏「候选项列表」的统一排布与标注语言

## 问题

两条待答项各自悬着，但它们要的是同一样东西：

1. **事件选择区的呈现与导航手感**（`open-questions/02-event-options.md`）。进程形态已定为「逐批择一的线性推进 + 月圆之夜式菜单 + 横向滑动选择区」，但**每批的选项排布与滑动手感未定**；难点是**批次规模区间 1–5**（`systems/adventure-event/common-properties.md`，众数 3，两端稀薄），两端差 5 倍而竖屏宽度是固定的。另外，**寿元告警的静态标注如何嵌进这套排布**同样未定。
2. **闭关（Research）构筑面板的竖屏呈现与走火入魔风险档标注**（`open-questions/03-adventure-event-types.md`）。方向已定为「与战后奖励面板在**呈现层**同构（候选纵向排列、点按选中）、交互层不同构（本面板选完全部槽再一次确认提交）」，但**风险档的视觉标注与不得为 hover-only 的说明通道未设计**。

两处卡住的是同一件事：**本库至今没有一套成文的「一批候选项在竖屏怎么摆、怎么标」的通用语言**，于是每新增一个决策面（战后奖励、置换、构筑槽、剧本分支、Exchange、储物袋）都要重新裁一次，而这正是「不发明第二种选择语言」这条已被反复引用的纪律所要防的漂移。故本草稿**先给一套可复用的候选项列表语言，再把它落到这两个场景**。

## 约束（来自既有设计）

**A · 全局 UI 纪律**
- 竖屏优先、`Container` + 锚点重排、尊重安全区、最小触控目标 ≈ 48dp、**绝无 hover-only 可供性**、UI 文案一律走 `res://text/` 翻译键 —— `.claude/rules/ui-input-rules.md`、`.claude/knowledge/standards/mobile-portrait-ui.md`。
- 内容层文案（条目名 / 描述 / 风味）走 `LocalizedText`，**不进 `res://text/`** —— `ux/_index.md` 的四问判据。
- 详情入口按「对象是否可拖拽」分化：不可拖拽的对象用**长按** —— `decisions/ADR-0085-gesture-split-tap-versus-longpress.md`。
- 「不在最高频操作上加模态弹层」 —— `ux/combat-ux.md`，已被结算面板剧本段、揭示转场层、储物袋「使用」三处引用。

**B · 事件选择区侧**
- 进程 = **逐批择一的线性推进**，不是可俯瞰 / 可回溯的分支地图；`locationMap` 在轮回内不呈现 —— `systems/game-progression.md`。
- 载体 = **横向滑动选择区**（既定，`answer-logs/log-0725c.md`）；批次规模 **1–5**、常态 3，由 `BatchSizeWeights` 掷定；三种结构性场景不走该表：**闸门批**（规模 = 当前 location 的邻接数，加载期校验保证出度 ≤ 5）· **`Priority = 1` 收窄批**（通常 1 项）· 闸 ②③ 移出条目后少一项 —— `systems/adventure-event/common-properties.md`、`systems/services/future-event-service.md`。
- **一批只有一次操作：择一进入**；无跳过通道、无跳过手势 / 按钮；**不设不可选 / 置灰态**（付不起照付、支付后判定）—— `systems/adventure-event/common-properties.md`。
- 卡面既定项：`selectCost` 的 `−m` 与回寿 `+n` **恒精确、两侧对称**（量级 9–189 / 50–600+，按三位数排版）· 战斗类卡片**并列双方等级**（境界名 + 层级，全局序不出现在 UI，**不做方向标记**）· **不标注经验产出档位** · `Priority` 不作数字呈现 —— `ux/screen-flow.md`、`ux/combat-ux.md`、`systems/game-progression.md`。
- **Explore 遮罩卡与其余选项完全同构：同尺寸、同触控目标、同滑动节奏，不做异形 / 加大 / 特效卡**（异形单元会破坏横滑区的等宽节奏，窄屏尤甚）—— `ux/screen-flow.md`（承重，本方案的硬边界）。
- 选择区上方已有一条**常驻角色状态条**（`炼气七层 · ❤920 · ✦5/5 · 灵石 120` + 经验条 + 袋 / 卡组入口），**竖屏窄栏此处已是压力最大处**，`❤` 位按四位数排版 —— `ux/screen-flow.md`。
- **寿元告警的既定形态**：只落在该状态条的 `❤` 位，余量低于本章可用预算 10% 时**转红字**，形态是**静态标注**（随结算而变、平时静止，不做跳动 / 计时器动画）；**不做「大限将至」一类预警文案**；是否伴随音效 / 震动**仍待答**（另一条独立待决项）—— `systems/character-profile/life-span.md`、`ux/screen-flow.md`。
- **横滑是「推进进程的择一」专属语汇**：Exchange 屏明确**不做横滑**、剧本分支明确**不复用横滑区语汇**，理由同一句 ——「横滑区已是事件选择面的语汇，复用会让两个层级的操作读成同一件事」；主动弃置入口同理否决了横滑删除手势 —— `ux/screen-flow.md`。

**C · 闭关构筑面板侧**
- 面板 = **若干决策槽**（常态 1 槽，开局构筑事件 2 槽），每槽 `CandidateCount` 默认 3（**上界不是保证**，短缺时给几条算几条，整槽为 0 则该槽不进面板），`AllowDecline` 默认 `true`（开局条目为 `false`）—— `systems/adventure-event/research/common-properties.md`。
- **交互层：选完全部槽再一次确认提交**（奖励面板是逐项即时领取 / 跳过）；**槽内选择不落存档**，中途退出恢复回面板初始态、候选一字不变 —— `research/_index.md`。
- **风险档**：`ResearchCandidate.IsRisky` 为真的候选，成功 `manaLimit +1` / 失败 `−1`，**结果在物化时已掷定并落存档，面板上只标注「有风险」、不预先展示结果**；「**玩家自选**而非随机惩罚」是承重理由 —— `research/_index.md`、`research/common-properties.md`。
- **短缺不给玩家任何提示、不新增文案键** —— `research/common-properties.md`。
- 候选的显示名 / 描述**不进快照**，由 UI 按 `TargetId` 现场取模板组装 —— 同上。

**D · 明确的空白（不得预设）**
- **战后奖励面板的形态本身仍未定**（`ux/combat-ux.md` 待决问题：强制项与可选项如何同屏区分、逐项列表在竖屏的排布、已领取 / 已跳过两态的视觉处置）。故「构筑面板与它同构」这条约束目前**指向一个尚未成形的对象**；本草稿因此只把同构落在**可独立成立的构件层**（见下方 §0 与 `## 前置依赖`）。

## 建议方案

### 0. 先立一套通用的「候选项列表语言」（本草稿的主体）

#### 0.1 两条排布轴的分工判据 `[既有推演]`

本库已有六处「一批候选项」的落点，逐处核对后可归纳出一条**已经在事实上生效、只是没写下来**的判据：

> **推进进程的择一 → 横滑等宽 carousel；面板内 / 事件内的择一与列举 → 纵向堆叠或网格。**

| 落点 | 轴 | 既有依据 |
|---|---|---|
| eventOptions 选择区 | **横滑** | `answer-logs/log-0725c.md`、`systems/game-progression.md` |
| 角色选择屏 | **横滑** | 「沿用 eventOptions 已定的同款手感，不发明第二种选择语言」 |
| Exchange offer 网格 | 纵向网格 | 明确否决横滑（同上引句） |
| 剧本分支按钮 | 纵向堆叠 | 明确否决复用横滑语汇 |
| 储物袋 / 图鉴单本页 | 纵向网格 | `GridContainer.columns` 随宽度调整 |
| 战后奖励面板 / 置换面板 / **构筑槽** | 纵向 | 「候选纵向排列、点按选中」 |

**推论：两个待答场景各自落在轴的两侧** —— 事件选择区在横滑侧（既定），构筑面板在纵向侧（既定方向）。它们**共用的不是轴，而是下面 0.2 的条目构件与 0.3 的标注语言**。这一点很重要：它让「构筑面板与战后奖励面板同构」这句既有约束落在一个**可独立成立的层**上，不必等奖励面板的排布定案。

**建议把这条判据写成一句成文纪律**（落 `ux/_index.md` 或 `ux/screen-flow.md` 的横切段），此后新增决策面照它落位，不再逐次裁决。

#### 0.2 统一的「候选条目」构件 `[通行做法]` + `[既有推演]`

两条轴共用同一个构件（只有外框比例不同：横滑侧是纵向长卡，纵向侧是横向长条）：

```
┌──────────────────────────────┐
│ ①类型 / 来源标识    ②标注带  │   ← 顶带：类型图标 + 短名；右上角 0–2 枚静态标注
│                              │
│        ③ 视觉（Artwork）      │   ← 中带：内容层图，缺失走统一占位图
│                              │
│ ④ 名称（内容层 LocalizedText）│   ┐
│ ⑤ 一行副文本（描述 / 风味）    │   ├ 底带
│ ⑥ 数值行  −m寿元  +n寿元 …    │   ┘   恒精确、双向对称
└──────────────────────────────┘
```

- **六个位全部可空**，缺位即整格不渲染、其余上移（`Container` 重排），**不留空占位**——与「储物袋售出后条目直接移出、不留『已售』占位」「战斗前确认页未解锁则摘要区不出现、不留灰占位」同一条处置。
- **长文本永不截断成省略号**：④ 名称单行、⑤ 副文本至多两行，超出部分归**长按展开的详情**（见 0.4），而不是在卡上做微缩排版。
- **触控目标 = 整个条目**，恒 ≥ 48dp（横滑侧由卡宽 / 卡高保证，纵向侧由行高保证）。

#### 0.3 标注层：三类标注，位置与优先序固定 `[既有推演]`

「标注」在本库已经出现三种彼此不同的东西，混在一起谈正是两条待答项各自卡住的原因。建议明确分成三类，**各有固定位置、互不挤占**：

| 类 | 是什么 | 位置 | 形态纪律 | 既有实例 |
|---|---|---|---|---|
| **① 资源数值标注** | 会被加减的明面资源 | 条目底带 ⑥（数值行） | **恒精确、成本 / 产出两侧对称**、按最大位数排版、**不做跳动动画** | `−m` `+n` 寿元；Exchange 的价格 + 币种 |
| **② 状态 / 风险标注** | 关于该条目本身的一个二值事实 | 条目顶带 ② 右上角 | **静态、常驻可见**（图标 + ≤4 字短文），**无动效、无 hover**，每条目至多 **2 枚** | 功法卡的属性图标与「单灵根专属」角标；本方案新增的**风险档标注** |
| **③ 实例信息标注** | 本次遭遇 / 本次批次的实例事实 | 条目底带 ⑥ 的独立一行 | 恒精确、只标注一次（同屏不出现第二处） | 战斗类卡片的并列双方等级 |

**三条禁则（逐条都有既有依据，建议一并成文）：**
1. **不加由已展示的数字机械导出的符号。** 敌人等级的 `↑ / = / ↓` 方向标记已被明确否决，理由是「由两个等级机械导出」且会滑向模糊的危险度档位。**推论：也不给「这一步会让你归零 / 跌破 10%」的卡片级致死标记** —— 余量与成本两个数都已恒精确常驻，标记是它们的机械导出物，且它正是被否决的「大限将至」预警文案换了个形状。
2. **不显示隐藏的映射量**：经验产出档位（明文禁令）、`SelectionWeight` / 稀有度权重、`Priority` 档、Explore 真身。
3. **不做灰态表达「不划算」**：置灰只用于「明知做不到仍然去做没有意义」的可变状态（Exchange 买不起 / 无支付物），**事件选择面整体没有灰态**。

#### 0.4 统一的说明通道（无 hover 的等价物）`[既有推演]`

一条通道，三层深度，**全库共用**：

| 层 | 触发 | 载体 |
|---|---|---|
| 1 · 恒常可见 | 无 | 条目上的 ①②④⑤⑥ 六个位 |
| 2 · 短说明 | **长按条目** | **半屏 bottom sheet**，复用「随身」抽屉 / 图鉴词条同款控件，可下滑关闭、点按遮罩关闭 |
| 3 · 深说明 | 层 2 内的可点入项 | 叠一层 bottom sheet（先例：敌人词条页内点入功法词条） |

- **选长按而非点按**：`ADR-0085` 的分化判据是「对象是否可拖拽」——候选条目不可拖拽，故用长按；且**点按已被择一 / 选中占用**，同一根手指上不能有两个点按语义。储物袋「长按查看详情」是同款先例。
- **绝不用悬停、绝不用「ⓘ」小图标**：前者无触控等价物，后者是一个远小于 48dp 的次级热区，会与整条目的点按热区争抢。

#### 0.5 1–5 的自适应规则（横滑轴专用）`[通行做法]` + `[既有推演]`

> **一句话：卡宽恒定、逐项吸附、按常态 3 项同屏标定；N 变只改「要不要滑」，绝不改卡的尺寸与形状。**

| # | 规则 | 依据 |
|---|---|---|
| R1 | **卡宽 / 卡高在批与批之间恒定**，不随 N 缩放、不做异形卡 | Explore 遮罩卡「同尺寸、同触控目标、同滑动节奏、不破坏等宽节奏」是硬约束；跨批缩放会让同一张卡在不同批里大小不一，读成「这批更重要」 |
| R2 | **标定基准 = 常态 3 项恰好同屏**，左右各露出相邻卡的一个窄边（peek） | 众数是 3；peek 是「还有更多」的通行可供性，且不占额外纵向空间 |
| R3 | **N ≤ 3：整批居中、滑动区不可滚动**（回弹） | 无内容可滑时仍能滑会读成「后面还有」，是假可供性 |
| R4 | **N = 4 / 5：可横滑，逐项吸附（snap-to-item）**，一次滑动移动一张 | 与「逐批择一」的心智一致；自由惯性滚动会让玩家滑过头、失去「一共几项」的把握 |
| R5 | **N ≥ 4 时在滑动区下方给 N 枚位置点**（当前项高亮）；N ≤ 3 不出现 | 页点是批次规模的唯一读数，让「一共有几条路」在一眼内成立；N ≤ 3 时全部可见、点是噪音 |
| R6 | **N = 1 与多项批完全同形**：一张卡居中，照常点按进入，**不加任何「本批只有这一条路」的说明文案** | `Priority` 不作呈现、「呈现层只做呈现」；且 PlotManager 那条承重理由明写「玩家看到的仍是一批可选项，而非一个被系统钉死的选项」 |
| R7 | **闸门批（整批 Travel）复用同一选择区，零特殊形态** | 「不发明第二种选择语言」；闸门批规模 = 邻接数（出度 ≤ 5，加载期已校验）或 1，恰好落在同一区间内 |

**手感参数（`[通行做法]` · 待实测初值 + 旋钮位置）** —— 这些只能在真机上调，此处给的是起点：

| 参数 | 初值 | 说明 |
|---|---|---|
| 卡宽 | ≈ 屏宽的 **28%**（1080 基准下 ≈ 300 px） | 由 R2 反推：`3 × 卡宽 + 2 × 间距 + 2 × peek + 2 × 安全边距 = 屏宽` |
| 卡高 : 卡宽 | ≈ **1.45 : 1** | 需容下六个位；最终由 §1.1 的实排验证 |
| 卡间距 | ≈ 16 px | |
| peek 宽 | ≈ 36 px | 足以读出「那里还有一张」，不足以被误读为可点 |
| 翻页阈值 | 位移 > 卡宽的 **25%** 或甩动速度超阈 | |
| 吸附动画 | ≈ **180 ms**，缓出 | 与揭示转场 ≈ 1.2s 一样是待实测初值 |

**旋钮位置：** 六个参数全部是呈现层常量，**不进任何数据资源、不进存档、不进内容条目**（它们不是平衡数值，改它们不改任何玩法结果）。建议集中在选择区场景脚本的 `[Export]` 字段上，供在编辑器里实调。

### 1. 落到场景一 —— 事件选择区

#### 1.1 屏幕排布 `[既有推演]`

```
┌─────────────────────────────────────┐
│ [安全区]                             │
│ 炼气七层 · ❤920 · ✦5/5 · 灵石 120    │  ← 既有角色状态条（❤ < 10% 转红字）
│ ▓▓▓▓▓▓▓░░░ 经验 3/4   [袋]6 [卡组]  │  ← 既有经验条 + 两个入口
├─────────────────────────────────────┤
│   ┌──────┐  ┌──────────┐  ┌──────┐  │
│   │      │  │          │  │      │  │
│  ◂│ 选项 │  │  选项 ★  │  │ 选项 │▸ │  ← 横滑等宽 carousel（★ = 焦点）
│   │      │  │          │  │      │  │
│   └──────┘  └──────────┘  └──────┘  │
│            ● ○ ○ ○                  │  ← N ≥ 4 才出现的位置点
│ [安全区 · 避开 Home 指示条]           │
└─────────────────────────────────────┘
```

- **滑动区落屏幕中部偏下的拇指可及带**；状态条恒在顶部安全区内、**不随滑动移动**。
- **不新增任何常驻控件**：无跳过键、无「重掷」、无地图入口、无批次说明文字。

#### 1.2 卡面六个位的落位 `[既有推演]`（逐位都有既有权威，此处只是把它们摆进 0.2 的构件）

#### 1.3 寿元告警怎么嵌进这套排布 `[既有推演]`

> **建议：告警只发生在角色状态条的 `❤` 位（既定形态，一格不动），选项卡上不做第二处告警表达。**

三条依据各自独立成立：
1. **既定落点已经写死**：告警的形态是「静态标注于 EventOption 选择界面的角色状态条、`< 10%` 转红字」，而那条状态条**恰好就常驻在选择区正上方** —— 它本来就在这套排布里，不需要「嵌入」，只需要**明确它不下沉到卡片层**。
2. **卡片级告警撞禁则 1**：任何形如「选这个会归零」的卡上标记都是「余量」与「成本」两个已精确展示的数字的机械导出物，与被否决的方向标记同形；且它实质上就是「大限将至」预警文案换一个视觉外壳。
3. **它会当场取消一条承重取向**：「明知是死路仍然走」要求玩家**知情地**走进去，而不是被系统在那张卡上标一个「死」字劝阻——后者把一次玩家的抉择降级成一次系统警告。

**配套的两条小结论：**
- **红字状态与滑动无关**：状态条不参与滑动、不随焦点变化，红字只在一次事件结算后改变一次（静态标注的定义）。
- **音效 / 震动不在本方案射程内** —— 那是一条**独立的待答项**（`ux/screen-flow.md` 待决问题），本方案只定视觉，不预设它的答案。

#### 1.4 进入手势 `[取向选择]` → 见 `## 仍需用户决定` 第 1 题

推荐 **焦点制**：点按非焦点卡 → 该卡滑到中心成为焦点（**不支付、不进入**）；点按焦点卡 → 支付 `selectCost` 并进入。理由与备选见下。

#### 1.5 文案 `[既有推演]`

- 选择区的框架文案（位置点无文案；长按详情 sheet 的项目标签）走 **`EVENT_` 分区 / `event.csv`**，**不写字面量、不占 `ERR_` 前缀**（本地呈现，无后端 `code`）。
- 事件名 / 描述 / 风味 **一个字不进 `res://text/`** —— 内容层 `LocalizedText`（四问皆是）。

#### 2.1 屏幕排布 `[既有推演]`

├─────────────────────────────────────┤

│   └────────────────────────────┘    │ │
│                                     │ │
│  槽 2 · 得一件法宝                   │ │  ← 多槽时继续纵向堆叠
│   …                                 │ ┘

└─────────────────────────────────────┘

| # | 规则 | 依据 |
|---|---|---|
| P1 | **全部槽同屏、共用一个纵向滚动容器**，槽以小标题分段，**不做逐槽分步向导** | 交互层已定「选完全部槽再一次确认提交」——分步会让「一次提交」的语义模糊；且常态 1 槽、最多 2 槽（开局），量级根本不需要分步 |
| P2 | **确认按钮固定底部拇指可达区、避开 Home 指示条，滚动时不移出视野** | 与轮回结束屏 / 篇章结束屏 / 战斗前确认页逐字同款 |
| P3 | **未选满时确认键置灰 + 一行说明「还有 N 个槽未做选择」** | 灰态判据「明知做不到仍然去做有没有意义」——提交一份不完整的构筑没有意义，落在 Exchange 那一侧 |
| P4 | **`AllowDecline == true` 时，「什么都不做」是该槽候选列的最后一行**（同一构件、同一触控尺寸），不是角落里的次级链接 | 它是槽内的一个平等选项（`AllowDecline` 的语义就是「允许选它」）；做成次级控件会诱导玩家以为它是「跳过」，而跳过在本作是被整体移除的概念 |
| P5 | **选中态用于「已选」的即时反馈**（选中项高亮 + 一枚 ✓，同槽其余项恢复常态）；**改选零代价、无二次确认** | 槽内选择不落存档、可反复改；二段确认留给不可逆的资源损失（储物袋售出 / Exchange 兑换先例） |
| P6 | **候选短缺不做任何呈现区分**（少一条就是少一条），整槽为 0 的槽本就不在面板上 | 「短缺不给玩家任何提示、不新增文案键」 |
| P7 | **面板顶部不显示 `lifeSpanCost`**（进入时已支付并已在结算前读过） | 成本是选择面的信息，不是事件内的信息；同屏重复会造第二处口径 |

**与战后奖励面板的同构落在哪一层：** 同构 = **0.2 的条目构件 + 0.3 的标注语言 + 0.4 的说明通道**（同一种候选长条、同一套标注位、同一条长按通道）。**不同构的是交互**（本面板一次确认提交，奖励面板逐项即时处置），这与既有陈述完全一致。**本方案不预设奖励面板自身的排布**，见 `## 前置依赖`。

#### 2.2 说明通道 `[既有推演]`

#### 2.3 风险档标注 `[取向选择]` → 见 `## 仍需用户决定` 第 2 题

形态骨架（三个选项共有、不进入取舍）：
- **位置**：候选条目的 ② 标注位（顶带右上角），**常驻可见、静态、无动效**。

### 工程形态（提案，落地时由 `/blueprint` 定稿）

- 选择区 = `MarginContainer → ScrollContainer(horizontal) → HBoxContainer`，卡为 `PackedScene` 实例；吸附与翻页阈值在脚本内实现，六个参数为 `[Export]`。**卡宽用 `custom_minimum_size` + 屏宽比例计算，不做绝对定位。**
- 构筑面板 = `MarginContainer → VBoxContainer(ScrollContainer 内) + 底部固定按钮`；每槽一个 `VBoxContainer`，候选为同一 `PackedScene` 的实例。
- **候选条目构件建议做成一个共用 `PackedScene`**（事件卡 / 构筑候选 / 奖励候选三处复用，仅外框比例与可空位不同）—— 这正是 0.2 的工程兑现，也是「同构」这句约束唯一能被机械保证的形式。
- 安全区按 `DisplayServer.GetDisplaySafeArea()` 内缩顶层边距；触控目标 ≥ 48dp。
- 两个面板的 ViewModel **随屏出生随屏消亡、不进 `_Process`**（沿用图鉴屏 / 数据导出区的既定工程纪律）。

### 验收断言（供 `/derive-requirements` 消费的形态）

1. 同一角色连续三批（N 分别为 1 / 3 / 5）中，选项卡的**渲染尺寸完全一致**。
2. N ≤ 3 时滑动区不可滚动（滑动只回弹）；N ≥ 4 时位置点数量 == `Options.Count`。
3. 任一事件选项卡上**不出现**：经验档位、`Priority`、稀有度 / 权重、灰态、致死标记。
4. 寿元余量 < 本章预算 10% 时，**仅**状态条 `❤` 位转红；同屏任何卡片上无第二处红色告警。
5. 构筑面板：任一槽未做选择时确认键不可提交；`AllowDecline == false` 的槽不渲染「什么都不做」行。
6. `IsRisky == true` 的候选常驻风险标注；面板任何位置**不出现** `ManaDelta` 的具体值。
7. 全屏任意位置**不存在** hover-only 才能获得的信息（可用「关闭所有指针悬停事件后信息不丢失」机械核对）。

## 备选方案（已考虑并否决）

- **按 N 自适应卡宽（1 项占满宽、5 项各缩到 1/5）** —— 否决：直接撞「Explore 遮罩卡与其余选项同尺寸、不破坏等宽节奏」这条承重约束的精神（它防的正是「卡的大小承载含义」），且 N=5 时卡宽会逼近触控目标下限。
- **纵向列表取代横滑选择区** —— 否决：横滑是既定形态（`answer-logs/log-0725c.md`），且纵向已被 Exchange / 剧本分支 / 储物袋占为「面板内列举」的语汇，换轴会让两个层级的操作读成同一件事。
- **卡片级的致死 / 破线标记（「选这个会归零」）** —— 否决：机械导出物（撞禁则 1）+ 实质是被否决的「大限将至」预警 + 削弱「明知是死路仍然走」这条承重取向。
- **在选择区加一条「本批 N 项」的文字说明或批次编号** —— 否决：位置点已给出同一信息且零文案；批次编号是「还有几步」类读数的近亲，与「轮回内不提供任何进度读数」同向。
- **构筑面板逐槽分步向导（选完槽 1 才出槽 2）** —— 否决：与「选完全部槽再一次确认提交」语义冲突；且最多 2 槽，分步换不到任何空间收益。
- **构筑面板用横滑呈现候选（复用事件选择区手感）** —— 否决：撞 0.1 的轴分工；且多槽时会出现「两条横滑带上下叠放」，滑动手势归属立刻模糊。
- **风险候选加一道二次确认** —— 否决：「风险是被选择的，不是被施加的」是 Research 的承重理由，确认层把主动选择读成误触；且槽内选择可反复改，本就没有不可逆损失。
- **在槽标题上预告「本槽含风险候选」** —— 否决：由候选列表机械导出，撞禁则 1。

## 与既有决策的张力

**① 卡宽标定基准 vs 角色选择屏「5 张卡同屏容纳度待实测」（需用户裁决其一）。**
`ux/screen-flow.md` 的角色选择屏写明「角色卡横滑选择区——沿用 eventOptions 已定的同款手感」，同时留了一句「**5 张卡在主流竖屏比例下的同屏容纳度待实测**」——它隐含的期待是「5 张最好能同屏」。而本方案 R2 把卡宽标定在**常态 3 项同屏**，推论是**角色选择屏的 5 张卡同样需要滑动 1–2 次**。

- **若采纳本方案**：两处横滑区共用同一个卡宽基准，「同款手感」这句由构件与参数共用来兑现；代价是角色选择屏不再可能一屏看全 5 张，玩家要滑动比对。
- **若坚持 5 张同屏**：卡宽须压到屏宽的 ≈ 18%（1080 基准下 ≈ 190 px），而事件卡要装六个位（含双方等级一行），该宽度下副文本与数值行几乎不可读，实际后果是**两处横滑区必须各用一套卡宽** —— 「同款手感」当场退化为「同一种手势、不同的排版」。
- **本草稿的倾向**：共用基准（选前者），并把「角色选择屏 5 张卡的同屏容纳度」这条待实测项**改写为已答**（结论：不追求同屏，滑动即可）。**但这条改写触及一份既有文档的待决项，故列在此处由用户裁决，不在草稿里自行落笔。**

→ **已裁决（2026-09-08 · 批量评审）：两处共用同一卡宽基准**（常态 3 项同屏 + peek 标定）。角色选择屏 5 张卡照常滑动、不追求同屏。**连带落笔项（纯机械，答案已定于本裁决）：** `ux/screen-flow.md` 角色选择屏那条「5 张卡在主流竖屏比例下的同屏容纳度待实测」改写为已答（不追求同屏，滑动即可）——该改写归 `/analyze-new-ideas`，本批不动主题文档。

## 仍需用户决定

### 第 1 题 · 事件选项的「进入手势」（横滑区的择一动作）

**背景（自包含）：** 事件选择区是一条横向滑动的卡片带，玩家从本批 1–5 个事件里选一个进入。选中即**立即、不可逆地支付寿元**（`selectCost` 无条件施加，付不起也照付，付完可能当场归零 → 角色终结），而这是全游戏最高频的操作（一个篇章 30+ 次，一次轮回 100+ 次）。本库两处先例相反：**角色选择屏**用「点选 + 独立确认按钮」（明写理由是「防误触即开局」），**储物袋的道具使用**不做任何确认（明写理由是「不在最高频操作上多一次点击」）。

| 选项 | 形态 | 后果 |
|---|---|---|
| **A · 焦点制（推荐）** | 点按**非焦点**卡 → 它滑到中心成为焦点，不支付、不进入；点按**焦点**卡 → 支付并进入 | 零新增控件、零额外纵向空间；误触需要在**同一张卡上连点两次**才成立，安全度接近两段确认；与 `ux/screen-flow.md` 里 Explore 流程图「横滑选择区 ──点选──▶ [支付]」一致（点的就是焦点卡）。代价：新手第一次点边缘卡会「只居中不进入」，有一次学习成本 |
| **B · 单击即进** | 点按任意卡（含边缘卡）→ 立即支付并进入 | 操作最少，最贴「不在最高频操作上加点击」。代价：竖屏窄栏下边缘卡只露一部分，误触概率实打实，而这次误触**不可逆且可能致死** |
| **C · 选中 + 底部确认按钮** | 点按卡 = 选中（高亮），底部主按钮「进入」提交 | 与角色选择屏逐字同构、最安全。代价：全游戏最高频路径上每次多一次点击（一轮回 100+ 次）；底部常驻按钮吃掉一条横带，而选择区上方已有状态条 + 经验条两行；且要改写 Explore 那张既有流程图 |

**推荐 A。** 理由：它在**不新增任何控件**的前提下拿到了两段确认的安全性（第一次点是导航、第二次点才是提交），且与既有的 Explore 流程图不冲突；B 的误触后果是本作最重的一类（角色终结），C 的持续成本落在全游戏最高频的那条路径上。

→ **已裁决（2026-09-08 · 批量评审）：A · 焦点制。** §1.4 按此收口：点非焦点卡 = 居中导航、不支付；点焦点卡 = 支付并进入。零新增控件、不改 Explore 既有流程图。

### 第 2 题 · 闭关构筑面板中「走火入魔风险档」候选的标注强度

**背景（自包含）：** 闭关（Research）= 玩家调整卡组的事件。面板上每个「决策槽」摆 3 个候选（学新功法 / 升阶 / 弃置 / 移除散牌 / 得法宝），其中可能有一个**风险档候选**：选它则法力上限 `manaLimit` **成功 +1、失败 −1**，成败在事件生成时已掷定并落存档，**面板上绝不预先展示结果**（既定纪律）。设计上它是 Research 唯一的内部张力（没有它，闭关就是「最贵但必然赚」的无脑首选），承重理由是「**玩家自己按下那个按钮**，风险是被选择的，不是被施加的」。待定的是**这枚标注长什么样、要不要把 `+1 / −1` 的规则明写在候选上**。

| 选项 | 形态 | 后果 |
|---|---|---|
| **A · 中性标记 + 明写规则（推荐）** | 顶带右上角一枚**中性色**符号（如「险」字章 / 阴阳纹），下方常驻一行小字：「成功 法力上限 +1 · 失败 −1」 | 玩家能给这个赌注定价（与「`selectCost` 恒精确、可比价」同调），又不被劝退——风险读作一个**可选的赌注**而非警告。代价：新手可能低估它，第一次 `−1` 才明白分量（可接受：这正是「自选风险」的体验） |
| **B · 警示色 + 明写规则** | 同 A，但标记与描边用**警示色**（与寿元 `< 10%` 转红同一套告警色） | 最醒目、最不容易被忽略。代价：**稀释告警色的语义** —— 本库目前告警色的唯一用法是「寿元见底」这条真实危机，把它扩到「玩家主动选的赌注」上之后，红色就不再等于「你有麻烦了」；且它在观感上像是系统在劝阻，与「风险是被选择的」相抵 |
| **C · 标记 + 只给定性文案** | 一枚标记 + 一行定性文案（如「有走火入魔之险」），**不写 `+1 / −1`** | 保留神秘感，与「给方向不给数字」同族。代价：`manaLimit` 是**明面资源**（战斗内常驻可读、经验条式的明面成长量），藏起一条纯规则会让玩家无法为赌注定价——这与「隐藏的是经验档位映射 / 隐藏属性数值」不是同一类东西，可能被读成信息缺失而非神秘 |

**推荐 A。** 理由：`manaLimit` 是明面资源、`+1 / −1` 是**规则**而非隐藏映射（既定的「不预先展示」保护的是**已掷定的结果**，不是规则本身）；而告警色在本库有一个已确立、且值得保护的专属语义（寿元危机）。

→ **已裁决（2026-09-08 · 批量评审）：A · 中性标记 + 明写规则。** §2.3 按此收口：中性色标记 + 常驻一行「成功 法力上限 +1 · 失败 −1」；告警色的专属语义（寿元见底）不被稀释；已掷定的结果仍绝不预展。
