# 方案草稿 — 跨库失配收口与桥接机制（后端侧）

> **本草稿只承载归属判给后端的那一半。** 客户端侧的一半（`Source` 收口的传导、`profile-sync` 七点欠账的落笔形态、桥接台账的客户端落点）在 `counterpart` 那份里，两份**必须同批采纳**——单侧采纳即两侧仍不一致。

## 问题

2026-08-16 的两库全量就绪度评估暴露出三处跨边界失配（完整分类见 counterpart 的问题段）。**其中只有一处欠在后端侧**，但它是三处里唯一需要**新增契约面**的：

> 客户端 `systems/monetization.md`（08-15b）已定案：**购买由后端验票**，验票通过后**后端把云端 `bundleGrantOrdinal` 与 `cloudRevision` 各 +1**。客户端 `systems/services/sync-service.md` 称之为同步模型此前没有的**第四种情形：后端主动写入**。
>
> 本库对此**零承载**：`contracts/` 四份不含购买域、无验票端点；`profile-sync.md` §2 / §5 仍写「`accountSeed` 是后端唯一写入的字段」；`contracts/_index.md` 仍宣称「契约面成文完毕——四份，无第五份」。

另两处（`Source` 序列化形态、`profile-sync` §6 §7 七点）**后端侧不欠任何东西**——它们已在 `profile-sync.md` §5a / §6 / §7 写完，欠的是客户端的传导落笔。本草稿对这两处只做一件事：在桥接台账里确认它们的状态，不重复设计。

## 约束（来自既有设计）

- **技术栈未定**（`06-platform-stack.md`）⇒ 方案必须停在**协议与语义层**，不指定语言 / 框架 / 存储实现。
- **客户端侧语义已定，是硬前提**：谁有权 +1（只能是后端）· 兑现段仍由客户端掷骰、后端复算 · 购买只在主菜单发起且待发队列必须为空 · 购后强制一次 pull。这些**不在本库重新讨论**（归属判据：客户端语义已定、只剩服务端如何兑现 → 本库承接兑现形态）。
- **`revision` CAS 的三分支表不得为购买开例外**（`profile-sync.md` + 客户端 `sync-service.md`）——客户端已用时机纪律在结构上关闭了冲突窗口。
- **契约表达形式已定**：OpenAPI 3.1 单点，markdown 承载语义、spec 承载形态（`envelope.md` §1）。
- **枚举值一律字符串、与客户端 C# 成员名逐字相同**（`envelope.md` §2）。
- 复算不一致的既定处置：**接受写入 + 打风控事件，不拒绝、不改写**（§7a）。

## 建议方案

### B1. 购买域单开第五份契约 `contracts/purchase.md`，不塞进 profile-sync
`[既有推演]` · 文件命名 `[已裁决 2026-08-16]`：取 `purchase.md`，与既有四份的**域命名**同形（`envelope` / `content-manifest` / `auth` / `profile-sync` 皆按域而非按数据类命名）。否决 `entitlement.md`——本域的内容主体是验票流程，权益本身的形态归客户端 `PlayerEntitlement`。

**⇒ 首先要作废一条断言**：`contracts/_index.md` 与 `01-contracts.md` 的「契约面四份齐备，无第五份」不再成立。它当初排除的是已撤销的剧本契约，没有预见到购买段。

**为什么单开一份而不并进 `profile-sync.md`：**

- **域不同。** `profile-sync` 的全部端点是「客户端上行 / 下行自己的 profile」，其承重纪律（后端对透明段只读、后端不裁决、复算不拒绝）**恰恰全部不适用于购买**——购买是后端权威写入、必须裁决、必须能拒绝。把两套相反的纪律塞进一份契约，读者无法判断哪条管哪个端点。
- **`_index.md` 已有的分域惯例**（边界层 / 内容分发 / 登录会话 / 存档同步）是按**域**分的，购买是第五个域。
- **它牵动平台 SDK 与渠道回调**，与 `02` 的「自建 vs 第三方」耦合；独立成文才能让那条耦合显式可见。

### B2. 端点形态：一个验票端点 + 一个幂等查询，不要回调即写
`[既有推演]` + `[通行做法]`

| 端点 | 语义 | 谁调用 |
|---|---|---|
| `POST /v1/purchase/verify` | 提交平台收据 → 后端向平台校验 → 通过则 `bundleGrantOrdinal += 1` 且 `cloudRevision += 1`，回新序号与新 `revision` | 客户端（购买成功后） |
| `GET /v1/purchase/receipt/{receiptId}` | **幂等读**：查询某张收据的验票结果（未提交 / 已通过 + 序号 / 已拒绝 + 原因） | 客户端（pull 失败后重试、或跨启动补查） |

- **验票必须由后端向平台服务器校验，不信客户端自述**（`[通行做法]`：移动内购防篡改的标准形态；客户端已明写「付费凭证不能只信客户端」）。
- **第二个端点是承重的，不是可选便利**：客户端在「已付款、后端已 +1、但响应丢失」这一移动网络常态下**必须**有一条查得回来的路径。这与 `profile-sync` 为同一场景引入 `pushId` 幂等键是同一条理由——只是这里的幂等键是**平台收据 id**（天然全局唯一、由平台发放，无须客户端生成）。
- **幂等口径（承重）**：同一 `receiptId` 重复提交**绝不重复 +1**，直接回上次结果（与 `pushId` 的 `Deduplicated = true` 同构）。缺这一条，网络重试会让玩家的序号跳号、掷骰序列错位。
- **渠道回调 = 只作对账 / 补偿通道，不作写入路径**（`[已裁决 2026-08-16]`）。渠道回调时序不可控（可能早于、晚于、或永不到达客户端的 verify），把它作为写入路径会让「玩家已付款但序号未涨」无处排查，且要额外处理「回调与 verify 竞态」——而那条竞态的收益仅在「客户端崩溃且从不回来」这一场景。⇒ **写入只由 verify 端点承担**；回调记账 + 补偿任务落 `operations/`，作为「已付款但从未 verify」的兜底发现手段。

### B3. 后端主动写入与 CAS 的共存：不新增机制，靠客户端的时机纪律 + 一次 pull
`[既有推演]`

客户端已经把冲突窗口在结构上关掉了（购买前待发队列必为空 ⇒ 那一刻没有任何未上行的变更 ⇒ CAS 的 `baseRevision < cloudRevision` 分支不可能踩到）。**后端侧因此不需要为购买新增任何同步机制**，只需三条声明：

1. **`profile-sync.md` §2 / §5 的「`accountSeed` 是后端唯一写入的字段」改写为一张封闭两行表**（`[已裁决 2026-08-16]`，松动获准 + 护栏见「与既有决策的张力」）：

   > **后端写入字段表（封闭）**
   >
   > | JSON path | 写入时机 | 频次 | 权威 |
   > |---|---|---|---|
   > | `/accountInfo/accountSeed` | 账号创建时 | 一次，此后不变 | §2 |
   > | `/entitlement/bundleGrantOrdinal` | 每次验票通过时 `+1` | 反复 | `purchase.md` |
   >
   > **其余一切字段后端只读。本表封闭——新增后端写入字段是破坏性契约变更，须两侧同批评审。**

   措辞纪律：**不写成「后端可以写透明字段」**。规则仍是「后端只读，除表内两项外」，而不是退化为「后端有时可以写」。
2. **verify 端点的 `cloudRevision += 1` 必须与 `bundleGrantOrdinal += 1` 在同一次事务内**（与 §5 的 CAS 纪律「禁止先写 profile 再改 revision 的两步非原子形态」同一条）。
3. **verify 不接受客户端携带 `baseRevision`、不做 CAS 判定** —— 它是后端权威写入，不是客户端提交的 diff。客户端拿新 `revision` 的路径是**购后强制 pull**（客户端已定）。

4. **verify 的应答只回序号 + revision，不内联新 profile**（`[已裁决 2026-08-16]`）。客户端 08-15b 已明写「购买成功后强制一次 pull」，两侧形态因此一致；且让 verify 保持**窄接口**、不与 profile 的下行形态耦合。否决内联（省一个 RTT，但把 profile 的完整下行形态复制进购买域，两处形态从此要同步演进——正是本次要根治的那类第二权威）。

### B4. `bundleGrantOrdinal` 补进 §5 透明字段白名单
`[既有推演]`

§5 表中的预留行说明「落点在客户端尚未定」——**它已于 08-15b 定案**（`PlayerEntitlement.BundleGrantOrdinal`）。⇒ 按同形态补入：

| JSON path | 类型 | 后端用途 |
|---|---|---|
| `/entitlement/bundleGrantOrdinal` | number int | 复算 `PremiumBundle` 域掷骰的 `ordinal`；**单调 `+1` 校验**；**后端写入**（唯一的第二个写入字段） |

**须与 counterpart 同批落笔**——路径由客户端存档结构决定，本库单方面写死会在客户端改结构时静默失配（正是 §5 那条承重纪律描述的失败形态）。

### B5. 复算：购买段与残卷共用同一条复算链，不新开
`[既有推演]`

客户端兑现段用 `AccountRng.For(PremiumBundle, ordinal)` 掷骰抽 3 条，后端以同一 `(accountSeed, stream=1, ordinal)` 复算——**这正是 §6 SplitMix64 已经定义好的东西**（`AccountStream.PremiumBundle = 1` 已在 §6 冻结）。⇒ 购买契约**不定义任何新的随机源**，只回链 §6。

复算不一致的处置**沿用 §7a**（接受写入 + 打风控事件），不为购买单开更严的处置：兑现段的条目是客户端从池里抽的，与残卷同构；真正需要严格把关的是**验票**那一步，而它由平台校验兜住。

### D. 桥接机制：本库侧的承接台账
`[既有推演]`

完整的机制设计、病因诊断与维护者分工见 **counterpart 的 D 段**（两份不重复写，避免第二权威）。本库侧只记落点与首批条目：

- **新增 `open-questions/cross-boundary.md`**（`[已裁决 2026-08-16]` 不带编号，与客户端库同名同形；本库编号 `03` `05` 已空缺且约定不回填，新增编号只会加剧两库编号错位）。
- **只装「客户端已定案、本库尚未承接」的条目**，每条形态：`客户端权威文档路径#小节 | 客户端定案日期 | 本库需改的文档 | 一句话摘要`。**只回链、不复述。**
- **首批条目（1 条）**：购买段（客户端 08-15b 定案 → 本库需新增 `contracts/purchase.md` + 改 `profile-sync.md` §2 §5 + 改 `_index.md` 的四份断言）。
- **确认无欠账的两处**（写进台账抬头作为对账基线，不作为待办）：`Source` 序列化形态已由本库 §5a 收口（欠客户端传导）· `profile-sync` §6 §7 七点已成文（欠客户端落笔）。**这两处的球在对侧**，本库不重复设计、也不催办——它们出现在 counterpart 的客户端台账里。

## 具体形态（可 derive 的落地面）

> 停在协议与语义层（栈未定）。字段形态最终由 spec 单点承载，此处只给语义骨架。

**`POST /v1/purchase/verify`**

| 方向 | 字段 | 语义 |
|---|---|---|
| ↑ | `platform` | 枚举字符串，取值与客户端 C# 成员名逐字相同（`envelope.md` §2） |
| ↑ | `receiptId` | 平台收据唯一 id ——**幂等键** |
| ↑ | `receipt` | 平台原始收据负载（形态随渠道，待 `02`） |
| ↓ | `bundleGrantOrdinal` | +1 后的新序号（**兑现段掷骰的 `ordinal`**） |
| ↓ | `revision` | +1 后的新 `cloudRevision` |
| ↓ | `deduplicated` | boolean；同一 `receiptId` 重复提交时为 `true`，序号与 revision 回上次结果 |

失败面（错误码归 `envelope.md` 的分层台账，具体码待落笔）：收据无效 / 已被其他账号核销 / 平台服务不可达（**可重试**，须与「无效」在报文层面可区分——否则客户端无从判断该不该重试）/ 合规拦截（分支待 `02`）。

**`GET /v1/purchase/receipt/{receiptId}`** —— 回 `status ∈ {unknown, verified, rejected}` + `verified` 时的 `bundleGrantOrdinal` / `revision` + `rejected` 时的原因。**纯读、幂等、不产生任何写入。**

**服务端保证（可写成栈中立的验收断言）**

1. 同一 `receiptId` 提交 N 次，`bundleGrantOrdinal` 恰好 +1；第 2..N 次回 `deduplicated = true` 且序号与第 1 次逐位相同。
2. `bundleGrantOrdinal` 与 `revision` 的自增**要么都发生、要么都不发生**（同一事务）。
3. verify 通过后立即 `GET /v1/profile`，读到的 `/entitlement/bundleGrantOrdinal` 与 verify 应答一致。
4. `bundleGrantOrdinal` 账号级**严格单调递增、不清零**（与 `finaleWinOrdinal` 同一条纪律）。

## 后果

- **契约面从四份变五份** ⇒ `contracts/_index.md` 的「四份，无第五份」断言与 `01-contracts.md` 抬头同批改写（后者已于 08-16b 标注作废）。
- **`profile-sync.md` 两处改动**：§2 / §5 的「后端唯一写入字段」表述 · §5 白名单补 `/entitlement/bundleGrantOrdinal`。**这是本次唯一会改动已成文契约的地方**，属语义补充而非形态变更，**不 bump 任何已定形状**。
- **牵出 `02` 的一项新耦合**：验票走平台 SDK ⇒「自建 vs 接第三方」的决定同时决定了渠道回调与收据校验的形态。建议在 `02` 的该条目下加一句回链。
- **`operations/` 多一份计划文档**（购买对账与补偿），随栈落定后展开。
- **对 derive 就绪度的影响**：本库 blocked 项不因此减少（`systems/` / `operations/` 仍前置于 `06`），但 `contracts/` 的跨边界缺口收敛。（**本草稿不评估就绪度**。）

## 备选方案（已考虑并否决）

- **把购买端点并进 `profile-sync.md`** —— 否决，理由见 B1（两套相反的承重纪律不能同居一份契约）。
- **平台回调直接写库、不设 verify 端点** —— 否决，理由见 B2（回调时序不可控，且「已付款未涨序号」无处排查）。**回调保留为对账通道**。
- **让客户端携带 `baseRevision` 走 CAS 提交购买** —— 否决。购买是后端权威写入，走 CAS 等于承认客户端有权参与决定序号；且客户端此刻的 `baseRevision` 必然落后，CAS 只会失败。
- **为购买在 CAS 三分支表加第四分支** —— 否决。客户端的时机纪律已在结构上关闭该窗口，加分支等于为一个不可达的情形增加同步模型的复杂度，且与「不为购买开例外」正面冲突。
- **验票也由客户端做、后端事后复算** —— 否决（客户端已明确否决过同构方案：客户端置位 = 客户端有权发货，事后发现不一致时玩家已拿到东西）。
- **在本库复述客户端的时机纪律与兑现流程** —— 否决。回链即可；复述会制造第二权威，而客户端那侧才是它的归属。

## 与既有决策的张力（已裁决：松动获准）

`profile-sync.md` §2 / §5 的「**后端对透明段同样只读；唯一的写入是账号创建时的 `accountSeed`**」是一条写得相当绝对的承重纪律，本方案要求松动它（新增第二个后端写入字段，且是反复写入的）。

**⇒ 用户已于 2026-08-16 裁决：松动的代价可以接受，按松动定案，采用封闭两行表的护栏形态。**

- **为什么必须松动**：客户端 08-15b 已定「只能是后端」有权推进 `bundleGrantOrdinal`，否则防篡改归零。这条是客户端侧的承重定案，不可绕过。
- **被接受的代价（如实记录，不粉饰）**：那句话原本的价值在于「后端只读」是一条**无例外**的简单规则，读者不必记例外。开这个口子后，**未来每一条「能不能让后端也写这个」的讨论都会引用它作先例**——这是已知且被接受的后果。
- **护栏（定案形态）**：改写为**封闭的两行表**（形态见 B3 第 1 条），并明写「**本表封闭；新增后端写入字段是破坏性契约变更，须两侧同批评审**」。规则因此仍是「后端只读，**除表内两项外**」，而不是「后端有时可以写」。
  **落笔纪律**：任何后续要求扩这张表的提案，须在提案里显式引用本条护栏并说明为何不能用别的通道——**不得静默加行**。
- **已否决的替代方案**：把 `bundleGrantOrdinal` 移出 profile 聚合、单独存在后端的购买域（客户端只读取、不落存档）。代价更高——它会让兑现段的掷骰 `ordinal` 来自一个不在 profile 里的字段，破坏「整次授予由 `(域, 序号)` 完全确定且随授予事务同一次持久化」这条客户端承重纪律，且 `AccountRng` 的两个域会有两套来源。

## 前置依赖
