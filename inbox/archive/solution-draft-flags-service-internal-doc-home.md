# 方案草稿 — flags 请求处理路径（A6–A9）的文档归属

## 问题

`operations/content-delivery-ops.md` 的 A6–A9 描述的是 `GET /v1/content/flags` 的**请求处理路径**，即后端进程内的行为：

- **A6** 不引入按账号的解析结果缓存；缓存对象是**规则集本身**，键 = `flagsVersion`；冷启动 / 新版本首波用**请求合并（single-flight）**收敛回源；一旦引入按账号缓存，键**必须**是 `(flagsVersion, accountId)`。
- **A7** 应答体的 `flagsVersion` 取自它**实际使用的那条规则集记录**，绝不取自高水位。
- **A8** `X-Flags-Version` 下发值 = `min(高水位, 本实例当前能兑现的最大规则集版本)`。
- **A9** 「本实例能兑现的最大规则集版本」由 A6 的规则集缓存自然给出——该实例已装载的最大键。

这四条**都不是运维形态**：它们既不描述发布流程、也不描述人机接口或托管能力要求，而是「一次请求进来，进程内怎么算」。而：

- `systems/_index.md:18` 的服务职责表**已把这份职责登记给 `systems/content-delivery.md`**，该文件**至今不存在**（`systems/` 下只有 `_index.md` · `account.md` · `profile-store.md`）；
- `systems/_index.md:10` 写它「尚未建立…此前欠的两项前置**已全部答结**…**服务内部形态具备开写条件**；按『先有设计再建文件』，在有实质设计之前仍不预先占位」；
- `operations/content-delivery-ops.md:3` 自陈范围是「语义权威在 `contracts/content-manifest.md`；本文件只记它对**运维形态**的要求，以及由此反向落在托管选型上的约束」——**它没有认领服务内部形态**。

⇒ 这四条切片写成 FR 时 `service:` 无处可指；且全库无任何一处已作出该归属裁决（相关记述全部停在「未裁决 / 尚未建立 / 具备开写条件」）。

### 4. 迁入后各节要承载什么（含三条本次推演出的新内容）

#### 4a. 三份缓存的分工（承重）

`[既有推演]` 该请求路径上有**三份互不相干的缓存**，混用任意两份都会破坏一条已定纪律，故必须在文档开头一次列清：

| 缓存 | 键 | 值 | 位置 | 生命周期 |
|---|---|---|---|---|
| 规则集缓存（A6） | `flagsVersion` | 规则集记录（不可变） | **进程内** | 永不失效，LRU 回收 |
| 当前版本读取缓存 | —（单值） | `flagsVersionHighWater` | 进程内 | TTL 5 秒（`ops` 旋钮表） |
| 应答签名结果缓存 | `(flagsVersion, accountId)` | `sig` | 进程内 | LRU 回收 |

- **规则集缓存必须是进程内、不得落 Redis。** A9 的整个取数面是「**本实例**已装载的最大键」——Redis 是跨实例共享的，放进去就没有「本实例能兑现什么」这个概念，A8 的 `min()` 右操作数当场失去指称对象。这同时是 `_index.md:41`「Redis 只承担限流计数器」在本域的具体落点。
- **当前版本读取缓存与 `environments.md` 配置三层里那个约 30 秒的 `config_knob` 进程内缓存是两份东西，不得混用**（`ops` 已定，此处只回链）。
- **签名结果缓存的键含 `accountId`，但它不是 A6 否决的那种「按账号解析结果缓存」**：缓存的是 `sig` 而非 `disabledIds`，契约要求 `disabledIds` 恒定、不要求 `sig` 逐字节恒定（`ops` 已论证，此处回链不复述）。

#### 4b. 版本预热：装载的触发面（**本次推演出的一处缺口**）

`[既有推演]` **这一条是新内容，不在 A6–A9 的任何一条里，但由它们合成推出。**

A6 只说「冷启动 / 新版本首波用 single-flight 收敛回源」，读起来装载是**请求驱动**（懒加载）的。但 A8 把头钉成 `min(高水位, 本实例可兑现)`，而客户端「等值不拉」⇒ 组合出一个自锁：

```
实例未装载新版本 → 它下发的头不涨 → 客户端不拉 flags → 该实例收不到 flags GET → 永不装载
```

集群内每个实例都懒加载时，**一次 `publish` 可能对全体设备永不生效**，而 T 的探针（实例间 gauge 极差 ≠ 0 且持续超 T）**发现不了**——极差为 0，全体一致地卡在旧版本。

⇒ **装载必须有请求无关的触发**：实例侧的当前版本读取缓存每次刷新（TTL 5 秒）发现高水位更大时，**主动装载该版本的规则集**，装载成功后本实例可兑现的最大版本才随之抬高（保住 A8 的「头永不领先」）。成本 = 实例数 × 每次发布一次回源，可忽略。

**配套的观测缺口（属对侧运维文档）：** 现有告警断言只看实例间极差，看不见「全体一致地落后」。建议在 `operations/observability.md` 补一条断言：**`高水位 − 本实例可兑现的最大版本` 持续 > T 即告警**（取数面仍是 A9 那个 gauge，零新增机制）。本草稿只提出，不代该文档落笔。

#### 4c. 应答的构造：一次快照引用（A7 的实现手法）

`[既有推演]` A7 说「绝不取自高水位」，`ops` 已点明「高水位就在手边、取错极自然」。把它从「要靠实现者记住的纪律」变成**结构上不可能违反**的手法：

> 一次请求**先取定一个规则集缓存条目的引用**，此后应答的全部取值——`disabledIds` 的分桶计算输入 · 应答体的 `flagsVersion` · 签名缓存的键 · 签名覆盖的字节——**一律从这一个引用派生**，请求处理路径上不再第二次读取高水位或缓存。

这与 `profile-store.md` 纪律 2「回声校验读的是本事务内已加锁的当前值」是同一手法的两个实例：**先取定一个快照，其后全部取值同源**。

#### 4d. 回源失败的降级（A8 不对称性的直接推论）

`[既有推演]` single-flight 回源失败时的处置，由 A8 的不对称性直接给出：

- **本实例已装载过更旧的版本** → **用它兑现应答**，应答体与头都是那个更旧的版本号。这正是 A7 / A8 整套设计要覆盖的情形：头落后于高水位在客户端侧**零告警、零上报**，只是晚一拍。
- **本实例一个版本都没装载**（冷启动首个请求且回源失败）→ **返回错误应答，绝不以空 `disabledIds` 兑现**。空集合语义上是「什么都没关」，会让秒关静默失效，且客户端会把它当作一批合法的 flags 持久化下来作降级值（`contracts/content-manifest.md` B 组第 7 条的依赖方②）。
- **失败不写负缓存**——一次瞬时存储故障会被缓存住，把秒级抖动放大成 TTL 级失效。
- 错误应答用 `Retryable` 类；**是否需要一条专属 `code` 归 `contracts/envelope.md` §6 台账裁决，本文件不新增码**（见 `## 前置依赖`）。

#### 4e. 规则集缓存的容量上限

`[通行做法]` 键不可变 ⇒ 无失效逻辑，只需一个 LRU 容量上限。稳态下同时可达的版本只有 1–2 个（当前版本 + 刚发布尚在传播的那个），故上限取 **8**（数量级余量，规则集体积极小——一批 `Id` 集合 + 分桶规则）。**待实测校准的初值**；它是进程内容量常数、不构成运营旋钮，**建议不进 `ops` 的「数值初值一览」**（那张表登记的是运维可调面）。

- **A6 / A7 / A8 / A9 四行整体删除**，在原表位置留**一行**：

## 备选方案（已考虑并否决）

- **明文裁决 A6–A9 就地留在 `operations/content-delivery-ops.md`** — 见「仍需用户决定」第 1 项的选项 B；否决的主要理由是它要改三处自陈 / 台账，且让第三个服务永久缺服务文档，与 `systems/_index.md:3` 的分工判据正面冲突。
- **新建一份只装 A6–A9 的窄文档**（如 `systems/flags-request-path.md`） — 与「文件名与它所服务的客户端成分对齐」的约定相抵（`systems/_index.md:57`），且会让 `content-delivery` 的其余服务内部形态日后无处可去、又要再建一份。
- **把 A6–A9 上提到 `contracts/content-manifest.md`** — 契约是边界报文与服务端**义务**的清单，A6–A9 是兑现手段；上提会让契约面凭空长出实现细节，且 B 组已明写「是否引入缓存层本身不在此裁决」。
- **规则集缓存放 Redis 以省一次跨实例回源** — 破坏 A9 的取数面（见 4a），且与 `_index.md:41`「Redis 不持有任何权威状态」的边界模糊。省下的是每实例每次发布一次读取，收益近似为零。
- **靠压小当前版本读取缓存 TTL 来缓解 4b 的自锁** — 治不了：无论 TTL 多小，懒加载下不发生 flags GET 就不装载，自锁与 TTL 无关。

## 与既有决策的张力

**一处，且只在「只迁 A6–A9」这一选项下存在。**

`systems/_index.md:3` 的分工使「规则集表的承重列与唯一写入面」（现 `ops` A1 / A2 / A3 / A5）本应落在 `systems/`。只迁 A6–A9 时，新文档的「存储形态：承重列」与「唯一写入面与事务边界」两节将**回链 `operations/`**——这与本库其余两份服务文档的方向相反（它们持有承重列，由 `ops` 回链它们），是一次方向反转的回链。

- **不松动时的替代**：按「仍需用户决定」第 2 项的选项 B 同批迁移，方向即不反转。
- **松动的代价**：留一个已知的、可在下一次 handoff 补齐的结构不齐；不影响任何机制正确性，也不影响 A6–A9 的 FR 可切出。

`ADR-0047` / `ADR-0009` **无张力**——本方案不改任何一条纪律的内容，只改它写在哪份文档（ADR-0047 的一句指路需同批对齐，见「后果」）。
