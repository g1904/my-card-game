# 方案草稿 — 「还有几步到 Finale」的前瞻

> **⚠ 裁决结果与本草稿的主体提案相反（2026-09-06 · 批量评审）。**
> 用户裁决：**不补这一角，三章一律不显示**，接受「知道自己在长多快、不知道还剩多远」（即「仍需用户决定 ①」的选项 B）。
> ⇒ **下方「建议方案」A–G 各节的落笔面整体作废**，`targets` 里的 `ux/screen-flow.md` 不再有改动面。

## 问题

中长期规划感的三角已答两角：

- **地理方位感** —— `LocationCodex` 记连边，玩家跨轮回重建 `locationMap`，在 Travel 闸门处提前两步规划路线（08-06c 定案）。
- **进度感的时间那一半** —— 经验条常驻 EventOption 选择界面的角色状态条（`当前 / 本级阈值`），在 ch2 / ch3 是唯一的连续进度感来源（08-30 承接）。

**仍悬着的是空间那一角**：全库没有任何通道回答「还有几步到 Finale」。玩家读得到「我在长多快」（经验条）与「我还能走多远」（寿元恒精确常驻），读不到「我还需要走多远」。是否补一条轮回内的前瞻（篇章进度条？前瞻提示？），还是接受这一角空着。

**一条必须先钉死的前置**（本草稿的全部推演都建立在它上面，且它**已定、无需臆造**）：

> Finale 的出现条件 = **`level == 该境界末级`（全局序 13 / 17 / 21）**，由 future-event-service 在物化时以 `Priority = 1` 抬升，`prioReason = Finale`。
> —— `systems/services/future-event-service.md`「三条抬升条件」表与置位段伪码；同条另有明写「Finale 不绑定 location、不受 `eventCountLimit` 牵制」。

**推论（承重）：「还有几步到 Finale」不是一个待发明的量——它就是「还差几级到本境界巅峰」，而这个量的两个输入（`level`、`experiencePoint`）都已经在角色档案上，且都已经是明面量。** 缺的不是机制，只是把已常驻的经验条从「本级进度」升格为「到巅峰的进度」。

## 约束（来自既有设计）

- **Finale 的闸是等级，不是事件数、不是 location、不是寿元。** → `systems/services/future-event-service.md`、`systems/adventure-event/travel/_index.md`「与篇章 / 境界推进不耦合」。
- **本章事件总数在运行中不是一个确定的数。** 「篇章事件总数 ≈ 途经各 location 的容量之和」，而途经哪些 location 由玩家往后的 Travel 选择决定，各 location 的 `EventCountLimit` 取值不同 ⇒ **「本章共 N 个事件」这个 N 在轮回进行中不存在**。→ `systems/game-progression.md`「`eventCountLimit` 是篇章节奏的结构单位」。
- **经验条已常驻，显示 `当前 / 本级阈值`**；`ch2 / ch3 每 9–11 个事件才升一级`，中段十几分钟无等级反馈已被认定为**必须补偿的节奏缺口**。→ `ux/screen-flow.md`、`systems/game-progression.md`。
- **eventOption 卡片不标注该事件的经验产出档位**（保护的是**隐藏的**经验档位映射）。→ `ux/screen-flow.md`「配套纪律」。
- **寿元明文常驻、恒精确**，且**明确否决「大限将至」一类预警文案**（余量已精确 ⇒ 预警没有存在理由）。→ `systems/character-profile/life-span.md`、`ux/screen-flow.md`。
- **角色状态条的版面已经紧**：第一行五个字段并排、`❤` 位按四位数排版、字宽须实测。→ `ux/screen-flow.md`「⚠ `❤` 位按四位数排版」。
- **满级后经验直接丢弃，UI 标注「已圆满」** —— 这条标注已定，只是尚未定落点。→ `systems/game-progression.md`「溢出即弃」的缓解项。
- **future-event-service 是无记忆的纯产出侧，零改动、不新增写入面**；不持有跨批次状态。→ `systems/services/future-event-service.md`。
- **UI 文案一律走 `res://text/` 翻译键，无 hover-only 可供性。** → `.claude/rules/ui-input-rules.md`、`ux/error-and-blocking-ux.md`。
- **不为分章写分支**（赋级带 / 批次规模 / 阈值表同款纪律）。→ `systems/balance.md`。

## 建议方案

### A. 补，且只补一条读数：把经验条升格为「到巅峰」的两级读数

`[既有推演]`

角色状态条第二行的经验条**保持原样**（`当前 / 本级阈值`，它承载的是「长多快」），**在其右侧追加一格静态文本读数**：距本境界圆满还差几级。

```
┌─────────────────────────────────────┐
│ [安全区]                             │
│ 炼气七层 · ❤920 · ✦5/5 · 灵石 120    │  ← 第一行不动
│ ▓▓▓▓▓▓▓░░░ 经验 3/4 · 距圆满 6 级     │  ← ✚ 新增的只有「· 距圆满 6 级」这一格
│                     [袋]6 [卡组]     │
└─────────────────────────────────────┘
```

- **它就是「还有几步到 Finale」的精确答案**，因为 Finale 的判定式就是 `level == 末级`。两级读数合起来读作：「本级还差 1 点经验，再往上还有 6 级就到天劫」。
- **零新机制、零新字段、零存档增量**：`level` 与 `experiencePoint` 都已在 `CharacterProfile.Status` 上，阈值曲线已在平衡资源里（`Content.Single<T>()` 取，见 `.claude/rules/data-resource-rules.md`）。剩余级数 = 该境界末级全局序 − 当前 `level`，呈现层现算。
- **它同时消化掉一条已定但无落点的标注**：`level == 末级` 时这一格改读「已圆满 · 天劫将至」，正是「满级后 UI 标注『已圆满』」的落点——**同一格，不开第二处标注**。

### B. 粒度 = 以「级」为单位精确，绝不给「还需几个事件」的估算

`[既有推演]` + `[通行做法]`

- **「距圆满 N 级」是一个确定量**（读两个已知整数相减），说出口就永远兑现。
- **「还需约 M 个事件」是一个会漂移的承诺**：带经验的产出点只占事件总数约 75%、档位（`Minor / Standard / Major`）是隐藏映射、失败还要按 `FailureRatio` 折半。要算出 M 就得把隐藏的档位映射暴露出来——**这直接撞上「eventOption 卡片不标注经验产出档位」那条既定纪律**，而且算出来的还是个期望值，玩家按它规划后连输两场就发现被骗。
- 同款克制在本库已有先例：**寿元恒精确、但明确否决预警文案**（精确的量直接给，模糊的判断留给玩家）。本条与之同调——**给一个不会错的数，不给一个会错的估**。

### C. 不做篇章进度条（`x / N` 形态）

`[既有推演]`

**分母不存在。** 本章要走多少个事件 = 途经各 location 的 `EventCountLimit` 之和，而「往后途经哪些 location」由玩家自己在 Travel 闸门处选（80 / 20 掷定，且各地域容量不同）⇒ 运行中算不出 N。硬要给一个 N 就只能拿平均值编，那是「臆造一个数字」而不是「呈现一个事实」。

**且它答的也不是这个问题**：即便 N 存在，走满 N 个事件也不触发 Finale——**触发它的是升满级**。进度条会把玩家的注意力引向一个不是闸门的量。

### D. 不做「天劫将近」的叙事前瞻提示

`[既有推演]`

- **最后一步本就自带前瞻**：升到末级的下一批 eventOptions 里 Finale 必现（旁路直占槽位，`Priority = 1`），玩家当场就看见它。再在前一级加一条「大劫将近」的旁白，是在**已经看得见的东西**前面加一次预告。
- 它还会撞既定纪律两处：**「不做『大限将至』一类的预警文案」**（同一族的预警型提示），以及**跨档叙事「只在跨档时触发、稀缺才有分量」**——多加一条固定触发的旁白会稀释那 2–4 条里程碑文案的分量。
- A 项那格「已圆满 · 天劫将至」是**静态读数**不是叙事旁白：它常驻、无演出、无入场动画（与寿元告警「静态标注、不做跳动」同调）。

### E. 服务查询面：不新增

`[既有推演]`

- **不给 future-event-service 加任何「剩余事件数 / 距 Finale 还有几步」的查询方法。** 它是无记忆的纯产出侧、不持跨批次状态、`Priority` 抬升由它独占置位——加一个前瞻查询面就是让它开始回答「未来」，而它的全部设计前提是「只算当前这一批」。
- 呈现层（EventOption 选择界面的 ViewModel）读 `CharacterProfile.Status.level` / `experiencePoint` + 平衡资源的阈值表，**现算、不缓存、随屏出生随屏消亡**（与图鉴屏、数据导出轮询同款工程纪律）。
- **零存档字段、零 schema 迁移、零新增存档点。**

### F. 触控与可供性

`[通行做法]`

- **纯静态文本，常驻可见，零 hover 通道、零点按通道**——它不是一个可交互元素，不新增触控目标，也就不产生触控目标尺寸问题。
- **不做点按展开「剩余各级阈值明细」的弹层**：那是在全游戏最高频的操作界面上加一层模态（撞「不在最高频操作上加模态弹层」）；两级读数本身已经把话说完了。
- **不做数字跳动 / 高亮动效**；升级那一刻数字自然变化即可（与寿元「静态标注、不做持续跳动」同调）。

### G. 文案与翻译键

`[通行做法]`

- 走 `res://text/` 翻译键，**不写中文字面量**；本路径不产生 `ERR_*` 键（无后端 `code`）。
- **不新开分区**——沿用角色状态条上既有标签（寿元 / 经验）所在的那个分区（分区划的是界面，不是内容域；本草稿不替它命名，见「前置依赖」第 2 条）。
- 两个键 + 一个数字格式参数：

  | 键（后缀形态，前缀随既有分区） | 文案 | 触发 |
  |---|---|---|
  | `..._STATUS_LEVELS_TO_PEAK` | 「距圆满 {0} 级」 | `level < 该境界末级` |
  | `..._STATUS_PEAK_REACHED` | 「已圆满 · 天劫将至」 | `level == 该境界末级` |

- **「级」这个量词是初值**：本作在 UI 上说的是「炼气七层」「筑基中期」，量词随境界变（层 / 期）。要不要按境界分两条键换成「层 / 阶」，是内容侧文案打磨项，**不改结构**（结构上恒是「一条键 + 一个数字参数」）。
- **全局序 1–22 绝不出现在 UI 上**（既定口径），呈现的永远是相减后的剩余级数。

## 后果

- **玩家第一次同时握有「还能走几步」与「还需升几级」两侧。** 寿元（明文精确）给出预算余量，本读数给出剩余需求——两者相除就是玩家自己的容错判断。**这正是「失败螺旋」被玩家提前察觉而非事后发现的通道**：连输两场后，寿元掉了一截而「距圆满」一格没动，螺旋当场可见。（本条**不**替 `失败螺旋的容错量验收` 那条待答项拍板 N，它只是让螺旋对玩家可见。）
- **补的是空间那一角，但补法是「把时间那一半的读数拉长一档」**——不新增第三套心智，玩家只需要读懂一条经验条。
- **应提炼进：** `ux/screen-flow.md`（角色状态条那一小节，权威）与 `systems/game-progression.md`（「中长期规划感的来源」待决项收口 + 「经验条常驻」那条承重推论的补充）。**`open-questions/06-meta-progression.md` 与 `systems/game-progression.md` 的待决问题小节里那一条随之移出**（由 `/analyze-new-ideas` 执行）。
- **不产生迁移**：无存档字段、无 schema 版本变化、无新增 `user://` 文件。
- **代价如实记下：** 状态条第二行多一格，竖屏窄栏的字宽压力再增一分（见「与既有决策的张力」）。

## 备选方案（已考虑并否决）

- **篇章进度条 `第 12 / 25 个事件`** —— 分母在运行中不存在（途经地域由玩家往后的选择决定），且事件数不是 Finale 的闸门。见建议 C。
- **「预计还需约 8 个事件到圆满」的估算读数** —— 要算它必须暴露隐藏的经验档位映射，撞既定纪律；且是会被两场失败打脸的期望值。见建议 B。
- **升到末级前一级时给一条「天劫将近」旁白** —— 与「不做预警文案」及跨档叙事的稀缺性两条纪律相撞；且末级那一批 Finale 必现，前瞻本就存在。见建议 D。
- **把经验条画成分段刻度（一段 = 一级，走完全境界）** —— ch2 / ch3 只有 3 段（够看），ch1 有 12 段（竖屏窄栏读不出来）。一个控件在一端好看、另一端不可读，就要为 ch1 特判——而「不为分章写分支」是既定纪律。纯文本两端都成立。
- **给 future-event-service 加 `GetRemainingToFinale()` 一类的查询** —— 它是无记忆的纯产出侧，加前瞻查询即让它开始持有「未来」。数据本就全在角色档案上，不需要绕道服务。
- **在主菜单 / 篇章结束屏也展示该读数** —— 主菜单是 PlayerProfile 级、轮回外无「当前角色的本章进度」可言；结束屏那一刻本章已结束。落点唯一。

## 与既有决策的张力

1. **版面预算（真实，需实测裁定）。** `ux/screen-flow.md` 已警示角色状态条「竖屏窄栏此处已有五个字段并排、字宽须实测」，且 `❤` 位在 ch3 要按四位数排版。本方案在第二行再加一格文本（约 6–8 个汉字宽）。
   - **缓解（不松动任何决策）：** 新增格落在**第二行**（该行当前只有经验条 + 两个入口图标，比第一行宽松），且它是本方案唯一的新增元素；若实测仍挤，退让顺序是 ①「距圆满 6 级」缩为「圆满 −6」② 再不够则把两个入口图标下沉一行——**绝不缩减寿元的四位数位宽**（恒精确是承重决策）。
   - **这条不需要用户裁决**，它是实测项；写在此处是为了让实测时知道退让顺序已定。
2. **与「不做『大限将至』一类的预警文案」的关系 —— 不冲突，但必须写明区别。** 那条否决的是**预警型文案**（在一个已精确显示的量之上再喊一嗓子）。本方案加的是**一个此前不存在的量的静态读数**，不是对已有量的提醒；且它无演出、无颜色告警、无触发时机（常驻）。**「已圆满 · 天劫将至」那一格同理**——它是状态名，不是预警。
3. **与「给方向不给数字」的关系 —— 不冲突。** 那条保护的是**隐藏的**经验档位映射（单个事件值多少经验）。本方案只读玩家早已看得见的 `level` 与经验条，**一格都不碰事件侧的标价**。

## 前置依赖
