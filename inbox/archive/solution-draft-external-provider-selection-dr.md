# 方案草稿 —— 外接原子能力的选型判据 · 灾备与切换 · 昵称频次阈值 · 微信资质时序

## 问题

`contracts/auth.md` 与 `systems/account.md` 已定「C 层原子能力一律外接、每类能力在后端内部有一个稳定接口使服务商可换」，并定死「服务商错误码不上契约面」。但**接口长什么样、归一映射怎么写、接几家、什么时候切、切的时候会不会重复计费**全部悬着；同分片另挂三项：昵称改名频次阈值（`auth.md` §8 唯一未定值的旋钮）、第三方昵称审核的服务商与评分阈值、以及**微信开放平台资质**——它绑在一个不可逆时刻上（首个玩家建号）。

本草稿**不点名任何一家服务商**：那是商业决定（价格、合同、资质、既有关系），不是可推演项。可推演的是它周围的全部形态。

## 建议方案

### 1. 四类能力的稳定内部接口（形态，不是实现）

`[既有推演]` 契约已定「每类能力有一个稳定接口使服务商可换」；下面把这句话落成可验收的形状。四个接口**共用同一套出参判别式**——`Outcome` 三档（`Accepted` / 明确拒绝 / `Unavailable`）正是 C3 那条纪律在类型层面的兑现，合并即当场违规。

**共有形状（四个接口逐条满足）：**

| # | 要求 | 理由 |
|---|---|---|
| A1 | 出参含 `Outcome` 判别式，且**「明确拒绝」与「不可达」是两个不同取值**，永不合并 | C3；合并 = `Fatal` 与 `Retryable` 在源头就分不开 |
| A2 | 出参含可选 `providerCode`（原始码）+ `providerTraceId`，**只随日志上报，永不进报文、永不参与分支** | C2；与 `auth.md` §3a 对 `channelCode` 的处理逐字同构 |
| A3 | 入参含 `requestId`（透传 `X-Request-Id`） | `observability.md`「三者贯通」——服务商侧排障要能由玩家上报的 `requestId` 反查 |
| A4 | **每次外部调用有硬超时**，超时归 `Unavailable`；适配层内**不做应用层重试**（唯一例外见 §3 的跨供应商 fail-over 那一次） | 应用层重试在下游劣化时放大流量，把一次抖动变成一次雪崩 |
| A5 | 个人信息**只作入参穿过适配层**，不落适配层自己的日志与缓存 | C10 |
| A6 | 适配层**不认识 `code`**：它只产出 `Outcome`，归一到 `code` 发生在调用方（端点）——否则每换一家服务商都要重读一遍契约的错误码台账 | 单一归一点 |

**四个接口的入出参：**

```
// ① 短信 / 邮件下发（同一接口，channel 分形；Email 首版无调用面，见 §2）
SendChallenge(channel, identifier, code, purpose, ttl, requestId)
  → { outcome: Accepted | Rejected | Unavailable,
      providerMessageId?, providerCode?, retryAfter? }
  硬超时初值 3s

// ② 实名核验
VerifyRealName(accountId, realName, idNumber, docKind, requestId)
  → { outcome: Verified | Mismatch | Malformed | Pending | Unavailable,
      birthDateUtc?（仅 Verified）, providerCode?, providerTraceId? }
  硬超时初值 5s

// ③ 第三方昵称审核（首版留位、透传恒放行，C5）
ModerateNickname(normalizedText, originalText, requestId)
  → { outcome: Reject | Review | Pass | Unavailable,
      score?, labelKeys[], providerCode? }
  硬超时初值 800ms

// ④ 第三方渠道换 openid —— 义务与错误映射已在 contracts/auth.md §3a 定死，
//    本草稿不复述，只登记它与上述三者同属适配层、同守 A1–A6。
```

- **`birthDateUtc` 只在 `Verified` 时返回、且只用于算 `isMinor`**——`compliance.md` §7 已定「不单独存年龄」、§10 定「出生日期本身永不下发」。
- **`ModerateNickname` 传归一化串与原串两个入参**：词表匹配用归一化串是既定纪律（`auth.md` §8），但多数外部审核服务自带归一化，把原串一并给它使其能用自己的模型；本方不因此放松自己的归一化。
- **`ModerateNickname` 的 800ms 硬超时是玩家等待预算**：它在 `POST /v1/auth/nickname` 的同步路径上，超时即按 C4 落第⑤级接受，玩家侧无可见失败。

### 2. 归一映射表（这是本草稿最可写全的一块）

`[既有推演]` 目标集合逐条取自 `envelope.md` §6 台账，不新增任何 `code`。

**① 短信下发（`POST /v1/auth/challenge` 调用点）**

| 服务商侧情形 | `Outcome` | 归一 `code` | `class` |
|---|---|---|---|
| 号码非法 / 空号 / 明确黑名单 / 模板不匹配被拒 | `Rejected` | `auth.credential_invalid` | `Fatal` |
| 服务商限流 / 单号码频控 / 账户余额或额度耗尽 | `Unavailable` | `rate.limited`（带 `Retry-After` + `detail.retryAfterSeconds`） | `Retryable` |
| 超时 / 5xx / 连接失败 / 服务商状态页故障 | `Unavailable` | `server.unavailable` | `Retryable` |

- **`auth.challenge_expired` 永不来自服务商。** 验证码由本方生成、本方存储、本方判超时；服务商只负责把一串字符送出去。这一条必须写明——`06` 分片把它列进归一目标集合，会让实现者去找一个服务商侧根本不存在的对应物。
- **余额 / 额度耗尽归 `rate.limited` 而非 `server.unavailable`**：客户端处置需要 `Retry-After`（`envelope.md` §6 台账已把 `detail` 形状写死），而 `server.unavailable` 没有这个字段。语义上它确实是「此刻不给你发」，不是「我方组件坏了」。
- **余额耗尽同时是一条运维告警，不只是一个错误码**：见 §5。

**② 实名核验（`POST /v1/compliance/realname` 调用点）**

| 服务商侧情形 | `Outcome` | 归一 `code` |
|---|---|---|
| 姓名 / 证件号不匹配 | `Mismatch` | `compliance.verification_failed` + `reasonKey: "Mismatch"` |
| 证件号格式非法（**本方先判，不调外部**） | `Malformed`（本地） | `compliance.verification_failed` + `reasonKey: "Malformed"` |
| 核验异步未回 | `Pending` | `200` + `realnameStatus: "Pending"`（**不是错误**） |
| 不可达 / 超时 / 限流 / 额度耗尽 | `Unavailable` | `server.unavailable` |

> **`06` 分片的归一目标集合措辞需要订正。** 分片列的四个 `code` 是 **auth 域**的目标集合；实名核验的「明确拒绝」归 `compliance.verification_failed`（`compliance.md` §11 已定，且它明写「必须与核验服务不可达在报文层面可区分」）。照分片字面把核验拒绝归进 `auth.credential_invalid` 会破坏该条既定纪律。建议提炼时顺手订正分片措辞为「归一到**本库已有的** `code`（按调用点所在域取）」。

**③ 第三方昵称审核（`POST /v1/auth/nickname` 判定链第④级）**

**本能力的归一目标不是 `code`，而是判定链的档位**——这是它与前两者的结构性差异，必须写明：

| `Outcome` | 落点 | 来源 |
|---|---|---|
| `Reject`（评分 ≥ 拒绝阈值） | `auth.nickname_rejected` + `reasonKey: "SensitiveWord"` | C4 |
| `Review`（评分落在两阈值之间） | 第⑤级接受（`204`）+ 入复核队列 | C4 |
| `Pass` | 第⑤级接受（`204`） | C4 |
| `Unavailable` | 第⑤级接受（`204`）+ 入复核队列，**不返回任何错误** | C4、`systems/account.md` N9 |

- **两个阈值，不是一个**：`rejectThreshold`（判拒绝）与 `reviewThreshold`（入复核）。单阈值表达不了 C4 要求的三档落点。
- **阈值的维度是「服务商 × 环境」，不是一个全局数。** `[通行做法]` 不同审核服务的评分刻度互不可比（有的 0–1、有的 0–100、有的分类标签 + 置信度），把它写成一个全局单值，换一家服务商当天判定口径就会静默漂移。
- **具体取值待启用时以真实样本标定**，方式是拿一批人工已判定的昵称跑一遍、取使漏放（判 Pass 实为违规）最小且误拒可接受的一对阈值。**首版不启用 ⇒ 首版不定值**（C5）。

### 3. 多供应商灾备与切换

`[既有推演] + [通行做法]` 逐能力给形态。**判据是「这个能力停摆，玩家会怎样」**，而不是一刀切上双供。

| 能力 | 首版供应商数 | 停摆的玩家后果 | 结论 |
|---|---|---|---|
| **短信** | **2（主 + 备，首版即接）** | `Phone` 渠道玩家**全体无法登录**——且他们无法改走 `WeChat`（那会建出第二个账号，`auth.md` §1a 明禁隐式合并） | 唯一「外部停摆 = 一半玩家完全进不来」的能力，必须双供 |
| **邮件** | **0（首版不选型，只留接口位）** | 零调用面：`Email` 渠道首版返回 `auth.channel_rejected`（C7） | 为一条不存在的路径选型、报备模板、养一份凭据，是纯负债 |
| **实名核验** | **1（+ 一家完成合规评估但不接入）** | 新账号卡在实名前；契约已有 `Pending` 态与 `server.unavailable`（`Retryable`），玩家稍后重试即可 | 按次计费、一生一次、有既定的可重试语义 ⇒ 双供的收益不抵接入与合规成本 |
| **第三方昵称审核** | **0（首版不启用）** | 判定链第④级透传恒放行，玩家零感知 | C5 |

**切换触发判据（只对短信）：**

```
滑动 5 分钟窗口内：Outcome = Unavailable 占比 > 20% 且样本 ≥ 20 次
                 或 连续 10 次 Unavailable
  → 自动降级到备用供应商，同时发一条 P1 告警
回切：备用运行 ≥ 30 分钟 且 主供在旁路探测上连续 10 分钟成功率 ≥ 95%
  → 自动回切（带滞后），回切也发告警
```

- **`Rejected` 不计入触发判据。** 它是号码本身的问题，与供应商健康无关；把它计进去，一批脏号码就能触发一次假降级。
- **降级自动、回切带滞后。** `[通行做法]` 无滞后的自动回切会在主供半死不活时来回抖动，而每次抖动都在真实地少发一批验证码。
- **备用供应商必须持续保持「可用」而非「可接入」**：至少一条低频合成探测（旁路，不占玩家路径），否则降级当天才发现备用家的模板报备过期了。

**重复计费与重复送达的风险处置（承重）：**

- **禁止并发双发**（同一码同时发两家）。双倍计费，且玩家收到两条一模一样的短信，可用性收益仅在「主供受理后静默不送达」这一小类失败上，不值。
- **允许「同码转备用」一次，且只在首家未返回受理 id 时。** 关键性质：**验证码由本方生成**，因此重发同一个码是幂等的——两条短信里是同一个码，玩家用哪条都对，唯一代价是可能多一条计费。若首家已返回 `providerMessageId`（已受理），**不转备用**：那时更可能是送达慢而非失败。
- **一次 `challenge` 请求至多产生两次外部调用**（首家 + 转备用一次），此外一律返回 `server.unavailable` 交由客户端退避重试。这与 A4「适配层内不做应用层重试」不冲突——转备用是**换目标**，不是重试同一目标。
- **`resendAfterSeconds` 与验证码 TTL 由本方决定，与供应商无关**（`auth.md` §8 的两个旋钮），切换不改变契约面的任何一个字段。

**验证码日上限的计数口径（顺带落笔项，答案由推演唯一确定）：**

`[既有推演]` **「单标识符验证码日上限 10 次」只计成功受理的一次下发。** 与 C6「频次只计被接受的一次改名」逐字同构，理由同源：把失败也计进去，一次主供故障就能把玩家锁死在自己的日配额上，而他一条短信都没收到。这一句建议补进 `auth.md` §8 该旋钮行。

**禁止双验（实名核验）：** 两家同时验一次，双倍计费，且两家结论不一致时**没有任何仲裁规则**——而这是一个直接决定「这个人是不是未成年」的判定。

### 4. 选型判据清单（给的是判据，不是家名）

`[通行做法] + [既有推演]` 逐条可核对，接入前逐项签核；不满足 H 类即出局。

| # | 类 | 判据 | 不满足的后果 |
|---|---|---|---|
| H1 | 硬 | **数据处理节点全部在中国大陆境内**，含任何边缘 / 加速 / 灾备节点 | 直接违反 C1（个人信息不出境） |
| H2 | 硬 | **资质齐备**：短信需增值电信业务经营许可与签名 / 模板报备通道；实名核验需持牌数据源（权威库或运营商要素核验） | 无资质的通道会在过审或抽查时整条中断 |
| H3 | 硬 | **提供沙箱 / 测试通道**，使 `backend-testing` 环境不真实发短信、不真实计费、不真实核验 | 与 `purchase-ops.md` §1「测试环境用沙箱凭据」同构；缺它则每次集成验证都在真花钱、真发短信 |
| H4 | 硬 | 凭据可**无停机轮换**，且支持新旧并存窗口 | 轮换当天该能力整体中断 |
| S1 | 软 | 与主区**同区或内网可达**，公网出口有确定的 IP / 域名（便于出网白名单） | 时延与网络故障面 |
| S2 | 软 | 有可查的 **SLA 与状态页**，且回执 / 送达率可按条查询 | 缺回执则「服务商受理了但没送达」永远归因不了 |
| S3 | 软 | **计费模型清晰**：按条 / 按次；预付余额有**可编程的余额查询接口** | 无余额查询 ⇒ §5 的低水位告警做不了，只能等发不出去才知道 |
| S4 | 软 | 支持按业务维度拆分子账户 / 子签名，使 `testing` 与 `production` 用量可分账 | 分账不清则成本模型（`06` 另一条）拿不到干净输入 |

**凭据托管：形态复用 `purchase-ops.md` §1，条目粒度 = 能力 × 供应商 × 环境。**

- 载体同为云 Secrets 条目（底层 KMS 加密），沿用「只在内存、不落盘、不进环境变量、不进镜像」与「运行角色只读、写入只经部署角色」。
- **不与三把钥匙（内容签名 / 会话 token / 渠道验票）共用条目或轮换流程**——`environments.md` 已把「三把钥匙不共用托管配置」立为纪律，本类是**第四类凭据、第四条审计线**，理由同源：轮换节奏由各自的外部方驱动。
- 新旧并存沿用 `credentials[]` 数组 + 供应商侧标识的形态，轮换 = 追加新项 → 确认 → 删旧项。

### 5. 可观测性与告警（挂既有面，不新建通道）

`[既有推演]` `observability.md` 已有「RED 三件套 + 按 `code` 的错误分布」与既有告警面，本节只补外接能力特有的维度。

| 指标 | 标签（低基数） | 告警口径 |
|---|---|---|
| 外部调用结果分布 | `capability` · `provider` · `outcome` | `Unavailable` 占比触及 §3 的降级判据即 P1 |
| 外部调用时延 p50/p95/p99 | `capability` · `provider` | 相对基线劣化 |
| **供应商余额 / 剩余额度** | `capability` · `provider` | **低水位两档**：可用量 < 7 天用量 ⇒ 提醒；< 1 天用量 ⇒ P1。余额耗尽是**可预警**的事故，等它变成 `rate.limited` 才发现是纯粹的运维失职 |
| 降级 / 回切事件 | `capability` · `provider` | 任一次即告警（两个方向都告） |
| 备用供应商合成探测 | `capability` · `provider` | 连续失败即告警——它是「降级当天才发现备用家也不能用」的唯一防线 |

**`providerCode` 的分布也上看板**：它是唯一能发现「服务商悄悄改了错误码语义、我方归一映射从此错位」的面，与「新增未登记 `code` 会在按 `code` 的分布里显形」同一手法。

### 6. 昵称改名频次阈值 `TooFrequent`

`[既有推演]` 按平衡数值的规矩给「初值 + 推导 + 可调位置 + 待实测校准」。

| 旋钮 | 初值 | 推导 |
|---|---|---|
| 改名频次上限 | **3 次 / 30 天滚动窗口** | 昵称在本作**没有任何玩家间可见性**（`auth.md` §8 已论证），改名是低频动作；3 次覆盖「首次设定 + 两次反悔」这一完整的正常用法。窗口取 30 天，与 `pushId` 保留时长 / refresh 滑动 TTL / 存量扫描 T3 周期同量级——本库已有的「使几处窗口不互相穿帮」的惯例（`moderation.md` T3 行）。滚动窗口而非自然月：自然月边界会让月末改两次、月初再改三次成为一条免费的刷子路径 |

- **落 `config_knob` 表**（C12），并补进 `environments.md`「旋钮清单」——该表已留了一行「昵称改名频次阈值尚未定值，定值后落本表」。**待实测校准。**
- **计数口径已定，不重开**：只对被接受的一次改名 `+1`（C6）。

**⚠ 一条必须同批处理的自锁：`nicknameChangeRequired` 为真时须豁免频次闸。**

`moderation.md` 的处置阶梯里，「须改名」档的解除路径是**玩家走一次改名流程**。若该玩家此前刚好用尽了改名配额，他会撞上 `TooFrequent` 而**无法解除自己的处置状态**——处置阶梯与频次闸互相锁死，且没有任何自解通道。

`[既有推演]` 建议：**`nicknameChangeRequired == true` 时跳过判定链第②级**（频次），其余四级照走。理由：频次闸防的是刷子，而处于「须改名」档的玩家是**被我方要求**改名的；此时限制他改名是我方自己制造的死锁。该次改名照常 `+1` 计数（不豁免计数，只豁免拦截），使解除后立刻再刷仍会被挡住。

> 这是一条**答案由推演唯一确定**的补丁，但它改的是 `auth.md` §8 的判定链与 `moderation.md` 的处置阶梯，**本技能不改主题文档** —— 已列入 front matter 的 `targets`，请在提炼时一并落笔。

### 7. 微信开放平台资质：时序、前置与延误退路

`[既有推演] + [通行做法]`

**为什么它比清单上另外三项更险。** 前置清单的另外三项（透明路径命名、`Source` 枚举冻结、`accountId` 形态）**全部在我方掌控内**——想定就能定。本项的完成时刻**由外部审批决定**，我方只能等。因此它是清单上唯一一项**可能因为外部原因而未能在闸门前完成**的，而闸门本身不可协商（过了那一刻，identity 已按 per-app 标识落地）。

**前置链（逐环都是外部审批，串行、以周计）：**

```
企业主体资质 → 软件著作权 → ICP 备案 / 域名备案（与 environments.md 同批推进）
  → 微信开放平台账号 + 企业开发者认证（年审制）
    → 创建「移动应用」并提交审核（需包名 / 签名指纹 / 应用材料）
      → 应用审核通过并绑定到该开放平台账号
        → 此后渠道登录才会同时返回 unionid
```

- **`unionid` 的产生条件是「该应用已绑定到一个开放平台账号」，与应用数量无关。** 首版只有一个 App 时同样能取到 `unionid`——这正是「首版即以 `unionid` 建 identity」这条决定成立的前提，也是提前申请的全部价值所在：**不是为了今天有两个应用，是为了明天有第二个应用时不必迁移。**
- **过闸断言必须是可验证的运行时事实，不是「已提交申请」。** 建议把 `deployment.md` 前置清单第 4 项的验收改写为：*在 `backend-testing` 环境完成一次真实的微信登录，服务端取到非空 `unionid`，且该 identity 的 `idKind` 落为 `unionid`。* 一份「审核通过」的截图不能证明我方代码走的是 `unionid` 那条分支——而这个分支恰恰是不可逆的那一个。
- **与支付侧解耦**：`deployment.md` 已写明「支付侧渠道排期不影响本条」，本草稿不改。微信支付商户资质是另一条链、另一个闸（`purchase-ops.md`），两者不互为前置。

**延误时的退路——这是一个真取向，见 `## 仍需用户决定`。**

## 备选方案（已考虑并否决）

- **首版只接一家短信供应商，靠人工快速切换** — 「人工切换」在无人值守时段等于停摆数小时，而后果是 `Phone` 渠道玩家全体无法登录且**无替代登录路径**（改走 WeChat 会建出第二个账号）。这是全部外接能力里唯一具备这种后果的一条。
- **并发双发同一验证码到两家** — 双倍计费、玩家收两条同内容短信；可用性增益只覆盖「已受理但静默不送达」这一小类，而顺序转备用已覆盖其余全部。
- **两家实名核验并行核验、取一致结论** — 双倍计费（按次），且不一致时无仲裁规则；而这是决定「是否未成年」的判定，一个没有仲裁规则的双源是比单源更坏的形态。
- **为「服务商不可达」新增一条 `code`** — 直接违反 C2；`server.unavailable` 逐字覆盖，且客户端已有 `Retryable` 处置。
- **把服务商原始码放进 `detail` 供客户端分支** — `auth.md` §3a 已为 `channelCode` 定死「客户端不解析、只随日志上报」，理由（服务商版本更新时分支静默失效）在此完全同源。
- **首版即为 `Email` 选型并接入** — 该渠道首版返回 `auth.channel_rejected`，零调用面；接入即产生一份要轮换的凭据、一次模板报备与一条要监控的曲线，全是负债。
- **第三方昵称审核首版即启用，以求更严的过审** — 与 `moderation.md` C5「首版不启用、只留位」直接相反，且它从属于仍未答的「合规能力上线分级」（见 `## 前置依赖`）。
- **昵称审核用单一评分阈值** — 表达不了判定链要求的三档落点（拒绝 / 待复核 / 放行）。
- **昵称审核阈值取全局单值** — 不同服务商评分刻度不可比，换家即静默漂移。
- **改名频次上限按自然月计** — 月末月初连改是一条免费的刷子路径。
- **`nicknameChangeRequired` 时不豁免频次闸**（保持规则统一） — 处置阶梯与频次闸互锁，被我方要求改名的玩家无法解除自己的处置状态，且无自解通道。
- **豁免时连计数一起豁免** — 解除后可立刻继续刷，闸门在该账号上等于消失。
- **验证码日上限把失败的下发也计进去** — 一次主供故障即把玩家锁死在日配额上，而他一条短信都没收到。
- **把「已提交微信开放平台申请」作为发布前置清单第 4 项的过闸条件** — 证明不了我方代码实际走的是 `unionid` 分支，而那正是不可逆的那一条。
- **外接能力凭据并入三把钥匙中任意一把的托管配置** — `environments.md` 已立「不共用托管配置」的纪律，理由（最慢的轮换节奏绑架其余）在此同源。
- **适配层内对外部调用做多次重试** — 下游劣化时放大流量；跨供应商 fail-over 是换目标而非重试，不在此列。

## 与既有决策的张力

**一条，且只在延误情形下才成立。**

`contracts/auth.md` §3a 把「首版即以 `unionid` 建 identity」写为**不可逆**决定，`deployment.md` 把它列为首个玩家建号前的硬闸。本草稿 `## 仍需用户决定` 中的**退路 C（双列 + 回填）**若被采纳，会把这句「不可逆」削弱为「一次可增量回填」——因为 `identity` 上已有的 `idKind` 字段恰好承载了「这条 identity 当初以哪种标识建立」这一事实，而渠道在应用绑定开放平台后会**同时**返回 `openid` 与 `unionid`，使回填在技术上可行。

- **松动的代价：** ① 回填期间 `(channel, channelUserId)` 唯一约束要允许一次键迁移，且要处理「同一人的两条 identity（旧 openid 建 + 新 unionid 建）」的合并——而 `auth.md` §1a 的承重纪律是**绝不做隐式账号合并**，一次合并必然要丢弃其中一份存档。② 「不可逆」这句话本身是清单第 4 项的全部强制力来源，削弱它就削弱了闸门。
- **不松动时的替代方案：** 退路 A（推迟上线直到资质到位）。它保住全部既有决策，代价是上线时程受外部审批牵制。
- **本草稿的立场：** 主路径仍是「资质先行、不改任何既有决策」。退路 C 只在资质确实延误、且用户明确接受上述代价时启用，**它不是放宽前置清单的理由**。裁决权在用户。

### ① 微信开放平台资质若在计划上线日之前未到位，走哪条退路？

**→ 已裁决（2026-09-06 · 批量评审）：取退路 A —— 推迟上线，直到资质到位。** 既有决策原样成立、零技术债；`unionid` 的不可逆性不让步（B 与 C 的代价都随存量账号数增长，C 更会把 `auth.md` §1a「绝不做隐式账号合并」这条保护玩家存档的承重禁令推上台面）。
**附带一并采纳**：把微信资质链的启动时点前移到与域名备案同批推进（`operations/environments.md` 已把二者列为同批），使它不成为上线路径上最后暴露的那一环。
⇒ 本草稿 `## 与既有决策的张力` 中那条**只在选 C 时才成立**的张力（削弱 §3a 的不可逆性）**因此不成立**，提炼时不必处理。

**→ 同批采纳（推演唯一确定，未出题）**：① `nicknameChangeRequired == true` 时豁免判定链第②级频次闸的**拦截**、不豁免**计数**；② 「单标识符验证码日上限 10 次」只计**成功受理**的一次下发。

**背景：** 首个玩家建号那一刻起，identity 以哪种标识建立就固定了。资质链条全是外部审批（企业认证 → 移动应用审核 → 绑定），我方无法压缩。这一题问的是**「审批没赶上」时怎么办**，不是要不要申请（申请是既定的）。

| 选项 | 做法 | 后果 |
|---|---|---|
| **A. 推迟上线**（推荐） | 资质未过闸即不放真实账号进来 | 全部既有决策原样成立，零技术债。代价：上线时程被外部审批牵制，且延误天数不可控 |
| **B. 以 `openid` 建号，接受日后全量迁移** | 照常上线，`idKind = openid` | 上线不受阻。代价：新增第二个应用时需要一次**全量身份迁移**——正是 `auth.md` §3a 明确要避免的那件事，且届时存量账号越多代价越大 |
| **C. 双列 + 增量回填** | 以 `openid` 建号，但 identity 结构上预留 `unionid`；资质到位后，玩家下次登录时渠道同时返回二者 ⇒ 就地回填并把键切到 `unionid` | 上线不受阻，且迁移是增量的、随玩家自然登录完成。代价：削弱「不可逆」这句话（见 `## 与既有决策的张力`）；且**回填必然撞上「同一人两条 identity」的合并**，而隐式合并是 `auth.md` §1a 的承重禁令 |

**推荐 A。** 三条依据：① 本项与其余三项前置清单不同，它一旦做错**没有任何低成本的事后补救**——B 与 C 的代价都随存量账号数增长；② C 看似最优，但它把一个身份模型的承重禁令（绝不隐式合并）推到了台面上，而那条禁令保护的是**玩家的存档**，不是一条工程偏好；③ 时程压力是可以协商的，`unionid` 的不可逆性不能。

> **若用户选 A**，建议同时把「微信资质链条启动」的时点前移到与域名备案同批（`environments.md` 已把二者列为同批推进），使它不成为上线路径上最后暴露的那一环。
