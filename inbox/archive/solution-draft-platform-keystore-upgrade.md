# 方案草稿 — 平台密钥库的后置评估：触发条件与四端能力差异

## 问题

「refresh token 首版明文落 `user://cache/refresh-token.json`」已于 08-23 复核定案（`answer-logs/log-0823.md` · `decisions/ADR-0080-refresh-token-client-custody.md`），并把「平台密钥库是**后置评估项而非否决项**」写进了 `systems/services/account-service.md:84`。但**「后置」两个字没有兑现物**：

1. **何时该升级？** 文档只说「后置评估」，没有任何可判定的触发条件。这类留口的失败模式是已知的——它不会在某天被想起来，而会在某次「顺便看看还有什么没做」时被再次记为「后置」。
2. **四端行为差异如何处置？** Android / iOS 有平台机制，桌面有 OS 级凭据库但威胁模型不同，**Web 没有等价机制**。若升级会导致「三端走密钥库、Web 走明文」，那就是一处**平台分支**——而 `ui-input-rules.md` 的既有纪律是「不按平台分叉输入逻辑；仅在某项能力确有本质差异处分支」。这里是否属于「确有本质差异」，需要一个结论。

本问题**不重开「首版是否明文」**——那一条已定案，本草稿在它之上。

## 约束（来自既有设计）

- **明文首版的依据是「沙箱 + 后端 rotation + 窗口外重放即吊销全部会话」三件套**，不挂靠「不承诺防作弊」的威胁模型（`systems/services/account-service.md:84`；`decisions/ADR-0080`）。⇒ **这三件套中任何一条被削弱，明文的依据当场失效**——这是第一条触发条件的来源。
- **已登记的残余风险恰好三条**：root / 越狱设备 · 系统备份提取 · 共享设备上的他人访问（同上）。⇒ 升级的收益只能按「它消掉了这三条中的哪几条」来度量，不能按感觉。
- **凭据的落盘点已经收敛为唯一一处**：文件 I/O 落在 `AuthManager` 内、不沉进 `HttpAccountBackend`，且**不提供 `TryGetRefreshToken()` 这类公开取值方法**（`account-service.md:108`）。⇒ 替换存储实现的成本**已经是最低的**，不需要现在预留任何抽象。
- **落盘失败 = 可降级**：`PushWarning` + 本次进程内存持有、不阻塞登录；症状一次性、可自愈（`account-service.md:102`、`:105`）。⇒ 任何新存储后端的失败语义必须能落回这同一格，否则就是把一条可降级路径升级成「登不上游戏」。
- **带 `schemaVersion`，「版本不认识就整份丢弃」在本文件上是安全的**（丢弃 = 玩家多登录一次，`account-service.md:83`）。⇒ 升级即使把老档全丢，代价上界也只是一次重登，**不需要复杂迁移**。
- **平台优先级已定**：Android / iOS 首要，桌面 / 网页次要（`vision/scope.md:29-30`）。**没有游客登录**（同上 `:31`），故每个端都必须持有凭据。
- **API 面零改动是既有承诺**（`account-service.md:134`）：现有六条失效路径 + 三条读写失败处置由 `RefreshTokenAsync` / `SignInAsync` / `SignOutAsync` 原样承载。任何升级方案不得改动服务 API 面。
- **条件编译清单穷举 5 处、不得扩张**（`systems/architecture.md:645`）。⇒ 密钥库实现**不得**靠 `#if ANDROID` / `#if IOS` 之类落地——那是清单外的第 6 / 7 处。
- **`.claude/rules/environment-rules.md`**：本机无法验证任何平台 SDK 行为；`game-feature-branch/` **尚无 `.csproj`**（`open-questions/05-service-contracts.md:27`）。⇒ 下方能力矩阵中凡涉及 Godot 侧绑定与具体 API 行为的格子，一律标注实测口径，**不作为已确认事实落笔**。

## 建议方案

### 1. 四端能力矩阵（本草稿的第一件交付物）

`[通行做法]` + `[待核实]` 混合。**凡未在本库或本机验证过的格子逐格标注**，不得据此写进主题文档而不复验。

| | **Android** | **iOS** | **桌面（Win / macOS / Linux）** | **Web** |
|---|---|---|---|---|
| **是否存在 OS 级密钥 / 凭据机制** | 有 —— Android Keystore（系统持有密钥、应用不接触密钥材料） | 有 —— Keychain Services（`kSecClassGenericPassword`） | 有，但**三套互不相同**：Windows DPAPI / 凭据管理器 · macOS Keychain · Linux Secret Service（**不保证存在**，取决于桌面环境） | **无等价机制** |
| **Godot 4.7 是否内置绑定** | **否**（需自建 Android 插件，Java/Kotlin 侧） `[待核实：Godot 4.7 是否新增了任何内置安全存储 API——本机无 Godot CLI，须在编辑器侧确认]` | **否**（需自建 iOS 插件，Obj-C/Swift 侧） `[同上待核实]` | **否**（需 GDExtension，且三套 OS 各写一份） | 不适用 |
| **`user://` 的实际落点** | 应用私有目录（沙箱内） | 应用沙箱内 | **用户可读写的普通目录**——同用户下任意进程可直接读取 | 浏览器持久化存储（Godot Web 导出经 Emscripten 把 `user://` 落到浏览器端存储） `[待核实：Godot 4.7 web 导出的具体后端与持久化保证]` |
| **消掉哪几条已登记残余风险** | 备份提取 ✅（密钥不随备份迁移）· 共享设备 ⚠ 部分（取决于是否挂生物识别 / 锁屏门）· **root ❌**（root 下密钥库的保护取决于是否硬件后备，且应用自身可被注入） | 备份提取 ✅（须显式选 `ThisDeviceOnly` 类可访问性，否则会随 iCloud Keychain / 备份走）· 共享设备 ⚠ 部分 · **越狱 ❌** | **一条也消不掉** —— 桌面威胁模型下，能读取 OS 凭据库的正是「以该用户身份运行的进程」，与能读 `user://` 的是同一批 | **一条也消不掉** —— 同源的任意脚本可读，且不存在「OS 拒绝应用读取」这一层 |
| **各自的失效场景（升级后新增的坏路径）** | 锁屏 / 生物识别凭据变更可使密钥永久失效；换机恢复后旧条目不可解密 `[待核实：具体异常与触发面]` | **Keychain 条目在应用卸载后仍存活** —— 重装即读到一份旧 token（后端已吊销 ⇒ 走 `auth.session_revoked` → 登录屏，可自愈，但**必须明写**，否则读者会以为「重装 = 干净态」） | 三套 OS 各自的可用性问题；Linux 上服务可能根本不存在 → 必须有明文回退 | 浏览器在存储压力 / 用户清理下可整体清空 → 表现为一次强制重登（已是既定可自愈路径，`account-service.md:100`） |
| **升级的边际成本** | 一个自建插件工程 + 导出配置 | 一个自建插件工程 + 导出配置 + 上架复验 | 三份 GDExtension，**收益为零**（见上一行） | 不适用 |

**矩阵读出的两条结论：**

- **收益集中在移动双端，且只覆盖三条残余风险中的「备份提取」一条半。** root / 越狱这条——恰恰是三条里唯一被主动攻击者利用的一条——**密钥库消不掉**。这使「升级」的定性从「补上安全短板」降为「关掉备份提取这一条被动泄漏面」。
- **桌面与 Web 的升级收益是零，不是「小」。** 桌面是威胁模型使然（同用户进程本就等价），Web 是机制缺失。这决定了下方第 3 条的平台分支结论。

| # | 触发事件（可机械判定） | 落在哪条轴 | 为什么它是分界线 |
|---|---|---|---|

### 3. 是否引入平台分支：结论 = **不引入**

`[既有推演]`。**升级时不出现平台分支**，理由三条：

1. **能力差异不落在 API 面上，落在一处实现内。** 凭据落盘点已经收敛为 `AuthManager` 私有的一处（`account-service.md:108`），且**没有公开取值方法**。升级 = 换掉这一处的读写实现，**服务 API 面、`Session`、六条失效路径、三条读写失败处置一格不动**（`account-service.md:134` 的既有承诺照旧成立）。
2. **Web / 桌面不是「降级分支」，而是同一个默认实现。** 明文实现**不被移除**，它是四端共同的缺省；Android / iOS 在**插件可用时**替换。判据不是「我在哪个平台」而是「**这一端有没有可用的凭据存储实现**」——运行期一次探测，探测不到即用缺省。这与 `BackendSelector` 的「唯一选择点 + 换实现而非插 `if`」（`architecture.md:257`）是同一条纪律的第二次应用，不是新机制。
3. **它因此也不碰条件编译清单。** 平台实现的存在与否是**构建产物**层面的事（某端的导出里没有那个插件），不是 `#if` 分支；清单仍是 5 处（商业化落地后 6 处）。

**推论：`ui-input-rules.md` 的「仅在某项能力确有本质差异处分支」这一口子在这里用不上——因为根本没有分支。**

### 4. 现在**不**预留抽象（`ICredentialStore` 之类）

`[既有推演]`。当前落盘点只有一处、只有一个实现、且 API 面已隔离，此刻抽出一个接口只满足 `architecture.md:45` 三条反判据里的第 ②③ 条（只被调用一次且无变体 / 为了让结构看起来更完整）。**替换成本已经是最低的**，预留抽象换不来任何东西。触发条件命中、真要落第二个实现时再抽——那时它自动满足「≥ 2 个同形态的实现」这条判据。

### 5. 升级真发生时的落地形态（备好，但现在不落笔）

`[通行做法]`。写在这里是为了让触发条件命中时不必从零想，**不构成现在就做的建议**：

- **存的还是同一份 JSON 串**（`{ schemaVersion, accountId, refreshToken }`），只是载体从文件换成密钥库条目 ⇒ `schemaVersion` 与「版本不认识就整份丢弃」原样保留，**存档 schema 零影响**。
- **迁移 = 一次性搬迁，不写迁移代码路径以外的任何东西**：升级版本首次启动时，密钥库为空 且 明文文件存在 → 读明文 → 写密钥库 → 删明文。搬迁失败即删明文走登录屏（代价上界 = 一次重登，`account-service.md:83` 已论证该上界可接受）。
- **失败语义落回既有那一格**：密钥库不可用 / 写入失败 → `PushWarning` + 本次进程内存持有、不阻塞登录（`account-service.md:102`），**不新增阻塞点**（阻塞点穷举清单见 `sync-service.md`「三条不变式」①）。
- **iOS 侧必须显式选「不随备份 / 不随 iCloud 同步」的可访问性**，否则「消掉备份提取」这条唯一收益当场归零；且**必须明写「Keychain 条目在卸载后存活」**及其自愈路径。
- **原子写纪律不适用于密钥库条目**（它不是 `user://` 文件）⇒ `AtomicJsonFile` 的调用方名单相应少一处，`architecture.md:580` 那份「写入方分散在四处以上」的清单须同批复核。

## 备选方案（已考虑并否决）

- **现在就升级到平台密钥库。** 否决：三条残余风险只消掉一条半，root / 越狱这条消不掉；成本是两个自建插件工程；且 08-23 复核刚刚确认了首版明文取向，无新信息支持推翻。
- **在客户端自行加密后落明文文件（自选密钥 + 对称加密）。** 否决：密钥必须与密文同处一个可读位置，安全性提升为零，代价是一层假保障——比明文更糟，因为它会让人以为已经处理过了。此形态与本库「不制造第二权威 / 不留假承诺」的一贯取舍同向。
- **Web 端禁止持久化凭据（每次启动都重登）。** 否决：Web 是次要目标但仍是**同一套代码库**，为它单开一条登录流即制造平台分支，正是第 3 条要避免的；且它把一条可自愈的存储清空路径升级成常态摩擦。
- **给桌面端接 OS 凭据库。** 否决：桌面威胁模型下收益为零（能读凭据库的进程与能读 `user://` 的是同一批），成本是三份 GDExtension。
- **只写「日后评估」不定触发条件。** 否决：这正是本待答项存在的原因，重复一遍即等于不答。
- **现在预留 `ICredentialStore` 接口。** 否决：命中 `architecture.md:45` 的两条反判据；替换成本已经最低。

## 仍需用户决定 → **已全部裁决（2026-09-02 · 批量评审）**

1. **T3（首次引入原生插件时同批重估）是「必须给出结论」还是「必须升级」？**
   - **选项 A —— 必须给出结论（推荐）。** 插件工程存在后重新裁决一次，可以裁决为「仍不升级」。后果：保留了拒绝的余地，但也保留了「又一次后置」的可能——由「必须在当次同批裁决、不得再记为后置」这句话兜住。
   - **选项 B —— 必须升级（硬绑）。** 内购插件落地即同批做密钥库。后果：商业化那一批的工作量确定性增加（两个平台的插件方法 + 一次性搬迁 + 两端复验），换来「不会再拖」。
   - **推荐 A，理由：** 密钥库消掉的是三条残余风险中的**备份提取**一条半，而**内购本身并不放大凭据泄漏的后果**——bundle 是一次性权益，盗号者拿不到钱，兑现走后端验票（`architecture.md:647`）。硬绑会把一件收益未变的事塞进本就最重的一批里。若用户认为「上架付费产品时账号安全必须到位」是一条对外承诺而非收益计算，则选 B——**这一层是产品取向，不是工程判断，故留给用户**。
   - → **已裁决（2026-09-02 · 批量评审）：选项 A —— T3 写成「必须给出结论」。** 到那一刻强制重估并记下结论（可裁决为「仍不升级」），但不预先承诺一定升级；「必须在当次同批裁决、不得再记为后置」这句兜底照写。
