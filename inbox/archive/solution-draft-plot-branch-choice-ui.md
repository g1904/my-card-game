# 方案草稿 — DnD 式选分支的触发点与 UI

## 问题

剧本树的**数据挂点已定**（08-16i）：`PlotEdge.BranchLabel` 非空 = 对玩家可见的分支边、`PlotCondition.Kind == BranchChosen` 是它专用的推进条件、`PlotSegment.Branches : IReadOnlyList<PlotBranchOption>` 是产出载体、`ChooseBranch(branchId)` 的 `branchId` = 该边的 `ToNodeId`、`ChooseBranch` 经 `ProfileManager` 写入一条 `PlotKeyPointAssignment`。

**仍悬着的是呈现侧的三问：**

1. **何时**——在一次事件推进的哪个时刻把分支摆给玩家；
2. **哪一屏**——落在既有的哪一个呈现面上，还是新增一屏 / 一层；
3. **可见 / 不可见的边界**——哪些分岔应当明示给玩家，哪些应当由隐藏属性与自动边静默决定。

它卡住的下游：`ux/screen-flow.md` 里剧本层至今没有任何呈现面（剧本正文 `PlotNodeData.Body` 的落屏同样无明文）；剧本内容条目要写到可 blueprint，内容作者需要知道「写一个分支节点，玩家会在什么场合读到它」。

## 约束（来自既有设计）

| 约束 | 来源 |
|---|---|
| **玩家永远不会「进入一个剧本节点」**；剧本树纯调制、无并行结构、不产出事件、不持有事件序列 | `systems/services/plot-manager.md`「树 = 纯调制」（承重） |
| **调制才是隐藏属性与剧本的主要显影通道，旁白只是极值时刻的一次强调** | 同上「关键的解耦」 |
| **剧本推进时点 = 已有的 `eventEnd`，单步推进**；判定并入隐藏属性 band 写入的同一次 `TryApply`，不新增存档点、不新增结算阶段 | 同上「推进时点」 |
| **`ChooseBranch` 亦经 `ProfileManager` 写入，不另开写入口**；组装出的同样是一条 `PlotKeyPointAssignment` | 同上 |
| **同一节点不得混有 `BranchChosen` 边与自动边**（加载期 `PushError`）；同节点两条 `BranchChosen` 边 `ToNodeId` 不得相同 | 同上「出边与推进条件」 |
| **收口是一次事务、一个存档点**；`eventEnd` 五步组装顺序承重，中间态永不需要持久化，**取消点与存档点永远重合** | `systems/services/life-cycle-service.md` |
| **自动存档点是一份已穷举的清单**，不得凭直觉自造新落点 | `.claude/rules/state-save-rules.md` · `life-cycle-service.md` |
| **批次层的玩家主动操作 = 独立的即时提交**，三条连带纪律（不触发 `RefreshAfterEvent` · 照跑终态判定 · 不计软阻塞闸门） | `life-cycle-service.md`「批次层的储物袋操作」 |
| **跨档叙事播在事件结算面板内，一档一行，不是独立弹层**；不在最高频操作上加模态 | `ux/screen-flow.md` · `ux/combat-ux.md` |
| **本作是 deck building / turn-based card combat game，不是 visual novel**；叙事是点缀不是载体，存疑时取少 | `plot-manager.md`「体裁定位」（承重） |
| **不给数字**：文案正文含属性名 / 阿拉伯数字 / 档位序号 → `PushWarning` | `plot-manager.md` 加载期校验 |
| 竖屏优先 · 最小触控目标 · **无 hover-only 可供性** · UI 文案走 `res://text/` 翻译键 | `.claude/rules/ui-input-rules.md` · `ux/error-and-blocking-ux.md` |
| **内容 / 界面四问判据**：`BranchLabel`、`Body` 是内容层 `LocalizedText`，框架文案是翻译键 | `ux/_index.md` |

## 建议方案

### 1. 触发点 = 事件结算面板，落在 `eventEnd` 的那一次 `TryApply` **之后**

`[既有推演]`

分支必须摆在**收口提交之后**，这一条不是取舍而是被既有纪律逼出来的唯一位置：

- **不能落在 `eventEnd` 组装之内。** 五步组装里插一次玩家等待，等于在 ⑤ 提交之前引入一个可退出点 ⇒ 需要持久化中间态，与「中间态永不需要持久化」「取消点与存档点永远重合」两条正面冲突。
- **不能落在事件推进之外的独立时机**（例如每 N 个事件弹一次）：剧本推进的唯一时点是 `eventEnd`，另设时机就是给剧本层开第二个出口。
- **故落点唯一**：`eventEnd` 提交完成 → 该 arc 的 key point 已经停在分支节点上 → 结算面板呈现该节点的正文与分支 → 玩家点选 → `ChooseBranch` 一次 `TryApply` → 面板收起，回到 EventOption 选择界面。

**分支呈现在 arc 抵达该节点的同一次结算面板上，不延后一次收口。** key point 在这次收口里已经提交为分支节点，`TryResolvePlot` 当场就能产出非空 `Branches`；延后一次只会让分支正文与产生它的那个事件脱节。

### 2. 屏 = 既有的事件结算面板内追加一段「剧本段」，不新增屏、不新增弹层

`[既有推演]`

跨档叙事已经确立了先例：**一句由状态转换触发的定性文案播在事件结算面板内，不是独立弹层**（独立弹层 = 新结构 + 在最频繁的操作上多一次点击）。剧本分支是同一族的东西——由剧本推进触发、附在收口上、内容层文案——**没有理由为它选一个跨档叙事被明确否决过的形态**。

竖屏形态（结算面板底部追加一段）：

```
┌─ 事件结算面板 ─────────────────────┐
│  ...本次结算逐行（寿元 / 产出 / …） │
│  <斜体弱化色 · 跨档叙事行>          │  ← 既有，至多两行
├────────────────────────────────────┤
│  <PlotNodeData.Body 正文>           │  ← 内容层 LocalizedText，纵向滚动
│                                     │
│  ┌────────────────────────────────┐ │
│  │  <BranchLabel 1>               │ │  ← 全宽按钮，一条一行
│  ├────────────────────────────────┤ │
│  │  <BranchLabel 2>               │ │
│  └────────────────────────────────┘ │
└────────────────────────────────────┘
     ▲ 有分支时：分支按钮**取代**「继续」，离开面板的那一次点击就是选择本身
     ▲ 无分支时：面板与今天完全一致（有正文则呈现正文 + 「继续」）
```

- **零额外点击。** 玩家本来就要点一次「继续」离开结算面板；分支节点上那一次点击变成「选哪一条」。「不在最高频操作上加模态弹层」原样成立。
- **纵向堆叠全宽按钮**，每条一行、承载 `BranchLabel` 全文（不截断、不做省略号）；满足触控目标尺寸下限，落在拇指可达区、安全区内。**横滑区语汇不复用**——横滑是 eventOptions 与角色选择的语言，剧本分支复用会让两个层级的操作读成同一件事（与 Exchange 屏「不做横滑」同一条判据）。
- **无 hover-only 可供性**：正文与全部分支标签常驻可见；正文过长时面板内纵向滚动，按钮不随之移出视野。
- **不做二次确认。** 分支不损失任何资源、两条都是剧情而非「对与错」，与储物袋「使用」不做二段确认同判据（二段确认留给不可逆的资源损失：售出 / 兑换）。
- **无跳过、无默认选中、无超时自动选。** 该节点的出边全是 `BranchChosen`（加载期已禁止混边）⇒ 不选就没有出边可走，arc 会永远停在这里。**未选完退出游戏 = arc 停在该节点，下次收口的结算面板照常再呈现**（key point 已提交，恢复即读结果）。
- **文案分区**：面板框架文案走 `EVENT_` 分区（`event.csv`）；**`Body` 与 `BranchLabel` 一个字都不进 `res://text/`**——它们四问皆是，是内容层（`ux/_index.md`）。

### 3. 剧本正文（`PlotNodeData.Body`）与分支共用同一落点

`[既有推演]`

分支必然需要正文作语境（「答应还是拒绝」得先知道谁在问）。既然分支落在结算面板，正文只能同屏——否则一次选择要跨两个呈现面。**纯叙事节点（有 `Body` 无分支）照同一形态呈现，后面跟既有的「继续」**。这顺带填上了「剧本正文落哪一屏」这个至今无明文的空位，且不新增任何呈现面。

> 若评审认为纯叙事节点的落屏应单独裁决，可把本节收窄为「仅分支节点的正文落结算面板」，其余不变。

### 4. 一次收口至多呈现一条 arc 的分支

`[既有推演]`

同时 `Active` 的 arc 最多四条（Story + Chapter + `MaxConcurrentSideArcs` 2 条 side），理论上可能同一次收口有多条 arc 停在分支节点。

- **一次结算面板至多问一次**，其余 arc 停在各自节点，下次收口再呈现——与「一次 `eventEnd` 每条 arc 至多前进一个节点」「一次 `eventEnd` 至多出队一条」同款节制。
- **固定优先序**：`Tier` 序 `Story → Chapter → SideChapter → SideStory`，同 `Tier` 按 `ArcId` 字典序。**确定性是硬要求**（同一存档恢复后必须问同一条），字典序是零成本的确定性来源；取「主线优先」与跨档叙事「离终局最近的先说」同向。
- 与跨档叙事同屏时，**跨档叙事行在上、剧本段在下**：前者是刚发生的事的回响，后者是要玩家做的下一个动作。

### 5. 终态时不呈现分支

`[既有推演]`

终态判定 ①（支付 `selectCost` 后短路）与终态判定 ②（收口后判负 / 篇章通关）命中时，轮回已经结束——此时呈现一个没有下文的剧情抉择是纯噪音。**判负 / 通关 → 直接走轮回结束屏**（形态见配套草稿 `solution-draft-cycle-end-screen.md`），分支段整段不渲染，arc 停在原节点随角色数据一并拆解。

### 6. 可见 / 不可见的边界：结构判据 + 内容编排判据 + 一条禁令

#### 6a. 结构判据（可机械检查）

`[既有推演]`

既有形态已经把二分做完了一半：`BranchLabel` 非空 = 可见分支，`Condition.Kind == BranchChosen` 是它专用的推进条件。**把这两者焊成充要条件**，边界就不再依赖内容作者的自觉：

| 违规 | 处置 |
|---|---|
| `BranchLabel` 非空而 `Condition.Kind != BranchChosen` | `PushError` + arc `Id` + 节点 `Id` + `ToNodeId`（一条摆给玩家看却由后台条件推进的边——玩家点了不生效） |
| `Condition.Kind == BranchChosen` 而 `BranchLabel` 为空 | `PushError` + 同上（一条等玩家选、却没有标签可呈现的边 ⇒ 该 arc 死锁） |

两行与既有的「同节点混边 → `PushError`」同严厉度，落在 `plot-manager.md` 既有的加载期校验表里，**不新增结构、不新增字段**。

#### 6b. 内容编排判据（写不写成分支节点）

`[通行做法]` — DnD / 月圆之夜 / Reigns 一族的通行口径，落到本作约束上收敛为三条**同时成立**才写成可见分支：

1. **它是一次当下可理解的承诺**——答应 / 拒绝某人的条件、走哪条路、收不收下某物。玩家不需要任何隐藏信息就能判断自己在选什么。
2. **两条分支在**调制上**真的分岔**（不同的 `EventWhitelist` / `EnemyPoolScope` / 后续节点），而不是两句措辞不同、汇回同一节点的文案——同节点两条 `BranchChosen` 边 `ToNodeId` 不得相同这条既有校验已经挡掉了最极端的形态，判据在此把它延伸到语义层。
3. **不依赖玩家读出隐藏量**才能做出选择。

**其余一律写成自动边。** 由 `HiddenStatBand` / `EventResolved` / `EventCount` / `ChapterAdvanced` 驱动的推进本就是「玩家的行为累计决定走向」——那正是隐藏属性显影纪律要求静默的部分：**玩家学到方向与因果，学不到精确数值**。

#### 6c. 禁令：分支不得成为隐藏属性的读数口

`[既有推演]`

`BranchLabel` 是玩家能读到的文案，且它由剧本节点触发 ⇒ 它是隐藏属性泄露的一条新通道（「你已煞气缠身，要不要……」= 把档位公开）。

- **既有的软检查扩用到 `BranchLabel`**：正文含属性名 / 阿拉伯数字 / 档位序号 → `PushWarning` 逐条列出（严厉度与既有的档位文案检查一致）。
- 6a 的结构判据同时封住了更硬的那一半：`HiddenStatBand` 条件的边**在结构上就不可能带标签**（它的 `Kind` 不是 `BranchChosen`）。

### 7. 频次：全轮回个位数量级，属内容编排目标值

`[通行做法]`

- 多数边是后台自动推进的单出边；分支节点是里程碑而非常态。建议初值：**每条 Story / Chapter arc 每篇章 0–2 个分支节点**，一次轮回合计**个位数**——与跨档叙事「合计 ≈ 2–4 条 / 轮回」同量级，同属「稀缺才有分量」。
- **单节点分支条数 2–3 条**（与档位候选文案 2–3 条同量级；竖屏一屏内可读完）；> 3 条 → 加载期 `PushWarning`（软检查，同 `LevelBias` 越界那一行的严厉度）。
- **它是内容编排目标值，不入结构**：改的只是写几个分支节点，schema / 字段 / 校验一格不动。待首批真实剧本条目写完后实测校准。

## 具体形态（可 derive 的落地面）

**呈现契约（无新类型）：**

| 项 | 取值 |
|---|---|
| 载体 | **事件结算面板内的一段**（面板本身是事件收口流程内的既有呈现面）——不进屏幕栈、无返回路径、非弹层 |
| 触发 | `eventEnd` 的那一次 `TryApply` **提交之后**，`TryResolvePlot` 返回 `true` 且 `PlotSegment.Branches` 非空 |
| 数据源 | `PlotSegment(ArcId, NodeId, Body, Branches, Modulation)`——`Body` 与 `Branches[].Label` 直接渲染，`Modulation` 不呈现 |
| 呈现内容 | `Body` 正文（可空）+ 每条 `PlotBranchOption.Label` 一个全宽按钮；**不展示 `ArcId` / `NodeId` / `BranchId` / 任何数值** |
| 选择 | 点选即定，无二次确认、无跳过、无默认选中、无超时 |
| 提交 | `ChooseBranch(branchId)`，`branchId = PlotBranchOption.BranchId`（= 该边的 `ToNodeId`）→ 既定的一次 `PlotKeyPointAssignment` |
| 多 arc | 一次至多一条；序 = `Tier`（Story → Chapter → SideChapter → SideStory），同 `Tier` 按 `ArcId` 字典序 |
| 终态 | 判定 ① / ② 命中 → 整段不渲染，直接走轮回结束屏 |
| hover | 零 hover 通道，信息常驻可见 |
| 文案 | 框架走 `EVENT_` 分区；`Body` / `BranchLabel` 是内容层 `LocalizedText`；此路径不产生 `ERR_*` 键 |
| 音效 / 震动 | 与既有结算面板一致，**不为分支另加强调**（跨档叙事「不做入场动画强调」同调） |

**`ChooseBranch` 那一次写入的定位（承重）：** 它是**批次层的一次独立即时提交**，与储物袋道具使用 / 随售同族——**不新增存档点清单条目**（该写入本就是既定的：`ChooseBranch` 经 `ProfileManager` 写入）。三条连带纪律逐条核过：

| 纪律 | 本处 |
|---|---|
| **不触发 `RefreshAfterEvent`** | 成立且必须——重算会消耗 `map` 子流，并开出「用一次分支选择刷新这一批事件」的通道 |
| **照跑终态判定** | **不需要**——`PlotKeyPointAssignment` 不动任何资源 element，不可能把任何资源打到 `Min`（与储物袋道具的差别正在于此） |
| **不计软阻塞闸门** | 成立（闸门只数事件级存档点） |
| push policy | `Debounced`（与 X1 / X2 同款；它不是篇章边界 / 轮回结束 / 进入战斗前那三类 `Immediate` 时刻） |

**新增的加载期校验（并入 `plot-manager.md` 既有那张表）：**

| 违规 | 处置 |
|---|---|
| `BranchLabel` 非空 ⊕ `Condition.Kind == BranchChosen`（异或成立即违规） | `PushError` + arc `Id` + 节点 `Id` + `ToNodeId` |
| 单节点 `BranchChosen` 边 > 3 条 | `PushWarning` |
| `BranchLabel` 正文含属性名 / 阿拉伯数字 / 档位序号 | `PushWarning` 逐条列出 |

## 后果

- **`ux/screen-flow.md`**：新增「事件结算面板的剧本段」一条（正文 + 分支的呈现形态、优先序、终态不呈现）。剧本层由此第一次在 UX 文档里有落点。
- **`systems/services/plot-manager.md`**：待决问题「DnD 式选分支：触发点、UI、可见 / 不可见边界」整条移出；加载期校验表加三行；「出边与推进条件」一节补上「`BranchLabel` 非空 ⟺ `BranchChosen`」这条充要关系。
- **`open-questions/04-hidden-attributes-plot.md`**：第 14 行整条可移出（由 `/analyze-new-ideas` 执行）。
- **存档 schema：零改动、零迁移。** 无新字段、无新存档点、无新结算阶段、无新屏幕。
- **内容侧**：剧本类型档案（`content/plot-arc/` · `content/plot-node/`，两者尚未开张）的字段核对清单需带上 6a / 6b / 6c 三条判据。
- 呈现层多一段可选 UI；`EVENT_` 分区增补少量框架键（如「继续」已存在则零增补）。

## 备选方案（已考虑并否决）

- **分支摆在 EventOption 选择界面（作为一张特殊卡 / 一条横幅）。** 否决三条：① 它会让剧本层长出第二个出口——玩家在选择面上看到一个非 eventOption 的可选项，与「eventOptions 唯一出口」相抵；② 横滑区的等宽节奏被异形单元破坏（与 Explore 遮罩卡「不做异形卡」同一条判据）；③ 选择面是「花寿元买一步」的决策面，插入一个不花成本的选择会污染它的语义。
- **分支摆成一层独立全屏剧本层**（沿用 Explore 揭示转场的载体）。否决：揭示转场是**演出**、明写「自身不承载确认」；把决策放进那一层等于推翻它的定位，且新增一层全屏覆盖只为承载两个按钮，与「体裁定位：叙事是点缀不是载体」相抵。
- **分支延到下一次收口呈现。** 否决：分支正文与产生它的事件脱节，玩家读到的是一段没有由来的话；且它不换来任何结构收益（key point 已经停在分支节点上了）。
- **允许「不选 / 稍后再说」通道。** 否决：该节点出边全是 `BranchChosen`，不选即 arc 死锁；且「无跳过通道」是既定纪律（`AdvanceMode` / skip 分支整层删除的同一条精神）。
- **给分支加二次确认。** 否决：不损失资源、不可逆但无「错误答案」，与储物袋「使用」不做二段确认同判据；纵向全宽按钮的误触率也远低于横滑卡片。
- **把分支选择记进 key point 的已走路径数组。** 否决：既定明写 key points 不持久化已走分支路径（判据「重算不出来**且有消费方**」——当前无消费方），日后确需时的落点是 `PastEventEntry`。

## 与既有决策的张力

> → **已按标准默认采纳（2026-09-02 · 批量评审），未作为取向题呈交用户。** 判据：行为零改动，只是把作用域写明——「一次 `eventEnd` **之内**至多前进一个节点」。防自动连跳的承重理由未被削弱（两步之间无 eventOptions 重算，第二步是玩家输入）。

**一条，轻度，需用户点头：一次收口后剧本可前进两个节点。**

- **冲突的是哪一条**：`plot-manager.md`「一次 `eventEnd`，每条 arc 至多前进一个节点」。本方案下，一次收口里 arc 先自动进入分支节点（第 1 步，在 `eventEnd` 内），玩家随后选定（第 2 步，`ChooseBranch` 的独立提交）。
- **为什么需要它松动**：`ChooseBranch` 按既定就是一次**独立于 `eventEnd`** 的写入（玩家输入不可能塞进一次原子事务里等），所以「两步」是既定形态的必然结果，而不是本方案引入的。
- **松动的代价很小**：该纪律的承重理由是「避免一次结算跑完半条剧本线，玩家在一个事件后突然发现候选池换了三轮」。这里两步之间**没有任何 eventOptions 重算**（重算只在下一次 `eventEnd`），且第二步是玩家亲手做的而非自动连跳 ⇒ 承重理由一条都没被削弱。逐 `TryApply` 的拓扑断言（新 `NodeId` 必须是当前节点的一条出边）对两步各自照常成立。
- **不松动的替代方案**：把分支呈现延到下一次收口（见上方备选，已否决）；或把「至多前进一个节点」重述为「一次 `eventEnd` **之内**至多前进一个节点」——**推荐后者**，它只是把既有句子的作用域写明确，不改变任何行为。

## 仍需用户决定 → **已全部裁决（2026-09-02 · 批量评审）**

- **[取向选择] 分支段是否带一枚「这是一次剧情抉择」的显式标识（底色 / 图标 / 小标题）。**
  - **A · 不标识（推荐）** —— 分支段与结算面板其余部分同一视觉层级，正文与按钮就是全部。**后果**：剧本层继续保持隐匿，玩家读到的是「有人问了我一句话」，而不是「系统给了我一个剧情选择」；与「玩家永远不会『进入一个剧本节点』」「隐藏剧本层」同向。代价是首次遇到时玩家可能一时不确定这次点击与平时的「继续」有何不同。
  - **B · 轻标识** —— 一枚小图标或一行小标题（走 `EVENT_` 分区）点明这是一次抉择。**后果**：可读性更高、DnD 味更足；代价是把本作刻意隐藏的剧本层在 UI 上显形一次，且它会诱使玩家去追问「我什么时候还能遇到这种选择」——那正是隐藏属性 / 剧本层不想被建模的东西。
  - **推荐 A**，理由：承重的「隐藏剧本层 + 调制才是显影通道」是本作区别于 Reigns 的核心路径；而 A 的代价（一时不确定）由分支按钮本身的文案自然消解——按钮上写的是「答应他」而不是「继续」。
  - → **已裁决（2026-09-02 · 批量评审）：选项 A —— 不标识。** 分支段与结算面板其余部分同一视觉层级，剧本层继续保持隐匿。
