# 方案草稿 — 可信服务端时钟

## 问题

`contracts/compliance.md` §6 已定：**时段判定的时间源必须是可信的服务端时钟**，`envelope.md` §4b 的 `X-Server-Time` 仅供诊断、设备时钟不可信——时段判定若读设备时钟，改一次系统时间即绕过。但「可信服务端时钟」本身没有形态：

1. **哪一个时钟**是判定的基准（应用容器进程时钟？数据库时钟？），多副本之间如何一致；
2. 它如何**保持准确**（NTP 层级、漂移容忍、跳变纪律）；
3. 判定使用的**时区口径**是什么，落在哪一层；
4. **法定节假日表**（含调休上班的周末）从哪来、谁维护、多久更一次、**过期时怎么办**；
5. 时钟或规则数据**不可用时的降级语义**——拒绝？放行？记账告警？

第 4 条是最容易被略过的一块：现行国内口径「未成年人仅周五 / 六 / 日**与法定节假日** 20:00–21:00 可玩」中的「法定节假日」在中国是一份**每年由国务院办公厅发布、且带调休**的日历，它不是一条可由星期推算的规则。

同一个时间源还被另外三处判定共用：注销冷静期的到期（`compliance.md` §9，形态见 `inbox/solution-draft-compliance-domain-storage.md`）· `complianceTicket` 的 10 分钟寿命与 60 秒回放窗口（同上）· 未成年 access token 的 `min(15 分钟, 距时段结束剩余)` TTL（§7）。**口径必须只有一份。**

## 约束（来自既有设计）

- **单区域部署、单主 PostgreSQL、不做跨区域多活**（`operations/environments.md`「拓扑与副本」· `systems/_index.md`「明确不引入」）。
- **并发单元统一为 `account` 行**，全库只有一套并发模型（`systems/_index.md`）。
- **时段口径落配置、不进契约**；契约只给 `reasonKey` 与 `resumeAtUtc`（`contracts/compliance.md` §6）。改口径不发版，与 pillar #5「线上可干预」一致。
- **`compliance.playtime_blocked` 的 `detail` 形状已在台账写死为 `{ reasonKey, resumeAtUtc }`**（`contracts/envelope.md` §6）——任何降级路径都必须能产出一个 `resumeAtUtc`。
- **`GET /v1/compliance/status` 的 `playtimeRemainingSeconds` 是相对量，由服务端按可信时钟算好**（`compliance.md` §10）——客户端不做任何本地时钟比较。
- **access token 的 `iat` / `exp` 从会话状态派生、不从 `now()` 取**（`systems/account.md`），这是 `signin` 幂等回放能字节相同的前提。
- **配置三层**：运行期可调旋钮落 `config_knob` 表 + 进程内约 30 秒缓存，改值不发版（`operations/environments.md`）。
- **降级的既有先例是分档的，不是一律 fail-open**：限流走 Redis 且「Redis 不可用 → 放行并告警」，但**验证码 / 短信计数是明写的例外**，因为放行的代价是真金白银（`operations/environments.md`「限流的实现分层」）。
- **客户端零判定权**：`ComplianceManager` 不读年龄、不比时钟、不算时段（`game-design-documents/systems/services/account-service.md`）。本方案不产生任何客户端义务。

## 建议方案

### 1. 判定基准 = 数据库时钟，一次事务一个时刻

`[既有推演]`

**全部合规判定与长时状态机的时刻，一律取该次判定所在事务的数据库时钟**（`now()`，即事务开始时刻），不取应用容器的进程时钟。

- 单主 PostgreSQL 已经是全库唯一的串行点与并发单元（`systems/_index.md`）；容器可弹性伸缩、副本各有各的进程时钟，而**主库只有一台**。取库时钟即天然得到「全站唯一的时间基准」，不需要为「跨副本时钟一致性」再引入任何机制。
- 合规判定本就发生在一次已经握着 `account` 行锁的事务里（`signin` 的 `SELECT … FOR UPDATE`，见 `systems/account.md`），因此 `now()` **零额外开销**。
- **判定与写入看到同一个时刻**，不在两者之间开竞态缝——与 `systems/profile-store.md` 纪律 2「回声校验读的是本事务内已加锁的当前值，不是事务外的一次预读」是同一条纪律的第二个实例。

**两处例外，明写以免被误推广：**

| 例外 | 用什么时钟 | 为什么不受本条约束 |
|---|---|---|
| access token 的 `iat` / `exp` | 从**会话状态**派生（`systems/account.md` 已定） | 它必须对同一次回放字节相同，取任何「当前时刻」都会破坏这一点 |
| JWT 验签时的 `exp` 比对 | 验签侧进程时钟 | 它的时钟容错已由「旧 `kid` 保留 ≥ access token TTL + 时钟偏移余量」承接（`operations/environments.md`） |

### 2. 跨区域一致性：在当前拓扑下不存在，明写以免被反复重提

`[既有推演]`

待答条目把「跨区域一致性」列为时钟形态的一部分。**在已定的拓扑下它不是一个问题**：单区域部署、不做跨区域多活、只读副本不承接任何玩家读路径（`operations/environments.md`）。加上第 1 条把基准收敛到主库一台机器，**参与合规判定的时钟只有一个**。

海外扩展是另一套独立部署 + 独立 `accountId` 空间（同文件），届时它有自己的一套时钟与自己的一套监管口径，**不是本套的跨区域拉伸**。

> 这一段的价值是记下「已经消解」，而不是给出机制。不写它，下一次读到待答条目的人会重新去设计一套跨区域时钟同步。

### 3. 时钟同步：内网 NTP + 常驻守护 + 只 slew 不后跳

`[通行做法]`

- 容器宿主与数据库实例一律由**云厂商内网 NTP 授时**，`chrony` 一类守护进程**常驻**，不用 `ntpdate` 之类的一次性对时。托管数据库的授时由厂商负责，本条对它的要求是「可观测」（见第 4 条），不是「可配置」。
- **绝不允许时钟向后跳变。** 偏差修正一律走渐进式（slew）；超出 slew 能力的偏差应当**告警并人工介入**，不静默 step。理由：向后跳的时钟会让「一次性消费」「到期即生效」「单调序号」这类判定看到时间倒流，而这些判定的错误后果都是不可回收的（一枚已消费的 ticket 重新变得可用、一次已生效的注销回到冷静期）。
- **不可逆动作在时钟异常期间暂停。** 检测到 step 级跳变或 NTP 失同步时，**注销执行**这条唯一不可逆的动作暂停一轮（下一轮扫描自然重试，形态见 counterpart 草稿）；时段判定与 ticket 判定照常（它们的边界是小时 / 分钟级，秒级偏差不改变结论）。这条把「时钟异常」的爆炸半径限制在「晚几分钟执行」，而不是「错误地永久删号」。

### 4. 两条时钟探针

`[既有推演]`

`operations/observability.md` 的口径是「契约语义的哪些性质必须在线上可见」。可信时钟是一条契约明写的性质（`compliance.md` §6），因此它需要可见面，落 `observability.md`「其余最小集合」的数据面一节：

| 探针 | 形态 | 告警口径 |
|---|---|---|
| `clock.db_process_skew` | gauge，标签 `environment` + `instance`（均低基数） | 绝对值 > **1 秒** 记警告、> **5 秒** 工程告警 |
| `clock.ntp_unsynchronized` | 计数器 / gauge，取自 `chrony` 的同步态 | **阈值 = 0，任一次即告警** |

- 1 秒 / 5 秒的推导：本域的判定粒度是秒级（`playtimeRemainingSeconds` 是秒、ticket 回放窗口 60 秒、寿命 10 分钟）。1 秒偏差在一台常驻 NTP 的机器上「不该出现」，5 秒开始侵蚀 60 秒窗口的余量假设。**待实测校准。**
- 探针标签**不含 `accountId`**，照 `observability.md` 的低基数纪律。

### 5. 时区：`Asia/Shanghai`，落配置而非常量，且是 IANA 名不是固定偏移

`[既有推演]` + `[通行做法]`

- **判定一律在 `Asia/Shanghai` 本地时间下进行；存储与报文一律 UTC**（`envelope.md` §2 已定 RFC 3339 UTC 带 `Z`、字段名以 `AtUtc` 结尾）。`resumeAtUtc` / `playtimeRemainingSeconds` 由服务端在该时区算好后转 UTC 下发。
- **时区是时段规则的一员，与时段表同处配置，不是代码常量。** 判据与 `compliance.md` §6 那句「时段口径落配置」逐字相同：口径由监管决定，而监管口径的任何一部分都不该要求发版才能改。
- **用 IANA 时区名（`Asia/Shanghai`），不用固定偏移 `+08:00`。** 中国大陆当前无夏令时，两者今天等价；但写成固定偏移时，扩展到任何带夏令时的地区都需要改代码形状，而用 tz 名的成本为零。
- **镜像必须内置 tzdata，并作为一条部署断言。** 精简基镜像（Alpine 一类）默认不含 tzdata，`Asia/Shanghai` 会在运行期解析失败——这是一次典型的「本地跑得通、云上跑不通」，而它的表现是**合规判定当场抛异常**。断言形态：启动自检解析一次配置中的时区名，失败即**拒绝启动**（同 `operations/purchase-ops.md` 对收据表 TTL 策略的启动期断言取向）。落 `operations/deployment.md`。

### 6. 时段规则表：走词表那套不可变版本化发布

`[既有推演]`

`compliance.md` §6 只说「落后端配置」，没说落哪一层配置。**时段规则不是一个单值旋钮，是一份结构化的规则集**（星期集合 + 时段区间 + 日历），因此它不该塞进 `config_knob` 的 `key/value` 表，而应**逐条复用昵称词表的不可变版本化发布**（`operations/moderation.md`：无原地编辑路径 · 版本号单一分配点且单调 · 回滚 = 以历史内容发起更大版本 · 留痕四项（操作者 / 时间 / `derivedFrom` / 变更摘要）· 历史永久保留）。

理由与词表那条**同构且更强**：

- 存量审计必须能回答「**这一次拦截是按哪一版规则做的**」。防沉迷是监管面，一次「谁在什么时候把时段改宽了」的追问是可以预期的；而「随手改一下数据源」正是 O1 要堵的静默失效模式。
- 规则集体量与词表同量级（一年一张日历 + 几行周规则），**永久保留成本近似为零**。
- **零新增机制**：发布通道、留痕字段、回滚语义全部已经存在，本条只是给它加第二类载荷。

规则集的形状（供 `operations/compliance-ops.md` 落笔）：

```
playtime_ruleset (version BIGINT PK 单调, published_at_utc, published_by,
                  derived_from BIGINT NULL, change_summary,
                  timezone TEXT,                  -- IANA 名，例 "Asia/Shanghai"
                  weekly_days INT[],              -- 允许的星期，初值 {5,6,7}
                  window_start TIME, window_end TIME,   -- 初值 20:00 / 21:00
                  daily_limit_seconds INT,        -- 初值 3600，供 MinorDailyLimit
                  calendar JSONB)                 -- 见第 7 条
```

- `daily_limit_seconds` 与时段并列，**因为契约把 `MinorCurfew` 与 `MinorDailyLimit` 分列了**（`compliance.md` §5）——即使现行口径下两者几乎重合，规则表也要能分别表达，否则监管口径一旦拆开就要改表结构。
- **生效时刻只有一个：判定时读当前最高版本。** 不做「预约生效」——它会引入一个自己也要判时刻的调度器，而运营在发布动作上择时的成本为零。

### 7. 法定节假日日历：人工录入 + 两类条目 + 到期告警

`[通行做法]` + `[既有推演]`

**数据源：人工录入，随规则集一次发布。** 国务院办公厅每年（通常 11–12 月）发布次年放假安排，**没有官方机读 API**。因此：

- **不接任何第三方节假日 API 作权威。** 它是无 SLA 的外部依赖，一旦不可达就直接影响未成年玩家能否进入；而这份数据一年只变一次、总量二十余行。第三方 API 可作**发布前的交叉核对**辅助，**不作判定输入**——这与 `contracts/auth.md` 对 C 层原子能力「一律外接以适配器隔离」是相反方向的两类：外接的是**每次请求都要调**的能力，日历是**一年录一次**的数据。
- 录入走 `operations/moderation.md` 的来源通道 ②（人工判定结果回灌）同一条路：**收敛到同一次发布动作，不存在旁路写入**。

**日历必须有两类条目，只列节假日是错的：**

| `kind` | 语义 | 对判定的影响 |
|---|---|---|
| `StatutoryHoliday` | 法定节假日（含调休放假日） | 该日**可玩**，无论星期几 |
| `WorkingWeekend` | 调休上班的周六 / 周日 | 该日**不可玩**，尽管它是周末 |

**`WorkingWeekend` 是最容易漏的一项**：中国的调休会把周末调成工作日，若日历只有节假日正列表，一个被调成工作日的周六仍会被基础周规则判为可玩——**方向是「多给」，即不合规的那个方向**。

判定算法（顺序即语义，写死）：

```
本地日期 d = now() 在 ruleset.timezone 下的日期
① d ∈ calendar[WorkingWeekend]        → 不可玩
② d ∈ calendar[StatutoryHoliday]      → 可玩（受 window 与 daily_limit 约束）
③ weekday(d) ∈ ruleset.weekly_days    → 可玩（同上）
④ 否则                                 → 不可玩
```

`WorkingWeekend` 排在最前，因为它是**减法**：一个既被调休上班、又碰巧在假期尾巴的日子，减法必须赢——判定顺序永远让保守的那一侧优先。

**到期告警（这是日历失效唯一的机制发现面）：** 日历覆盖的最后一个日期距今 < **60 天** ⇒ 工程告警，进 `observability.md` 的告警台账。没有它，日历过期的表现是**静默地按第 5 条的降级路径走**，而没有任何人会知道。60 天的推导：次年安排通常在 11–12 月发布，60 天使告警在「已经可以拿到数据」之后、且在跨年之前留出录入与发布的余量。**待实测校准。**

年度录入本身作为一条**运维日程项**登记（每年 12 月），与 `operations/deployment.md` 的发布前置清单并列但不同批——那份清单绑的是「首个真实账号」这个一次性时刻，本条是周期性的。

### 8. 降级语义：合规判定是 fail-open 默认的第二个例外

`[既有推演]` + 一条 `[取向选择]`（见「仍需用户决定」）

三个失败面，处置不同，逐条给：

| # | 失败面 | 处置 |
|---|---|---|
| F1 | **NTP 失同步 / 进程与库时钟偏差超阈** | 判定**照常进行**（库时钟仍是唯一基准，秒级偏差不改变小时级的时段边界）+ 探针告警；**但暂停注销执行**这条不可逆动作（第 3 条） |
| F2 | **时段规则集读取失败**（配置存储抖动、进程缓存已失效且回源失败） | 对**未成年账号 fail-closed**：判为不在允许时段，回 `compliance.playtime_blocked` + `MinorCurfew`；成年账号不做时段判定，**不受影响** |
| F3 | **日历过期**（当天超出 `calendar` 覆盖范围） | 见「仍需用户决定」① |

**F2 为什么 fail-closed，而限流是 fail-open：** `operations/environments.md` 已经把这条判据立好了——限流「Redis 不可用 → 放行并告警」，但短信计数是明写的例外，因为**放行的代价是真金白银、不可回收**。合规判定是这条判据下的**第二个例外**，且代价方向更硬：错误放行一个未成年账号是合规事故（渠道下架 / 监管处罚），不可回收；错误拦截的代价是一小部分未成年账号在几十秒内进不去，**完全可回收**（配置回源恢复即自动解除）。

**爆炸半径三重夹住，因此这条 fail-closed 不撞 pillar #4：**

1. 只影响**已判定为未成年**的账号（成年账号根本不走时段判定）；
2. 只在**配置回源失败**时触发——`config_knob` 有约 30 秒进程内缓存（`environments.md`），寻常抖动根本到不了这条路径；
3. 拦截发生在 `signin`，**不打断进行中的轮回**（pillar #4 的例外面本就在这里）。

**F2 / F3 下 `resumeAtUtc` 怎么给（承重，否则报文形状不成立）：** 台账把 `compliance.playtime_blocked` 的 `detail` 写死为 `{ reasonKey, resumeAtUtc }`，而降级路径下「什么时候能玩」恰恰是算不准的那一项。解法：**给基础周规则下的下一个允许时段起点**——它只依赖星期与时钟，不依赖日历与规则集（用编译期兜底常量：周五 / 六 / 日 20:00，`Asia/Shanghai`）。它可能**晚于**实际可玩时刻（漏掉了节假日），方向保守、形状完整、零契约改动。

## 具体形态（可 derive 的落地面）

### 新增 / 修改的配置对象

| 对象 | 落点 | 说明 |
|---|---|---|
| `playtime_ruleset` | 后端配置存储，走词表的不可变版本化发布 | 第 6 条的列 + 第 7 条的 `calendar` |
| `compliance.playtime.timezone` | `playtime_ruleset.timezone`（**不是** `config_knob`） | 与规则集同版本发布，避免「时区改了但时段没改」的半版本态 |

## 备选方案（已考虑并否决）

- **以应用容器的进程时钟为判定基准** — 容器可伸缩、多副本各自漂移，会把「一个时钟」变成「N 个时钟」，并凭空需要一套跨副本一致性机制；而库时钟已经在事务里免费拿到。
- **接第三方节假日 API 作判定输入** — 无 SLA 的外部依赖直接决定未成年玩家能否进入，且这份数据一年只变一次、总量二十余行，把它做成运行时依赖是纯粹的自造故障域。
- **把时段规则塞进 `config_knob` 的 key/value 表** — 规则集是结构化多字段对象且需要留痕与版本追溯，塞进单值旋钮表会失去「这次拦截按哪一版规则做的」这个必须能回答的问题。
- **日历只列法定节假日，不列调休工作周末** — 漏掉减法那一半，方向是「多给可玩时段」，即不合规的那一侧。
- **规则集支持「预约生效时间」** — 引入一个自己也要判时刻的调度器，而运营在发布动作上择时的成本为零。
- **时区写成固定偏移 `+08:00`** — 今天等价，但任何带夏令时的扩展都要改形状；用 IANA 名成本为零。
- **时钟异常时暂停全部合规判定（含时段拦截）** — 那等于把一次时钟抖动升级成「全体未成年账号可以随便玩」或「全体登不进」，两个方向都比「照常判定 + 告警」差；秒级偏差不改变小时级边界这一事实使暂停毫无收益。
- **允许 NTP 做 step 跳变以求快速收敛** — 向后跳的时钟会让一次性消费、到期生效、单调序号同时失去意义，而这些判定的错误后果不可回收。
- **让客户端上报设备时钟供服务端交叉校验** — 设备时钟不可信是 `envelope.md` §4b 的既定前提；引入一个不可信输入去校验一个可信基准，只会制造一条可被伪造的分支。
- **降级时把 `resumeAtUtc` 省略** — 台账已把 `detail` 形状写死为 `{ reasonKey, resumeAtUtc }`；省略即报文不合契约，且客户端的解除时间呈现会落空。

## 与既有决策的张力

**一处，已给出不需要松动任何既有决策的解法：**

`operations/environments.md` 的降级默认是 **fail-open**（「Redis 不可用 → 放行并告警：限流是防滥用，不是正确性的一部分」），而本方案第 8 条 F2 对未成年账号取 **fail-closed**。这**不是**推翻那条——同一份文件已经明写了 fail-open 有例外（验证码 / 短信计数），判据是「放行的代价是否不可回收」。本方案要做的是**把那条判据显式化**，并登记合规判定为它的第二个实例：

> **fail-open 是默认，例外的判据是「错误放行的代价不可回收」。** 已知两个实例：短信计数（真金白银）· 未成年时段判定（合规事故）。

建议提炼时把这句判据写进 `operations/environments.md`「限流的实现分层」一节，使第三个例外出现时有judged可依，而不是再来一次特事特办。**若用户认为不该让合规判定 fail-closed**，见「仍需用户决定」①——那一项同时决定 F2 与 F3。

### ① 日历过期（F3）时，对未成年账号取哪个方向？

**→ 已裁决（2026-09-06 · 批量评审）：取方向 A —— 未成年账号一律拦截（fail-closed），与 F2 规则集读取失败同处置。** 成年账号不受影响。理由：错误拦截可回收、错误放行不可回收；日历过期已有提前 60 天的告警，是可预防的运维失职，不为它设计一条产生合规风险的降级路径。降级路径就此只有一条。

**背景（自包含）：** 时段规则集里带一份**法定节假日日历**（含调休上班的周末）。它每年人工录入一次。若某年忘了录入 / 录入晚了，判定当天时会落到「日历覆盖不到今天」这个状态。此时基础周规则（周五 / 六 / 日 20:00–21:00）仍然可算，但**节假日增量与调休减量都失去了**。

**方向 A（推荐）—— 一律拦截（fail-closed），与 F2 同处置。**
- 未成年账号收 `compliance.playtime_blocked` + `MinorCurfew`，`resumeAtUtc` 给基础周规则下的下一个允许时段起点。
- 后果：日历过期期间未成年账号完全进不去（每天最多一小时的窗口消失）。**但日历过期已经被提前 60 天告警过**，它是一次可预防的运维失职；为一个可预防的失误设计一条会产生合规风险的降级路径是本末倒置。
- 代价上界明确：受影响人群 = 未成年账号，受影响时长 = 从过期到补录之间。

**方向 B —— 按基础周规则继续判定（部分 fail-open）。**
- 周五 / 六 / 日 20:00–21:00 照常可玩，节假日不额外开放（保守），**但调休上班的周六 / 周日会被错误地判为可玩**（不保守）。
- 后果：体验上更平滑，但每年有约 6–8 天存在「本该不可玩却放行」的窗口——方向正是不合规的那一侧。
- 若选此项，建议至少把「周六 / 周日」从降级期的可玩集合中剔除（只留周五），使减法那一半不失守；代价是周末体验仍然全失，收益相对方向 A 很小。

**方向 C —— 拦截成年账号之外的全部账号（全站 fail-closed）。**
- 不推荐，**列出只为说明它已被考虑**：成年账号本就不做时段判定，把它们一起拦住是把一次配置问题升级成全站不可用，直撞 pillar #4。

**推荐 A**，理由：日历过期是被提前警告过的可预防失误；错误拦截可回收、错误放行不可回收；且 A 与 F2 同处置，降级路径只有一条而不是两条（两条降级路径必然有一条长期没被走过、因而是坏的）。

**这一项为什么是取向而非推演：** 它取决于用户对「合规风险 vs 未成年玩家体验」的胃口，两个方向都能自洽地实现，既有设计没有能推出唯一解的约束。
