# 方案草稿 — MTG 借词定名与卡牌类型体系（第二版）

## 问题

08-02 立下借词纪律后，清单只答结了一半：`instant`（瞬间）明确**不借**、`stack` 定名**堆栈**、回合三步与回合归属方已登记，**待定名的第一批 = `sorcery speed` / `start step` / `main phase` / `end step` / `resolve` / `trigger`** 悬在原地。同时暴露出三个更深的空缺：三步结构的中英措辞各自不齐整；**卡牌类型维度从未被提出**（08-03 引入战场后，「结算后进弃牌堆」与「结算后留在战场」已是两种生命周期，缺一个字段承载）；**异能只谈了载体、没谈种类**（静止 / 启动 / 触发的三分至今无对应表述）。

本草稿一次收口。**第二版：** 第一版的五项取向选择已全部由用户裁决，卡牌类型整套重写（对齐万智的 sorcery / creature / enchantment 三支，另加 item 与业障两类），并新增三条用户给定的规则要求——**引入永久物概念**、**规则体系须支持「奥秘」式埋伏牌**、**道具类不洗进卡组、存于储物袋**。

**第三版：** ① 补入第六个卡牌类型 **`Power`（神通 / 法则）**——**徽记式条目，几乎不可被交互，战斗开始时直接入场**，它连带实质答定了 01-combat.md 上「PlayerPower（法则）能否承载战斗内触发」这一条；② **储物袋更正为非战斗概念**（角色的道具容器，上限 99 ≈ 不设限），战斗里出现的是「本场可用道具」这一筛选视图；③ **敌人同样持有 item 与 power**，只是没有储物袋这个概念；④ 另五项取向选择由用户裁决并落入正文。

## 约束（来自既有设计）

- **借词纪律：** 借词须在 `terminology.md` 登记为已定含义、写清与 MTG 原义的出入，**不得覆盖既有仙侠定名**（mana = 法力、momentum = 道念、PlayerPower = 法则、PlayerItem = 古宝、CharacterPower = 神通、CharacterItem = 法宝）。Source: `terminology.md` 借词纪律（08-02）。
- **交互与优先权整体移除，`instant` 明确不借。** 只有回合归属方能在自己的出牌阶段出牌，**栈非空时双方都不能出牌**。Source: `handoffs/2026-08-02b-stack-without-interaction-and-three-step-turn.md`。
- **栈与战场是两个区。** 结算路径 = 打出 → 入栈 →（LIFO）弹出结算 → 效果施加 →（若持续）落到战场。Source: `handoffs/2026-08-03-battlefield-stack-hand-limit-and-power-item-naming.md`。
- **弃牌堆流量的完整清单 = 打出后进弃牌堆 + 卡牌效果显式弃牌。** 没有回合末弃牌、满手不弃牌。同上。
- **手牌上限是纯上界，满手时抽牌抽不进**（牌留在抽牌堆）。同上。
- **道念是唯一胜负标尺，卡牌是道念的唯一产出途径；无伤害模型、无战斗步骤。** Source: `systems/character-profile/deck/_index.md`、`combat-service.md`。
- **无 mana 曲线**（每回合恢复至 `manaLimit`），故**不存在资源发展类牌**（MTG 的地牌一类）。Source: `systems/character-profile/mana.md`。
- **战斗内的一切写入经 `ProfileManager.TryApply`**；本服务不直接改 Profile 字段。Source: `combat-service.md`。
- **法宝 = CharacterItem（轮回级、CharacterProfile 持有、随轮回清理）；古宝 = PlayerItem（账号级、有使用次数限制）。** Source: `terminology.md`（08-03 定名）。
- **神通 = CharacterPower（轮回级）/ 法则 = PlayerPower（账号级 always-available、带 `status` 开关、默认开启）；两者共用 `status` 开关、事件触发器被动修正、capability flag + modifier pipeline 两条生效通道。** Source: `terminology.md`（08-03 定名）。
- **「参战方组装时要把角色持有的神通注册进战场」已定案**（08-03 推论 ③），且「PlayerPower 能否承载战斗内触发」被列为待答。Source: `combat-service.md` 触发载体条 + 待决问题。
- **卡牌是数据资源**（`CardData : Resource`、`.tres`、稳定唯一 `Id`），数值不硬编码，坏数据须在加载时大声失败。Source: `.claude/rules/data-resource-rules.md`。
- **移动优先 · 竖屏 · 休闲**：类型数量与关键字体系必须能在一张竖屏卡面上讲清。Source: `vision/scope.md`、`.claude/rules/ui-input-rules.md`。

## 建议方案

### 一、`sorcery speed` 不借，改写为一条全局出牌时机规则

`[已由用户裁决 · approve]` `[既有推演]`

**`sorcery speed` 从 `terminology.md` 整条删除，不给中文名。**

依据：它在本作里已不指代任何可区分的东西。MTG 需要这个词，是因为存在 `instant speed` 与之相对——它是一个**卡牌属性维度**。08-02b 已移除交互、明确不借 `instant`，`combat-service.md` 自己也写了「**出牌时机不再是卡牌的一个属性而是全局规则**」。单一取值的维度不是维度，保留它反而制造「本作有出牌时机之分」的错觉。

**替代表述**（建议直接写进 `combat-service.md` 与 `deck/_index.md`，取代所有「所有牌都是 sorcery speed」的措辞）：

> **出牌时机（唯一）：** 一张牌只能在**自己回合的行动阶段、且栈为空时**打出。这是全局规则，不是卡牌属性——本作不存在第二种出牌时机。**启动式异能与道具的使用窗口与之完全相同。**

**这不是推翻决策，只是措辞重构**：机制原样保留。

### 二、三步结构统一为「阶段」，`main phase` 重构为 `action step`

`[已由用户裁决 · approve]`

**中文侧三步统一以「阶段」收尾，英文侧三步统一以 `step` 收尾**：

| 现行（作废） | 定名 | 英文 / 代码 |
|---|---|---|
| 起始步 | **开始阶段** | `start step` / `TurnStep.Start` |
| **主阶段** | **行动阶段** | **`action step`** / `TurnStep.Action`（**从 `main phase` 重构而来**） |
| 结束步 | **结束阶段** | `end step` / `TurnStep.End` |

`main phase` 一并弃用：MTG 的 `main` 有 `beginning` / `combat` / `ending` 等同级 phase 与 precombat / postcombat 两个 main 作对照系；本作**无战斗步骤、无双主阶段**（08-02b 定案），对照系不存在，`action` 直接陈述这一步做什么。

**与 `eventStart` / `eventEnd` 的同词问题：已裁决为接受。** 二者语境不同（事件级 vs 回合级）且从不同屏出现，不作重构。

### 三、`resolve` = 结算，`trigger` = 触发；战斗收口处改称「收口」

`[已由用户裁决 · approve]`

- **`resolve` = 结算。** 与既有措辞吻合（「打出 → 入栈 → LIFO 弹出结算」「每一次结算时截断」），本次正式登记为借词。与 MTG 的出入：MTG 的 resolve 只作用于栈上对象，本作同义。
- **战斗收口处的「结算」改称「收口」（`settle`）。** 「失败时才在结算时刻扣 lifeTotal」「结算时角色道念」这类表述全部改为**收口**，把「结算」一词让给 `resolve` 专用。**一词两义就此消除。**
- **`trigger` = 触发。** 登记时须写清出入：**本作的触发时点全部有归属方**（「回合开始时」是**某一方的**回合开始），MTG 无此约束；且**触发命中后压栈者一律是 StackManager**，与载体解耦。

### 四、异能三分：静止式 / 启动式 / 触发式（启动式已采纳）

`[已由用户裁决 · 采纳启动式异能]`

| 中文 | 英文 / 代码 | 是否入栈 | 何时可用 | 载体 |
|---|---|---|---|---|
| **静止式异能** | `static ability` | **否**（持续生效，不经栈） | 只要载体在战场上就一直生效 | 战场条目（永久物、场上持续状态、神通） |
| **启动式异能** | `activated ability` | **是**（启动后压栈） | **自己回合的行动阶段、栈为空时**（与出牌同一窗口） | 同上 |
| **触发式异能** | `triggered ability` | **是**（命中后由 StackManager 压栈） | 触发时点命中时，**可跨归属方**（见第六节） | 同上 + 牌上触发器 |

这三分补完了 08-03「载体开放」的另一半：**载体说的是「挂在谁身上」，异能类型说的是「怎么生效」**，两者正交。

**关键自洽点：启动式异能不重新引入交互。** 其可用窗口被限定为**与出牌完全相同的那一个窗口**，不构成「在对手回合插手」的通道，08-02b 的定案不被松动。

**推论 ①：异能应是独立于 `CardData` 的可复用资源类型。** 神通、场上持续状态、道具都能带异能，异能就不能是 `CardData` 的私有字段结构——抽为 `AbilityData : Resource`，由 `CardData` / `CharacterPowerData` / `ItemData` / 战场条目共同引用。这与 08-03 推论 ①（触发匹配逻辑不能写死在卡牌类型里）是同一条。

**推论 ②：静止式异能是 BattlefieldManager 的一条与栈无关的写入路径。** 它不经栈——载体一进场即时生效、一离场即时失效。

**推论 ③：启动式异能给 mana 第二个花费去向。** 此前 mana 只用于出牌，「每回合刷满、不结转」意味着手牌不足时 mana 纯浪费；现在场上永久物也能吃 mana，**沉没成本问题被缓解**，且战场从纯被动区变成有操作面的区。

### 五、引入永久物（permanent）

`[已由用户裁决 · 用户指定引入]` `[既有推演：与战场条目的划分]`

**永久物 = 落在战场上、无限期存在直到被移除的条目。** 第一版曾以「本作战场条目带生命周期标记、与 MTG 的无限期语义不符」为由否决借入——**该否决作废**。用户指定引入后，正确的解法不是不借，而是**用永久物把战场条目切成两类**：

| 战场条目 | 生命周期 | 举例 |
|---|---|---|
| **永久物（permanent）** | **无限期**，直到被效果移除或战斗结束 | 灵宠、阵法 |
| **非永久条目（持续状态）** | 带生命周期标记（**回合内** / 跨回合 / 持续 N 回合） | 「我方本回合所有牌 +1 道念」这类临时状态 |

这个二分把 08-03 留下的「回合内状态的判定边界」问题**结构上收窄了一半**：结束阶段「清理回合内状态」**只清理非永久条目中标记为回合内的那些，永远不碰永久物**——「永久物会不会在结束阶段被误清」这个潜在歧义直接消失。

**与 MTG 原义的出入（登记时须写明）：** MTG 的 permanent 是**区的成员资格**（在战场上的对象一律是永久物）；**本作的战场上同时住着永久物与非永久的持续状态**，故永久物在本作是战场条目的一个**子集**，不等于「在战场上」。

**推论 ①：「可被移除」这件事只对永久物有意义。** 针对 / 移除类效果的目标合法性因此有了明确的类型级判据。
**推论 ②：永久物必须可序列化**（决策点存档要求局面可恢复，08-03 推论 ⑤）；非永久条目同理，但二者的字段形态不同（永久物带来源卡牌 `Id` + 运行态，持续状态带生命周期标记 + 剩余回合数）。

### 六、规则体系支持「奥秘」式埋伏牌

`[已由用户裁决 · 用户指定要求]` `[既有推演]`

这条要求**实质上答定了 01-combat.md 里悬着的「触发条件能否跨归属方」**：埋伏牌的本质就是「**在对手回合的某个时点触发**」，若触发条件不能跨归属方，奥秘无从成立。故：

> **触发条件可以跨归属方。** 时点本身有归属方（「回合开始时」是某一方的），但**监听方不必是该归属方**——一个条目可以监听「**对手的**回合开始时」「**对手**打出牌时」。

**（注：这条的正式答结归 `/analyze-new-ideas`，本草稿只做推演与登记建议。）**

**建议的埋伏牌形态：**

| 项 | 建议 | 依据 |
|---|---|---|
| 归属类型 | **阵法（enchantment）的一个次类型**，暂名「**埋伏**」 | 炉石的奥秘正是「Secret 次类型」；本作阵法就是「留场且承载异能」的那一类，埋伏 = 面朝下的阵法 |
| 是否永久物 | **是** | 它留在战场直到被触发或战斗结束 |
| 触发后去向 | **弃牌堆** | 与「打出后进弃牌堆」同路，不新增流量类型 |
| 对手可见性 | **对手只知道「有一张埋伏」，不知道是哪张** | 若完全不可见，则对手无从规避、变成纯 gotcha；若完全可见则失去意义。这是炉石的成熟做法 |
| 数量上限 | **同名埋伏不可重复布置** | 否则同一触发条件叠放多张，连锁结算的可读性在竖屏上崩掉 |

**推论 ①（承重 · 与既有待答问题合流）：埋伏牌会让「意图即承诺」出现第三种落空方式。** 08-02c 已定案「意图公布后不因玩家行动重算」，并把「承诺与执行不一致时如何处理」列为待答；**玩家布下的埋伏在敌人回合触发，正是让敌人计划落空的典型场景**，且它比「资源变化」更频繁、更主动。这条**加压**了那个待答问题——建议在答它时**以埋伏牌为首要样例**。

**推论 ②（已裁决）：敌人 AI 知道「有一张埋伏」，但不知道是哪张。** 与玩家看到的信息完全对称——**这是本作第一处双向对称的信息规则**（意图揭示是单向的：玩家按等级差看敌人，敌人不「看」玩家）。落地上，EnemyManager 规划时从战场读到的是**埋伏的计数，不是条目内容**；它可以据此变得谨慎（例：留一张牌不打），但无法针对性规避。这也意味着**埋伏的威慑力与实际效果是两件事**——即便埋伏很弱，它的存在本身就在改变 AI 行为，这是设计上可利用的。

**推论 ③：埋伏牌的结算入口不变。** 触发命中后由 **StackManager 压栈**（08-03 定案「压栈者与载体解耦」），埋伏不需要任何新的结算通道——**这正是移除交互后 stack 仍然承重的又一个证明**：玩家不能在对手回合主动响应，但可以**预先布置**在对手回合自动响应的东西。埋伏牌因此是**交互被移除后，留给玩家的唯一一条「在对手回合发生作用」的通道**，设计价值很高。

### 七、卡牌类型 —— 一套六类

`[已由用户裁决 · 类型与定名由用户给定]` + `[既有推演：落地形态]`

| 中文 | 英文 / 代码 | 所在区 | 结算后去处 | 是否永久物 | 可带的异能 |
|---|---|---|---|---|---|
| **法术** | `Sorcery` | 卡组 → 手牌 | **弃牌堆** | 否 | 触发式（限「在栈上 / 结算时」的触发） |
| **灵宠** | `Creature` | 卡组 → 手牌 | **战场** | **是** | 静止式 / 启动式 / 触发式 |
| **阵法** | `Enchantment` | 卡组 → 手牌 | **战场** | **是** | 静止式 / 启动式 / 触发式 |
| **法宝 / 古宝** | `Item` | **储物袋**（不洗进卡组） | **弃牌堆**（或按次数消耗，见下） | 否（除非其效果留下永久物） | 启动式为主 |
| **神通 / 法则** | `Power` | **开局直接入场**（不洗进卡组，也不经储物袋） | **不离场**（战斗结束才消失） | **是**（且**几乎不可被交互**） | 静止式 / 启动式 / 触发式 |
| **业障** | `Affliction` | 卡组 → 手牌 | **弃牌堆** | 否 | — |

**三个来源区，各自绕开的东西不同**——这是六类之间最本质的结构差别，值得单列：

| 来源 | 类型 | 受抽牌运制约 | 需玩家动作才生效 |
|---|---|---|---|
| **卡组** | 法术 / 灵宠 / 阵法 / 业障 | **是** | 是（打出） |
| **持有的道具**（玩家侧来自储物袋，敌人侧来自 `EnemyTemplate`） | 法宝 / 古宝 | 否 | 是（使用） |
| **开局入场** | 神通 / 法则 | 否 | **否**（自动在场） |

> **储物袋不是战斗概念。** 它是角色的道具容器（跨战斗内外存在，上限 99 ≈ 无限制）；战斗只从中筛出 `UsableScene` 含 `InCombat` 的那些。**敌人没有储物袋，但同样持有 item 与 power**——这正说明「容器」与「本场可用道具」是两个必须分开的概念。

**类型间的具体差异化留待日后**（用户已明确）。以下只给**当前已能确定的结构性差别**，即那些不定就无法写 schema 的部分。

#### 7.1 法术（`Sorcery`）

对位 MTG 的 Sorcery。一次性效果，结算后进弃牌堆。**因不存在 Instant，本作不需要 sorcery / instant 的对照**——「法术」在本作里就是「一次性牌」的通名，无速度含义。

**定名提示（非阻塞）：** 「法术」与既有的**法力**（mana）、**法则**（PlayerPower）、**法宝**（CharacterItem）共用「法」字根，是本表第四个「法」字词。08-03 已定「中文名不承担层级表达」，故不构成规则冲突；但 UI 文案里「法术 / 法宝」相邻出现时（二者都是卡牌类型）需靠卡框色与图标区分，不能只靠文字。

#### 7.2 灵宠（`Creature`）

对位 MTG 的 Creature，**形态改写**：**无战斗步骤、无伤害模型，故灵宠不互相攻击**。它是场上的实体永久物，典型形态 = 靠触发式异能每回合稳定产出道念，或以静止式异能持续修正双方数值；**可被针对 / 移除**是它区别于阵法的候选轴（待日后定）。

**推论：灵宠是「延迟回报」型的道念产出通道。** 法术是即时产出，灵宠是分期产出——两者的取舍（现在拿 5 点，还是每回合拿 2 点但可能被拆）正是定长 10 回合对局里最自然的一条策略轴，且**越接近第 10 回合，灵宠越不划算**，定长战斗天然给了它一条内建的时间价值曲线。这条不需要额外机制支撑。

#### 7.3 阵法（`Enchantment`）

对位 MTG 的 Enchantment。场上的非实体永久物，承载静止式 / 启动式 / 触发式异能，是 build 的骨架。**埋伏（奥秘）是它的一个次类型**（见第六节）。

> 第一版曾建议「阵法不可被针对、灵宠可被针对」作为二者的区分轴。**第三版建议弃用该轴**——「场上不可被移除的东西」这个生态位已由 `Power` 独占（见 7.5 推论 ④），阵法与灵宠应当都可被针对，二者的区分轴另找。具体差异化仍按用户要求留待日后。

#### 7.4 法宝 / 古宝（`Item`）—— 储物袋与不洗进卡组

`[承重 · 结构性新增]`

**这是本版最大的结构变化：卡牌不再只有一个来源区。**

| 项 | 定案（用户给定） | 推演出的落地形态 |
|---|---|---|
| 不洗进卡组 | ✔ | 道具**不参与抽牌 / 洗牌 / 弃牌循环**，抽牌堆确定性完全不受影响 |
| 存于**储物袋**（`magic pack`） | ✔ | **储物袋是角色的道具容器，不是战斗概念**——它跨战斗内外存在，容量上限 **99**（**等于不设限制**，只是防溢出的护栏）。战斗只是**从中筛出本场可用的那些**（`UsableScene` 含 `InCombat`），不改变储物袋本身的地位 |
| 战斗内的道具来源 | —（推演） | 参战方各持一份**本场可用道具**：**玩家侧来自储物袋的筛选结果，敌人侧来自 `EnemyTemplate`**（敌人没有储物袋这个概念，但**同样持有 item 与 power**） |
| **敌人的道具效果计入意图数值** | ✔（已裁决） | 意图是「本回合全部行动的最终结果」，道具是行动的一种；排除它会让「意图即承诺」不可信 |
| 「像精灵球一样随时可用」 | ✔ | **不受抽牌运制约**——想用就能用，这是它与卡牌最本质的差别 |
| **使用窗口 = 仅自己回合** | ✔（已裁决） | 与出牌 / 启动式异能**完全同窗口**（自己回合的行动阶段、栈为空时）。**「随时」= 不受抽牌运制约，不是不受回合限制**——交互不回归，`RunCombatAsync` 状态机形状不变 |
| 可能有法力费用 | ✔ | `ItemData` 带可选的 mana 费用；零费道具亦合法（与启动式异能必须有费用的规则**不同**，因为道具有使用次数这层天然限制） |
| **并非所有道具都能在战斗中用** | ✔（已裁决） | `ItemData` 带 `UsableScene { InCombat / OutOfCombat / Both }`；储物袋**只装本场可用的那些**（`InCombat` 或 `Both`），战斗外才有意义的道具（恢复寿元、影响事件掷骰）不进储物袋、不占容量 |
| 分两级 | 法宝 = CharacterItem（轮回级）/ 古宝 = PlayerItem（账号级、有使用次数限制） | 储物袋在战斗内**同时呈现两级**，条目上需带一个 `ItemScope { Character, Player }` 标识来源 |
| **古宝次数即时写** | ✔（已裁决） | 用掉一次即经 `ProfileManager.TryApply` 写 PlayerProfile，**不攒到收口**。与既有定案「战斗过程中的变更即时经 ProfileManager，`Spoils` 只承载收口产出」一致，且堵死「用完退出重进恢复次数」的窗口 |

**推论 ①（承重）：道具是战斗内唯一会即时写 Profile 的卡牌行为。** 其余所有牌都是战斗内运行态（道念、手牌、战场条目战斗结束即消失）；**但古宝的使用次数是账号级持久数据**，法宝的消耗是轮回级持久数据。这两者一旦在战斗中被消耗，就必须经 `ProfileManager.TryApply` 落到 Profile 上——**既有定案「战斗内的一切写入经 ProfileManager」正好承接这条**，无需新机制。写入时机见「仍需用户决定」。

**推论 ②：战斗界面需要一个道具区，但它不是「储物袋」。** 战斗界面此前已有手牌 / 栈 / 战场三个区要显示（08-03 推论 ⑦），现在加一个**本场可用道具**区。竖屏空间紧张，建议**默认收起为一个角标（显示可用道具数），点开为抽屉式面板**——它不像手牌那样每回合变化，不值得常驻占位。**措辞上不要在战斗语境里称它为「储物袋」**：储物袋是角色的容器（含大量战斗外道具），战斗里出现的只是它的一个筛选视图；敌人没有储物袋却同样有道具，也证明这两个概念必须分开。

**推论 ③：道具绕开了手牌上限这条节奏约束。** 手牌上限的设计意图是「逼玩家出牌腾位」（08-03 推论 ④），而道具不占手牌位、不受满手影响。**这是有意的松弛阀**：卡组构筑受抽牌运摆布，道具是玩家可以规划的确定性资源。但也意味着**道具的强度必须比同费法术低**，否则「确定性 + 不占位 + 不受抽牌运」三重优势会让卡牌相形见绌。这条属平衡，归 `systems/balance.md`。

**推论 ④（已裁决 · 张力消解）：使用窗口 = 仅自己回合。** 「随时可用」被明确解读为**不受抽牌运制约**，而非不受回合限制——道具的窗口与出牌 / 启动式异能完全相同。**08-02b「交互与优先权整体移除」的定案因此毫发无损**，TurnManager 不需要对手回合的输入窗口，「定长 10 回合 → 时长可预测」也继续成立。精灵球式的手感由「想用就能用、不看抽牌运」承载，与回合限制不冲突。

**推论 ⑥（由「敌人道具计入意图」推出 · 承重）：EnemyManager 的回合级规划必须把道具一并算进去。** 意图已定案为**回合级综合描述、公布即承诺、且综合数值 = 计算后合并的最终结果**；道具计入意图意味着 AI 在玩家回合开始之前**就要连道具一起定好本回合的整套行动**，而不是出牌规划完再临时决定用不用道具。**这不新增机制**——「回合级一次性规划」本就排除了逐张即时决策，道具只是规划输入里多了一个来源。但它**加固了一条既有的待答问题**：道具用不出来（次数耗尽、目标失效）同样会造成「承诺与执行不一致」，与埋伏牌一起构成该问题的两个主要样例。

**推论 ⑦：`UsableScene` 是战斗道具区的筛选条件，与储物袋容量无关。** 储物袋装角色的**全部**道具（含纯事件类的恢复寿元、影响掷骰），上限 99 ≈ 无限制；战斗只呈现其中 `InCombat` / `Both` 的那些。**两件事互不牵扯**：容量护栏管的是存档体积与 UI 溢出，`UsableScene` 管的是战斗界面的信噪比。

#### 7.5 神通 / 法则（`Power`）—— 徽记式的开局入场条目

`[已由用户裁决 · 用户指定]` `[既有推演：它落在 08-03 已铺好的位置上]`

**对位 MTG 的徽记（emblem）**：由效果产生、留在场外的指挥区、**不是永久物、几乎不能被任何东西针对或移除**、一旦存在就一直存在。本作把这个语义接过来，但落点改到战场（见下）。

| 项 | 定案（用户给定） | 推演出的落地形态 |
|---|---|---|
| 不洗进卡组、不经储物袋 | ✔ | 它不需要「获得」的动作——**开局即在场** |
| 战斗开始时入场 | ✔ | 入场发生在参战方组装阶段，**早于第一个开始阶段**，因此「回合开始时」类触发从第 1 回合起就已挂载 |
| 几乎不可被交互 | ✔ | **默认不可被针对 / 不可被移除**；「几乎」而非「绝不」——留一个显式后门（见「仍需用户决定」第 7 项） |
| 分两级 | 神通 = CharacterPower（轮回级）/ 法则 = PlayerPower（账号级） | 与 `Item` 完全对称：条目上带 `PowerScope { Character, Player }` |
| **并非所有神通 / 法则都进战斗** | ✔（已裁决 · 与道具同规） | `PowerData` 同样带 `UsableScene { InCombat / OutOfCombat / Both }`。**只有 `InCombat` / `Both` 的才在开局入场**；纯事件向的能力（影响掷骰、推拉隐藏属性、商店折扣）继续走 capability flag / modifier pipeline 两条既有通道，不进战场 |
| **敌人同样持有 power** | ✔（已裁决） | `EnemyTemplate` 需要一个 power 持有列表字段。**「不可被移除的场上特性」正是 boss / 天劫最自然的表达**，与既有的「越阶 = 意图完全黑箱」共同构成境界压迫感的两条腿 |

**这条几乎不需要新机制——08-03 已经把位置铺好了。** 当时定案「参战方组装时要把角色持有的**神通注册进战场**」，本条只是给这个已存在的行为**一个类型名**，并把**法则**一并纳入同一条路径。

**推论 ①（承重 · 答定一条待答问题）：法则能承载战斗内触发。** 01-combat.md 与 `combat-service.md` 都把「PlayerPower（法则）能否承载战斗内触发」列为待答，并预言了后果——「若可，则 combat-service 还要读 PlayerProfile 一侧的持有列表」。**`Power` 成为卡牌类型即意味着答案是「能」**，那条预言的后果照单成立：参战方组装时要读**两个 Profile**。（正式移出待答清单归 `/analyze-new-ideas`。）

**推论 ②：入场条件是两条与门——`status == 开启` **且** `UsableScene` 含 `InCombat`。** 神通与法则都已定案带 `status` 开关（默认开启），开关的语义因此在战斗内有了确切落点：**关闭 = 不入场**，而非「入场但不生效」——前者更干净，且让战场上不出现无效条目。`UsableScene` 是第二道闸：**它是内容侧的静态属性（这个能力在战斗里有没有意义），`status` 是玩家侧的运行时开关（我要不要用它）**，两者正交，不能合并成一个字段。

**推论 ③：法则获得了第三条生效通道，但用得极少（已裁决）。** 此前法则只有 capability flag（具名布尔）与 modifier pipeline（具名数值修正）两条，二者都是**在消费点被查询**的被动形态；作为 `Power` 入场后，它可以**主动挂触发器、带启动式异能**，设计空间从「全局参数修正」扩展到「战斗内的玩法」。**裁决为允许但极其稀缺**——理由是 premium bundle 花了钱就该让体验更好，而战斗是核心体验的关键一环。**代价由稀缺性而非规则承担**（配额纪律、强度定位、付费战斗价值主要压在有次数限制的古宝上），完整形态见「与既有决策的张力」第 6 条。

**推论 ④（澄清了一条悬着的区分轴）：「不可被针对」这个位置被 `Power` 占了。** 第一版曾建议以「阵法不可被针对 / 灵宠可被针对」作为二者的区分轴，第二版已降级为候选——现在可以进一步说：**该候选不宜采用**。「场上不可被移除的东西」这个生态位应当由 `Power` 独占，否则「哪些永久物能被拆」这条规则会出现两套判据。**阵法与灵宠应当都可被针对**，它们的区分轴另找（实体 vs 非实体、产出形态、次类型体系等，日后定）。

**推论 ⑤：`Power` 是永久物，但要在永久物内部再分一档。** 它满足永久物的定义（无限期留场直到战斗结束），但**不满足「可被移除」这条永久物的通常推论**。落地上给永久物加一个 `IsProtected` 标记即可，不必再开一个区——**不建议引入 MTG 的指挥区（command zone）**：战斗内已有卡组 / 手牌 / 弃牌堆 / 栈 / 战场 / 本场可用道具六处位置，为一类不可交互的条目再开第七处，收益不抵竖屏 UI 与存档形态的成本。

**推论 ⑥：`Power` 无 mana 费用。** 它不被「打出」，故费用字段对它无意义（启动式异能的启动费另算）。这是一条可校验的规则。

**推论 ⑦：`Power` 是唯一不产生弃牌堆流量、也不产生栈上「打出」事件的类型。** 08-03 定案的弃牌堆流量完整清单（打出后进弃牌堆 + 效果显式弃牌）**不受本条影响**；`Power` 的触发式异能照常经 StackManager 压栈，但**它自身永远不入栈**。

#### 7.6 业障（`Affliction`）

`[已由用户裁决 · 采纳，且已选定解法]`

负向牌，由事件的负向奖励条目塞进**卡组**（对齐 Slay the Spire 的 Curse）。**采纳的解法：业障可被打出，但没有任何正面效果，打出的唯一作用就是把自己送进弃牌堆。**

**这条解法把死锁风险完全消除了**，且与既有定案高度同调：
- 08-03 定案「弃牌不是被规则强制的动作原语」——**业障不需要任何弃牌机制**，它走的是「打出后进弃牌堆」这条既有通道，弃牌堆流量的完整清单不变。
- 08-03 推论 ④「满手的代价是 tempo 而非资源」——**业障的代价同样是 tempo**：它占一个手牌位，玩家要花一次出牌动作把它清掉。整套惩罚模型自洽为同一条「时间即代价」。
- **它比 Slay the Spire 的 Curse 温和**（那里 Curse 不可打出、只能靠回合末弃手牌自然清），也比第一版草稿担心的「永久堵塞」安全得多。

**额外代价：逐条目而定，通常没有（已裁决）。** 业障**不是**一个统一强度的类型——**多数业障零代价**（只消耗一次出牌动作，惩罚就是那一拍 tempo），**少数带额外代价**（例：耗 1 mana 才能打出，或打出时削自己 1 点道念），由内容侧逐条目书写。

**推论：`Affliction` 的校验规则要放宽。** 不能硬性要求「mana 费用必须为 0」——那会把带代价的业障挡在门外。改为：**`Affliction` 允许有 mana 费用与负向效果，但不得有任何正面效果**。「不得有正面效果」难以机械校验（效果流水线的正负要看具体内容），故这条落为**内容侧纪律 + `PushWarning` 级的软检查**（例：业障若带产道念的效果 → 警告），而非启动即失败的硬校验。

**推论 ②：业障因此获得了一条强度轴。** 「通常零代价、少数带代价」意味着业障可以按惩罚烈度分层——轻度业障只偷一拍节奏，重度业障在 mana 紧张的回合造成真两难。这让它有资格作为**高风险事件的负向奖励条目**出现在不同厚度的档位上，而不是一个只有单一强度的惩罚。

### 八、次类型（secondary card type）

`[已由用户裁决 · 用户指定存在，细节日后定]`

**每个主类型下都会有次类型**，对位 MTG 的 subtype（Creature — Goblin / Enchantment — Aura / Sorcery — Arcane）。已能确定的两点：

- **埋伏是阵法的次类型**（第六节）。
- 次类型是**内容侧可扩展的**，故建议**不用 C# 枚举**，而用**稳定字符串 id + 一份次类型注册表**（`.tres`），使新增一个次类型 = 新增一个 `.tres`，不改代码。这直接对应 `data-resource-rules.md` 的「让内容保持可加性」。

**推论：次类型必须能被效果引用**（「所有『灵兽』获得 +1」这类牌是次类型存在的主要理由），故次类型 id 要进入效果的目标筛选条件——它不是纯展示标签。

| 结束阶段 | `end step` | MTG 的 end step 之后还有 cleanup step（弃到手牌上限）；**本作无 cleanup、无弃牌机制**，结束阶段只做「触发『回合结束时』→ 清理回合内状态」 |
| 结算 | `resolve` | 同义，**专指栈上对象的结算**；战斗收口那处已改称「收口」 |
| 收口 | `settle` | 非 MTG 词。战斗打满后的胜负判定 → 奖励计算 → lifeTotal 扣减这一段 |
| 触发 | `trigger` | 本作的触发时点**全部有归属方**，**但监听方可跨归属方**；命中后压栈者一律是 StackManager |
| 静止式异能 | `static ability` | 同义。不入栈、载体在场即生效 |
| 启动式异能 | `activated ability` | MTG 可在任意优先权窗口启动；**本作限定为自己回合的行动阶段、栈为空时**——与出牌同窗口，不构成交互 |
| 触发式异能 | `triggered ability` | 同义 |
| 永久物 | `permanent` | MTG 的 permanent = 战场上的对象（区的成员资格）；**本作的永久物是战场条目的子集**——战场上同时住着非永久的持续状态 |
| 卡牌类型 | `CardType` | 五值枚举，见下 |
| 次类型 | `card subtype` | 对位 MTG 的 subtype；本作以**稳定字符串 id + 注册表**表达，内容侧可加，不是 C# 枚举 |
| 法术 | `Sorcery` | 一次性牌的通名。**因无 Instant，本作的「法术」不含速度含义** |
| 灵宠 | `Creature` | **不互相攻击**（无战斗步骤、无伤害模型）；靠异能产出道念 |
| 阵法 | `Enchantment` | 合并了 MTG 的 Enchantment 与 Artifact（本作无「针对面」之分） |
| 埋伏 | `Ambush`（暂定标识符） | 阵法的次类型 = 炉石的「奥秘」：面朝下布置，在**对手回合**触发后进弃牌堆 |
| 道具（卡牌类型） | `Item` | **非 MTG 概念**。法宝 / 古宝在战斗内的卡牌形态；不洗进卡组、存于储物袋 |
| 储物袋 | `magic pack` | **非 MTG 概念，且不是战斗概念**。角色的道具容器，存放持有的全部法宝 / 古宝，跨战斗内外存在，容量上限 **99**（≈ 不设限，仅防溢出）。战斗从中筛出 `UsableScene` 含 `InCombat` 的部分呈现；**敌人无储物袋但同样持有道具** |
| 神通 / 法则（卡牌类型） | `Power` | 对位 MTG 的**徽记（emblem）**：几乎不可被交互、一旦存在就一直存在。**出入**：MTG 的徽记在指挥区且不是永久物；**本作的 `Power` 就落在战场上、是永久物**，只是带保护标记不可被针对。且它不由效果产生，而是**开局按持有列表入场** |
| 业障 | `Affliction` | 对位 StS 的 Curse，但**可被打出**（打出无正面效果、只是送自己进弃牌堆），故不产生永久堵塞 |

### `CardType` 枚举

public enum CardType
{
    Sorcery     = 0, // 法术：一次性，结算后进弃牌堆

    Enchantment = 2, // 阵法：结算后作为非实体永久物落战场（埋伏为其次类型）

### 战场条目的二分

| | 永久物 · 常规 | 永久物 · 受保护（`Power`） | 非永久条目（持续状态） |
|---|---|---|---|
| 来源 | 灵宠 / 阵法结算后落场 | **开局按持有列表入场** | 效果施加的临时状态 |
| 生命周期 | 无限期，直到被移除或战斗结束 | **战斗结束才消失** | 带标记：回合内 / 跨回合 / 持续 N 回合 |
| 结束阶段清理 | **永不清理** | **永不清理** | 清理标记为「回合内」的那些 |
| 可否被针对 / 移除 | 可 | **否**（`IsProtected = true`，除非显式置 false） | 待定 |

### 加载时校验规则（坏数据启动即失败）

| 规则 | 违反时 |
|---|---|
| `CardType` 必填 | `PushError`，带 `Id` 与 `.tres` 路径 |
| `Sorcery` 不得带 `Static` / `Activated` 异能 | `PushError`——不留场，无生效载体 |
| `Affliction` 不得带任何异能 | `PushError`——打出的唯一作用是送自己进弃牌堆 |
| `Affliction` **允许**有 mana 费用与负向效果，但不得有正面效果 | `PushWarning`（软检查，例：业障带产道念的效果 → 警告）——正负难以机械判定，主要靠内容侧纪律 |
| `ItemData` / `PowerData` 的 `UsableScene` 必填 | `PushError`——默认值会让内容侧漏填的东西悄悄进战斗 |
| `PowerData` 中 `Scope == Player` 且 `UsableScene` 含 `InCombat` 的占比 ≤ 1/5 | `PushWarning` + 报出当前比例——**稀缺性纪律的机械化检查**，让越界在启动时被看见 |
| `Creature` / `Enchantment` 至少带一个异能 | `PushWarning`——不带异能的永久物是空条目，多半漏填 |
| `AbilityKind == Activated` 时 `ActivationCost` 非空 | `PushError`——零费启动式异能会造成无限循环 |
| `AbilityKind == Triggered` 时 `TriggerWhen` 非空 | `PushError` |
| `Subtypes` 中每个 id 须在次类型注册表中存在 | `PushError`，报出悬空 id |
| 次类型须与主类型匹配（如「埋伏」只能挂 `Enchantment`） | `PushError` |
| `ItemData.Scope == Player` 时 `Charges > 0` | `PushError`——古宝定义上有使用次数限制 |
| `PowerData` 不得带 mana 费用字段 | 编译期即排除（该字段不存在于 `PowerData`） |
| `PowerData` 至少带一个异能 | `PushError`——不带异能的 `Power` 在战斗内是纯空条目，与 capability flag / modifier pipeline 形态的法则混淆了 |
| `PowerData.IsProtected == false` 的条目须显式登记 | `PushWarning`——可被移除的 `Power` 是规则例外，出现即应被看见 |

- **`terminology.md`**：删 1 条、改 4 条、增 19 条。

- **`ux/combat-ux.md`**：竖屏战斗界面新增**储物袋**（建议收起为角标 + 抽屉面板）、**埋伏标记**（对手场上「有一张埋伏」的指示）与**神通 / 法则条**（建议贴在己方战场区边缘的一排小图标，**长按查看详情**——`ui-input-rules.md` 禁止 hover-only 可供性）；`Power` 因不可交互，视觉权重应低于常规永久物，但**带启动式异能的 `Power` 例外**，它需要可点击的启动入口。卡面需呈现类型标识（建议卡框色 + 类型角标，不用纯文字——竖屏卡面横向空间紧）。
- **`systems/adventure-event/combat/` 与 `EnemyTemplate`（`future-event-service.md`）**：`EnemyTemplate` 需新增 **item 持有列表** 与 **power 持有列表** 两个字段（敌人无储物袋，道具直接挂模板）；埋伏是否进入敌人卡池需一并陈述。**这也给「物化时充实 / 改写敌人的规则」那条待答问题多了两个可调旋钮**——赋级时除了改样本卡组，还能增删 item / power。
- **存档 schema**：`CardType` / `Subtypes` 是静态字段**不进存档**（存档只记 `Id`），**无迁移**。储物袋本身是角色档案的一部分（照旧随 CharacterProfile 落存档，上限 99 使其体积可控）；但**战斗内的道具运行态**（本场已用掉哪些、剩余次数）**须进决策点存档**——这是新增的一块可序列化状态，落在既有的「战场条目须可序列化」这条未答问题旁边，是它的邻居而非它。**`Power` 的入场本身不必存档**（可由两个 Profile 的持有列表 + `status` 确定性重建），但**它的战斗内运行态必须存**（例：「本场已触发 3 次」这类计数器）。
- **参战方组装流程**：`RunCombatAsync` 的开场多一步——读 CharacterProfile 的神通列表 **与 PlayerProfile 的法则列表**，按 `status` 过滤后注册进战场。**这是 combat-service 第一次需要读 PlayerProfile**（此前它只读 CharacterProfile），`combat-service.md` 的「与其他服务的关系」示意图需相应补线。
- **对 `attemptIndex` / 决策点粒度**：埋伏牌与道具都不改变决策点的候选位置，二者仍落在「回合 / 出牌」这一级。
- **不影响**：道念模型、意图分档阈值、回合数、奖励结构、`CombatResult` 契约的字段构成。

## 备选方案（已考虑并否决）

- **`sorcery speed` 保留并定名** — 否决：单一取值的维度不是维度，保留会制造「存在第二种时机」的错觉。
- **三步沿用「起始步 / 主阶段 / 结束步」** — 否决：中文两「步」夹一「阶段」不齐整；`main` 的对照系不存在。
- **卡牌类型按「攻击 / 防御 / 增益 / 特殊」分（跟随意图类别）** — 否决：意图类别是**敌人行为的展示分类**，与卡牌的**结算生命周期**正交。共用一套枚举会导致「既产道念又削对方道念的牌属于哪类」这种无解归类，且意图类别一改就波及卡牌数据。
- **Artifact 独立成第六类** — 否决：MTG 里 Artifact 与 Enchantment 的差别只是可被什么牌针对；本作的「器物」语义已由**法宝 / 古宝（`Item`）** 承载，且它走的是储物袋而非卡组，比再开一个卡组内类型更贴合「道具」的直觉。
- **道具照旧洗进卡组**（如 StS 的遗物之外还有装备牌） — 否决：用户已定不洗进卡组。补一条支持理由：道具若进卡组，会与抽牌确定性、手牌上限、洗牌 RNG 全部纠缠；独立成区后**抽牌堆的 seeded 确定性完全不受道具影响**，是明显更干净的切法。
- **引入放逐区（exile）** — 否决：现有位置（卡组 / 手牌 / 弃牌堆 + 栈 + 战场 + 本场可用道具）已能表达全部已定案的流转，业障有了「打出即进弃牌堆」的出口后更不需要放逐。
- **把储物袋当作战斗内的一个区** — 否决（用户已更正）：储物袋是**角色的道具容器**，跨战斗内外存在，且**敌人根本没有储物袋却同样有道具**。战斗里出现的是「本场可用道具」这一筛选视图，把容器与视图混为一谈会让敌人侧无处安放。
- **为 `Power` 引入指挥区（command zone），照搬 MTG 徽记的落点** — 否决：本作已有六处位置，为一类**不可交互、不移动、只是持续生效**的条目再开第七处，收益不抵竖屏 UI 与存档形态的成本。08-03 已定案「把神通注册进战场」，`Power` 落在战场上带一个保护标记，是改动最小且已被既有设计接受的形态。
- **借 `emblem` 并定中文名「徽记」作 `Power` 的类型通名** — 否决：08-03 已定「`power` 不再有统一中文通译，两层各自定名（神通 / 法则）」，再造一个通名会与该决策冲突；类型名照 `Item` 的处理方式并列书写「神通 / 法则」即可，代码侧 `CardType.Power` 承担统一性。
- **`Power` 完全不可被交互（`IsProtected` 硬编码为 true）** — 否决：用户的措辞是「**rarely** be interacted」而非 never。留一个显式后门（默认 true、可置 false）成本几乎为零，却为「压制对手法则」这类高阶敌人特性保留了设计空间；硬编码则把这条路彻底封死。
- **埋伏牌独立成第六个主类型** — 否决：它的一切规则（留场、永久物、承载触发式异能）都与阵法相同，唯一差别是**面朝下 + 触发后进弃牌堆**，这正是次类型该承担的粒度。
- **业障不可打出、靠结束阶段自动移除** — 否决（用户已选定「可打出」方案）：自动移除要给结束阶段加一条清理，与「结束阶段只做触发 + 清理回合内状态」的定案冲突；且「可打出」把惩罚统一为 tempo，与既有的满手代价模型同调。

## 与既有决策的张力

1. ~~**「道具随时可用」与「交互 / 优先权整体移除」**~~ —— **已消解（裁决为「仅自己回合」）。** 道具的使用窗口与出牌 / 启动式异能完全相同，不构成 instant 通道，08-02b 的定案毫发无损。**本作至此没有任何一条机制能让一方在对手回合主动行动**——唯一能在对手回合发生作用的东西是**预先布置的埋伏牌**（被动触发，非主动决策），这条边界现在是完整且自洽的。

2. **`sorcery speed` 是 08-02b handoff 的已定案表述**（写在三份文档里）。本方案删除该词——**但机制原样保留**，改的是措辞不是规则。

6. **法则的战斗内强度：允许影响战斗，但极其稀缺（已裁决 · 承重）。** 法则是**账号级、跨轮回持有、默认开启、不可被针对**的东西，作为 `Power` 入场后它能挂触发器、带启动式异能——账号级内容由此进入战斗玩法层。**裁决为不设规则禁令**：premium bundle 是花钱买的，理应让体验更好，而**战斗是核心体验的关键一环**，把法则整类挡在战斗之外等于承认付费买不到核心体验的改善。**代价由稀缺性而非规则来承担。**

   **可执行形态（否则「very rarely」会在内容阶段失效）：**
   - **配额纪律：** `UsableScene` 含 `InCombat` 的法则应是**明确的少数**（建议 **≤ 1/5** 的法则条目）。这是可机械检查的——内容加载时统计比例，超标 `PushWarning`，让越界在启动时被看见，而不是靠人记得。
   - **强度定位：** 战斗内的法则偏向**体验改善与容错**（信息、便利、少量兜底），而非**直接抬高道念产出上限**。允许影响胜负，但不应成为胜负的主要来源。已定名的**探查**（付出代价换取当回合敌人意图）正是这类能力的样板。
   - **付费战斗价值主要由古宝承载。** premium bundle 给的是**随机 1 法则 + 随机 2 古宝**，而古宝**有使用次数限制**——次数天然是节流阀，让付费的战斗收益是「关键时刻多几次转圜」而非「永久变强」。**法则保持稀缺、古宝承担主要付费战斗价值**，这个分工同时满足「花钱体验更好」与「不滑向 pay-to-win」，且不需要任何新机制。
   - **仍需留意：** 法则**不可被针对**且**跨轮回永久持有**，故同一条战斗内法则的价值会随账号年龄单调累积；平衡时应按「老账号全开」而非「新账号裸奔」来校准难度曲线。这条归 `systems/balance.md`。

7. **法宝 / 古宝的定义面被扩宽了。** 它们原本是「事件中使用的道具」，现在同时是「战斗内的卡牌类型」。`systems/character-profile/item/` 与 `player-profile/player-item/` 两份文档需要相应扩写——**这不是推翻，是补全**，**已裁决**：分「战斗内可用 / 战斗外可用 / 两者皆可」三档（`UsableScene`），因为有些道具的效果在战斗里没有意义。另需在两份文档中写明**储物袋是道具容器而非战斗概念**（上限 99 ≈ 不设限），战斗里出现的只是它的筛选视图。
