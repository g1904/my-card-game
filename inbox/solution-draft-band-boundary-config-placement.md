# 方案草稿 — 带边界的配置落点

## 问题

敌人物化赋级的合法区间是角色当前等级的对称带 `[L−2, L+2]`（三章统一，在全局序 1–22 上截断）。**这组边界值住在哪里**——一份平衡资源 `.tres`，还是 future-event-service 自己的服务配置——从 08-06b 起悬着。

08-15d 的意图机制整条移除已**砍掉这个问题的一半**：原本与它捆绑的「意图阈值三处门槛是否同住一份资源」以及「下界不得使 `diff` 门槛不可达」这类一致性检查，**随机制作废，不要复活**。剩下的是一个轻问题：**落点 + 形态 + 加载期校验**。

## 约束（来自既有设计）

- **`balance.md` 已经表过一次态**：「**带边界是内容侧可调数值**，随内容 overlay 可调。代码侧只读『**当前篇章的带**』这一个概念，**不为分章写分支**（当前三章取同一组值）。」这句话既定了「可调」，也定了读取形态。
- **`±2` 是无例外的硬规则——赋级函数不接受任何区间覆盖参数。** → `systems/enemies/_index.md`
- **带内分布权重表已定为平衡资源里的一张表**（`−2 / −1 / 0 / +1 / +2` = 5% / 20% / 40% / 25% / 10%），配套**截断重分配**、**乘性调制修正**（只改权重不改支撑集）、**批内去重**。→ `systems/balance.md`
- **全库既有落点一律是平衡资源 `.tres`**，且逐条都有先例：`CombatRulesData`（起手 / 抽牌 / 手牌上限）· `TravelFullFanoutChance = 0.80` · 篇章重试上限的两行 · `rewardPerMomentum` 单价表 · `ExperienceGrade` / `HiddenStatGrade` 映射表 · `itemPowerRatio` · `MaxConcurrentSideArcs`。→ `systems/balance.md`
- **`TravelFullFanoutChance` 的收口范式**：住平衡资源、可线上调、**只有一份全局值，不接受任何按剧情线 / location 的覆盖参数**——「不给这个口子，就不存在『谁有权用它』」，且 **PlotManager 不得推拉它**。→ `systems/adventure-event/travel/_index.md`、`systems/services/future-event-service.md`
- **平衡表属本地内容层**（`res://` 基线 + overlay 热更），**被存档引用、需启动期强校验、只改不增**。→ `systems/architecture.md`、`decisions/ADR-0007`、`systems/services/content-service.md`
- **篇章数是固定的游戏结构，不用字典 / 索引数组**——`chapterRetry` 与三个隐藏属性 band 都落成**具名字段**。→ `systems/character-profile/_index.md`
- **可调数值不硬编码在系统逻辑里，系统从数据中读取。** → `.claude/rules/data-resource-rules.md`

## 建议方案

### 1. 落点 = 平衡资源。「服务配置」这一选项在本库里不存在
`[既有推演]`

**本库没有「服务配置」这一层。** 七个服务里没有任何一个持有自己的可调数值配置面——凡是可调的数字，无一例外住在平衡资源 `.tres`（上方约束里列了 7 处先例，没有反例）。把带边界做成 future-event-service 的 `[Export]` 字段或场景导出值，会：

- **绕开 overlay 热更通道**——`[Export]` 值随场景 / 代码走，改一个数字要发版，而带边界正是「实测后要调」的头号候选（`balance.md` 已注明权重是纯经验初值、待 ch1 数值标杆专场回归校准）；
- **绕开启动期强校验**——平衡表在 ContentRegistry 加载时全量校验、坏数据大声失败；服务导出字段没有这条闸；
- **制造第二种「可调数值住哪」的答案**，而这正是 `.claude/rules/data-resource-rules.md` 与 `balance.md`「平衡数值集中管理」要收口的东西。

**故本题的正面答案是：平衡资源。** 它不是一个取向选择，而是既有约定的直接后果——之所以在 08-06b 显得是个开放问题，是因为当时它与「意图阈值三处门槛」捆在一起问，而那一半已经作废。

### 2. 与带内分布权重表**同住一份资源**，不分家（本草稿的实质建议）
`[既有推演]`

带边界与权重表是**同一张表的两个部分**：权重表的**支撑集就是带宽**。`−2 / −1 / 0 / +1 / +2` 五个档位不是五个独立数字，而是「从下界到上界逐档」的枚举。分放两处会立刻产生一条**跨文件不变式**：

> 权重表的档数必须 == `Upper − Lower + 1`，且档位顺序必须与带一一对应。

跨两份资源的不变式要么没人校验，要么校验代码得同时加载两份并猜它们的对应关系——而这条不变式一旦破了，赋级会静默取到错位的权重（下界档吃到了上界档的 10%），**是那种能上线、线上分布悄悄不对却不崩的洞**。放同一份资源里，它退化为一次本地断言。

建议形态：**新增一份 `EnemyLevelingData : Resource`**（名称待用户确认，见「仍需用户决定」第 2 题），承载「敌人赋级」这一件事的全部旋钮：三章各一行的带边界 + 该行对应的权重数组。

**不并入 `CombatRulesData`**：那一份的消费者是 combat-service（起手 / 抽牌 / 手牌上限，且可被 `EncounterSpec` 可空覆写），而赋级发生在 **future-event-service 的物化阶段、战斗开始之前**，且**明确不接受任何覆写参数**。两者消费者不同、覆写纪律相反，合成一份会让「哪些字段可被 `EncounterSpec` 覆写」变成需要逐字段记忆的事。

### 3. 形态 = 三章各一行的具名字段，当前三行同值
`[既有推演]`

`balance.md` 那句「代码侧只读『**当前篇章的带**』这一个概念，不为分章写分支」已经预设了**按篇章取行**的形态——它说的是「业务逻辑里不写 `if (chapter == 1)`」，不是「只存一个全局值」。故：

- **三行**，沿用 `chapterRetry` / 三个隐藏属性 band 的既有判据（**篇章数是固定的游戏结构，用具名字段而非字典 / 索引数组**）；
- 读取收敛成**一次取值**（`BandFor(chapter)`），调用侧看到的仍是「当前篇章的带」这一个概念——这与「不为分章写分支」完全自洽；
- **当前三行取同值 `(−2, +2)`**，权重行同为 `5 / 20 / 40 / 25 / 10`。三行同值不是冗余：它是「三章统一」这条**当前**取值，而非结构性约束（08-06 曾定过 ch1 非对称的 `[−4, +2]`，08-06d 才回退——留三行等于把那次回退的可逆性保留在数据侧，而不是焊进代码）。

### 4. 写权收口：只有内容侧能改它，PlotManager 不得推拉
`[既有推演]`

沿用 `TravelFullFanoutChance` 的收口范式，一字不改地适用：

- **带边界只有一份权威**（这份资源），**赋级函数不接受任何区间覆盖参数**——既定条款，本方案不松动；
- **PlotManager 只能施加乘性权重调制**（既定：「只改权重不改支撑集」），**不得改带边界**。这条须明写：调制改支撑集就等于给剧本开了一个绕过 `±2` 硬规则的后门，而 `±2` 的数值安全性推导（「一次惨败打穿耐久」由规则层封住）正建立在支撑集封闭之上；
- **事件类型不修正**（`Practice` / `Standard` 共用同一张表，`Finale` 不掷骰）——既定，不变。

### 5. 加载期校验（五条）
`[既有推演]`

| 违规 | 语义 | 处置 |
|---|---|---|
| 某章 `Lower > 0` 或 `Upper < 0`（带不含 `diff = 0`） | 「多数同级、偶有硬仗」的众数档不存在，与既定分布正面冲突 | `PushError` + 抛，带章号 |
| 某章 `Lower > Upper` | 空带，物化取不出任何等级 | `PushError` + 抛 |
| 某章权重数组长度 ≠ `Upper − Lower + 1` | 档位与带宽错位，**能上线、线上分布静默不对** | `PushError` + 抛，带章号与两个长度 |
| 某章权重和 ≠ 1（或百分数和 ≠ 100，按最终取值单位定） | 抽取实现分歧 | `PushError` + 抛 |
| 某章权重含负值 | 不可能态 | `PushError` + 抛 |

- **不再设「下界不得使 `diff` 门槛不可达」这条一致性检查**——它的被检查对象（意图揭示的 `diff` 门槛）已随意图机制整条移除。**这一点必须写进文档**，否则它会作为「曾经提过的校验」被日后实现重新捡起来，去检查一个不存在的东西。
- **截断重分配不进校验**：全局序 1–22 的截断是**运行期**行为（角色 L1 时 `−2 / −1` 落空、权重按比例并入剩余档），与加载期的「权重和 = 1」不冲突——两者作用在不同时刻，须写明以免实现者以为二者矛盾。

## 具体形态（可 derive 的落地面）

```csharp
[GlobalClass]
public partial class EnemyLevelingData : Resource   // 名称待确认，见「仍需用户决定」第 2 题
{
    // 三章各一行；篇章数是固定的游戏结构 → 具名字段，不用字典 / 索引数组
    [Export] public LevelBand Chapter1 { get; set; }
    [Export] public LevelBand Chapter2 { get; set; }
    [Export] public LevelBand Chapter3 { get; set; }
}

[GlobalClass]
public partial class LevelBand : Resource            // 内嵌类型一律 Resource 派生（[Export] 的取值域约束）
{
    [Export] public int     Lower   { get; set; } = -2;   // 相对角色等级的下界（含），须 <= 0
    [Export] public int     Upper   { get; set; } = +2;   // 上界（含），须 >= 0
    [Export] public float[] Weights { get; set; }         // 从 Lower 到 Upper 逐档；长度须 == Upper - Lower + 1，和为 1
}
```

初值（三章同值，与 `balance.md` 现表一致）：

| 篇章 | `Lower` | `Upper` | `Weights`（`−2 → +2`） |
|---|---|---|---|
| ch1 炼气 | −2 | +2 | 0.05 / 0.20 / 0.40 / 0.25 / 0.10 |
| ch2 筑基 | −2 | +2 | 0.05 / 0.20 / 0.40 / 0.25 / 0.10 |
| ch3 金丹 | −2 | +2 | 0.05 / 0.20 / 0.40 / 0.25 / 0.10 |

读取面（future-event-service 物化赋级）：

```
LevelBand BandFor(int chapter)         // 一次取值，调用侧只见「当前篇章的带」
level = Clamp(characterLevel + WeightedPick(band, mapStream), 1, 22)   // 截断后按比例重分配落空档权重
```

## 后果

- **平衡资源新增一份**（或既有平衡资源新增一节，视第 2 题的答案），`balance.md` 的赋级带条目补一句落点、删掉待决问题那行。
- **`future-event-service.md` 的物化伪码补一行读取面**（`BandFor(chapter)`），并写下「PlotManager 不得改带边界，只能乘性调制权重」这条写权收口。
- **无存档影响**：带边界是内容侧数值，赋级结果 `EnemyInstance.Level` 在物化时即定稿并随 `EventOption` 落存档；**线上调带边界不影响已定稿的实例**（与「`BaseReward` 随物化定稿」同款）。
- **`enemies/_index.md`「赋级带的接受面」**里「带边界是内容侧可调数值」那句获得确切落点，可从「可调」升级为「住在 X」。
- **ch1 数值标杆专场的回归对象 +1**（权重与带宽一并回归）。

## 备选方案（已考虑并否决）

- **住 future-event-service 的服务配置 / `[Export]` 字段** —— 否决三条：绕开 overlay 热更、绕开启动期强校验、在本库制造第二种「可调数值住哪」的答案（见第 1 条）。
- **只存一个全局值、不分章** —— 否决：与 `balance.md` 既有表述「三章的带边界」「代码侧只读**当前篇章的带**」不符，且会把 08-06 → 08-06d 那次「分章 → 统一」的回退焊进结构，日后若要再分章就得改 schema 而非改数据。
- **并入 `CombatRulesData`** —— 否决：消费者不同（物化 vs 战斗）、覆写纪律相反（不接受覆写 vs `EncounterSpec` 可空覆写），合并会让覆写规则变成逐字段记忆。
- **带边界与权重表分放两份资源** —— 否决：制造一条无人校验的跨文件不变式（档数 == 带宽），破了就静默错位（第 2 条）。
- **允许剧本 / 事件类型覆写带边界** —— 否决：既定「赋级函数不接受任何区间覆盖参数」，且 `±2` 的数值安全性推导建立在支撑集封闭之上。

## 与既有决策的张力

**无。** 本方案是既有约定（平衡数值集中管理 · 数据资源规则 · `TravelFullFanoutChance` 收口范式 · `chapterRetry` 的具名字段判据）的直接延伸，不要求任何既有决策松动。

唯一需要**显式作废**的是一条已经失效的旧要求：08-06b 提出的「下界不得使 `diff` 门槛不可达」一致性检查——它的检查对象随意图机制移除而消失，本方案主张在文档里写明「不设此校验」，而不是沉默地不实现（沉默会让它日后被重新捡起）。

## 前置依赖

**无阻断性前置。** 落点、形态与校验全部可由既有决策推出。

带边界与权重的**取值**待 ch1 数值标杆专场回归校准（`balance.md` 已注明权重是纯经验初值），但**结构不依赖取值**——这正是把它落进可线上调的平衡资源的理由。

1. **三章各一行 vs 单一全局值？**（轻）
   - **A（推荐）：三章各一行具名字段，当前三行同值 `(−2, +2)`。** 理由：与 `balance.md` 现有表述「三章的带边界」「只读当前篇章的带」一致；把 08-06d 那次回退的可逆性留在数据侧。代价：内容侧要维护三行同值的重复。
   - B：单一全局值，沿用 `TravelFullFanoutChance`「只有一份全局值、不接受任何覆盖」的最强收口。更简洁，但要同步改写 `balance.md` 那两句表述，且日后再分章需改 schema。
2. **资源命名与切分：新开一份 `EnemyLevelingData`，还是并进既有平衡资源的一节？**（轻）
   - **A（推荐）：新开一份 `EnemyLevelingData`**（带边界 + 权重表同住）。理由：它有独立且封闭的消费者（future-event-service 的物化赋级），且带边界与权重必须同资源（第 2 条）。名称备选：`LevelBandData` / `EncounterLevelingData`。
   - B：作为既有平衡资源（`balance.md` 所述的那一族 `.tres`）里的一节。少一个文件，但「带边界 + 权重必须同住」这条约束会依赖编写纪律而非文件边界。
3. **权重的取值单位：归一化小数（和为 1）还是百分数整数（和为 100）？**（极轻）推荐**归一化小数**——运行期的截断重分配本就要做归一化，用小数少一次单位换算；`balance.md` 现表以百分数呈现，那是**呈现形态**，与存储单位不必一致（呈现时乘 100 即可）。
