# ② 账号与合规（路线已定，仅剩落地）

> 路线权威：`game-design-documents/decisions/ADR-0003-online-cloud-authority.md`（强制在线 · 云端权威 · 重账号，已删游客态）。
> 客户端侧门面：`game-design-documents/systems/services/account-service.md`。

- **账号系统自建还是接第三方。** 重账号意味着注册 / 登录 / 找回 / 多端绑定全链路都要有；自建与接入渠道账号（应用商店 / 社交登录）的取舍未定。与 `06-platform-stack.md` 的托管形态耦合。

- **合规落地。** PIPL、实名、防沉迷、渠道审核、账号注销、数据导出——重账号 + 已删游客态 + 国内渠道意味着这些必须正面处理。哪些能力必须在首次上线前具备、哪些可后置，未分级。**边界已定（2026-08-14）**：合规拦截的分支形态可自由决定，但**落点不得选在 `/v1/profile/*`**——同步是后台行为，在它上面返回合规拦截会让客户端只剩「待同步 N 永远不减」或「丢进度」两条路（`contracts/profile-sync.md` §11，pillar #4）。

- **多设备并发登录的裁决语义。** 同账号在两台设备同时在线时，云端权威如何裁决（后登录挤下线？拒绝？只让先到的写入生效？）。它直接决定 `sync-service` 冲突分支的实际触发频率。**现在还多卡着两处报文取值**（`contracts/auth.md` 已成文，形状已定、只差取值）：`auth.session_revoked.detail.reasonKey` 的取值集合、以及 `signin` 携带的 `deviceId` 如何参与裁决。

- **风控与滥用面。** 客户端执行、后端可离线复算的掷骰意味着存在改包伪造收益的通道。**处置口径已定（2026-08-14）**：复算不一致 → **接受写入 + 打一条结构化风控事件，不拒绝、不改写**（`contracts/profile-sync.md` §7a）；且**有一条已知的残留通道**——`lastEffectiveChance` 后端无法验真，「篡改客户端把生效概率写成 10000」只能由风控接住，不被复算接住。**仍待定**：是否建风控系统、风控事件的字段与落地形态、累计频次到什么程度算异常、异常账号如何处置（观察 / 限制 / 封禁）。与 `06` 的可观测性口径耦合。
