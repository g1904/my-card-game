# ⑦ 内部运营工具（人工处置面）

> 面向**内部运营人员**而非玩家的工具面：风控与内容审核的人工处置台、客服侧的账号查询与工单入口。
> 它与 `operations/` 的区别是「谁在用」——`operations/` 记的是系统自己怎么跑（定时任务、探针、发布流水线），
> 本片记的是**人坐在什么界面上做处置**。权威落点尚未确定，这正是本片的第一条待答项要裁决的东西。
>
> 本面此前无分片：昵称复核、风控工单、账号处置阶梯的**机制侧**已分别落在 `operations/moderation.md` 与
> `systems/account.md`，但它们一致地停在「入队 / 出工单」这一步，人工那一端的形态全库零承载。

- **昵称人工复核台的形态。** `nickname_review` 表已定形态（状态机 `Pending → Claimed → Decided` · 条件 `UPDATE` 取租约 · 租约初值 30 分钟 · 同一账号在办至多一条 · 终态按批清理），
  但**谁来复核、经什么界面复核，全库未定**：
  - 复核员是运营岗、客服岗还是研发轮值？是否需要按渠道 / 语言分派？
  - 界面是内部后台 Web 页、既有工单系统的一个视图，还是首版就用一条运维脚本 + 人工读写数据库？
  - **`claimed_by` 的取值从哪来** —— 它是内部账号体系的标识符，而本库至今没有任何「内部人员身份」的概念（`account` 表承载的是玩家）。
    这一条最承重：`claimed_by` 是租约归属与「迟到提交被拒」这条不变式的键，取值域定不下来，
    `nickname_review` 的领取语义就只在纸面上成立。

  它**不阻断**任何已落笔的表形态与服务端保证（M6–M8 断言的是数据库侧行为，与界面无关），
  但**阻断「复核这条链路端到端可用」**——首版若要启用词表复核级，这一条必须先有答案。
  相关机制：`operations/moderation.md`「四张台账的存储形态」· `systems/account.md` 昵称判定链 N8。

- **风控工单的落点同源。** `operations/moderation.md` 已定「自动化止于工单、账号 `status` 的任何变更须人工确认」（`decisions/ADR-0027-risk-control-human-in-the-loop.md`），
  但工单进哪个系统、谁看、处置动作经什么面写回 `account.status`，与上一条是同一个未定的内部工具面。
  两条宜一并裁决，不要各定一套内部身份。
