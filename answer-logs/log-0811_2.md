**`manifestSchema` 的版本化**（原在 `open-questions/05-service-contracts.md` 与 `systems/services/content-service.md` 的待决问题）
→ **已答结。** 三版本号分工：`appVersion`（客户端二进制）· `contentVersion`（内容版本，严格单调递增，存档与 push 信封携带）· `manifestSchema`（manifest 结构自身的版本）。客户端内置「支持的 `manifestSchema` 集合」，**两种情形分开**：支持但本地 overlay 按旧 schema 落地 → 整包全量重下；**不受支持（高于内置集合）→ 跳过本次更新、照常用现有 overlay / 基线**（与断网降级同构）。归档去向：`systems/services/content-service.md`「增量下载：文件级事务」。

**`ContentEnabled` 的粒度是否够用**（原在 `open-questions/deferred-content.md`）
→ **已答结：分桶规则哪也不放在客户端。** `GET /v1/content/flags` 需鉴权、按账号解析，只下发**结果**（`disabledIds`）；客户端始终只看到「这些 `Id` 现在不进抽取池」，永远不知道分桶规则存在。**连带解除 `DrawPool<T>` 的唯一依赖**——构造签名不必变成 `AllEnabled(bucketContext)` 一类，其第二阶段排期的第二条理由随之消失。归档去向：`systems/services/content-service.md`「flags：`ContentEnabled` 的第三层」。
