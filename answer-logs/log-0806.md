**⚠ `±2` 赋级带与意图揭示阈值的算术冲突（承重 · 08-05 挂起）** → **答结，收口取向 = 调赋级带、不调阈值。** 08-05 列出的三条候选（调阈值 / 接受退化 / 放宽下界）**均未采用**；实际方案是两条并行的改动：**① ch1 赋级带放宽为 `±4`，ch2 · ch3 仍 `±2`**；**② 新增「降阶 = 碾压」硬门**（敌人境界低于角色 ⇒ 一律完整意图，与既有的「越阶 ⇒ 完全无信息」对称）。三处 `diff` 门槛**原样保留**，故「完整意图 = 碾压专属」的定位不必重新定义。
**推论：** ch1 三档全部恢复可达（`−4~−3` 完整 / `−2~+2` 仅类别 / `+3~+4` 无信息）；ch2 · ch3 的碾压档由降阶硬门成立（篇章开头刚突破进新境界时，`−2` 正好探进下一层境界）；**ch1 之所以单独放宽，是因为炼气是最低境界、拿不到降阶硬门**——分档不是随意的；碾压档自动向篇章头部集中、越阶黑箱向尾部集中，**一个篇章因此天然有一条「开局看得清 → 收尾看不清」的信息曲线**；ch1 的越阶范围从末两级扩到末四级。
**代价（新增待答）：** `+4` 那一侧把 ch1 最坏开局落差从 9 抬回 17，超出炼气 `lifeTotal` 10/10——`±2` 当初正是为封住这条而立的。
（归档去向：`systems/balance.md`、`systems/services/future-event-service.md`、`systems/adventure-event/combat/_index.md`、`ux/combat-ux.md`）

**「1% 的游戏场景」的分母口径（08-05 新增 · 待确认）** → **答结 = 全部 event，且失去法则不限于战斗。** 分母是玩家经历的**全部 AdventureEvent（九类）**，不只战斗遭遇。
**连带带出一条此前没有的结构：移除 `Power` 有两条通道，性质完全不同**——**战斗内效果侧的 `IgnoresProtection`** 只作用于**本场**（战场条目被移除，Profile 不动）；**事件 outcome / reward 侧的负向条目**是**持久的**（走 `ProfileChangeSpec` → `TryApply`，角色 / 账号真的失去它）。此前只设计了第一条。第二条不需要新机制（与「负向奖励塞业障进卡组」同类），但需要一个新的 element 形态。
**其余推论：** `Power` 的「受保护」语义要**分层表述**——`IsProtected` 管战场上的可针对性，持有权层面的保护是另一回事；1% 仍是出现频次口径、仍无法机械化校验，但**校验面从战斗内容扩到整个事件池**，落点由 combat 侧移到 future-event-service 的物化与加权侧；量级上 ≈ 一个篇章遇上一次或更少。
（归档去向：`systems/player-profile/player-power/_index.md`）

**sync-service 断线缓冲上限的口径（08-05 分发方案时暴露的张力）** → **答结 = 事件级存档点。** 闸门「未同步存档点 ≥ 3」计的是**轮回开始 / 每个 AdventureEvent 结算后 / 篇章边界 / 轮回结束**这四类，**不含事件推进过程中的决策点存档**。理由：决策点密度约 31 点/场战斗，按旧口径一场战斗打到第三个决策点就会弹出软阻塞模态。
**推论：** 这把「存档点与 push 解耦」贯彻到了闸门口径上（**闸门计 push 单位，不计本地写入单位**）；**决策点存档回归本职** = 纯本地的崩溃恢复与防重掷手段，不驱动 push、不计入闸门、不影响断线判定；**「决策点粒度决定 push 防抖压力」这句表述作废**（该待答的承重程度随之下降）；两个闸门语义齐了，且软阻塞的触发时机与闸门口径自动对齐。
（归档去向：`systems/services/sync-service.md`、`combat-service.md`、`systems/balance.md`）

**`attemptIndex` 是否还需要（动机已消解 · 长期挂起）** → **答结 = 整层删除，改由 `CharacterProfile.chapterRetry` 承载。** 「篇章重试时同名事件是否应换一套战斗随机」答定为**换**，而换法是**给这一次重试一套新的随机流**，不是在既有流上再派生一层——`Hash64(combatStreamSeed, eventId, attemptIndex)` 这一层因此没有任何剩余职责，字段与派生层一并去掉。
**新增 `chapterRetry`：** `CharacterProfile` 上的一个类，计数第一 / 第二 / 第三篇章各自的重试次数（因 ch2 与 ch3 有重试上限）。**它是计数器容器、不是上限持有者**——上限仍按 ADR-0004 的既定纪律读取（可被账号级持有状态改写、不得硬编码）。**推论：** 「重开一局」说的是**随机流，不是角色**——ADR-0004 的「从该篇章起始存档重试」「篇章继承 = 全部继承」不变；篇章解锁 / 重新锁定与「剩余重试次数展示」有了确定的数据源。
**新增待答：** ⚠ ch1 的计数挂在哪（现状语义下 ch1 重试 = 随机生成新角色，故角色级的 ch1 计数恒为 0，是死字段）。
（归档去向：`systems/common-properties.md`、`systems/services/life-cycle-service.md`、`systems/character-profile/_index.md`、`systems/services/combat-service.md`）
