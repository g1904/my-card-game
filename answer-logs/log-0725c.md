- **篇章继承什么** → **全部继承**上一篇章信息（`systems/services/life-cycle-service.md`、`systems/game-progression.md`）。
- **CharacterProfile 状态机（discarded vs defeated）** → 合并为单一终态 `defeated`，`discarded` 降为其原因子类型；`status = ongoing | defeated | completed`（`systems/services/life-cycle-service.md`）。
- **「每篇章至多一个 ongoing」精确语义** → 该篇章有 ongoing 角色时不能用其他角色玩该篇章；不同篇章可并行（`systems/services/life-cycle-service.md`）。
- **篇章解锁触发条件** → 通关上一篇章即成为下一篇章可挑战角色；无可挑战角色则该篇章重新锁定（`ux/onboarding.md`、`systems/services/life-cycle-service.md`）。
- **战斗模型** → **life + mana**（参考 MTG / Hearthstone）（`systems/adventure-event/combat/`、`systems/character-profile/mana.md` + `life.md`）。
- **节点 map 形态** → 月圆之夜风格（精心策划的事件菜单，非 StS 完全分支）（`systems/game-progression.md`）。
- **节点选择界面 UI** → **可横向滑动的选择区**（`systems/game-progression.md`）。
- **篇章总数 / 重试上限** → **四境三篇章**；重试上限 ch1=无限、ch2=3、ch3=1（`systems/services/life-cycle-service.md`、`systems/game-progression.md`）。
- **mana 曲线** → **无曲线**，采用「上限 + 逐步恢复」；炼气基线 life=10/10、mana=5/5（`systems/character-profile/mana.md` + `life.md`、`systems/balance.md`）。
- **境界突破复用 Combat 还是独立** → **`AdventureEvent-Finale` 作为第七类并入 ADR-0002 枚举**，独立于 Combat。
- **faith 归可见还是隐藏** → `faith` = **道心，隐藏数值属性**（`terminology.md`、`systems/services/life-cycle-service.md`、`systems/services/plot-manager.md`）。
- **后端 / 账号系统路线** → **重账号**（参考三国杀 Online）；已固化 `decisions/ADR-0003`。仅剩合规实现落地（仍在待答清单）。
- **游客态语义 / 迁移** → **彻底移除游客态**，强制账号登录（`vision/scope.md`、`ux/screen-flow.md`、`ux/onboarding.md`）。
- **AdventurePlot 层级结构 / 内容存放** → 四级 **Story > Chapter >（SideChapter / SideStory）**；Character 只存 **key points**，完整剧本存云端**剧本服务**（`systems/services/plot-manager.md`）。
- **成就自动发放 / 阈值 / 可见比例** → **组内加权进度**；**60% / 90% 两档一次性奖励**；目录 **80% 可见、20% 隐藏**（`ux/screen-flow.md`）。仅剩「两档各发放何种奖励」仍在待答清单。
- **「修行事件」单复数语义** → `修行事件` = AdventureEvent（单节点）、`修行历程` = `List<AdventureEvent>`（`terminology.md`）。
- **「大限将至」触发后果（defeated？转 Finale？）**（07-25） → **寿元递减到 0 → defeated**（`systems/services/life-cycle-service.md`、`systems/services/plot-manager.md`）。
- **character-profile 结构不一致（是否统一升为文件夹）**（07-25） → `deck` / `item` 为**文件夹**（含内容设计：起始卡组 / 道具设计）；`life` / `currency` / `mana` 为**扁平 `.md`**（系统性资源，规则短）（`systems/character-profile/_index.md`）。
- **「下一步能去哪」的架构归属**（07-25） → 归 **future-event-service**（依 CharacterProfile 产出 eventOptions，每个事件后重算；事件之间不设预连边）；生成 / 加权规则仍在待答清单（`systems/services/future-event-service.md`）。
- **寿元递减机制**（07-25） → 按 AdventureEvent 的 **`lifeSpanCost`（基准 -1）** 扣减，归 0 → defeated（`systems/adventure-event/common-properties.md`、`systems/services/life-cycle-service.md`、`systems/balance.md`）。仅剩分档 / 增长途径仍在待答清单。
- **元婴阶段是否再加寿元预算**（07-25b） → **+500**（累计 1000），但元婴为游戏终点，该增量**无玩法影响**，只是最后一次数值更新并存档（`systems/balance.md`、`terminology.md`）。
- **隐藏剧本层与 future-event-service 是否并列**（07-25b） → **隐藏剧本层隶属于 future-event-service**（07-25c 进一步降级为其内部的 **PlotManager**）；后者调用前者接口计算 eventOptions，并且是 eventOptions 对外的**唯一出口**（`systems/architecture.md`、两份服务文档）。
- **PlayerPower 开关的落地形态**（07-25b） → 落为类上持久字段 **`status`（启用 / 禁用，默认启用）**；与「拥有 / 失去」正交（失去 = 移出 `List<PlayerPower>`）（`systems/player-profile/player-power/`）。
- **`selectCost` 与 `lifeSpanCost` 是否语义重叠**（07-25b） → **包含关系**——`selectCost` 是一个**定制的复合成本类型**（由若干成本 element 组成），**`lifeSpanCost` 是其中一个 element**；**`skipCost` 与 `selectCost` 同为该类型**（同一套 element 体系，数值取向不同）（`systems/adventure-event/common-properties.md`、`terminology.md`）。
- **展示（充血）字段应放哪一层**（07-25b · ADR 候选） → **三层切分**——静态展示留 `XxxData : Resource`；运行时 / 存档只带 `Id` + 状态；组合展示走 UI **ViewModel**（不落存档 / 不进云端负载）。不为充血另建并行类（`systems/architecture.md`、`systems/common-properties.md`）。
- **全局设定类 PlayerPower 效果如何系统化**（07-25b · ADR 候选） → **capability flag（布尔）+ modifier pipeline（数值）** 两条通道，统一形状「数据声明 → 中心聚合（按 `status`）→ 单点查询」（`systems/player-profile/player-power/common-properties.md`）。落地细节仍在待答清单。
- **服务该按什么轴拆分（是否为 power / item / card / resource 各开 collection 服务）**（07-25c · ADR 候选） → **拆分轴 = 生命周期层 + 行为边界，不是数据类型**；按类型拆会撕碎事务、横切生命周期层、退化为贫血 CRUD。同理不为九类 AdventureEvent 各开服务（只有 Combat 有状态机）。「同类内容的统一入口 + 标准操作接口」由 **ContentRegistry + 泛型仓储接口**满足（`systems/services/_index.md`）。
- **PlayerProfile 侧无服务（缺口 1）**（07-25c） → 新增 **profile-service**，因 `PlayerProfile ⊃ List<CharacterProfile>` 而**同时拥有两层 profile**、作为唯一写入面；内含 **ProfileManager**（`TryApply` 全有或全无 + modifier pipeline 生效点）、**CapabilityManager**（flag 聚合宿主）、**AchievementManager**（`systems/services/profile-service.md`）。
- **战斗驱动归属（缺口 2）**（07-25c） → 新增 **combat-service**（TurnManager / DeckManager / IntentManager）；**Finale 复用其状态机**，其余七类走通用结算器（`systems/services/combat-service.md`）。
- **存档 / 云同步归属（缺口 3）**（07-25c） → 新增 **sync-service**（ProfileSyncManager / LocalCacheManager / MigrationManager）；登录另归 **account-service**（`systems/services/sync-service.md`、`account-service.md`）。
- **本地 `.tres` 与云端下发内容的分界（缺口 4）**（07-25c） → **有稳定 `Id`、被存档引用、需启动期校验 → 本地内容层**（`res://` 基线 + `user://overlay/` 热更）；**按进度动态请求、一次性呈现、不被存档引用 → 云端剧本服务**。故 **AdventureEvent 的定义属本地**，启动期强校验模型成立（`systems/services/content-service.md`）。
- **编排顶点是谁（缺口 7）**（07-25c） → **game-progression**（不是服务，是屏幕流程编排层）；服务之间不互相直呼（`systems/architecture.md`）。
- **skip 通道的 API 归属（缺口 5 · 部分）**（07-25c） → 复用 `life-cycle-service.AdvanceEvent` 的 **`mode = Skip`** 分支，`skipCost` 经 ProfileManager 施加。**玩法语义仍未定**，留在待答清单。
