## 移出的问题

**「道念差 → lifeTotal 损失的换算公式（负侧）」** → **1:1**：`lifeTotal -= (敌人道念 − 角色道念)`，道念差就是损失量，中间不隔系数或分档。推论：道念差成为一把通用刻度，战斗屏上的「落后 8 点」同时就是「输了掉 8 点」。**胜利侧是否也 1:1 仍未定，留在待答清单**。（归 `systems/scoring.md`、`systems/character-profile/life-total.md`、`systems/balance.md`）

**「`lifeTotalLimit` 是否须与 `baseMomentum` 量纲对齐 / 损失量是否设截断」（追加拍板）** → **不设上限截断，也无需为此抬高 `lifeTotalLimit`**：**「一次惨败打穿耐久」由内容设计侧规避**——遭遇编排不会给出会导致该结果的等级差。推论：**约束从规则层转移到内容层**，future-event-service 的赋级规则须持有一条上界（最坏情况下的道念差落在当前 `lifeTotal` 可承受范围内），上界取值作为新条目进入待答清单。连带：更高境界的 `lifeTotalLimit` 基线降级为普通数值待办，不再是承重矛盾。（归 `systems/scoring.md`、`systems/character-profile/life-total.md`、`systems/services/future-event-service.md`、`systems/balance.md`）

**「道念差结算量由谁计算（归属边界）」** → **combat-service 计算**，且**「获取奖励」属于 combat 流程的一部分**——不是 life-cycle 拿着 `CombatResult` 的双方道念在 `eventEnd` 再算。分工定为**计算归战斗、施加归生命周期**：本服务产出最终 `Spoils`（`ProfileChangeSpec`），life-cycle 仍在 `eventEnd` 合并为一次 `TryApply`，「一个事件 = 一次事务 = 一个存档点」不变。（归 `systems/services/combat-service.md`、`life-cycle-service.md`）

**「失败侧的奖励 / 惩罚结构」** → **输了通常只发 `baseReward`**；**少部分事件有额外惩罚，且惩罚包在 reward 里**（奖励结构中的负向条目），**不另立惩罚结构**——与 `ProfileChangeSpec` 的带符号约定天然自洽。三档结算产物由此齐全（胜 = baseReward + 加厚 / 平 = 只发 baseReward / 负 = baseReward，少数带负向条目）。（归 `systems/scoring.md`、`systems/adventure-event/combat/`）

**「奖励的发放形态」** → **分两类：强制奖励自动计入**（无需玩家操作，例：`experiencePoint`）**+ 可选奖励由玩家从若干候选中择一**（参照 Slay the Spire 的战后奖励面板）。推论：战斗后需要一个奖励选择步骤与对应界面，且它在战斗流程内。（归 `systems/services/combat-service.md`、`systems/adventure-event/combat/`、`ux/combat-ux.md`）

**「奖励选择是否构成一个决策点」（追加拍板）** → **不是**：**奖励是预先算好的**，退出重开得到同样的选项，故不存在「不满意就退出重开换一批」的窗口，无需为它单独落决策点。推论：**候选生成必须落在战斗的确定性边界内**（走 `Reward` 子流、随战斗 RNG `State` 一同持久化），否则该保证不成立。（归 `systems/services/combat-service.md`、`life-cycle-service.md`、`ux/combat-ux.md`）

**「『经验』是否为新引入的字段」（追加拍板）** → **是新字段 `experiencePoint`**：**每个等级各有一个升级所需的经验阈值**，事件奖励**发放经验值而非直接给等级**，累积达阈值才升一级。**这推翻了 08-01 的「等级成长 = 事件 reward 直接给等级」**。推论：等级产出可做得细碎连续、「失败给得比胜利少」有了自然表达、字段落在 `CharacterProfile.Status` 上、升级判定是 ProfileManager 施加后的派生检查。**阈值曲线待定**，作为新条目进入待答清单。（归 `systems/game-progression.md`、`systems/services/life-cycle-service.md`、`terminology.md`、`systems/balance.md`）

**「MTG stack 借到什么深度」（追加拍板 · 承重）** → **连响应窗口一并借入，回合是交互式的**：牌先入栈、按 LIFO 结算，**结算前对方可插入自己的牌**。**这推翻了「双方各 5 回合、我打完换你打」的简单交替**——回合数仍固定，但每回合内双方来回交互。推论：TurnManager 多一层「优先权在谁」的内循环；EnemyManager 的代理操作面扩大（AI 也要在窗口中决策）；卡牌设计多出「能否在响应窗口打出」这一维（MTG 关键字体系的落点）；「定长 10 回合 → 时长可预测」被削弱；决策点粒度须覆盖响应窗口。**规则细则（优先权轮转、可响应的牌、响应是否耗 mana、栈深上限、移动端交互）作为新条目进入待答清单。**（归 `systems/character-profile/deck/`、`systems/services/combat-service.md`、`systems/adventure-event/combat/`、`ux/combat-ux.md`、`terminology.md`）

**「Finale / Practice 是否同为 10 回合」** → **不一定**：**回合数与胜负条件都是遭遇参数，可被变体改写**。**标准 Combat = 10 回合、道念高者胜**；**Practice 更简单、Finale 更难**，三者对位 Balatro 的 **small / big / boss blind**。推论：TurnManager 仍是定长循环但长度来自本场配置，胜负判据是可替换的判定而非写死的比较。**具体改写值仍未给，留在待答清单**。（归 `systems/scoring.md`、`systems/adventure-event/practice/`、`finale/`、`systems/services/combat-service.md`）

**「越级追分是否可能」** → **可能，但很难，且境界差越大越难**。这确认了 `baseMomentum` 表「每级跨度持续放大、境界之间跨度更大」的形状正是为此而设——起跑线差就是越级难度的调节旋钮。推论：越级挑战是一条连续的风险曲线而非开关，与「敌人等级精确标注」合起来，玩家看到的是可估的赔率。（归 `systems/scoring.md`、`systems/balance.md`、`systems/adventure-event/combat/`）

**「`momentum` 的字段形态」** → **`>= 0` 的 Integer**：下限 0 在类型层面即已表达，不引入小数与负值。推论：削减是饱和减法，故若要如实呈现「本次削了多少」需区分意图削减量与实际削减量。**`CombatSnapshot` / `PlayResult` 的完整字段结构仍未定，留在待答清单**。（归 `systems/scoring.md`、`systems/services/combat-service.md`）
