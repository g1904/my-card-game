## 逐条

**回声校验的适用面与比较口径（08-22 新增 · 承重）** → **两小问一并答定：**

① **受约束路径的封闭清单如何表述** → 不列举，写成一条**恒等式**：**受回声校验约束的 JSON path 集合 ≡ §5 后端写入字段表的行集合**。它是「够格进表」两条判据的直接推论，带来三条推论：写入表加一行该路径自动进入约束 · 写入表封闭 ⇒ 约束面封闭（「适用面未穷举」结构性不再发生）· 不属写入表的透明路径一律不受约束（**判据是所有权，不是透明性**）。当前具体面四条 path、两个受约束顶层键（`accountInfo` 由改昵称触发 · `entitlement` 由兑现触发）。

② **非整数路径的比较口径** → **类型感知的语义相等，不是原始字节相等**：整数按数值 · 定长 hex 串逐字 · **RFC 3339 时间串按时刻** · **对象数组有序逐元素**（元素内逐字段递归）。**后两项此前是「采纳推荐 — 待复核」，本次已由用户逐条确认。** 承重理由：按字面比较时间串等于把两侧时间序列化器的逐字一致做成隐含契约，其破坏形态是「所有玩家改昵称都丢一次进度」，且无处校验。

**连带刚性（同批落笔）：** 向受约束顶层键内的对象**追加**字段 = 两侧同批落笔的变更（客户端的强类型往返会静默丢掉未知字段 ⇒ 回声当场失败）。这是 `envelope.md` §8「客户端加字段零配合」的例外，§8 已留一句指路。

**计数订正：** 上游草稿登记的「§4 拒绝清单由两类变三类」计数有误——实际含 `schemaVersion` 闸门，为**四类**；契约现文已是四类，无需再改。
