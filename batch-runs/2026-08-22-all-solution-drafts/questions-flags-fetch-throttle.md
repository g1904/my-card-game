# Phase A — flags-fetch-throttle

目标库：`game-design-documents/`（草稿 targets 全部落在客户端库；后端零新增义务，本次不写对侧库）

## 一句话意图

把 flags 拉取规则从「版本**不同**即拉」收紧为「**增大**即拉」，成功路径**不设最小间隔**（改由单调闸门 + 单飞/尾随一次界定上界），把护栏移到失败路径（指数退避 1s ×2 · cap 60s · 无放弃阈值），并让「观测到更小版本」从静默行为变成一条告警；三样新增运行态全私有，API 面零改动。

- **退避上限取值** → **A · 60 s**（与 push 退避 cap 同值，便于统一配表；flags 延迟容忍度本以分钟计）。备选 B · 30 s（恢复更快，不可用期间请求翻倍）。落 `balance.md`，可随时调，不影响结构。

## 🔴 冲突

- **[问题陈述] 「拉取失败进入指数退避、窗口到期时若仍落后则拉」与目标文档现存的一句直接相抵。** ✗ `systems/services/content-service.md`「flags：`ContentEnabled` 的第三层」原话：「拉取失败 → `PushWarning` + 用缓存 …… **下一次搭车观察到版本差异时自然重试——不为它另开重试机制**。」草稿称「张力：无」「API 零改动」，但**没有点名这一句会被改写**，也没有澄清退避是不是「另开的重试机制」。
  - 选项 (a) **纯闸门式退避（无定时器）**：退避窗口只是「窗口内的观测不发请求」，窗口到期后**仍等下一次搭车观测**才拉。后果：「不为它另开重试机制」这句原样成立，只需在其后补一句退避闸门；代价是后端恢复后的生效点最晚被推到下一次上行（分钟级，与既定的秒关延迟口径同量级，无实质损失）。
  - 选项 (b) **定时器式退避**：窗口到期即主动拉一次。后果：确实引入了一条独立于搭车的重试通道，**必须改写**「不为它另开重试机制」，且与「零轮询」这条 flags 通道的立身理由产生解释负担（60 s cap 的定时重试在后端长期不可用时形态上接近轮询）。
  - **推荐 (a)。** 理由：flags 的刷新语义**全部**建立在「搭车信封、零轮询」上（`content-service.md` + 后端 `contracts/content-manifest.md` 两侧同款表述）；(a) 用一条纯抑制规则拿到草稿要的全部收益（消灭「每次业务请求跟一次必然失败的 flags 请求」的链），且不新增任何主动发起面。草稿正文第 3 节列的收益在 (a) 下**一条不少**。

- **[问题陈述] 「尾随一次」在应答版本低于已观测版本时会自我递归，形成无限拉取环。** ✗ 草稿「具体形态」原文：「拉取结束：成功 → `FlagsVersion` = 新值；…… 若仍 < `_highestObserved` 则尾随一次」。若某次拉回的 body 版本**始终**低于头部观测到的 `_highestObserved`（头与 body 来自不同后端实例 / 中间层缓存了旧 body——正是契约点名要防的那类事故；后端库另有未决项「按账号计算是否需要缓存层」与「多区域间版本是否同步推进」），则每次尾随结束后条件依旧成立 ⇒ **无休止连发**。这与草稿自称「不排队、不累积」的意图相反，也与本子项「加护栏」的目的相反。
  - 选项 (a) **尾随至多一次，且尾随本身不再触发尾随**（尾随后无论结果都回到「等下一次观测」）。后果：形态最简，最坏情况每次观测最多 2 次请求。
  - 选项 (b) **尾随条件改为「本次拉回版本 > 拉取前的 `FlagsVersion`」**（即只要有实质推进就允许再追一次），否则停并告警。后果：多一条判定，但能把「body 版本不推进」这类事故也变成一条可见告警。
  - **推荐 (b)**（其中「停」的行为等同 (a) 的封顶）。理由：本子项最被草稿看重的收益就是「把只在放量时显形、极难定位的事故从静默变可见」；头/body 版本不一致与「观测值 < 内存值」是同一类事故的两个面，只防一面、另一面还留一个无限环，不成立。

- **[问题陈述] 「观测到更小版本 → `GD.PushWarning`」的可见性主张，与目标文档自己写下的判据相抵。** ✗ `content-service.md`「负向能力条目清单告警」一节原话：「**告警要落在能被看见的地方**……落在玩家进程里的 `PushWarning` 等于落在没人看的地方」；同文件对同类事故（验签失败 / `keyId` 未知）的既定处置是「`PushError` + **上报一次**」。草稿把 `PushWarning` 称为「本子项最有价值的一条」，但按本库既有判据，它对**线上**运营者不可见——而这类事故（灰度串号 / 中间层缓存旧应答）只可能在线上发生，本地开发期几乎复现不到。
  - 选项 (a) **`PushWarning` + 上报一次**（沿用验签失败那条既定通道，本会话去重）。后果：真正拿到可见性；需在 `content-service.md` 明写上报，并确认上报通道对「非错误级」事件可用。
  - 选项 (b) **只 `PushWarning`（草稿原样）**。后果：形态最轻、零新增依赖；但收益退化为「本地 / QA 期可见」，草稿的核心论据不成立，须在文档里如实写窄（不宣称它提供线上可见性）。
  - **推荐 (a)。** 理由：本库对「事故只在放量时显形」这一类已有既定处置模板（验签失败），复用它比新造一个更弱的形态一致；且这正是那条「告警要落在能被看见的地方」判据的适用场景。

- **[问题陈述] 「增大即拉」在服务端版本回退场景下会让设备**永久**停止同步开关，而草稿把这一后果记为纯收益。** ✗ 草稿断言「观测值 < 内存值只可能来自事故」「收益是三条、代价是零」。核实：契约 `backend-design-documents/contracts/content-manifest.md` 只钉死「`flagsVersion` 单调递增」，**没有**为 flags 写下 `contentVersion` 那条「回滚即前滚」的配套纪律（该纪律只登记在 ADR 候选①、针对 `contentVersion`）；同库两条未决项（多区域间版本是否同步推进 · 按账号计算是否需要缓存层）意味着**同一账号从不同区域 / 缓存层观测到更低版本并非纯理论**。一旦设备内存值高于服务端此后能提供的任何版本（回滚、库恢复、区域切换），「增大即拉」下该设备**再不拉取 flags** —— 症状是「秒关不生效 / 误关的内容永不恢复」，且只有一条（按推荐还去了重的）本地告警。「不同即拉」在同一场景下会自愈。
  - 选项 (a) **采纳「增大即拉」，并要求后端把「flags 回滚即前滚（回退须以更高 `flagsVersion` 发布）」写成契约条款** —— 触发跨库承接项：对侧库 `backend-design-documents/` 记一条待答 / 契约补充，两侧互相回链。后果：客户端语义干净；边界两侧对称落笔（符合跨库纪律「不允许只改一侧就宣称收口」）。
  - 选项 (b) **采纳「增大即拉」+ 客户端自愈兜底**：观测到更小版本连续 N 次（或跨一次冷启动仍持续）后，接受一次回退拉取并告警。后果：无需后端任何承诺；代价是把草稿最看重的「回退拉取被关死」打开一道口子，需定义 N。
  - 选项 (c) **采纳「增大即拉」，把永久停摆如实记为已接受的代价**（在 `content-service.md` 正面写下这条依赖与其后果）。后果：零新增机制；但「客户端开始依赖一条此前不依赖的契约条款」的失败模式是静默的。
  - **推荐 (a)。** 理由：草稿「后果」一节自己已经承认「客户端开始依赖『`flagsVersion` 单调递增』」，并建议「在 `content-service.md` 明写这条依赖并回链契约，**无需后端改动**」——但依赖的强度被低估了：单调递增只约束**正常发布序列**，不约束回滚与多区域，而后者恰恰是本条依赖会被违反的两个真实入口。按跨库纪律，这属于「客户端语义已定、只剩服务端如何兑现」，归对侧库承接。
  - ⚠️ **连带修正：草稿「与既有决策的张力：**无**」与「前置依赖：**无**」两处结论若采纳 (a) 即不再成立**（存在跨库承接项）。

## 🟠 含糊

- **内存 `FlagsVersion` 的启动初值到底是不是 `0`。** 草稿 §4 把「初值 = 0 ⇒ 启动后首次观测必然增大 ⇒ 必拉」当作 `[既有推演]`，但 `content-service.md` **从未写过**这一点：它写的是本地缓存 `user://cache/flags.json` 携带 `flagsVersion`、且该缓存的真实收益是「登录成功但 flags 拉取失败时的降级值」。两种解读导出不同文档内容：(a) 冷启动一律归零（缓存只提供 `disabledIds` 降级值，不回填版本）⇒ 每次冷启动必拉一次，🔴-4 的停摆被限制在单次会话内；(b) 冷启动从缓存回填版本 ⇒ 首次观测可能不触发拉取（省一次请求），但 🔴-4 的停摆**跨启动永久化**。**推荐 (a)**，并要求把它明写进 `content-service.md`（它是 🔴-4 的爆炸半径闸）。

- **失败退避是否带抖动 / 是否尊重服务端给出的等待时间。** 草稿只给「底数 1 s · ×2 · cap 60 s · 无放弃阈值」，对既有 push 退避另外两条只字未提：`push 退避抖动 +0~20%（乘性，只向上）` 与 `实际间隔 = max(本地退避计算值, 服务端给的等待时间)`（`sync-service.md`「push 侧退避的形态」）。草稿同时声称「与 push 退避同构」——若真同构，这两条应一并沿用；若有意省略，理由须写下（flags 拉取由观测触发、天然错峰，可能确实不需要抖动）。两种解读会写出**不同的 `balance.md` 行数**（2 行 vs 3–4 行）。**推荐**：沿用「尊重服务端等待时间」（省略它会把一次限流变成第二次限流，这条与通道无关）；抖动**不沿用**并写明理由（观测触发已错峰）。

- **验签失败的「本会话不再重试该 `flagsVersion`」记忆与 🔴-1 选项的交互。** 草稿把它与网络失败并列为「拉取结束」的第三分支，判据引自 `Upgrade` 类错误「重试必然失败 ⇒ 暂停退避」。含糊点：该记忆是记**单个版本号**还是**自该版本起的全部批次**？若 `keyId` 未知（密钥轮换未覆盖），后续每个**更高**版本都会各触发一次拉取 + `PushError` + 上报一次——上界是运营发布批次数，可接受，但须明写这是有意的（否则读者会以为已被抑制）。**推荐**：记单个版本号，并明写「更高版本照常重试，上界 = 发布批次数」。

## 🔵 可推演

- **单飞（同一时刻至多一次在途）** —— 与既有任何纪律无冲突，纯私有运行态；`RefreshFlagsAsync` 的既定失败语义（`PushWarning` + 降级 + 绝不阻塞）原样成立。依据：`content-service.md` API 面表。
- **判断留在 `ContentService` 内、观测者不判断** —— 草稿全程守住，与既定纪律一致（`content-service.md` API 面「flags 版本观测」行）。
- **等值不拉** —— 既定，不变。
- **不设最小拉取间隔（成功路径）** —— 与「秒关延迟 = 下一次上行、分钟级以内」这条 flags 通道的存在理由一致；节流会直接抬高该延迟。依据：`content-service.md` + `contracts/content-manifest.md` 两侧同款表述。
- **不违反 `sync-service.md`「降级只有三种形状」不变式** —— 草稿明写「退避只影响重试节奏、不影响生效值」，生效值仍是「用上一个已知好值（内容 / flags 侧）」，落在第二种形状内，未发明第四种。
- **切账号一并清零退避阶梯与 `_highestObserved`** —— 由既定的「`accountId` 不匹配 → 丢弃缓存」与「分桶是按账号解析后的结果」逻辑必然推出。
- **存档 schema / `flags.json` 字段面 / 后端报文零影响** —— 核实成立：三样新增运行态均不落盘、不进 Profile、不进报文。
- **「API 面零改动」这一断言本身成立** —— `RefreshFlagsAsync` / `OnFlagsVersionObserved` / `FlagsVersion` 三者**签名**确实一字不变。**但「语义不变」不成立**：`OnFlagsVersionObserved` 的失败语义行与 flags 一节的两句正文都要改写（见 🔴-1、🔴-4）。报告里应按「签名零改动、语义有改动」如实写，不沿用草稿的「零改动」措辞。
