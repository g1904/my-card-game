## 方案草稿：`PickMany` 抽不足 `count` 时 Research 候选与 Exchange 库存两个调用侧的处置

- library: `game-design-documents`
- file: `game-design-documents/inbox/solution-draft-pickmany-shortfall-handling.md`
- 依据构成：既有推演 7 项 · 通行做法 0 项 · 取向选择 5 项

### 建议要点

- **先补一条原语侧契约细化**：`PickMany` / `TryPickGrantableMany` 短缺时返回 `false` + `PushWarning`，但 `out` 参数**带回已抽到的那几条**（可为空列表、永不为 `null`）。两个调用侧的一切降级都建立在此之上。
- **复用 monetization 的空池三道闸体例**（加载期 / 前置拦截 / 运行期兜底），但**逐闸内容按本处重填**，且**失败处置方向与礼包相反**——分界判据明写为「**玩家有没有为这一次产出付过钱**」：付过钱 → 宁可拒绝进入流程；玩法内容 → 降级到更少是可接受的方差。
- **闸 ①（加载期 `PushError`）**：Research 每个槽的内容池型操作，池条目数 ≥ `CandidateCount` + 余量；Exchange 同 `Kind`+`RarityFilter` 的 Σ`SlotCount` + 余量 ≤ 过滤后池大小（**收紧既有那条「过滤后为空 → PushError」**）。
- **闸 ②（取池期，未物化前把该条目移出候选池）是「不能留空面板」的真正防线**，且与既有的 **Explore 壳过滤完全同构**（同为取池阶段一次判定、不落快照、防加载期够不着的运行期收缩）。计数能力全部现成：能力族用 `GrantableCount`，内容族用 `DrawPool<T>.Count`——**零新增接口、零新增抽取原语**。
- **闸 ③（物化期）= 降级到更少**：Research 该槽给几条算几条（正是 `CandidateCount` 已明写「上界不是保证」的兑现），整槽为 0 则剔除该槽；Exchange 该规则少产出几个 offer。全空为理论不可达 → `PushError` + 上报 + 该条目本次作废。
- **落存档记实际结果，不记「本该有几个」**：`ExchangeStock` / `ResearchSlot.Candidates` 长度即实际；**零新增字段、不 bump schema、无迁移**。推论明写：短缺的面板在退出重进后仍然短缺（防重掷纪律的正确行为，不是 bug）。
- **不设保底商品 / 不下调刷新价 / 不用别族补位 / 不在 UI 提示**——直接引自「空池是运营事故，不是玩法分支」。
- 日志形态逐闸给出（`[ContentRegistry-Validate]` / `[FutureEvent-PoolGate]` / `[FutureEvent-ResearchSlot]` / `[FutureEvent-ExchangeStock]`），闸 ② 用 `PushWarning`（flags 秒关是正常运营手段），闸 ③ 的空面板分支用 `PushError`（闸 ② 判定与实际抽取不一致 = 真缺陷）。

## 仍需用户决定（结构化）

### ① `PickMany` 短缺时 `out` 参数的语义 —— 阻断性最高，其余四项均建立在它之上

- **【问题陈述】** 契约已定「短缺 → 返回 `false` + `PushWarning`，不静默少给」。但 `out` 参数在部分成功时是否带回已抽到的那几条，未定；它决定两个调用侧能不能一次调用完成降级。
- **【选项 + 后果】**
  - **A：`picked` 带回池中全部已抽出条目**（可为空列表，永不为 `null`）。→ 调用侧一次调用完成降级；取池链只跑一遍；`TryPickGrantableMany` 失败语义里那句「含『不足 count』的部分情形」得到确切含义。
  - **B：`false` 时 `picked` 恒为空。** → 调用侧必须「先数池、再用较小 `count` 抽第二次」，同一条取池链在同一次物化里跑两遍，且 RNG 消耗次数依赖池大小。
- **【推荐 + 理由】** **A**。「不静默少给」防的是**原语假装成功**（返回 `true` 却少给），`false` + 告警已完整兑现这一点；丢弃已抽出的结果不增加任何安全性，只增加一条代码路径与一份确定性上的复杂度。

### ② 余量参数：新设两个 / 合并一个 / 不设

- **【问题陈述】** 闸 ① 若只断言「池 ≥ 所需」，因两条取池链都含「排除已持有」、池随玩家推进单调收缩，中后期必然频繁落到降级路径。是否引入余量、几个？
- **【选项 + 后果】**
  - **A：新设 `ResearchPoolMargin` / `ExchangePoolMargin` 两格**（与 `GrantPoolMargin` 同表不同值）。→ 三处用途各有旋钮可独立调；`balance.md` 多两格。
  - **B：三处共用一个 `DrawPoolMargin`。** → 表更小，但「礼包兑现保护」与「商店不缺货」两个量级完全不同的诉求被焊在同一个数上。
  - **C：不设余量，闸 ① 只断言「≥ 所需」。** → 最小新增，但闸 ① 形同虚设。
- **【推荐 + 理由】** **A**。与 `GrantPoolMargin` 的用途量级差异明显（一个防退款争议，一个防商店略显冷清）；C 的失败模式在本库已被 monetization 的余量设计预演过。

### ③ 短缺时是否给玩家任何可见提示

- **【问题陈述】** 一个因池收缩而少给的商店 / 构筑槽，玩家是否应当看到任何说明？
- **【选项 + 后果】**
  - **A：完全不提示。** → 零 UI 改动、零文案键；玩家看到的与内容作者编排的小店无法区分。
  - **B：商店显示一行「今日货源不足」类风味文案。** → 需新文案键 + ViewModel 判据；把运营事故包装成叙事，成为常态后会稀释文案可信度。
- **【推荐 + 理由】** **A**。直接落在「空池是运营事故，不是玩法分支——不为它设计兜底玩法」之内；B 只是把兜底玩法从机制层挪到呈现层，同一条判据仍适用。

### ④ 开局构筑事件（`AllowDecline == false` 的槽）的短缺处置

- **【问题陈述】** 开局强制构筑事件两槽均 `AllowDecline = false`；若某槽降到 0 候选，玩家会卡在一个无法提交的强制面板上。
- **【选项 + 后果】**
  - **A：闸 ② 对 `AllowDecline == false` 的槽逐槽收紧为「必须 ≥ 1 条候选」**，不满足 → `PushError` + 上报、该条目不进批次。→ 面板恒可提交；但真发生时开局那个 `eventPriority = 1` 的强制事件会**缺席**。
  - **B：短缺时把该槽临时降级为 `AllowDecline = true`。** → 面板永远可提交，但开局底盘（2 门绑定功法 + 1 门选来的 + 1 件法宝）残缺，与 `research/_index.md` 明写的底盘冲突。
- **【推荐 + 理由】** **A**。B 用「静默改写一条内容侧强约束」换「不缺席」，而底盘残缺的后果贯穿整个轮回；A 的失败面是一次可见的运营事故，符合「大声失败」。
  **⚠ A 留下一个连带问题需一并裁决：开局强制构筑事件缺席时，开局流程是否仍成立**（首批退化为常规批）。它触及「`Priority = 1` 依什么条件抬升」那条待答项。

### ⑤ 闸 ② 的判据阈值：`≥ 1` 还是 `≥ 所需`

- **【问题陈述】** 取池期把条目移出候选池的门槛，是「至少能产出 1 条」还是「能填满编排数量」？
- **【选项 + 后果】**
  - **A：`≥ 1`。** → 只兑现「不留空面板」这条硬约束，其余交给闸 ③ 降级。
  - **B：`≥ 所需`。** → 面板永远是「满的」，但一次轻微的运行期收缩会把整类事件从候选池删掉；对 Research 尤其致命（构筑的唯一落点），且会**静默改变事件类型分布**——而类型配比正是另一条待答项在调的东西。
- **【推荐 + 理由】** **A**。硬约束的原文是「不能留空面板」，不是「面板必须是满的」；B 用更强的拦截换一个更严重的失败模式。

## 与既有决策的张力

1. **「不静默少给」的读法。** 本草稿把 `out` 定为部分成功时带回已抽出条目，需用户确认这不违背原意（见待决项 ①）。
2. **与 monetization 三道闸的处置方向相反**（礼包「不补发、不折价、不降级替代」vs 本处「降级到更少」）。不是打架，但**必须在两处都写下分界判据**（玩家有没有付过钱），否则本库会多出第二组「看似相反的规则」而无人给出边界——`ux/error-and-blocking-ux.md`「灰态判据」一节正是为同类情形而存在。**建议在 `monetization.md` 三道闸小节补一句回链。**
3. **Exchange 加载期校验被收紧**（从「过滤后为空 → `PushError`」到「≥ Σ`SlotCount` + 余量」）。纯收紧、方向一致，但会让编排更容易在启动期失败；当前内容存量为零 ⇒ 零代价，写进文档时应明写这是有意的收紧。
