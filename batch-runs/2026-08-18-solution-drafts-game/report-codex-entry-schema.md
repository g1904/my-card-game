## 建议要点

- **`CodexEntry` 首批就一格 `Id`，对已写下的 record 零改动** —— 计数字段与首次解锁元数据（篇章 / 境界 / 日期）两组候选**全部不落**。三条依据：加法窗口已被 `CodexEntry` 这层包装本身买下（加一格是零迁移）· 计数是纯读数、落进标为「规则」层的字段即两层混装 · 日期撞「`X-Server-Time` 不用于校正本地时钟」、境界撞「词条正文绝不写等级」。
- **六处 `⟨待定⟩` 写入通道全部填 `CodexElements`** —— `ProfileChangeSpec` 新增一列，元素 `CodexUnlock(CodexKind Kind, string Id)`，新增六值 `enum CodexKind`。element 带 `Kind` 做路由、存档落六个具名字段，与 `AbilityChangeElement` 逐字同构；不复用 `(Kind, Scope)`（Enemy / Location 落在其值域外）。零 `Op`、恒不经 modifier pipeline、`SelectCost` 内恒为空。
- **`profile-service.CodexManager` 采集触发、写入仍经 `ProfileManager.TryApply` 单点提交** —— 与 `AchievementManager` 同构。
- **四本能力 / 道具类的解锁触发 = 「获得即记」**（`Op == Grant` 那一次提交）。两条最强依据：①「使用过即记」对 `PlayerPower` 根本无法定义（always-available，无离散使用事件），六本无法统一表述；② 六本触发**全部搭在一次已存在的 `TryApply` 上，零新增提交点 / 存档点 / push**。配套 `#if DEBUG` 断言兜底（`Grant` 无对应 codex element → `PushWarning`），**不由 `ProfileManager` 自动派生**（会让 `AppliedChange` 与提交的 spec 不一致）。
- **四本词条不套用敌人的五项规格** —— 五项规格昂贵是因为「不给数值地传达路数」，而该约束**只对敌人成立**。四本词条 = 条目自身 `DisplayName` / `Description` / `Rarity` / 立绘 + 一段可选 `CodexFlavor: LocalizedText`。**连带须明写一条边界：「不含阿拉伯数字」只约束 EnemyCodex，「不给动态情报」才是全族通则**。
- **六本一律不分档解锁**（直接来自「解锁是一次性全量写入」）。
- **EnemyCodex 慷慨度：推荐维持 3 张关键卡**，旋钮交给词条 ③④ 的写作厚度；预留退让阶梯「写厚 ③④ → `KeyCardIds` 上界 3 放宽到 5 → 才考虑全表」。
- **序列化形态**（直接答掉 sync-service 那条阻塞）：六个 camelCase 单数顶层键、`[{"id":"..."}]`、`PlayerProfileDiff` 顶层键**整键替换** ⇒ 解锁一条 = 整本全量上行；体积上限 ≈ `N × 30 B`，六本合计 20–40 KB 量级；**不进透明路径白名单**（后端不复算）；本地缓存无独立文件，随整个 Profile 走 `LocalCacheManager` 原子写；**不另起 bump**，追加进「两层 Profile 字段面收口」那一次。
- **新增软上限告警**：任一本条目数 > 该内容类型 `AllIncludingDisabled()` 总数 → `PushWarning`。图鉴统计分母走 `AllIncludingDisabled()`（否则线上关一条内容会让完成度百分比跳变）。

## 仍需用户决定（结构化）

### 取向 1 · 商店里见到但没买的法宝 / 古宝，要不要记进图鉴？
- **A · 不记，严格「获得即记」（推荐）** — 图鉴纯粹反映「你真正拥有过什么」；六本口径统一；零新增写入点。
- **B · 记，「获得或在商店中见到即记」** — 填充速度显著加快；但 Exchange 库存**可花灵玉刷新**（`RerolledCount` 已在册），刷新按钮成为最高效的图鉴填充手段；且需在库存物化时提交一次 profile ⇒ **新开一个呈现层写入点**。
- 理由：「遭遇即记」的内核是「接触即记，不要求你从中获益」，橱窗一瞥不构成接触；更承重的是 B 会把收集面挂到一个**可用货币无限重试的按钮**上。

### 取向 2 · 逐条目计数字段：真的一个都不要吗？
- **A · 一个都不要（推荐作首批）** — 只显示「已解锁 / 未解锁」；日后要加是零迁移的加法。
- **B · 加一个 `EncounterCount` / `AcquiredCount`** — 换来收集感；代价除「规则字段层混进纯读数」外，还有一条**新发现、此前未被评估过的成本**：计数随每次遭遇变化 ⇒ **每场战斗都让整本 `enemyCodex` 整键替换上行一次**（A 下只有首次解锁才产生 diff）。
- **C · 落 `PlayerStatistics` 聚合项**（如 `TotalEnemiesEncountered`）— 拿到总数、拿不到逐敌人计数；宽松同步、零迁移、后端零配合。**作将来的加法方向。**

### 取向 3 · EnemyCodex 的慷慨度（承重 · 本组核心）
- 意图机制移除后敌人图鉴是**事前知识的唯一主通道**。
- **A · 维持 3 张（推荐）**，慷慨度交给词条写作厚度；退让阶梯「写厚 ③④ → 3→5 → 才考虑全表」。**已知代价：信息劣势保持现有水平，而该水平在意图移除后尚未经实测检验。**
- **B · 给完整 15 张** — 事前知识大幅变宽。代价三重：突破「150–280 字一屏读完」· 推翻「关键卡 3 张（5 张就成背卡表）」· 玩家可据全表推算剩余牌 ⇒ **从事前知识滑向事中情报**，动摇图鉴与战斗信息体系共存的**前提**。
- **C · 全卡表作第六项、第二次遭遇后解锁** — **直接推翻「一次遭遇全文案解锁」**（分档解锁已被否决），并推翻「解锁状态只需表达已解锁这一态」⇒ `CodexEntry` 被迫加一格，**与取向 2 的推荐直接冲突**。
- **取向 2 与取向 3 存在耦合：先问 3 再问 2 更稳**（3 选 C 会直接改变 2 的可选项）。

### 取向 4 · `CodexFlavor` 是否真做
- **A · 做且可选（推荐）**（缺失不渲染、不告警）：可选字段做与不做的**结构成本相同**（不做 = 全部留空），却留出一格；且符合「加法窗口在写下第一批 `.tres` 时关闭」。
- **B · 不做** — 零成本，但收集感很薄。

3. 「图鉴的入口与浏览形态」—— 主菜单现有五个一等入口，图鉴族**尚无入口**。

## 与既有决策的张力
1. 「不要计数字段」vs 收集感取向 → 取向 2。
2. **`ProfileChangeSpec` 增列。** 准入判据（既有列装不下该载荷形状）成立。**若用户认为列数已过多，唯一替代是「`CodexManager` 直接写」，而那绕过唯一写入面、已被否决。**
3. **「『不含阿拉伯数字』只约束 EnemyCodex」是对现有措辞的一次显式收窄。** `codex/_index.md` 写着「对整族适用」。本方案主张：「不给动态情报」是全族通则，「不含阿拉伯数字」不是。须在 `common-properties.md` 明写。
4. 取向 2 与 3 耦合，先问 3。

## 越界发现
1. **`LocationCodex` 显影粒度**：`codex/_index.md` 写着「**本库现按前者理解，待确认**」——即库内有一个**未经确认的默认理解**正在被后续推论依赖（「提前两步规划路线」「整张图可重建」两条推论都建立在它之上）。它答定前那三条推论的成立性是悬的。
2. **对并行 `GameSetting` worker 的隐含要求（请交叉核对）：**
   - **`PlayerProfileDiff` 顶层键 = 整键替换、不表达删除**（契约既定）。若 `GameSetting` 方案打算做**字段级增量**同步，与该契约不兼容 —— 必须整键替换。
   - 切出的「设备本地」那一半不在 `PlayerProfile` 里，因而不在 `PlayerProfileDiff` 顶层键中。本方案的体积口径（六本 20–40 KB）**未计入 `GameSetting`**。
   - 15 字段表第 15 行 `gameSetting` 的「层」列当前是 `—`（空），而本方案填的六行都是「规则」。**两个 worker 对该表的填法应保持同一口径。**
3. `07` 分片相邻两条未纳入本批：「入口与浏览形态」（消费方）与「是否与成就挂钩」（本方案的**真前置依赖**）。
4. **`profile-service.md` 已有三条同源待决项**（`activeCombat` / RNG / `pastEvent`）与 `CodexElements` 是同一类问题（「某个 Profile 字段没有 spec 列」）。**若用户希望一次性收口 `ProfileChangeSpec` 的列面，应同批处理——分开做会让列面连续 bump 两次**（当前无线上存档 ⇒ 均为空迁移）。
