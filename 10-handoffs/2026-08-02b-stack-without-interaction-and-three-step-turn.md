## Intent（distilled）

**一句话：** 对 08-02 定下的「stack 连响应窗口一并借入」做一次**范围收窄**——**stack 作为核心结算模型保留**，但**交互（instant / 栈非空时出牌）与优先权传递（priority passing）整体移除**；理由是**交互 / 优先权把对局拉长、决策点过多、整体复杂度高而玩法深度收益小**。同时**给出回合的完整结构：三步（起始步 / 主阶段 / 结束步）**——**去掉战斗步骤，也不设双主阶段**，主阶段是**唯一**的出牌阶段，且**只有回合归属方能主动出牌**（sorcery speed）。

### ① 保留：stack 是核心结算模型

- **卡牌不立即生效，先入栈，按后进先出（LIFO）依次结算。** 「打出」与「结算」仍是**两个时刻**——这一条是 08-02 借入 MTG stack 的核心价值，**不变**。
- **推论：触发与效果系统的骨架仍在。** 至今空白的「回合内效果 / 状态系统」依然可以挂在「入栈 → 结算」这条轴上，且本次新给的两个触发时点（见 ③）正是它的第一批锚点。

### ② 移除：交互与优先权传递

- **移除「交互（interaction）」** —— 即 **instant（瞬间）类牌**、以及**在栈非空时出牌**这两件事，一并取消。
- **移除优先权传递（priority passing）规则。** 不再有「双方轮流取得优先权、连续 pass 才结算栈顶」这一层。
- **理由（用户原话的整理）：** 交互 / 优先权 **① 把对局时长拉得太长；② 决策点过多；③ 整体过于复杂，而换来的玩法深度收益很小。** 这是一次明确的**复杂度 / 收益权衡**，不是实现难度上的妥协。
- **推论 ①：08-02 的「回合是交互式的」被推翻。** 「一方行动完再交给另一方」的**简单交替恢复成立**——TurnManager **不需要**「优先权在谁手上」的内循环。
- **推论 ②：「定长 = 每场时长可预测」恢复成立。** 08-02 因交互次数不固定而削弱的这条推论重新生效：回合数固定、每回合的步骤固定，故一场战斗的时长回到可预测——篇章时长控制不必再另加约束（响应次数上限 / 计时一类护栏无须设计）。
- **推论 ③：决策点粒度回落。** 一个回合内可退出的时刻收敛回「回合边界 / 每次出牌」这一类，**不再需要覆盖响应窗口与优先权移交**。
- **推论 ④：EnemyManager 的代理面回落。** AI **只在自己的回合**选行动，不必再在对手的响应窗口中决策——08-02 记下的「代理操作面变大」随之作废。
- **推论 ⑤：卡牌少一个设计维度。** 「这张牌能否在响应窗口中打出」不再是卡牌的一个字段 / 关键字；**instant 一类关键字明确不借**，MTG 借词的第一批因此不含它。
- **推论 ⑥：`00-vision/pillars.md` 的反目标得到贯彻。** 「不搞深度的堆栈 / 优先权复杂度」这条既有反目标，与本次「留 stack、去优先权」完全一致——借的是 stack 的**结算顺序**，不是 MTG 的**优先权体系**。

### ③ 回合结构 = 三步（已定案）

**去掉战斗步骤（combat step），也不设双主阶段。** 一个回合固定走三步：

| 步骤 | 内容 |
|------|------|
| **起始步（start）** | 回合归属方 mana 恢复至 `manaLimit` → 触发「回合开始时」→ 抽牌 |
| **主阶段（main）** | **唯一**的出牌阶段。**只有回合归属方能主动出牌**（sorcery speed） |
| **结束步（end）** | 触发「回合结束时」→ 清理回合内状态 |

**三步流程是回合归属方的流程，双方不同时走（已定案 · 追加）。** 每一方在**自己的回合内**各走一套完整的三步；「回合开始 / 回合结束」是**有归属方的时点**，不是双方同步发生的公共时刻。

- **步内顺序是规则的一部分。** 起始步里 **mana 恢复在「回合开始时」触发之前、抽牌在触发之后**——这个次序决定了「回合开始时」类效果能否影响本回合的抽牌，是可被卡牌利用的确定顺序，不是实现细节。
- **推论 ①：mana 恢复精确化为「回合归属方在起始步恢复」。** 既有表述「战斗内每回合开始 mana 自动恢复至 `manaLimit`」在此收紧：**恢复的是本回合归属方的 mana**。因非归属方无法出牌，其 mana 在对手回合没有用途——mana 实际语义是「**每次轮到我时刷满**」。「响应是否消耗 mana、用谁的 mana」这个 08-02 遗留问题**随交互移除而消解**。
- **推论 ②：sorcery speed 成为全体卡牌的统一出牌时机。** 既然 instant 不存在，**所有牌都是 sorcery speed**——只能在自己回合的主阶段打出。这条不再是卡牌的一个可选属性，而是全局规则。
- **推论 ③（已被追加意图改写）：手牌上限是一条恒定不变式，不是结束步的弃牌结算。** **手牌在任何时刻都不得超过上限**——不存在「先超出、再到结束步弃到上限」的窗口，**没有时间限制，也没有必须弃牌的机制**。**上限值待定。** **这推翻了本 handoff 首轮三步表中的「结束步 → 手牌上限弃牌」一项**，结束步收窄为「触发『回合结束时』→ 清理回合内状态」。**推论：约束点前移到会让手牌增加的时刻**（抽牌、以及任何「加入手牌」类效果）——**达到上限时该如何处理**（抽不进 / 抽了即弃 / 溢出销毁）未陈述，见 Open questions。
- **推论 ④：「回合内状态」成为一个正式的状态生命周期档位。** 结束步「清理回合内状态」把状态分成了**回合内临时**与**跨回合持续**两类——这是效果 / 状态系统的第二个锚点（第一个是两个触发时点）。
- **推论 ⑤：抽牌时机定在起始步。** 每回合抽牌发生在起始步末尾；**每回合抽几张、首回合是否抽、起始手牌多少**均未给。
- **推论 ⑥：没有独立的战斗步骤，与「道念由卡牌产出」自洽。** 本作没有 MTG 式的生物攻击阶段——道念的产出 / 削减**全部经由主阶段打出的卡牌**，不存在第二条在战斗步骤中结算的通道。

### ④ 栈深由**触发式能力入栈**撑起（已定案 · 追加 · 承重）

- **在栈上的牌可以触发能力，被触发的能力**也进栈**——因此即便只打出了一张牌，栈深也可以大于 1。** 这答结了「移除交互后 stack 是否名存实亡」：**stack 的承重点是触发的解决顺序**，不是双方互插牌。
- **推论 ①：「栈非空时不能出牌」对双方都成立，不需要为归属方开口子。** 上一轮列出的另一条候选路线——「允许在主阶段连续压入多张牌再统一结算」——**不采用**：栈深不靠玩家连续出牌撑起，靠触发。
- **推论 ②：LIFO 在此有了实际意义。** 一次结算可能连锁产生多个触发，它们按后进先出解决——**结算顺序成为可被卡牌设计利用的资源**（后触发的先生效）。
- **推论 ③：「多张削减牌同时在栈上」是会真实发生的情形。** 故「道念下限 0 的饱和减法在**每次结算时**截断还是**全栈结算完**后截断」这个问题**不会自动消失**，必须回答（见 Open questions）。
- **推论 ④：栈需要进入呈现层。** 玩家要能看懂「现在有哪些东西在等待结算、以什么顺序」，否则触发连锁不可读——上一轮「若栈深恒为 1 则栈可完全不呈现」的退路不成立。
- **推论 ⑤：三步中的两个触发时点是这套机制的第一批入栈来源。** 「回合开始时」/「回合结束时」触发产生的效果同样压栈解决。

### ⑤ 与既定战斗骨架的接口

- **定长 10 回合、双方各 5、交替**（Combat 档默认值）不变；三步结构描述的是**其中一个回合**的内部形状。
- **回合数与胜负判据仍是遭遇参数**（Practice / Finale 可改写）不变；三步结构本身不随档位变化。
- **奖励环节仍在战斗流程尾部**（结算 → 计算奖励 → 可选奖励选择 → 收口），不变。

## Open questions

- **手牌达到上限时如何处理（承重 · 由「不得超出上限」逼出）。** 上限是恒定不变式且**无弃牌机制**，故约束点落在会让手牌增加的时刻：**满手时抽牌是抽不进（牌留在抽牌堆）、抽出即弃、还是直接销毁**？「加入手牌」类的卡牌效果同理。这条不定，抽牌流程就写不出来。→ `20-systems/character-profile/deck/`、`20-systems/services/combat-service.md`。
- **手牌上限的取值。** 上限存在与语义已定；**数值未给**（敌人侧是否同值亦未给）。→ `20-systems/character-profile/deck/`。
- **触发式效果的载体形态。** 「触发入栈」已定案（见 ④），但触发**由什么承载**（卡牌上的触发器？场上的持续状态？CharacterPower？）、以及触发条件能否写「对手的回合开始时」这类跨归属方的时点（时点本身已定为有归属方，但监听方未必是归属方），均未陈述。→ `20-systems/adventure-event/combat/`、`20-systems/character-profile/deck/`。
- **每回合抽牌数、首回合抽牌与起始手牌。** 抽牌**时机**已定（起始步、「回合开始时」触发之后）；**数量**、以及先后手是否有抽牌差（对位 MTG 的先手不摸）未给。→ 同上。
- **「回合内状态」的判定边界。** 结束步清理的是哪些东西——本回合获得的临时增益？本回合打出的牌留下的持续效果？「持续到下回合结束」这类跨回合时长如何表达？→ `20-systems/adventure-event/combat/`。
- **sorcery speed 的中文定名。** 概念已定（只能在自己回合主阶段、栈空时打出），属 MTG 借词，须按借词纪律在 `terminology.md` 登记；中文名未给。同批需定名的还有 start step / main phase / end step 与 resolve / trigger。→ `terminology.md`。
- **决策点粒度（问题仍在，但加压解除）。** 「须覆盖响应窗口」这条约束随交互移除而作废；剩下的仍是原问题：战斗内的决策点落在每回合开始 / 每次出牌后 / 每次结算后哪一处。→ `20-systems/services/life-cycle-service.md`、`combat-service.md`、`sync-service.md`。
- **stack 与「道念下限 0」的交互（承重 · 已确认会真实发生）。** 触发入栈使栈深可以大于 1，故「多张削减效果同时在栈上」是会出现的情形：饱和减法在**每次结算时**截断，还是**全栈结算完**后截断？两者结果不同（前者更保护落后方）。→ `20-systems/scoring.md`。
- **栈与触发的呈现（承重）。** 触发连锁要可读，栈就必须以某种形式进入呈现层：竖屏小尺寸上如何表达「有哪些东西在等待结算、以什么顺序」、连锁触发的动画如何不拖慢节奏。→ `40-ux/combat-ux.md`。
