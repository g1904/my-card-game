## Intent（你的原话，已提炼）

一次性铺开**前置屏幕（登录 → 主菜单）的 UX 骨架**，并顺带敲定**开发顺序**。架构细节未定；美术资源全部延后（TBA），但要在架构里为其预留可替换的挂点。

### 1. 登录屏（首个屏幕）

- 应用的**第一个屏幕**是登录屏，含**服务条款（Terms & Services）**。
- 背景是一段 **live2d 风格的循环动画视频**（氛围演出）。美术资源 TBA，此处先留空占位。
- 登录方式（用于**在线存档**）：**微信 / QQ / 邮箱 / 手机号**。
- 也可**游客账号（Guest）**进入——不登录直接开玩。

### 2. 在线存档 + 服务器（对既有「仅离线」约束的调整）

- 尽管游戏玩法本身离线，但**倾向于**通过账号登录把进度**在线存档**。
- **会有一台服务器**来存储这些账号 / 进度数据。
- 与 `00-vision/scope.md` 现有的「仅离线——`user://` 持久化，无网络」直接冲突 → 见 Open questions，需你确认调整后的存档模型。

### 3. 主菜单（登录后）

首玩者进入主菜单后，**只能从第一篇章（炼气 / Qi Refining）开始**；其余篇章选项**隐藏**（后续解锁后才出现）。

主菜单除了「切换篇章以开始一次 run」外，还有以下入口按钮：

| 按钮 | 中文 | 内容 |
|------|------|------|
| PlayerProfile | 玩家档案 | 状态与账号信息 |
| PlayerPower | 玩家能力 | 可开 / 关的特殊能力 |
| Achievements | 成就 | 分组成就；某一组达成度到 **90%** 时**自动**发放该组奖励 |
| Settings | 设置 | 音频开 / 关等 |

**隐含结构（从上述推演，非新增机制）：**
- 这四个入口精确对应上一份 handoff 里 **PlayerProfile** 的账号级字段：`AccountInfo`→PlayerProfile 按钮、`List<PlayerPower>`→PlayerPower、`List<Achievements>`→Achievements、`GameSetting`→Settings。主菜单即 PlayerProfile 数据模型的**视图层**。
- 「首玩只解锁炼气、其余隐藏」是**篇章解锁门禁**：解锁态是账号级元进程数据（落在 PlayerProfile / 元进程层），与既有「篇章边界存档 → 读档续章」模型衔接——炼气可无门槛起手，后续篇章需先解锁 / 有存档角色。
- 「切换篇章开始 run」= 在**已解锁**篇章中选一个作为该次 run 的起始篇章。

### 4. 美术资源策略（延后但架构友好）

- 音轨、卡面、动画等**几乎所有美术相关资源**在设计达 ~90% 前一律 **TBA**。
- **此刻留空这些文件**，但在架构中**始终为其保留可轻松替换 / 定制的挂点**。
- 开发推进过程中，是一项待办：找一些**通用 / 免费的占位资源**作默认——优先用现成 库 / package，或让用户从 Godot 社区资源里找。

### 5. 开发顺序（设计先行，自顶向下）

用户提出的计划，并请求批评：

1. **设计先行**（自顶向下）
2. **工程系统**——先让系统能跑起来
3. 最后再做**测试、平衡、美术**

理由：测试与平衡是劳力密集型，美术成本高昂——因此把它们放在「先有一个可运行 demo」之后的末段。

> 见 Open questions：对该计划的批评与一个改良提案（作为流程 ADR 候选）。

## Design pillars / 承接

- 呼应「移动优先、竖屏、触控」：登录屏、主菜单都需按竖屏触控目标尺寸设计（见 `ui-input-rules.md`）。
- 呼应上一份 handoff 的 **PlayerProfile 元进程脊梁**：主菜单四按钮把该数据模型显性化为 UX 入口。
- 美术挂点策略呼应「展示字符串 / 资源与逻辑分离」原则——占位资源可无痛替换。

## Open questions

- **在线存档 vs「仅离线」约束（矛盾，需拍板）。** `scope.md` 现声明「仅离线，无网络」；本 handoff 要求账号登录 + 服务器 + 在线存档。二者不能同时为真。我的解读：目标是**离线可玩 + 在线云同步账号进度的混合模型**（本地 `user://` 权威存档，联网时向服务器同步；游客态纯本地）。请确认——这会推翻 scope 的一条平台约束，且引入一个此前明确排除的服务器组件（后端选型、账号系统、同步冲突解决全部为新增待决项）。这是否仍属 **MVP 范围之外**（即 MVP 保持纯离线 + 游客，在线登录延后）？
- **游客 → 登录的账号迁移。** 游客账号先玩、之后再登录时，本地进度如何并入云端账号？（首次登录合并 / 覆盖 / 提示选择？）
- **服务器 / 后端选型未定。** 自建服务、还是微信 / QQ 的开放平台 SDK + 某 BaaS？账号体系与登录 SDK 均待定。
- **登录方式的平台边界。** 微信 / QQ 登录主要面向国内 Android/iOS；桌面 / 网页 / 海外 iOS 上这些渠道不可用——非国内渠道的回退（邮箱 / 手机号 / 游客）是否作为跨平台基线？
- **T&S / 隐私合规。** 在线账号 + 服务器存储个人数据触发合规要求（隐私政策、账号注销、数据导出，尤其国内《个人信息保护法》与各渠道审核）。服务条款文案与合规范围待定。
- **成就自动发放的精确语义。** 「一组达 90% 自动发放该组奖励」——90% 按组内成就**数量**算还是**加权进度**？发放的是什么奖励（PlayerPower？PlayerItem？账号级？）？剩余 10% 未达成时该组能否重复触发 / 是否一次性？
- **PlayerPower「开 / 关」的语义。** 特殊能力可开关——是玩家自选的 buff / 修改器（影响难度 / 计分）？还是解锁后可装配的被动？开关是否影响 run 的 seed / 公平性？
- **篇章解锁条件。** 首玩只开炼气；其余「后续解锁」——解锁触发是什么（通关上一篇章？成就？元进程？）？与既有「篇章存档角色是有限资源」模型如何衔接？
- **登录屏循环视频的技术实现。** Godot GL Compatibility + 移动 / 网页导出下，循环视频背景用 `VideoStreamPlayer`（Theora/WebM）还是 live2d 风格的骨骼 / 序列帧动画？影响资源管线与包体。此为架构待决，非设计断言。
- **开发顺序批评（流程 ADR 候选）。** 见 Notes；总体方向合理，但「测试 / 平衡完全押后到末段」有风险——建议改为**垂直切片 + 贯穿式轻量平衡**。待你认可后可固化为流程决策。

**对开发顺序的批评（写给报告 / ADR 候选，非设计断言）：**
方向正确——设计先行、先跑通系统、把高成本的美术押后，对独立 / 小团队是务实的。但两处风险：
1. **平衡完全押到末段**过于滞后。数值手感（能量曲线、伤害、掉率）会反过来影响系统 API 设计；若系统全部成型后才首次平衡，可能被迫返工接口。建议在系统落地时就用**占位数值 + 数据驱动配置**（平衡值本就该在 `.tres` 而非硬编码，见 `data-resource-rules.md`），使后期平衡是「调数据」而非「改结构」。
2. **纯瀑布式自顶向下**推迟了端到端验证。建议改为**垂直切片**：先打通一条最细的可玩链路（登录 → 主菜单 → 炼气一场战斗 → 存档），端到端跑通后再横向铺开系统。这样最早暴露架构风险，也让美术挂点在真实链路里被验证。
→ 改良提案一句话：**"设计先行 + 垂直切片先跑通端到端 + 贯穿式用占位数据做轻量平衡 + 美术挂点占位、末段替换"**。
