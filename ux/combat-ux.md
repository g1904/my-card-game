# combat-ux

> 战斗手感:出牌/拖拽/指定目标、节奏。**主视觉 = 双方道念对比**;**敌人的行动不作事前预告**,可读性由敌人回合的逐步执行呈现承担(见下)。

## 意图

- **道念是战斗屏幕的主视觉。** 胜负判据是**道念(momentum)高者胜**(见 `systems/scoring.md`),因此战斗屏幕的视觉重心是**双方道念的对比**——玩家任何时刻都应一眼看出「我现在领先还是落后、差多少」。**lifeTotal 退居次要**:它在战斗过程中不变化,只在结算时按道念差被扣减,故不需要战斗内的常驻血条式强调。具体形态(对比条 / 双数值 / 天平隐喻)待战斗 UX 专场。
- **道念显示位:双方各随其头像（承重）。** 道念对比条横贯屏幕,**双方的头像与数值分居其两端**——对比条与头像位不互斥,两者同时成立,合称**双方道念位**。**玩家侧因此有一个头像位**(战斗屏此前只写了敌人立绘):它只作道念的锚点,**不承担任何图鉴入口**,也不并列玩家自身等级。本文件中以「道念对比条」为基准的布局纪律,凡涉及压暗豁免与压缩顺序处,指的都是这一整组。
- **战斗是定长的 10 个回合,故进度可视。** 双方各 5 个回合、打满即比大小——**「还剩几回合」是一个必须呈现的信息**:它把「我落后 8 点、还剩 2 个回合」变成玩家可算的账,是限时积分对抗的紧张感来源。**起始道念按等级给**,故战斗一开场就可能呈现出一段明显的落差。呈现形态(回合计数器 / 进度条 / 双方轮次指示)待战斗 UX 专场。
- **敌人等级精确可见(答结「等级差是否可见」)。** 玩家**能**看到敌人的等级——**在 eventOptions 上就已精确标注**(见 `systems/services/future-event-service.md`),而非模糊的危险度档位(「同阶 / 略高 / 越阶 / 无从揣度」一类标签**否决**)。**承重理由:看到等级即看到起跑线**——等级 → `baseMomentum` → 开局领先 / 落后量,故标注的等级**就是这场遭遇的难度刻度**;「越级挑战」也因此成为可主动选择的风险 / 回报维度。
- **敌人的行动不作任何事前预告（承重）。** **意图区、三档呈现、类别符号体系、综合数值、「预估」视觉提示与偏差对照,全部从战斗屏移除。** 玩家在自己回合看不到敌人下一回合要做什么;可读性改由**事中呈现**承担(见下一条)。规则侧权威见 `systems/adventure-event/combat/_index.md`「敌人回合的可读性」。
  - **推论 ①:战斗屏少一个区**,释放约屏高 8%,且**少一个随回合归属切换而出现 / 消失的区域**——一场约 20 次的收起 / 展开动画整条消失,布局跳位的风险源随之减少一个。
  - **推论 ②:玩家回合的决策面收敛为「道念对比 + 剩余回合数 + 战场 + 埋伏计数」**。「我落后 8 点、还剩 2 个回合」这本账仍然可算,只是账里没有「它下回合要打 12」这一项。
  - **推论 ③:探查(probe)的入口不再需要在战斗屏留位置**。
  - **已知代价(明写接受):** 本作已移除交互与优先权,故敌人回合对玩家而言是**信息与交互双零**的一段观看。这正是下一条把逐步呈现升为硬要求的原因。
- **敌人回合的逐步执行呈现是硬要求（承重）。** **敌人回合是玩家获取动态情报的唯一时刻**——看不清就完全不可读:
  - **飘字为主 + 战报为辅,两者都要**:飘字**注意力跟随对象**(敌人打出牌 → 牌面飞出 + 道念条上 `+5`;玩家侧被削减 → `−3`),不需要阅读但转瞬即逝;战报可回看。**战报的收起态必须常驻可见**——藏在按钮后等于取消这条硬要求(玩家不会主动开日志)。形态见下「战报」条。
  - **截断量必须被说明**:一次结算的效果标称量与实际量不等时(道念下限 0 的饱和减法),战报给出「削减 8(对方仅剩 5,溢出 3 未结转)」。数据由呈现事件流每条自带的 `Declared` / `Actual` 一对承载——**`Declared` 是效果的标称量、`Actual` 是实际生效量**,契约见 `systems/services/combat-service.md`。
  - **目标落空(fizzle)必须被说明**:结算时逐槽位重检,已选定的目标可能已被拆掉。**部分槽位落空 → 战报写明是哪一半没生效;全部槽位落空 → 战报明写「目标已不存在」**,而不是让玩家看到一张牌打出去后什么也没发生。规则侧见 `systems/services/combat-service.md`。
- **结算呈现 = 逐层弹栈 + 短暂强调,不做滚动播报流（承重）。** 结算时先显示栈上的卡牌 / 效果,再**逐层 LIFO 弹出**,每弹一层做一次短暂的视觉强调,弹完即落账——因果顺序因此保持可见,而不是把一串结果冲刷进一条滚动播报里。
  - **「不可暂停」读作「无玩家侧的暂停 / 跳过控件」。** 结算中途停下来问「指谁」是规则层的停顿 + 玩家的一次真实输入(见下「结算会在中途停下来问『指谁』」),不是暂停;演出可以在那里挂起、再继续弹栈。
- **结算演出的节奏(双方回合通用)。** 单步节拍 **0.35–0.5 s** · **超过 4 步后压到 0.2 s** 并**合并同来源、同类型、同符号的连续增量**(跨来源不合并——跨来源正是玩家需要区分的)· 点按屏幕任意处 **3× 加速**(**只能加速不能跳过**,「逐步可见」是硬要求)· 永久快速演出为设置项(默认关,开启后基线节拍 0.2 s)。**演出中没有不可跳过的节拍**——不设「某一步额外停顿且加速无效」一类的强制停留,加速手势在任何一步都生效。
  - **总时长的硬上界只约束敌人回合**:单个敌人回合演出**总时长 ≤ 4 s**(一场合计 ≤ 20 s;若每回合演出 8 秒,一场就是 40 秒纯观看,在 30–40 分钟篇章预算下不可接受)。**该上界针对的是玩家完全无交互的整段观看**,故不对称适用于玩家回合:玩家回合的演出是玩家自己出牌的结果、有心理预期,加速手势也就在手边,**不设总时长上界**,由上面三重护栏次线性收敛。给玩家回合也设死上界,会在栈深大时撞上天花板而只剩「跳步」一条出路,与「逐步可见是硬要求」直接相抵。
- **战报(`combatLog`):收起态与展开态是同一份数据的两个视图（承重）。** 战报记的是**已经弹出、已经落账**的东西,与**栈**(等待结算的队列)是两个对象。**竖屏净增 0 个区**——收起 / 展开共用同一格。
  - **收起态(常驻)** = 固定预留高度的**单行**,显示最新一条条目。**双方回合都常驻有内容**:玩家回合里是自己打出的牌与它引发的触发链。
  - **展开态** = 点按升起的半屏面板(可上滑),内容是**本场**战报的**因果树**:按**一次结算批次**分组并缩进——一次出牌与它引发的整条触发连锁归为一组;整体**按回合分组**,默认定位到最新一条。

    ```
    第 3 回合 · 我方
      打出「叠嶂符」
        └ 触发「山岳共鸣」      对方道念 −5
        └ 削减 8(对方仅剩 5,溢出 3 未结转)
    第 3 回合 · 敌方
      打出「回风诀」
        └ 目标已不存在(未生效)
    ```

    **因果树是「栈与战场的连锁可读性」的承担者**:玩家读不懂触发连锁,是因为看不到「谁引发了谁」,而扁平列表给不出这一层。因果关系由栈条目**既有的来源引用**承载,字段面权威见 `systems/services/combat-service.md`——UX 侧不新造字段名。
  - **条目粒度 = 结算事件,不是卡牌**:卡牌结算、触发式异能、疲劳扣减各占一条,保证「我的道念为什么少了 3」有账可查。
  - **保留本场全部条目,不设条数上限。** 战报不落存档,故上限省的是内存而非存档体积;一场 `Standard` 是 10 个回合,量级不过几十条结构化条目。设上限恰好废掉战报自己的理由——「第 3 回合我的道念为什么少了 3」正是要翻回去才答得出的问题。
  - **不进战斗存档。** 退出重进后战报从空开始,**代价明写接受**:「选目标态必须自解释」这条硬要求的承担者是**选目标态的指令条**,它本就不依赖战报。依据既有先例「为一条呈现便利新增一个存档字段不划算」,以及 `ActiveCombat` 的量级护栏与「本块新增的字段只有一格」的克制取向。
  - **展开态在结算态可开,在选目标态禁用。** 结算态玩家无输入,展开态可随时开且**演出不停、不设暂停控件**,列表照常流式追加新条目。选目标态则**只保留收起态单行、禁用展开入口**:展开态是半屏面板,会压住栈区与部分合法目标,而「栈区保持可见且不被压暗」「合法目标不被压暗」「暗幕只压暗决策必需信息之外的一切」三条是承重;叠加「单点即确认、不做二次确认、误触不做保护、该步已落存档」,遮挡会直接抬高误触率。
    - **判据一句话:禁用与否看的是「是否与决策面争抢屏幕或语义」。** 随身抽屉一类可能改变局面的入口争的是**语义**(点按语义与选目标态相撞);战报展开态争的是**屏幕**。**纯只读不是豁免理由。** 这是有判据的分化,不是漂移。
  - **三个消费者读同一条呈现事件流**:飘字 · 收起态单行 · 展开态因果树。三处各自去结算返回值里捞增量,迟早不一致;负载形状(类别、侧别、来源引用、增量值)的权威在 `systems/services/combat-service.md`,UX 侧不复述字段面。
  - **条目存结构化数据,渲染期才套 `res://text/` 翻译键**,不存已格式化的字符串——否则战报会成为本作最大的一处文案字面量泄漏源,且热路径上多出 `string` 拼接。
  - **占用固定预留高度(承重)。** 容器保留固定高度、内容变化不改变高度:工程形态 = `custom_minimum_size.y` 固定的 `Control`,变化的是其**子节点**(淡入 / 淡出),**容器本身不参与布局变化 ⇒ 动画不触发 `Container` 重排**。**这条纪律防的是「手牌区跳位干扰拖拽出牌的肌肉记忆」,与战报归属哪一方的回合无关**,且正是「拖出手牌区 = 打出」所依赖的。
  - **「元素上移(回收空间)」排除**:每回合两次重排,手牌区跳位已被明确点名为不可接受。
  - **落位与尺寸**:紧贴道念对比条(与道念对比、剩余回合数同属决策面板一组);尺寸 **≈ 屏高 6%** 为初值(单行文字),**写成百分比 / `SizeFlags` 比例而非像素常量**(`stretch/mode = canvas_items` + `aspect = expand` 下像素常量无意义)。**单行,永不换行**(换行会引起高度变化,与固定高度矛盾),超长文本省略并由展开态承载。
  - **动画**:本场第一条到达时淡入 **0.20 s**、战斗结束时淡出 **0.15 s**,**无高度动画**——这正是固定预留的收益。
  - **若实测排不下的压缩顺序**:先压敌方区(立绘可缩)→ 再压栈 / 战场(可做浮层而非常驻)→ **双方道念位最后动**(它是主视觉与核心决策面)。
  - **不上提为跨事件类型的 `eventLog`(边界)。** 战报只属于 Combat,**不外延到 Exchange / Research / Explore / Travel**。三条理由:
    - **会制造第二权威。** `PastEventEntry`(`SelectCost` / `AppliedChange` / `EventOutcome` / `Unchosen`)已经是「一个事件里发生了什么」的事实来源,且已被剧本调制、履历、诊断三方消费。再立一份「记录事件中有意义的决策」的日志 = 同一批事实的第二份表,两份各自漂移而无机制发现。
    - **非战斗事件没有可记的时间轴。** 其余四类都是单决策点事件(择一 → 结算 → 收口一次 `TryApply`)。战报存在的两条前提——**LIFO 栈使因果链长于 1**、**敌人不作事前预告故事中呈现是唯一情报通道**——一条都不外延。
    - **非战斗事件里唯一「值得记」的东西恰好必须隐藏。** 玩家自己选了什么他知道;他不知道的是道心 / 煞气 / 寿元被推了多少、剧本被怎么调制——而那正是「给方向不给数字、调制是隐藏属性的主要显影通道」所要遮住的(见 `systems/adventure-event/plot-manager.md`)。诚实的 `eventLog` 会掀开这层;不诚实的只剩「你选了 A」这种零信息条目。
    > **一句话纪律:一个权威、两种寿命——事件内的过程态是纯呈现层、不落存档(战报);事件间的账目归 `PastEventEntry`、落存档。**
- **战斗屏再多两个可读对象:本场可用道具区与神通 / 法则条。** 卡牌不再只有一个来源区,呈现层要跟着补:
  - **本场可用道具区** —— 竖屏空间紧张且它不像手牌那样每回合变化,**建议默认收起为一个角标(显示可用道具数),点开为抽屉式面板**,不值得常驻占位。**措辞上不要在战斗语境里称它为「储物袋」**:储物袋是元界面里的持有物全量视图(含大量战斗外道具),战斗里出现的只是它的一个筛选视图;**敌人没有储物袋却同样有道具**,也证明这两个概念必须分开。该区**同时呈现两级持有物**(轮回级法宝 + 账号级古宝),条目上带 `AbilityScope` 标识来源——两级的规则面权威见 `systems/player-profile/player-item/_index.md`,UX 侧不复述。
  - **神通 / 法则条** —— 贴在己方战场区边缘的一排小图标。`Power` 因不可交互,**视觉权重应低于常规永久物**。**详情须长按查看** —— `ui-input-rules.md` 禁止 hover-only 可供性。**启动式异能的启动入口落在长按升起的那个弹层内**(bottom sheet,复用既有控件语言),**图标条本体保持纯只读**——详情与启动键合一,同一排图标上不并存两种手势;可发现性由图标上一个**静态启动可供性标记**补偿(标记形态待竖屏分区专场)。**只读层不列被禁用的神通 / 法则**——被禁用者根本不入场,见 `systems/character-profile/power/_index.md`。
  - **埋伏标记（必做项）** —— 对手场上「有一张埋伏」的指示(**只给计数,不给内容**);**双向对称**,玩家与 AI 读到的是同一层信息。**埋伏进入敌人卡池**,故这块指示是必做的。它**挂在战场区**(埋伏是面朝下的战场条目),不与战报混住——一个是「场上有什么」,一个是「刚刚发生了什么」。
  - **卡面须呈现类型标识(适用于会以卡面出现的类型)** —— 五类卡牌(法术 / 阵法 / 道具 / 神通·法则 / 业障)靠**卡框色 + 类型角标**区分,**不用纯文字**:竖屏卡面横向空间紧,且「法术 / 法宝」等相邻中文名共用字根,只靠文字读不开。
- **战斗内持有物面板按「可操作 / 只读」分两层。** 战斗内需要被查看或使用的持有物有四种(法宝 / 古宝 / 神通 / 法则),它们按**能否被操作**归两层,而不是按数据归属分:
  - **可操作层 = 随身**(角标 + 底部抽屉):按 `UsableScene` 筛出的本场可用道具,可直接使用;抽屉内同时呈现两级并带 `AbilityScope` 标识。派生规则 = 按 `UsableScene` 筛 + 一条禁用过滤,权威见 `systems/character-profile/item/_index.md` 与 `systems/services/combat-service.md`。
  - **只读层 = 神通 / 法则**:本身不承载操作,长按查看详情;启动式 `Power` 的启动键落在该弹层内。
    - **启动键的灰态与长按原因由服务算好交给 UI,呈现层不自行重演规则**——每条启动式异能的费用、本场剩余次数、能否启动与不能启动的原因,取自 `CombatSnapshot` 中该战场条目上的 `ActivatableAbilities`,字段面权威在 `systems/services/combat-service.md`,UX 侧不复述。**启动被拒时不弹 toast**:`Accepted == false` 时只回到原态,解释由灰态 + 长按承担——与选目标态「不做『点非法目标弹提示』」同一条纪律。拒绝文案走 `COMBAT_` 分区普通键(本地业务拒绝无后端 `code`,**不占 `ERR_` 前缀**),见 `ux/error-and-blocking-ux.md`。
  - **弹层与随身抽屉同规格禁用**(敌人回合 / 结算中 / 选目标态禁用入口)。依据上面那条判据「禁用与否看的是「是否与决策面争抢屏幕或语义」」:启动键争**语义**(它可能改变局面),半屏弹层争**屏幕**(压住栈区与合法目标),两种争抢都构成禁用理由,故不为它另立一套规格。
  - **功法与货币不进战斗 HUD。** 功法在参战方组装时已展开为卡牌、战斗内不感知功法(见 `systems/character-profile/deck/_index.md`);货币在战斗内无用途,灵石与仙玉的非战斗查看落点见 `ux/screen-flow.md`。
  - **卡组构成查询不在此收口**:不为它单开面板,复用抽牌堆信息面,形态待战斗 UX 专场(「抽牌堆剩余张数是否常驻」本身仍是待决项)。
  - **只读层的形状**(角标 vs 常驻一排小图标)本处不裁定——它与竖屏分区排布同一个问题,归已排期的专场;本条只定分层原则。
- **神通 / 法则的呈现气质是技能感,不是卡牌感。** 参照武将技能栏——被动常驻、身份绑定、少而精;UI 上它们**不应长得像手牌**。这与 `CardType.Power` 的机制定位一致:开局入场、受保护、不可针对、**永不入栈也不产生弃牌堆流量**(见 `systems/services/combat-service.md`)。
  - **卡面形态的适用面**:战斗内 `Power` **一律以技能条目呈现**;**卡面形态只用于图鉴 / 详情卡 / 奖励与置换选择面**。理由:它在战斗内从不以一张牌的姿态出现,卡面的类型标识对它本就是空转;而奖励 / 图鉴面需要与其他族并排,保留卡面成本最低。
  - 技能条目的**信息密度**(是否显示名与一行效果文字)与只读层形状同归竖屏分区专场,本条只定气质与适用面。
- **不做「敌人状态可读」的事前补偿(已否决)。** 「以蓄力 / 凝聚 / 破绽等显式状态标记预告敌人下一步」的方案**明确否决**——那是换个名字把事前预告装回来。事前信息一律归敌人图鉴(它会做什么),事中信息一律归逐步呈现(它做了什么)。
- **敌人图鉴给静态知识,不给动态情报。** 账号级敌人图鉴(`systems/player-profile/codex/`)记录「这个敌人**会做哪些事**」;它**不揭示本回合的具体行动**。**这条边界的理由是「事前知识 / 事中情报」的分工**。**图鉴是事前知识的主通道,而事前知识的查阅与兑现集中在开打之前——全部图鉴在战斗内一律不可查阅**:战斗屏没有任何图鉴入口,战斗内的可读性完全由事中呈现(飘字 + 战报)承担。**首遇的信息差就是这场遭遇的风险定价**,战前准备的分量正来自「进场前能看到什么」与「进场后只能看它做了什么」这条切分。已解锁敌人的词条在战斗前确认页呈现,见 `ux/screen-flow.md`。
- **战后奖励面板是战斗流程的一屏(新增)。** 「获取奖励」属于战斗流程本身,故战斗结束后**在战斗流程内**呈现奖励:**强制部分自动计入**(无需玩家操作,例:`experiencePoint`),**可选部分逐项列出、由玩家逐项领取或跳过**——形态**参照 Slay the Spire** 的战后奖励面板,**不是三选一**:三项各自独立,可以全领、也可以一项不领。**推论 ①:这是战斗 UX 至今未有的一屏**,且它在返回结果之前,不是事件收口后的另一步。**推论 ②:面板须能表达每一项的三种态**(未处置 / 已领取 / 已跳过),且已处置的项**不允许反悔**——面板上没有撤销,也没有"放弃全部"按钮(一项都不领是逐项跳过的自然结果)。**推论 ③:每一次领取 / 跳过都会落存档**(决策点 `D6`,见 `systems/services/combat-service.md`),而 UI **不必**为此表达"已存档"——与选目标态同理。**候选本身预先算定,退出重进得到同一组选项**,故也没有 reroll 的表达需求。具体形态(候选项呈现、已处置项的视觉处置、强制项的提示方式、竖屏布局)待战斗 UX 专场。
- **回合不是交互式的:stack 保留、交互与优先权移除（承重）。** 卡牌入栈后按 LIFO 结算,但**没有响应窗口、没有优先权传递**——**"我打完换你打"的简单交替成立**,理由是交互 / 优先权**拉长时长、决策点过多、复杂度高而深度收益小**。**推论 ①:不需要"轮到你响应"这套交互**(何时提示 / 如何 pass / 自动 pass / 超时),竖屏触控上最吃紧的那一环由此消失。**推论 ②:栈仍必须进入呈现层**——虽然玩家不再为"是否响应"读栈,但**触发式能力也入栈**,故栈深可以大于 1(见 `systems/character-profile/deck/`);玩家要看懂"现在有哪些东西在等待结算、以什么顺序",否则触发连锁不可读。**推论 ③:敌人的出牌仍要呈现**(敌人也持有卡组),但只在敌方回合内呈现,不再穿插进玩家回合。
- **回合的三步结构给了 UX 一条明确的时间轴。** **开始阶段**(归属方 mana 恢复至 `manaLimit` → 触发「回合开始时」→ 抽牌)→ **行动阶段**(唯一出牌阶段)→ **结束阶段**(触发「回合结束时」→ 清理回合内状态)。**三步是回合归属方的流程,双方不同时走。** **推论 ①:每回合有三个可被呈现的节拍**——mana 刷满、抽牌、以及结束阶段的触发 / 状态消散,动画节奏可依此编排,不必自创分段。**推论 ②:手牌上限需要在 UI 上可读**——上限是**任何时刻都不得超过**的硬约束(**没有弃牌机制**),故玩家必须能随时看出"我还能拿几张";满手时抽牌的表现要能被看见(见待决问题)。**推论 ③:"轮到谁"是一个必须常驻的指示**,它现在是回合归属权的唯一表达。具体形态待战斗 UX 专场。
- **结算会在中途停下来问「指谁」（承重）。** 触发式异能在栈上若需要选择目标,**那次目标选择是玩家的一次真实输入,也是一个决策点**(见 `systems/services/combat-service.md`)。**推论 ①:结算动画不能是一段不可打断的过场**——它必须能在中途停住、进入一个可交互的选目标态,再继续弹栈。**推论 ②:选目标态需要明确的进入 / 退出信号**,否则玩家会以为战斗卡住了(尤其在连锁触发中,停顿点可能出现在玩家没有预期的时刻)。**推论 ③:这不是「响应窗口」,呈现上必须区分**——玩家此刻不是在决定"要不要插手",而是在补全一个已经在结算中的效果的参数;措辞与视觉都不该暗示这是一次可放弃的机会。**推论 ④:这一步会落存档**,而 UI **不必**为此表达"已存档"(与战后奖励面板同理)。
- **战斗屏多了一个区:战场(battlefield)（承重）。** 场上**正在生效**的卡牌 / 持续状态 / 等待中的触发器落在 battlefield 上,与**栈**(等待结算的队列)是**两个不同的区**。**推论 ①:竖屏要容下三块**——战场 / 栈 / 手牌,再加上道念对比、回合计数与战报,窄高屏的分区压力显著上升(具体排布待战斗 UX 专场)。**推论 ②:玩家须能区分"已经在生效"与"正在等待结算"**——二者混成一片就读不懂触发连锁。**推论 ③:回合内状态的消散有了可视对象**——结束阶段清理的是战场上标记为回合内的条目,动画有了明确的落点。
- **满手时抽牌的表现:牌抽不进(规则已定)。** 满手时抽牌**抽不进**(牌留在抽牌堆、本次抽牌无事发生),「加入手牌」类效果同理落空——**规则已定,剩下的只是表现形式**。**推论 ①:需要一个"没抽进"的可见反馈**,否则玩家会以为抽牌漏了或界面卡了;**推论 ②:手牌上限本身要常驻可读**(「我还能拿几张」),否则满手是个突然出现的意外;**推论 ③:不会有牌被弃掉或销毁的画面**——上限是纯上界,不产生弃牌堆流量,视觉上不该出现"牌被丢掉"的动作。
- **道念差是玩家可直接换算的账。** 失败时 `lifeTotal` 的扣减量**就是道念差**(1:1),故战斗屏上的「我落后 8 点」同时就是「输了要掉 8 点 lifeTotal」——**这条 1:1 关系让主视觉的价值大增**:玩家不需要额外的教学就能读懂风险,也让「道念差是否显式呈现」这个问题的答案更倾向于「显式呈现」。
- **回合数不是固定的 10。** 10 回合是 **`Standard` 档的标准值**;`Practice` / `Finale` 档可改写回合数与胜负条件。**推论:「还剩几回合」的呈现必须由本场遭遇的配置驱动**,不能把 10 写死进 UI。
- **敌人等级的展示措辞。** **面向玩家一律用「境界名 + 层级」,全局序 1–22 不出现在任何 UI 上**(例:「筑基中期」「炼气十三层」)。
  - **理由(最强的一条):境界名让 `baseMomentum` 的跨度断层可读** —— 「筑基巅峰 vs 金丹初期」一眼就是跨境界,而跨境界正是起跑线的量级跳变处(32 → 45);「17 vs 18」看不出来。**起跑线就是「这场有多难」的唯一刻度**,故让它可读是等级展示的全部目的;全局序是内部比较刻度,不是玩家词汇。
  - **`EventOption` 的战斗类卡片上并列显示双方等级**(`我 · 筑基中期 ⟶ 敌 · 筑基后期`)——把比对成本降到零,而不是要求玩家记忆。
  - **战斗屏内敌人区常驻一行敌人境界名,但不并列玩家自身等级、不常驻**(玩家知道自己是谁;竖屏空间已是本作压力最大处),需要时在角色面板查看。
  - **不做方向标记**:`↑` / `=` / `↓` 一类由两个等级机械导出的符号**一律不加**——它同时把「日后被扩成三色 / 加文字 → 滑向模糊危险度档位」的风险从根上掐掉。任何主观危险度词汇(「略强」「凶险」「无从揣度」)照旧被否决。
  - **已知代价**:境界名不利于表达带内细微差(ch2 · ch3 只有四个层级名,`diff = ±1` 就是相邻两个词,玩家读得出差一档但读不出「差一档意味着 `baseMomentum` 差多少」),且比对成本回到玩家自己身上——**接受**,这正是「精确标注、不做主观解读」的直接体感。
- **选目标态的呈现形态。**
  - **规则层先削掉一半的进入次数:合法目标集合大小为 1 时自动选定,不进入该态、不产生决策点、不落存档。** 这条**一并缓解三个问题**(连锁打断次数 / 决策点密度 / 操作疲劳),是本节最有价值的一条,**且它是规则层的、不只是呈现层的**。(合法目标为 0 时按既定的效果落空规则处理,同样不进入。)
  - **进入信号** = 全屏低透明度**暗幕**(≈45%)0.15 s 淡入,压暗一切非决策必需元素;**双方道念位与栈区豁免不压暗**——前者是判断「该指谁」的依据,后者是「队列里还剩什么」的唯一来源。**暗幕因此是「压暗除决策必需信息外的一切」,不是字面的全屏。**
  - **来源指示**:栈上的该条目**上浮 + 放大 1.1× + 描边**,一条引导线连向指令条——**连锁中玩家必须知道「是谁在问」**,否则第三次弹出时完全失去上下文。**指令条位置绝对固定**(屏幕中部偏上,道念对比条与栈之间),每次进入同一位置、同一套视觉:**节奏可预期 = 不迷失**。
  - **合法目标**不被压暗 + **描边呼吸动画**(1.2 s 周期,静态描边在小屏易被忽略);**非法目标随暗幕压暗、点击无反馈**——压暗即答案,**不做「点非法目标弹提示」**(连锁中反复弹提示是噪音)。退出总时长 ≤ 0.4 s。
  - **指向手势 = 单点即确认**,不用拖拽连线:拖拽要求精确的起点落位与长路径,而起点(栈条目)在屏幕中上部、终点可能在顶部敌方区或底部手牌,**竖屏单手拇指跨不过去**;连锁中可能连续进入 2–4 次,**任何多余的操作都要乘以次数**。**也不做二次确认**——误触代价用「目标足够大 + 呼吸描边足够醒目」化解,而不是用二次确认换(那把每次操作翻倍)。**误触不做保护**(与「玩家主动退出静默处理」的手感取向同向);**已知代价**:一次误触在连锁中可能改变结算结果,且该步已落存档、退出重进也回到误触之后。**退让位**:若实测误触率高,退到「点选 + 确认键」,且只在合法目标 ≥ 4 个时启用。
  - **连锁中不迷失的四条**:① **连锁进度可见** —— 指令条第二行常驻 **`还有 N 项待结算`**(= 栈深,**永远可算**;不用「还有 N 项待选」——后者要求预知后续条目是否需要目标,而那依赖前面的结算结果,未必可精确预知)。**这是把「不可预期的停顿」变成「有限的、可数的停顿」,是四条里最关键的一项。** ② 位置绝对固定。③ **连续两次之间不完全淡出暗幕**(只交叉淡变来源高亮与文案,0.2 s)——避免全屏明暗闪烁,同时让「这是一段连续结算」在视觉上成立。④ **栈区保持可见且不被压暗**。
  - **措辞与「响应窗口」严格区分(三条禁令)**:文案用「选择一个目标」「指定」,**不用**「是否响应 / 跳过 / pass / 等待你的回应」;控件上**无取消键、无跳过键、无「不使用」**;**无倒计时、无超时自动选**(倒计时暗示「不选也会过去」,与「不可放弃」矛盾)。
  - **硬要求:选目标态必须自解释。** 玩家可能退出后隔几小时回来,正对着一个「请选择目标」的界面——呈现层必须交代**是哪张牌 / 哪个异能在要求选目标、它要做什么**,**不能依赖玩家的短期记忆**。恢复语义(回到该选择点、栈原样挂起、不允许反悔)见 `systems/services/combat-service.md`。
  - **道具使用后若需目标,直接进入这同一套形态,不另做一套。**
  - **整套形态与其频次相称,不因低频而削减。** 它服务的是「需要选目标的触发式异能 ≤ 10%、一场期望进入 1~2 次」的场景,而**这正是本作少数几个真正的战斗内交互时刻——密度低是它有分量的原因,不是削减它的理由**。暗幕 / 呼吸描边 / 固定指令条 / 连锁进度 / `pending` 存档形态**全部保留**。
- **战斗内的道具视图称「随身」,不称「储物袋」(形态落定)。**
  - **默认收起为角标**(小图标 + 本场可用道具数),贴在**己方战场区边缘**,与神通 / 法则条**分居两侧**——两者都是「己方的非手牌资源」,**对称落位让玩家一次学会两处**。
  - **点按 → 底部抽屉(bottom sheet)**,高约屏高 40%,其余半透明压暗:底部是竖屏拇指可达区,且抽屉是移动端母语控件、不需要教学。
  - **抽屉内 = 横向滚动的一行**(不是网格):本场可用道具通常 ≤ 8 件(`UsableScene` 筛出的子集远小于储物袋全量),一行足够;**与 EventOption 选择区的横向滑动手势一致**,玩家复用同一套肌肉记忆。
  - **不可用项灰显 + 长按给原因**(mana 不足 / 非行动阶段 / 栈非空)——**灰显即答案,不做点击弹提示**。**使用流程**:点按选中 → 抽屉自动收起 → 若需目标则**直接进入选目标态**(复用同一套形态)。
  - **敌人回合 / 结算中:角标置灰、抽屉入口禁用** —— 使用窗口是全局规则,UI 应把它表达为**可供性的有无**,而不是让玩家点了才被拒。
  - **⚠ 竖屏分区压力**:己方战场区左右两侧同时挂法则条与随身角标会挤压战场本身的可用宽度,**需在实际排版时验证**。
  - 元进程侧的储物袋落位与全屏面板形态见 `ux/screen-flow.md`。
- **卡面是全幅插画(full art)（承重）。** 卡牌为整图,**卡面上的文字信息只有 `manaCost`**——无规则文字、无卡名。规则描述、卡名、关键字、`Power` 的明示内容一律后置到**点按升起的详情页**。呈现哲学一句话:**卡面极简,信息后置到详情页与战报**。
  - **非文字的 UI 叠加保留并因此升格**:五类卡牌(法术 / 阵法 / 道具 / 神通·法则 / 业障)仍靠**卡框色 + 类型角标**区分(**适用于会以卡面出现的类型**),它们是呈现层 UI、与插画分开生成(UI 需要可九宫格拉伸)。在 full art 下它们是卡面上**唯一的非 `manaCost` 呈现元素**,其权重与可辨性随之升格。
  - **硬约束:插画内不得烧入任何承载可翻译语义的文字 / 字符。** 卡名 / 规则文字若烧进插画,等于把语言数焊进美术资产——切语言时静默留在中文,且失去热更通道,与「UI 文案一律走 `res://text/` 翻译键」的承重纪律相抵。(装饰性的符文 / 印章 / 书法笔触一类不承载语义的图形不在此限;判据与豁免的权威在 `art/visuals/art-direction.md`。)
  - **缩略可辨是玩家在手牌区认牌的唯一通道。** 手牌区的卡面很小,而 full art 下没有卡名可读——插画主体必须在缩略尺寸下仍能辨认,**且跨卡之间彼此可区分**(剪影 / 主色 / 构图有别),否则一手牌读不开。
- **手势分工:点按手牌 = 升起详情页,拖出手牌区 = 打出（承重）。** 卡面无文字使「点按看详情」成为刚需,故它必须与出牌手势显式分工。两者都是触控原生手势,不依赖悬停。
  - **详情入口的手势按「对象是否可拖拽」分化**:**可拖拽**的对象(手牌)用**点按**开详情;**不可拖拽**的对象(关键字定义、`Power` 详情、灰显道具的不可用原因)用**长按**。理由:长按与拖拽起手在同一根手指上争同一段时间窗,而手牌是战斗屏唯一同时承载拖拽的对象。**这条判据必须留在文档里**——否则日后读者会把两种手势并存读成漂移。判据的辖域仅限**详情入口**;「点按」在别处另有语义(随身抽屉内点按 = 选中使用、选目标态单点 = 确认),不是一张通用手势表。
  - **详情页复用既有的 bottom sheet 控件语言**,不另造控件:战斗屏内的先例是随身抽屉;库内另一处先例是战斗前确认页的功法词条(见 `ux/screen-flow.md`)。
  - **选目标态中手牌的点按语义被该态独占**:`HandCard` 槽位使手牌可成为合法目标,而该态已定「单点即确认」,故该态下点按手牌 = 指定目标,不升起详情页。
- **关键字只印名字,完整定义走长按(宿主在详情页)。** 卡面无文字,故关键字名与完整定义**一并落在详情页**:详情页印关键字名,长按展开 `KeywordData.ReminderText`——`ui-input-rules.md` 禁止 hover-only 可供性 ⇒ 触控等价物只能是长按。**永远长按,首次出现不自动展开**:「首次」这件事要记账(落哪个 Profile？跨轮回还是轮回内？),**为一条呈现便利新增一个存档字段不划算**。若实测新手看不懂,自动展开一次是现成的退让位(属实测调整)。关键字的形态见 `systems/character-profile/deck/common-properties.md`。
- **多目标槽位的询问顺序 = `slotIndex`。** 一张牌有多个目标槽位时,UI **在打出前按 `slotIndex` 顺序逐个问、一次收齐**;**各槽位的类别由选目标态的指令条按同一顺序点名**(「摧毁目标阵法」而非「摧毁目标」)——否则玩家不知道自己现在在选哪一个。指令条本就「必须自解释」、位置绝对固定、常驻连锁进度(见上),故这项告知**不新增任何部件**。
- **静默退出的告知责任落在战斗屏。** 玩家主动退出**不做二次确认弹窗**(手感优先,不在最频繁的操作上加模态);代价是「进度保留在当前决策点、成本不退还」这条规则玩家看不见——**须由战斗屏的常驻措辞或首次退出时的一次性提示承担告知,不是弹窗流程**。
- **进入战斗前的同步失败不产生任何额外提示。** 告知由**常驻的「离线 · 待同步 N」指示**承担——**该指示在战斗屏内必须可见**(这是本条成立的前提)。理由:断线期间**每一场**战斗的入口都会命中这条路径,在此弹 toast 等于把一次性的网络状态变成**逐场重复的打扰**,且时机恰是玩家最专注处。**这与「静默退出的告知责任」是同一条纪律的第二个实例**:不在最高频操作上加提示,告知由别处的常驻呈现承担。**边界**:真正需要打断玩家的情形仍由既定机制承担——缓冲超限的软阻塞模态(下一次事件选择前)与两处硬阻塞(启动 pull 失败、被挤下线)。规则侧见 `systems/services/sync-service.md`「`Immediate` flush 的失败语义」。
- **寿元红字倒数不进战斗内。** 寿元告警的呈现位置已定为 **EventOption 选择界面**的静态标注,**不常驻战斗屏幕**、不做全局 HUD。见 `ux/screen-flow.md`。
