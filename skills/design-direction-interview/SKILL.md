# Design Direction Interview

`/provide-solution-draft` 是**推演**：把一个可由既有决策 + 通行做法推出答案的问题写成提案，interview 被刻意压到最少（0–2 项取向）。本技能是它的**反面**：面向那些**没有客观最优解**的重大方向问题——玩法手感、UI/UX 基调、数值曲线的性格、让本作区别于同类的独有特色。这里 **interview 本身就是产出过程**：用户在会话中亲口回答艰难的抽象设计问题，每一个答复都是**拍板**，最后综合成一份方向定案式的设计草稿。

**两技能的分工判据：**

| | `/provide-solution-draft` | `/design-direction-interview`（本技能） |
|---|---|---|
| 问题性质 | 有通行做法 / 可由既有设计推演（偏工程向） | 纯取向——答案取决于用户想做一款什么样的游戏 |
| interview | 压到最少（0–2 项） | 就是主体——多轮、逐轴问透 |
| 产物语气 | **提案**（「建议 / 推荐」，待评审） | **定案**（用户当场拍板的方向陈述） |
| 产物文件 | `inbox/solution-draft-<slug>.md` | `inbox/design-draft-<slug>.md` |
| 范围 | 一个待答问题（可窄） | 一个重大主题（一次会话专注一个） |

拿不准走哪个：**一个有经验的从业者能不开会就给出答案 → solution-draft；必须由「这款游戏的主人」表态 → 本技能。**

流水线定位：
```
一个重大设计主题（战斗 UI/UX、数值手感、……）
  → /design-direction-interview <主题>        （本技能：拆轴 → 多轮 interview → 综合成稿）
  → inbox/design-draft-<slug>.md            （用户复核措辞——裁决已在 interview 中做出）
  → /analyze-new-ideas inbox/design-draft-<slug>.md   （按定案提炼进主题文档 + 移出相关待答项）
```

**范围守则（强制）：** 只作用于 `game-design-documents/`（设计方向 / 风格取向天然属客户端体验；不接受库参数，见 `.claude/rules/design-library-routing.md`）。只写 `inbox/design-draft-<slug>.md` 这一个草稿文件，外加在 `inbox/_index.md` 的「待处理」表登记一行。**不**改 `open-questions.md` 与 `open-questions/`、**不**改任何主题文档、**不**写 ADR、**不**碰 `handoffs/`、**不**碰代码、**不**评估 derive 就绪度。interview 中答定的待答项也**不**在本技能内移出——移出与 answer-log 归 `/analyze-new-ideas` 提炼时一并收口。**无批量版**：一次会话专注一个主题，这是刻意设计——方向问题需要用户全程在场逐轮作答，扇不出去。

## 步骤

### 1. 锁定主题（一次一个）
解析 `$ARGUMENTS`：
- **主题词**（如 `combat-ui-ux`、`战斗数值`）→ 采用；先在 `open-questions/` 各分片与主题文档的待决小节中检索该主题下已登记的取向类问题，纳入第 3 步的问题域。
- **空（无参数）** → 列出候选主题供用户选：从 `vision/pillars.md` 的支柱、`systems/_index.md` 的系统清单、`open-questions/` 各分片中**标注为取向 / 手感 / 基调类**的待答项归纳出 5–8 个候选大主题（每个附一行「悬着什么」），询问处理哪一个。
- 主题过大（一场 interview 问不透，如「整个战斗系统」）→ 先与用户切分出本次的子主题，其余明确留给后续会话。

### 2. 读全上下文（问之前先读）
提出的问题必须站在既有设计之上，绝不问已经定过的事。必读：
- `vision/scope.md`（范围 / 硬约束 / anti-goals）与 `vision/pillars.md`——支柱是方向问题的裁决基准。
- 该主题涉及的**每一份**主题文档（`systems/` / `art/` / `ux/`）：既有 `## 意图` / `## 决策` 与待决小节。
- `terminology.md`——用本作的领域词提问，不自造术语。
- 相关 `decisions/ADR-*`——**已固化的决策是硬边界**：它们框定选项空间，而非重新拿出来问。
- `open-questions/` 中该主题的分片 + 相关 `answer-logs/log-*.md`——已答定的不再问；已否决的方向不当新选项端出来。
- 同类作品的公开设计参照（Balatro / Slay the Spire / 月圆之夜等）——用于给选项配「参照系」，让抽象问题变得可比较。

### 3. 把主题拆成取向轴（interview 的题库）
把主题分解成**取向轴**（decision axes）：每根轴是一个「本作在这个维度上站在哪里」的问题。逐轴分类：
- **已定** —— 既有决策 / ADR / 支柱已经回答 → **不问**，作为约束列进草稿的「既有边界」。
- **可推演** —— 有通行做法或工程常识默认（错误处理、结构常规、标准参数）→ **不问**，记为「配套默认」附在草稿末尾（`/analyze-new-ideas` 提炼时按 🔵 采纳）。发现整个主题大半落在这一类 → 停下来告诉用户该走 `/provide-solution-draft`。
- **真取向** —— 无客观最优、答案定义本作的性格 → **这是 interview 的正题**。

真取向轴的组织：
- **按承重排序**：先问会框定其他轴选项空间的（先「战斗的情绪基调是紧张算计还是爽快连锁」，后「伤害数字要不要飘字」）。
- **每轴出成一道自包含的题**：这个维度为什么重要、2–4 个候选站位、每个站位的**下游后果**（牵动哪些系统 / UX / 数值结构）、**参照系**（同类作品各自站在哪里）、以及你的推荐与理由（依据支柱，不是个人偏好）。
- **敢问难的**。本技能存在的意义就是逼出那些用户一直没空面对的抽象抉择——「失败在本作里是惩罚还是学费」这类问题不要因为难以启齿而降级成实现细节题。

### 4. 多轮 interview ⏸️（本技能的主体）
用 `AskUserQuestion` 逐轮提问，每轮 ≤ 4 题、按承重排序，推荐项放第一个并标注「(Recommended)」。与 `/analyze-new-ideas` 的一次性澄清门不同，**本技能预期多轮**：
- 每轮答完，把答复带回题库：上一轴的裁决会收窄或改写后续轴的选项（用户选了「爽快连锁」，数值轴的选项就该重构再问）。有新分叉就补题，不硬按预设清单走完。
- 开放式、无法枚举站位的问题（「用一句话说这款游戏的战斗想让玩家记住什么」）直接以文字提出，让用户自由作答。
- 用户答复与既有决策 / ADR 冲突 → 当场点明冲突与代价，问清是否有意推翻。**有意推翻记入草稿的「张力」区**，由 `/analyze-new-ideas` 提炼时执行改写——本技能不改 ADR。
- 用户对某轴答不出、想留到有 demo 再定 → 尊重，记入草稿的「留白」区，不逼答、不代答。
- 用户说「按你推荐的来」→ 该轴按推荐**定案**（视同拍板），在裁决记录中注明「用户授权按推荐定案」。
- 收束判据：承重轴全部有了裁决（或明确留白），且用户确认没有想补的方向 → 进入综合。

### 5. 综合成 design-draft
写到 `game-design-documents/inbox/design-draft-<slug>.md`（顶层 = 在办；提炼后由 `/analyze-new-ideas` 移入 `inbox/archive/`）。`<slug>` 取主题的短横线小写英文（如 `design-draft-combat-ui-ux.md`）；同名已存在 → 追加 `-2`（若确认是同一主题的重做，先问是否覆盖）。

```markdown
---
type: design-draft
date: <YYYY-MM-DD>
topic: <一行主题陈述>
targets: <应提炼进的文档路径清单>
status: awaiting-review
---

# 设计方向 — <主题>

## 方向陈述
<3–6 句话的定案式陈述：本作在这个主题上是一款什么样的游戏。这是全文的提纯，
 要能独立成段地回答「它和 Balatro / StS 在这里有什么不同」。>

## 独有特色
- <让本作在该主题上区别于同类的具体特色——来自 interview 裁决，不是善意脑补>

## 既有边界（interview 未重新讨论）
- <框定本次选项空间的既有决策 + 来源（ADR / 支柱 / 主题文档）>

## 逐轴裁决
### <轴 1：一行轴陈述>
**裁决：** <用户选定的站位——定案语气>
**理由：** <用户给出的 / 认可的理由>
**后果：** <这个站位对系统 / UX / 数值结构意味着什么>
（被否决的站位与否决理由，一行带过——理由承重的才写）

### <轴 2>
...

## 张力
<裁决与既有决策 / ADR 相抵、用户明确有意推翻的项：冲突哪一条、推翻的代价。无则写「无」。>

## 留白（用户明确不在本次定的）
- <轴 + 用户为什么留（缺什么信息 / 等什么验证）>

## 配套默认（可推演项，非 interview 裁决）
- <有标准答案的配套细节 + 依据，供提炼时按 🔵 采纳>
```

- **「逐轴裁决」用定案语气**（「战斗基调是 X」而非「建议 X」）——这些是用户当场拍的板，与 solution-draft 的提案语气刻意相反。但**只有 interview 裁决过的才配这个语气**：你补的结构、措辞、后果推演若超出用户答复的逻辑必然，一律降级进「配套默认」或「留白」——**绝不把自己的品味混进用户的拍板**（与 `/analyze-new-ideas` 的「充实 vs 臆造」同一条边界）。
- 保留领域术语原样（用 `terminology.md` 的词）；用户在 interview 中的关键原话值得直接引用——那是意图的一手记录。

### 6. 登记进 inbox 台账（强制）
在 `game-design-documents/inbox/_index.md` 的「待处理（ongoing）」表**顶部**追加一行：`文件 | 类型 | 日期 | 主题 | 下一步`。`类型` 写 `design-draft`；`下一步` 写 `复核措辞后 /analyze-new-ideas`。若表中是 `*（空）*` 占位行，用这一行替换。只动这张表。

### 7. 报告并交回
```
## 设计方向定案：<主题一行摘要>

- file: game-design-documents/inbox/design-draft-<slug>.md（已登记进 inbox/_index.md 待处理表）
- interview：<N> 轮 · 裁决 <M> 轴 · 留白 <K> 轴 · 张力 <J> 项

### 方向陈述
<草稿「方向陈述」的原文>

### 逐轴裁决
- <轴>：<裁决一行>

### 张力 / 留白
- <有则列，无则省>

### 下一步（复核措辞后直接复制运行）
/analyze-new-ideas game-design-documents/inbox/design-draft-<slug>.md — design-draft 的「逐轴裁决」为用户在 interview 中亲口拍板的定案，按定案提炼（不再当提案）；「留白」区保持 Open question；「张力」区列出的 <J> 项推翻已获用户确认，提炼时改写对应权威文件。作用于 game-design-documents/。
```

- 「下一步」提示词遵守 `/provide-solution-draft` 第 7 步的构造规则：完整路径、评审状态前提（这里是**复核措辞**而非评审方案——裁决已做出）、写库授权、顺带事项（有则一句话点明）。
- 若第 3 步就发现主题实为可推演的工程问题 → **不建草稿**，直接报告并指向 `/provide-solution-draft`。

## 无批量模式（刻意设计）

本技能**没有也不会有** `batch-` 版本：方向 interview 依赖用户全程在场、逐轮作答、答复实时改写后续问题——这个回路无法外包给 worker，也不该被合并 interview 摊薄。一次会话一个主题；多个主题就开多个会话。
