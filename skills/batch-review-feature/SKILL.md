# Batch Review Feature

编排规则见 `.claude/rules/batch-orchestration.md`。worker 执行的单会话技能是 **`/review-feature`**——链条追踪方式、逐项检查清单、严重度分级，全部以它为准。全程只读（`game-feature-branch/`），无共享写入面，因此没有 interview 与台账阶段，是最简单的批量形态。

批量的价值：一次覆盖多条链；**跨功能归因**——同一个 autoload / 信号 / 数据类的缺陷会在多条链上各自表现为一个 bug，逐条报告会把一个根因数成五个问题。

## 步骤

### 1. 圈定批次
- 给了清单 → 逐项作为一个分片。
- 空 → 读 `.claude/knowledge/systems/_index.md` 与 `scenes/_index.md`，列出**已落地**的系统 / 链条请用户圈选（不审尚未存在的东西）。
- 两条链共享大量入口时可并成一个分片，避免重复读同一批文件。

### 2. 并行审查（worker）
按 worker 契约派单执行 `/review-feature`（只读；不写任何文件；发现范围外的问题记「越界发现」）。报告按原技能的 🔴/🟡/🔵 分级落 run 目录。

### 3. 合并（orchestrator）
- **去重归因**：多个分片报同一文件同一问题 → 合一条，列出受影响的全部链条；同一共享部件的多个表象 → 归为一个根因条目（这是批量的核心增值，花力气做）。
- **交叉一致性**：各分片对同一部件的观察互相矛盾（一个说信号有订阅者、一个说没有）→ 复核后裁定，不双列。
- 全批按严重度重排；设计一致性红旗（实现 ≠ 设计库）单独列出。

### 4. 报告
```
## Batch review: <N> 条链

### 🔴 Bug（按根因去重，最严重在前）
- <file:line> <问题> —— 影响链条：<清单>；建议修复：<一句>

### 🟡 Warning / 🔵 Info
- ...

### 跨功能根因
- <共享部件>: 一个根因 × <k> 处表象（<原始条目归并清单>）

### 设计一致性
- <实现 vs game-design-documents 的偏差>

### 干净的链条
- <清单>
```
**不自动修复**（原守则）。修复建议按根因给，不按表象给。
