# Add Detail Log

排障期的**临时脚手架**：在目标方法里按下方清单高密度打点，让一次运行的输出足以复盘「走了哪条路径、每步拿到什么数据」。它与 `Context.md`「日志」条款的常态打点（关键状态转换处有意义的日志）不冲突——常态是**低密度基线**，本技能是排障期**临时加密**，事后由 `/remove-detail-log` 收敛回去。

**范围：只写 `game-feature-branch/`。** 四个 testing/production 快照目录只读；`backend-feature-branch/` 尚未开工，开工后再扩展。

## 打点位置（逐方法核对的清单）

- **方法入口 / 出口**：入参摘要（id / 关键字段，非整个大对象）；返回值或结果条数。
- **每次 `GetNodeOrNull` / `ResourceLoader.Load` / registry·字典查找之后**：命中与否 + 关键标识（与 `null-check-rules.md` 的校验共存，不替代）。
- **EventBus 信号发出前 / 接收处**：信号名 + 载荷关键值。
- **关键分支决策点**：命中哪个分支 + 决定条件的值。
- **循环批处理**：总数 → 逐条业务键（量大时每 N 条一次）→ 成功·失败·跳过计数。
- **异常与降级分支**、**存档读写前后**（含 schemaVersion 与关键字段）。

格式统一 `[System-Method]` 标签，例：`GD.Print($"[Combat-PlayCard] start card={card.Id} energy={state.Energy}");`。级别：主流程 `GD.Print`，可选缺失降级 `GD.PushWarning`，必需缺失/失败 `GD.PushError`（后两者通常已由 null-check 纪律要求，勿重复）。

## 硬边界

- **只增加日志语句，不改业务逻辑**：不调语句顺序、不抽方法、不改条件与返回值、不顺手修 bug（发现 bug 单独报告，交用户决定）。
- **日志表达式无副作用**：不在插值里调用会触发加载、状态变更或信号的方法；不为打日志提前消费迭代器/LINQ。
- **热路径豁免（Godot 特有，强制）**：`_Process` / `_PhysicsProcess` 及每帧回调内**不打点**（字符串插值即分配，违反 `csharp-godot-rules.md` 热路径纪律）——确需观测每帧状态时，只在**状态变化的那一帧**打，或打在触发该变化的事件处理器里。
- **耗时统计**：唯一允许新增的非日志语句是方法入口的 `var t0 = Time.GetTicksMsec();`。
- **集合打 `Count` + 关键标识清单**，不整体序列化大列表。
- 不留 AI 署名与生成标记；注释只描述业务。

## 步骤

1. **圈定范围**：有输入 → 定位目标文件与调用链，列出要打点的方法清单;无输入 → `git -C game-feature-branch status --porcelain` 枚举未提交变更的 `.cs` 文件，范围限定在这些文件本次改动涉及的方法。范围为空 → 报告后退出。
2. **逐方法盘点缺口**：对照上方清单列出缺哪类、在哪。`System` 名取该脚本所属系统（与既有日志标签一致），同一条链路共用同一个前缀。
3. **补写日志**：按缺口逐文件编辑，严守硬边界。
4. **自检**：`git -C game-feature-branch diff` 逐行确认除日志语句（与入口 `t0`）外没有任何其它改动；插值花括号配对；热路径内没有新增打点。
5. **报告** ⏸️：按文件列出新增打点（方法、条数、覆盖的类别）；因硬边界跳过未打的位置及原因；顺带发现但**未修改**的问题。**每次都提醒**：改动只含日志，建议单独成一次提交便于整体回退；本次打点属排障脚手架，`promote.cmd` 向 testing 线提升前先跑 `/remove-detail-log` 精简。

## 并行子代理

范围跨多文件时，可把第 1、2 步的**定位与盘点**按文件切分派发只读子代理（`Explore`）并发执行；第 3 步的编辑与最终报告留在主上下文（承 `CLAUDE.md` 派发规则：写文件不外包）。
