# Scaffold Content Type

把一个内容类型从「只有类定义」推进到「可以开始写条目」：产出 `game-design-documents/content/<类型>/_index.md`（**类型档案**）。

**这是一道闸门，不是一次建目录。** 本技能的价值全在第 2 步的**就绪度核对**——在类定义还不足以写出可实现的条目时把话说清楚，好过建一个空壳目录让 `/author-content` 在上面写出一份看起来完整、实则实现侧无法消费的文档。

**只作用于 `game-design-documents/`。** 内容层只存在于客户端库。

## 步骤

### 1. 定位类型

- 参数给了类型名（`location` / `地域` / `player-power` / `法则`）→ 在 `content/_index.md` 的类型登记表中定位它。
- **不在登记表里** → 这可能是一个**全新的内容类型**。停下确认：它在 `systems/` 里有没有对应的类文档？没有 ⇒ 归 `/analyze-new-ideas`（先有类定义才谈得上条目），**不要在此发明一个类型**。有 ⇒ 与用户确认类型名、中文名、代码类型，本次一并补进登记表。
- **已开张**（文件夹已存在）→ 报告现状并询问意图：是要**刷新**类型档案（类定义有更新、字段清单该重对一遍）还是走错了技能（写条目走 `/author-content`）。刷新是合法用法。
- **无参数** → 读登记表，按「就绪度 + 依赖链」列出**当前最该开张的类型**（依赖已就位、readiness 最高的排前），请用户选。

### 2. 就绪度核对（本技能的核心 · 只读不写）

读该类型的全部 `class-authority` 文档（`systems/` 下的类文档）+ `systems/common-properties.md` + `content/_index.md` 的依赖链，逐项判定：

**2a. 字段是否成表。** 类文档里这个类型的字段是**已定案的一张表**，还是散落在意图段落里的若干提及？散落 ⇒ 先把字段汇出来给用户确认（这是本技能唯一允许的「归纳」动作，因为它不引入新决策，只是把已写下的东西列齐）；类文档明写「字段待定 / 载体定名待答」⇒ 🔴。

**2b. 上游依赖是否就位。** 按 `content/_index.md` 的依赖链检查：本类型引用到的其他类型，是否已开张、是否已有可引用的条目？

- 底座未开张（典型：卡牌 / 神通 / 法则 / 法宝 / 古宝依赖 `ability/` 的效果原语）⇒ 🔴，**这是最常见的阻塞**。
- 上游已开张但条目为空（典型：敌人依赖卡牌条目做样本卡组）⇒ 🟠，可开张但第一批条目会带悬空引用，须在档案里写明写作顺序。

**2c. 类文档的 `## 待决问题` 里有没有会改变条目字段形状的项。** 有 ⇒ 逐条列出，判定它是「会改变条目怎么写」（🔴 / 🟠）还是「不影响条目层」（🔵）。

**2d. 共有字段的适用面。** 对照 `systems/common-properties.md` 判定本类型是否挂载 `ContentEnabled` / `LocalizedText` / `Rarity` / `ExclusiveSource` / `SourceCode`——**判定依据一律引用那份权威的挂载面清单，不自行裁量**。清单没提到本类型 ⇒ 🟠，问一句。

**2e. 图鉴宿主判定。** 本类型是否是六本图鉴之一的收录对象（敌人 / 神通 / 法则 / 法宝 / 古宝 / 地域）？是 ⇒ 条目模板保留「图鉴词条」一节；否 ⇒ 在档案的写作要点里注明该节删除。

**裁定：**

| 结论 | 条件 | 处理 |
|---|---|---|
| 🟢 **可写实** | 字段成表、上游就位、无会改形状的待决项 | 直接开张 |
| 🟠 **部分阻塞** | 有 🟠 项，但主体字段已定 | **先 interview**，与用户确认后开张，把阻塞项写进档案的 Open questions 与就绪度节 |
| 🔴 **阻塞** | 字段未成表 / 底座未定案 / 有会改形状的待决项 | **停下，不建目录**。报告阻塞项与它们各自的归属文档，建议先跑 `/analyze-new-ideas` 补类定义 |

**🔴 时用户仍坚持开张** → 按根约定尊重用户裁决，开张并在档案顶部与 `readiness` 字段醒目标注 🔴 与阻塞清单，同时在报告中如实说明：在此之上写出的条目**不可 blueprint**。

### 3. Interview（存在 🔴 / 🟠 时强制）

用 `AskUserQuestion` 一次性问齐。典型问项：

- 本类型的**条目 `Id` 形态**——库级约定 `<内容类型>.<snake_case_slug>` 已定案，**照抄，不各自发明**；只需确认本类型的前缀词。**四类持有条目一律用全名前缀**（`character_item` / `player_item` / `character_power` / `player_power`），**绝不用裸 `item` / `power`**——那是次类型的主类型前缀，撞上即两套 id 无法区分。
- 字段清单里有歧义或缺失的那几行（它是必填还是可选？默认值是什么？）。
- 共有字段的挂载判定（2d 的 🟠）。
- 上游条目为空时，第一批条目的写作顺序。

每个问题给出选项的**后果**与**你的推荐项**（推荐项放第一个，理由依据既有设计而非偏好）。

### 4. 开张

1. **建 `content/<类型>/`**，以 `content/_TEMPLATE-type.md` 为骨架写 `_index.md`：
   - frontmatter：`type` / `code-type` / `class-authority`（列全，不只列一份）/ `opened` / `id-form` / `readiness`。
   - **字段核对清单** —— 每行 `字段 | 必填 | 这个条目需要作答什么 | 权威回链`。
     **只写字段名与回链，绝不复述类型定义 / 取值域 / 枚举成员 / 校验语义**（`content/_index.md` 的硬边界）。自检：这一行删掉回链之后，读者还能不能从本文件知道合法取值？**能 ⇒ 你已经把权威抄过来了，删掉它。**
   - **条目形状与写作要点** —— 这类条目相对通用骨架多出什么、最容易写空的地方。控制在几条。
   - **交叉引用表** —— 本类型的哪些字段指向哪些别的类型，以及悬空的后果。`/audit-content` 直接消费这张表，**写不全等于那条引用不会被检查**。
   - **就绪度与阻塞** —— 第 2 步的结论原样落盘，包括 🟠 / 🔴 项。
   - **空的条目台账**（保留表头 + 一行 `_(暂无)_`）。
2. **更新 `content/_index.md` 的类型登记表**：该行的「就绪度」改为核对结论、「开张」改 ✓。若本次是新类型，补一整行；若定下了 id 形态，把「⚠ 待用户确认」那段改写为确定的形态描述——**直接陈述结论即可，不加「已定案」戳、不写它取代了什么**。
   溯源：`Source:` 挂在**该小节末尾**（一个 `##` 小节最多一条），指向承载这次裁定的 handoff；**不逐行、逐条挂**。全文见 `/analyze-new-ideas` 第 6b 步「溯源三条」。
3. **不改 `systems/`。** 核对中发现的类定义缺口写进类型档案的 Open questions 并在报告中点名，由用户走 `/analyze-new-ideas`。

- <问项> → <裁决>
- （未触发时写「核对通过，未触发 interview」）
