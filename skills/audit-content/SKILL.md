# Audit Content

内容条目的**全量对账**。内容一多，悬空引用、撞名、池分布倾斜与漏填字段就不再靠肉眼能发现——这些错误的共同点是**都要到启动期校验或线上才暴露**，而那时现场已丢。

**只写两类东西：** 对账报告，以及**台账 / 索引的订正**（类型档案的条目台账、`content/_index.md` 的登记表）。
**绝不改条目的设计取值**——发现某条目稀有度定错了，报告它，由用户决定；改数值是 `/author-content` 的事，且要走它的 interview 门。

**判定对象只有 `game-design-documents/content/` 的条目。** 判定所需的阈值与字段语义**照常回链 `systems/` 的类定义与类型档案去读**——那是**参照只读**，不对被参照的文档作任何判定，也绝不改动它们。

## 范围

- **无参数** → 全量（全部已开张类型的全部条目）。
- **类型名** → 只审该类型，但**跨类型引用仍要检查两端**（否则悬空引用查不出来）。
- **条目 id** → 只审该条目及所有引用它 / 被它引用的条目。

## 检查项

逐项执行；每一项都要给出**具体的文件与行**，不给笼统结论。

### A. `Id` 唯一性与形态（🔴 级）
- 在**整个 `content/` 下**收集全部条目 `Id`，找重复。撞名 ⇒ 两条内容中必有一条线上不可见。
- 每个 `Id` 是否符合其类型档案的 `id-form`。
- 文件名与 `Id` 是否对应（`content/_index.md` 约定：文件名 = `Id` 去掉类型前缀）。

### B. 交叉引用不悬空（🔴 级）
- 读每个类型档案的**交叉引用表**，按它列出的字段逐个解析条目里引用到的 `Id`，确认目标条目存在。
- 反向核对条目 frontmatter 的 `references` 是否与正文实际引用一致（**漏登记 = 这条引用不会被后续对账检查到**）。
- 类型档案的交叉引用表本身有没有漏列的引用方向——正文里出现了某类型的 `Id`、但表里没有这一行 ⇒ 报告为表的缺口。

### C. 必填字段缺失（🟠 级）
- 拿每个类型档案的**字段核对清单**逐行比对该类型每个条目的字段填写表。
- 标 `⟨待定⟩` 的字段是**已知未决**（合法，但该条目不该是 `ready`）；**整行缺失**才是漏填。
- **`status: ready` 却仍有 `⟨待定⟩` 或非空 `## Open questions` 的条目 ⇒ 🔴**（签核语义被破坏，它会被当作可 blueprint 的输入）。

### D. 稀有度与抽取池分布（🟠 级）
- 按 `(类型, Rarity)` 统计条目数，对照 `systems/balance.md` 的权重表：某档权重不低却只有一两个条目 ⇒ 该档的抽取高度重复。
- 按类型档案里记录的池归属统计每个池的候选数；候选数为 0 或 1 的池 ⇒ 报告（抽取退化为定值）。
- 机制上近乎等价的同池同档条目 ⇒ 报告为候选重复（稀释池而不增加决策深度）。

### E. `ExclusiveSource` 与 `SourceCode`（🔴 级 · 方向相反易混）
- `ExclusiveSource != null` 的条目**不得**出现在任何抽取池的候选里。
- 成就奖励指定的每个条目：目标存在、且 `ExclusiveSource == Source.AchievementReward`。**两条缺一，成就奖励就可能空发**（论证见 `systems/player-profile/achievement/_index.md` 的三条校验）。
- 条目文档里把 `SourceCode`（记账 · 落持有条目）当成内容定义字段来写 ⇒ 🔴，它不属于内容条目。
- 判定一律回链 `systems/common-properties.md` 的并排对照表，不自行裁量语义。

### F. `LocalizedText` 覆盖率（ℹ 级）
- 每个面向玩家的文案字段：`zh` 是否填了（缺 `zh` ⇒ 🔴，那是默认回落语言）；`en` 缺失 ⇒ 统计为未翻译，**不是错误**（缺 `en` 是合法且默认的状态）。
- 输出一张按类型的覆盖率表。
- 内容文案被写成 `res://text/` 翻译键、或 UI 文案被写进条目 ⇒ 🔴（归属四问见 `ux/_index.md`）。

### G. 台账一致性（🟠 级 · 本技能可直接修）
- 类型档案的条目台账 ↔ `content/<类型>/` 的实际文件：缺行、多行、`status` 与条目 frontmatter 不符。
- `content/_index.md` 的登记表 ↔ 实际存在的类型文件夹：开张标记、就绪度是否过时。
- **以实际文件为准修台账**，并在报告中逐条列出改了什么。

### H. 硬边界越界（🟠 级）
- 条目文档 / 类型档案里出现**枚举成员表、字段取值域穷举、完整校验语义表述、C# 类型定义** ⇒ 违规（`content/_index.md` 的硬边界，可机械检查）。报告位置并给出压回「值 + 回链」的建议，**但不要就地删**——那可能删掉用户有意写下的东西，先问。

### I. 过程坐标渗入活文档（🟠 级 · 可机械检查）
`content/` 是活文档——它要独立可读，读者理解一个条目时不应需要打开一份 handoff。逐份扫：

```bash
grep -nE "已定案|推翻|取代|作废|原方案|由.*降为|handoffs/|\b0[0-9]-[0-3][0-9][a-z]?\b" content/**/*.md
grep -c "Source:" <每份文档>   # 应 ≤ 该文档的 ## 小节数
```
- 正文里的 handoff 日期戳（`08-12` 这类）、`handoffs/*.md` 路径、「推翻 X / 取代 X / 原方案」⇒ 报告位置。
- 「已定案」戳 ⇒ 报告——条目的每个取值默认就是当前定案，加戳等于没加。
- `Source:` 逐条挂而非逐小节挂 ⇒ 报告，给出合并建议。
- **只报告，不就地删。** 被删的可能是承重的**否决理由**（不写下来日后会有人重新提出同一取值）——那部分应改写为正面陈述保留，而非删除，这需要用户判断。判据与改写形态见 `/analyze-new-ideas` 第 6b 步「溯源三条」。

### J. 每个角色的可修功法池是否铺够（🔴 级）

角色的灵根决定它能修哪些功法，故**全池够用不等于每个角色都够用**——某个角色的可修池铺不够，它就开不出局，而这在启动加载前不可见。

- 逐个在册角色算出它的可修功法条目数（`Pool != Enemy` 且通过灵根修习准入），与该类型的取池余量阈值比对；低于阈值 ⇒ 🔴。
- 汇总各灵根档的功法条目数、无属性要求（通用）功法的条数与占比，并逐角色列出可修池大小。**通用功法占比异常膨胀**同样报告——它会把灵根辨识度稀释回「所有角色抽到的东西差不多」。
- 某个在册灵根成员没有任何 `Pool != Enemy` 的功法条目 ⇒ 报告（若无角色持有它则降为 ℹ）。
- **判定的阈值与准入规则不在本技能内复述**：按 `content/cultivation-technique/_index.md` 与 `systems/balance.md` 的阈值核对，准入判定式回链 `systems/character-profile/deck/_index.md`。**参照只读，不对这些文档作判定。**
- 两个类型任一未开张（条目数为 0）⇒ 本项跳过并在统计节注明「未开张」，不报为问题。

## 步骤

1. **读约定**：`content/_index.md`（硬边界 · id 约定 · 状态词汇 · 登记表）、每个在审类型的 `_index.md`（字段清单 · 交叉引用表 · 台账）。
2. **收集**：用 Glob / Grep 把 `content/**/*.md` 的 frontmatter 与字段表扫出来，建立 id → 文件、id → 引用 的映射。**用 Grep 收集，不要逐个 Read 全文**——条目多时 Read 全量会吃光上下文；只对报出问题的条目 Read 细看。
3. **逐项执行 A–J**，按 🔴 / 🟠 / ℹ 分级。
4. **修台账（仅 G 项）**，其余一律只报告。
5. **需要用户裁定的（D 的候选重复、H 的越界、I 的坐标残留、以及任何「看起来是有意为之」的偏离）** → 用 `AskUserQuestion` 问，一轮最多 4 项，按严重度排序。不确定是不是错误的，**报告为「待确认」而不是断言为错误**。

## 输出形态

```
## Content audit: <范围>

条目 <N> 个 · 类型 <M> 个 · 🔴 <a> · 🟠 <b> · ℹ <c>

### 🔴 必须修
- [A/B/C/E/F/J] <文件:行> — <问题> → <后果：会在启动期 PushError / 线上不可见 / 成就空发 / 该角色开不出局…>

### 🟠 应当看一眼
- [C/D/G/H/J] <文件> — <问题> → <建议>

### ℹ 统计
- 稀有度分布：<类型> Tier1 <n> · Tier2 <n> …
- 池候选数：<池名> <n>（候选 ≤1 的池：<列表>）
- 可修功法池：<角色 id> <n> · …（通用功法 <n> 条 · 占比 <p>%；各灵根档条目数：<表>）
- 文案覆盖：zh <n/N> · en <n/N>

### 已修（台账 / 索引）
- <文件> — <改了什么>
- （无则写「本次未修改任何文件」）

### 待确认
- <需要用户裁定的项>
```

**全部通过时**照样输出统计节——「零问题」与「没检查」必须可区分。
