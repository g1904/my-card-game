# Author Content

把一份**内容条目草稿**打磨成完整的条目设计文档。这是内容创作流水线：**草稿 → 校验 → interview → `content/<类型>/<id>.md` → `/blueprint`**。

**先校验、再澄清、最后才落笔（强制顺序）。** 与 `/analyze-new-ideas`、`/blueprint` 同构：在确认这个条目**字段齐备、交叉引用不悬空、与既有条目和承重纪律相容**之前，**不写任何文件**。写进 `content/` 的东西是 `/blueprint` 的直接输入，猜错的成本在整条链路上放大。

## 边界（先读，决定这次该不该由本技能承接）

| 输入实质 | 归属 |
|---|---|
| 「**这一个**地域是云梦泽，它有这些字段」 | **本技能** |
| 「**地域这一类**内容该怎么运作 / 该有哪些字段」 | `/analyze-new-ideas` → `systems/` |
| 「地域这个类型可以开始写条目了，给它开张」 | `/scaffold-content-type` |
| 「已有的这批条目有没有对不上的地方」 | `/audit-content` |

**判据：讲这一类内容的规则 → `systems/`；讲某一个具体条目 → `content/`。** 输入里两者都有 → 先点明，把类型级那部分**指回 `/analyze-new-ideas`**，本次只承接条目级那部分；类型级那部分未定案而条目又依赖它 → 这是一个 🔴，见第 4 步。

**只作用于客户端设计库。** 内容层只存在于 `game-design-documents/`；本技能**不接受 `--lib=backend`**（后端库没有 `content/`）。

**不改 `systems/`。** 条目在填写过程中暴露出的类型级缺口，一律写进条目文档的 `## Open questions` 并在报告中点名，**不要顺手去改类文档**——那会让类定义在没有 handoff 承载的情况下被条目倒逼着改。

## 步骤

### 1. 定位草稿并判定内容类型

解析 `$ARGUMENTS`：

- **文件路径**（`game-design-documents/inbox/draft-xxx.md` 或不带前缀的 `inbox/draft-xxx.md`）→ 读取它。
- **粘贴的文本** → 把该消息当作草稿。
- **只给了一个条目名 / 主题词** → 询问草稿在哪里，或请用户直接粘贴。
- **空（无参数）** → 读 `game-design-documents/inbox/_index.md` 的待处理表并与 `inbox/` 顶层实际文件对照，挑出**看起来是内容条目**的草稿（描述某一个具体的东西，而非某一类的规则），列出来请用户选。

**逐字读完草稿再动手。**

**判定类型：** 读 `game-design-documents/content/_index.md` 的类型登记表，把草稿归到某一个类型。

- 参数里显式给了类型（`/author-content location <草稿>`）→ 用它，但仍要核对草稿内容是否真属该类型；不符则**停下询问**。
- 判不出、或落在两个类型之间（典型：一件**法宝**还是一件**古宝**——判据是轮回级还是账号级）→ **停下询问，绝不静默默认**。归错类型会让条目落在错误的档案下、字段清单整套用错。

### 2. 就绪度闸门 ⏸️（强制）

读 `content/_index.md` 的登记表与该类型的档案 `content/<类型>/_index.md`：

- **类型尚未开张（无文件夹）** → **停下**，报告该类型的 readiness 与阻塞项，建议先跑 `/scaffold-content-type <类型>`。不要就地把类型档案建出来——那是另一个技能的职责，且它带自己的就绪度核对。
- **类型档案 readiness 为 🔴** → **停下**，点名阻塞项（典型：效果原语 `AbilityData` 语法未定案 ⇒ 卡牌 / 神通 / 法则 / 法宝 / 古宝的效果定义写不实）。**可以**征得用户同意后写一份**只含定位与文案、机制部分标 `⟨待定⟩`** 的 `draft` 条目，但**必须明说它不可 blueprint**。
- **readiness 为 🟠** → 继续，但把阻塞项对应的字段预先标记出来，第 4 步逐个确认它们是否正好落在本条目上。

### 3. 读权威（写之前先读）

1. `content/_index.md` —— 硬边界（本层不定义字段）、id 约定、状态词汇。
2. `content/<类型>/_index.md` —— **字段核对清单**（本次的作答提纲）、条目形状与写作要点、交叉引用表、条目台账。
3. `content/_TEMPLATE-entry.md` —— 要遵循的条目骨架。
4. 该类型档案 `class-authority` 列出的**全部** `systems/` 文档 —— 类定义与机制语义。
5. `systems/common-properties.md` —— 共有字段（`ContentEnabled` / `LocalizedText` / `Rarity` / `SourceCode` / `ExclusiveSource`）与承重纪律。
6. **同类型的既有条目**（`content/<类型>/*.md`）—— 用于第 4 步查重复与定位比较；条目多时抽读同稀有度 / 同池的那些。
7. `systems/balance.md` —— 数值量纲；`terminology.md` —— 凡引入新领域词都要在此核对是否撞名。

**凡本次会引用到的其他类型条目，读它的实际文件**，不要凭台账摘要判断它存在。

### 4. 校验（强制，先于一切写入 · 只读不写）

**4a. 字段完备性** —— 拿类型档案的字段核对清单**逐行**过：

- 草稿作答了 → 记下取值。
- 草稿没答、但能由草稿内容**逻辑必然推出** → 🔵，记下推演与依据。
- 草稿没答、且有多种合理填法 → 🟠。
- 必填字段无从作答 → 🟠（不要填一个「合理的默认值」——内容条目的默认值会静默地把条目落进错误的池）。

**4b. 交叉引用不悬空** —— 条目引用到的每个 `Id`（功法→卡牌、敌人→样本卡组 / 道具、成就→奖励条目、地域→连边、剧本→事件）：

- 目标条目已存在 → ✅ 记入 `references`。
- 目标条目不存在但**本次草稿一并定义了它** → 这是**一次多条目输入**，见第 5 步的分流。
- **功法的写作顺序**：功法条目持每层的卡牌 `Id` 列表 ⇒ **先写卡牌、后写功法**；反过来写，功法的列表在中间态必然悬空。
- 目标条目不存在、草稿也没定义 → 🔴。悬空引用会在启动期校验时 `GD.PushError`，且这条内容线上不可见。

**4c. `Id` 合规与唯一** —— 形态符合类型档案的 `id-form`（库级约定 `<内容类型>.<snake_case_slug>`）；在**整个 `content/` 下**（不只本类型）grep 一遍确认不撞。撞名 → 🔴。
**前缀词表纪律**：条目 id 不得用裸 `item.` / `power.` 前缀（那是次类型的主类型前缀，见 `content/_index.md`）→ 违反即 🔴。

**4d. 与既有条目的重复** —— 同 `(类型, 稀有度)` 且同池的既有条目里，有没有机制上几乎等价的？等价条目稀释抽取池而不增加决策深度 → 🟠，请用户裁定是差异化还是取代。

**4e. 承重纪律**（逐条判，抵触即 🔴，理由与回链一并给出）：

- **效果必须能由既有的效果原语表达。** 表达不了 ⇒ 这个条目实际上在要求一条新机制 ⇒ 归 `/analyze-new-ideas`，不是本技能。这是本步最常见的 🔴。
- **抽取一律走 `AllEnabled()`**；条目若声称「保证一定出现」，必须落在既有的准入机制上（`ExclusiveSource` / `eventPriority` / `ifMandatory`），不新造保底逻辑。
- **`ExclusiveSource`（准入 · 落内容定义）与 `SourceCode`（记账 · 落持有条目）方向相反，不得混用。**
- **面向玩家的内容文案走 `LocalizedText`，UI 文案走 `res://text/` 翻译键**——归属四问见 `ux/_index.md`。把内容文案写成翻译键、或反过来，都是 🔴。
- **数值不硬编码进逻辑**：条目里写的是数据字段的取值，不是「在 X 处加一个 if」。
- **玩法随机一律经种子子流**，条目不得要求未加种子的随机。
- **`XxxData` 是共享只读单例**，条目不得要求运行时写回自身。
- **⚠ 新增条目 = 新增 `Id` ⇒ overlay 补不上，只能随包发版。** overlay 是「只改不增」。凡草稿里暗示「先上线再补一条」的，直接点明这条代价。
- **移动端竖屏**：描述文案长度与信息密度要能在竖屏卡面 / 弹窗里读完。

**4f. 自洽性** —— 数量对不上、同一术语前后含义不同、条件互斥却要求同时成立、边界与退化情形无交代（数值为 0 / 上限 / 空集合 / 重复触发 / 与自身叠加）、数值单位不可解释。

**4g. 分级裁定**

| 级别 | 含义 | 处理 |
|---|---|---|
| 🔴 **冲突** | 与承重纪律 / 既有条目 / 类定义抵触，或草稿自相矛盾，或引用悬空 | **必须 interview** |
| 🟠 **含糊** | 有两种以上合理填法，且不同填法会写出不同的字段取值 / 机制 | **必须 interview** |
| 🔵 **可推演** | 由草稿与既有设计逻辑必然推出 | 不必 interview；在报告中列出推演与依据 |

**拿不准就往高判。** 把 🟠 当 🔵，代价是一条带着臆造数值的内容；把 🔵 当 🟠 问一句，代价只是一个问题。

### 5. Interview 澄清阶段 ⏸️（强制门）

**存在任何 🔴 或 🟠 → 停在这里，一个文件都不写。** 一次性把问题摆齐。

1. **先给结论，再给问题：**

```
## 校验结论：需要澄清（<N> 项）
类型：<类型>（判定依据：<一句话>）  ·  就绪度：<🟢/🟠>
### 🔴 冲突
- <草稿中的陈述> ✗ <权威：文件路径 + 该处要点>
### 🟠 含糊 / 字段待答
- <字段名> —— 可填 (a) … / (b) …，两者会导致 <后果差异>
### 🔵 已推演（无需回答，仅告知）
- <字段> = <取值>（依据：<文档>）
```

2. **用 `AskUserQuestion` 逐项澄清。** 每个问题包含：这是什么字段 / 什么冲突、各选项的**后果**（进哪个池、影响哪些既有条目、是否需要先改 `systems/`）、以及**你的推荐项与理由**（依据既有设计与同类条目的定位，推荐项放第一个）。一轮最多 4 问，按阻断程度排序——先问会改变条目归类与机制形状的。
3. **等待答复。** 用户的答复优先级高于草稿原文；冲突时以答复为准，并在条目文档的依据列如实记下。
4. **答复引入新冲突 → 重跑第 4 步**，直到只剩 🔵 才落笔。
5. **用户授权「按你的判断来」** → 按推荐项推进，但每个被自动定下的字段在依据列标 `[采纳推荐 — 待复核]`，并同时留在 `## Open questions`。**不要当成用户拍板。**
6. **草稿一次描述了多个条目** → 在此确认拆分方案（每个条目一份文档），并确认**本次写哪几个**。相互引用的一组条目（功法 + 它整组的卡牌）应一次写完，否则中间态必然悬空。
7. **条目要求一条新机制** → 明确告知这归 `/analyze-new-ideas`，询问是先去补类型级设计、还是把该机制标 `⟨待定⟩` 先写一份 `draft`。

**未经澄清的 🔴 / 🟠 不得进入条目文档。** 不要用「先按最合理的填法写下去，再在 Open questions 里备注」绕过这道门。

### 6. 写条目文档

按 `content/_TEMPLATE-entry.md` 产出 `content/<类型>/<id>.md`。

- **frontmatter 齐全**：`id` / `type` / `date` / `status: draft` / `source-draft` / `references`（第 4b 步收集的全部被引用 `Id`）。
- **字段填写表**：类型档案清单的每一行都有一行对应。取值未定 → 写 `⟨待定：<指向本文档的 Open question>⟩`，**不留空白、不臆造**。依据列写清「为什么是这个值」——同类条目的相对定位、balance 的量纲、用户在 interview 中的裁决。
- **机制细节写到实现侧能照做的程度**：触发时机、作用对象、数值、结算顺序、与既有机制的交互、退化情形。规则语义（何为一次结算 / 一个回合）**回链 `systems/`，不重新定义**。
- **验收断言是本文档最关键的一节**（`/blueprint` 直接消费）：每条都要能由一个人在 Godot 编辑器里跑起来核验。至少包含一条加载期断言（`Id` 唯一、引用不悬空、必填齐备 → 启动期 `GD.PushError`）。
- **充实 ≠ 臆造。** 充实的是措辞、结构与由草稿逻辑必然得出的含义；草稿未陈述的机制、数字、决策**一律进 `## Open questions`**，以问题形式表述，绝不断言为意图。
- **不复述字段定义。** 类型、取值域、枚举成员、校验语义写回链，不抄进来（`content/_index.md` 的硬边界）。
- **不写过程坐标、不写「已定案」**（`content/` 是活文档）：正文不出现 handoff 日期戳（`08-12` 这类）、`handoffs/*.md` 路径、「推翻 X / 取代 X / 原方案」；条目的每个取值默认就是当前定案，只标注**非定案项**（暂定 / 待验证）。溯源用 frontmatter 的 `source-draft`，正文里不重复。
  某个取值曾被否决过、且否决理由不写下来日后会被重新提出 → 把**理由本身**写进「依据」列，**不写它推翻了谁、在哪一天**。全文见 `/analyze-new-ideas` 第 6b 步「溯源三条」。
- 领域术语保留原样，与 `terminology.md` 对齐；引入新词 → 在 Open questions 中点名它需要一次术语登记。

### 7. 登记与闭环

- **类型档案的条目台账**：`content/<类型>/_index.md` 追加一行（最新置顶）`id | 标题 | status | blueprint | 备注`。
- **类型档案的 Open questions**：本次暴露出的**类型级**缺口追加进去（条目级的留在条目文档里）。
- **归档草稿**（输入来自 `inbox/` 时强制，与 `/analyze-new-ideas` 同一套）：草稿 front matter 的 `status` 改 `distilled` + `distilled-to:` 指向本次条目文档 → `git mv` 进 `inbox/archive/` → 更新 `inbox/_index.md` 两张表。
  **前置条件**：条目文档已写就、草稿 `status` 已改。有未决项导致条目仍是半成品 → **草稿留在顶层**，在待处理行的「下一步」列写清还差什么。
- **不碰** `open-questions.md` / `open-questions/` / `answer-logs/`——那是设计意图流水线的台账，内容条目的未决项归条目文档与类型档案。若本次恰好答定了一条 `open-questions/` 里的**类型级**问题，只在报告中点名，让用户走 `/analyze-new-ideas` 或 `/summarize-open-questions` 归档。
- **不评估 derive 就绪度**，不建议跑 `/derive-requirements`（内容不走 FR，见 `content/_index.md` 流水线图）。

## 输出形态

```
## Authored: <条目显示名> (`<id>`)

类型：<类型>（判定依据：<一句话>）  ·  就绪度闸门：<通过 / 有限通过：…>

### 校验与 interview
- 冲突 <N> 项 · 含糊 <M> 项 · 自行推演 <K> 项
- 🔴 已裁定：<冲突> → <裁决>
- 🟠 已澄清：<字段> → <取值>
- 🔵 自行推演：<字段> = <取值>（依据：<文档>）
- （无冲突无含糊时写「校验通过，未触发 interview」）

### 条目文档
- file: content/<类型>/<id>.md  (status: draft)
- 字段完备：<已答 / 清单总数>  ·  未定：<字段列表，或「无」>
- 交叉引用：<被引用的 Id 清单>（全部已核实存在）
- 验收断言：<N> 条

### Open questions（仍开放）
- <条目级未决项；含任何 `[采纳推荐 — 待复核]`>
- <类型级缺口 → 已记入 content/<类型>/_index.md，需一次 /analyze-new-ideas>

### Inbox
- <草稿路径> → archive/ ｜ 留在顶层：<还差什么> ｜ 无草稿输入

### 下一步
- 请签核：把 status 改 `draft → ready` 后即可 `/blueprint content/<类型>/<id>.md`
```
