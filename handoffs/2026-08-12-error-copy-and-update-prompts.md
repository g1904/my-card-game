## Intent（distilled）

**一句话：** 玩家可见的错误文案由**客户端 UI 层**持有，键就是后端 `code`，载体是 **Godot 翻译键**；三条「去更新」提示收敛为**同一根严重度轴上的三档、同一时刻只呈现最高一档**；三种「玩家在此走不下去」的终局态收敛为**一个阻塞屏 + 一份数据驱动的变体表**。

### 1. 文案归属：UI 层持有，键 = `code`，载体 = 翻译键

- **否决「服务返回已本地化串」。** 三条各自充分：后端 `message` 已定为英文调试串且永不展示 · 后端不掌握界面上下文（同一 `code` 在登录屏与轮回中途该有不同措辞）· 文案会成为契约的一部分（改一个错别字要发后端版）。**判据是「谁掌握上下文，谁产出」**——它与「客户端不持有兼容矩阵副本」方向相反但同源：兼容性判定的上下文在服务端故服务端判，措辞的上下文在客户端界面故客户端产。
- **处置表与文案表是两张表，共用同一个键。** `src/Core/` 的 `code → (OpError, 处置)` 表跑在后端适配层，**没有界面上下文，也不该有**——往里塞文案会让一个网络适配器依赖 UI 层。处置表回答「怎么办」，文案表回答「怎么说」。
- **从 `code` 到文案键是机械规则，不是第二张手写表。** 规则：`ERR_` 前缀 + `code` 全大写 + `.` 替换为 `_`（`auth.session_revoked` → `ERR_AUTH_SESSION_REVOKED`）。手写对照表会引入一个新的失效面——「后端加了个 `code`，处置表加了一行、文案表忘了加」；机械规则下该失效面**不存在**，键必然存在，只可能是翻译条目缺失，而那可在启动期一次性扫出。
- **兜底 = 四条 `class` 默认路径在文案侧的镜像。** Godot 的 `tr()` 缺键时原样返回键本身，故必须包一层 `ErrorText.For(code, error)`：命中则用专属文案；缺失则 `PushWarning`（定位标识符 = `code`）+ **按 `OpError` 回落**（此时正是不认识这个 `code`，不能再按 `code` 分辨）。
- **启动期审计（纪律的可执行化 · 第 2 级）。** 遍历处置表全部已知 `code` 逐个查翻译条目，缺失者一次性 `PushWarning` 列出。成本一个 `foreach`，把「上线后错误弹出一串大写英文键」挡在开发期。
- **翻译资源随包，不走 overlay 热更。** overlay 的既定纪律是「只改不增」且只覆盖**内容条目**；错误文案不进抽取池、不被存档引用、无 `Id`、不参与 `AllEnabled()`，硬塞进 overlay 会把一条**被刻意限窄**的热更通道撑宽。代价（改文案要发版）可接受——错误文案是变动频率最低的一类文本，而真正需要事后补救的那一项（更新地址）由后端下发单独解决。
- **`requestId` 需要一个玩家可达的出口。** 强制在线 + 云端权威下，客服工单第一件事是定位「这一次请求」，而移动端导出日志基本不可行（与「设置屏显示同步版本 #N」同一判据）。**在阻塞屏与错误模态底部放一行极小字 `#<requestId>`，可长按复制**；非模态提示与 toast 级不放（那是高频呈现，加编号是噪音）。

### 2. 三条版本提示：同一根轴上的三档，同一时刻只呈现最高一档

| 档 | 触发 | 含义 | 呈现 | 阻塞 |
|---|---|---|---|---|
| ③ 强更 | `client.version_unsupported`（登录 / 启动 pull） | 完全不能玩 | 全屏阻塞屏 | 硬阻塞 |
| ② 需更新 | `UpgradeRequired == true` | 还能玩，但进度上不去 | 常驻状态指示改写 + 既定软阻塞模态第二变体 | 非模态 / 既定软阻塞 |
| ① 建议更新 | `X-Recommended-App-Version` > 本机版本 | 无实际影响 | 主菜单一条可关闭横幅 | 永不 |

**去重规则一句话：同一时刻只呈现最高一档，低档被高档吸收。** `UpgradeRequired == true` ⇒ 不渲染 ① 的横幅（二者指向同一个动作，而 ② 已在常驻位置说了同一句话）；硬阻塞屏出现时 ① ② 的载体都已不在屏上。**承重依据 = `combat-ux.md` 的既定纪律「不在最高频操作上加提示，告知由别处的常驻呈现承担」的第三个实例**——当已有常驻呈现在承担告知时，不再另加一条。

- **② 的载体 = 既有的常驻同步指示，不新增第二处常驻 UI。** `UpgradeRequired` 是同一条链路（同步）的另一种失败态，理应同处呈现。**`UpgradeRequired == true` 时必须换掉「离线」二字**——「离线」隐含「正在重连、会自己好」，但 `Upgrade` 态已定案为**本会话内永不恢复**（退避已暂停，唯一解除条件是重新登录），继续显示「离线」是在给出一个已知为假的承诺。点按该指示 → 打开更新引导半屏（与阻塞屏「去更新」同一入口）。**不在轮回内新增任何模态**。
- **① 的频次护栏：每个 `recommendedVersion` 取值只提示一次。** 玩家关闭后把该版本号写入 `user://cache/`；服务端推荐版本变了再提示一次。位置为主菜单顶部（安全区内），**绝不在轮回内 / 战斗内呈现**。
- **仍需比较 semver，且与「`X-Min-App-Version` 客户端不比较」不冲突**：不比较的是**硬闸门**（判定权在服务端），软提示不阻塞任何东西。复用 `minAppVersion` 已定规则：三段逐段整数比较，**不做字典序**（字典序会判 `1.10.0 < 1.9.0`，且这类 bug 发版后才显形）。
- **推论：客户端总共只在两处做 semver 比较**——manifest 的 `minAppVersion`（内容维度）与 `X-Recommended-App-Version`（软提示），**两处都只导致「不做某事」或「说一句话」**。协议维度的比较一处也没有。可机械检查。

### 3. 阻塞屏：一个屏三个变体，不是三个屏

三种终局态形态完全同构（全屏 · 不可返回 · 一句原因 · 一个主动作 · 一个退出），收敛为一个 `BlockingNoticeScreen` + 数据驱动的变体表。理由与「错误码映射是数据表不是 switch」「三个 `HttpXxxBackend` 共用一处头处理点」同源：**多于一处就会出现「一个改了另一个没改」的半配置态。**

**⚠ 三个变体 ≠ 三处硬阻塞。** 硬阻塞点仍是既定的两处（登录 / 启动 pull 闸门、被后端明确挤下线）；迁移失败落在「启动 pull」那一处**之内**，不新增第三处，总则 7 的「硬阻塞只有两处且只由已知 `code` 触发」原样成立。

- **「去更新」按钮的落点 = 后端下发为主 + 客户端渠道配置兜底。** 优先 `detail.updateUrl` → 缺失 / 断网 → 随包 `ChannelConfig` 的渠道地址（`PushWarning` + 定位上下文）→ 两者皆无 → 主按钮置灰只留「退出游戏」（**绝不给一个跳空的按钮**）。采纳理由与「客户端不持有兼容矩阵副本」同源：判定权在服务端，判定的**产物**（去哪更新）也应与判定同处；客户端那份只是安全默认值。`detail.updateUrl` 落地前**必须校验 scheme**（只接受 `https://` 与已登记的应用商店 scheme），这是内容分发之外的第二个注入面。
- **迁移失败的玩家侧表现（顺带答结 `sync-service.md` 的待答项）。** 否决「提示重装」（存档权威在云端，重装不改变任何东西，只制造「我的进度没了」的误解）与「回退到云端上一个可用版本」（`revision` 严格单调递增，回退即主动丢弃已确认进度，直接违反云端权威）。**`OpError.Migration` 先分两种情形**：云端 `schemaVersion` 高于客户端支持上界（迁移前即可判定）→ 走**「需更新」变体**，与 `client.version_unsupported` **同因不同径**；`schemaVersion` 在范围内但迁移逻辑抛错 → 走**「存档读取失败」变体**并**必上报一次**——它是**真正的程序缺陷态**，对上「处置相同但它是应当被观测到的异常，静默处理会让它永远看不见」。**绝不静默降级放行**：带着半迁移的 Profile 进主菜单，下一次 push 会把一份已损坏的档写回云端，那才是不可逆的。

### 4. `OpResult.Detail` 正式收口为诊断串（推翻一处旧表述）

07-27b 的「`Detail` 携带面向玩家的原因串」与 08-11b 的「`message` + `requestId` 拼进 `Detail`，随 `GD.PushError` 输出」**不能同时为真**。**以 08-11b 为准**（更晚、更具体，且它那三条承重纪律都建立在这个前提上）：`Detail` = `code` + `requestId` + 后端 `message`（本地失败则为定位上下文），**UI 永不直接渲染 `Detail`**，玩家可见文案一律经 `ErrorText.For(code, error)`。理由是可机械检查性：若 `Detail` 兼两个身份，那三条纪律**一条也无法机械检查**——只要 `Detail` 可能被渲染，英文调试串就随时可能漏到屏上。连带改写 `account-service.md` 的 `OpError.Compliance` 那一行；合规文案此后按 `code` 走 `ErrorText`，**这实际上更好**：合规文案是最需要精确措辞、也最需要按渠道调整的一类。

### 5. 全库 UI 文案统一走翻译键（追加裁决）

**全库 UI 文案（按钮、界面标签、叙事文本）统一走 `TranslationServer` 翻译键**，错误文案的 `errors.csv` 只是第一批。**中文是默认语言与优先制作的一列，英文列全部预设占位符。** 与 `scope.md`「本地化打磨在 MVP 范围外」不冲突——现在做的是**键与结构**，不是实际的英文文案；这正是那条软约束要的「现在不做多语言，但现在就不能挡住多语言」。否决「先用 C# 常量表、待全局 i18n 决策时再迁」：键的形态两者一样，**晚迁没有任何收益**，只多出一次改所有调用点的迁移。
