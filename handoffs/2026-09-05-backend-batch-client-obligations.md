## Intent（distilled）

**一句话：** 后端批量评审定下的四条取向各给客户端新增了一项义务，本次把这四项在客户端侧收口。四项都**不新增屏、不新增阻塞点、不新增阻塞屏变体、不动存档 schema**；唯一的结构增量是 `OpError` 多一个成员。跨边界的语义一律回链对侧契约，**本库一条也不复述**。

四项与各自的落点：

| | 义务 | 客户端这一半 | 落点 |
|---|---|---|---|
| **A** | 未过审昵称的「登录后强制改名」呈现 | 启动链内的一道 fail-open 全屏模态 | `account-service.md` · `screen-flow.md` · `error-and-blocking-ux.md` |
| **B** | 未成年账号的剩余可游玩时长呈现 | 两级提醒 + 主菜单常驻指示，只呈现不判定 | `account-service.md` · `screen-flow.md` |
| **C** | 购买失败的处置档与长等待 UX | `OpError` 增一档 `Purchase`；四种情形的呈现与待兑现态联动 | `architecture.md` · `monetization.md` · `error-and-blocking-ux.md` |
| **D** | overlay 打包工具的机读产包证明与基线快照 | 两项产出 + 一条可达性约束 + 首版内置两把公钥 | `content-service.md` |

### 一、A —— 须改名：启动链内一道 fail-open 的一次性门

- **形态 = 全屏模态，不是一屏。** 本库没有独立的改名屏，昵称编辑本就是 PlayerProfile 屏内的一个区；模态复用它的输入与提交路径。与购后等待期的全屏模态进度态同款先例。
- **时机 = 启动链内、主菜单之前**，与既有合规检查**同一次 status 读取**，不新开请求。
- **取不到 status 即放行**（fail-open 的原义）：本次会话不拦，下次会话再拦。真正的强制力在后端的存量扫描与复核通道。
- **它不是穷举四处阻塞点之一。** 那四处是**失败态**阻塞——由后端 `code` 触发、玩家在当下没有任何自愈路径；须改名由一个布尔驱动、玩家改个名就过。两者不同类。这条消歧必须明写在 `account-service.md`，否则「下次会话再拦」与「不新增阻塞点」会被读成互相矛盾。
- **不进 `BlockingNoticeScreen` 变体表**：准入判据两条（由已知 `code` 触发 · 玩家无自愈路径）**都不成立**，`BlockingNoticeKind` 一格不动。
- **提交失败沿用既有映射，不新增处置路径**；「须改名」这个标记本身不带二级原因键，它与「这次提交为什么被拒」是两件事。

### 二、B —— 剩余时长：两级提醒 + 一处常驻，只呈现不判定

- **数据源单点**：合规 status 的那一个相对量字段（仅未成年账号下发）。
- **阈值落数据资源、不硬编码**，字段以**秒**计（与下发量同量纲，不做换算），初值 **1800 / 600**（30 分钟 / 10 分钟），待实测校准。
- **常驻指示复用主菜单顶部同步指示同一条带的形态**，不新增第二处常驻 UI。**战斗内至多常驻指示、不弹窗打断。**
- **呈现用的倒计时不属「判定」。** 后端刻意下发相对量而非时刻，正是为了免除本地时钟比较；该倒计时永不决定能否继续游玩，到点仍由既有的会话失效路径接住。这条须就地澄清在 `account-service.md`「四件不归它的事」的第 1 条旁，否则「不比时钟」会被读成「不许显示」。
- **主菜单加常驻指示与「注销冷静期主菜单零增量」不矛盾**：同一条判据的两侧——注销是玩家主动发起、有明确心智；剩余时长是玩家不知情的状态。

### 三、C —— 购买失败：只加一个枚举成员，处置落 `monetization.md`

- **`OpError` 增一档 `Purchase`**，承载「这笔购买没成」这条既有错误档都不表达的处置轴。付费面是玩家最不能容忍含糊的地方。
- **不建逐 `code` 表。** 本库从来没有逐 `code` 表（只有按 `class` 的默认表）；开一张只有购买几条的半张表，即制造与对侧台账重复的第二权威。四种情形的呈现与处置写进 `monetization.md` 的购买流程段——与合规三条的落法同构（处置落发起它的那份主题文档）。
- **购买域并非每一条都映 `Purchase`**：报文格式错误那一类仍是上行校验失败，照常映既有的校验档。逐 `code` 清单的权威在对侧 `contracts/envelope.md`。
- **四种情形的待兑现态联动**：处理中 → 保持；收据无效终态失败 → 解除；已在另一账号核销 → 解除；渠道未开通 → 不进（玩家尚未付款）。
- **长等待不新增变体、不设硬超时**，只是既有的 15 秒软提示按「收据还在处理」与「平台不可达」两种情形分岔文案。**等待期间收到的可重试 `code` 只改写文案，不改变它是否进变体表**——判据仍是二者缺一即不进。
- **客服可达面 = 复用既有的 `#requestId`**：一句 `STORE_` 文案 + 底部可长按复制的编号 + 一行「请提供此编号联系客服」。不新增独立客服入口、不引入客服地址配置面。**玩家尚未付款的那一类不出这条通道**——没有钱需要申诉。
- **补两个流程步骤**：① 渠道要求商户侧下单时，先经下单端点取支付参数与收据标识并随待兑现态持久化（**首版微信不开通，这一步首版不发生、不阻塞上线**）；② Apple 侧的 `finish()` 是流程内的显式步骤，只能在验票成功或幂等命中后调用，**不挂在 UI 回调的顺手处**。

### 四、D —— 打包工具：两项产出，校验规则不变不外移

- **机读产包证明**，字段下限四项（工具版本 · 基线 `appVersion` · 断言项计数 · 逐文件 `path` + `sha256`）。字段形态归本库自定，对侧只读前三项作留痕。
- **证明须与产包同批产出、同批上传，并内嵌在产包的唯一路径上**——单独一个「记得再跑一下」的步骤会让整条链退回评审级。
- **按在架版本归档基线内容快照**，且须**归档到发布侧可达处**，否则闸对老基线根本跑不了。存放位置与生命周期归本库自决，可达性是硬约束。
- **打包工具不自持在架版本清单**：跑哪几个基线由发布侧按其兼容矩阵决定并作为输入喂进来。既有的「客户端不持有兼容矩阵的任何副本」指的是**运行时客户端**，须就地澄清，否则这两句会打架。
- **校验规则本身不变、不外移**：仍是既有的两条合并期闸 + `LoadAll()` 路径，本项只把它的产出物变成可被发布侧核对的东西。
- **首个客户端版本即内置 active + standby 两把内容签名公钥**（报文零改动）。价值全在「首版就做」——等到需要轮换才加第二把就已经晚了。

## Open questions

- **更高版本客户端的基线内容集是否为更低版本基线的超集？** 若成立，「兼容矩阵内每个在架基线各跑一遍」可简化为「只跑最新」。它取决于「客户端发版能否删除随包内容条目」这条尚未定的内容纪律。本次取安全默认（逐基线各跑一遍），不依赖它。
- **产包证明是否加「按类型的条目计数」一格。** 对侧有一条**尚未采纳**的优化路径需要它（池规模由产包证明供数、对侧只读数字不解析内容文件），且自注须与对侧同批落地。本次不纳入字段集。
