**一行摘要：** 借词第一批全部定名（`sorcery speed` 整条删除、三步改称 开始 / 行动 / 结束阶段、`resolve` = 结算而战斗收口改称「收口」），并由定名连带落定**卡牌类型六分**（法术 / 灵宠 / 阵法 / 法宝·古宝 / 神通·法则 / 业障）、**异能三分**（静止式 / 启动式 / 触发式）、**永久物**概念、**意图 = 快照而非承诺**、以及**战场与两个参战方 manager 的边界判据**。

## Intent（distilled）

### 一、出牌时机是全局规则，`sorcery speed` 不借

**`sorcery speed` 不给中文名，从 `terminology.md` 整条删除。** 它在本作里已不指代任何可区分的东西：MTG 需要这个词，是因为存在与之相对的 `instant speed`——它在那里是一个**卡牌属性维度**。08-02b 已移除交互、明确不借 `instant`，单一取值的维度不是维度，保留它反而制造「本作有出牌时机之分」的错觉。

**替代表述（全局规则）：**

> **出牌时机（唯一）：** 一张牌只能在**自己回合的行动阶段、且栈为空时**打出。这是全局规则，不是卡牌属性——本作不存在第二种出牌时机。**启动式异能与道具的使用窗口与之完全相同。**

机制原样保留，改的是措辞不是规则。

### 二、回合三步 = 开始阶段 / 行动阶段 / 结束阶段

中文侧三步统一以「阶段」收尾，英文侧三步统一以 `step` 收尾：

| 定名 | 英文 / 代码 | 内容 |
|---|---|---|
| **开始阶段** | `start step` / `TurnStep.Start` | 归属方 mana 恢复至 `manaLimit` → 触发「回合开始时」→ 抽牌 |
| **行动阶段** | `action step` / `TurnStep.Action` | **唯一**的出牌阶段，只有归属方出牌 |
| **结束阶段** | `end step` / `TurnStep.End` | 触发「回合结束时」→ 清理回合内状态 |

`main phase` 弃用：MTG 的 `main` 有 `beginning` / `combat` / `ending` 等同级 phase 与 precombat / postcombat 两个 main 作对照系；本作无战斗步骤、无双主阶段，对照系不存在，`action` 直接陈述这一步做什么。**与 `eventStart` / `eventEnd` 的同词不作重构**——二者语境不同（事件级 vs 回合级）且从不同屏出现。

### 三、`resolve` = 结算，`settle` = 收口，`trigger` = 触发

- **`resolve` = 结算**，与既有措辞吻合（「打出 → 入栈 → LIFO 弹出结算」「每一次结算时截断」）。与 MTG 同义：只作用于栈上对象。
- **战斗收口处的「结算」改称「收口」（`settle`）。** 「失败时才在结算时刻扣 lifeTotal」「结算时角色道念」这类表述全部改为**收口**，把「结算」一词让给 `resolve` 专用。**一词两义就此消除。**
- **`trigger` = 触发。** 与 MTG 的出入：**本作的触发时点全部有归属方**（「回合开始时」是**某一方的**回合开始）；**但监听方可跨归属方**（见第六节）；且**触发命中后压栈者一律是 StackManager**，与载体解耦。

### 四、异能三分：静止式 / 启动式 / 触发式

| 中文 | 英文 / 代码 | 是否入栈 | 何时可用 | 载体 |
|---|---|---|---|---|
| **静止式异能** | `static ability` | **否**（持续生效，不经栈） | 只要载体在战场上就一直生效 | 战场条目（永久物、持续状态、`Power`） |
| **启动式异能** | `activated ability` | **是**（启动后压栈） | **自己回合的行动阶段、栈为空时**（与出牌同一窗口） | 同上 |
| **触发式异能** | `triggered ability` | **是**（命中后由 StackManager 压栈） | 触发时点命中时，**可跨归属方** | 同上 + 牌上触发器 |

这三分补完了 08-03「载体开放」的另一半：**载体说的是「挂在谁身上」，异能类型说的是「怎么生效」**，两者正交。

**关键自洽点：启动式异能不重新引入交互。** 其可用窗口被限定为**与出牌完全相同的那一个窗口**，不构成「在对手回合插手」的通道，08-02b 的定案不被松动。

- **推论 ①：异能是独立于 `CardData` 的可复用资源类型。** 神通、持续状态、道具都能带异能，故抽为 `AbilityData : Resource`，由 `CardData` / `PowerData` / `ItemData` / 战场条目共同引用。这与 08-03「触发匹配逻辑不能写死在卡牌类型里」是同一条。
- **推论 ②：静止式异能是 BattlefieldManager 的一条与栈无关的写入路径。** 载体一进场即时生效、一离场即时失效。
- **推论 ③：启动式异能给 mana 第二个花费去向。** 此前 mana 只用于出牌，「每回合刷满、不结转」意味着手牌不足时 mana 纯浪费；现在场上永久物也能吃 mana，**沉没成本问题被缓解**，且战场从纯被动区变成有操作面的区。

### 五、永久物（permanent）

**永久物 = 落在战场上、无限期存在直到被移除或战斗结束的条目。** 它把战场条目切成两类：

| 战场条目 | 生命周期 | 举例 |
|---|---|---|
| **永久物（permanent）** | **无限期**，直到被效果移除或战斗结束 | 灵宠、阵法、`Power` |
| **非永久条目（持续状态）** | 带生命周期标记（**回合内** / 跨回合 / 持续 N 回合） | 「我方本回合所有牌 +1 道念」 |

**与 MTG 原义的出入：** MTG 的 permanent 是**区的成员资格**（在战场上的对象一律是永久物）；**本作的战场上同时住着永久物与非永久的持续状态**，故永久物在本作是战场条目的一个**子集**，不等于「在战场上」。

- **这个二分把「回合内状态的判定边界」收窄了一半：** 结束阶段「清理回合内状态」**只清理非永久条目中标记为回合内的那些，永远不碰永久物**——「永久物会不会在结束阶段被误清」这个潜在歧义直接消失。
- **推论 ①：「可被移除」这件事只对永久物有意义**，针对 / 移除类效果的目标合法性因此有了类型级判据。
- **推论 ②：永久物必须可序列化**（决策点存档要求局面可恢复）；非永久条目同理，但二者字段形态不同——永久物带来源卡牌 `Id` + 运行态，持续状态带生命周期标记 + 剩余回合数。

### 六、规则体系支持「奥秘」式埋伏牌

这条要求**逻辑上蕴含了触发条件可跨归属方**——埋伏牌的本质就是「在对手回合的某个时点触发」，若触发条件不能跨归属方，埋伏无从成立。故：

> **触发条件可以跨归属方。** 时点本身有归属方（「回合开始时」是某一方的），但**监听方不必是该归属方**——一个条目可以监听「**对手的**回合开始时」「**对手**打出牌时」。

**埋伏牌的形态：**

| 项 | 形态 | 依据 |
|---|---|---|
| 归属类型 | **阵法（`Enchantment`）的次类型「埋伏」** | 炉石的奥秘正是「Secret 次类型」；本作阵法就是「留场且承载异能」的那一类，埋伏 = 面朝下的阵法 |
| 是否永久物 | **是** | 留在战场直到被触发或战斗结束 |
| 触发后去向 | **弃牌堆** | 与「打出后进弃牌堆」同路，不新增流量类型 |
| 对手可见性 | **对手只知道「有一张埋伏」，不知道是哪张** | 完全不可见 → 纯 gotcha；完全可见 → 失去意义 |
| 数量上限 | **同名埋伏不可重复布置** | 否则同一触发条件叠放多张，连锁结算的可读性在竖屏上崩掉 |

- **推论 ①：埋伏是本作唯一一条「在对手回合发生作用」的通道。** 玩家不能在对手回合主动响应，但可以**预先布置**在对手回合自动响应的东西。结算入口不变——触发命中后由 StackManager 压栈。**这是移除交互后 stack 仍然承重的又一个证明。**
- **推论 ②：敌人 AI 知道「有一张埋伏」，但不知道是哪张。** 与玩家看到的信息完全对称——**这是本作第一处双向对称的信息规则**（意图揭示是单向的）。落地上 EnemyManager 规划时从战场读到的是**埋伏的计数，不是条目内容**；它可以据此变得谨慎，但无法针对性规避。**埋伏的威慑力与实际效果因此是两件事**。

### 七、卡牌类型 —— 一套六类

| 中文 | 英文 / 代码 | 所在区 | 结算后去处 | 是否永久物 | 可带的异能 |
|---|---|---|---|---|---|
| **法术** | `Sorcery` | 卡组 → 手牌 | **弃牌堆** | 否 | 触发式（限「在栈上 / 结算时」的触发） |
| **灵宠** | `Creature` | 卡组 → 手牌 | **战场** | **是** | 静止式 / 启动式 / 触发式 |
| **阵法** | `Enchantment` | 卡组 → 手牌 | **战场** | **是** | 静止式 / 启动式 / 触发式 |
| **法宝 / 古宝** | `Item` | **储物袋**（不洗进卡组） | **弃牌堆**（或按次数消耗） | 否（除非其效果留下永久物） | 启动式为主 |
| **神通 / 法则** | `Power` | **开局直接入场** | **不离场**（战斗结束才消失） | **是**（且**受保护**） | 静止式 / 启动式 / 触发式 |
| **业障** | `Affliction` | 卡组 → 手牌 | **弃牌堆** | 否 | — |

**三个来源区，各自绕开的东西不同**——这是六类之间最本质的结构差别：

| 来源 | 类型 | 受抽牌运制约 | 需玩家动作才生效 |
|---|---|---|---|
| **卡组** | 法术 / 灵宠 / 阵法 / 业障 | **是** | 是（打出） |
| **持有的道具**（玩家侧来自储物袋，敌人侧来自 `EnemyTemplate`） | 法宝 / 古宝 | 否 | 是（使用） |
| **开局入场** | 神通 / 法则 | 否 | **否**（自动在场） |

> **储物袋不是战斗概念。** 它是角色的道具容器（跨战斗内外存在，上限 **99** ≈ 不设限，仅防溢出）；战斗只从中筛出 `UsableScene` 含 `InCombat` 的那些。**敌人没有储物袋，但同样持有 item 与 power**——这正说明「容器」与「本场可用道具」是两个必须分开的概念。

**类型间的具体差异化留待日后。** 以下只给当前已能确定的结构性差别，即那些不定就无法写 schema 的部分。

#### 7.1 法术（`Sorcery`）

对位 MTG 的 Sorcery。一次性效果，结算后进弃牌堆。**因不存在 Instant，本作不需要 sorcery / instant 的对照**——「法术」在本作里就是「一次性牌」的通名，无速度含义。

**定名提示（非阻塞）：** 「法术」与既有的**法力**（mana）、**法则**（PlayerPower）、**法宝**（CharacterItem）共用「法」字根。08-03 已定「中文名不承担层级表达」，故不构成规则冲突；但 UI 文案里「法术 / 法宝」相邻出现时需靠卡框色与图标区分，不能只靠文字。

#### 7.2 灵宠（`Creature`）

对位 MTG 的 Creature，**形态改写**：**无战斗步骤、无伤害模型，故灵宠不互相攻击**。它是场上的实体永久物，典型形态 = 靠触发式异能每回合稳定产出道念，或以静止式异能持续修正双方数值。

**推论：灵宠是「延迟回报」型的道念产出通道。** 法术即时产出、灵宠分期产出——两者的取舍（现在拿 5 点，还是每回合拿 2 点但可能被拆）是定长 10 回合对局里最自然的一条策略轴，且**越接近第 10 回合，灵宠越不划算**。定长战斗天然给了它一条内建的时间价值曲线。

#### 7.3 阵法（`Enchantment`）

对位 MTG 的 Enchantment（合并了 Artifact——本作无「针对面」之分）。场上的非实体永久物，承载三类异能，是 build 的骨架。**埋伏是它的一个次类型。**

**阵法与灵宠都可被针对。** 「场上不可被移除的东西」这个生态位由 `Power` 独占，故不以「可否被针对」区分阵法与灵宠；二者的区分轴（实体 vs 非实体、产出形态、次类型体系）留待日后。

#### 7.4 法宝 / 古宝（`Item`）—— 储物袋与不洗进卡组

**这是本次最大的结构变化：卡牌不再只有一个来源区。**

| 项 | 内容 |
|---|---|
| 不洗进卡组 | 道具**不参与抽牌 / 洗牌 / 弃牌循环**，抽牌堆确定性完全不受影响 |
| 存于**储物袋**（`magic pack`） | 角色的道具容器，跨战斗内外存在，容量上限 **99**（≈ 不设限，仅防溢出） |
| 战斗内的道具来源 | 参战方各持一份**本场可用道具**：**玩家侧来自储物袋的筛选结果，敌人侧来自 `EnemyTemplate`** |
| **敌人的道具效果计入意图数值** | 意图是「本回合全部行动的推算结果」，道具是行动的一种；排除它会让意图失去参考价值 |
| 「像精灵球一样随时可用」 | **不受抽牌运制约**——想用就能用，这是它与卡牌最本质的差别 |
| **使用窗口 = 仅自己回合** | 与出牌 / 启动式异能**完全同窗口**。**「随时」= 不受抽牌运制约，不是不受回合限制**——交互不回归，`RunCombatAsync` 状态机形状不变 |
| 可能有法力费用 | `ItemData` 带可选 mana 费用；零费道具亦合法（与启动式异能必须有费用的规则**不同**，因为道具有使用次数这层天然限制） |
| **并非所有道具都能在战斗中用** | `ItemData` 带 `UsableScene { InCombat / OutOfCombat / Both }`；战斗外才有意义的道具（恢复寿元、影响事件掷骰）不进战斗道具区 |
| 分两级 | 法宝 = CharacterItem（轮回级）/ 古宝 = PlayerItem（账号级、有使用次数限制）；条目上带 `ItemScope { Character, Player }` |
| **古宝次数即时写** | 用掉一次即经 `ProfileManager.TryApply` 写 PlayerProfile，**不攒到收口**，堵死「用完退出重进恢复次数」的窗口 |

- **推论 ①（承重）：道具是战斗内唯一会即时写 Profile 的卡牌行为。** 其余所有牌都是战斗内运行态；但古宝的使用次数是账号级持久数据，法宝的消耗是轮回级持久数据。既有定案「战斗内的一切写入经 ProfileManager」正好承接这条，无需新机制。
- **推论 ②：战斗界面需要一个道具区，但它不是「储物袋」。** 建议默认收起为一个角标（显示可用道具数），点开为抽屉式面板。**措辞上不要在战斗语境里称它为「储物袋」**：敌人没有储物袋却同样有道具，这证明容器与视图必须分开。
- **推论 ③：道具绕开了手牌上限这条节奏约束。** 手牌上限的设计意图是「逼玩家出牌腾位」，而道具不占手牌位、不受满手影响。**这是有意的松弛阀**；但也意味着**道具的强度必须比同费法术低**，否则「确定性 + 不占位 + 不受抽牌运」三重优势会让卡牌相形见绌。
- **推论 ④：EnemyManager 的回合级规划必须把道具一并算进去**——AI 在玩家回合开始之前就要连道具一起定好整套行动。**这不新增机制**，道具只是规划输入里多了一个来源。
- **推论 ⑤：`UsableScene` 与储物袋容量无关。** 容量护栏管的是存档体积与 UI 溢出，`UsableScene` 管的是战斗界面的信噪比。

#### 7.5 神通 / 法则（`Power`）—— 徽记式的开局入场条目

**对位 MTG 的徽记（emblem）**：几乎不可被针对或移除、一旦存在就一直存在。本作接过这个语义，但落点改到战场。

| 项 | 内容 |
|---|---|
| 不洗进卡组、不经储物袋 | 它不需要「获得」的动作——**开局即在场** |
| 战斗开始时入场 | 入场发生在参战方组装阶段，**早于第一个开始阶段**，故「回合开始时」类触发从第 1 回合起就已挂载 |
| 几乎不可被交互 | **`Power` 一律不可被针对 / 不可被移除，无条目级例外**；「几乎」而非「绝不」的那个后门**落在效果侧**——某些效果声明 `IgnoresProtection` 后可移除任意 `Power`。此类效果的稀缺性与可预期性**由内容设计侧保证**，**不在代码中加硬规则保护** |
| 分两级 | 神通 = CharacterPower（轮回级）/ 法则 = PlayerPower（账号级）；条目上带 `PowerScope { Character, Player }` |
| **并非所有神通 / 法则都进战斗** | `PowerData` 同样带 `UsableScene`。**只有 `InCombat` / `Both` 的才在开局入场**；纯事件向的能力继续走 capability flag / modifier pipeline 两条既有通道 |
| **敌人同样持有 power** | `EnemyTemplate` 需要一个 power 持有列表字段。「不可被移除的场上特性」正是 boss / 天劫最自然的表达 |

**这条几乎不需要新机制——08-03 已经把位置铺好了。** 当时定案「参战方组装时要把角色持有的神通注册进战场」，本条只是给这个已存在的行为一个类型名，并把**法则**一并纳入同一条路径。

- **推论 ①（承重）：法则能承载战斗内触发**，故**参战方组装时要读两个 Profile**——这是 combat-service 第一次需要读 PlayerProfile。
- **推论 ②：入场条件是两条与门——`status == 开启` 且 `UsableScene` 含 `InCombat`。** `status` 关闭 = **不入场**，而非「入场但不生效」。两个字段正交不可合并：**`UsableScene` 是内容侧的静态属性**，**`status` 是玩家侧的运行时开关**。
- **推论 ③：法则获得了第三条生效通道，但用得极少。** 此前法则只有 capability flag 与 modifier pipeline 两条被动形态；作为 `Power` 入场后，它可以主动挂触发器、带启动式异能。**允许但极其稀缺**——premium bundle 花了钱就该让体验更好，而战斗是核心体验的关键一环。**代价由稀缺性而非规则承担。**
- **推论 ④：`Power` 是永久物，但要在永久物内部再分一档。** 落地上给战场条目加一个 `IsProtected` 标记（`CardType.Power` 落场时一律置 true，**不由 `PowerData` 逐条目声明**）。**不引入 MTG 的指挥区（command zone）**：为一类不可交互的条目再开第七处位置，收益不抵竖屏 UI 与存档形态的成本。
- **推论 ⑤：`Power` 无 mana 费用。** 它不被「打出」，故费用字段对它无意义（启动式异能的启动费另算）。
- **推论 ⑥：`Power` 是唯一不产生弃牌堆流量、也不产生栈上「打出」事件的类型。** 它的触发式异能照常经 StackManager 压栈，但**它自身永远不入栈**。

#### 7.6 业障（`Affliction`）

负向牌，由事件的负向奖励条目塞进**卡组**（对齐 Slay the Spire 的 Curse）。**业障可被打出，但没有任何正面效果，打出的唯一作用就是把自己送进弃牌堆。**

**这条解法把死锁风险完全消除了**，且与既有定案高度同调：

- 08-03 定案「弃牌不是被规则强制的动作原语」——**业障不需要任何弃牌机制**，它走「打出后进弃牌堆」这条既有通道，弃牌堆流量的完整清单不变。
- 08-03「满手的代价是 tempo 而非资源」——**业障的代价同样是 tempo**：它占一个手牌位，玩家要花一次出牌动作把它清掉。整套惩罚模型自洽为同一条「时间即代价」。
- 它比 StS 的 Curse 温和（那里 Curse 不可打出），也比「永久堵塞」的形态安全得多。

**额外代价：逐条目而定，通常没有。** 业障**不是**一个统一强度的类型——**多数业障零代价**，**少数带额外代价**（例：耗 1 mana 才能打出，或打出时削自己 1 点道念），由内容侧逐条目书写。

- **推论 ①：`Affliction` 的校验规则要放宽。** 不能硬性要求「mana 费用必须为 0」。改为：**允许有 mana 费用与负向效果，但不得有任何正面效果**；「不得有正面效果」难以机械校验，故落为**内容侧纪律 + `PushWarning` 级软检查**。
- **推论 ②：业障获得了一条强度轴。** 轻度业障只偷一拍节奏，重度业障在 mana 紧张的回合造成真两难——它因此有资格作为**高风险事件的负向奖励条目**出现在不同厚度的档位上。

### 八、次类型（card subtype）

**每个主类型下都会有次类型**，对位 MTG 的 subtype（Creature — Goblin / Enchantment — Aura）。已能确定的两点：

- **埋伏是阵法的次类型。**
- 次类型是**内容侧可扩展的**，故**不用 C# 枚举**，而用**稳定字符串 id + 一份次类型注册表**（`.tres`），使新增一个次类型 = 新增一个 `.tres`，不改代码。

**推论：次类型必须能被效果引用**（「所有『灵兽』获得 +1」这类牌是次类型存在的主要理由），故次类型 id 要进入效果的目标筛选条件——它不是纯展示标签。**具体的次类型清单留待日后。**

### 九、意图是决策链路的快照，一切以执行为准

> **意图 = 敌人在玩家回合开始前，按当时局面用公式推算出的本回合预期决策链路的快照。** 它**不是**对结果的保证：**一切以执行为准，意图无需与执行完全一致。**

这答定了「承诺与执行不一致时如何处理」这条待答问题，**答案是不做处理**——三个候选解（跳过该张照打其余 / 降级执行 / 允许临场替换）**全部不采用**，因为它们都在为「让快照与执行对齐」造机制，而快照本就不承担对齐义务。

**「意图即承诺」的措辞随之修正为：**

> **意图即快照：公布后不重算，但不保证与执行一致。** 敌人的下一回合计划在玩家回合开始时由公式推算定案，玩家在行动阶段做什么都不会改写它、也不刷新显示；**敌人回合的实际执行按执行时的真实局面求值**，与已公布的快照可能有偏差。

- **推论 ①（承重 · 代码面净减）：EnemyManager 不需要一致性校验与回退逻辑。** 执行阶段逐步走规划链路，每一步按**执行时的实际状态**求值；不可执行的步骤自然落空。没有「检测到不一致 → 选择处理策略」这条分支，`RunCombatAsync` 的敌人回合形状不变。**这是三个候选解里唯一不新增状态的解。**
- **推论 ②：埋伏牌与敌人道具不再是加压源，而是偏差的正常来源。** 在快照语义下它们不需要任何特殊处理，与「资源变化」同属一类。
- **推论 ③：「意图数值 ≠ 实际结算量」从异常升为常态。** 与 08-03「道念下限 0 在每一次结算时截断」「`PlayResult` 须携带本次实际削减量」完全合流：**意图是声明的量，`PlayResult` 是发生的量。**
- **推论 ④（唯一的新增落地要求）：意图的呈现语气必须是「预估」而非「契约」。** 措辞不给保证；**偏差发生时必须可解释**——敌人回合的执行过程需有逐步可见的反馈（每一步的飘字 / 结算日志），否则玩家会把偏差读成 bug。**这是本条对呈现层的硬要求。** 「仅类别」档本就无数值，呈现风险集中在完整意图档。
- **推论 ⑤：意图快照不必单独进存档。** 它由「局面 + 已持久化的 RNG `State`」确定性重算得到；若重算成本高可作为缓存写入，但那是优化不是正确性要求。
- **推论 ⑥：难度调节的旋钮不变**（规划算法与卡组，不在反应速度）。

### 十、战场与两个参战方 manager 的边界划线

**层级不动：五个 manager 保持平级。** TurnManager / CharacterManager / EnemyManager / BattlefieldManager / StackManager 同为第二级，`DeckModule` 仍是第三级。

> **划线判据：** 一件东西**在场上生效、可被效果针对 / 查询、需在结束阶段被清理、需进决策点存档** → **战场条目，归 BattlefieldManager**，条目自带 `OwnerSide` 表示归属方。**参战方的私有资源与牌堆**（mana、道念、手牌、卡组、本场可用道具）→ **归 CharacterManager / EnemyManager**。

按此判据，「我方本回合所有牌 +1 道念」是**战场条目**（`OwnerSide = Character` 的非永久条目），不是参战方状态——因为它要被针对、要被清理、要进存档。**「属于谁」只是它的一个字段，不是它的住处**：这正是那条待答问题此前卡住的地方——只用「属于谁」划不开，还要看「是否在场上生效」。

**双方场区不分开记录。** 单一战场记录 + 条目上的 `OwnerSide` 字段。理由：跨归属方的触发（埋伏监听「对手打出牌时」）与全场查询（「场上所有灵宠」）在单一记录下是一次遍历；呈现层按 `OwnerSide` 分区渲染即可。

**读侧统一、写侧分权。** 需要「整场全部信息」的场合（EnemyManager 规划意图、决策点存档、UI 组装）读 combat-service 组装的 `CombatSnapshot`。写入仍各归其主。

**为什么不把 BattlefieldManager 提为参战方之上一层**（四条理由）：

1. **它会把 BattlefieldManager 变成 god object。** 降级后 TurnManager（开始阶段恢复 mana、抽牌）与 StackManager（结算写双方道念）都不能再直接碰参战方，必须经 BattlefieldManager 转发。
2. **级联降级会强迫回答一个尚无判据的问题**——`DeckModule` 会被压到第四级 `processor`，而「module 以下的下沉判据未给」。
3. **层级词表的拆分轴是「生命周期层 + 行为边界」，不是「谁的信息全」。** 战场与两个参战方的生命周期完全同长（一场战斗），不存在包含关系。
4. **「拥有整场信息的顶点」已经存在**——combat-service 本身，且它已有现成的聚合出口 `CombatSnapshot`。

## 落地形态（schema 面）

### `CardType` 枚举

```csharp
public enum CardType
{
    Sorcery     = 0, // 法术：一次性，结算后进弃牌堆
    Creature    = 1, // 灵宠：结算后作为实体永久物落战场
    Enchantment = 2, // 阵法：结算后作为非实体永久物落战场（埋伏为其次类型）
    Item        = 3, // 法宝 / 古宝：不洗进卡组，存于储物袋
    Power       = 4, // 神通 / 法则：开局直接入场的徽记式永久物，受保护
    Affliction  = 5, // 业障：可打出但无正面效果，仅将自己送进弃牌堆
}
```

### `CardData` 的新增字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `CardType` | `CardType` | **必填**，无默认值（缺失 → 加载时 `PushError`） |
| `Subtypes` | `string[]` | 次类型 id 列表，可空。须在次类型注册表中存在 |
| `Abilities` | `AbilityData[]` | 该牌携带的异能列表，可空 |

### `ItemData` / `PowerData` / `AbilityData` / `TriggerConditionData`

```csharp
public enum ItemScope   { Character = 0, Player = 1 }              // 法宝 / 古宝
public enum PowerScope  { Character = 0, Player = 1 }              // 神通 / 法则
public enum UsableScene { InCombat = 0, OutOfCombat = 1, Both = 2 } // 道具与 Power 共用
public enum AbilityKind { Static = 0, Activated = 1, Triggered = 2 }
public enum TriggerOwnerScope { Self = 0, Opponent = 1, Either = 2 } // Opponent ← 埋伏靠这个成立

// ItemData  : Id / Scope / UsableScene / ManaCost(可选,可为 0) / Charges(古宝必有,法宝可 -1 无限)
//             / Abilities(启动式为主) / Subtypes
//             使用窗口 = 自己回合的行动阶段、栈为空时（全局规则，不是字段）
//             次数消耗 = 即时经 ProfileManager.TryApply 写回对应 Profile
// PowerData : Id / Scope / UsableScene / Abilities / Subtypes
//             无 IsProtected 字段（Power 一律受保护，后门在效果侧）
//             无 mana 费用字段（它不被「打出」）
//             status 开关仍在 Profile 侧：status == 关闭 ⇒ 不入场
// AbilityData          : Id / Kind / ActivationCost(仅 Activated) / TriggerWhen(仅 Triggered) / Effect
// TriggerConditionData : TimingId("turn.start"/"turn.end"/"card.played"…) / OwnerScope / Filter
```

### 效果侧的 `IgnoresProtection`（`Power` 的唯一后门）

「移除 / 针对战场条目」这一类效果元素上的 `bool IgnoresProtection = false`：`false` → 目标合法性排除 `IsProtected` 的条目（即所有 `Power`）；`true` → 可针对任意战场条目。

**纪律归内容侧，不归代码侧。** 代码只提供这一个开关与目标合法性分支，**不加「每场至多一次」「不得移除 Player 级法则」这类硬规则**：带 `IgnoresProtection` 的效果应极其稀缺、集中在高阶敌人 / boss 机制上；卡面文本**必须明示**它能拆 `Power`；若出现在敌人侧，它落在已公布的意图快照里，玩家有一回合的预警窗口。**代价（明确接受）：** 「我的法则会不会被拆」不再是类型级的绝对保证，而是内容级的稀缺保证。

### 战场条目的三分

| | 永久物 · 常规 | 永久物 · 受保护（`Power`） | 非永久条目（持续状态） |
|---|---|---|---|
| 来源 | 灵宠 / 阵法结算后落场 | **开局按持有列表入场** | 效果施加的临时状态 |
| 生命周期 | 无限期，直到被移除或战斗结束 | **战斗结束才消失** | 带标记：回合内 / 跨回合 / 持续 N 回合 |
| 结束阶段清理 | **永不清理** | **永不清理** | 清理标记为「回合内」的那些 |
| 可否被针对 / 移除 | 可 | **否**（`IsProtected = true`，唯一后门 = `IgnoresProtection`） | 待定 |

**所有战场条目共有字段：** `OwnerSide`、`IsProtected`、`SourceId` + 可序列化的运行态。**单一战场记录，不分双场区容器。**

### 加载时校验规则（坏数据启动即失败）

| 规则 | 违反时 |
|---|---|
| `CardType` 必填 | `PushError`，带 `Id` 与 `.tres` 路径 |
| `Sorcery` 不得带 `Static` / `Activated` 异能 | `PushError`——不留场，无生效载体 |
| `Affliction` 不得带任何异能 | `PushError` |
| `Affliction` 允许有 mana 费用与负向效果，但不得有正面效果 | `PushWarning`（软检查） |
| `ItemData` / `PowerData` 的 `UsableScene` 必填 | `PushError`——默认值会让漏填的东西悄悄进战斗 |
| `PowerData` 中 `Scope == Player` 且 `UsableScene` 含 `InCombat` 的占比 ≤ 1/5 | `PushWarning` + 报出当前比例（稀缺性纪律的机械化检查） |
| `Creature` / `Enchantment` 至少带一个异能 | `PushWarning`——空条目多半漏填 |
| `AbilityKind == Activated` 时 `ActivationCost` 非空 | `PushError`——零费启动式异能会造成无限循环 |
| `AbilityKind == Triggered` 时 `TriggerWhen` 非空 | `PushError` |
| `Subtypes` 中每个 id 须在次类型注册表中存在 | `PushError`，报出悬空 id |
| 次类型须与主类型匹配（「埋伏」只能挂 `Enchantment`） | `PushError` |
| `ItemData.Scope == Player` 时 `Charges > 0` | `PushError`——古宝定义上有次数限制 |
| `PowerData` 至少带一个异能 | `PushError` |
| 带 `IgnoresProtection == true` 的效果条目须逐个报出 | `PushWarning` + 列出条目 `Id` |
| 带 `IgnoresProtection == true` 的效果，其宿主的描述文本须非空 | `PushWarning`——「卡面必须明示」的最低限度检查 |

## 与既有决策的张力

1. **`sorcery speed` 是 08-02b 的已定案表述**（写在三份文档里）。本次删除该词——**但机制原样保留**，改的是措辞不是规则。
2. **「意图即承诺」的措辞被修正。** 08-02c 的定案在措辞上暗示了结果保证，快照语义把它收窄为「不重算」。**这不是推翻**：08-02c 的实质内容（玩家回合开始前一次性规划、不因玩家行动刷新、玩家能据它布局）全部保留；变的是**偏差不再是需要处理的异常**。代价是**呈现层要承担解释责任**。
3. **法则的战斗内强度：允许影响战斗，但极其稀缺（承重）。** 账号级内容由此进入战斗玩法层。**不设规则禁令**，代价由稀缺性承担：
   - **配额纪律：** `UsableScene` 含 `InCombat` 的法则 ≤ **1/5**，加载时统计比例、超标 `PushWarning`。
   - **强度定位：** 战斗内的法则偏向**体验改善与容错**（信息、便利、少量兜底），而非直接抬高道念产出上限。已定名的**探查**正是这类能力的样板。
   - **付费的战斗价值主要由古宝承载**——古宝有使用次数限制，次数天然是节流阀，让付费收益是「关键时刻多几次转圜」而非「永久变强」。
   - **仍需留意：** 法则不可被针对且跨轮回永久持有，故同一条战斗内法则的价值会随账号年龄单调累积；平衡时应按「**老账号全开**」而非「新账号裸奔」校准难度曲线。
4. **法宝 / 古宝的定义面被扩宽了。** 它们原本是「事件中使用的道具」，现在同时是「战斗内的卡牌类型」。**这不是推翻，是补全**：分 `UsableScene` 三档，因为有些道具在战斗里没有意义。

## 备选方案（已考虑并否决）

- **`sorcery speed` 保留并定名** — 单一取值的维度不是维度。
- **三步沿用「起始步 / 主阶段 / 结束步」** — 中文两「步」夹一「阶段」不齐整；`main` 的对照系不存在。
- **卡牌类型按「攻击 / 防御 / 增益 / 特殊」分（跟随意图类别）** — 意图类别是**敌人行为的展示分类**，与卡牌的**结算生命周期**正交；共用一套枚举会导致无解归类，且意图类别一改就波及卡牌数据。
- **Artifact 独立成一类** — 本作无「针对面」之分；「器物」语义已由 `Item` 承载，且它走储物袋而非卡组。
- **道具照旧洗进卡组** — 会与抽牌确定性、手牌上限、洗牌 RNG 全部纠缠。
- **把储物袋当作战斗内的一个区** — 敌人根本没有储物袋却同样有道具；容器与视图混为一谈会让敌人侧无处安放。
- **引入放逐区（exile）** — 现有六处位置已能表达全部已定案的流转。
- **为 `Power` 引入指挥区（command zone）** — 为一类不可交互、不移动的条目再开第七处位置，收益不抵成本。
- **借 `emblem` 并定中文名「徽记」作 `Power` 的类型通名** — 08-03 已定「`power` 不再有统一中文通译」；代码侧 `CardType.Power` 承担统一性即可。
- **`Power` 完全不可被交互（后门整个不开）** — 用户措辞是「rarely」而非 never，且日后开这条路要改 schema。
- **`Power` 后门做成条目级** — 它把例外钉在被拆的一侧：内容侧要为每个 `Power` 判一次「它是不是例外」，且「哪些法则会被拆」变成一张要维护的清单。
- **效果级后门 + 代码侧硬规则保护** — 硬规则会在规则层立一道日后必然要拆的墙，且把平衡决策编译进代码。
- **埋伏牌独立成一个主类型** — 它的一切规则都与阵法相同，唯一差别是面朝下 + 触发后进弃牌堆，这正是次类型的粒度。
- **业障不可打出、靠结束阶段自动移除** — 与「结束阶段只做触发 + 清理回合内状态」的定案冲突。
- **意图不一致时跳过该张 / 降级执行 / 允许临场替换** — 三者都在为「让快照与执行对齐」造机制；「临场替换」还等于开了重算的口子。
- **BattlefieldManager 提为参战方之上一层** — 四条理由见第十节。

## Open questions

- **埋伏是否进入敌人卡池。** 规则体系已支持埋伏（阵法的次类型 + `TriggerOwnerScope.Opponent`），但敌人侧是否也布置埋伏未陈述；若是，则玩家侧也需要「敌方场上有一张埋伏」的对称指示与 AI 之外的可读性设计。
- **埋伏是否计入敌人意图的呈现。** 埋伏在**对手回合**触发，而意图描述的是敌人**自己回合**的行动——它大概率不进意图，但需与意图类别枚举一并确认。
- **`Ambush` 的标识符与次类型 id 形态未定案**（当前为暂定值）；次类型注册表的 `.tres` 布局、id 命名规范亦未定。
- **各主类型的次类型清单**（法术 / 灵宠 / 阵法 / 道具各有哪些次类型）留待日后。
- **阵法与灵宠的区分轴**（实体 vs 非实体？产出形态？次类型体系？）按用户要求留待日后——目前二者的规则差别为零。
- **非永久条目（持续状态）的生命周期标记取值**，以及「持续到下回合结束」如何表达；非永久条目可否被针对 / 移除亦未定。（永久物一侧已由本次的二分答定。）
- **`IgnoresProtection` 的内容配额具体值**（多少条、集中在哪些档位的敌人）归内容侧，尚无数字。
- **储物袋的 UI 形态**（99 容量下的排序 / 分页 / 筛选）与它在元进程界面的落位未设计。
- **战斗内道具运行态与 `Power` 运行态的存档字段形态**（本场已用掉哪些、剩余次数、「本场已触发 N 次」这类计数器）需与决策点存档 schema 一并落定。
