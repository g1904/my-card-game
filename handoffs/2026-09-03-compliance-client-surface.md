## Intent（distilled）

**一句话：** 后端合规域六端点与七条 `code`（四条 `signin` 拦截 + 三条端点错误）已在对侧落笔完毕，边界另一侧交回客户端的三件事在此收口——三条新 `code` 的呈现、`ComplianceManager` 的覆盖面切分、注销 / 导出 / 实名的落屏。**全部增量都是既有纪律的直接应用，一条新规则也不立。**

### 一、三条端点码：零新增纪律

三条码全为不可重试档、全映 `OpError.Compliance` ⇒ **不新增 `OpError` 成员、阻塞屏变体表一格不动、不新增硬阻塞**。客户端只做两件事：处置表加三行（写在 `account-service.md` 的「失败映射」段——本库从无逐 `code` 表，逐 `code` 的跨边界台账权威在对侧 `contracts/envelope.md`，本库不复述）；`errors.csv` 加若干条翻译（键全由机械变换得出，`ERR_COMPLIANCE_TICKET_INVALID` / `_VERIFICATION_FAILED` / `_DELETION_IRREVOCABLE`，二级键同理）。

正向审计自动覆盖三条一级键；反向审计的前缀匹配天然放行二级键；`errors.csv` 的二级行是**措辞的载体**而非取值域声明，故本库仍不持有任何 `reasonKey` 清单。

### 二、呈现落在发起该操作的那一屏，一屏也不进阻塞屏

七条 `compliance.*` 逐条核过变体表的两条准入判据（由已知 `code` 触发 **且** 玩家没有任何自愈路径），**七条全部卡在后一条上**。四条拦截码落**登录屏**就地呈现 + 各一个主动作；三条端点码落**发起它的那一屏**内联呈现。准入若在此松动就会造出第三处由 `code` 触发的硬阻塞。

### 三、`ComplianceManager` 只做编排与呈现驱动，不做任何判定

切分判据一句话：**凡需要「一段流程」（多于一次请求、或需持有流程内凭据）的归它；凡只是「把一次失败说清楚」的归发起它的那一屏。** 四件明确不归它的事：任何判定（不读年龄、不比时钟、不算时段）· 会话中途下线（`AuthManager` 既有路径）· 昵称合法性判定与提交 · 拦截错误的措辞选择。

流程凭据**只在内存、绝不落盘、绝不出 API 面**，随凭据下发的过期时刻**读取即丢弃**；过期的唯一发现方式是拿去用一次。

### 四、合规态查询是单点且可降级

`GET /v1/compliance/status` 的调用点唯一，**排在会话到手之后、`SyncService.InitializeAsync` 之前**——不写作「`signin` 成功之后」，因为静默续期那条路径根本不走 `signin`。失败按「可选缺失」降级：重试一次 → 仍失败则告警 + 照常进主菜单，本次会话不呈现附加合规面。它归入 `sync-service.md` 三条不变式③ 的**第二形状**（「已知好值」含缺省值），不是第四种降级形状。

### 五、注销 / 导出落 PlayerProfile 屏；实名新增一屏

注销与导出排在绑定列表 · 昵称 · 持有的古宝之下，**不新增主菜单入口、不落设置屏**；注销走**就地二段确认**，冷静期提醒**只在本屏内**，主菜单零增量。导出按应答给出的建议间隔轮询，**离屏即停**，任务标识不落盘。实名屏是登录流程内新增的一屏（未登录态可达，竖屏单列 / 满足触控目标尺寸 / 安全区内 / 无 hover-only）。

**总账：** 不新增硬阻塞 · 不动阻塞屏变体表 · 不增 `OpError` 成员 · 不 bump 存档 schema · 不新增 `user://` 文件 · 不新开翻译分区 · 对后端零新增义务。

## Clarifications（interview 产物）

- **强制改名的强制力边界与「status 失败即降级」相抵吗？** → 维持 fail-open，并**明写边界**：客户端侧的强制改名不是硬阻塞，其兑现依赖一次可降级的请求；后端侧的兜底是存量扫描与复核通道。不要求后端在 `signin` 侧补一条拦截。依据：客户端不做任何本地合规拦截、强制力在后端；把它升级成启动阻塞则需改写阻塞点穷举那条承重不变式，代价远高于收益。
- **`ExportTaskInfo` 一型两用、字段填不满？**（标准默认）→ `RequestedAtUtc` 改可空 + 新增 `Deduplicated`。非空会逼客户端本地填当前时刻，撞「设备时钟不可信」；补 `Deduplicated` 后与注销应答口径一致。
- **三条 `code` 的处置写在哪份文档？**（标准默认）→ 写进 `account-service.md`「失败映射」段，**`systems/architecture.md` 零改动**。本库从无逐 `code` 表（只有 `class` 默认路径表），在那里开一张只有合规三条的半张表会制造一份天生残缺、且与对侧台账重复的第二权威。
- **status 失败的降级归入不变式③ 的哪一格？**（标准默认）→ 归入**第二形状**，并就地把「已知好值」明确到**含缺省值**（此处缺省 = 无附加合规面）。不变式仍是三条，属澄清而非松动。
- **账号注销的确认强度？**（评审阶段已定）→ 就地二段确认，**不新增 `ChallengePurpose` 成员**，契约面零增量。误触的兜底由冷静期 + 撤销通道承担。
- **冷静期是否在 PlayerProfile 屏之外常驻提醒？**（评审阶段已定）→ 只在本屏内呈现，主菜单零增量。
- **对侧台账把四条拦截码的客户端处置写作「阻塞屏 + XX 动作」。**（评审阶段已授权）→ 授权把对侧那一列改为回链本库的呈现形态；**语义不变，只消除措辞不一致**。本次不在对侧落笔，作为承接项登记。

## 落笔时核实出的三处订正

- **`ComplianceManager` 的职责行原写「防沉迷时长**校验**」**——「校验」二字与「不做任何判定」及「客户端不读年龄」相抵，同批改为「流程编排 + 呈现驱动」。草稿未提到这一行。
- **status 的调用时点措辞**：草稿写「`signin` 成功之后」，照字面落笔会让静默续期的玩家永不取 status；改为「会话到手之后」，落点复用 flags 刷新的先例。
- **`DeletionEffectiveAtUtc` 统一命名**：同一语义此前在两个类型上有两个名字，落笔时统一。
