# 静默续期绕过强更闸门的收口：refresh 链绝对寿命上限

- status: distilled
- distilled-to: `contracts/auth.md`、`contracts/envelope.md`、`operations/` 无改动、`open-questions/01-contracts.md`、`open-questions.md`、`open-questions/update-log.md`、`answer-logs/log-refresh-lifetime-cap.md`

## Intent（distilled）

**一句话：** `signin` 独占强更闸门 + 滑动续期无上限 = 闸门对长期在线的老版本客户端**永久且静默地**失效；收口手段取**时间维度**的 refresh 链绝对寿命上限，不取任何版本维度的形态。

### 缺口

`auth.md` §5 定「强更闸门只在 `signin` 判定，`refresh` 永不判定」，§2 定「refresh token 30 天滑动续期」。两条叠加：一个只走 `refresh` 的客户端在下一次真正 `signin` 之前永不被 `client.version_unsupported` 拦到。而客户端已把静默续期落到启动链第二步（续期成功即跳过登录屏），故「下一次真正 `signin`」在活跃玩家身上**可以永不到来**——只要不换设备、不清缓存、不主动登出、不被挤下线。失效是静默的：运营提升 `minAppVersion` 后，后台看到的仍是这批客户端在正常刷新。

### 采纳的形态

| 项 | 定案 |
|---|---|
| 机制 | 会话增一个 `signin` 时锚定、**rotation 永不顺延**的 `absoluteExpiresAtUtc`；有效性 = `now < min(滑动截止, 绝对截止)` |
| 判定点 | **只有 `refresh` 请求到达时**；不主动扫表吊销（那是运营触发的批量踢人，撞 `envelope.md` §7b） |
| 顺序 | **先判绝对到期、再判 60 秒宽限回放**——反过来会让一条已到期的链靠重放多活 60 秒 |
| 报文 | **不新增错误码**：复用 `auth.session_revoked` + 新 `reasonKey` `SessionExpired`。refresh 错误面仍是两条，客户端「有无明确应答」的判据一字不动 |
| 下行字段 | 不新增时间字段；`refreshExpiresAtUtc` 语义收紧为 `min(滑动, 绝对)`——下发一个链条已注定活不到的时刻是一句假话 |
| 旋钮 | 绝对上限 **60 天**（2× 滑动 TTL）· 软信号提前量 **3 天**。皆落后端配置，非代码常量 |
| 软着陆 | `signin` / `refresh` 应答增可选布尔 `reauthRecommended`，**服务端算好的布尔、绝不是时间戳** |

**为什么是时间维度而非版本维度——这句必须留在契约正文。** 服务端不因为「你版本旧」而终止你，只因为「这条链够老了」：截止时刻在 `signin` 那一刻已确定，与 `clientVersion`、与运营动作无关，玩家按登录时间天然错峰。少了这一句，日后的读者会把它读成「按 `X-App-Version` 定向失效」的委婉说法，而那一条正是 §5 禁止的。

**滑动续期承诺的是「永不因闲置而被动重登」，不是「永不被动重登」。** 后者与「闸门只在 `signin`」同时为真时，闸门必然可被无限规避——缺口就是这么来的。代价照录：活跃玩家每 60 天重登一次；`Phone` 渠道每次多一条短信成本。

**`profile-sync.md` §9 的 `pushId` 保留时长（30 天）零连带**（已核对）：它的推导依据是**闲置**失效口径，而本次不改闲置口径。

### 软信号的三条形态（后端半）

它**不是闸门，是着陆坡**——强制力全在绝对上限，改包客户端忽略它照样到期照样吊销，故它不构成「闸门退化为可忽略的建议」（单用软信号才会）。形态只能是服务端算好的布尔：客户端既定纪律禁止任何本地时钟比较，下发时间戳它合法地无法消费，而一台时钟偏了一个月的设备会得出完全错误的结论。**服务端持有唯一可信的时钟，判定就必须发生在服务端。**

## Clarifications（interview 产物）

本批四项取向已于 08-23 批量评审裁决，本次提炼照裁决落笔，未新增提问：

- 是否收口、走哪条路线 → **采纳绝对寿命上限**（另三条候选各撞一条更重的既有条款：批量强制 re-signin 撞 §7b；按 `clientVersion` 定向失效撞 §5 且把可伪造的自报头变成会话存续的判定输入；只下发软信号则闸门退化为建议）。连带确认 §2 的「永不被动重登」收窄，须同批落笔。
- 上限取值 → **60 天**（下界 ≥ 滑动 TTL，否则滑动旋钮失效并连带惩罚闲置玩家；上界 ≤ 一次强更的可接受排空窗口）。
- 是否引入软信号及其承载位置 → **引入，作为可选 body 布尔**（不走应答头：它是按账号算出的会话级判定，塞进「任意应答都带」的传输信封会造出一个大多数应答里恒缺的头）。
- 新 `reasonKey` 取值命名 → **`SessionExpired`**（与既有取值的「事件完成态」构词一致；它面向玩家措辞的分辨，不是机制的自述）。
- 契约正文里写死的封闭计数（合并 interview 新增）→ **统一消掉**：`envelope.md` §6 台账原写的 `reasonKey` 条数改为不带数目的回链，客户端同形写法同批处理。计数是会漂移的副本，与「回链而非复述」同向。

## Open questions

- **`refresh` 的滥用面与限流形态**（`open-questions/01-contracts.md`，待 `06`）—— 与本条同在 refresh 面上但互不阻塞、采纳顺序任意。本方案刻意不新增错误码，故**不消耗**「refresh 错误清单只有两条」那条纪律的额度、也不预设那一条的答案。两点实质关联供那一条决策时取用：① 绝对上限使任何一条 refresh 链的总刷新次数有界，滥用面收敛一档；② 若两条都松动，客户端将同时面对第三、第四条 refresh 失败路径，**总代价必须一起评估，不能各自单独评估后累加**。
- 绝对上限的**存储落点**（会话记录多一格）与 §4a 已移交实现层的三项同处，栈落定后一并承接（`06-platform-stack.md`）。

## 客户端侧影响

**是，跨边界，且已成对采纳。** 客户端半同批落笔于 `game-design-documents/handoffs/2026-08-23-refresh-lifetime-cap-client-half.md`：一条二级文案键 `ERR_AUTH_SESSION_REVOKED_SESSION_EXPIRED`（措辞取最平淡的例行口吻、不附原因句）+ `reauthRecommended` 的反应形态（内存态 · 不做任何本地时钟比较 · 启动期续期成功即呈现可跳过的登录屏 · 失败即忽略）。受影响的客户端成分只有 `account-service`。

**单侧采纳的失败形态**：后端下发一个客户端没有二级文案的取值虽有兜底（回落一级键、不报错），但玩家会在一次完全正常的例行到期上看到一句为「被挤下线」准备的措辞——**静默的错文案，没有任何报错会提示到它**。
