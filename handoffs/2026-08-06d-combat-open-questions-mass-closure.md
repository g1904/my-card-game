### 一 · 赋级带与意图

**① 意图揭示阈值整体收紧一级，三档在 `±2` 带内全部可达。**

| 篇章 | 完整意图 | 仅类别 | 完全无信息 | 带内格数分布 |
|---|---|---|---|---|
| **ch1 炼气** | `diff ≤ −2` | `−1 ~ +1` | `diff ≥ +2` | 1 / 3 / 1 |
| **ch2 筑基 · ch3 金丹** | `diff ≤ −1` | `diff = 0` | `diff ≥ +1` | 2 / 1 / 2 |

- **越阶硬门不变**（敌人境界更高 → 一律完全无信息，不论 `diff`）；上表只管同阶。
- **「碾压」重定义为「压到带内下界」**——ch1 `diff = −2`、ch2 · ch3 `diff = −1`，不再是「低 3 级」。
- `diff = 0` 三章恒为「仅类别」，08-02c「同级只给类别、不做补偿」原样成立。
- 角色全局等级 1 · 2 时带被上截断为 `[1,3]` / `[1,4]`，`diff = −2` 不存在 → 轮回最初两级恒为「仅类别」，是开局的自然状态而非死档。
- **代价（有意接受）**：ch2 · ch3 的黑箱门下移到 `diff ≥ +1`，后两章约五分之二的同阶遭遇完全无意图信息；**不做可读性补偿**（沿 08-02c），压力转嫁给图鉴、卡面文本与道念主视觉。**「仅类别是常态呈现」这条判断因此只在 ch1 成立**。

**② `±2` 是无例外的硬规则。** 任何调制源（PlotManager、location、事件模板、Finale）都不得产出带外 `diff`。**赋级函数不接受任何区间覆盖参数**——不给这个口子，就不存在「谁有权用它」。绝境感只能由样本卡组 / item / power / 遭遇参数四个旋钮表达，**永不由等级差表达**。最强论据来自 Finale：全作最凶的天劫都不享有等级例外。

**③ `lifeTotalLimit` 概念整体删除（承重）。** 角色只跟踪 **`lifeTotal` 一个值**：无上限字段、无上限截断。境界跃升仍在，但它是**给 `lifeTotal` 加一笔**而非抬高上限。

```
lifeTotal 境界基线 ≈ ceil(1.1 × 该境界内可能出现的最坏开局落差)
```

| 境界 | 带内最坏开局落差 | `lifeTotal` 境界基线（进入该境界时跃升到的值） |
|---|---|---|
| 炼气 | 9 | **10**（既定，公式恰好复现之） |
| 筑基 | 23 | **25** |
| 金丹 | 35 | **40** |
| 元婴 | —（终点，不产生遭遇） | **40**（仅供界面展示） |

连带：**回复类事件的单次幅度必须随境界基线跳档**（10 → 25 → 40 量纲），否则后两章的回复事件不痛不痒；玩家把 `lifeTotal` 堆到远高于基线是他自己攒来的容错，不是漏洞（堆耐久要花事件位，有机会成本）。

**④ 赋级分布 = 基础权重表（按角色在本境界内的等级位置分段）× 调制修正 × 截断重分配。**

| 章内进度段 | `−2` | `−1` | `0` | `+1` | `+2` |
|---|---|---|---|---|---|
| **早段**（本境界前 1/3 的等级） | 10% | 25% | 40% | 20% | 5% |
| **中段** | 5% | 20% | 40% | 25% | 10% |
| **末段**（本境界最后两级） | 5% | 15% | 35% | 30% | 15% |

- 众数恒为 `diff = 0`（「多数同级、偶有硬仗」）；分布随章内进度右移，与「压迫感向篇章尾部集中」同向。
- **PlotManager 只能改带内权重**，改不到区间。**事件类型不修正**（Combat / Practice 共用同一张表——Practice 的低风险由回合数与胜负门槛承担，不由派更弱的对手承担）。**Finale 不掷骰**（天劫是指派，恒为 `diff = +1` 且必然越阶）。
- **截断重分配必须显式写出**：全局序 1–22 截断后落空的档位权重按比例并入带内剩余档。
- **批内去重**：同一批 eventOptions 内多个战斗事件的赋级尽量互不相同（重掷一次，仍重复则接受）——只有一批里同时存在高低档，「越级挑战是可主动选择的风险维度」才成立。
- 已知代价：分段判据在 ch2 · ch3 天然粗（4 级里末段占一半，「一进中段就进末段」），**接受，不用第二把尺子去补**。

**⑤ 意图类别枚举 = `IntentCategory { Offense, Defense, Buff, Special }`**，判据以**道念语义**定义而非卡牌类型：

| 中文 | 标识符 | 判据 |
|---|---|---|
| 攻击 | `Offense` | 净效果是削减对手道念 |
| 防御 | `Defense` | 净效果是保护自身道念（抵消 / 减免 / 免疫 / 清除对手场上条目） |
| 增益 | `Buff` | 净效果是提升自身道念或自身后续产出 |
| 特殊 | `Special` | 其余：抽牌 / mana 操作 / 弃牌 / 探查 / 规则改写 |

- **映射 = 内容侧静态标注**（每个 `AbilityData` / 效果原语带一个 `IntentCategory` 字段），**不从合并结果反推**——卡牌类型与意图类别正交，正交的两套分类只能各自标注。
- **主类别选取可机械计算**：按类别归桶 → 每桶累计道念当量（`Special` 桶「存在即计 1」）→ 取贡献占比 **≥ 20%** 的全部桶 → 至少 1 个、至多 4 个 → 有序陈列。20% 是把符号数从 4 压到通常 1~2 的可调旋钮。
- **完整档的「一个结果值」**：主类别含 `Offense` → 数值 = 对玩家道念的预估净削减量，负号呈现（`−12`）；不含 `Offense` → 敌人道念的预估净增量，正号呈现（`+9`）。**共用一个数字位，靠符号区分。**
- **不进意图但仍参与合并计算**：埋伏、静止式异能。「不进意图」≠「不参与计算」，须写明。
- 需要一个正式的 `IntentRevealTier { Full, CategoryOnly, Hidden }` 枚举承载三档。

**⑥ 敌人等级标注：面向玩家一律「境界名 + 层级」，全局序 1–22 不出现在任何 UI 上。**
- 境界名让「越阶」自动可见（「筑基巅峰 vs 金丹初期」一眼跨境界，「17 vs 18」看不出来）——这让「意图为何被遮蔽」无需教学即可读出。
- `EventOption` 的战斗类卡片上**并列显示双方等级**（`我 · 筑基中期 ⟶ 敌 · 筑基后期`）；**战斗屏内不并列玩家自身等级**（竖屏空间压力最大处）。
- **不做方向标记**（`↑` / `=` / `↓` 一律不加）——把「日后被扩成三色 / 加文字 → 滑向模糊危险度档位」的风险从根上掐掉。

**⑦ 物化时「充实 / 改写」敌人 = 五旋钮管线，输入固定、顺序固定、产物落存档。**

```
① 选池 + 选模板 ← 池归属标签（通用 / 地点专属 / 剧情线专属）+ location + 篇章 + eventType 框定 → 加权抽取
② 赋级         ← 角色全局等级 ±2 带 + 权重表
③ 卡组结构对齐  ← 以 ② 的等级为输入（仅费用曲线对齐与风味替换）
④ item / power 持有列表 ← 直接取自模板
⑤ 遭遇参数     ← eventType（Combat 默认 10 回合 / 道念高者胜；Practice · Finale 改写）
产出：EnemyInstance（定稿 · immutable · 随 EventOption 落存档）
```

- **剧情线不可调制敌人模板；剧情线与地点各自可拥有专属敌人模板池。** 差异化的表达位从「改写模板内容」整体移到「**换一个池子抽**」。PlotManager 的权力收敛为三项：**框定用哪个池 · 偏移带内赋级权重 · 拧紧遭遇参数**，**碰不到模板的任何字段**。好处：改写幅度天然有界、图鉴词条与实际遭遇恒对得上、可确定性复算；代价：专属敌人是完整条目，内容量上升。
- **等级先定，其余四项以等级为输入，且不叠加第二条强度曲线**——卡组保持强度中立，等级只经 `baseMomentum` 生效，否则 `±2` 带的数值安全性推导立刻失效。
- **可机械检查的改写上界**：物化改写必须保留模板标注的关键卡牌，否则图鉴与实际遭遇对不上 → `PushWarning` + 该次改写回退。**定制卡组条目显式豁免**（`OverridesDeck = true` 时跳过检查，图鉴条目自带说明）。
- 卡组改写形态：常规敌人走**算子式**，boss / 天劫走**多套预制**，二者并存。

**⑧ `EnemyTemplate` 与 `EnemyData` 是同一个东西，统一定名 `EnemyData`；物化实例定名 `EnemyInstance`。**
- `XxxData` 是全库内容层的命名族；`EnemyTemplate` 只是叙述性说法，不是第二层结构。中文领域词「敌人模板」保留不动。
- `EnemyInstance` 性质**对齐 `EventOption` 而非 `CardInstance`**：物化即冻结、落存档、下游只读。**敌人的战斗内运行态由 EnemyManager 持有**，不进 `EnemyInstance`、也不另立类型。
- **嵌在 `EventOption` 上随批次落存档**，不在战斗开始时二次展开（唯一物化点 / 选择界面就要显示等级 / 意图档位在战斗前即需可算，任一条单独成立即封死另一选项）。
- **本作不存在多敌人场景 —— 字段写单数** `EnemyInstance Enemy`，不写列表、不留伸缩位。

### 二 · 存档与结构

**共用公理：决策点 = 战斗状态机唯一可以停下来的地方。** 存档 schema、取消语义、内容密度、决策点清单、取消触发方全部由它导出。

**① `ActiveCombat` —— `CharacterProfile` 上一个可空块**，战斗开始时创建、`eventEnd` 收口时置空；不进 `pastEvent`、不与 `Rng.Streams[]` 混住。diff 天然落在 `CharacterProfile` 粒度，无需新同步单元。

顶层：`eventInstanceId` · `encounterId` · `turnLimit` · `turnIndex` · `activeSide` · `step` · `rng` · `sides`（恰两条）· `battlefield` · `stack` · `pending`（全局至多一个）。

- **参战方**：`side` / `momentum` / `currentMana` / `manaLimit` / `drawPile` · `hand` · `discardPile`（`CardInstanceId` 有序序列）/ `instances` / `items` / `enemyRef`。`CardInstanceSave(InstanceId, CardId, Counters)`。**`InstanceId` 确定性发号**（闭集，按固定顺序 `c#0` / `e#0`…），**`CardType` / `Subtypes` 不落存档**。
- **战场条目单表 + `kind` 表达三档**（`PermanentCard` / `PermanentPower` / `Transient`）：`entryId`（目标引用锚点）/ `sourceId` / `sourceInstanceId` / `ownerSide` / `lifetime` / `remainingTurns` / `faceDown`（埋伏）/ `counters`。**`Power` 的战斗内运行态不需要独立结构——它就是战场条目的 `counters`。**
- **栈条目**（数组序即栈序，0 = 栈底，**不落 `position` 字段**）：`stackEntryId` / `kind`（`PlayedCard` / `TriggeredAbility` / `ActivatedAbility`）/ `controllerSide`（决定这次目标选择是否产生决策点）/ `sourceInstanceId` / `sourceEntryId` / `abilityId` / `chosenTargets` / `targetState`。
- **`pending` 全局至多一个**（`stackEntryId` + `slotIndex`）：结算是 LIFO 单线程推进，不可能同时有两处等输入；**合法目标集不落存档**，恢复时按当前局面重算。
- **道具运行态只落「本场已用几次」**（`CombatItemSave(ItemId, UsesThisCombat)`）：可用道具列表本身派生自 `UsableScene` / `EnemyData` 持有列表，古宝总剩余次数权威在 PlayerProfile（存两份即双写）。**本作确实存在「本场配额」类道具效果**，故 `items` 是 schema 的正式组成部分。
- **不落存档的可重建项**：`isProtected`（`kind == PermanentPower` 即 `true`）· 触发器注册面 · `Power` 的入场本身 · 合法目标集 · 意图快照。
- **读档校验四条**（强制）：`eventInstanceId` 不一致 → `PushError` + 拒绝恢复；内容 id 解析不到 → `PushError`（注意 `Get(id)` 不过滤 `ContentEnabled`，故中途被线上关闭的条目仍能恢复）；`pending.stackEntryId` 找不到 → `PushError`；**三区 `Id` 序列的并集 ≠ `instances` 全集 → `PushError`**（闭集不变式的自校验，是「无凭空生成的牌」买来的一条免费断言）。

**② 挂起态的取消语义：回到该选择点，栈原样挂起，不允许反悔。**
- 回退到更粗的边界意味着重放已弹栈结算的条目，而 RNG `State` 已随之前进——要么局面分叉，要么就得回滚 `State`，那等于给玩家开了「不满意就退出重掷」的窗口。与「`SelectCost` 不回滚」同一条纪律：**已经发生的事就是发生了**。
- **进入挂起态本身即一个决策点**，故「恢复到该选择点」不需要额外机制。
- 硬要求：**选目标态必须自解释**（交代是哪张牌 / 哪个异能在要求选目标、它要做什么），不能依赖玩家的短期记忆——玩家可能隔几小时才回来。

**③ 需要选目标的触发式异能：稀少（≤ 10%），作为设计亮点。**
- 配额纪律（统计 + `PushWarning`，本库第三次应用）：占全部触发式异能 **≤ 10%**；一场标准 Combat 期望进入挂起态 **1~2 次**（编排口径，不可机械化）。
- 频度天然低：玩家主动出牌的目标在**打出时**就选定（`targetState = Resolved`），挂起态只来自「压进去的东西在结算时回头问一句『指谁』」；敌人侧的目标选择由 EnemyManager 自行决定、不产生决策点。
- **稀少改变的是性能预算，不是正确性要求**：D4 必须在决策点清单里。连带成立——挂起态存档不做任何专门优化，`ActiveCombat` 全量序列化足够，**栈的增量写入不做**。

**④ 决策点清单（判据：战斗状态机即将停下来等玩家输入，且此前消耗的随机已全部反映在持久化的 RNG `State` 里）。**

| # | 决策点 | 精确时刻 | push |
|---|---|---|---|
| **D0** | 战斗开始 | 参战方组装完成（含 `Power` 入场）、第一个开始阶段之前 | `Immediate` |
| **D1** | 行动阶段开始 | 开始阶段全部走完（mana 恢复 → 触发结算完 → 抽牌完），栈为空 | `Debounced` |
| **D2** | 一次出牌 / 启动 / 用道具结算完毕 | 栈再次清空、控制权回到行动阶段 | `Debounced` |
| **D3** | 玩家回合结束 | 结束阶段清理完，移交对手之前 | `Debounced` |
| **D4** | 进入挂起态 | `targetState = AwaitingChoice`、`pending` 写入那一刻 | `Debounced` |
| **D5** | 敌人回合结束 | 敌人整回合执行完（含其栈全部结算完）、交回玩家之前 | `Debounced` |
| **D6** | 战斗收口 | 胜负判定 + 奖励算定完成 | 并入 `eventEnd` 的单一事务存档点 |

**明确不是决策点**：弹栈结算的每一次弹出（除非因此进入 D4）· 敌人回合内部的任何一步 · 意图呈现 · 战后奖励选择。

密度 ≈ **31 个决策点 / 场**（本地写 ≈ 93 KB/场，毫秒级）。**保留 D2**——它是「退出重进得到同一局面」在最自然位置的兑现；若实测超预算，**第一刀砍 D2 的 push 而非 D2 本身**。**缓冲上限闸门口径改为「未同步的事件级存档点 ≥ 3」**，战斗内 D0–D5 照常写本地、照常防抖 push，但不参与软阻塞判定。

**⑤ `attemptIndex` 整层删除。** `Hash64(combatStreamSeed, eventId)`（去掉一层）；`RetryChapter` 内部生成新 seed，与首次 `StartCycle` 走同一条生成路径；从未落存档 → **不 bump schema 版本、无迁移**。承重结论：**「篇章重试」是重开一局，不是重打这一局**——同 seed 重试会让它退化为背版，而重试在本作是稀缺且可付费扩容的资源。

**⑥ 取消只有两个真触发方：玩家主动退出、后端把他踢下线。** 其余六类（应用失焦 / 进程被杀 / 断线 / overlay 热更 / 软阻塞 / 正常收口）全部是既有定案已明确「不打断」的路径——「谁会取消」的答案因此是**闭合的**。

- **`ct` 只在决策点被观察**：`AdvanceToNextDecisionPoint()` → `PersistDecisionPoint()` → `ThrowIfCancellationRequested()` → `WaitForPlayerInput()`。三条推论：**取消点与存档点永远重合**（对齐问题不存在，而非「靠约定去对齐」）· **中间态永不需要持久化** · 等待输入期间收到取消则落在 D1/D2/D4 之一。
- **`AdvanceStage` 新增 `Cancelled`**：取消是预期内的，不该以异常穿透。它与其余四值的区别是「**这一步还没结束**」而非「这一步不合法」——编排顶点据此**不清理 `ActiveCombat`、不推进状态机、不记 `pastEvent`**。
- **玩家主动退出取静默退出**，不做二次确认弹窗（手感优先）。代价：「进度保留在当前决策点、成本不退还」这条规则玩家看不见，须由战斗屏常驻措辞或首次退出的一次性提示承担，**不是弹窗流程**。

**⑦ module 以下的下沉判据：第四 / 第五级的判据是「形态」而非「职责」。**
- **processor = 无状态的处理阶段**；拆出需**三条与门全中**：① 可独立命名、输入输出明确、**不持有跨调用状态**（这是与 module 的分界——module 持有状态）；② 有 ≥ 2 个同形态实现或明确的可替换性；③ 拆出后调用入口仍只有宿主 module 一个。
- **handler = 按开放 `kind` 分派的叶子**：kind 集合封闭且稳定时（如 `TurnStep` 三值），一个 `switch` 比五个 handler 类清晰得多。handler 的价值在**可加性**——与「新增一张卡 = 新增一个 `.tres`」是同一条纪律在代码侧的投影。
- **三条反判据**：只是文件太长 / 只被调用一次且无变体 / 为了让层级看起来更完整。**层数不是成熟度指标**——「抽象层次不封顶在两级」同样意味着不封底。
- **第四 / 第五级暂不落实例**（保持空是健康的）。校准样本：目标合法性筛选 ✅ 最强候选 · 效果施加 ✅ 强候选 · seeded 洗牌 ❌ 不拆 · 意图生成 ❓ 观察。`BattlefieldManager` 提级仍不推荐（本判据只消解了它的第二条理由）。

### 三 · 卡牌与规则

**① 次类型 = `CardSubtypeData : Resource`，权威匹配面落在字段上而非 id 前缀。**
- 字段：`Id` / `DisplayName` / `Description` / **`AllowedCardTypes`（数组）** / `ContentEnabled`。
- **id 规范 `<maintype>.<name>`**，全小写 `snake_case` 词身、点号分段——沿用 `TriggerConditionData.TimingId` 的 `"turn.start"` 惯例，前缀是可读性约定而非校验依据。
- **`Ambush` 的最终标识符 = `enchantment.ambush`**（显示名「埋伏」），从 `terminology.md` 移除 PascalCase 暂定形态（它不是枚举值）。
- 注册表：目录按主类型分只为浏览方便，**DataRegistry 递归扫描并建单一全局索引**。新增两条加载校验：`Id` 重复 → `PushError`（报两个 `.tres` 路径）；`AllowedCardTypes` 为空 → `PushError`。**「次类型 X 未被任何筛选条件引用」的 `PushWarning` 做**（这条可机械化）。
- **准入判据**：一个次类型只有在同时满足「≥ 3 个内容条目共享它」+「≥ 1 处目标筛选引用它（存在 payoff）」时才应存在。**没有 payoff 的次类型就是展示标签**，纯风味写进描述文本。
- 初值清单（可随内容重排，不动 schema）：`sorcery.talisman` 符箓 / `sorcery.sword_art` 剑诀 / `sorcery.incantation` 咒术 · `creature.spirit_beast` 灵兽 / `creature.puppet` 傀儡 / `creature.artifact_spirit` 器灵 · `enchantment.ambush` 埋伏 / `enchantment.formation` 法阵 / `enchantment.ward` 护阵 · `item.pill` 丹药 / `item.scroll` 玉简 / `item.instrument` 器物 · `power.technique` 功法 / `power.physique` 体质 / `power.dao_law` 道则 · `affliction.injury` 伤势 / `affliction.karma` 业力。
- **`Item` 与 `Power` 也建次类型**：它们不进卡组但同样带 `Subtypes`，且储物袋 99 容量的筛选 UI 需要一个分类轴。
- **阵法与灵宠的区分轴仍留待日后**：上表只是各自的内部分档，不构成两个主类型之间的差异化。

**② 回合三步结构的卡牌侧数值（初值，归 ch1 数值标杆专场回归）：**

| 项 | 值 | 依据 |
|---|---|---|
| 起始手牌 | **5** | 与 mana 基线 5/5 同值，「起手 5 张、每回合 5 点」对称易记 |
| 每回合抽牌 | **2** | 流入 5 + 10 = 15 张，与 5 回合 × 5 mana 预算下可打出的张数量级吻合——三个候选里唯一让两条资源线大致等长的取值 |
| 首回合是否抽 | **抽**（无例外） | 三步结构对每个回合一视同仁；为一条没有必要性的例外增加状态是错的 |
| 先后手抽牌差 | **不设** | 本作胜负是打满 10 回合比总量、不设提前终止，先手抢先致死的 tempo 优势**根本不存在**；后手反而握有信息优势 |
| 手牌上限 | **10** | 起手 5 → 第 3 回合 11 > 10：**不出牌的玩家第 3 回合就撞上限，正常出牌永不撞**——这正是「逼玩家出牌腾位的节奏约束、不是惩罚」 |
| 敌人侧 | **完全同值** | 参战方对称；意图可读性依赖对称（否则玩家无法从自己的经验推断敌人的行动空间，图鉴的「关键卡牌」也失去参照系） |

- **接受「敌人侧不做规则层差异化」**：难度差异走 `baseMomentum` 与遭遇参数，不走规则分叉。规则层的不对称是第四条冗余旋钮，且是玩家看不见的最不可读的一条。这确实关闭了一条平衡手段，已知并接受。
- **落点**：三项数值住在平衡资源（`CombatRulesData` 一类），**`EncounterSpec` 可携带一组可空覆写**（null = 取默认）——「更宽容的 Practice」最自然的形态之一就是多抽一张。

**③ 「回合内状态」= 三值枚举 + 两个配套字段。** 难点在于本作的回合**有归属方**，「下回合结束」在双方视角下指向两个不同时刻：

```csharp
enum EntryLifetime  { UntilEndOfTurn, ForTurns, Indefinite }
enum CountdownSide  { Owner, Opponent, Either }
// 非永久战场条目：OwnerSide / IsProtected(恒 false) / SourceId / Lifetime / CountdownSide / RemainingTurns
```

- **`Indefinite` 与「永久物」不是同一件事**（须写死）：永久物是「来源是灵宠 / 阵法 / `Power`」的**类型级判定**，`Indefinite` 是非永久持续状态的一个**生命周期取值**。差别落在可被什么效果针对上。
- **回合内状态的精确定义**：战场上 `IsPermanent == false` 且 `Lifetime == UntilEndOfTurn` 的条目。结束阶段清理其中 `CountdownSide` 解析到当前归属方的那些，**永远不触碰永久物，也不移除 `ForTurns` / `Indefinite`**（后者只递减）。
- **「持续到下回合结束」不是新档位，是三件套的组合**：「到你的下回合结束」= `ForTurns(2) + Owner`；「到对手的下回合结束」= `ForTurns(1) + Opponent`；「持续 3 个回合」= `ForTurns(3) + Either`；「本场战斗内」= `Indefinite`。**卡面文案必须显式点明归属方**（「到你的下回合结束」而非「到下回合结束」）——这是措辞硬要求。
- **`Either` 保留但内容侧默认不用**，使用时 UI 必须显示剩余跳数。加载期校验掉无意义组合（`Lifetime != ForTurns` 时 `RemainingTurns` 必须为 `-1`；`ForTurns` 时 `>= 1`）。
- **非永久条目可被针对 / 移除，但效果必须显式声明目标类别**。目标合法性 = 类别匹配 **且**（`IsProtected == false` 或 `IgnoresProtection`）；非永久条目 `IsProtected` 恒 `false`，故常规移除类效果自然命中，**不需要第二条保护规则**。理由：封死规则层等于让「驱散临时增益」这类最经典的反制面在本作永远写不出来，而交互移除后节奏张力全部落在效果系统上，砍掉一整条设计面与压力方向相反。**内容侧保持稀少**（多数临时增益本就自动过期，价值集中在拆 `Indefinite`），配清单式 `PushWarning` 逐条列出。

**④ 效果 / 状态系统 = 三层。**

```
第一层  EffectData（原子操作，数据驱动可组合）
第二层  BattlefieldEntry（由「施加持续状态」产出，带生命周期三件套）
第三层  求值管线（数值在「使用时」按战场上的静止式修正聚合得出）
```

- **原子操作初值**：`ModifyMomentum` / `Draw` / `Discard` / `ModifyMana` / `ApplyState` / `RemoveEntry` / `MoveCard`。清单开放可加，**关键是它是数据不是代码分支**。
- **承重推论：本作不存在「参战方身上的 buff / debuff 列表」这个数据结构。** 一切增益减益都是战场条目（要被针对、要被清理、要进存档）。这消除了「有的状态在角色身上、有的在场上」的双轨制，也让结束阶段清理成为**唯一**的状态过期通道。
- **求值管线 = 加法层 + 乘法层两层**，「翻倍 / 减半」类效果可以存在。**「加法先于乘法」写成规则而非实现细节**（与「步内顺序是规则的一部分」同一处理）。静止式修正不入栈、不参与 LIFO，只在求值瞬间被读取。
- **`CardInstance` 运行态的判据（承重）：有过期时刻的 → 战场条目；无过期时刻且属于这张牌本体的 → `CardInstance`。**
  - 三条理由：**回滚是不可承受的复杂度**（求值期聚合根本没有回滚这个概念）· **动态集合写不进实例**（「所有『灵兽』+1」作用于随时间变化的集合，写进实例语义直接错）· **存档面净减**（否则每个决策点都要序列化全部手牌的临时修正）。
  - 允许写入实例的只有：无时限的本体改写（「本场费用永久 −1」）、本体计数器（「本场已被打出 N 次」）。
  - **边界情形**：「本场战斗内所有符箓费用 −1」虽无时限，但作用于**集合** → 仍是战场条目（`Indefinite`）。**集合性效果一律走战场，无论有无时限。**
- **非永久条目也可以带 `AbilityData[]`**；**条目被清理时其上的触发器同时注销**——这是清理逻辑的隐含义务，须写进 BattlefieldManager 的职责。

**⑤ 敌方卡组：共用 `CardData` 体系，不共用卡池。**
- **`CardData.Pool : CardPool { Character, Enemy, Both }`，必填、无默认值、缺失即 `PushError`**（同 `CardType` / `UsableScene`——默认值会让漏填的东西悄悄进玩家奖励池）。
- 共用体系的理由：`DeckModule` 双方各持一个（两套 `CardData` 要泛型化或分叉）· 战场单一记录 + 单一 StackManager（不同数据类型则 `SourceId` 无法统一解析）· 异能三分 / 次类型筛选 / 效果元素否则要实现两份。
- 不共用卡池的理由：**奖励抽取必须能排除敌方专用牌**（一个字段过滤 + 与 `ContentEnabled` 完全同构的产出侧位置）· 两侧设计目标不同（构筑 vs 可读的对手行为）· `Both` 档保留交集避免 `Id` 二义与图鉴重复。
- 新增两条校验：玩家侧抽取源必须只含 `Pool != Enemy`；`EnemyData` 样本卡组不得含 `Pool == Character`。
- **卡组规模固定 15**（= 一场牌流入上限 5 + 5×2，**保证永不重洗**），**允许同名条目重复**——「牌少而精的小怪」靠重复条目表达（8 种牌重复到 15 张），重复 = 行为可预测，且让图鉴的「关键卡牌」真正有意义。规模**不作为物化旋钮**（改规模会牵动确定性）。
- 抽牌规则与玩家完全同规则；**敌人抽牌走独立的战斗 RNG 子流**（玩家的一次额外抽牌不打乱敌人牌序）；重洗代码路径共用（Finale 改写回合数时会真实发生）。

**⑥ 探查（probe）——仍搁置到内容横向扩展阶段，但方向一并定死，不再作为待答项挂着。**
- **6.3 的「升一档」现在就固定为规则层结论**：完全无信息 → 仅类别；仅类别 → 完整意图；已完整 → 无效果且 UI 禁用。**越阶黑箱不得被任何内容道具打穿**——否则一条结构性规则被一件内容道具整个绕过。
- 载体取**古宝 + 阵法双载体**（前者「关键回合一定拿得到」，后者 build 向）；法则可有但极稀缺；**法术不做**（信息能力最怕需要时抽不到）。
- 花费 **mana 为主 + 古宝上叠 `Charges`，明确排除弃牌**（弃牌把信息成本压在 5 回合对局里极稀缺的手牌上，代价过重且不可预测）。
- 时效：只揭示当回合已公布的快照，不重算、不延续 → **探查是纯呈现层开关，`RunCombatAsync` 形状不变**。

**⑦ `manaLimit` 推拉：单次幅度恒为 1，不设 ±2 档。**

| 事件类型 | 推高 | 压低 |
|---|---|---|
| **闭关 Research** | **主通道 · 常见** +1 | — |
| **境界突破 Finale** | **每篇章一次** +1（保底成长） | — |
| **探索 Explore** | 稀有 +1 | **罕见 −1**（唯一常见的下降来源） |
| **交易 Exchange** | 稀有 +1 | — |
| **社交 Social** | 稀有 +1 | — |
| **战斗 Combat / 修炼 Practice** | **不给** | — |
| Travel | — | — |
| Mystery | 继承揭示后的实际类型 | 同 |

- `+1` = 出牌预算 +20%，已是可明确感知的一档；`+2` 一次事件就改写整个卡组的可打出性，与「长期成长应是细步累积、不是跳变」不符。
- **战斗类不推高 `manaLimit`** 是有意的分工（避免滚雪球）——战斗的长期价值走「道念差 → 奖励厚度」与经验。**已知代价**：若篇章内战斗占比过高，玩家会感到成长停滞，须与事件池分布一并校准。
- 篇章预算感：一章净增 **+1~+2**（炼气 5 → ch1 末 6~7）。**牌流是 `manaLimit` 增长的天花板**（手牌流入 15 张 / 上限 10），膨胀过快会出现「有 mana 没牌打」。
- **压低只以「负向奖励条目」的形态出现**，不另立结构。
- **mana 有上限字段而耐久没有，这处非对称必须连同理由写清**（mana 是每回合重置的节奏资源，耐久是跨事件累积的容错资源），否则日后极易被当作不一致而「顺手统一」。

### 四 · 奖励与遭遇参数

**① 胜侧「道念差 → 奖励厚度」= 两条支路。**
- **支路 A · 强制奖励（可数量）= 线性 1:1 × 可调单价**：`element 量 = baseReward 中该 element 的量 + 道念差 × rewardPerMomentum[element]`。**「1 点道念差 = 1 个 `rewardPerMomentum` 单位」——这是本条问题的正面答案**：它不是写死的物件，而是一条数据侧系数（全取 1 时退化为字面 1:1）。不设上限截断（与负侧一致）。
- 单价**逐篇章下调**（ch1 1/点 → ch2 1/2点 → ch3 1/4点），否则奖励通胀曲线会被偷偷绑死在为「越级难度」设计的 `baseMomentum` 百倍曲线上。
- **支路 B · 可选奖励（品质）= 归一化三档**：`advantage = 道念差 / max(1, 角色 baseMomentum)` → `< 0.25` 险胜 `Narrow` / `0.25~0.75` 优胜 `Solid` / `≥ 0.75` 碾压 `Crushing`。归一化是必要的——绝对值不可跨境界比较。
- **奖励结算屏显式陈列算式**；档位以标签呈现，玩家不需心算 `advantage`。
- 已知：道念差有**两个消费点**，调平衡时要同时看；单价表是承重旋钮，必须进 ch1 数值标杆专场。

**② 可选奖励候选：固定 3 项，道念差只改质量。**
- 数量恒定使 UI 布局稳定，也避免「多给一项」这种价值跳变让玩家更想 reroll（而 reroll 通道已被「奖励选择不是决策点」封死）。
- **池 = 事件模板的 `RewardPoolId`，经 `AllEnabled()` 取池**，混合 `CardData` 与 `ItemData`；**挂 `AdventureEventData` 不挂 `EnemyData`**——「打赢什么敌人」与「这场给什么奖」是两件事。稀有度权重按 `Tier` 调整。
- **候选结果预先算定并落存档**（3 个 `Id` + 一个 `Tier`），恢复时**读已抽定的结果，绝不用同一 `State` 重抽**——后者依赖抽取算法永不变更，是脆弱保证。
- **不设「放弃全部候选」通道**（放弃会重新制造一个心理决策点）。合法池不足 3 条目时**显式降级**（`PushWarning` + 给出实际项数），不静默给 2 项。

**③ 回合数与胜负判据落在 `EncounterSpec` 上**，值由 future-event-service 物化时从 `AdventureEventData` 代入，**`EnemyData` 完全不携带**（否则同一敌人条目无法同时用于 Practice 与 Combat）。

```csharp
public sealed record EncounterSpec(
    string            EncounterId,   // 战斗类事件下 = EventOption.InstanceId
    EventType         EventType,     // Practice | Combat | Finale —— 仅供呈现 / 埋点，规则不由它派生
    EnemyInstance     Enemy,         // 单数：本作不存在多敌人场景
    int               TurnLimit,     // 双方合计回合数；标准 Combat = 10
    VictoryRule       VictoryRule,
    string            RewardPoolId,
    ProfileChangeSpec BaseReward);   // 物化时定稿

public readonly record struct VictoryRule(int WinMargin, bool DrawCountsAsLoss);
// d = 角色道念 − 敌人道念： d >= WinMargin → Victory；否则 DrawCountsAsLoss ? Defeat : Draw
```

- **关键简化：胜负判据不需要「可替换的判定对象」，两个数就够。** 标准 Combat `(1, false)`、Practice `(0, false)`、Finale `(N, false)` 已完全覆盖已陈述的全部需求——无需策略枚举、无需分发。
- **`IsFinale` 收编为 `EventType`**：一旦回合数与胜负判据显式化，规则不再从它派生，它退化为呈现 / 埋点标记。
- **`BaseReward` 随物化定稿**（热更不影响进行中的遭遇），与「`EventOption` 产出即定稿」一致。
- `EncounterSpec` 由 `readonly record struct` 改为 **`sealed record`**（字段多、含引用类型、落存档、非热路径）。

**④ Practice / Combat / Finale 的改写值：难度旋钮 = `WinMargin`，回合数 = 节奏旋钮。**

| 档 | `TurnLimit` | `VictoryRule` | 语义 |
|---|---|---|---|
| **Practice**（small blind） | **8** | `(0, false)` | 道念相等即判胜——「点到为止」 |
| **Combat**（big blind） | **10** | `(1, false)` | 标准档 |
| **Finale**（boss blind） | **12** | `(N, false)` | 须领先 N 点方可突破 |

`N` 初值：ch1 **3** / ch2 **5** / ch3 **8**（对应开局落后 5 / 13 / 25）。

- Practice 减到 8：追分窗口少 2 回合，但要求从「反超」降到「追平」，两侧相抵 → 更简单且更快，正是 small blind 该有的节奏。
- Finale 加到 12：若同时减回合会退化为**纯粹的起跑线检定**，玩家一整章攒起来的 build 无从表达。**「更难」体现在门槛，不体现在窗口。**
- **Finale 失败不直接 `defeated`**（不新增 `DefeatReason.FinaleFailed`）：按 1:1 扣 `lifeTotal`，打穿则经既有的 `LifeTotalExhausted` 自然导向 defeated。**结果上「Finale 失败常常等于死」，但走的是既有通道。** 失败后角色留在本篇章，`lifeTotal` 未归零即可继续消耗寿元找事件并**再次挑战 Finale**。
- **⚠ Finale 四重压迫叠加**（天然越阶黑箱 + 开局落后 + `WinMargin` + 失败扣得最狠），四条都是既有定案的必然结果。`WinMargin` 是唯一新增的一条，故取值偏保守；**若实测过难，先砍 `WinMargin` 再动回合数**。
- Practice 的 `WinMargin: 0` 使 `Draw` 在 Practice 档永不可达——干净的退化，呈现层需知晓。

**⑤ Practice 的对手 = 复用同一批 `EnemyData`，加一个作用域字段。**
- `EnemyData.EncounterScopes : EventType[]`（取值仅限 `{ Practice, Combat, Finale }`；**空 = 数据缺陷 → 加载期 `PushError`**）。同门师兄 → `[Practice]`；凶兽 → `[Combat]`；天劫 → `[Finale]`。
- **图鉴的正向增益（承重论据）**：共享池使玩家**能先在低风险的 Practice 里遇到并解锁某个敌人的图鉴，再在 Combat 里正式对上它**——这条教学路径正好补上「意图揭示退出教学职能」后留下的空缺。另立一批则图鉴要么翻倍、要么分裂成两套。
- 取池共三层，全部在 `AllEnabled()` 之后叠加：**① `EncounterScopes` · ② `PoolScope`（通用 / 地点专属 / 剧情线专属）· ③ 篇章框定**。`PoolScope` 为空 = 通用池，不报错。**这是剧情线表达差异化的唯一合法途径**（模板本身不可被调制）。

**⑥ enemies 升格为 `systems/enemies/`，与 `adventure-event` 平级。**
- 三个事件类型引用同一份内容，把共用类型挂在其中一个使用者名下违反归属直觉。**这不违反「内容并入系统、不单列内容层」**——本方案不建泛化内容层，而是承认 `Enemy` 已具备独立的「类」身份（模板 ↔ 实例二元 / 自己的 `.tres` 注册表 / 独立图鉴引用面 / 自己的赋级规则）。**并列的另两个二元中 `Card` 已住在 `character-profile/deck/`，Enemy 却寄居在 Combat 名下，是三者中唯一不对称的一个。**
- 五处引用方改为薄引用，**一次做完**（combat / practice / finale / future-event-service / enemy-codex）。

**⑦ 四个类型的完整字段。**
- **`TargetRef(TargetKind Kind, Side Side, string EntryId)`**，`TargetKind { None, Side, BattlefieldEntry, HandCard }`。**必须有 `None`**（`PlayCard` 每次都要传一个，`None` 使「无目标」成为已表达的取值而非 null 约定）。**`StackEntry` 不保留**——本作不做「反制栈上条目」，枚举里不留永无消费者的取值。
- **`CombatSnapshot`**（只读视图、不落存档）：`TurnIndex` / `TurnLimit` / `ActiveSide` / `Step` / 两个 `SideSnapshot` / `Battlefield` / `Stack` / `Intent?` / `PendingTargetRequest?`。
- **`SideSnapshot` 单类型**（不拆己方 / 对方），保住参战方对称模型：`ActorId` / `GlobalLevel` / `Momentum` / `MomentumDeltaThisTurn` / `CurrentMana` / `ManaLimit` / `HandCount` / `HandCardInstanceIds`（**敌方恒为空，不是 bug**）/ `DrawPileCount` / `DiscardPileCount` / `AmbushCount`（双向对称，只给计数）/ `UsableItemIds`。
- **道念字段结构 = 当前值 + 本回合增量，且明确不分来源**：08-02c 已定「意图不暴露张数与逐张分解」，若 snapshot 按来源拆分，UI 就能反推出敌人的逐张分解，**直接架空那条定案**。分来源的诉求由 `PlayResult`（事件流）承载。
- **`PlayResult`** 带 `MomentumDelta(Before, After, Declared, Actual)` 四字段——**「意图削减量 vs 实际削减量」由 `Declared` / `Actual` 一对承载**，二者之差 = 被下限 0 截断吞掉的量。放在 `PlayResult` 而非 snapshot：snapshot 是**状态视图**（现在是多少），`PlayResult` 是**事件视图**（这一次发生了什么），截断是每次结算发生的事件。
- **补上 API 缺口：新增 `PlayResult ProvideTarget(TargetRef target)`** —— 结算循环可挂起，但此前没有让玩家把目标交回去的方法。返回同一个 `PlayResult` 类型（它是**同一次出牌的续报**）；`AwaitingTarget` 可连续为 true。**不走 EventBus 回传**（广播是既成事实、不承载请求）。
- **`CombatSnapshot` 按变更广播 + 缓存**，不是每次访问现组装（否则 UI 每帧读会在热路径分配）；调用纪律 = 每回合 / 每次结算后组装一次。

### 五 · 数值进程与呈现

**① `experiencePoint` 阈值曲线：境界内递增 + 境界间重置量纲。**
- 阈值必须从**一章有多少个事件**倒推（估算 ch1 26–30 / ch2 28–34 / ch3 32–38 个事件，单事件均值 ≈ 1.3–1.5 分钟）。
- **境界间必须重置量纲**——理由不是美观，而是既定的「进阶即归位初期」：等级在境界边界重置，若阈值仍连续累加就出现「等级归零、阈值不归零」的语义割裂。跨境界的难度阶梯已由 `baseMomentum` 跨度**独占承载**，经验侧不叠第二条曲线。
- ch1 阈值：`threshold(L) = 4 + floor((L−1)/2)`（L = 1..11），**L = 12 特例取 10**（与 `baseMomentum` 表「第十三层跳到 15」的突破前台阶同构），合计 **79**。ch2 = 32 / 38 / 44（合计 114）；ch3 = 38 / 46 / 54（合计 138）。
- **给予量以「一次标准事件的成功产出」为基准**，`ExperienceGrade { None 0 / Minor 0.5× / Standard 1.0× / Major 1.5× }` 枚举 + 平衡表映射，**内容侧不落裸数字**。
- **阈值与给予量同比放大**（ch1 标准 4 / ch2 12 / ch3 16），与 `baseMomentum` 跨境界放大的数值语言同构，避免「ch3 要 34 个标准事件才升一级」的产出感稀释。
- **失败 = 同档的 50%**，向下取整、下限 1（给了就不能是 0，否则「挫折亦是修行」在数值上落空）。50% 而非更低的理由：失败**已经付了一笔硬代价**（`lifeTotal` 按道念差 1:1 扣、归 0 即角色终结），靠反复失败刷经验天然不是优势路线。
- **承重推论：经验的目标点不是「篇章结束」，而是「Finale 之前」。** 08-05 的天劫自洽性验证（`diff` 恰为 +1）隐含一条此前未被记下的硬约束——**角色必须在进入 Finale 之前就已升满本境界**，否则 `±2` 带会给出更低的天劫等级，「渡劫 = 突破到下一境界」的叙事随之破裂。连带得到 **Finale 的出现条件 = 角色已达本境界巅峰**（不需要新机制，`eventPriority` + `ifMandatory` 已能表达），且 **Finale 本身不承担经验供给**。
- 供给 / 需求 ≈ **1.15–1.20**；**满级后经验直接丢弃**，不结转、不开兑换通道；卡级（寿元耗尽而等级未满 → `defeated`）是**有意保留的失败面**，但要求 `lifeSpanCost` / `eventCountLimit` 的反推必须验证「按标准路线走能在预算内升满」。
- **单次给予量 ≤ 该境界的最小阈值**（`Major` 是唯一例外，仍 < 最小两级之和）——一次事件跳两级违背「产出可细碎而连续」这条定案，作为内容侧硬纪律 + 加载期断言。

**② 等级产出的频次与分布。**
- 经验模型下**不存在「升级型产出」这种离散条目**，只有「带 `ExperienceGrade ≠ None` 的 reward」。带经验的产出点约占事件总数 **75%**（全覆盖会让经验变成时间的自动函数；< 50% 则玩家只挑带经验的事件，压扁事件池多样性）。
- 档位偏置 = **「产出对位成本」的一致化**：Combat 胜利 `Major` · Practice 胜利 `Standard` · Finale `None`/`Minor` · Research `Major` · Explore `Standard`/`Minor` · Social `Minor` · Exchange `None`。它与 location 的事件类型概率修正自然咬合——**荒野多 Combat = 经验更密但风险更高，坊市多 Exchange = 经验稀疏但资源丰**，地域由此自带成长节奏的风味，**不需要为 location 再加一个经验修正字段**。
- **失败产出 = 一条 reward 两个字段，不是两套内容**：`ExperienceGrade` + `FailureRatio`（默认 0.5，逐条可覆写，留给「这场输了才真正学到东西」的特例）。折算在 `ProfileChangeSpec` 组装时完成。
- **承重推论：ch2 / ch3 的升级稀疏（9–11 个事件才升一级）是一个必须补偿的节奏缺口**，它与「中长期规划感的来源」那条长期待答在此合流。**补偿 = 经验条常驻**于 EventOption 选择界面的角色状态条（`当前 / 本级阈值`）——玩家读到「还差 12 点到筑基中期」，就有了跨越十来个事件的中期目标。与寿元隐藏纪律不冲突：**经验从未被定为隐藏属性**。
- **eventOption 卡片不标注经验产出档位**（与「给方向不给数字、不可电子表格化优化」的一贯纪律一致）。玩家看得到自己的进度、看不到单个事件的标价。若实测新手困惑，「标档位不给数字」是预留的退让位。

**③ 道具折价与战斗内法则的强度上沿。**
- 三重优势逐项估价：不受抽牌运 ×1.40（单张特定牌本场可用概率 ≈ 0.7）· 不占手牌位 ×1.10 · 使用时机确定 ×1.15 → 合计 ≈ ×1.77 → **等价折价 ≈ 0.57**。
- 但 **`Charges` 是反向修正**（次数越少，三重优势越不成立），故**折价按 `Charges` 分层而非单值**：

| `Charges` | `itemPowerRatio` |
|---|---|
| -1（无限法宝） | **0.55** |
| ≥ 5 | **0.65** |
| 2 – 4 | **0.75** |
| 1（一次性） | **0.90** |

  判据一句话：`道具的效果量 ≤ 同 ManaCost 法术的效果量 × itemPowerRatio(Charges)`。**这条分层让 monetization 的既定分工有了数字**——古宝（必有 `Charges`）落在 0.75–0.90，单次强度接近法术但总量被次数封死，兑现「付费收益 = 关键时刻多几次转圜而非永久变强」。单一常数 0.65 会把最该强的一次性古宝削到与无限法宝同价。
- **「不受抽牌运的溢价」写成公式而非常数**：`1 / P(本场见到该牌)`，`P` 由卡组规模与抽牌数算出，随二者调整自动跟随。
- **战斗内法则的强度上沿用「对一场道念的净贡献 / 本方 `baseMomentum`」作量纲**（`baseMomentum` 已是既定的战斗强度主刻度）：单条 **≤ 10%**；**老账号全开口径合计 ≤ 25%**（关键的第二道闸——法则不可被针对且跨轮回单调累积，没有总闸必然在老账号处失控，这正是「难度曲线按老账号全开校准」的可执行形态）；**不得随对局延长而累积**（「每回合 +X 道念」「按手牌数缩放的倍率」一律禁止——它们在 10 回合定长下是线性放大器）。
- 形态清单：✅ 信息类（探查）/ 便利类（重排手牌、查看牌堆顶）/ 容错类（有次数上限的兜底）；❌ 稳定产出类 / 倍率类。
- **接受「战斗内法则在 ch1 前段只能是纯信息 / 便利类、道念贡献为 0」**（`baseMomentum` 1–5 时 10% 不足 1 点）——新手期不该被账号级内容干扰。**这条必须明写**，否则内容侧会以为可以给一点点数值。
- 总闸不可机械校验，作为**内容评审口径**，与 `IgnoresProtection` 的 1% 同性质。

**④ 「1% 的游戏场景」的分母口径。**
> **分母 = 一次完整轮回（三篇章）中玩家进入并结算的战斗类遭遇总数**（Combat + Practice + Finale，按「进入」计不按胜负计）；**分子 = 其中至少发生过一次 `IgnoresProtection` 实际结算的遭遇数**。

- 「实际结算」而非「敌人持有」是关键：带该效果的敌人若本场没打出那张牌，不计入分子。
- 量级换算：一次轮回约 30–36 场战斗 → **1% ≈ 每 3 次完整轮回撞上 1 次**。**这个数字应当被写下来**，它比「1%」直观得多，且验证了「被拆是一个足够罕见、值得记住的事件」。
- 编排规则 R1–R5：**仅挂 boss 档载体**（Finale 天劫 + 精英 `EnemyData`，不挂常规敌人）· **每篇章至多 1 个载体条目**且出现概率由目标频次反推（不写死 3%）· **一次轮回内至多结算一次**（`CycleState` 上一个 bool，命中后本轮回其余载体权重置 0）· **绝不挂在玩家可主动获取的内容上**（1% 只能约束内容侧派发，管不了玩家构筑）· 保留加载时 `PushWarning` 逐条列举 + 一份编排侧人工核对表。
- **08-05 的「1% 不落代码」措辞微调为「1% 的分布归内容编排，仅一个轮回级布尔位落代码」**——一个 bool 的代价极小，而它是「平均 1%」与「体感 1%」之间的唯一桥。
- ⚠ 留给实测的复核提示（不是待答项）：1% ≈ 每 3 轮回一次可能比直觉更罕见；若上线后体感「几乎遇不到」，**调整方向是抬高目标频次（例如 5%），规则结构不变**。

**⑤ 储物袋 UI。**
- **不进主菜单**——主菜单入口全是 PlayerProfile 级，而储物袋持有的是 CharacterProfile 级、随轮回清理的东西。入口在**轮回内 EventOption 选择界面的角色状态条**上（与经验条、卡组入口同排）。
- 元进程面板 = **全屏 · 纵向滚动网格（4 列，平板 6 列）· 不分页**：分页在触控上多一次操作、且「第几页」对无位置语义的道具毫无意义。
- **筛选 = 顶部一排 chip**（全部 / 战斗可用 / 战斗外 / 已耗尽），全部基于既有字段（`UsableScene` / `Charges == 0`），**不新增字段**。排序默认「获得时间倒序」。
- **同 `Id` 道具可以持有多份**，格内堆叠显示 `×N`（这条同时补上 `item/_index.md` 的隐含空缺）。
- **不做拖拽整理 / 手动排序**（99 格手动排列是纯负担，道具无位置语义）；**长按查看详情**（触控等价物，禁 hover-only）。战斗外可用的可在此直接使用，战斗内可用的只能查看。
- **战斗内视图定名「随身」**（两字、省空间、有修真味、与「储物袋」明确区分）→ 进 `terminology.md`。形态 = **默认收起为角标**（贴己方战场区边缘，与法则条**分居两侧**——两者都是「己方的非手牌资源」，对称落位让玩家一次学会两处）→ **点按升起底部抽屉**（屏高约 40%，拇指可达区，移动端母语控件）→ **抽屉内横向滚动一行**（与 EventOption 选择区的横向滑动手势一致，复用同一套肌肉记忆）。
- **不可用项灰显 + 长按给原因**（mana 不足 / 非行动阶段 / 栈非空），**灰显即答案，不做点击弹提示**。使用后若需目标则**直接进入选目标态**（复用同一套形态）。敌人回合 / 结算中角标置灰、入口禁用——使用窗口是全局规则，UI 应把它表达为可供性的有无。
- 实现注意：99 项需虚拟化 / 复用，不能实例化 99 个节点。

**⑥ 选目标态的呈现形态。**
- **规则层（不只呈现层）：合法目标集合大小为 1 时自动选定，不进入选目标态、不产生决策点、不落存档。** 这条**一并缓解三个问题**（连锁打断次数 / 决策点密度 / 操作疲劳），削掉约一半进入次数，是本节最有价值的一条。（合法目标为 0 时按既定的效果落空规则处理，同样不进入。）
- 进入 = 全屏低透明度暗幕（≈45%）0.15 s 淡入，压暗一切非决策必需元素；**道念对比条与栈区豁免不压暗**（前者是判断该指谁的依据，后者是「队列里还剩什么」的唯一来源）。
- **来源指示**：栈上该条目上浮 + 放大 1.1× + 描边，一条引导线连向指令条——连锁中玩家必须知道「是谁在问」。**指令条位置绝对固定**（每次进入同一位置同一套视觉，节奏可预期 = 不迷失）。
- 合法目标不被压暗 + 描边呼吸动画；**非法目标点击无反馈**（压暗即答案，连锁中反复弹提示是噪音）。退出总时长 ≤ 0.4 s。
- **指向手势 = 单点即确认**，不用拖拽连线（拖拽要求精确起点与长路径，起点在屏幕中上部、终点可能在顶部或底部，竖屏单手跨不过去），**也不做二次确认**（连锁中每次操作都要乘以次数）。**误触不做保护**，与「玩家主动退出静默处理」的手感取向同向；B（点选 + 确认键）保留为实测退让位。
- **连锁进度文案取 `还有 N 项待结算`**（= 栈深，永远可算），不用 `还有 N 项待选`——后者要求预知后续条目是否需要目标，而那依赖前面的结算结果，未必可精确预知。
- **连续两次之间不完全淡出暗幕**（只交叉淡变来源高亮与文案）——避免全屏明暗闪烁，同时让「这是一段连续结算」在视觉上成立。
- **措辞与「响应窗口」严格区分**（三条禁令）：用「选择一个目标」「指定」，**不用**「是否响应 / 跳过 / pass」；**无取消键、无跳过键、无「不使用」**；**无倒计时、无超时自动选**（倒计时暗示「不选也会过去」，与「不可放弃」矛盾）。

**⑦ 快照与执行偏差的呈现。**
- **「预估」= `≈` 前置 + 数值下方短虚线底纹**（虚线提供不依赖颜色的第二重冗余）。括注「(预估)」与整体淡化均否决（后者与「不可用 / 已失效」的通用语义冲突）。首次出现完整意图档时给一条一次性教学提示。
- **逐步反馈 = 飘字为主 + 一条日志 ticker 为辅**，两者都要：飘字**注意力跟随对象**、不需要阅读；ticker 可回看。ticker 默认显示最近一行（隐藏在按钮后 = 玩家不会主动开 → 偏差解释形同虚设，08-04b 的硬要求落空），点按展开本回合完整日志。**一条 ticker 同时解决「栈与战场的连锁可读性」那条待答。**
- **偏差时的对照标记（最关键的一项）**：飘字 `≈12 → 8`（划掉预估值给出实际值）、ticker `预估 ≈12，实际 8（你的「明镜台」减免 4）`。**把偏差本身变成一次明确的说明，而不是让玩家自己对账**——光有「逐步可见」还不够，玩家还得能把那些步骤加总回意图数字。这是「偏差不做处理」这条定案能被玩家接受的实际前提。
- **节奏**：单个敌人回合演出 **≤ 4 s**（一场合计 ≤ 20 s，在 30–40 分钟篇章预算下不可超）· 单步节拍 0.35–0.5 s · 超过 4 步后压到 0.2 s 并**合并同来源同类型同符号的连续增量**（跨来源不合并）· 点按任意处 **3× 加速**（**只能加速不能跳过**，「逐步可见」是硬要求）· 永久快速演出为设置项 · **偏差对照那一步额外停 0.4 s 且加速无效**——偏差是唯一必须被看到的时刻。

**⑧ 意图区收起后的布局稳定性：固定预留高度 + 敌人回合复用为结算日志 ticker。**
- 先化解一处表面矛盾：**「不留占位」与「不能让邻居跳位」并不冲突，只要区分「占位符」与「预留高度」**——容器保留固定高度，内容整体清空，视觉上该区域是空的。工程形态 = `custom_minimum_size.y` 固定的 `Control`，收起时**子节点**淡出，**动画不触发 `Container` 重排**。
- **承重结论：把腾出的空间交给结算日志 ticker。** 玩家回合 = 意图区，敌人回合 = ticker。布局零变化、空间零浪费，且**语义连贯**——同一块区域始终回答「敌人在干什么」，玩家回合答「它**打算**做什么」，敌人回合答「它**正在**做什么」。**这不是两个功能挤在一起，是同一个信息槽的两个时态。**
- 这**明确修订** `ux/combat-ux.md` 中「意图区收起后不换成其他指示」那一句（按治理原则直接重写，不留考古）。
- 落位紧贴道念对比条（同属决策面板一组）；**尺寸 ≈ 屏高 8%**（初值，写成百分比 / `SizeFlags` 比例而非像素常量），单行横排 2–4 个类别符号，**永不换行**（换行会引起高度变化，与固定高度矛盾）。
- 动画：收起 0.15 s（淡出 + 上移 8 px）、展开 0.20 s（淡入 + `ease out back`），**无高度动画**——这正是固定预留的收益。展开比收起略长并带弹性：展开是信息到达（值得强调），收起是信息离场（应当不打扰）。
- 若实测排不下，**压缩顺序 = 先敌方区 → 再栈 / 战场（可做浮层）→ 意图区与道念对比条最后动**。
- **元素上移（回收空间）排除**：手牌区跳位会干扰拖拽出牌的肌肉记忆，已被明确点名为不可接受。

**⑨ 敌人图鉴的写作规格与实例信息。**

| 项 | 长度 | 口径 |
|---|---|---|
| ① 人物背景 | 2–3 句 / 40–80 字 | 他是谁、从哪来、为何在此。叙事性，可有情绪 |
| ② 功法简介 | 1–2 句 / 25–50 字 | 功法名 + 一句概括其路数 |
| ③ 运作方式 | 2–3 句 / 50–90 字 | 机制性但不带数字（「前期蓄势，越到后半越难缠」） |
| ④ 特点与弱点 | 2 句 / 30–60 字 | 一条特点 + **一条可行动的弱点** |
| ⑤ 关键卡牌 | **3 张**卡名 + 每张一句（≤ 20 字） | 见下 |

- **每项一段连续文本，不分行不用项目符号**；总长 **150–280 字**，一屏读完不需滚动。
- **三条口径纪律（承重）**：① **禁止出现任何具体数值**——「不含阿拉伯数字」是「图鉴不侵蚀越级黑箱」这句话**唯一可被审阅执行的形式**，作为内容评审的硬检查项（但它是形式检查不是语义检查，作者仍可用「大约十二点」绕过，不能替代人工评审）；② 禁止「本回合」类动态措辞；③ **④ 的弱点必须可行动**——玩家读完要知道该改什么打法，否则这一项是废话，也辜负了「死亡至少换来知识」的设计意图。
- **关键卡牌列 3 张，由 `EnemyData.KeyCardIds` 显式标注，不做自动挑选**：自动挑出的往往是最平庸的低费填充牌；关键卡是**叙事与教学的选择**，不是统计问题；词条挂模板且是静态的，自动挑选会随卡组改写而漂移。加载校验：id 必须在样本卡组内、数量 2–3、词条启用则不得为 0，违反皆 `PushError`。
- **实例信息分离为「静态正文 + 动态页眉」**：词条正文绝不写等级（同一模板会以 5 个不同等级出现）；**动态页眉只在战斗内查阅时出现**，只写本次遭遇实例的**境界名 + 层级**（如「本次遭遇：筑基后期」），**不写「高你 1 级」**——与「敌人等级标注不做方向标记」的裁决对齐，差几级由玩家自行比对。
- **战斗内可查阅**：点按敌人立绘 → 半屏 bottom sheet（与随身抽屉同一套控件语言）。**结算过程中 / 选目标态中禁用入口**（该态独占立绘的点按语义，这条点按优先级须在实现时明确）；不暂停战斗；只读。
- **解锁写入发生在战斗开始时，第一次遭遇本场即可读全部五项**：静态知识的价值本就不在藏起来，**越级的信息压迫由意图三档独占承载**，不该让图鉴再分担一份遮蔽；且「词条分级可见」会打破「一次遭遇全文案解锁」这条已定案。代价是试错记忆的仪式感被削弱，已知并接受。
- 写作规格是可观的文案成本：给一份**模板 + 两三个范例词条**放进内容制作流程，本方案的长度区间正是为此而设。
