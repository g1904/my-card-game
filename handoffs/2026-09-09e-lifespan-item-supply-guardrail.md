## Intent（distilled）

**一句话：** 储物袋取消容量上限后空掉的那道软闸，由**四条获取通道逐条给闸 + 三格内容编排口径（出现频率 / 库存深度 / 定价）+ 一条取池侧排除**补齐；同时把 λ 反推式里整格挂在事件侧的 `R_c` 拆成事件侧 / 道具侧两格书写口径，Σ 不变，21 格 `lifeSpanCost` 定价表一格不动。

### 1. 先把账分清 —— `R_c` 拆两格，Σ 不变

```
R_c = R_event,c + R_item,c          （Σ 不变 ⇒ λ 与 21 格定价表零改动）
```

| | ch1 | ch2 | ch3 |
|---|---|---|---|
| `R_c`（既定，不动） | 100 | 116 | 317 |
| `R_event,c` 事件侧 | 50 | 58 | 159 |
| `R_item,c` 道具侧 | 50 | 58 | 158 |

- **道具侧是事件侧的替代品，不是补充品。** 两者在玩家语言里是同一件事（「买回容错」），只是一个当场兑现、一个可以攒着 ⇒ 按替代关系分账、Σ 不变。
- **代价（已接受）：** 回寿事件由「每章 2 次小档」降为「每章 1 次小档」，在事件流中相当罕见。
- 两格都是**书写口径**（标定台账），不进 `.tres`、不进任何 `Resource`，与 `t(type)` 耗时台账同档。
- **`R_item,c` 的唯一来源是商店购入** —— 池抽产出被 L-0 关闭，事件产出并入 `R_event,c` 同一本账，开局三选一被 L-0 的索引一并排除。

### 2. 四条获取通道，逐条给闸

| # | 通道 | 量级 | 闸 |
|---|---|---|---|
| ① | 开局强制事件的法宝三选一 | ≤ 1 次 / 轮回 | **L-0 排除**（免费通道，无定价闸） |
| ② | Exchange 商店库存 | ≈ 10 / 10 / 12 次 Exchange | 三格口径的主战场（有定价闸） |
| ③ | 事件产出（`AbilityElements` 的 `Grant`） | 由编排决定 | 并入 `R_event,c` 一本账 |
| ④ | 战后奖励池 | ≈ 4–5 次奖励面板 / 章 × 3 项候选 | **L-0 排除**（免费通道，无定价闸） |

**L-0：含 `(CostKey.LifeSpan, BaseValue > 0)` 产出的 `ItemData` 不进战后奖励池，也不进开局强制事件的法宝三选一池。** 加载期反建一份索引、两处取池点共用，形态照「成员卡不从散牌产出侧发放」——**不新增字段、不落存档、不加任何计数器**。

四条依据：
1. **定价这一格在免费通道上整条失效** —— 三格护栏里唯一的硬闸是货币。
2. **量级差** —— 免费候选位的次数正比于挂了 `RewardPoolId` 的战斗场数，与商店侧带价曝光（≈ 1.2 次 / 章）差一个量级；一个池占比旋钮同时满足两条通道必然一头松一头紧。开局三选一虽只 1 次 / 轮回，但**单次给量**（大档 = 200 点）是 ch1 道具侧整章预算（50 点）的 4 倍 ⇒ 「一轮回至多一件」只封住次数、没封住量级，而寿元护栏要封的是量。
3. **抵消回路** —— 免费掉丹让「打输一场」的代价被「打赢下一场」直接抵消，与 Travel 禁令「换图的代价不得被同一事件抵消」逐字同构。
4. **形态零新概念** —— 按族排除已有既成实例（`Practice` 档整族排除 `PowerData`）。

**代价（已接受）：** 内容侧编排不出「打赢一场硬仗掉一颗补天丹」这一风味；开局三选一从此不出补天丹（一颗满血时用不掉的丹本就是三选一里的坏选项）。回寿法宝只能靠买与靠事件给。

### 3. 三格编排口径（落 `/audit-content` 汇总，只报告不阻断）

| 编号 | 口径 | 首批等价形态 |
|---|---|---|
| **L-1** 出现频率 | 含 `(CostKey.LifeSpan, BaseValue > 0)` 产出的 `ItemData(Scope == Character)`，在**每一个抽取池的每一个 `RarityTier` 档内**占该池该档 `Scope == Character` 条目数的比例 ≤ 6% | 每池每档至多 1 条 |
| **L-2** 库存深度 | 单个 Exchange 条目内 `CharacterItem` 族的 Σ`SlotCount` ≤ 3；不为回寿法宝单设 stock rule、也不用 `RarityFilter` 给它开专属编排位 | 同左 |
| **L-3** 定价 | 回寿档 ↔ `RarityTier` 一一绑定，定价直读「族 × 稀有度」表，不填 `PriceOffset` | 40 / 80 / 160 灵石 |

- **L-1 逐池逐档，不按整池核算** —— 商店库存与战后奖励池均按篇章分池后，分母是**该池**该档的条目数；理由与 Exchange 闸 ①「逐 `Kind` 逐 `RarityTier` 档位」同一条：整池够而某档扎堆同样失控，而抽取恰是在档内进行的。
- **「同一家店至多一件同 `Id` 回寿法宝」免费成立**（`PickMany` 无放回）；不同 `Id` 两件同店在 6% 口径下 ≈ 1.2%，量级可忽略，不为它加规则。

### 4. 三档绑定与条目形态

| 回寿档 | 绝对回寿量 | `RarityTier` | 定价（`CharacterItem` 行 · 恒灵石） | 单位价 |
|---|---|---|---|---|
| 小 | 50 | Tier2 | 40 灵石 | 0.80 灵石 / 点 |
| 中 | 100 | Tier3 | 80 灵石 | 0.80 灵石 / 点 |
| 大 | 200 | Tier4 | 160 灵石 | 0.80 灵石 / 点 |

- 回寿量三档（50 / 100 / 200）与 `CharacterItem` 行基价（20 / 40 / 80 / 160 / 320）**同为 ×2 递进** ⇒ 绑定后单位价恒定，玩家在三档之间读不出套利。Tier1（碎到没有决策感）与 Tier5（单件吃掉 ch1 全章灵石收入的 2.5 倍）留空不编排。
- **绝对点数三章通用、不按篇章分条目** —— 道具是跨篇章持有物，`OutOfCombatUseOutcome.Elements` 的 `BaseValue` 是定值、读不到当前篇章，「占本章预算百分比」这个书写口径在道具侧结构上用不了。
- **`Charges = 1`（一次性）** —— 四条依据：次数补充机制未设计（`ItemChargeElement.Delta > 0` 是 `PushError`）· `Charges > 1` 会把价格闸按次数稀释（单位价从 0.80 掉到 0.27）· 一颗 = 一档回寿是最可读的映射，数量由储物袋 `×N` 堆叠承载 · `Charges == -1` 已被 `I-12` 挡死。

### 5. 收支回代与两条结构性推论

```
R_item,c = 期望遇到次数 × 该章典型档位点数 × 购买转化率（≈ 0.7 ⚠ 无实测）
期望遇到次数 = Exchange 事件数 × P(某店至少含一件回寿法宝)
P = 1 − (1 − 0.06)² ≈ 11.6%
```

| | ch1 | ch2 | ch3 |
|---|---|---|---|
| Exchange 事件数 | 10.0 | 10.0 | 11.9 |
| 期望遇到次数（按每店 ≈2 槽 · 档内占比 6%） | 1.16 | 1.16 | 1.38 |
| 典型档位点数 | ⚠ 见下 | ⚠ 见下 | ⚠ 见下 |

**⚠ 「典型档位点数」一列的机制前提在本批内被改写，回代待补一轮校准。** 草稿写的 ≈ 50 / 70 / 150 建立在「商店库存池按篇章分档幅（ch1 主要遇 Tier1–2、ch3 遇 Tier3–4）」之上；本批裁定**每个池五档全非空、稀有度分布完全由权重表给出**（商店侧取「`Solid` 表 × 本篇章位移 `m(c)`」），档幅上下界这个表达手段被取消。以三档回寿丹各占 Tier2 / Tier3 / Tier4 一条、条件概率正比于该档权重反解，典型档位点数收敛为 ≈ 87 / 92 / 99（三章趋平），`R_item,c` 随之低于 50 / 58 / 158 的分账目标，ch3 缺口最大。

- **分账目标（50 / 58 / 158）不因此变动**——它是 `R_c` 拆格的结果，λ 与 21 格定价表仍零改动。
- **收口方向是三个内容侧旋钮，不是改结构**：提高 L-1 的档内占比上限、在高档位多编排一条回寿条目、或下调道具侧的分账目标。三者都落在内容编排面，与「护栏落在编排层、规则层不设限」一致。
- 回代里的两个输入（购买转化率 0.7 · 每店约 2 槽）本就无实测，故这条缺口的绝对量级同样是软的；它与三档绝对点数归同一次实测校准。

- **囤积自然贬值** —— 一颗 50 点的丹在 ch1 值本章预算的 5%，攒到 ch3 只值 1.6%。「囤到 ch3 一次性解围」被算术自动削弱，不需要任何新规则，正好接住「储物袋不设容量上限」留下的口子。
- **价格闸随篇章自动松开（代价，须明写）** —— 定价表不设篇章维而 `I(c)` ≈ 127 / 300 / 480 ⇒ 40 灵石在 ch1 是本章收入的 31%、在 ch3 只有 8%。**定价这一格只在 ch1 是有效闸**；ch2 / ch3 由出现频率与库存深度承接。

### 6. 零增量的面

存档 schema 零改动（不新增字段 / 枚举成员、不 bump `schemaVersion`）· 后端零配合 · 不引入计数器 / 篇章配额 / 轮回内次数上限（与 `ADR-0066` 否决硬上限、`IgnoresProtection` 的同向先例一致）。

## Clarifications（interview 产物）

- **道具侧回寿的预算是从 `R_c` 分账还是另加？** → **分账，Σ 不变**（选项 A）。λ 与 21 格 `lifeSpanCost` 定价表零改动；接受回寿事件降为每章 1 次小档。推翻草稿此前把 `R_c` 整格挂事件侧的写法。
- **是否采纳 L-0（战后奖励池排除含 `LifeSpan` 产出的道具）？** → **采纳**（选项 A），落成取池侧排除。
- **开局强制事件的法宝三选一是否也套用 L-0 的排除索引？** → **同样排除**（Q7）。这**推翻**了草稿「通道 ① 有天然硬上限、不需要闸」的判断：硬上限只封次数不封量级，一次免费大档丹 = ch1 道具侧整章预算的 4 倍。复用同一份加载期索引，零额外结构；代价是开局三选一不再出补天丹。
- **`ADR-0066` 的「三道软闸 + 一条结构性禁令」这句是否随之改？** → **删掉计数词「一条」**（直读裁定 DR-3）。补「后果」一行后，决策句说「一条」、后果说「两条」会自相矛盾；禁令的逐条清单本就由该 ADR 推给 `systems/adventure-event/common-properties.md` 持有，ADR 侧持有计数即造第二权威。**决定本体不改。**
- **稀有度分布是否按篇章分池？** → **按篇章分池**（连带裁决 X-1），商店库存同样分池。⇒ 收支回代的「典型档位点数」一列被机械保证，`R_item,c` 与 L-1 的 6% 口径维持原值；草稿 `## 前置依赖` 第 ① 条关闭。
- **「每档都有可能」的适用面？** → **三处产出一律五档可达**（Q6）。⇒ `RarityFilter` 不再用于卡掉整档，L-2 的措辞相应改为「不用 `RarityFilter` 给回寿法宝开专属编排位」，不再暗示可以按档卡池。
- **L-1 的分母口径** → 按 X-1 机械对齐为「逐**池**逐档」（原写「全库逐档」）；首批等价形态「每档至多 1 条」不变。
- **`R_item,c` 的「来源」一格** → 由「商店购入 + 池抽产出」收窄为「**商店购入**」；L-0 已把池抽归零，事件产出并入 `R_event,c`。数值一格不动。
- **「一章约 33 个免费候选位」这个数** → **不成立且不写进任何活文档**。战后奖励面板不是每场都开（`RewardPoolId` 可空），改写为「≈ 4–5 次奖励面板 / 章 × 3 项候选」，具体数字回链战斗侧的挂池占比口径，不在本案复写第二份。L-0 的四条依据逐条复核后结论不变。
- **Exchange 事件数** → 按权重 0.32 × 管线事件数校正为 ≈ 10.0 / 10.0 / 11.9（原写 10 / 10.4 / 12.4），`R_item,3` 随之 ≈ 145（偏差 −8%，仍在 ±20% 内）。
- **首批 3 条回寿法宝的字段取值表** → 属条目层，本次**不落 `content/`**（`item` 类型尚未开张）。类型级口径（三档绑定 + `Charges = 1`）落 `systems/character-profile/item/_index.md`；条目本体待 `/scaffold-content-type character-item` → `/author-content` × 3。

## Open questions

- **回寿量三档的绝对点数**（50 / 100 / 200 仍是折算初值），归内容扩充后的统计校准。它被实测改写时，L-3 的定价绑定按同一条 ×2 对齐关系自动跟随——改的是数，不是形状。
- **购买转化率 0.7 与「`CharacterItem` 族每店约 2 槽」**两个输入无实测，与败率 20% / `E[道念差]` 同款处置：写下来是为了让三格可复算，不得引为任何设计的承重依据。
- **道具的种类目录本身**（L-1 占比的分母）。首批「每池每档至多 1 条」这一等价形态不依赖它，可先落。
- **道具侧回代的收口（本批新生）。** 五档全非空 + 权重表给稀有度分布之后，商店侧的典型档位点数三章趋平，`R_item,c` 低于分账目标（ch3 缺口最大）。三个内容侧旋钮（L-1 占比上限 / 高档位多编排一条 / 下调道具侧分账目标）择一收口，待一次裁决；在此之前 `balance.md` 的回代表只写公式与口径，数值格标 ⚠。
- **其余道具族的三格口径**（哪些事件给、给几件、商店库存里各族的深度、置换对价）——本次只答定回寿法宝这一族。
