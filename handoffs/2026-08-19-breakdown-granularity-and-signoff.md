## Intent（distilled）

> **一句话：** `derive → breakdown → blueprint → implement` 这条链上，`breakdown` 一环的**签核语义**与**拆解粒度**此前只有经验、没有判据；本次把两者都落成可机械判定的条文，权威在 `requirements/_index.md`，技能侧只留一句祈使 + 回链。

### 起点：两处「按实现落下来、从未被确认」的形态

**① 签核语义。** 父 FR 有 `draft → ready` 的人工签核门，拆出的子需求直接继承父状态。继承在主干上是成立的——拆解**不新增**验收标准（充实 vs 臆造门），且覆盖核对强制每条父标准都被映射，故签核的实质对象（验收标准集合）在拆解前后同一，逐个签核等于把同一批标准签第二遍。

但继承漏了三样父 FR 里不存在、只在拆解时产生的东西：**切分本身**（切成几片、边界画在哪）、**`depends-on` 依赖链**（含跨库依赖，可能指向尚不存在的 id）、**被隔离出来的未决部分**（切分启发式要求把带 Open questions 的部分单独成条）。第三样是实打实的裂缝：父 FR 模板规定「`## Open questions` 非空 ⇒ 不是 `ready`」，而这类子需求继承出来却是 `ready`，进 `/blueprint` 时又被当作未签核拦下——**状态词与下游行为不一致**。

**② 粒度判据。** 原判据三句里只有「1~5 条验收标准」可数；「一次 `/blueprint` 能一口吃下」没有量纲，「能在编辑器里跑出来」对纯数据资源型子需求是否成立没有回答。结果是每次拆解的粒度取决于当次执行者的手感，而拆解产物是 `/blueprint` 的直接输入，粒度失控会一路传导到实现。

### 结论一：继承 + 一条 Open-questions 例外闸

> 子需求的签核状态继承父 FR 的签核状态；**唯一例外——`## Open questions` 非空的子需求一律产出为 `draft`**。

这不是新规则，而是父 FR 模板已有的同一条规则**原样下沉一层**。它可机械判定（看一个小节空不空），签核负担只落在真正未决的少数条目上，并顺带消掉上面那处状态词与下游行为的不一致。

**判定对象是「签核状态」，不是 `status` 字面值。** 父 FR 拆解后 `status` 即变为 `broken-down`，而增量拆解（往既有拆解文件夹里补新子需求）是技能明写支持的路径——按字面值判定时三条规则一条都不匹配，新补的子需求无规则可依。故：**`broken-down` 只由 `ready` 或 `draft` 迁入，父 FR frontmatter 用一格 `signed-off-as` 记住迁入前的签核状态**，规则读它而非读 `status`。

**切分与依赖链不新增状态词。** 它们是工程判断而非需求内容，评审入口已经现成：拆解文件夹的 `_index.md` 就装着子需求一览、覆盖映射表与构建顺序。把它明确为**拆解结构的评审面**（技能报告里点名请用户过一眼）即可。为一件已有评审面的事新增状态词，会让 FR 状态机变长、台账多一列，而它带来的信息全部已在 `_index.md` 里可见。

### 结论二：一张可数的软上下界判据卡，超界须写理由

把「一口吃下」换成可数指标，分**软上界**（超过任一 ⇒ 应再切）与**软下界**（触发 ⇒ 应并入兄弟子需求），并附一条机械处理：**超界 / 触发下界都不禁止，但必须在拆解 `_index.md` 里写一行理由，否则再切 / 再并**。软界的价值在于强制显式辩护；硬性拒绝会在真有不可分的切片时把技能逼进死角，逼出「为过闸而人为切碎」的假子需求。

指标选取的理由逐条：改动文件数是「一口吃下」唯一有量纲的代理（`/blueprint` 要逐文件列出、对每一次查找 / 加载给 null 校验计划）；涉及的服务数——七服务是本作唯一稳定的职责切面，碰两个服务通常意味着它其实是两条通路；新引入 EventBus 信号数——信号是跨系统契约面，一次只引入一条蓝图才能把负载定死；存档 schema 迁移点——迁移牵动原子写入与版本化，是承重且易错的一点；验证前置操作步数——验证靠人在编辑器里游玩，步数过多说明这片太靠链路末端。

**软下界取析取而非合取。** 「可观察验收标准 < 1 条」与「在编辑器中无可观察结果」两条中任一成立即触发；改动文件数与「完成后项目仍可运行」降为辅助信号。合取会让一个改三个文件、却零可观察产出的横向层子需求漏网——而那恰是切分启发式第一条要挡的东西。

**阈值是推导出的初值，本库零实证。** 按数据资源里的平衡数值同等对待：先给初值 + 留旋钮位置，在前三次 `breakdown → blueprint → implement` 完整跑通后回看一次改动文件数与验证前置步数的实际值。

### 结论三：纯数据资源型子需求允许独立成条，但须过三条闸

**明确回答：允许。** 现行技能的启发式只举了正例、不是判据，执行者无从知道自己手上这片算不算。升格为三条同时成立的闸：定义 `XxxData : Resource` 并至少一个真实（非空壳）`.tres` 条目 ∧ 该条目经 DataRegistry 在启动期加载并能按 `Id` 被查到 ∧ 至少一条负向验收标准（故意坏 id / 缺必填字段 ⇒ 启动期 `GD.PushError` 报出 id 与路径）。缺任一条 ⇒ 并入消费它的那个子需求。

**这层区分必须写明，否则会被读成「数据层可以横着切」：** 过闸的数据型子需求之所以不违反「按可观察行为切」，是因为**启动期校验报错本身就是一种可观察行为**（开发者在编辑器输出里看得见）；而不过闸的「把所有数据类建好」正是那条启发式要挡的东西。

### 结论四：判据的归属 —— 阈值与准入闸归设计库，切法与顺序归技能

粒度判据讲的是**流水线工艺**。ADR-0005 的冲突裁决表把「流程」已经列在设计性内容一侧，故判给设计库按现有条文即成立；缺的只是判据列的措辞（「讲游戏是什么」）不覆盖流水线工艺。本次把归属判据补进 ADR-0005：**判据 = 用户的评审面在哪一侧**。

同一条判据也划出了技能与设计库的分界：**阈值与准入闸（可数、是评审面）→ 设计库；切法与顺序（工程手法）→ 技能**。用户会评审「这片是不是太大」，不会评审「先切骨架还是先切数据」。据此，粒度判据表与纯数据三条闸迁进 `requirements/_index.md`，其余切分启发式留在技能内。

**不为 `.claude` 开任何具名例外。** ADR-0005 的硬边界禁止技能文本出现表格 / 具体阈值 / ≥3 步编号流程，阈值表因此不进技能；技能第 4 步压成一句祈使 + 回链。技能第 2 步本来就把 `requirements/_index.md` 列为第一份必读，判据移出不增加读取成本。

### 结论五：两库对称落笔

粒度判据须两库通用，但后端库没有文件边界（技术栈未定）、没有 EventBus、没有 Godot，客户端那几个指标直接搬过去是空的。**两库各写各的指标，形态同构、内容不复述、互相回链**——客户端 `requirements/_index.md` 只写客户端指标，后端 `requirements/_index.md` 落一份同构的后端指标（触及端点 / 主写持久化对象 / 契约字段组 / 存储 schema 迁移，加上一条后端专有的不可切约束：`## Failure & retry semantics` 必须在同一子需求内完整）。把后端指标写进客户端表即是两库台账合并，制造第二权威且无机制发现漂移。

后端侧的落笔见 `backend-design-documents/handoffs/2026-08-19-breakdown-granularity-and-signoff.md`。

## Clarifications

本次由合并 interview 裁决、并推翻或细化了原始草稿的各项：

- **后端等价指标写在客户端表里，还是两库对称落笔？** → **两库对称落笔**：客户端 `requirements/_index.md` 只写客户端指标，同一次运行在后端库落一份同构判据，互相回链、绝不复述对方内容。**推翻**草稿「具体形态」两张表中的「后端上界」列，并落实草稿 `## 后果` 末条自己写下的「这一半的落笔归后端库」——但不推迟到下一次运行。
- **签核状态规则表对「父 FR = `broken-down`」的增量拆解无对应行。** → 规则的**判定对象改为「签核状态」而非 `status` 字面值**；配套：`broken-down` 只由 `ready` 或 `draft` 迁入，父 FR frontmatter 保留一格记住迁入前的签核状态。**细化**草稿「签核状态规则（子需求）」代码块的三行条件。
- **切分启发式 6 条是否随粒度判据一并迁出技能？** → 只迁「粒度判据 + 启发式第 2 条」，其余留技能；并补写分界判据「阈值与准入闸 → 设计库；切法与顺序 → 技能」。**补全**草稿未回答的部分。
- **归属判据写进 ADR-0005 还是只写 `requirements/_index.md`？** → **写进 ADR-0005**（用户明确授权本次改写 `decisions/`），`requirements/_index.md` 以一句回链承接。同时**订正**草稿的描述：ADR-0005 冲突裁决表第一行原文已把「流程」列在设计库侧，故这是**判据列的措辞补充**，不是草稿所称的「对分类表的外延扩展」。
- **U3「跨服务边界数 ≤ 1」的计数口径。** → 读作「**涉及的服务数 ≤ 1**」，指标名改为「涉及的服务数」消歧。**推翻**草稿该格括号后半句「跨 2 个以上按服务再切」的读法（同一格里两种口径互相打架）。
- **软下界的合取条件与豁免机制。** → 改为 **`L1 ∨ L2` 成立 ⇒ 应并入，`L3` / `L4` 降为辅助信号**；并入的豁免与上界对称（写一行理由）。**推翻**草稿的「全部成立 ⇒ 应并入」，属对已定案阈值卡的结构性调整，用户知情后批准。
- **U6「验证前置操作步数」的起算点未定义。** → **从该子需求所属系统的首个可交互屏起算**，不计全局启动链路。**补全**草稿未定义处；不动阈值本身。
- **落点表遗漏 `requirements/_TEMPLATE-sub.md`。** → 同批更新该模板两处（`status` 注释补例外闸；`## Open questions` 注释口径对齐）。**补全**草稿落点表。
- **技能第 7 步「已知边界 · 签核语义」删除还是改写为回链？** → **改写为一句回链**，不删除——例外闸是新加且反直觉（父 `ready` 却产出 `draft`），删净后执行者会按旧习惯一律产出 `ready`。**定下**草稿的二选一。
