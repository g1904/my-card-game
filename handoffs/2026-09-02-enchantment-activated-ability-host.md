# 阵法（Enchantment）上启动式异能的 UI 宿主

## Intent（distilled）

`ActivateAbility(entryId, abilityId, targets)` 的服务契约按**战场条目 id** 寻址，与 UI 宿主无关；灰态预判 `BattlefieldEntryView.ActivatableAbilities` 逐条目填充、只对 `ViewerSide` 己方条目非空。呈现侧此前只定了 `Power` 那一半（图标条 → 长按弹层 → 弹层内的启动键），**阵法条目在战场区内没有对应的启动入口** —— 没有宿主就没有玩家可发起的路径，服务算好的那格在阵法上永无消费者，一整类「留场 + 每回合花 mana 启动」的内容在客户端写不出来。

本次只补这条功能性缺口：宿主落点、发起手势、可用 / 不可用 / 配额耗尽的表达、需目标时的衔接、禁用窗口。**不重排战斗屏分区、不为它规定屏面积配额** —— 那归竖屏分区专场。

### 1. 宿主 = 己方战场区里的那个阵法条目本身，不新开任何区

理由三条，全部由既有设计直接推出：

1. 服务按 `entryId` 寻址、`ActivatableAbilities` 逐条目填充 ⇒ **数据本就是逐条目的**，宿主与它同构时零映射成本；另立集中入口等于在 UI 侧再建一份「异能 → 载体条目」的对应关系。
2. `Power` 的宿主就是它在战场上的呈现物（图标条）。二者同为战场条目、同一条 API，阵法另找宿主会让同一个动作有两条心智路径。
3. **零新增区、零新增常驻部件** —— 这是本方案不与竖屏分区取舍冲突的唯一形态。

**明确不做**：不单开「启动式异能条」；不把阵法的启动入口并进随身抽屉（随身是按 `UsableScene` 筛出的**道具**视图，阵法不是道具，`Use` 与 `Activate` 在契约面已是两条路径）。

### 2. 交互链 = 长按条目升起 bottom sheet →「详情 + 启动」合一

与 `Power` 那一半逐字同构：**详情与启动键合一，同一对象上不并存两种手势**。

```
战场区的阵法条目
  └─（长按）→ bottom sheet 弹层
        ├─ 详情区：卡名 · 规则文字 · 关键字名（长按展开 ReminderText）· 插画
        └─ 启动区：该条目上每条启动式异能一行
              [异能名]  [ManaCost]  [剩余 N 次]   〔启动〕
```

- 弹层复用既有 bottom sheet 控件语言，不另造控件（先例：随身抽屉、手牌详情页、战斗前确认页的功法词条）。
- 详情区的内容清单与排布沿用卡牌详情页那一份，本次不裁定（归专场）；本条只定「启动区是该弹层里多出来的一节」。
- **启动键必须放进弹层，不能直接挂在战场条目上**：竖屏战场条目尺寸小，塞不下满足最小触控目标尺寸的按钮；而启动扣 mana、占掉行动阶段的一个动作位、不可撤销、不做二次确认，弹层这一步正是唯一的误触门槛。

### 3. 启动区逐行映射 `AbilityAvailability`，呈现层不重演规则

| 行内元素 | 数据源 | 呈现 |
|---|---|---|
| 异能名 | `AbilityId` 解析出的 `AbilityData` 显示名 | `LocalizedText` |
| 费用 | `ManaCost` | 与手牌卡面 `manaCost` 同一套 mana 符号 |
| 剩余次数 | `RemainingUses` | `-1` 时整格不渲染；`>= 0` 时显示剩余次数 |
| 启动键 | `CanActivate` | `false` → 灰态；长按灰态启动键给不可启动原因 |
| 原因文案 | `Reason` | `COMBAT_` 分区普通键，不弹 toast |

- 启动区是**逐行列表**而非单键：`ActivatableAbilities` 本就是列表，且本场配额语义为「每载体条目、每场」，同一条异能挂两个条目即两份独立计数，故一个条目挂多条启动式异能是常态。行数极少，弹层内不需要滚动分页。
- `Accepted == false` 时 UI 只回到原态（弹层保持打开、不关闭、不提示）—— 与选目标态「不做『点非法目标弹提示』」同一条纪律。
- 启动键动词用「启动」不用「使用」：`Use` 已被道具占用，两条来源路径在契约面已分开，UI 措辞跟着分。

### 4. 可发现性 = 战场条目上的静态启动可供性标记，与 `Power` 侧共用同一套

阵法侧复用 `Power` 那个静态启动可供性标记，**不另设第二套** —— 两者是同一条 API 的两个载体，标记分叉会让玩家学两遍。标记带两态，数据源均在 `ActivatableAbilities` 内、呈现层不重演规则：

- 常态 =「此条目有启动式异能」（列表非空）；
- 强调态 =「此刻至少有一条可启动」（任一 `CanActivate`）。

只给常态时玩家每回合都得逐个长按去查「现在够不够 mana」，而这份判断服务已经算好；显示出来是零额外规则成本的信息。**具体形状归竖屏分区专场**（它要占己方战场区边缘那圈已经很挤的空间），且该项同时约束 `Power` 侧，两者并案处理。

### 5. 需目标的启动：弹层先收起，直接进入既有选目标态

1. 点启动键 → **弹层收起**（半屏面板会压住栈区与合法目标，而「栈区保持可见且不被压暗」「合法目标不被压暗」是承重）；
2. 该异能的目标槽位总数 > 0 → 按 `slotIndex` 顺序逐个问、**一次收齐**（玩家主动发起的动作，槽位在发起前收齐），指令条按同一顺序点名各槽位类别；
3. 收齐后调用 `ActivateAbility`。

合法目标集合大小为 1 时自动选定、不进入该态。来源指示由该阵法条目的上浮 + 放大 + 描边承担，与栈条目发起时同一套视觉，不新增部件。这一段与结算中途的挂起式目标询问呈现形态相同、来源不同，玩家不需要区分。

### 6. 己方面朝下条目（埋伏）照常有启动入口；对手侧不渲染

`faceDown` 的语义是对**对手**隐藏内容，而 `ActivatableAbilities` 只对己方条目填充。故己方战场区照常呈现自己的面朝下条目，其启动入口与明置阵法完全同形；不给己方埋伏宿主，服务在这一格算出的可启动性将永无消费者。对手侧的面朝下条目不渲染任何条目级入口或标记，只汇总进计数指示。

**边界**：己方埋伏在战场区是逐条渲染还是折叠成一格，归竖屏分区专场；本次只定「无论何种形状，它必须有启动入口」。

### 7. 敌方阵法不渲染任何启动可供性

对侧 `ActivatableAbilities` 恒为空列表，敌人启动走 EnemyManager 内部路径、不经本 API。UI 不为对侧条目渲染标记、不渲染启动区 —— 既无消费者，又是一条信息泄漏面（与手牌 id / 可用道具 id 同一条填充纪律）。敌方启动的可观测性由飘字与战报承担。

### 8. 入口的禁用规格与 `Power` 弹层 / 随身抽屉完全同规格

**敌人回合 / 结算中 / 选目标态：条目上的启动可供性标记置灰、详情弹层入口整体禁用。** 判据是既有那条「禁用与否看的是是否与决策面争抢屏幕或语义」—— 启动键争**语义**，半屏弹层争**屏幕**（压住栈区与合法目标），两种争抢都成立，故不为阵法另立一套规格；**弹层是否只读，不影响该判定**。

选目标态下战场条目的点按 = 指定目标（该态已定「单点即确认」），且该态一并禁用详情入口。

**代价（明写接受，非待修副作用）**：敌人回合与结算中无法查阅战场阵法的规则文字。这段的可读性由飘字与战报因果树承担 —— 战报展开态在结算态可开、只在选目标态禁用，故结算中仍有「刚刚发生了什么」的通道。

### 9. 契约面 / 存档面

**零服务契约改动、零 schema 改动、零存档迁移。** 本方案完全消费既有契约面（`ActivatableAbilities` 与 `AbilityAvailability` 五格、`ActivateAbility` 签名、`ActionResult` / `ActionRejection`、`CombatSnapshot` 按变更广播）。新增的只有呈现层部件：启动可供性标记（两态）· 弹层内的启动区一节 · `COMBAT_` 分区的拒绝原因文案键（由 `ActionRejection` 成员机械映射，不占 `ERR_` 前缀）· 启动键与「启动」动词的文案键。**不新增**：区、常驻挂件、手势、控件类型、服务方法、存档字段。

## Clarifications（interview 产物）

- **发起详情弹层的手势：长按还是点按？** → **长按战场条目升起弹层**（2026-09-02 评审裁决）。「详情入口的手势按『对象是否可拖拽』分化」这条判据一字不改；`Power` 侧与阵法保持同一套手势 —— 不得只改一半。草稿原文把这一项列为待决，本次取其选项 A。

- **详情弹层在敌人回合 / 结算中能否打开为纯只读？** → **不能：三态一律禁用整个弹层入口，阵法与 `Power` 弹层、随身抽屉完全同规格。** 本项推翻草稿子项 8 的末条「详情本身照常可看，只禁用启动区那一节」，该句不写入任何文档。禁用理由是**半屏弹层争屏幕**，与内容是否只读无关；「纯只读不是豁免理由」这条判据的辖域不变。被接受的代价：敌人回合与结算中无法查阅战场阵法的规则文字（见上方子项 8）。

以下按标准默认直接采纳，不占待答清单：

- 宿主 = 战场区该阵法条目自身 → 依据服务按 `entryId` 寻址、`Power` 宿主先例、零新增区。
- 启动键落在弹层内而非条目上 → 依据最小触控目标尺寸与「不做二次确认」的既有手感取向。
- 启动区逐行映射 `AbilityAvailability`、`RemainingUses == -1` 整格不渲染 → 依据服务已算好灰态、不显示空槽的通行做法。
- `Accepted == false` 只回原态、拒绝文案走 `COMBAT_` 分区不占 `ERR_` → 依据既有的不弹 toast 纪律与 `ERR_` 前缀的机械来源。
- 动词取「启动」 → 依据 `Use` 已被道具占用。
- 可供性标记两态、与 `Power` 共用一套、形状归专场 → 依据同一条 API 两个载体不应分叉；单态是现成退让位。
- 需目标时弹层收起 → 按 `slotIndex` 一次收齐 → 依据「主动发起的动作槽位在发起前收齐」与「栈区 / 合法目标不被压暗」。
- 己方埋伏有启动入口、对侧不渲染 → 依据 `faceDown` 只对对手隐藏 + `ActivatableAbilities` 只对己方填充。
- 启动占行动阶段一个动作位、不可撤销、不做二次确认、不加快捷启动手势 → 依据契约面「启动替代一次出牌」与既有手感取向。
