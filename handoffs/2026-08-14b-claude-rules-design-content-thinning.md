## Intent（distilled）

> **一句话：** ADR-0005 已定「rules 里的设计结论只能是一句话承重纪律 + 回链」，但那句话**不可判定、也无人执行**——本次给它补上**阈值**与**执行者**。

### 起点：ADR-0005 缺的第三样东西

ADR-0005 对 `.claude/knowledge/*` 给了可执行的**副本判据**（凡在设计库里已是代码形态的东西 → 只留链接，不留副本），对 `.claude/rules/*` 只留下一句形态描述——「形态只能是**一句话承重纪律 + 回链**，不得展开为设计说明」。这句话没有阈值（一句话到底多长？举一个例子算不算展开？），也没有兜底（`/sync-knowledge` 的对账范围不含 `rules/`）。

**漂移已实际发生，不是假设。** `state-save-rules.md` 写「CycleState 拥有全部单次轮回数据（deck、**relic**、灵玉、地图位置、**ante/楼层**、当前遭遇战）」——`relic` / `ante` / `楼层` 都是本作**不使用**的泛体裁词（本作是神通 / 法宝 / 篇章 / 境界，见 `terminology.md`），且轮回状态的持有者已定为 `life-cycle-service.CycleStateManager`，不叫 `CycleState`。这正是 ADR-0005 预言的「副本 = 下一次漂移的唯一来源」的现场，也是「纪律的可执行化」阶梯第 4 级（人工评审清单）在此失效的实证。

### 结论一：形态合法，**不**瘦身到纯链接——依据是加载模型差异

|  | `.claude/knowledge/*` | `.claude/rules/*` |
|---|---|---|
| 加载方式 | Claude **主动去读**（导航后按需展开） | **前置注入**（起手 / 触及领域即在上下文里） |
| 那段文字的职责 | 告诉 Claude **去哪找** | 在 Claude **还没有理由去读设计库时**就阻止它写错 |
| 纯链接够用吗 | **够**——读它的那一刻本就在找东西，多跳一次即可 | **不够**——写错代码的那一刻，往往正是「没觉得需要查」的那一刻 |

ADR-0005 原文的措辞差异（knowledge「只留链接」vs rules「一句话 + 回链」）不是笔误，而是同一条判据在两种加载模型下的**两个刻度**。本次是把那句话**量化**，不是放宽它。

### 结论二：两步判据 + 可机械检查的硬边界

**第一步 · 归属分类**（沿用 ADR-0005 判据，不新增）：讲「游戏是什么」→ 设计库，受第二步约束；讲「代码怎么写」→ rules 自身即权威，原样保留、写多长都不算副本；讲「引擎 / 语言实践」→ 引擎，设计库无权威，同样不受约束（与 ADR-0005 对 `standards/` 三份的处理同理）。

**第二步 · 投影四件套**（仅对第一类）：一句祈使 + 该纪律涉及的标识符名 + 一句代价说明 + 一条直指设计库的回链，**缺一不可、多一即越界**。代价那句是让 Claude 不去绕过它的唯一理由，删掉它这条就退化成可商量的口味。

**硬边界七条**（出现任一者 ⇒ 违规 = 第二权威）：代码块 · 表格 · 枚举成员清单 / 字段清单（两个以上并列成员名）· 具体数值 / 阈值 / 默认值 · 完整取值域或分支穷举 · ≥3 步的编号流程 · 超过 3 行。理由与 08-14 判据卡逐字同构：两份表会各自漂移，而本库没有任何机制能发现它们不一致。

**三条附带机械规则：** 回链一律直指设计库、不经 `knowledge/` 中转（该层自己也只是薄引用 ⇒ 二跳且中间那跳是额外失效点）· 已被阶梯第 1 / 2 级手段强制的纪律，rules 里只留一句「由 X 强制」+ 回链 · 没有回链的设计性表述一律视为违规（缺回链与「还没想」不可区分）。

**自检问句**（给写的人用，不入正式判据）：**「把这句话删掉，Claude 会不会写错代码？」**——会 → 承重，留（并压进四件套）；不会 → 背景说明，删。投影只留**行为后果**，不留**定义**。

### 结论三：执行者 = 扩 `/sync-knowledge` 的对账范围到 `.claude/rules/*`

判据来自阶梯本身：本纪律只在文档层显形、且违反后会累积（`relic` / `ante` 已积了一处），按选级判据属「第 3 级足够」——但文档没有编译期，这里的「第 3 级」等价物就是**一个会定期跑的对账技能**。留在第 4 级已被实证证伪。

`/sync-knowledge` 是天然落点：它已有「副本化」这一首要漂移类型与 `### Thinned` 报告段，rules 的漂移与 knowledge 的漂移是**同一种**。**技能不更名**（三处引用它，更名的连带修改多于收益），改为在描述与正文首段写明对账对象 = **整个 `.claude` 的设计投影面**（`knowledge/*` + `rules/*`）。否决新开 `/audit-rules`——两份高度重复的技能文本各自演化，正是本方案在反对的第二权威。

### 结论四：`design-library-routing.md` 的两库结构表 = 显式例外

它复述的是两库 README 的**目录结构**，不是设计内容——「哪个文件夹在哪个库」讲的是工程层路由。且它是技能执行的**前置信息**：换成回链等于每次跑设计流水线技能都要先读两份 README，而路由判错的代价是把一侧的意图写进另一侧的库（污染事实来源）。**保留结构表 + 显式标注为「路由用副本」**，两库结构变更时须同改、由 `/sync-knowledge` 对账兜底——是一份**已知的、有理由的、被审计覆盖的**副本，而非漏网。

### 落地面（工程层，本 handoff 不执行）

九份规则文件逐份核对的结论：**需改 3 份**（`data-resource-rules.md` 的 `AllEnabled()` 段 6 行 → 3 行 + 「加载时校验」压句 · `state-save-rules.md` 的轮回状态段改写 + 确定性边界段压句 + 删 RNG 子流括号举例 · `Context.md` 的「离线 stub」补回链），**轻改 2 份**（`csharp-godot-rules.md` 的 EventBus 回链改直指 `systems/architecture.md` 总则 5 · `ui-input-rules.md` 补回链 `vision/scope.md`），**1 份标注为显式例外**（`design-library-routing.md`），**3 份完全不动**（`null-check-rules.md` / `scene-rules.md` / `environment-rules.md`）。

**净瘦身约 15~20 行，无任何工程约束条目被删**——瘦的全是设计结论的复述。设计库中 5 处 `Source: .claude/rules/*` 的指认（稳定 `Id` 键 / 字段命名与类型一致性 / Null 校验 / 日志约定 / 原子写入）**全部属工程约束、全部保持有效，不需要反转任何一处方向**。

**排期由用户自行掌握**，执行清单见归档草稿 `inbox/archive/solution-draft-claude-rules-design-content-thinning.md` 的 `## 执行清单（按顺序）`（步骤 3 瘦身 rules · 步骤 4 扩 `/sync-knowledge` · 步骤 5 空跑验证）。

### 边界

**不改任何机制 / 字段语义 / 存档 schema / API 签名。不 bump schema，无迁移。** 后端库无 `knowledge` 引用层、`.claude` 侧无对应物 ⇒ **对 `backend-design-documents/` 零影响**。
