## Intent（distilled）

回寿法宝这一族的护栏已答全（四条获取通道逐条给闸 + 三格编排口径 L-1 / L-2 / L-3 + 取池侧排除 L-0）。本次收的是同一句话的另一半——**其余道具族的同三格口径**。

**承重的那一步是先拆问题，而不是逐族各写一套 L-1/L-2/L-3。** 道具能表达的功能族只有两个来源：战斗外 `OutOfCombatUseOutcome.Elements` 可写的资源 key，与战斗内 `CombatUseEffects` 的八原语。把事件侧已定的可写 key 白名单搬到道具侧之后，待答的三格口径塌缩成三件具体的事。

### 1. 道具侧的可写 key 白名单 `I-13`

**新增加载期校验 `I-13`：`OutOfCombatUseOutcome.Elements` 中任一行的 `Key ∉ { CostKey.LifeSpan }` → `PushError` + 条目 `Id` + 报出该 `Key`。** 与 `I-6`（key 在 `ResourceElements` 表内、`Op` 在该行 `AllowedOps` 内）**并存不合并**：`I-6` 管 `Op`，`I-13` 管 key 的编排准入；形态照事件侧「模板可声明的 key ≠ 物化后可出现的 key」两张表。

三条依据：

1. **事件侧已就同一问题定案为白名单**，而 `OutOfCombatUseOutcome` 与 `OutcomeRule` 同层同性质（都是内容侧模板），没有理由适用不同的表。
2. **不补白名单，三个已封的口全部从道具侧重开：** `ExperiencePoint`（绕开 `ExperienceGrade` 枚举档 + 平衡表映射，且直改 `G_c` 供给账）· `Faith` / `Bloodlust`（绕开 `HiddenStatGrant(Stat, Grade, Direction)` 的档位映射，逐篇章推拉供给对账当场失真）· **账号层六个 `CostKey`**（`PowerFragment*` × 5 · `BundleRedeemedOrdinal`——一件写 `PowerFragmentAccumulated` 的法宝就是一条绕开残卷机制的道统碎片通道，与 `AbilityElements` 恒空那一格封的是同一件事）。
3. **它让问题自己收敛：** 战斗外可表达的功能族 = 白名单长度。收到 1 ⇒ `Elements` 一列只剩回寿，而它的口径已答定。与「不设 `Abilities` 一格」同形：**把写不出来当作护栏，而不是写得出来再加校验**。

**拒绝面：** `SpiritStone` / `ImmortalJade` / `ManaLimit` / `ExperiencePoint` / `Faith` / `Bloodlust` + 六个账号层 `CostKey`，全部在内。

- **`ManaLimit`**：载体判据不成立（`manaLimit +1` 是永久增量，`Charges` 这个节流阀名存实亡 ⇒ 它在载体判据上属神通 / 法则那一侧）；且预算已被事件侧铺满（一章净增 +1~+2，含 `Finale` 每篇章一次 +1 的保底），道具侧再开一条即账外增量，溢出即「有 mana 没牌打」。
- **两种货币**：商店侧结构上无意义（`CharacterItem` 五档恒收灵石 ⇒ 一件产灵石的法宝是「用灵石买灵石」，产出 < 价格则无人买、≥ 价格则套利）；免费通道上它是账外的 `I(c)` 增量（战后奖励一轮回给 ≈ 18.5 件法宝）；仙玉尤甚（`J(c)` 三章仅 ≈ 2 / 3 / 5 枚，一件产 1 枚的法宝即占一章收入的 20–50%，与「仙玉一格都不落 `CharacterItem` 族」同向）。

**代价明写（被接受）：** 内容侧从此编排不出经验丹 / 静心符 / 血煞珠 / 碎片袋 / 灵石袋 / 储物锦囊的**道具形态**；同名风味改由战斗 `BaseReward` 与事件 outcome 承载（两处都在账内）。方向**可逆**：日后要开货币须同时补「加回白名单一格 + L-0 同构的免费通道排除 + 商店侧『产灵石的法宝不进 `CharacterItem` 库存』排除」；要开 `ManaLimit` 须同时补「`|BaseValue| == 1` 的加载期闸 + `Charges == 1` 强制 + L-0 同构排除」。

### 2. 「一个族需不需要独立护栏」的判据

**一个道具功能族需要独立的供给护栏，当且仅当它产出的量进入某条已被反推封账的预算线**（λ 反推的寿元账 `B_c` / `R_c` · 货币账 `I(c)` / `J(c)` · 经验账 `G_c` / `D_c` · 卡组规模口径）。

- **战斗内八原语的六族一条都不进**——产出随战斗结束一并消失、不落 Profile、不跨事件；`counters` 那一支由 `I-9` 已封（道具没有宿主 `AbilityData`，键拼不出）。它们由「强度」维度的既有三件套（`itemPowerRatio(Charges)` 折价系数 · 25 格定价表 · 稀有度权重表）完整承接，**不需要第四套口径**。
- **战斗外仍开三列**（`Elements` / `CodexElements` / `Stats`）：白名单收窄后 `Elements` 只剩回寿，但 `CodexElements`（使用后解锁一条图鉴词条，幂等收录）与 `Stats`（纯计数自增）两族仍写得出来。按上述判据，这两族一条都不进任何账 ⇒ **同样不需要三格口径**。
- 推论：三格口径里 L-1 在战斗内族上退化为「族占比 + 条目数矩阵」（已是既有物），L-3 退化为「读表、不填 `PriceOffset`」（也已是既有物）；战斗内族只欠 L-2 那一半。

### 3. 商店库存深度：五族分配表（补齐 L-2）

单个 Exchange 条目内逐 `Kind` 的 Σ`SlotCount` 上界 = **3 / 2 / 1 / 1 / 0**（法宝 / 散牌 / 神通 / 功法 / 古宝），**Σ = 7**。

- `Card` ≤ 2：池分母只剩游离散牌（首批 4 条），且卡组规模口径「一轮回全部通道合计 +3 ~ +7 张」中战后奖励已占 ≈ 1.9 张。
- `CharacterPower` ≤ 1：池只有 4 条，逐档核算 + `ExchangePoolMargin` 下深度 2 即被闸 ① 拦在启动期。
- `CultivationTechnique` ≤ 1：池首批 1 条，分母须按可修条目最少的那个灵根收缩；另有「一次轮回至多一门功法从任一通道进组」的卡组规模硬约束。
- `PlayerItem` = 0：「规则层开放、首批内容不编排」是既定内容口径。
- **Σ 7 ≤ 8 是有意的**：槽位总数上界是快照体积护栏，逐族上界之和顶死它会让两条校验永远同时触发，其中一条从此没有独立信息。
- **不为逐族上界新开字段**：按 `ExchangeSpec.StockRules` 的 `Kind` 分组求和即得，与闸 ① 是同一次分组。处置同 L-2：`/audit-content` 一项汇总、只报告不阻断。

### 4. 事件产出侧给道具的量（补齐通道 ③）

载体是既有的 `OutcomeRule.Kind == GrantFromPool` + `PoolKind == CharacterItem`（模板侧 ↔ 物化侧的 `AbilityElements` 是同一条链）。

- **期望到手 ≈ 1.5 件 / 完整轮回**；每条规则 `Count` 恒 1（编排口径，不改 `Count >= 1` 的既有校验——「一颗 = 一档」的可读性纪律，数量语义已由储物袋按 `ItemId` 堆叠 `×N` 承载）；旋钮 = 带该规则的 `AdventureEventData` 条目数 × 各条 `SelectionWeight` 档（**零字段、零校验、零状态位**）；首批等价形态 = 每篇章 1 条 `Rare` 档条目 × `Count = 1`。
- 依据：事件位是全局最稀缺的资源（一章约 35 批次、每批至多 5 项候选），而通道 ④ 一轮回已白给 ≈ 18.5 件法宝 ⇒ 占掉一个事件位去发一件消耗品，收益远低于让那个事件承载一次决策或一段叙事；且它与回寿事件（每章 1 次小档）的量级对齐，同为「事件位换一件消耗品」不该差一个数量级。
- **新增软校验 `X-1`：`eventType == Exchange` 的条目携带 `OutcomeRule(Kind == GrantFromPool)` → `PushWarning` + 条目 `Id`。** 消费点白给商品 = 给定价表打一个不可见的折；软检查而非拒绝，赠礼式风味条目是正常例外，本行的职责是让每个例外被看见。`eventType == Travel` 的排除由既有禁令承担，不重述。

### 5. 置换对价

规则形态已全部答定（同池判据 · 同 `Rarity` · 排除已持有 · 先看后决 · 拒绝无代价 · 继承 `SourceCode` · 空池即空操作 + `PushWarning`）。本次给的只有编排口径：

- **法宝置换目标频次 ≈ 2 次 / 完整轮回**（≈ 法宝总供给 24 件的 8%），旋钮同为条目数 × `SelectionWeight` 档。**它与法宝 / 古宝禁用一并计入「失去能力」上层 ≈ 1.0 的分子；具体份额归 `systems/character-profile/item/` 侧裁定**，四支频次表的权威在 `systems/player-profile/player-power/_index.md`。理由：置换写 `CharacterProfile`（自持口径的首条判据是「它不写 Profile」，故不成立），同层的神通置换在上层合计内已占 ≈ 0.5。它反而应比法则两支更常见——法宝在「持久度 × 是否经玩家同意」两轴上都是最轻的一端（轮回级 + 有同意，储物袋不设容量上限、随售是常态弃置途径）。
- **法宝逐档启用条目数 ≥ 2**（与神通那条并列）：置换池 = 同 `(CarrierKind, Scope)` + 同 `Rarity` + **排除已持有** ⇒ 首批矩阵的法宝 Tier5 = 1 条会让玩家一旦持有它、Tier5 置换池恒空。矩阵法宝行 Tier5 由 1 提到 2。
- **barter 两格护栏**（此前它一个护栏都没有）：对价按**档差**——`产出物的 RarityTier ≤ 支付物的 RarityTier + 1`；条数 **≤ 1 条 / 店**。两条均为 `/audit-content` 汇总、只报告不阻断。

### 6. 回代式修正与分账重填

商店侧回寿供给的回代式漏了一层条件概率：抽取先按 `RarityTier` 权重选档、再在档内等概率取条目，而回寿只编排 Tier2 / Tier3 / Tier4 三档。补上后 `p(单槽为回寿)` = 0.0282 / 0.0306 / 0.0324、`P(某店至少含一件, 2 槽)` = 5.6% / 6.0% / 6.4%（原式 11.6% 高估约一倍）、期望遇到次数 = 0.56 / 0.60 / 0.76、`R_item,c` = 33.9 / 38.9 / 52.7。

`R_c` 两格按实际可供给重填：**`R_item,c` = 34 / 39 / 53 · `R_event,c` = 66 / 77 / 264**，Σ 恒等于 `R_c` = 100 / 116 / 317 ⇒ **λ 与 21 格 `lifeSpanCost` 定价表零改动**。`R_event,c` 三章统一表述为「每章 1 次小档（5% × 本章预算）+ 点名给回寿法宝的事件产出补足至本格」，逐章补足量 +16 / +19 / +105。

**⚠ 三个标定假设（败率 20% · `E[道念差]` · 购买转化率 0.7）未实测，上述三个数字与 0.56 / 0.60 / 0.76 不得被引为任何设计的承重依据。**
