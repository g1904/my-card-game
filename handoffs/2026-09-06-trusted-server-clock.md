## Intent（distilled）

契约已定「时段判定的时间源必须是可信的服务端时钟」，但**可信时钟本身没有形态**：哪一个时钟是基准、多副本如何一致、怎么保持准确、时区口径落在哪一层、法定节假日表从哪来、时钟或规则不可用时往哪一侧倒。同一个时间源还被另外三处判定共用（注销冷静期到期 · ticket 的寿命与回放窗口 · 未成年 access token 的 TTL），**口径必须只有一份**。

### 一、基准 = 该次事务的数据库时钟

不取应用容器的进程时钟。单主库已经是全库唯一的串行点，容器可伸缩、副本各有各的时钟，而**主库只有一台**：取库时钟即天然得到全站唯一的时间基准，不需要为跨副本一致性引入任何机制；判定本就发生在已握着账号行锁的事务里，故零额外开销，且**判定与写入看到同一个时刻**，不在两者之间开竞态缝。

两处例外明写以免被误推广：access token 的签发时刻与到期时刻从会话状态派生（否则同一次幂等回放会产出字节不同的 token）· JWT 验签时的到期比对用验签侧进程时钟（其容错已由旧 `kid` 的保留窗口承接）。

**跨区域一致性在当前拓扑下不是一个问题**：单区域部署、不做跨区域多活、只读副本不承接玩家读路径。这一段记的是「已经消解」，不写它，下一个读到这条需求的人会重新去设计一套跨区域时钟同步。

### 二、同步纪律：内网授时 + 常驻守护 + 只 slew 不后跳

绝不允许时钟向后跳变：向后跳会让「一次性消费」「到期即生效」「单调序号」看到时间倒流，而这些判定的错误后果不可回收。超出渐进修正能力的偏差告警并人工介入，不静默 step。**不可逆动作在时钟异常期间暂停**：注销执行暂停一轮，时段与 ticket 判定照常（它们的边界是小时 / 分钟级，秒级偏差不改变结论）。这条把时钟异常的爆炸半径限制在「晚几分钟执行」，而不是「错误地永久删号」。

### 三、时区与时段规则集：随规则集版本化发布

判定在 `Asia/Shanghai` 本地时间下进行、存储与报文一律 UTC；**时区是时段规则的一员，与时段表同处规则集**，不是代码常量也不落单值旋钮表——否则会出现「时区改了但时段没改」的半版本态。用 IANA 时区名而非固定偏移：今天等价，但任何带夏令时的扩展都要改形状，而用 tz 名成本为零。**镜像必须内置 tzdata 并作为启动断言**——缺失时的表现是运行期合规判定当场抛异常，启动自检解析一次时区名是它唯一可靠的发现面。

时段规则不是单值旋钮而是结构化规则集（星期集合 + 时段区间 + 每日时长 + 日历），因此**逐条复用昵称词表的不可变版本化发布**：存量审计必须能回答「这一次拦截是按哪一版规则做的」，而「随手改一下数据源」正是不可变发布要堵的静默失效模式。规则集与词表同量级，永久保留成本近似为零，且发布通道 / 留痕字段 / 回滚语义全部已存在——**零新增机制**。生效时刻只有一个：判定时读当前最高版本，不做预约生效。

### 四、法定节假日日历：人工录入，两类条目

现行口径里的「法定节假日」是一份每年由国务院办公厅发布、且带调休的日历，不是可由星期推算的规则，也没有官方机读接口。**人工录入、随规则集一次发布，不接第三方接口作判定输入**——那是一个无 SLA 的外部依赖，却直接决定未成年玩家能否进入，而数据一年只变一次、总量二十余行。

**日历必须有两类条目**：法定节假日（该日可玩，无论星期几）与调休上班的周末（该日不可玩，尽管它是周末）。后者最容易漏，而漏掉它的方向是「多给」，即不合规的那一侧。判定顺序把减法排在最前，让保守的那一侧永远优先。

**到期告警是日历失效唯一的机制发现面**：覆盖的最后一个日期距今不足 60 天即工程告警。年度录入本身是一条周期性运维日程项，不并入「首个真实账号建号之前」那份一次性清单——那份清单的成立前提是共用同一个不可逆时刻。

### 五、降级：合规判定命中「错误放行不可回收」这条例外判据

三个失败面：时钟异常 → 判定照常 + 告警，但暂停不可逆动作；规则集读取失败 → **对未成年账号 fail-closed**（成年账号不做时段判定，不受影响）；日历过期 → 与规则集读取失败同处置。

fail-open 是默认，**例外的判据是「错误放行的代价不可回收」**——既有实例是短信计数（真金白银），合规判定是同一判据下的又一实例且代价方向更硬：错误放行一个未成年账号是合规事故、不可回收；错误拦截可回收（配置回源恢复即自动解除）。爆炸半径三重夹住：只影响已判定为未成年的账号 · 只在配置回源失败时触发（有约 30 秒进程内缓存兜着）· 拦截发生在登录而非轮回中途。

降级路径下的解除时刻取**基础周规则下的下一个允许时段起点**（只依赖星期与时钟，用编译期兜底常量）：它可能晚于实际可玩时刻，方向保守、报文形状完整、零契约改动。

## Clarifications

- **日历过期时对未成年账号取哪个方向** → 一律拦截（fail-closed），与规则集读取失败同处置（2026-09-06 批量评审裁决）。错误拦截可回收、错误放行不可回收；日历过期已有提前 60 天的告警，是可预防的运维失职，不为它设计一条会产生合规风险的降级路径。**降级路径因此只有一条**——两条降级路径必然有一条长期没被走过，因而是坏的。「按基础周规则继续判定」被否决：它会让每年约 6–8 天的调休工作日被错误判为可玩。
- **日历到期告警落在观测文档的哪一节** → 与两条时钟探针同处「其余最小集合」的数据面（自行推演；原表述用的是泛指措辞，该文档没有同名小节）。
- **年度日历录入的登记位置** → 落发布文档新起的一节，与一次性的建号前置清单分开（自行推演，依据两者触发形态不同：一个绑不可逆时刻、一个每年重来）。
- **tzdata 启动断言的形态** → 启动自检解析一次时区名，失败即拒绝启动（通行做法 + 既有先例：收据表 TTL 策略的启动期断言取向相同）。
