# flags 拉取的频次护栏 —— 增大即拉 + 单飞/尾随封顶 + 闸门式失败退避

- date: 2026-08-22
- topic: systems/services/content-service · systems/balance
- status: distilled
- distilled-to: systems/services/content-service.md, systems/balance.md, backend-design-documents/contracts/content-manifest.md（对侧承接项）

## Intent（distilled）

把 flags 的拉取规则从「版本**不同**即拉」收紧为「**增大**即拉」，成功路径**不设最小拉取间隔**（拉取次数的上界由单调闸门 + 单飞/尾随界定），把护栏移到失败路径与异常路径。

1. **成功路径 = 单调闸门。** 增大即拉 · 等值不拉 · **更小不拉**。不设最小间隔：单调闸门已把上界压到运营的发布批次数，而最小间隔会把秒关延迟从「分钟级」抬到「间隔级」，恰在运营连发多批（= 正在处理线上事故）时最伤。
2. **单飞 + 尾随一次，且尾随有显式封顶。** 在途期间的更高观测只更新「最高已观测版本」，不发第二次请求；结束后**仅当本次拉回版本 > 拉取前的内存值**（确有实质推进）且仍落后 → 尾随一次，否则**停并告警**。封顶杜绝「头部观测值与 body 版本来自不同来源 ⇒ 每次尾随后条件依旧成立 ⇒ 无休止连发」这条无限环。
3. **失败路径 = 闸门式退避（无定时器）。** 退避窗口只是「窗口内的观测不发请求」；**窗口到期不主动发起，仍等下一次搭车观测才拉**。它是一条抑制规则，不是独立的重试通道——`content-service.md`「不为它另开重试机制」原样成立，「零轮询」这条 flags 通道的立身理由未被松动。底数 1 s · ×2 · cap 60 s · **无放弃阈值**；沿用「实际间隔 = max(本地退避计算值, 服务端给的等待时间)」，**不沿用抖动**（观测触发已天然错峰）。
4. **异常路径获得线上可见性。** 观测到更小版本（灰度分桶串号 / 中间层缓存旧应答）→ 不拉 + `PushWarning` + **上报一次**，沿用验签失败那条既定通道。
5. **验签失败按版本记忆。** 记**单个** `flagsVersion` 本会话不再重试；**更高版本照常重试**，上界 = 发布批次数——这是有意的，不是漏抑制。
6. **内存 `FlagsVersion` 冷启动一律归零。** 缓存只提供 `disabledIds` 的降级值、不回填版本 ⇒ 首次观测必拉。这是「增大即拉」的爆炸半径闸。
7. **API 面：签名零改动，语义有改动。** `RefreshFlagsAsync` / `OnFlagsVersionObserved` / `FlagsVersion` 三者签名一字不变；但 `OnFlagsVersionObserved` 的触发条件由「不同」收紧为「增大」，flags 一节的刷新时机与失败重试两句正文随之改写。**不要沿用「零改动」这一措辞。**
8. **三样新增运行态全私有**（最高已观测版本 · 退避阶梯 · 验签失败版本记忆）：不出 API 面、不落盘、不进 Profile、不进报文；账号维度，切账号一并清零。存档 schema / `flags.json` 字段面 / 后端报文零影响。

## Clarifications（interview 产物）

- **退避是不是「另开的重试机制」？** → **纯闸门式退避（无定时器）**。推翻草稿把退避与「窗口到期时若仍落后则拉」并写、却称「张力：无 / API 零改动」的表述；`content-service.md`「不为它另开重试机制」这半句**保留不改**，只在其后补一句退避闸门。
- **尾随会不会自我递归成无限环？** → 尾随条件改为「**本次拉回版本 > 拉取前的 `FlagsVersion`**」，否则停并告警。细化草稿「若仍 < `_highestObserved` 则尾随一次」这句（该句在 body 版本长期不推进时会无休止连发）。
- **观测到更小版本只 `PushWarning` 够不够？** → **`PushWarning` + 上报一次**，去重口径为「上报侧本会话一次」。推翻草稿「只 `PushWarning`」：本库既有判据是「告警要落在能被看见的地方，落在玩家进程里的 `PushWarning` 等于落在没人看的地方」，而这类事故只可能在线上发生。
- **「增大即拉」在服务端版本回退时会让设备永久停止同步开关，草稿把它记为纯收益。** → **采纳「增大即拉」+ 要求后端补契约条款**：客户端明写对「`flagsVersion` 单调递增」的行为依赖及其失败症状并回链契约；后端库落一条承接项（flags 回滚须以更高 `flagsVersion` 发布）。**推翻草稿「与既有决策的张力：无」「前置依赖：无」两处结论**——本次存在跨库承接项，两侧互相回链。
- **内存 `FlagsVersion` 的启动初值。** → 取解读 (a) **冷启动一律归零**（缓存只给 `disabledIds` 降级值、不回填版本），并明写进 `content-service.md`。依据：它是上一条那个契约依赖的爆炸半径闸——把停摆限制在单次会话内，而非跨启动永久化。草稿把「初值 = 0」当 `[既有推演]`，但目标文档从未写过这一点。
- **退避是否带抖动 / 是否尊重服务端等待时间。** → **沿用**「实际间隔 = max(本地退避计算值, 服务端给的等待时间)」（省略它会把一次限流变成第二次限流，这条与通道无关）；**不沿用抖动**并写明理由（flags 拉取由搭车观测触发，天然错峰）。草稿声称「与 push 退避同构」却对这两条只字未提。
- **验签失败的版本记忆粒度。** → 记**单个版本号**，并明写「更高版本照常重试，上界 = 发布批次数」。依据：不写明，读者会误以为该路径已被抑制。

## Open questions

- **退避上限（cap）取值 = 60 s** `[采纳推荐 — 待复核]`。理由：与 push 退避 cap 同值、便于统一配表；flags 的延迟容忍度本以分钟计。备选 30 s（恢复更快，不可用期间请求翻倍）。属待实测校准的初值，落 `balance.md`，改动不触及任何结构。
- **观测到更小版本的告警去重口径 = 上报侧本会话一次** `[采纳推荐 — 待复核]`。理由：中间层缓存旧应答时旧值可能持续到达数十次，逐次上报淹没日志。备选：每次都报（便于估算事故规模）· 按 `(observed, FlagsVersion)` 对去重（多一层状态，对诊断日志不划算）。
