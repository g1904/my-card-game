# 剧本树不按篇章分包

## Intent（distilled）

**一句话：剧本树不按篇章分包——三篇章的完整剧本树整体随 `res://` 基线发布，更新走 overlay 的文件级增量热更。这条待答项就此关闭，只留一道零成本的复核闸。**

### 结论

- **不分包。** 不按 `PlotArcData.ChapterScope` 分 3 包、不按 `PlotTier` 分 2 包、不把剧本正文外置为独立文本类型只分包正文、不重开云端按需请求。
- **零机制增量。** manifest 不加字段、`manifestSchema` 不提升、`ContentUpdateManager` 不加运行时下载路径、不新增第三处硬阻塞、`PlotArcData` / `PlotNodeData` / `PlotKeyPoint` schema 全不动、不新增任何失败语义或降级分支。
- **零跨库影响。** 由客户端的内容合并与打包决定，服务端不感知、报文无变化 ⇒ 本条不横跨库边界，后端库零改动。

### 承重理由（三条，按分量排序）

**① 分包与「合并后全量强校验」在结构上冲突。** ContentRegistry 在 overlay 合并后跑一遍全量强校验，剧本侧有四类悬空校验（`EntryNodeId` / `ParentArcId` / `ArcId` / `ToNodeId`）+ 层级校验 + 可达性 / 含环校验 + `PlotTriggerId` 双向校验。分包意味着某一包未下载时，跨包引用当场悬空 ⇒ 启动即 `PushError` + 抛。要让分包成立只有三条路，每条都在拆一件承重件：

- 放宽剧本侧悬空校验为 `PushWarning` ⇒ 一个真的编排错误与一个「这个包还没下」在日志里长得一模一样；
- 给剧本条目造第三种状态「未下载」⇒ 内容层出现既非「存在」也非「不存在」的态，立刻传染到 `Get(id)` / `AllEnabled()` / `newIds` 双闸 / 悬空 key point 降级四处；
- 让分包边界切在「无跨包引用」处 ⇒ 但 Story arc 按定义贯穿三篇章、`SideStory` 按定义跨篇章、`PlotTriggerId` 按定义跨到档位表。**跨包引用不是可以避开的编排问题，是剧本层级模型本身的形状。**

**② 收益侧本就很薄，强制在线把它削得更薄。** 玩家启动即须登录 + 跑一次 pull（两处硬阻塞）⇒ 他必然处在有网环境；「让用户先玩起来、剩下的慢慢下」这条离线优先产品的核心动机在本作没有对应场景。反过来，分包会造出一个既有设计里不存在的失败态：「推进到第 2 篇章却没网」在不分包下完全无害（剧本在盘上、`TryResolvePlot` 是纯内存查找），在分包下要么变成第三处硬阻塞，要么变成「整章剧本静默缺席」——后者正是悬空 key point 降级规则刻意把爆炸半径限制在「不阻塞其余剧本线」时要避免的那种放大。

**③ 量级不成立。** 剧本文本落在包体的**百分之一量级**：以偏保守的假设估算，未压缩约 2 MB 级、落地包体增量不足 1 MB——约等于一首 BGM，而引擎基线与卡面美术都是数十 MB 级。为百分之一的收益买一整套分发机制（≥ 6 条新机制 / 被拆的承重件）是净亏。

此外：overlay 侧**本来就已经是文件级增量下载**（逐文件 hash 比对），所以本题真正问的只剩「随包基线要不要拆」——热更侧的增量能力早已有了，分包在那一侧买不到任何新东西。且 MVP 只有一个篇章，「三篇章完整剧本树」这个体积在 MVP 阶段根本不会出现。

### 复核闸（零成本，非待答项）

第二阶段（内容）第一批真实剧本条目写完后，实测 `res://content/plot-arc/` + `plot-node/` 的字节总和与应用总包体之比。**仅当占比与绝对值双双越过届时设定的门槛时**才重开分包讨论；届时的首选形态是**平台原生按需资源**（Android Play Asset Delivery / iOS On-Demand Resources），而非 manifest 分包。

留这道闸的理由：不分包的结论是一个**相对**结论（剧本文本相对包体可忽略），它依赖「美术 / 音频确实是数十 MB 级」这个前提。若日后包体预算被定成一个极小的数，这条相对结论要重算。成本是一次 `du`。

### 方向性记录：真要缩初装包，落点是平台原生按需资源

平台原生机制是**发行侧的打包配置**，不是内容分发契约的成员 ⇒ 不碰 manifest schema、不碰文件级事务的单一提交点、不碰 `LoadAll()` 的一次性合并；平台自己承担下载、缓存、驱逐、续传与失败重试；且它天然选中的资产是美术与音频（数十 MB 级）而非剧本文本。**换句话说：真到了那天，要拆的也不是剧本树。**

记这一句的理由与既有的「不为每日种子 / 排行挑战预留冻结结构，但把正确做法记一句」同款纪律：不预留结构，但留下路标，免得将来有人因为「manifest 已经现成」而回退全局决策。

### 体积护栏的形态

`content/plot-arc/_index.md` 与 `content/plot-node/_index.md` 两个类型档案开张时，在「条目台账」小节记一行口径：**条目数 + 字节总和**。**不加任何加载期校验**——那需要定两个当前没有任何依据的数字，而剧本侧的加载期校验清单已经很长。两个类型档案当前尚未开张（随事件类顺延），故本项在开张时才落地。

### 明确不采纳

- **不**往后端库 `contracts/content-manifest.md` 写任何承接。平台原生按需资源是发行侧打包配置，后端零参与、报文零变化；往对侧库写等于在那边放一条不属于它的内容。
- **不**重开云端剧本服务（08-11 已定案的四条理由原样成立）。
- **不**把剧本正文外置为独立文本类型（正文内嵌节点是既定形态，拆开会让 overlay 新增 arc 时写不出它的正文，剧本例外当场失效）。

## Clarifications（interview 产物）

批量评审中的三项取向，用户授权按推荐推进，均为 `[采纳推荐 — 待复核]`：

- **这条待答项是关闭为定案，还是保留为「已倾向不分包、待实测复核」？** → **关闭为定案 + 留复核闸**。理由：结论不依赖任何未知量（结构冲突与强制在线论证是纯推演），它不是「信息不足待补」型待答项，而是一道已经可以答的取舍题。复核闸把「相对结论的前提可能变化」这个风险补上，成本为零。
- **要不要在类型档案里立体积护栏？** → **只在条目台账记「条目数 + 字节总和」，不加加载期校验**。两个类型档案尚未开张，本项开张时才落地。
- **「平台原生按需资源」要不要写进主题文档？** → **写一句方向性记录**；明确**不**往后端库写承接。

主结论「不分包」本身在合并 interview 中无人反对，照草稿采纳。
