## Intent（distilled）

**一句话：** 回声校验从「`entitlement` 一处的特例」升为**通则**——受约束的 path 集合**恒等于**后端写入字段表的行集合，适用面因此结构性封闭；比较口径取**类型感知的语义相等**，因为选错的代价是正常玩家在一次改昵称上被整批拒绝 = 丢一次进度。

### 1. 适用面 = 一条恒等式，不是第二份清单（承重）

> **受回声校验约束的 JSON path 集合 ≡ 后端写入字段表的行集合。**

这是「够格进表」两条判据的直接推论：一条路径够格进写入表 ⟺ ① 真值只可能在服务端产生 且 ② 客户端无任何其他通道取到它 ⟺ **客户端提交的任何值都只能是它 pull 到的那个值**。三条推论：

- 写入表加一行，该路径**自动**进入回声约束——不需要第二次决定、不需要加强扩表护栏；
- 写入表封闭 ⇒ 回声约束面封闭，「适用面有没有列全」这个问题**结构性地不存在**；
- 不属写入表的透明路径一律不受约束——**判据是所有权，不是透明性**。

**另立一张「受约束 path」清单是明确否决的**：它与写入表必然漂移，漂移形态正是「进了写入表却没进回声表」，即这条恒等式要关掉的那个口子。

当前的具体面共四条 path、**两个受约束顶层键**（`accountInfo` 由改昵称触发 · `entitlement` 由兑现触发）。两者的共同形状是「同一顶层键内混有后端写入路径与客户端写入路径」——这正是整键替换把覆写窗口变成**常规路径**的充要条件。

### 2. 比较口径 = 类型感知的语义相等（承重）

| 类型 | 口径 |
|---|---|
| 整数 | 数值相等 |
| 定长 hex 串 | 逐字相等（形态已被 §2 钉死，两侧无归一化自由度） |
| RFC 3339 时间串 | **按时刻相等** |
| 对象数组 | **有序逐元素**，元素内逐字段递归 |

**时间串必须按时刻比较。** 客户端持有强类型时间值，反序列化 → 再序列化会在 `Z` / `+00:00`、小数秒位数上产生合法但不同字面的表示。按字面比较等于要求两侧时间序列化器逐字一致——**一条无人声明、无处校验、一次库升级就会静默破坏的隐含契约**，破坏时的症状是「所有玩家改昵称都丢一次进度」。**不按原始字节比较**同理，并追加一条：JSON 键序与空白不稳定，字节比较把序列化器实现细节抬成契约。

**数组取有序而非集合相等**：顺序由后端产出、客户端原样回声，要求有序既更严格也更便宜；宽松只会掩盖客户端的重排 bug。

**连带刚性：向受约束顶层键内的对象追加字段 = 两侧同批落笔的变更。** 客户端的强类型往返会静默丢掉它不认识的字段 ⇒ 回声当场失败。这是 `envelope.md` §8「客户端加字段零配合」的**例外**（那句讲不透明段，本条讲白名单内），故 §8 须留一句指路。

### 3. 已在位、本次只做收口的部分

`profile-sync.md` §4 的四类拒绝清单（含所有权类）、判定顺序（`schemaVersion` → 信封形状 → CAS → 回声 → 写入，拒绝不消耗 revision）、§5c 规则本体与 `detail.field` 形状、§7a 与 `purchase.md` §5 的「判据是所有权、不是严格程度」——**均已由前一批落笔**。本次把 §5c 末尾那句「`/accountInfo` 的清单与口径尚未落笔、在落笔前不得按字节相等实现」改写为定案，并补上恒等式、口径表与栈中立的验收断言。

## Clarifications（interview 产物）

三项取向已于 08-22 批量评审裁决，其中两项系「采纳推荐 — 待复核」，**本次提炼前已由用户逐条确认**：

- `createdAtUtc` 的比较口径 → **按时刻相等**（用户 2026-08-23 确认）。备选「逐字相等」更简单更严格，但它把一条本可由后端一次解析消化的风险，压成客户端一条必须永远记得的纪律。
- `identities` 的比较口径 → **有序逐元素相等**（用户 2026-08-23 确认）。备选「集合相等」更宽松但无收益，只会掩盖客户端的重排 bug。
- 新刚性「受约束顶层键内追加字段 = 两侧同批」是否接受 → **接受**（与对侧同项同裁）。替代方案是要求客户端对受约束键采用保留未知字段的松散持有形态，代价落在对侧、打破其类型一致性纪律。
- 计数订正（本次落笔时核对）：上游草稿登记的「§4 拒绝清单由两类变三类」计数有误——实际清单含 `schemaVersion` 闸门，为**四类**。契约现文已是四类，无需再改。
