# `flagsVersion` 严格单调 + 回滚即前滚：contentVersion 那条纪律的 flags 对位

## Intent（distilled）

**一句话：** 客户端已把 flags 拉取由「版本不同即拉」收紧为「**增大**即拉」并开始依赖 `flagsVersion` 单调递增，本库欠这一半——补上的不只是「单调」一句，还有**同版本结果恒定**与**规则集不可变**，因为单调递增只堵住回退、堵不住原地改。

### 条款三半（缺一不可）

1. **单一全局单调序列。** `X-Flags-Version` 与 `GET /v1/content/flags` 应答体内的 `flagsVersion` 取自同一个序列，**不按区域 / 实例 / 账号分别计数**。这不是修辞：头搭任意应答的车，设备一次会话内会从多个实例（可能多个区域）读到它。号只由**发布动作**分配，草稿态编辑不占号。
2. **严格单调递增，回滚 = 以历史规则内容发布更大的版本。** flags 是**全量快照**，故前滚与首次发布走完全相同的路径，成本为零。**这条零成本的理由与 `contentVersion` 那条不同源**（那条靠内容寻址），因此不宜并进同一条 ADR。
3. **同一 `(flagsVersion, 账号)` 的解析结果恒定。** 任何影响解析结果的改动（规则增删、分桶比例、白名单、分桶盐值）都必须提升版本；分桶函数须是 `(accountId, 规则集版本)` 的纯函数，不依赖实例本地随机 / 当前时间 / 请求属性。

**第 3 条是本次相对「只写一句单调递增」的主要增量。** 客户端「等值不拉」使**内容变了而版本没变**成为一个静默失效模式，其危害不亚于版本回退且更难定位；`contentVersion` 不需要这半句（静态对象 + 内容寻址天然保证同版本同字节），flags 是按账号计算的结果，没有这层保护。

### 三个失效来源，逐个堵

| 来源 | 堵法 |
|---|---|
| 数据库回滚 / 备份恢复 | 分配点持久化单调高水位，与规则集存储同一事务边界；恢复后取 `max(恢复值, 高水位)` 强制跳号；「版本号未倒退」列为恢复演练必检项 |
| 多区域发布传播时延 | 钉死单一全局序列，区域差异降格为传播时延；运维 SLO「新批次须在窗口 T 内在全部区域可见」，窗口内客户端观测到更小版本是**已知良性态**（不拉 + 告警 + 按会话去重上报）。T 的数值待 `04` 的多区域一致性答定 |
| 手工改规则（绕过发布动作） | **规则集不可变**：无原地编辑路径。可选加固：内容指纹与版本绑定，同版本不同指纹即服务端告警（**指纹不下发**，ADR-0002 的载荷边界） |

**推论一条现在就能定**（不裁决缓存层是否引入）：若引入按账号的解析结果缓存，**缓存键必须含 `flagsVersion`**、不得跨版本复用。只按 `accountId` 缓存时，版本已增大而结果仍是旧的 ⇒ 客户端认为「已同步到最新」⇒ 此后等值不拉 ⇒ **这一批秒关对该账号永不生效**。

### 运营兑现：规则集不可变版本化 + 留痕四项

flags 发布的是**规则集**（端点按账号解析它得到 `disabledIds`），不是静态对象。O1–O7 落 `operations/_index.md`。留痕四项**缺一不可**：操作者 · RFC 3339 UTC 时刻 · **`derivedFrom` 来源版本** · 变更摘要与生效范围。理由：flags 是**唯一一条能绕过发版直接改变玩家可见内容**的通道；而 `derivedFrom` 是「回滚 = 以历史规则内容发布更大版本」能被机读核对的唯一凭据。

**报文层零成本**：不新增任何字段、`flagsSchema` 不提升、客户端零改动。

## Clarifications（interview 产物）

五项取向 + 两项合并 interview 新增项已于 08-23 批量评审裁决，本次照裁决落笔：

- 取值空间与来源 → **单一全局递增计数 + 持久化高水位**（时间戳派生把单调性押在服务端时钟上且无法表达同一时刻两批发布；「不在契约里约束来源」则条款不可核对，实现时按区域计数也不违反字面）。
- 多区域一致性口径 → **全局单一序列 + 允许传播窗口 T**（跨区读会让某区域故障即全球 flags 不可用；按区域独立序列须下发区域标识，泄漏区域概念给客户端）。
- 条款落笔位置 → **把「服务端保证」重构为两组小标题**（overlay 分发 · flags 通道），并**同批把 `contentVersion` 严格单调那条提上来**。理由：那一节是后端实现者唯一会当成义务清单读的地方，两条单调纪律都不在里面正是本次欠账的根因；重构一次即根治。**位置迁移不改 ADR 候选①的内容。**
- 历史规则集保留期 → **永久保留**（体量极小，与收据幂等窗口的同形取舍一致；「能回指到任意历史版本」正是回滚即前滚的输入面）。
- ADR 落点 → **新开一条**（ADR 候选④），不泛化改写 ADR 候选①——那条的「内容寻址 ⇒ 前滚零成本」对 flags 不成立。
- 审计留痕在哪一题定案 → **在本题**，采纳四项最低要求（脱离本题，`derivedFrom` 就失去判据）。
- 契约正文里写死的封闭计数 → **统一消掉**（与分片 A 同源；「三条，仅此三条」改为两组各自封闭的表述）。

## 客户端侧影响

**条款本身对客户端零改动**（无新增字段、`flagsSchema` 不提升）——客户端已按本条款成立的前提落笔完毕，本次是补上它所依赖的那一半。

**但本次连带发现客户端一处缺口，已同批在对侧落笔**：客户端的单调闸只挂在 `X-Flags-Version` **头**的观测处，`GET /v1/content/flags` **应答体**里的 `flagsVersion` 是否也过同一道闸未明写；在传播窗口内设备可能拉回一批版本更小的 flags，若被应用则被秒关的内容当场复活。对侧半见 `game-design-documents/handoffs/2026-08-23-flags-version-client-gate.md`。**本库不代为改客户端规则**；后端侧能做的缓解已在传播窗口 SLO 与缓存键含版本里。
