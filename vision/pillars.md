# Pillars — 后端的设计支柱

> 取舍发生冲突时据以裁决的少数几条原则。它们**由客户端侧的既定决定推出**，不是独立发明的方向。
> Source: `game-design-documents/decisions/ADR-0003-online-cloud-authority.md`、`game-design-documents/handoffs/2026-08-09-sync-revision-cas-and-immediate-flush-nonblocking.md`。

## 1. 云端是权威，但不是玩法的执行者

后端持有进度的最终解释权（冲突以云端为准），但**不重跑玩法**。它校验、排序、存储，不模拟战斗。这条决定了后端的复杂度上限，也决定了防作弊只能靠「可复算的少数关键掷骰 + 风控」，而非全量服务端验算。

## 2. 弱网优先：幂等重于优雅

移动网络下「请求已达、响应丢失」是常态而非异常。协议的每一处写入都必须能被安全重放——幂等（`pushId`）与 CAS（`baseRevision`）是承重设计，不是优化项。宁可协议更啰嗦，也不能让一次丢失的响应吞掉玩家进度。

## 3. 契约单点定义

客户端与后端唯一的耦合点是协议。它必须有**一个**事实来源（`contracts/`），两侧都从它派生，任何一侧都不得私自扩展报文。契约的变更是跨库事件，需要两侧的 handoff 各记一笔。

## 4. 不阻塞玩家

同步是后台行为。除鉴权失效等硬闸门外，网络状况不得让玩家在事件推进中等待——客户端侧已定「立即 flush · 非阻塞」，后端的延迟预算与降级设计必须与之相容。

## 5. 线上可干预

内容以 overlay 热更、条目带 `ContentEnabled` 秒关开关。后端要保证**改数值 / 关条目不需要发版**，这优先于「跨版本可复现」——后者已被明确放弃。
