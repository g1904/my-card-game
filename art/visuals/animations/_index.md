# 动画（Animations）—— 占位

**视觉的子分区**：动画是**让视觉资产动起来**，与静态插画同属一条视觉线（同一套基调、色彩与技术约束），故落在 `visuals/` 之内而非与之并列。

**本节尚未设计。** 会有一些动画，但**先咨询专业人士，再充实本节**——不预设形态，避免现在拍脑袋定下的东西日后全部返工。

## 已知的

- **继承 `../art-direction.md`**（视觉总方向）：基调、色彩、光照与构图约束对动画同样成立——动画不另起一套视觉语言。
- **不走 AI 生成流水线**（至少目前）。静态视觉的三段流水线（vision + 参考 → AI 写 guide → 投喂 Midjourney）**不适用于动画**，故本分区**不设 `guides/`**。
- 继承 `../../_index.md` 的技术约束：**GL Compatibility** 渲染器（着色器 / 粒子受限）、竖屏、手机可读性。
- **战斗外的演出默认允许跳过 / 快进；战斗内的结算演出不设玩家侧跳过控件**（后者权威：`decisions/ADR-0086-lifo-resolution-and-combat-log.md` 与 `ux/combat-ux.md`「结算演出的节奏」）。「逐步可见」的论证前提——敌人回合是玩家获取动态情报的唯一时刻——在战斗外不成立：UI 转场与立绘动效不承载任何玩家需要读取的动态情报，而轮回制下同一段转场会被重复观看数十次，不可跳过会直接侵蚀 `vision/scope.md` 的篇章时长预算。

Source: `handoffs/2026-09-06-stale-wording-roundup.md`

## 待决问题

> 本节全部条目**待咨询专业人士后确定**——不预设形态，避免现在拍脑袋定下的东西日后全部返工。

- **范围：** 卡牌打出 / 结算特效、立绘动效、UI 转场、战斗反馈动画——这四类分属完全不同的技术路径，不应笼统当成一件事。
- **技术载体：** Godot `AnimationPlayer` / 骨骼动画（Spine / Godot Skeleton2D）/ 粒子 / shader / 序列帧，各自的成本与 GL Compatibility 兼容性。
- **制作方式：** 自制、外包，还是工具生成。
- **与战斗节奏的关系：** 动画时长直接影响一局 10 回合的实际时长（`vision/scope.md` 的篇章目标时长是硬预算）。**战斗内的结算演出没有玩家侧的跳过控件**——「逐步可见」是硬要求，时长由「3× 加速 + 超 4 步压到 0.2 s + 敌人回合总时长 ≤ 4 s」三重护栏收敛（权威：`decisions/ADR-0086-lifo-resolution-and-combat-log.md` 与 `ux/combat-ux.md`「结算演出的节奏」，**本节不重复陈述、也不得与之相抵**）。⇒ 本节待定的是**在该护栏内**每类动画的时长上界与缓动，不是「能否跳过」。

## 结构（待本节开工时立起）

预计需要一份 `animation-direction.md`（动效原则：时长、缓动、**战斗外演出的跳过策略**——含战斗外跳过控件的统一形态：触点、是否记忆偏好；战斗内不可跳过是既定边界，见上）与逐条动画的规格；**制作流程与静态视觉不同，结构须另行设计——不要在咨询之前照抄 `guides/` 那一套。**
